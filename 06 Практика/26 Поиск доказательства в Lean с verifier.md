# Практика 26. Поиск доказательства в Lean с verifier

## Цель

Постройте небольшой prover loop, в котором модель или детерминированный baseline
видит текущее состояние доказательства, извлекает только доступные посылки,
предлагает tactic, исполняет её в Lean и использует новое состояние или ошибку
для следующего шага. Единственным положительным исходом считается proof term,
принятый kernel-ом в закреплённом окружении.

Практика соединяет механизм LeanDojo/ReProver с управлением историей и
backtracking из COPRA. Она опирается на лекции 8–11
[Berkeley Advanced LLM Agents](https://rdi.berkeley.edu/adv-llm-agents/sp25),
но не воспроизводит официальное задание курса.

## 1. Зафиксировать формальную среду

Создайте отдельный Lean project и закрепите:

- версию Lean и `lake`;
- commit Mathlib или другого набора библиотек;
- список импортов для каждого theorem file;
- хэш исходного проекта до запуска;
- предел времени, памяти, шагов и числа ветвей поиска.

Начните с одного утверждения из примера ниже. Для полного сравнительного
эксперимента подготовьте не менее двенадцати теорем: арифметика, списки, конечные
множества и одна цепочка из вспомогательной леммы. Этот расширенный набор нужно
составить самостоятельно; готового датасета из двенадцати задач здесь нет.
Разделяйте теоремы на обучающую, разработческую и тестовую части до генерации
доказательств. Готовые тестовые доказательства и леммы, появившиеся после
зафиксированной границы доступных знаний, не должны попадать в поисковый индекс.

### Первый запуск: ошибочная tactic и исправленное доказательство

Этот небольшой пример проверяет установленный Lean, обработку ошибки и повторную
проверку результата. Он не требует GPU, модели или Mathlib. Установите
[Lean 4.19.0](https://github.com/leanprover/lean4/releases/tag/v4.19.0)
через Elan либо официальный архив для своей ОС. Создайте пустой каталог проекта
и сохраните в нём следующие четыре файла. Формат проекта и команда `lake env`
описаны в [документации Lake 4.19](https://lean-lang.org/doc/reference/4.19.0/Build-Tools-and-Distribution/Lake/).

`lean-toolchain`:

```text
leanprover/lean4:v4.19.0
```

`lakefile.toml`:

```toml
name = "bookvar_lean_smoke"
version = "0.1.0"
```

`Bad.lean` — попытка сослаться на несуществующую лемму:

```lean
-- bookvar: lean-bad
theorem add_zero_right (n : Nat) : n + 0 = n := by
  exact missing_lemma
```

`Good.lean` — то же утверждение с корректным доказательством:

```lean
-- bookvar: lean-good
theorem add_zero_right (n : Nat) : n + 0 = n := by
  rfl
```

Из каталога проекта выполните команды по отдельности:

```bash
lake env lean --version
lake env lean Bad.lean
lake env lean Good.lean
lake env lean Good.lean
```

Проверьте, что первая команда сообщает версию 4.19.0. `Bad.lean` завершится с
ненулевым кодом и ошибкой `unknown identifier 'missing_lemma'`. Оба запуска
`Good.lean` должны завершиться с кодом 0 без ошибки доказательства. Встроенное
определение сложения натуральных чисел сводит `n + 0` к `n`, поэтому `rfl`
достаточно: обе стороны равенства вычислительно совпадают. Здесь не нужны ни
извлечённые посылки, ни новая аксиома.

Каждая команда запускает отдельный процесс Lean: неудачная попытка не изменяет
следующую. Сохраните statement, версии, содержимое файлов, коды возврата и вывод
трёх проверок. Получится простая траектория «неизвестная лемма → отказ → `rfl`
→ принятие → повторное принятие». Это проверка вашего окружения, а не результат
работы LLM и не реализация интерактивного proof-state API. Дальше замените
заранее заданные две tactic предложениями модели, сохранив неизменным
утверждение и способ окончательной проверки.

## 2. Отделить autoformalization от proving

Для основной части входом служит уже формальное утверждение:

```lean
theorem add_zero_right (n : Nat) : n + 0 = n := by
  -- proof hole
```

Если вы добавляете перевод естественного текста в Lean, оценивайте его отдельно.
Скомпилировавшееся утверждение может быть слабее исходной задачи или вообще
выражать другое свойство. Для autoformalization нужны пары эквивалентных и
неэквивалентных формулировок, ручная проверка смыслового соответствия и отдельная
метрика; kernel подтверждает лишь корректность proof term относительно
предъявленного statement.

Три разрыва — формулировка theorem, шаги proof и смысловая эквивалентность —
разобраны на
[слайдах 7–31 лекции 9](https://rdi.berkeley.edu/adv-llm-agents/slides/mathverification.pdf#page=7)
и в первичной работе
[Autoformalization with Large Language Models](https://arxiv.org/abs/2205.12615).

## 3. Реализовать минимальный интерфейс Lean

Harness должен предоставлять узкие операции:

```python
reset_theorem(theorem_id) -> ProofState
list_accessible_premises(state) -> list[Premise]
apply_tactic(state_id, tactic, timeout_ms) -> TacticResult
check_completed_proof(theorem_id, proof_text) -> KernelResult
```

`TacticResult` содержит новый `state_id`, goals, messages, elapsed time и один из
статусов `progress`, `no_progress`, `error`, `solved`, `timeout`. Полный файл и
произвольный shell модели недоступны. Каждое состояние получает устойчивый хэш,
чтобы обнаружить цикл и не исполнять одну и ту же tactic бесконечно.

Один переход `proof state → tactic → kernel response` показан на
[слайдах 14–22 лекции 8](https://rdi.berkeley.edu/adv-llm-agents/slides/alphaproof.pdf#page=14).

## 4. Построить индекс только доступных посылок

LeanDojo извлекает из репозитория состояния доказательств и информацию о том,
какие premises доступны в данной позиции. Повторите это ограничение на своём
проекте: индексируйте имя, тип, namespace, импорт и положение определения, но не
позволяйте retriever-у видеть теорему из будущего файла или скрытого тестового
решения.

Для каждого goal сохраните top-k, scores и метку того, встретилась ли посылка в
эталонном proof. Сравните:

1. `state_only` — предложение tactic без retrieval;
2. `retrieval` — то же предложение с top-k доступных premises;
3. `oracle_premises` — эталонные premises без готового proof term, только как
   диагностическую верхнюю границу.

Работа [LeanDojo](https://arxiv.org/abs/2306.15626) описывает ReProver,
hard negatives и benchmark из 98 734 теорем. Это контекст источника, а не размер
обязательного локального эксперимента. Pipeline курса представлен на
[слайдах 43–55 лекции 9](https://rdi.berkeley.edu/adv-llm-agents/slides/mathverification.pdf#page=43).

## 5. Добавить stateful search и backtracking

Поддерживайте явный стек ветвей. Узел поиска содержит theorem id, хэш proof
state, tactic prefix, доступные premises, предложенные actions и причины их
отклонения. После `error` или `no_progress` агент возвращается к последнему узлу
с неиспробованной tactic; после повторного state hash ветвь закрывается как цикл.

Например, для исходной цели `n + 0 = n` интерфейс может различать три исхода:

```text
n : Nat ⊢ n + 0 = n
  ├─ exact missing_lemma → error: неизвестная лемма
  ├─ skip                → no_progress: цель не изменилась
  └─ rfl                 → solved: целей не осталось
```

Здесь показаны переходы предполагаемого интерактивного интерфейса. В стартовом
примере целый файл проверяется отдельным процессом, поэтому оставленная после
`skip` цель дала бы ошибку незавершённого доказательства, а не отдельный статус API.

История в prompt не обязана содержать все ошибки. Сохраняйте текущий proof
state, выбранный путь, краткий список запрещённых повторов и релевантные
diagnostics. Такой выбранный контекст и backtracking составляют основу
[COPRA](https://arxiv.org/abs/2310.04353); механизм разобран на
[слайдах 14–24 лекции 11](https://rdi.berkeley.edu/adv-llm-agents/slides/swarat.pdf#page=14).

## 6. Сравнить монолитное и модульное доказательство

Добавьте четвёртый вариант `draft_sketch_prove`. Сначала модель пишет короткий
неформальный план, затем превращает его в Lean sketch с именованными holes, после
чего каждый hole решается отдельно тем же prover loop. Готовым считается только
файл без `sorry`, `admit` и незакрытых goals.

Этот вариант проверяет гипотезу, что высокоуровневый план помогает декомпозиции;
он не получает дополнительный evaluation budget. Сравнивайте при одинаковом
числе model calls, tactic executions и общем timeout. Разделение draft, sketch и
prove описано в [Draft, Sketch, and Prove](https://arxiv.org/abs/2210.12283) и на
[слайдах 61–69 лекции 10](https://rdi.berkeley.edu/adv-llm-agents/slides/welleck2025_berkeley_bridging.pdf#page=61).

## 7. Измерить не только число доказанных теорем

Для каждого варианта и seed публикуйте:

- `pass@1` и число теорем, доказанных хотя бы раз при фиксированном числе
  попыток;
- долю корректно восстановленных premises и recall@k retrieval-а;
- tactic error, timeout, no-progress и repeated-state rates;
- число kernel calls, развернутых узлов, глубину и время до первого proof;
- длину принятого proof term и наличие запрещённых placeholders;
- результаты по theorem difficulty и объёму доступного контекста.

Единица попытки для `pass@k` — **полный запуск поиска с исходного утверждения**
при одной фиксированной политике и бюджете. Для каждой теоремы выполните $n$
независимых таких запусков, из которых $c$ получили принятое доказательство.
При $1\le k\le n$ оценка имеет вид

$$
\widehat{\mathrm{pass@}k}
=1-\frac{\binom{n-c}{k}}{\binom{n}{k}}.
$$

Если $n-c<k$, числитель равен нулю. Усредняйте оценку по теоремам, а не по
узлам дерева. Например, при $n=5$, $c=2$, $k=2$ получаем
$1-\binom{3}{2}/\binom{5}{2}=0.7$. Эта комбинаторная оценка используется в
[Evaluating Large Language Models Trained on Code](https://arxiv.org/abs/2107.03374).

Адаптивные ветви внутри одного поиска зависимы: нельзя выдать пять проверенных
tactic за пять независимых запусков и подставить их в формулу. При одном
stateful search сообщайте долю доказанных теорем при его бюджете, число узлов
и вызовов Lean. Повтор детерминированного запуска из примера выше подтверждает
воспроизводимость проверки, но не создаёт независимые сэмплы для оценки успеха.
Успех retrieval-а и успех prover-а также остаются разными метриками.

## 8. Разобрать одну траекторию целиком

В отчёте покажите не менее одного доказательства с первой неудачной tactic до
kernel-accepted результата. Для каждого шага укажите goals до и после,
retrieved premises, точный ответ Lean и причину следующего выбора. Отдельно
покажите false lead: синтаксически допустимую premise или tactic, которая не
приближает доказательство.

Этот разбор важнее набора скриншотов. Он позволяет проверить, что модель
использовала обратную связь prover-а, а не получила готовое решение из индекса.

## Критерии зачёта

1. окружение и theorem split закреплены хэшами;
2. test proof terms недоступны retriever-у и модели;
3. все принятые решения повторно проходят `lake env lean` в чистом процессе;
4. ни одно решение не содержит `sorry`, `admit`, axioms, добавленных участником,
   или изменения statement;
5. состояния и diagnostics сохранены для каждой tactic;
6. циклы и timeout завершают ветвь детерминированно;
7. варианты сравниваются при одинаковом бюджете;
8. autoformalization, если включена, оценивается отдельно от proving;
9. evidence bundle проходит проверку contract-а.

## Что сдаётся

- закреплённый Lean project manifest и theorem split;
- индекс доступных premises с provenance;
- `attempts.jsonl`, `states.jsonl`, `retrieval.jsonl`, `kernel_results.jsonl`;
- принятые `.lean`-файлы и stdout чистого повторного запуска;
- таблица метрик по вариантам и seeds;
- полный разбор одной успешной и одной неуспешной траектории;
- `report.md` с границами утверждений.
