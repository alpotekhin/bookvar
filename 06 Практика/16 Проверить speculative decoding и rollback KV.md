# Проверить speculative decoding и rollback KV

Полное условие и кодовые заготовки находятся в [[02 Areas/ML & DL/05 Источники/Courses/Efficient DL Systems/week09_inference_algorithms/homework/homework.ipynb|EDLS Week 9 homework notebook]], краткое описание — в [[02 Areas/ML & DL/05 Источники/Courses/Efficient DL Systems/week09_inference_algorithms/homework/README|README задания]].

Реализуйте draft generation, одну проверку target model и принятие/отклонение
tokens так, чтобы итоговое распределение соответствовало target decoding.
Сначала тестируйте детерминированный greedy случай, затем sampling на маленьком
словаре, где распределения можно посчитать напрямую.

## Выданный токен ещё не обязательно записан в KV-кэш

Для каждой модели храните отдельно длину уже выбранной последовательности
и длину префикса, для которого вычислены K/V. Новый токен получается из
логитов предыдущего прямого прохода; его собственные K/V появятся только
после обработки этого токена моделью.

Рассмотрим $k=3$. До раунда обе модели уже обработали префикс длины $n$,
а логиты для следующего токена сохранены. Draft предлагает `a,b,c`:
`a` выбирается из сохранённых логитов, обработка `a` даёт `b`, обработка `b`
даёт `c`. Поэтому к этому моменту draft-кэш содержит только `prefix,a,b`.
Target одним вызовом обрабатывает `a,b,c`; оценка для `a` была сохранена
до вызова, а новые логиты позволяют проверить `b,c` и выбрать дополнительный
токен, если все предложения приняты.

Пусть принимается `a`, но отклоняется `b`; вместо него выбирается поправочный
токен `r` по правилу speculative sampling (в greedy-режиме — выбор target).

| Момент | Подтверждённый выход | K/V target | K/V draft |
|---|---|---|---|
| Начало | `prefix` — $n$ | `prefix` — $n$ | `prefix` — $n$ |
| Draft предложил `a,b,c` | пока `prefix` | $n$ | `prefix,a,b` — $n+2$ |
| Target проверил три предложения | пока `prefix` | `prefix,a,b,c` — $n+3$ | $n+2$ |
| Принято `a`, выбран `r`, отброшены лишние K/V | `prefix,a,r` — $n+2$ | `prefix,a` — $n+1$ | `prefix,a` — $n+1$ |
| Обе модели обработали `r` | $n+2$ | `prefix,a,r` — $n+2$ | `prefix,a,r` — $n+2$ |

Последняя строка может выполняться отдельным вызовом или внутри следующего
раунда. Нельзя увеличивать счётчик материализованных K/V лишь потому, что
`r` уже отправлен пользователю. Устаревшие логиты для отвергнутого продолжения
тоже нужно отбросить.

Отдельно проверьте принятие всех трёх предложений. После выдачи `a,b,c` и
дополнительного токена `z` длина выхода равна $n+4$, target-кэша — $n+3$,
draft-кэша в описанной реализации — $n+2$. Чтобы полностью синхронизировать
их с выходом, target обрабатывает `z`, а draft — `c` и `z`. Реализация,
которая заранее обрабатывает последний draft-токен, имеет другие промежуточные
счётчики; подпишите это отличие, а не переносите таблицу без проверки.

Добавьте тесты трёх случаев: отклонение первого предложения, частичное
принятие и принятие всех предложений. После синхронизации сравните следующий
выход и содержимое действительного префикса кэша с обычным декодированием.
Для sampling сравнивайте распределения, а не требуйте одинаковых строк от
одного seed: алгоритмы расходуют случайные числа по-разному.

Измерьте acceptance length, число target forward passes, tokens/s, TPOT и peak
KV memory при разных $k$, draft models и типах prompts. Ускорение объясняйте
через saved target invocations с учётом стоимости draft и verification; низкая
acceptance rate должна проявиться как отсутствие выигрыша.
