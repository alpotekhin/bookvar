# Реализовать ring all-reduce

Работа следует [[02 Areas/ML & DL/05 Источники/Courses/Efficient DL Systems/week03_data_parallel/practice.ipynb|EDLS Week 3 practice notebook]] и [[02 Areas/ML & DL/05 Источники/Courses/Efficient DL Systems/week03_data_parallel/homework/README|исходному homework]]. Теория collectives целиком доступна в [[02 Areas/ML & DL/05 Источники/Courses/Harvard ML Systems/vol2/collective_communication|Harvard CS249r — Collective Communication]].

Сначала проверьте алгоритм локально: запустите $p$ CPU-процессов с backend
Gloo и разбейте тензор на $p$ частей. Реализуйте reduce-scatter и all-gather
через обмен сообщениями, а после каждого шага записывайте, какая часть и
какая частичная сумма находятся у каждого rank. Для первой проверки достаточно
целых небольших значений, сумма которых известна заранее.

Локальный запуск проверяет обмен индексами, сумму и отсутствие зависаний.
Он **не измеряет** производительность многоузловой сети или NCCL. Измерения
задержки и пропускной способности выполняются отдельным этапом на целевой
топологии: укажите число машин, размещение процессов/GPU, backend и интерфейс
межсоединения. При отсутствии такого оборудования сдайте корректность на
CPU и явно оставьте сетевую производительность неизмеренной.

Сравните собственную реализацию с `torch.distributed.all_reduce`:

- correctness для разных размеров, dtype и числа ranks;
- latency для маленьких сообщений;
- effective bandwidth для больших;
- объём переданных данных на rank;
- поведение при неравномерном размере chunks.

Если выполняете этап с GPU, запустите также один шаг обучения DDP и найдите
на временной диаграмме группы градиентов и перекрытие обратного прохода с
обменами. Итог локального этапа — код, тесты и схема обменов ring; итог
измерительного этапа — график времени от размера сообщения и профиль DDP.

## Выполнить обмены в отдельных процессах

В [архиве лабораторий](/examples/runtime-labs-2026-10-29.zip) находятся
`Code/ring_collective_lab.py`, `Code/ddp_step_lab.py` и результаты запуска.
Распакуйте архив и выполняйте команды из его корневой папки. В репозитории
та же папка называется `06 Практика`.

```bash
uv run --with torch==2.14.1 --with numpy==2.3.5 \
  python Code/ring_collective_lab.py --output Results/ring.json
```

Скрипт создаёт настоящие Gloo-процессы и использует `isend`/`irecv`. У каждого
процесса есть собственный тензор. Для трёх процессов и пяти элементов начальные
векторы равны `[0,1,2,3,4]`, `[10,11,12,13,14]` и `[20,21,22,23,24]`.
Их сумма — `[30,33,36,39,42]`. Шесть позиций нужны для трёх равных блоков по
два элемента; последнюю позицию скрипт заполняет нулём и удаляет из результата.

*Harvard ML Systems Book contributors,
[Ring AllReduce](https://github.com/harvard-edge/cs249r_book/blob/45ecc8d82fcae70c149cdce550d3b3d3411df913/slides/vol2/06_collective_communication/images/ring-allreduce.svg),
CC BY-NC-SA 4.0. Исходный SVG без изменений. На рисунке четыре GPU; локальная
проверка ниже использует три CPU-процесса. Утверждение о пропускной способности
на рисунке относится к модели ring, а не к измерению нашей сети.*

Сравнение с tree на рисунке использует упрощённое дерево без сегментации:
на каждом уровне передаётся полное сообщение. Нижнее правило crossover —
эвристика источника, а не точная универсальная граница. Момент, когда ring
становится быстрее, зависит от алгоритма дерева, сегментации и параметров сети.

На первой фазе полученный блок прибавляется к локальному. После двух шагов
процесс 0 владеет полной суммой блока 1. На второй фазе он получает уже
просуммированные блоки; повторное сложение здесь испортило бы результат.
В сохранённой трассе процесса 0 видны все четыре обмена:

| Фаза и шаг | Отправленный блок | Полученный блок | Полученные значения | Блок после операции |
| --- | ---: | ---: | --- | --- |
| reduce-scatter, 0 | 0 | 2 | `[24,0]` | `[28,0]` |
| reduce-scatter, 1 | 2 | 1 | `[34,36]` | `[36,39]` |
| all-gather, 0 | 1 | 0 | `[30,33]` | `[30,33]` |
| all-gather, 1 | 0 | 2 | `[42,0]` | `[42,0]` |

Сначала запускаются отправка и приём, затем ожидание их завершения. Если все
процессы сначала вызовут блокирующую отправку и никто не начнёт приём,
кольцо может зависнуть. Размер сообщения в этой реализации одинаков на каждом
шаге благодаря дополнению нулями. Для $n$ элементов и $p$ процессов каждый
rank отправляет $2(p-1)\lceil n/p\rceil$ элементов. В примере это восемь,
включая передаваемые нули, а не только полезные пять элементов результата.

Проверка охватывает 2, 3 и 4 процесса, `int64` и `float32`, векторы длины 1,
$p$, $p+2$ и 17. Все 24 конфигурации, то есть 72 результата отдельных rank,
совпали и с аналитической суммой, и с `torch.distributed.all_reduce`.
Трассы находятся в `Results/runtime-2026-10-29/ring.json` внутри архива.

## Проверить усреднение градиентов DDP

```bash
uv run --with torch==2.14.1 --with numpy==2.3.5 \
  python -m torch.distributed.run --standalone --local-addr=127.0.0.1 \
  --nproc-per-node=2 Code/ddp_step_lab.py --backend gloo --output Results/ddp
```

Каждый rank считает MSE по четырём своим примерам; эталонная модель считает
MSE по объединённому batch из восьми примеров. DDP усредняет градиенты rank,
поэтому при одинаковых локальных размерах это градиент того же среднего loss.
Скрипт сравнивает градиенты до обновления и веса после одного SGD step.
На CPU максимальная абсолютная разница градиентов составила
$7.45\cdot10^{-9}$. Неравные локальные batch потребовали бы отдельно согласовать
веса локальных средних.

Для двух NVIDIA GPU замените `--backend gloo` на `--backend nccl`. Скрипт
проверяет число видимых устройств до инициализации группы; при их отсутствии
он завершает работу без файла результатов. CUDA-ветка подготовлена, но здесь
не исполнена. Она сохраняет CUDA-event duration одного малого all-reduce и
пики PyTorch allocator; такой тест не заменяет sweep размеров сообщений,
многоузловой benchmark или профиль перекрытия вычислений с обменами.
