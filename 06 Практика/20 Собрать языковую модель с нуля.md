# Capstone 1. Собрать языковую модель с нуля

Цель проекта — получить не просто уменьшающуюся функцию потерь, а проверяемую
цепочку от байтов исходного текста до логитов, контрольной точки и
сгенерированного продолжения. Проект основан на Stanford CS336 Assignment 1, но
эта страница не копирует решение: алгоритмы реализует студент, а Bookvar
фиксирует порядок работы, официальные интерфейсы и достаточный набор
подтверждений.

<a id="scope"></a>

## Что считается завершённой системой

Готовая работа включает byte-level BPE, токенизатор со служебными токенами и
потоковым кодированием, decoder-only Transformer, cross-entropy, AdamW,
разогрев и косинусное расписание, ограничение градиента, выбор пакетов,
сохранение и загрузку контрольной точки, обучающий цикл, декодирование и журнал
экспериментов. Компоненты собираются последовательно: сначала каждая
функция-переходник совпадает с ожидаемым интерфейсом, затем проходит весь набор
тестов, и лишь потом расходуется бюджет на обучение.

Проверки выполняются на трёх уровнях. Короткий запуск обнаруживает проблемы
окружения и ошибки исполнения на выбранном входе. Модульные тесты дополнительно
сравнивают операции с численными эталонами. Обучение до целевой проверочной
потери в заданном бюджете проверяет, как вместе работают данные, архитектура
и оптимизация. Успешный короткий запуск не заменяет две следующие проверки.

<a id="tokenizer-contract"></a>

## Этап 1. Байты, BPE и токенизатор

Сначала проверьте round-trip на пустой строке, ASCII, одном Unicode-символе,
многоязычной строке и служебных токенах. После этого реализуйте обучение BPE:
подсчёт соседних пар, детерминированное разрешение равных частот, объединение и сохранение словаря.
Последовательность важна — производительность бессмысленно оптимизировать, пока
Unicode и границы служебных токенов не корректны.

Команды для отдельных официальных тестов:

```bash
uv run pytest tests/test_train_bpe.py
uv run pytest tests/test_tokenizer.py
```

`cpu_local` ниже — рекомендуемый порядок локальной работы, **не готовая
конфигурация запуска или CLI-флаг**. Подготовьте собственный небольшой корпус
для отладки; обучающие счётчики BPE не собирайте по отложенной проверочной
части. Официальные тесты отдельно используют входы из `tests/fixtures/`.
Команды запуска этих тестов приведены выше, но реализацию токенизатора
нужно написать самостоятельно. Критерий handout для полного TinyStories BPE — не более 30 минут без
GPU и не более 30 GB RAM; отдельный speed test ожидает менее двух минут при
multiprocessing. Это верхние границы задания, а не универсальный ориентир скорости.

<a id="model-contract"></a>

## Этап 2. Модель от базовых операций к логитам

До реализации выпишите формы $[B,T]$, $[B,T,D]$, $[B,H,T,K]$,
$[B,H,T,T]$, $[B,T,F]$ и $[B,T,V]$. Затем идите по порядку зависимостей:

1. linear и embedding;
2. RMSNorm и SiLU/SwiGLU;
3. RoPE;
4. stable softmax и scaled dot-product attention;
5. causal multi-head self-attention;
6. pre-norm Transformer block;
7. полная Transformer LM.

```bash
uv run pytest -k "test_linear or test_embedding or test_rmsnorm or test_silu or test_swiglu"
uv run pytest -k "test_rope or test_scaled_dot_product_attention or test_multihead_self_attention"
uv run pytest -k "test_transformer_block or test_transformer_lm"
```

Эти команды выбирают существующие официальные тесты; они не задают реализацию.
Проверка усечённого входа особенно важна: заранее вычисленный кэш RoPE не должен
ограничивать корректный более короткий контекст.

<a id="training-contract"></a>

## Этап 3. Функция потерь, оптимизатор, данные и контрольная точка

Cross-entropy должна устойчиво работать с логитами, не создавая сначала
наивный `exp(logits)`. AdamW проверяется отдельно от расписания: раздельное
уменьшение весов не равно добавлению L2-штрафа в градиент Adam. Ограничение
градиента использует общую L2-норму всех градиентов, а не отдельное ограничение
каждого элемента.

```bash
uv run pytest tests/test_nn_utils.py tests/test_optimizer.py
uv run pytest tests/test_data.py tests/test_serialization.py
```

Проверка контрольной точки сильнее факта записи файла: после загрузки должны
восстановиться состояния модели и оптимизатора вместе с номером итерации, а
следующий шаг должен совпасть с непрерывным запуском при контролируемой
случайности.

Официальное задание не фиксирует имя команды обучения. Поэтому выбранную
команду нельзя выдавать за интерфейс Stanford: запишите её целиком в отчёт
вместе с конфигурацией, seed и `git status`. Перед полным запуском добейтесь
переобучения на одном пакете и проверьте сохранение с последующим возобновлением.

<a id="experiment-contract"></a>

## Два профиля исполнения

### `cpu_local`: корректность и дешёвая интеграция

Начальный исполняемый маршрут — команды `uv sync` и тематические
`uv run pytest` из разделов выше. До заполнения `tests/adapters.py` неудача
тестов ожидаема: это задания для реализации, а не поставляемое решение.
Для обучения на одном пакете создайте собственный training entrypoint
и запишите его команду; такого скрипта под именем `cpu_local` в архиве нет.

- device: CPU; MPS допустим как дополнительное измерение, но не как замена CPU
  unit suite;
- полный `uv run pytest`;
- BPE — на малом зафиксированном corpus/subset;
- короткое обучение — один пакет до явного снижения функции потерь;
- reduced TinyStories run — 40,960,000 tokens, если ресурс позволяет;
- ориентир курса для сокращённого запуска: проверочная потеря до `2.00`.

Авторы задания сообщают для своей реализации на M4 Max 36 GB около 1 ч 22 мин
на CPU и 36 мин на MPS для 40.96 млн токенов. Это наблюдение на одной машине, а
не критерий времени для вашей системы.

### `gpu_full`: результат в масштабе задания

- dataset: TinyStories;
- vocab size: 10,000;
- context length: 256;
- $D=512$, $F=1344$, $L=4$, $H=16$;
- total tokens: 327,680,000;
- цель курса: проверочная потеря на токен не выше `1.45`;
- ориентир авторов: примерно 20–30 минут на одном B200 для их реализации.

Абляции (без RMSNorm, post-norm, NoPE, SwiGLU→SiLU) запускаются только после
успешного базового прогона. Иначе меняются сразу две причины, и сравнение теряет смысл.
OWT и таблица результатов — расширение: они не отменяют обязательный базовый
прогон TinyStories и требуют отдельного вычислительного бюджета.

<a id="official-contract"></a>

## Официальные функции-переходники и тесты — граница совместимости

В `tests/adapters.py` закреплена 21 функция-переходник: linear, embedding, SwiGLU,
scaled-dot-product attention, MHA с/без RoPE, RoPE, block, LM, RMSNorm, SiLU,
batch sampling, softmax, cross-entropy, gradient clipping, AdamW class, cosine
schedule, save/load checkpoint, tokenizer и BPE training. Их точные Python-имена
и 48 тестовых функций перечислены в машиночитаемом файле требований и
автоматически сверяются с зафиксированным архивом.

Не меняйте тесты так, чтобы они принимали вашу реализацию.
Функция-переходник — тонкая граница между вашим API и ожидаемым API:
преобразование имён допустимо, изменение численной семантики — нет. Итоговая
проверка:

```bash
uv run pytest
```

Прохождение означает `exit code 0`, отсутствие skipped/xfail среди
перечисленных обязательных тестов и неизменённое дерево зафиксированных тестов.
Контракт рекурсивно хеширует не только `test_*.py`, но также `conftest.py`,
`common.py`, `_snapshots/` и `fixtures/`: изменение tolerance, эталонного
тензора или корпуса меняет смысл проверки не меньше, чем изменение самой
тестовой функции. Исключены только генерируемые кэши Python/pytest и `.DS_Store`;
точное правило записано рядом с hash в `stanford-cs336-a1.yml`.
Эта контрольная сумма проверяет **архивную копию курса**. В рабочей копии
студента тела `tests/adapters.py` должны измениться; их побитовое совпадение
с незаполненным шаблоном не является критерием сдачи. Неизменными остаются
проверки, входные примеры и численный смысл интерфейсов.

## Критерии прохождения и порядок остановки

`PASS cpu_local`:

1. ревизия совпадает с зафиксированным источником;
2. все 48 официальных тестов прошли без изменения тестов;
3. round-trip байтов и токенов, включая служебные токены, проходит;
4. переобучение на одном пакете снижает функцию потерь;
5. проверка сохранения и возобновления воспроизводит продолжение;
6. отчёт содержит все обязательные поля.

`PASS gpu_full` добавляет обработку ровно 327,680,000 токенов TinyStories и
проверочную потерю `≤ 1.45` при указанной базовой архитектуре. Сокращённая
локальная цель `≤ 2.00` не разрешает объявить полный профиль пройденным.

Немедленный `FAIL`: изменённые официальные тесты, fixtures или ожидаемые
сигнатуры и смысл функций-переходников; неизвестная ревизия источника;
NaN/Inf; утечка между
обучающей и проверочной выборками; потерянная конфигурация или неустановленный
набор данных; заявленная потеря без контрольной точки и исходной кривой; время
без описания оборудования и команды. При таком результате сначала
восстанавливают проверяемость, а не увеличивают вычисления.

Тела функций в `tests/adapters.py` нужно заполнить: они подключают вашу
реализацию к тестам. Запрет относится к подмене проверок и их интерфейсов,
а не к этой обязательной части работы.

После базового прогона выберите одну абляцию и до запуска письменно предскажите
знак изменения функции потерь, скорости и памяти. Сравнение считается
содержательным только при одинаковых данных, бюджете токенов и процедуре оценки.
Результат проекта — обученная модель и воспроизводимый эксперимент,
показывающий последствия одного выбранного изменения.

## Worked reference: tracing nanoGPT through an optimizer update

With gradient accumulation, several microbatches contribute to one update
of the model's parameters. A training script also samples data, evaluates a
held-out split, changes the learning rate, writes state, and decides when to
stop. Their order determines what a logged loss or saved iteration means.

Andrej Karpathy's
[nanoGPT, revision 3adf61e1](https://github.com/karpathy/nanoGPT/tree/3adf61e154c3fe3fca428ad6bc3818b27a3b8291)
provides a compact working implementation. The source files and quoted
excerpts below retain their original English and
[MIT notice](/licenses/nanogpt-3adf61e1-MIT.txt).
The local packet is `05 Источники/Originals/nanogpt-2026-10-30`.

This is a worked reference alongside the assignment above. It does not fill
the CS336 adapters or satisfy that assignment's 48 official tests. nanoGPT
uses learned positional embeddings, LayerNorm and GELU; the assignment asks
for RoPE, RMSNorm and SwiGLU. The shared next-token objective does not make
the implementations interchangeable.

### Text becomes a stream of targets

The published character preparer builds a sorted alphabet, maps characters
to integer IDs, splits the stream 90/10, and writes `train.bin`,
`val.bin` and `meta.pkl`. The arrays use `uint16`; the metadata preserves
the alphabet and both mappings. This is a character tokenizer, not a BPE
tokenizer. Its alphabet is constructed from the whole supplied text before
the split, so it should not be described as learning BPE merges on the
training split.

The loader samples a start index and takes two overlapping windows. For
the stream `[0,1,2,3,0,1]`, start 1 and length 3 give input `[1,2,3]`
and target `[2,3,0]`. The model receives three known input tokens; the
prediction after 3 is supervised by the following 0.

Original lines inside
[`get_batch`](https://github.com/karpathy/nanoGPT/blob/3adf61e154c3fe3fca428ad6bc3818b27a3b8291/train.py#L123-L125):

```python title="Original nanoGPT excerpt — MIT; surrounding function omitted"
    ix = torch.randint(len(data) - block_size, (batch_size,))
    x = torch.stack([torch.from_numpy((data[i:i+block_size]).astype(np.int64)) for i in ix])
    y = torch.stack([torch.from_numpy((data[i+1:i+1+block_size]).astype(np.int64)) for i in ix])
```

The conversion to `int64` supplies indices for the embedding lookup.
In `model.forward(idx, targets)`, logits and targets are flattened at
corresponding positions and cross-entropy is computed directly. The loader
has already shifted the targets. Applying another shift would train on the
token two positions ahead. The
[[00 Учебник/11 Pre-training и Scaling/42 Next-token prediction#Реализация без скрытых сдвигов|NTP implementation]]
uses a different interface: it accepts one full sequence and performs the
shift inside the loss function.

For a microbatch with two sequences of eight targets, the loss averages
16 predictions. The source ignores target ID `-1`, not ID 0.
In the character fixture below, 0 is a real newline character and contributes
to the loss. Changing a tokenizer's ID convention must not silently remove
its first vocabulary item from training.

### From microbatches to one update

For each accumulation cycle, the script computes a mean loss, divides it
by `gradient_accumulation_steps`, and backpropagates. It does not clear the
gradients between microbatches. With two microbatches of equal shape
`[2,8]`, one update therefore accounts for 32 target tokens.

Original update order in
[`train.py`](https://github.com/karpathy/nanoGPT/blob/3adf61e154c3fe3fca428ad6bc3818b27a3b8291/train.py#L306-L314):

```python title="Original nanoGPT excerpt — MIT; preceding microbatch loop omitted"
    # clip the gradient
    if grad_clip != 0.0:
        scaler.unscale_(optimizer)
        torch.nn.utils.clip_grad_norm_(model.parameters(), grad_clip)
    # step the optimizer and scaler if training in fp16
    scaler.step(optimizer)
    scaler.update()
    # flush the gradients as soon as we can, no need for this memory anymore
    optimizer.zero_grad(set_to_none=True)
```

For scaled FP16 gradients, clipping must operate on unscaled values.
The CPU fixture uses FP32 and a disabled scaler, so it checks the update
path without testing CUDA mixed precision. With dropout disabled and
identical data, its separate FP64 check compares the gradients of a full
`[4,8]` batch with two accumulated `[2,8]` microbatches. The largest
difference in the recorded run is about `1.25e-16`. That is a numerical
check under stated conditions, not a promise of bitwise equivalence for
arbitrary stochastic or distributed training.

The configuration variable for accumulation is adjusted when DDP starts.
The source default 40 is divided by the world size: eight replicas each
accumulate five local microbatches. The token count then includes all
replicas. Leaving 40 local microbatches on every replica would change
the global batch by a factor of eight. This CPU lab does not launch DDP;
the collectives and reduction assumptions are developed in
[[00 Учебник/11 Pre-training и Scaling/44 Distributed training и mixed precision|distributed training]].

The training-line loss also needs interpretation. After accumulation, the
source prints the final microbatch's scaled loss multiplied back by the
accumulation count. This recovers that microbatch's mean, not the mean of
all microbatches. If their means are 2 and 6, the printed value is 6 while
the combined mean is 4. The separate `estimate_loss` routine evaluates
multiple random batches in evaluation mode and averages them; it measures
another sample of the data at another point in the loop.

### Checkpoint contents and update boundaries

Evaluation and saving occur before the current iteration's update.
The checkpoint stores the model, optimizer, architecture arguments,
iteration number, evaluation value and configuration. It does not store
the random-number state, the already prefetched next batch, or the
GradScaler state.

The native execution below uses `max_iters=2`, evaluation every iteration
and `always_save_checkpoint=True`. The ordering is:

| Loop label | Completed updates at evaluation | Checkpoint written | Update executed afterwards |
|---|---:|---|---:|
| 0 | 0 | No: the source requires `iter_num > 0` | First |
| 1 | 1 | Weights and optimizer after one update | Second |
| 2 | 2 | Weights and optimizer after two updates | Third |

After the third update, the counter becomes 3 and the condition
`iter_num > max_iters` stops the process. Thus this particular run executes
three updates but saves the state after two. With 32 targets per update,
the process handles 96 training targets; the saved model has received 64.
Validation draws are separate from these counts. This is the behavior of
the pinned revision, not a convention that every training framework follows.

The second native experiment stops after writing iteration 1, then restarts
with `init_from=resume` and continues to a saved iteration 2. Both its
checkpoint and the uninterrupted checkpoint contain two AdamW steps, yet
their weights differ by up to approximately `0.00172` in this fixture.
Restoring parameters and optimizer moments resumes optimization, but the
source does not restore the stochastic trajectory or the prefetched input.
Matching an iteration label is insufficient to prove exact continuation.

A separate resume implementation can save the necessary RNG, scaler and
data-loader state at a defined update boundary. Which state is necessary
depends on the sampler and distributed layout. The assignment's
controlled-continuation criterion above is stronger than merely loading
this nanoGPT checkpoint successfully.

### Generation does not use a KV cache in this implementation

With targets, the original model returns logits for every position.
Without targets, it projects only the last hidden state into the vocabulary:
the result has shape `[B,1,V]`. This saves the earlier vocabulary projections,
not the Transformer computation for the prefix.

The native `generate` method repeatedly runs the full available context,
scales its last logits by temperature, applies optional top-k filtering,
samples one ID, and appends it. A forward hook in the lab observes input
lengths `[6,7,8,8,8]` when five tokens are generated from a six-token prefix
with an eight-position context. After the window fills, the source keeps
the last eight IDs and recomputes them with positions starting at zero.
That is an explicit cropped-context algorithm, not exact KV-cached
generation beyond a learned position table. Compare the distinct original
OpenAI cache contract in
[[00 Учебник/06 Encoder, Decoder и Encoder-Decoder/05 GPT-2 — zero-shot через язык#Сохранение ключей и значений|GPT-2]].

The member named `flash` only tests whether PyTorch exposes
`scaled_dot_product_attention`. It does not identify the kernel selected
for a particular call. The numerical check forces PyTorch's math backend
on CPU while this member is still `True`. Backend selection, dropout and
input limitations are documented in
[PyTorch SDPA](https://docs.pytorch.org/docs/2.15/generated/torch.nn.functional.scaled_dot_product_attention.html).
No CUDA FlashAttention speedup is measured here.

### Run the complete small reference

From the Bookvar repository root, after installing the listed dependencies:

```bash
uv run --offline --with torch==2.14.1 --with numpy==2.3.5 \
  --with requests==2.32.5 --with tiktoken==0.12.0 \
  python '06 Практика/Code/nanogpt_reference_lab.py' \
  --output '06 Практика/Results/nanogpt-2026-10-30/reference.json'
```

The script copies the pinned upstream files into a temporary directory and
runs them unchanged. It supplies a local 2048-character, four-symbol stream,
so the preparer does not fetch Shakespeare. It then runs two fresh training
processes, one resumed process, and the original sampling program. The
`meta.pkl` route avoids fetching a BPE vocabulary or pretrained weights.
Temporary corpora and checkpoints are removed after their contents have
been checked.

The saved JSON records 1843 training IDs, 205 validation IDs, a 6784-parameter
native model, a 110,392-byte temporary checkpoint, and the original
program's generated IDs `[2,1,1,1,1]`: the letter `A` followed by four spaces.
This output is not evidence of useful language modeling. It checks that
text preparation, model construction, optimization, state restoration and
sampling are connected. A separate 6832-parameter, seven-token model checks
logit shapes, causal-prefix invariance and accumulation gradients.

The reported byte count and numerical errors belong to the recorded Python
3.14.3 / PyTorch 2.14.1 run; serialization size and rounding can differ in
another environment. The script checks structural and numerical conditions,
not those illustrative numbers as a speed or quality threshold.
The result does not establish `PASS cpu_local` or `PASS gpu_full` for CS336.

### nanoGPT, build-nanogpt and nanochat

The three repositories serve different purposes. nanoGPT is the implementation
traced above. The
[build-nanogpt lecture](https://github.com/karpathy/build-nanogpt)
constructs a GPT-2 reproduction in a recorded sequence of commits and an
accompanying video.
The [Zero to Hero GPT lesson](https://www.youtube.com/watch?v=kCc8FmEb1nY)
is another lesson, linked separately in nanoGPT's README.

The retained nanoGPT README marks the repository deprecated in November
2025 and points to
[nanochat](https://github.com/karpathy/nanochat/tree/92d63d4e8bb4df75c3b71618f31ddde2378b2bcd).
The latter's pinned README covers tokenization, pretraining, fine-tuning,
evaluation and inference; its GPT-2 speedrun criterion uses a DCLM CORE
score rather than simply matching nanoGPT's OpenWebText loss. Costs,
hardware, data and evaluation criteria must therefore accompany any
"time to GPT-2" comparison. No nanochat training or dollar-cost result
has been reproduced by this CPU reference.
