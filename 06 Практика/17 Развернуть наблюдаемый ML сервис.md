# Развернуть наблюдаемый ML-сервис

A request can fail before the model runs, wait for a worker, fail inside the
model, or finish successfully after the caller has given up. Counting only
predictions hides the first two cases. Returning HTTP 200 for every exception
hides the third. A useful service needs separate evidence for input validation,
readiness, request outcomes and time spent in each stage.

The working token-streaming service in
[[02 Areas/ML & DL/06 Практика/14a HTTP streaming и жизненный цикл запроса|practice 14a]]
already handles IDs, cancellation and terminal events. Here the examples from
[Efficient DL Systems, Week 7](https://github.com/mryab/efficient-dl-systems/tree/e632aa89ca9e6638d52e1b686095e7442faffbb0/week07_application_deployment)
show how to inspect a service, package it and observe it. Original code remains
English and unchanged; the explanations and explicitly marked corrections are
Bookvar additions. The course authors credit Alex Kosmos for this week's
lecture and seminar. The [complete course MIT notice](/licenses/edls-deployment-MIT.txt)
applies to the reproduced code.

## A passing smoke test can hide a broken prediction contract

The course starts with two small repositories. In
[smokers-repo/app.py](https://github.com/mryab/efficient-dl-systems/blob/e632aa89ca9e6638d52e1b686095e7442faffbb0/week07_application_deployment/00_basics/smokers-repo/app.py),
model loading happens during import; mutable global keywords and unseeded
randomness affect predictions; a broad exception handler returns
`{"is_toxic": false}`. The smoke test checks status 200 and the presence of the
response key. It does not establish that invalid input is rejected or that
the classification is correct.

For a neutral string with no keyword, the source compares a uniform random
number with 0.5. Roughly half the predictions are therefore toxic even though
the text has not changed. An invalid JSON body also returns 200 with a negative
classification. A caller cannot distinguish malformed input from a valid
non-toxic result. These outcomes follow directly from the source; the local
checker exercises both paths.

The comparison repository separates settings, model logic and the HTTP app.
Its complete application is:

<!-- BEGIN SOURCE: goodapp -->
```python
import threading
from typing import Optional

from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

from app.config import Settings
from app.model import ToxicityModel

import redis


class PredictRequest(BaseModel):
    text: str


class PredictResponse(BaseModel):
    is_toxic: bool


def create_app(settings: Optional[Settings] = None) -> FastAPI:
    settings = settings or Settings.from_env()
    app = FastAPI(title="Non-Smoker Repo")

    app.state.settings = settings
    app.state.model = ToxicityModel(
        seed=settings.random_seed,
        startup_delay_seconds=settings.model_startup_delay_seconds,
    )
    app.state.ready = False
    app.state.redis_client = None

    def _load_model() -> None:
        app.state.model.load()
        app.state.ready = True

    @app.on_event("startup")
    def on_startup() -> None:
        if settings.redis_url:
            app.state.redis_client = redis.Redis.from_url(
                settings.redis_url, decode_responses=True
            )
        thread = threading.Thread(target=_load_model, daemon=True)
        thread.start()

    @app.get("/health")
    def health() -> dict:
        return {"status": "ready" if app.state.ready else "not ready"}

    @app.post("/predict", response_model=PredictResponse)
    def predict(payload: PredictRequest) -> PredictResponse:
        if not app.state.ready:
            raise HTTPException(status_code=503, detail="Model is still loading.")

        is_toxic = app.state.model.predict(payload.text)

        if app.state.redis_client is not None:
            try:
                app.state.redis_client.incr("app_http_inference_count")
            except redis.RedisError:
                # Prediction should still succeed if metrics backend is unavailable.
                pass

        return PredictResponse(is_toxic=is_toxic)

    return app


app = create_app()
```
<!-- END SOURCE: goodapp -->

*EDLS course authors, [non-smokers-repo/app/main.py](https://github.com/mryab/efficient-dl-systems/blob/e632aa89ca9e6638d52e1b686095e7442faffbb0/week07_application_deployment/00_basics/non-smokers-repo/app/main.py),
MIT. Original file, including comments and the older startup-event API.*

The app creates its model once, starts loading in a background thread, and
keeps predictions unavailable until loading finishes. Pydantic rejects a list
where text is required with 422. A request during loading gets 503. Redis is
optional: failure to increment the demonstration counter does not invalidate
an otherwise successful prediction.

The source's `/health` endpoint still returns HTTP 200 with
`{"status": "not ready"}` while loading. A readiness probe that checks only the
status code would send traffic too early. A corrected probe needs a separate
endpoint returning 503 until ready, or a body-aware check. In practice 14a the
application does not start serving readiness before its lifespan initialization
succeeds. Neither approach makes an uninterruptible model call cancellable.

The model used by this baseline is deliberately small:

<!-- BEGIN SOURCE: model -->
```python
import random
import time


TOXIC_KEYWORDS = ("idiot", "stupid", "trash", "moron", "hate")


class ToxicityModel:
    def __init__(self, seed: int, startup_delay_seconds: float = 0.0) -> None:
        self._rng = random.Random(seed)
        self._startup_delay_seconds = startup_delay_seconds
        self._is_loaded = False

    @property
    def is_loaded(self) -> bool:
        return self._is_loaded

    def load(self) -> None:
        if self._startup_delay_seconds > 0:
            time.sleep(self._startup_delay_seconds)
        self._is_loaded = True

    def score(self, text: str) -> float:
        if not self._is_loaded:
            raise RuntimeError("Model is not loaded yet.")
        lowered = text.lower()
        hits = sum(1 for token in TOXIC_KEYWORDS if token in lowered)
        # Tiny deterministic jitter demonstrates seeded behavior in tests.
        return hits + (self._rng.random() * 0.0002)

    def predict(self, text: str) -> bool:
        return self.score(text) >= 1.0
```
<!-- END SOURCE: model -->

*EDLS course authors, [app/model.py](https://github.com/mryab/efficient-dl-systems/blob/e632aa89ca9e6638d52e1b686095e7442faffbb0/week07_application_deployment/00_basics/non-smokers-repo/app/model.py), MIT, complete original.*

The keyword test is substring matching, not tokenization: a hit can occur
inside a larger word. A fixed seed reproduces a sequence of random values, not
one constant score for a given input. With seed 7 the first jitter is
0.32383276483316237 × 0.0002 = 0.00006476655296663248. The original test expects
0.0000323832 and fails. The checked run reports four passes and this one
failure. Changing the expected value to the value computed from the source
fixes that test; the archived test itself remains unchanged.

Loading in a daemon thread also leaves a failure path: if load() raises,
ready stays false without an explicit failed-start state. No concurrency
limit or request deadline is implemented in this baseline. Its improved file
layout should not be mistaken for a complete production lifecycle.

## Package dependencies before frequently changing code

The first Dockerfile copies the whole build context before installing
dependencies:

RUN pip install --no-cache-dir -r requirements.txt

<!-- END SOURCE: baddocker -->

*EDLS course authors, [Dockerfile.bad](https://github.com/mryab/efficient-dl-systems/blob/e632aa89ca9e6638d52e1b686095e7442faffbb0/week07_application_deployment/00_basics/smokers-repo/Dockerfile.bad), MIT, complete original.*

Editing app.py changes the input to COPY. That invalidates this step and the
following dependency-install step, even when requirements.txt is unchanged.
The second Dockerfile separates dependency metadata from application code:

<!-- BEGIN SOURCE: gooddocker -->
```dockerfile
# Docker image is semi-pinned: tag is better than nothing but worse than SHA256 pin
FROM python:3.13-slim-bookworm

WORKDIR /app

# UV version is pinned - this is a good practice
COPY --from=ghcr.io/astral-sh/uv:0.10.4 /uv /uvx /bin/

# Cache-friendly: dependency metadata copied before application code.
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev

COPY app ./app

EXPOSE 8080

CMD ["uv", "run", "uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8080"]
```
<!-- END SOURCE: gooddocker -->

*EDLS course authors, [Dockerfile.good](https://github.com/mryab/efficient-dl-systems/blob/e632aa89ca9e6638d52e1b686095e7442faffbb0/week07_application_deployment/00_basics/non-smokers-repo/Dockerfile.good), MIT, complete original.*

Now an app-only edit reaches the later COPY app step. The earlier dependency
layer can be reused if its inputs and parent layers still match. The original
Docker illustration shows the same dependency: changing a COPY invalidates
later steps, while unchanged earlier steps can stay cached.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/deployment-2026-10-26/docker-cache-invalidated.png]]

*Docker, Inc., [Build cache](https://github.com/docker/docs/blob/419ecb47185bf05c83f3cfb7e995b82266046c03/content/manuals/build/cache/_index.md),
complete original PNG. [Apache-2.0](/licenses/docker-419ecb4-Apache-2.0.txt).
The illustration's ubuntu:latest is an example of layer dependencies, not a
recommendation to use a mutable base tag.*

The [cache invalidation rules](https://docs.docker.com/build/cache/invalidation/)
also explain why changing only a file's modification time does not invalidate
COPY, and why a cached RUN does not automatically refresh packages from a
remote repository. Cache reuse and reproducibility answer different questions.

The course's `pyproject.toml` declares dependency ranges; `uv.lock` records the
resolved versions. `uv sync --frozen` uses that lock without checking whether it
still matches `pyproject.toml`; `--locked` performs the consistency check instead
([uv, Locking and syncing](https://docs.astral.sh/uv/concepts/projects/sync/)).
The source pins the uv image to 0.10.4 but uses a Python base tag rather than an
immutable digest. It also runs `uv run` at container startup, which can perform
an environment check; a prepared image is not evidence that startup is offline.
For a reproducible deployment, record the source revision, lock hash, model
artifact hash, base-image digest and resulting image digest separately.

In the original Compose file, `app:8080` is a service address on `seminar_net`;
`8080:8080` publishes its port on the host. Redis is named `redis` inside that
network. `depends_on` expresses startup ordering here, not proof that Redis is
ready. The application already tolerates Redis counter failures. Do not expose
the demonstration's Redis port or model endpoint to an untrusted network.

## Keep the preprocessing contract with the model artifact

The separate [Python-server example](https://github.com/mryab/efficient-dl-systems/blob/e632aa89ca9e6638d52e1b686095e7442faffbb0/week07_application_deployment/01_python_server/server.py)
accepts a JSON field named data containing an already prepared tensor. Its
client, not the server, opens the image, resizes it, converts pixels to a tensor,
normalizes the three channels and inserts the batch dimension. For an input
pixel value x, normalization computes (x - mean[channel]) / std[channel]
after ToTensor has scaled the usual byte-valued RGB image to [0,1]. Sending
raw 0–255 pixel arrays to this endpoint bypasses that preprocessing and changes
the model input distribution without changing the JSON field name.

The original client uses Resize(224). With an integer size, the
[shorter edge becomes 224](https://docs.pytorch.org/vision/0.16/generated/torchvision.transforms.Resize.html),
so a non-square image does not become 224×224 automatically. It also does not
explicitly convert images to RGB. A service contract must state permitted
channel counts and shapes, normalization and payload limits; its schema cannot
stop at “JSON containing numbers.” The course server reconstructs a tensor
directly and does not implement those bounds.

The artifact-producing script is short enough to inspect in full:

<!-- BEGIN SOURCE: trace -->
```python
import torchvision.models as models
import torch


def main():
    vgg16 = models.vgg16(pretrained=True)

    example = torch.rand(1, 3, 224, 224)
    traced_script_module = torch.jit.trace(vgg16, example)
    traced_script_module.save("vgg16.pt")


if __name__ == "__main__":
    main()
```
<!-- END SOURCE: trace -->

*EDLS course authors, [train_model.py](https://github.com/mryab/efficient-dl-systems/blob/e632aa89ca9e6638d52e1b686095e7442faffbb0/week07_application_deployment/train_model.py), MIT, complete original.*

The script does not call `eval()` before tracing. VGG's dropout behavior depends
on training/evaluation mode, so an inference artifact needs evaluation mode
selected before tracing and a repeated-input check afterward. The corrective
adaptation would call `vgg16.eval()` before `torch.jit.trace`, then compare traced
and eager predictions on the declared input shapes. `eval()` and disabling
gradient tracking [serve different purposes](https://docs.pytorch.org/docs/2.14/generated/torch.nn.Module.html#torch.nn.Module.eval). These VGG checks have not been
executed here; the local metric test replaces the model, not its instrumentation.

## Follow a metric from the route to Grafana

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/deployment-2026-10-26/prometheus-architecture.svg]]

*The Prometheus Authors, [Overview](https://github.com/prometheus/docs/blob/3576591af32864770ad6ff73a14fc485f70afb73/docs/introduction/overview.md),
complete original SVG. [Apache-2.0](/licenses/prometheus-3576591-Apache-2.0.txt);
[original NOTICE](/licenses/prometheus-3576591-NOTICE.txt).*

In the diagram, instrumented jobs expose metrics and Prometheus pulls them.
Stored samples can be queried through its API; Grafana is one query client.
The course stack uses direct scraping, so the Pushgateway and Alertmanager
branches are not required for this example. A request can succeed while a
scrape fails: `up` measures target scrape availability, not prediction quality.

The complete instrumented source server is:

<!-- BEGIN SOURCE: metrics -->
```python
import json

import torch
from flask import Flask, request, jsonify
from prometheus_flask_exporter import PrometheusMetrics
from prometheus_client import Counter


app = Flask(__name__, static_url_path="")
metrics = PrometheusMetrics(app)
PREDICTION_COUNT = Counter("predictions_total", "Number of predictions", ["label"])

model = torch.jit.load('vgg16.pt')
with open('labels.json', 'r') as f:
    labels_raw = json.loads(f.read())
    labels = {int(index): value for index, value in enumerate(labels_raw)}


@app.route("/predict", methods=['POST'])
@metrics.gauge("api_in_progress", "requests in progress")
@metrics.counter("api_invocations_total", "number of invocations")
def predict():
    data = request.get_json(force=True)
    features = torch.tensor(data['data'])

    result = model(features).data.numpy().argmax()
    label = labels[result]

    PREDICTION_COUNT.labels(label=label).inc()

    return jsonify({
        "label": label
    })


if __name__ == '__main__':
    app.run(host='0.0.0.0', port=8080)
```
<!-- END SOURCE: metrics -->

*EDLS course authors, [03_metrics/server.py](https://github.com/mryab/efficient-dl-systems/blob/e632aa89ca9e6638d52e1b686095e7442faffbb0/week07_application_deployment/03_metrics/server.py), MIT, complete original.*

PREDICTION_COUNT increments only after classification succeeds.
api_invocations_total surrounds the route; api_in_progress rises while the
wrapped route runs and falls on exit, including an exception.
PrometheusMetrics(app) also exports HTTP request duration and status metrics.
A useful check sends three successful requests and one controlled model error:
the prediction counter increases by three, the invocation counter by four,
and in-progress returns to zero. The local source checker verifies those
outcomes with the actual Flask exporter and a stub model; it does not load VGG.

The source reads labels and weights from the current working directory.
Run the example from 03_metrics after preparing vgg16.pt, not from an arbitrary
repository directory. The preceding train_model.py traces a pretrained VGG16;
despite its filename, it does not train a new classifier. Preparing that
artifact can download pretrained weights. This chapter's instrumentation
checks deliberately avoid that download and do not measure model accuracy.

The app, telegraf and Prometheus targets use their container-network names.
Grafana queries `http://prom:9090` from its own container. From the host, the
published interfaces are `localhost:3000` for Grafana, `localhost:9090` for
Prometheus and `localhost:8080/metrics` for the app. The course README's claim
that both 3000 and 9090 open Grafana is incorrect.

The nginx job points to `nginx_metrics:9113`, but this Compose file defines
neither that exporter nor nginx. It will not become healthy merely because the
other targets work. Remove that job in an explicitly modified local copy or
add a correctly configured exporter; do not silently call the original stack
healthy. Telegraf collects CPU and memory visible to its own container
namespace; this configuration does not establish host-wide or GPU utilization.

The label dimension is bounded here by the classifier's fixed label set.
Putting request IDs, arbitrary input text or image URLs in metric labels would
create an unbounded series set. Keep request-level details in logs or traces,
without input content or credentials by default. The demonstration counter
does not by itself provide queue time, model time or token-stream TTFT.

## Read latency buckets before reporting p95

For four observed durations 0.05, 0.20, 0.40 and 0.80 seconds, classic histogram
boundaries 0.1, 0.3, 1.0 and +Inf produce cumulative counts 1, 2, 4 and 4.
The total count is four and the sum is 1.45 seconds. Two requests met a 300 ms
threshold, so the observed threshold fraction is 2/4. These are deterministic
example values, not service measurements.

For the exporter's classic histogram, an across-instance p95 query is:

```promql
histogram_quantile(
  0.95,
  sum by (le) (
    rate(flask_http_request_duration_seconds_bucket{path="/predict"}[5m])
  )
)
```

The bucket counts must be combined before estimating the quantile; averaging
replica p95 values does not reconstruct the pooled distribution.
The estimate is limited by bucket resolution. A boundary placed exactly at the
SLO threshold permits a direct threshold count. See
[Prometheus, Histograms and summaries](https://prometheus.io/docs/practices/histograms/);
the example uses classic histograms already exported by this pinned library,
not a claim that classic histograms are the only available type.

A rising prediction counter is not a request rate. For example, a counter
increase from 800 to 860 over 15 seconds is four events per second if no reset
occurred. PromQL rate handles counter resets; subtracting two samples manually
does not. To compare success and errors, retain status/outcome dimensions
instead of dividing the success-only prediction counter by itself.

## Separate image preparation from inference over gRPC

In the course's [microservice example](https://github.com/mryab/efficient-dl-systems/tree/e632aa89ca9e6638d52e1b686095e7442faffbb0/week07_application_deployment/04_microservices),
the public HTTP process fetches an image and runs preprocessing. A separate
gRPC server receives numeric data, runs the traced model and returns a label.
The wire contract is:

<!-- BEGIN SOURCE: proto -->
```protobuf
syntax = "proto3";
package inference;

service ImageClassifier {
  rpc Predict(ImageClassifierInput) returns (ImageClassifierOutput);
}

message ImageClassifierInput {
  repeated int32 shape = 2;
  repeated double data = 1;
}

message ImageClassifierOutput {
  string label = 1;
}
```
<!-- END SOURCE: proto -->

*EDLS course authors, [inference.proto](https://github.com/mryab/efficient-dl-systems/blob/e632aa89ca9e6638d52e1b686095e7442faffbb0/week07_application_deployment/04_microservices/protos/inference.proto), MIT, complete original.*

For a 1×3×224×224 tensor there are 150,528 elements. The repeated double field
uses 1,204,224 bytes for the numeric elements alone, before protobuf framing;
the model later converts them to float32, whose element storage is 602,112
bytes. Splitting processes does not remove serialization, transport or
allocation costs. With a batch dimension larger than one, the source's global
argmax would also need replacement by a per-example decision.

The shape field supplies dimensions, not validation: the inference server
reshapes the provided array without checking an allowed rank, shape or element
budget first. The HTTP process accepts arbitrary URLs and does not set an
application-specific download-size limit or gRPC deadline. Its thread pool has
five workers, but the executor's waiting queue is not bounded by that number.
The inference-side four-worker pool similarly does not prove bounded admission.

The `client-url.py` shortcut uses `image-server:9091`, although the image service
listens on 9090 inside Compose; 9091 is its host-published port. Use
`http://image-server:9090/...` from a sibling container. The Compose file mounts
`./imgs`, which is not included at that path in the pinned snapshot. The source
Dockerfile's `COPY protos/* /app/protos` also lacks a trailing slash even though
the generated command expects an include directory; an adaptation should
create `/app/protos/` explicitly before code generation.

The example therefore explains an RPC boundary but is not a ready internet
image-fetching service. A deployable adaptation needs URL/network restrictions,
download and shape bounds, deadlines, bounded admission and explicit error
mapping. A timeout at the HTTP boundary must also reach the downstream request;
otherwise work can continue after its caller has disconnected. The lifecycle
cases in practice 14a supply the local request-side example.

## Execute HTTP, gRPC, scraping and a bounded overload test

Download and extract the [runtime lab archive](/examples/runtime-labs-2026-10-29.zip).
With a running local Docker daemon, run from the archive root:

```bash
uv run --with grpcio==1.76.0 --with grpcio-tools==1.76.0 \
  python Code/run_observable_lab.py --output Results/service
```

This builds an application image and starts it beside Prometheus. Ports bind
only to `127.0.0.1`; the service and scraper use a run-specific Docker network.
The script removes only its own containers and network when the experiment
ends. Public image pulls use an isolated Docker configuration, without invoking
the user's registry credential helper. The archive includes the Dockerfile,
pinned Python dependencies, model artifact, service and load generator.

The service retains the course's protobuf message and RPC names. Its model is
an explicitly different fixture: a 3×3 identity linear classifier over three
channel means. Input `[0.1,0.7,0.2]` with shape `[1,3]` returns `green` over both
HTTP and gRPC. Loading and evaluating this small JSON artifact needs no VGG
download. It does not implement image preprocessing or establish vision-model
accuracy. A mismatched shape returns HTTP 400 or gRPC `INVALID_ARGUMENT`.

One worker executes predictions. Admission permits at most four requests in
the service, leaving at most three waiting; further arrivals receive HTTP 429
or gRPC `RESOURCE_EXHAUSTED`. Readiness returns 503 during the configured
two-second startup interval. Readiness, HTTP overload, and HTTP/gRPC input
validation were checked over actual network connections. The gRPC overload
mapping is implemented but was not exercised in this run.

The load fixture deliberately adds a 20 ms delay while the worker is occupied.
`bookvar_stage_seconds{stage="injected_delay"}` records it separately from
validation, queue wait, model execution and serialization. The arithmetic
classifier itself takes far less time. The delay creates a reproducible queue
exercise; treating it as measured neural-network compute would give a false
capacity claim.

Each run offers requests at fixed target intervals for two seconds, then drains
outstanding work. All 620 request records retain planned arrival, actual send,
completion, status and successful-response stage times. On the checked Docker
Desktop arm64 run:

| Target arrivals/s | Offered | Completed | Rejected | Successful p95 | Fraction of offered requests completing within 60 ms |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 10 | 20 | 20 | 0 | 34.9 ms | 1.00 |
| 100 | 200 | 91 | 109 | 96.7 ms | 0.01 |
| 200 | 400 | 95 | 305 | 92.1 ms | 0.005 |

At the two higher arrival rates the bounded queue rejects work. The slightly
lower successful p95 at 200 requests/s is not an improvement in service:
305 requests are rejected, and only 0.5% of offered requests meet the declared
completion threshold. Successful-only latency and offered-request goodput
describe different populations. The exact timings vary across machines and
runs; two seconds does not estimate a production p99 or maximum sustainable
LLM throughput.

Prometheus scrapes the actual container every second. The checker queries its

`Results/runtime-2026-10-29/service.json` preserves those responses, all request

fully locked supply chain; use the recorded image IDs to identify this run.
Grafana dashboards, VGG accuracy, distributed tracing, downstream cancellation
and CUDA serving remain outside this bounded transport experiment.

## Budget a release and an incident

A monitored service still needs a rule for allowing more traffic onto a new
version. The Harvard ML Systems laboratory
[[02 Areas/ML & DL/05 Источники/Courses/Harvard ML Systems/labs/vol2/lab_12_ops_scale|MLOps at Scale]]
connects four calculations: a monthly error budget, a canary's evidence and
exposure, lost work during an incident, and simultaneous release constraints.
The following walkthrough uses its original `cloud_fleet` scenario.
Source code and marked excerpts are by the Harvard ML Systems authors,
[pinned at 45ecc8d](https://github.com/harvard-edge/cs249r_book/blob/45ecc8d82fcae70c149cdce550d3b3d3411df913/labs/vol2/lab_12_ops_scale.py),
under [CC BY-NC-SA 4.0](https://github.com/harvard-edge/cs249r_book/blob/45ecc8d82fcae70c149cdce550d3b3d3411df913/LICENSE.md).
The numerical walkthrough and counterexamples below are Bookvar additions;
the complete source remains available in its original language.

These are scenario calculations. They do not measure the EDLS classifier
above or estimate the reliability of an actual fleet. In particular, the
lab assigns quality-loss coefficients, response factors and policy indices.
They let us inspect how the decisions depend on assumptions; they are not
empirically fitted laws.

### A. Availability, quality and incident count

The source's default period is 30 days, or 43,200 minutes. A time-based
99.9% availability target permits 0.1% of that period as unavailability:
43.2 minutes. The scenario then places three incidents in the period, each
with 25 minutes before detection and 40 more minutes of impact. Counting
each interval as full unavailability gives 3 × (25 + 40) = 195 minutes.
The spend is 195/43.2 = 4.514 times the budget.

<!-- source-excerpt: harvard-ops-budget-minutes -->
> Error-budget minutes = period minutes x (1 - SLO).
<!-- /source-excerpt -->

*Harvard ML Systems, Lab 12, Part A, “Math Peek / source model”.*

The same function tracks two other amounts. Quality starts at 94%, and the
permitted floor is 91%, giving a three-percentage-point allowance. The
source assigns 0.6 percentage points of loss per incident and another
0.02 percentage points per hour before detection. Its assumed quality loss
is therefore 3 × 0.6 + 3 × (25/60) × 0.02 = 1.825 percentage points.
The implied quality is 92.175%, above the floor. Finally, three incidents
use a count budget of three.

| Amount | Allowed | Spent | Fraction of budget | Passes? |
| --- | ---: | ---: | ---: | --- |
| Full unavailability | 43.2 min | 195 min | 4.514 | No |
| Quality loss | 3 percentage points | 1.825 percentage points | 0.6083 | Yes |
| Incident count | 3 incidents | 3 incidents | 1 | Yes |

Availability blocks release in this scenario even though the other two
constraints pass. Dividing each amount by its own budget permits a comparison
of relative spend; adding minutes to percentage points would not.

The 195-minute interpretation requires non-overlapping intervals of complete
unavailability. If only 10% of uniformly arriving eligible requests fail
during those intervals, a request-based SLO counts 19.5 equivalent full-outage
minutes, not 195. If traffic varies, count failed and eligible requests
directly. Overlapping incidents must not double-count the same outage. The
model's assigned quality loss likewise does not replace labeled evaluation:
the 92.175% result follows from the coefficients, not from predictions.

### B. Canary duration and exposure

At one million requests per hour, a 5% canary receives 50,000 requests per
hour. Gathering a required 10,000 candidate requests takes 0.2 hours,
or 12 minutes. Leaving the canary at 5% for the default two hours exposes
100,000 requests, below the source's budget of 400,000.

<!-- source-excerpt: harvard-ops-stage-time -->
> Chapter formula: `T_stage = n_samples_needed / (request_rate * p_stage)`.
<!-- /source-excerpt -->

*Harvard ML Systems, Lab 12, Part B, “Math Peek / source model”.*

With request rate $R$, candidate fraction $f$ and stage duration $T$,
the number of candidate requests is $RfT$. A fixed-duration stage must
collect at least $n$ requests and expose at most $B$:

$$
n\leq RfT\leq B.
$$

For positive $R$ and $T$, this gives the allowable fractions

$$
\frac{n}{RT}\leq f\leq\frac{B}{RT},\qquad 0\leq f\leq1.
$$

For a four-hour stage with the same traffic and budgets, this interval is
0.25% through 10%. A 20% stage exposes 800,000 requests and fails the exposure
constraint. If $n>B$, no candidate fraction can satisfy both constraints.
The source widget starts at 1%; the 0.25% boundary comes from extending the
arithmetic, not from claiming that the widget offers that setting.

The source's complete canary function is reproduced unchanged:

```python
def v2_12_canary_budget(
    packet,
    *,
    canary_pct,
    stage_hours,
    sample_needed,
    traffic_multiplier,
):
    traffic_rate = packet["traffic_per_h"] * traffic_multiplier
    traffic_fraction = max(0.0001, canary_pct / 100)
    required_hours = sample_needed / max(0.001, traffic_rate * traffic_fraction)
    samples_collected = traffic_rate * traffic_fraction * stage_hours
    blast_units = samples_collected
    evidence_ok = stage_hours >= required_hours
    blast_ok = blast_units <= packet["blast_budget_units"]
    if not evidence_ok and blast_ok:
        actual = "tiny_blind"
    elif evidence_ok and not blast_ok:
        actual = "aggressive_exposed"
    elif evidence_ok and blast_ok:
        actual = "balanced"
    else:
        actual = "aggressive_exposed" if blast_units / packet["blast_budget_units"] > required_hours / stage_hours else "tiny_blind"
    return {
        "traffic_rate": traffic_rate,
        "traffic_fraction": traffic_fraction,
        "required_hours": required_hours,
        "samples_collected": samples_collected,
        "blast_units": blast_units,
        "evidence_ok": evidence_ok,
        "blast_ok": blast_ok,
        "actual": actual,
        "blind_ratio": required_hours / max(0.001, stage_hours),
        "blast_ratio": blast_units / max(0.001, packet["blast_budget_units"]),
    }
```

*Harvard ML Systems authors, `v2_12_canary_budget`, Lab 12, CC BY-NC-SA 4.0.
The surrounding Marimo application is not needed to call this function.*

The function checks the chosen stage duration, but never reads the packet's
four-hour `release_window_h`. A 1% canary left for five hours returns
`balanced`: it collects 50,000 requests without exceeding the exposure
budget. It nevertheless misses that deadline. A deadline check has to be
added explicitly when using this helper in a release decision. The following
Bookvar example demonstrates the difference without changing the original:

```python
packet = {"traffic_per_h": 1_000_000, "blast_budget_units": 400_000,
          "release_window_h": 4}
result = v2_12_canary_budget(
    packet, canary_pct=1, stage_hours=5,
    sample_needed=10_000, traffic_multiplier=1)
assert result["actual"] == "balanced"
assert result["samples_collected"] == 50_000
within_deadline = 5 <= packet["release_window_h"]
assert not within_deadline
can_promote = result["evidence_ok"] and result["blast_ok"] and within_deadline
assert not can_promote
```

The denominator clamps in the original function keep the widget's arithmetic
finite. They are not input validation for a general release service. At zero
traffic, evidence cannot arrive; a finite `required_hours` from a clamped
denominator must not be treated as a valid waiting-time estimate. The source
controls keep normal inputs positive. Production validation would also need
finite rates, valid fractions and non-negative durations.

#### A fixed-duration stage and stopping at the sample target

At a fixed two-hour duration, a 1% canary exposes 20,000 requests, while a
5% canary exposes 100,000. If instead each stops immediately after its
10,000th request, both expose 10,000 requests: one takes an hour and the other
12 minutes. Reducing the fraction slows evidence collection but does not
reduce this idealized sample-target exposure.

Detection and rollback are not instantaneous. If candidate traffic continues
for another five minutes after the sample target, the extra exposure is
about 833 requests at 1%, or 4,167 at 5%. The comparison assumes constant
traffic, no overshoot at the stop boundary and one counted request per
exposure. It does not count distinct users or account for persistent effects
of a bad response.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/mlops-review-2026-10/sre-canary-versions.webp]]

*Alec Warner, Štěpán Davidovič et al., Google SRE Workbook,
[Figure 16-4, Canarying Releases](https://sre.google/workbook/canarying-releases/),
CC BY-NC-ND 4.0, complete original without visual changes. This is the
source's per-version error-rate example, not a measurement of the Harvard
scenario or the EDLS classifier.*

The graph separates the candidate from the control. A fleet-wide average
can hide candidate failures when the candidate receives a small traffic
share; a sample count alone would still pass. In this experiment the
10,000-request target is a supplied input, not a statistical power
calculation. A release protocol must separately specify the quality metric,
detectable regression, comparison population, uncertainty and stopping rule.
Repeated requests from one user are not automatically independent evidence.

If quality labels arrive exactly $D$ hours after a request, the number of
candidate requests with mature labels after $T$ hours is

$$
N_{\mathrm{labeled}}(T)=Rf\max(0,T-D).
$$

The required elapsed time is then $D+n/(Rf)$. With 72-hour labels, no canary
fraction can supply labeled online quality evidence within a four-hour
window. Fast service metrics can gate latency and errors in that window;
offline evaluation and later labeled cohorts serve different checks.

#### Different traffic rates and exposure units

The source supplies four tracks. They use different counting units and
different evidence and exposure budgets. Applying each track's default
5% fraction for two hours gives:

| Source scenario and unit | Units/hour | Required sample $n$ | Exposure budget $B$ | Units exposed in two hours | Passes the two canary checks? |
| --- | ---: | ---: | ---: | ---: | --- |
| Cloud requests | 1,000,000 | 10,000 | 400,000 | 100,000 | Yes |
| Mobile opt-in sessions | 200,000 | 15,000 | 25,000 | 20,000 | Yes |
| Wearable syncs | 30,000 | 2,500 | 2,500 | 3,000 | No: too much exposure |
| Vehicle live miles | 1,200 | 3,000 | 120 | 120 | No: too little evidence |

*Original track constants from `v2_12_track_packet`; outputs computed with
the unchanged canary helper. These are hypothetical course scenarios, not
traffic measurements or validated deployment policies for named products.*

The wearable stage collects enough samples but spends 500 syncs beyond
its exposure budget. At 1,500 candidate syncs per hour, ending at 100
minutes would reach exactly 2,500. The example has no remaining exposure
allowance for detection or rollback delay, so even that idealized boundary
does not establish a deployable policy.

The vehicle stage stays within its assigned 120-mile exposure budget but
cannot collect its required 3,000 miles. Sending all traffic to the
candidate would gather the sample in 2.5 hours, within the four-hour window,
but still expose 3,000 miles against a budget of 120. Here $n>B$ rules out
every traffic fraction under this model. Changing the fraction alone cannot
solve the conflict. A different evidence protocol, a justified requirement
or a changed exposure allowance needs its own approval and validation; the
arithmetic does not authorize relaxing a safety constraint.

The units also limit comparison. One request, one opt-in session, one sync
and one live mile represent different exposures. Treating the four totals
as interchangeable independent observations would require a new model.
The same code can evaluate the four scenarios without establishing that
their risk or statistical evidence is comparable.

### C. Impact before and after mitigation

The default incident calculation uses a flow of 8,000 requests per minute,
of which 8% are affected: 640 affected requests per minute. Detection takes
20 minutes and diagnosis takes another 25. Before mitigation, the scenario
therefore loses 640 × 45 = 28,800 requests.

Mitigation removes 60% of the impact. The remaining affected fraction is
8% × 40% = 3.2%, or 256 requests per minute. Recovery lasts 50 more minutes,
adding 12,800 affected requests. Total modeled loss is 41,600 requests,
below the assigned budget of 110,000. The two phases are sequential; the
recovery interval begins after mitigation.

Writing $q$ for requests per minute, $p$ for the initially affected fraction,
$m$ for mitigation effectiveness, and $t_d,t_g,t_r$ for detection, diagnosis
and recovery durations, the source model computes

$$
L=qp(t_d+t_g)+qp(1-m)t_r.
$$

All durations must use the same units. Here “lost work” counts affected
requests, not GPU-seconds, money, or permanently lost customers. With
time-varying request rates or impact, sum the actual interval counts instead
of applying one average to the entire incident.

The runbook control multiplies the base diagnosis time by an assigned factor:

| Source option | Assigned factor | Diagnosis | Loss before mitigation | Loss after mitigation | Total |
| --- | ---: | ---: | ---: | ---: | ---: |
| Ad hoc notes | 1.25 | 31.25 min | 32,800 | 12,800 | 45,600 |
| Typed diagnostic runbook | 1 | 25 min | 28,800 | 12,800 | 41,600 |
| Drilled automated playbook | 0.70 | 17.5 min | 24,000 | 12,800 | 36,800 |

The assigned 0.70 factor explains the last row; the calculation is not
evidence that automation reduces diagnosis time by 30% in a real incident.
The response-time assumptions need measurements or justified estimates
before using the result to choose operational investment.

Under the default assumptions, detecting five minutes earlier saves 3,200
affected requests. Shortening post-mitigation recovery by 30 minutes saves
7,680 because the residual impact rate is only 256 per minute. An equal
minute saved in different phases does not remove equal harm:

```python
q, affected_fraction, mitigation = 8_000, .08, .60
before_rate = q * affected_fraction
after_rate = before_rate * (1 - mitigation)
assert before_rate == 640 and after_rate == 256
loss = before_rate * (20 + 25) + after_rate * 50
assert loss == 41_600
assert before_rate * 5 == 3_200
assert after_rate * 30 == 7_680
```

The original lab also marks “inspect data/model-quality signals first” as the
correct answer for every Part C run. That is its teaching scenario, not a
universal incident order. If an authorized rollback can stop ongoing severe
impact, a full semantic diagnosis need not precede mitigation. If rollback
cannot undo emitted actions, preserve that constraint. The
[[02 Areas/ML & DL/00 Учебник/19 Deployment, Reliability и MLOps/02 MLOps#Диагностика и инцидент|runbook discussion]]
ties the first action to the observed failure and the available safe action.

### D. Joint release constraints

<!-- source-excerpt: harvard-ops-policy-conjunction -->
> Policy feasibility is not a weighted average. The release is valid only when:
>
> `slo_ok and blast_ok and cost_ok and governance_ok`.
<!-- /source-excerpt -->

*Harvard ML Systems, Lab 12, Part D, “Math Peek / source model”.*

Part D compares proposed policies using rollout, automation, telemetry and
governance controls. Its default limits are SLO spend at most 100, exposure
at most 30, cost index at most 125, and governance score at least 2.5.
The model deliberately makes a faster policy cheap but poorly controlled,
while a conservative policy spends more on controls.

The source computes synthetic indices with fixed coefficients:

$$
\begin{aligned}
s&=\max(5,88+0.62r\\
 &\qquad-0.34a-0.30t),\\
b&=\max(0.5,r(1-a/260)),\\
c&=55+0.38t+0.28a\\
 &\qquad+8g-0.08r,\\
g_{\mathrm{eff}}&=g+t/120.
\end{aligned}
$$

Here $r,a,t$ are the source's rollout, automation and telemetry controls;
$g$ is the assigned governance level. These are toy indices. In particular,
$c$ is not dollars and $s$ is not the observed availability spend from
Part A. Their coefficients cannot establish an operating budget for a
real service.

| Source policy | $r,a,t$ | $g$ | SLO index $s$ | Exposure index $b$ | Cost index $c$ | Governance $g_{\mathrm{eff}}$ | Passes all? |
| --- | --- | ---: | ---: | ---: | ---: | ---: | --- |
| Fast rollout | 70, 45, 35 | 0.5 | 105.60 | 57.885 | 79.30 | 0.792 | No |
| Balanced control loop | 22, 75, 75 | 2.5 | 53.64 | 15.654 | 122.74 | 3.125 | Yes |
| Conservative gated rollout | 8, 88, 90 | 4 | 36.04 | 5.292 | 145.20 | 4.750 | No |

The fast option passes cost but fails the other three conditions. The
conservative option fails cost. Averaging its low exposure with its high
cost would conceal the violated cost limit. The balanced option passes
these four modeled constraints, but does not repair Part A's 195 minutes
of unavailability. Acceptance of one part must not override failure of
another:

```python
balanced_checks = {"slo": True, "blast": True, "cost": True, "governance": True}
assert all(balanced_checks.values())
availability_ok, canary_ok, incident_ok = False, True, True
all_parts_pass = (availability_ok and canary_ok and incident_ok
                  and all(balanced_checks.values()))
assert not all_parts_pass
```
