# Architecture selection: topology, scaling and constraints

At the lab's default 224-pixel input, two candidates pass the assigned
mobile deployment limits: a CNN with 16 MB of activations, 8 ms of latency
and a quality score of 88.5%, and an efficient transformer with 70 MB,
19 ms and 90%. The transformer scores higher on quality; the CNN has more
resource headroom. A third candidate scores 92% but fails several limits.
These inputs lead to different choices depending on the selection rule.

The scenario, original code and budget chart below come from Harvard ML
Systems, [[02 Areas/ML & DL/05 Источники/Courses/Harvard ML Systems/labs/vol1/lab_06_nn_arch|Lab 06: Architecture Tax]],
at commit `45ecc8d82fcae70c149cdce550d3b3d3411df913`. Its helper and variant
definitions supply the numerical inputs. The chapter's selection framework
comes from the separately pinned `2bd97c5` version. The walkthrough keeps
the original English and source code; calculations and qualifications
identified below are Bookvar additions. Both source versions use
[CC BY-NC-SA 4.0](https://creativecommons.org/licenses/by-nc-sa/4.0/).

This lab evaluates a scenario model. It does not load a CNN or transformer,
compile an NPU graph, time an inference, sample a latency distribution or
evaluate predictions. The constants named `latency_ms`, `quality_pct` and
`kernel_support_pct` are assigned inputs, not measurements produced by
the lab. The calculation can reveal a conflict among those inputs; it
cannot validate them.

## From a candidate family to a deployment decision

[Network Architectures — Decision framework](https://github.com/harvard-edge/cs249r_book/blob/2bd97c509923dc8d7cb0b3e2f489a7282fee5fbd/book/quarto/contents/vol1/nn_architectures/nn_architectures.qmd#L4644),

suggests initial candidates; it does not assign every dataset to exactly
one permissible architecture. Sparse recommendation models re-enter the
constraint checks after their separate candidate-selection step.*

Follow one path through the figure. Image structure suggests a local
convolutional candidate, but does not approve it for deployment. The
candidate still needs enough memory, adequate speed and acceptable quality
on the intended task. A quality failure and a memory failure lead to
different changes. Increasing capacity may help an underfitting model
while making a memory violation worse. After a change, repeat the checks
that depend on it rather than retaining the old acceptance result.

The book states its procedure as follows:

<!-- source-excerpt: architecture-four-selection-steps -->
> 1. **Data analysis**: Pattern types in data provide the strongest initial signal. Spatial data naturally aligns with CNNs, sequential data with RNNs.
> 2. **Progressive constraint validation**: Each constraint check (memory, computational budget, inference speed) acts as a filter. Failing any constraint requires either scaling down the current architecture or considering a fundamentally different approach.
> 3. **Iterative trade-off handling**: When accuracy targets remain unmet, additional model capacity may be needed, requiring a return to constraint checking. If deployment hardware cannot support the chosen architecture, reconsidering the entire architectural approach may be necessary.
> 4. **Multiple iterations**: Practitioners should anticipate several passes, as real projects typically cycle through this framework before reaching an optimal balance between data fit, computational feasibility, and deployment requirements.
<!-- /source-excerpt -->

## Read the default mobile scenario

The source sets the input resolution to 224 pixels. It allows 220 MB of
activation memory, 25 ms of latency and 4.5 W of power, with a quality
floor of 86% and a kernel-support floor of 85%. These are the selected
scenario's limits, not specifications for an actual phone.

| Source candidate | Parameters | Activation MB | Latency ms | Power W | Quality % | Kernel support % | Passes all five conditions? |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| Mobile CNN / inverted residuals | 3.5 M | 16 | 8 | 2.1 | 88.5 | 96 | Yes |
| Efficient mobile transformer | 18 M | 70 | 19 | 3.8 | 90 | 86 | Yes |
| Desktop-scale ViT | 86 M | 420 | 84 | 8.2 | 92 | 62 | No |

*Complete default candidate values from `variants.py`, scenario
`v1_06_iphone_architecture_tax`. GMAC counts are discussed separately below.*

For the CNN, the three resource ratios are 16/220 = 0.0727,
8/25 = 0.32 and 2.1/4.5 = 0.4667. All are below one. Quality and
kernel support use the opposite inequality: 88.5 ≥ 86 and 96 ≥ 85.
The efficient transformer also passes, but kernel support is only one
percentage point above the assigned floor. The desktop ViT exceeds all
three resource limits and falls below the kernel-support floor. Its
quality score of 92 does not compensate for any of those failures.

### What “memory” includes here

The helper checks `activation_mb`, not the complete process footprint.
It stores parameter count in the result but does not add parameter bytes
to the memory guard. For the CNN, 3.5 million FP32 parameters alone
occupy 14 decimal MB; for the efficient transformer, 18 million occupy
72 MB. Adding those weights to the assigned activation amounts gives
partial totals of 30 and 142 MB, respectively. The ViT's corresponding
sum is 344 + 420 = 764 MB.

These sums still omit the runtime, allocator reserve, operator workspaces,
inputs, outputs and any other live state. They assume four bytes per
parameter, not the source's unspecified weight format. They are not peak
memory measurements. Reinterpreting the 220 MB activation budget as a
total-RAM budget would change the experiment. A real deployment needs a
memory ledger with explicit overlapping lifetimes and a measured peak.

The kernel-support percentage also needs a definition before use outside
the lab. A percentage of operator types is different from a percentage of
executed work. One unsupported operation on the critical path can trigger
transfers or fallback even when most operator names are supported. The
source does not compile a graph or calculate that fallback cost.

## Locality, operations and bytes

The topology discussion compares sliding-window convolution, recurrent
state, token mixing and sparse routing. Their data reuse differs.
Convolution reuses filter weights across spatial positions. A recurrent
model reuses a state while imposing a dependency between successive
steps. Attention relates tokens through its projections and score/value
operations. A sparse expert block additionally dispatches tokens to the
selected experts. A model can contain several of these patterns.

The lab's topology table divides `ops_gmac` by `activation_mb`. For the
mobile CNN, 0.32 GMAC / 16 MB = 0.02 GMAC/MB. This compares an assigned
operation count with an assigned resident-activation amount. It is not
the arithmetic intensity needed for a roofline model: that denominator
is bytes transferred across a named memory boundary, such as HBM.
An activation buffer can be reused or transferred repeatedly, and
weight transfers are not counted in `activation_mb` at all.

For example, with the convention of two FLOPs per MAC, the assigned
0.32 GMAC is 0.64 GFLOP. If a hypothetical execution transfers 32 MB,
its intensity is 20 FLOP/byte; if it transfers 320 MB, the same operation
count gives 2 FLOP/byte. Neither transfer count is measured by this lab.
The execution, batch shape, numerical format and memory boundary must be
specified before comparing the result with a hardware ridge point. See
[[02 Areas/ML & DL/00 Учебник/10 ML Systems/03 Измерение производительности и roofline|measurement and roofline]].

The source's string-based topology helper also checks “Transformer” before
“Sparse” or “MoE”. Its sparse transformer therefore receives the generic
attention description rather than a separate routing description. Use
the actual operator graph to inventory work. A label chosen by this helper
is not evidence that the model lacks expert routing.

## Scale the input while keeping the assumptions visible

The source uses a power law for each assigned amount. If the resolution
changes from $s_0$ to $s$, let $r=s/s_0$. Parameter count, operations,
activation memory and latency are multiplied by separately assigned powers
of $r$. Power uses an exponent capped at 1.5. The complete original
function is:

```python
def _scaled(candidate: ArchitectureCandidate, profile: ArchitectureTrackProfile, scale_value: float) -> dict[str, float]:
    scale = max(profile.scale_min, min(profile.scale_max, float(scale_value)))
    ratio = scale / max(profile.default_scale, 1e-9)
    return {
        "scale": scale,
        "params_m": candidate.params_m * (ratio**candidate.param_exponent),
        "ops_gmac": candidate.ops_gmac * (ratio**candidate.op_exponent),
        "activation_mb": candidate.activation_mb * (ratio**candidate.activation_exponent),
        "latency_ms": candidate.latency_ms * (ratio**candidate.latency_exponent),
        "power_w": candidate.power_w * (ratio ** min(candidate.op_exponent, 1.5)),
    }
```

*Harvard ML Systems, [architecture.py, `_scaled`](https://github.com/harvard-edge/cs249r_book/blob/45ecc8d82fcae70c149cdce550d3b3d3411df913/labs/mlsysbook_labs/architecture.py#L255),
CC BY-NC-SA 4.0. Original function, used with its original source types.
The checker loads those types before executing this block.*

For the CNN, doubling 224 to 448 pixels leaves its assigned 3.5 million
parameters unchanged, quadruples operations and activation memory, and
multiplies latency by $2^{1.6}$. Its power becomes
$2.1\cdot2^{1.5}\approx5.94$ W, above the 4.5 W limit. Fitting at the
default resolution therefore does not establish that the doubled input
is feasible.

The exponents are inputs, not fitted results produced by the lab.
They do not derive a transformer's attention complexity or simulate
thermal throttling. For a fixed image patch size, doubling each image
dimension gives roughly four times as many patches; explicitly materialized
full-attention scores then have roughly sixteen times as many entries.
Other work, such as projections and FFNs, scales differently. The source's
single fitted-looking exponent cannot replace this operator-level ledger.
The derivation is in
[[02 Areas/ML & DL/00 Учебник/10 ML Systems/04 Арифметика Transformer и MoE|Transformer and MoE arithmetic]].

### A sampled first failure is not an exact boundary

For the mobile CNN, the source's power law reaches the limit when

$$
s_* = 224\left(\frac{4.5}{2.1}\right)^{2/3}
     \approx372.315\text{ pixels}.
$$

The lab evaluates 36 evenly spaced points between 112 and 448, a spacing
of 9.6 pixels. Its last passing sampled point is 371.2 and the next is
380.8. The reported first failure is 380.8, not the analytic boundary.
Neither is a hardware measurement. The curve samples also differ from
the resolution slider's 16-pixel step.

```python
import math

critical = 224 * (4.5 / 2.1) ** (2 / 3)
grid = [112 + (448 - 112) * i / 35 for i in range(36)]
failed = next(x for x in grid if 2.1 * (x / 224) ** 1.5 > 4.5)
assert math.isclose(critical, 372.31468343208985)
assert math.isclose(failed, 380.8)
assert 2.1 * (371.2 / 224) ** 1.5 < 4.5
```

The desktop ViT fails at the sweep's first point, 112 pixels. This does
not mean it crosses a memory threshold there. Its assigned kernel support
is 62%, below the 85% floor at every resolution. Likewise, the cloud
scenario's CNN is below its quality floor even at the smallest context.
Inspect the violated conditions before interpreting a first-failure scale.

## Compare the selection rules

For a candidate passing all five conditions, the helper's default score
reduces to

$$
q+0.08k,
$$

where $q$ and $k$ are the assigned quality and kernel-support percentages.
For the CNN this is 88.5 + 0.08 × 96 = 96.18; for the efficient transformer,
90 + 0.08 × 86 = 96.88. The source's topology summary therefore ranks
the efficient transformer first. The coefficient 0.08 is a scoring
choice, not a measured exchange rate between quality and kernel support.
The topology summary penalizes an infeasible candidate by a further 100
points rather than removing it from the set. The supplied values keep
those candidates from winning here, but a finite penalty is not a general
hard-constraint filter. Check feasibility separately before accepting a
ranked candidate.

The review panel uses a different criterion: among feasible candidates,
maximize the smallest resource-budget multiple,

$$
h=\min\left(\frac{M_b}{M},\frac{T_b}{T},\frac{P_b}{P}\right).
$$

The CNN has $h\approx2.143$, limited by power; the efficient transformer
has $h\approx1.184$, also limited by power. That review criterion prefers
the CNN. It excludes quality and kernel support from this headroom
calculation after checking their floors. Its 2.143 must not be read as
permission to double every input dimension: each resource has its own
scaling exponent.

| Source mobile rule | Selected candidate | Reason in the source arithmetic |
| --- | --- | --- |
| Highest assigned quality, without filtering | Desktop-scale ViT | 92%, but infeasible |
| Feasible quality/kernel score | Efficient mobile transformer | 96.88 versus 96.18 |
| Feasible resource headroom | Mobile CNN | 2.143 versus 1.184 |
| Default inductive-bias score | Mobile CNN | Assigned data-need and deployability indices |

The last rule is Part C. It assigns a bias-match factor of 1.15 to the
CNN and 0.92 to the efficient mobile transformer, then divides the
data-pressure index by that factor. At pressure 1, the resulting data-need
indices are 86.96 and 108.70. Another hand-chosen formula combines those
indices with resource violations, quality and kernel support.

Changing this slider does not train on more data or change the candidates'
quality values. The lab supplies no dataset sizes, learning curves or
estimates of sample complexity. The indices illustrate how a preference
for a structural assumption can change a decision; they cannot show that
a CNN needs 1/1.15 as many real training examples.

The source also calls the largest normalized condition the “dominant
constraint”. For the default CNN this is the quality-floor ratio
86/88.5, not activation memory, latency or power. This is a comparison
of distance to assigned limits. It does not identify the slowest kernel
or prove a bandwidth bottleneck. That needs profiling of an execution.

In the cloud scenario, the rejected CNN is fast and small but has an

## A camera trap: memory, event latency and battery energy

A camera trap in the course's second scenario classifies images locally,
without a cloud connection. Its assigned limits are 512 decimal MB of RAM,
a 100 MB model budget and less than 500 ms per detection. The intended task
has 50 species and a 90% accuracy target. The source asks for six months of
battery-powered operation, but gives no battery capacity or measured
whole-device power trace.

These are the inputs to Harvard's
[Real-time wildlife monitoring example](https://github.com/harvard-edge/cs249r_book/blob/2bd97c509923dc8d7cb0b3e2f489a7282fee5fbd/book/quarto/contents/vol1/nn_architectures/nn_architectures.qmd#L4808),
not results from a deployed camera.

### What fits in the memory budget

The source assigns its MobileNetV2 candidate 2.2 million parameters and
150 million operations per image. Storing each parameter in one byte gives
2.2 MB; storing it in FP32 gives 8.8 MB. Weight storage alone fits under
100 MB in both cases. That budget therefore does not by itself force
eight-bit weights or prove that quantization preserves task accuracy.

The source also counts one FP32 activation tensor of shape $224\times224\times64$:

$$
\begin{aligned}
M_a&=224\cdot224\cdot64\cdot4\\
&=12\,845\,056\text{ bytes}.
\end{aligned}
$$

With its assumed 50 MB for OS and buffers, the partial ledger is

| Item | Assumption | Decimal MB |
| --- | --- | ---: |
| Weights | 2.2 M values, one byte each | 2.2 |
| One activation tensor | 224×224×64 FP32 values | 12.845056 |
| OS and buffers | Assigned amount | 50 |
| Sum of these three amounts | No other allocations included | 65.045056 |

The sum is below 512 MB, but the middle row is one tensor, not a trace of
all live activations. A residual block may retain its input while producing
an output; a convolution may request workspace; quantization may add
scales or retain some tensors in a different format. Peak memory requires
the graph's allocation lifetimes and the runtime's actual footprint.
Replacing that measurement with the size of one feature map would approve
a different, incomplete memory ledger.

### A throughput assumption gives a conditional time estimate

The source divides its assigned 150 million operations by 2 billion
operations per second, obtaining 75 ms. This calculation requires the
numerator and denominator to count the same work. The source first calls
the numerator MFLOPs and later treats it as INT8 operations. Here 150 million
is explicitly an assumed integer-operation count, and 2 GOP/s is an assumed
sustained rate for those same operations, with the same MAC/FLOP convention.
Neither value is a measurement of the named processor or a verified
MobileNetV2 variant.

$$
t_{\mathrm{model}}=
\frac{150\cdot10^6}{2\cdot10^9}
=0.075\text{ s}.
$$

The resulting 75 ms is below the 500 ms limit for the counted model work.
Sensor exposure, waking the processor, resizing, input copies and output
handling still need time. If the 2 GOP/s rate is a peak rather than a
sustained end-to-end rate, the quotient is only a compute lower bound.
The 500 ms event deadline also differs from the earlier source example's
30-frame/s stream: a sequential stream has a 33.3 ms average service-time
budget before a backlog grows. A 75 ms service time cannot sustain that
stream without additional parallel capacity or dropping frames.

```python
from fractions import Fraction

camera_weight_bytes = 2_200_000
camera_activation_bytes = 224 * 224 * 64 * 4
camera_partial_bytes = camera_weight_bytes + camera_activation_bytes + 50_000_000
assert camera_partial_bytes == 65_045_056
assert camera_partial_bytes < 512_000_000
assert 2_200_000 * 4 < 100_000_000  # FP32 weights also fit the model-only budget.
camera_operations = 150_000_000
camera_assumed_rate = 2_000_000_000
camera_time_s = Fraction(camera_operations, camera_assumed_rate)
assert camera_time_s == Fraction(75, 1000)
assert camera_time_s < Fraction(500, 1000)
assert camera_time_s > Fraction(1, 30)  # Cannot serve a sequential 30-fps stream.
```

### Inference energy does not determine battery life

At the source's assumed 0.2 W during a 75 ms inference, one invocation uses
0.015 J, or 15 mJ. One hundred invocations per day use 1.5 J. Over 180 days,
that active inference energy is 270 J, or 0.075 Wh. This subtotal omits the
rest of each day and cannot establish six months of operation.

To complete a two-state example, suppose the whole device draws 10 mW
outside inference and 0.2 W during inference. The 10 mW value is an added
Bookvar assumption, not a source measurement. Let $N$ be the number of
invocations per day and $t$ their duration. The states occupy disjoint times:

$$
\begin{aligned}
E_{\mathrm{day}}&=P_{\mathrm{active}}Nt\\
&\quad+P_{\mathrm{idle}}(86400-Nt).
\end{aligned}
$$

For $N=100$ and $t=0.075$ s, active time is 7.5 s and idle time is
86,392.5 s. The daily energy is $1.5+863.925=865.425$ J.
Over 180 days, it is 43.27125 Wh. Counting 24 hours of idle draw and then
adding the full active energy would count the 7.5 s of idle draw twice.
The equivalent baseline-plus-increment expression is

$$
\begin{aligned}
E_{\mathrm{day}}&=P_{\mathrm{idle}}86400\\
&\quad+(P_{\mathrm{active}}-P_{\mathrm{idle}})Nt.
\end{aligned}
$$

| $N$ per day | $Nt$, s | J/day | Wh/180 days |
| ---: | ---: | ---: | ---: |
| 100 | 7.5 | 865.425 | 43.27125 |
| 10,000 | 750 | 1006.5 | 50.325 |

The second row could represent a busier trigger stream; it does not assume
10,000 true animal detections. False triggers and retries also consume
invocations. Both rows omit battery conversion losses, temperature effects,
self-discharge and any activities not included in the two assumed states.
Solar input, if present, needs a separate time-dependent energy balance.
The source's separate 2 W average-power envelope would amount to 8.64 kWh
over 180 days if consumed continuously. An allowed power envelope is not
the device's measured average draw or a battery specification.

```python
camera_active_w = Fraction(1, 5)
camera_idle_w = Fraction(1, 100)
camera_day_s = 86_400

def camera_daily_energy(count):
    active_s = count * camera_time_s
    assert 0 <= active_s <= camera_day_s
    return (camera_active_w * active_s
            + camera_idle_w * (camera_day_s - active_s))

camera_inference_j = camera_active_w * camera_time_s
assert camera_inference_j == Fraction(15, 1000)
assert 100 * camera_inference_j == Fraction(3, 2)
assert 180 * 100 * camera_inference_j / 3600 == Fraction(75, 1000)
assert camera_daily_energy(100) == Fraction('865.425')
assert camera_daily_energy(100) * 180 / 3600 == Fraction('43.27125')
assert camera_daily_energy(10_000) == Fraction('1006.5')
assert camera_daily_energy(10_000) * 180 / 3600 == Fraction('50.325')
assert 2 * camera_day_s * 180 / 3600 == 8640  # Wh at continuous 2 W.
```

The source's keyword-spotting candidate uses depthwise separable convolution:
one spatial filter per input channel, then a pointwise map across channels.
Relative to an ordinary $r\times r$
convolution with the same channel widths and output geometry, its weight
and MAC ratio is $1/C_{\mathrm{out}}+1/r^2$, ignoring bias and additional
operations. The
[[02 Areas/ML & DL/00 Учебник/01 Основы нейронных сетей/07 CNN — от свёртки до ResNet#Групповая и поканальная свёртки|CNN chapter]]
derives the factorization and its representational restriction. An always-on
audio trigger is a possible use case, not a guarantee of low whole-device
power. A 12-class audio model is not already a 50-species image classifier;
the different class counts alone do not prove that the architecture has
insufficient capacity. Its input representation, trained features and
evaluation task all need to change.

For this camera, accepting a candidate still requires measured event
latency and peak memory, evaluation on the intended species population,
and a whole-device power trace at the expected trigger rate. The numerical
checks above accept the arithmetic under the stated assumptions. They do
not supply those missing observations.

## Record what could overturn the decision

For the default mobile example, a headroom-based decision selects the
CNN and records both feasible alternatives and violated constraints.
It still needs an actual operator-support check, a sustained thermal
run and evaluation on the intended image task. State the workload and
which measurement would overturn the choice: for example, fallback
changing the latency distribution, a task-quality failure, or peak
memory exceeding the deployment budget.

Keep the operating envelope with the decision: input sizes, batch and
concurrency, numerical formats, runtime/compiler versions, preprocessing,
quality population, and required tail statistic. A model family name
alone does not specify that execution. If no candidate passes the
required checks, report no valid candidate. A high score cannot waive
a failed hard condition.
