## Слайд 3
**Название:** Двухэтапная архитектура: Retrieval → Reranking

**Содержание:**
**Диаграмма pipeline:**

**Этап 1: Retrieval (First-stage)**
- **Вход:** Query от пользователя
- **Процесс:** Быстрый поиск в большой коллекции (миллионы документов)
- **Методы:** BM25, векторный поиск (ANN)
- **Выход:** 50-100 кандидатов
- **Скорость:** ~10-50ms
- **Цель:** Высокий recall

**Этап 2: Reranking (Second-stage)**
- **Вход:** Query + топ-N кандидатов (50-100)
- **Процесс:** Точная оценка релевантности каждого документа
- **Методы:** Learning to Rank, Cross-encoders
- **Выход:** 5-10 финальных документов
- **Скорость:** ~50-200ms
- **Цель:** Высокий precision

**Почему два этапа?**
- Точные методы слишком медленные для всей коллекции
- Быстрые методы недостаточно точные для финальной выдачи

**Информация для лектора:**
*Ресурсы:* 
- Stanford CS276 Lecture 7 "Scoring": https://web.stanford.edu/class/cs276/handouts/lecture7-scoring.pdf
- "Efficient Passage Retrieval" paper: https://arxiv.org/abs/2104.04683
- Pinecone two-stage retrieval guide: https://www.pinecone.io/learn/series/rag/rerankers/
- Weaviate hybrid search docs: https://weaviate.io/developers/weaviate/search/hybrid

*Визуализация:*

- Timeline diagram показывающий latency breakdown
- Funnel diagram: 1M → 100 → 5

*Топики:* 
- Объяснить fundamental trade-off между скоростью и точностью
- Почему нельзя использовать точные методы для всей коллекции (вычислительная сложность)
- Аналогия: сначала фильтруем грубо, потом тщательно проверяем
- Первый этап можно pre-compute (индексы), второй - нет

## Слайд 4
**Название:** Метрики качества ранжирования: зачем нужны?

**Содержание:**
**Проблема:** Как понять, что одна система ранжирования лучше другой?

**Основные категории метрик:**
- **Set-based:** Precision@k, Recall@k, F1@k
  - Оценивают только наличие релевантных в топ-k
  - Не учитывают порядок
  
- **Rank-based:** MRR, MAP
  - Учитывают позицию релевантных документов
  - MRR - позиция первого релевантного
  - MAP - средняя точность по всем позициям
  
- **Graded relevance:** NDCG, ERR
  - Учитывают градации релевантности (0, 1, 2, 3)
  - NDCG - стандарт в современном IR
  
- **Coverage:** Hit Rate@k
  - Хотя бы один релевантный в топ-k

**Что будем изучать:**
1. Сначала простые метрики (Precision, Recall)
2. Затем учитывающие позицию (MRR, MAP)
3. Затем с градациями (NDCG)

## Слайд 5
**Название:** Precision@k и Recall@k

**Содержание:**
**Формулы:**

$\frac{|\text{relevant} \cap \text{retrieved@k}|}{k}$
$Precision@k = \frac{|\text{relevant} \cap \text{retrieved@k}|}{k}$

$Recall@k = \frac{|\text{relevant} \cap \text{retrieved@k}|}{|\text{total relevant}|}$

**Пример расчета:**
- **Запрос:** "машинное обучение PyTorch"
- **Всего релевантных в коллекции:** 10 документов
- **Топ-5 результатов:** [✓, ✗, ✓, ✓, ✗]
  - Позиция 1: PyTorch tutorial ✓
  - Позиция 2: NumPy guide ✗
  - Позиция 3: PyTorch examples ✓
  - Позиция 4: Deep Learning book ✓
  - Позиция 5: Pandas docs ✗
- **Precision@5 = 3/5 = 0.6** (60% из топ-5 релевантны)
- **Recall@5 = 3/10 = 0.3** (нашли 30% от всех релевантных)

**Интерпретация:**
- **Precision** - "из того что вернули, сколько хорошего?"
- **Recall** - "из всего хорошего, сколько нашли?"
- **Trade-off:** Чем больше возвращаем → выше recall, ниже precision

**Когда использовать:**
- Precision@k - для оценки качества топа (важно в RAG)
- Recall@k - для оценки полноты поиска (важно в retrieval)

**Информация для лектора:**
*Ресурсы:*
- Stanford CS276 Lecture 8: https://web.stanford.edu/class/cs276/handouts/lecture8-evaluation.pdf
- Manning IIR Section 8.3: https://nlp.stanford.edu/IR-book/html/htmledition/evaluation-of-unranked-retrieval-results-1.html
- scikit-learn precision/recall docs: https://scikit-learn.org/stable/modules/model_evaluation.html#precision-recall-and-f-measures
- Precision-Recall visualization: https://scikit-learn.org/stable/auto_examples/model_selection/plot_precision_recall.html

*Визуализация:*
- Precision-Recall curve для разных k
- Venn diagram showing overlap между Retrieved и Relevant
- Color-coded ranking list (green=relevant, red=irrelevant)
- Interactive widget: двигаем k, смотрим как меняются метрики

*Топики:* 
- Fundamental trade-off между precision и recall
- В ранжировании precision важнее (пользователь смотрит только топ)
- Recall важен на этапе retrieval
- Precision@5 и Precision@10 - самые популярные для оценки top-k
- Limitation: не учитывают порядок внутри топ-k

## Слайд 6
**Название:** Mean Reciprocal Rank (MRR)

**Содержание:**
**Формула:**
\[ MRR = \frac{1}{|Q|} \sum_{i=1}^{|Q|} \frac{1}{rank_i} \]

где rank_i - позиция первого релевантного документа для запроса i

**Reciprocal Rank (RR) для одного запроса:**
- Первый релевантный на позиции 1 → RR = 1/1 = 1.0
- Первый релевантный на позиции 2 → RR = 1/2 = 0.5
- Первый релевантный на позиции 3 → RR = 1/3 = 0.33
- Первый релевантный на позиции 10 → RR = 1/10 = 0.1
- Нет релевантных в топ-k → RR = 0

**Пример расчета для 3 запросов:**
- **Query 1:** "что такое BERT"
  - Результаты: [✗, ✗, ✓, ✗, ✓]
  - Первый релевантный на позиции 3 → RR₁ = 1/3 = 0.33
  
- **Query 2:** "как обучить GPT"
  - Результаты: [✓, ✓, ✗, ✓, ✗]
  - Первый релевантный на позиции 1 → RR₂ = 1/1 = 1.0
  
- **Query 3:** "transformer архитектура"
  - Результаты: [✗, ✓, ✓, ✓, ✗]
  - Первый релевантный на позиции 2 → RR₃ = 1/2 = 0.5

\[ MRR = \frac{0.33 + 1.0 + 0.5}{3} = 0.61 \]

**Когда использовать:**
- **Question Answering** - обычно нужен один правильный ответ
- **Entity search** - ищем конкретную сущность
- **Navigational queries** - пользователь ищет конкретную страницу

**Ограничения:**
- Игнорирует все релевантные документы после первого
- Не учитывает, сколько всего релевантных документов

**Информация для лектора:**
*Ресурсы:*
- MS MARCO leaderboard (использует MRR@10): https://microsoft.github.io/msmarco/
- TREC 2019 Deep Learning Track paper: https://arxiv.org/abs/2003.07820
- Natural Questions dataset: https://ai.google.com/research/NaturalQuestions
- "MRR vs NDCG" discussion: https://stats.stackexchange.com/questions/127041/mean-average-precision-vs-mean-reciprocal-rank

*Визуализация:*
- Bar chart показывающий RR для разных позиций (1/1, 1/2, 1/3, ...)
- Comparison: три примера запросов с визуализацией
- График зависимости RR от позиции (гиперболическая кривая)

*Топики:* 
- MRR очень популярна в QA системах
- MS MARCO использует MRR@10 как основную метрику
- Простая интерпретация: "в среднем, на какой позиции первый хороший ответ?"
- Критика: что если пользователю нужны несколько ответов? MRR этого не видит
- В RAG часто используем MRR@5 или MRR@10

## Слайд 7
**Название:** Mean Average Precision (MAP)

**Содержание:**
**Формула:**
 $MAP = \frac{1}{|Q|} \sum_{q=1}^{|Q|} AP(q)$ 

\[ AP(q) = \frac{1}{m_q} \sum_{k=1}^{n} P(k) \cdot rel(k) \]

где:
- m_q - количество релевантных документов для запроса q
- P(k) - precision на позиции k
- rel(k) - 1 если документ на позиции k релевантен, иначе 0

**Пример расчета для одного запроса:**
**Запрос:** "python data science"
- Всего релевантных: 4 документа
- **Результаты:**
  - Позиция 1: Pandas guide ✓ → P(1) = 1/1 = 1.0
  - Позиция 2: Java tutorial ✗ → пропускаем
  - Позиция 3: NumPy docs ✓ → P(3) = 2/3 = 0.67
  - Позиция 4: C++ guide ✗ → пропускаем
  - Позиция 5: Scikit-learn ✓ → P(5) = 3/5 = 0.6
  - Позиция 6: Matplotlib ✓ → P(6) = 4/6 = 0.67

\[ AP = \frac{1.0 + 0.67 + 0.6 + 0.67}{4} = 0.735 \]

**Пример для трех запросов:**
- Query 1: AP = 0.735
- Query 2: AP = 0.833
- Query 3: AP = 0.611
- **MAP = (0.735 + 0.833 + 0.611) / 3 = 0.726**

**Отличия от других метрик:**
- **vs Precision@k:** MAP учитывает позицию всех релевантных, не только топ-k
- **vs MRR:** MAP учитывает все релевантные, не только первый
- **vs NDCG:** MAP использует бинарную релевантность (есть/нет)

**Когда использовать:**
- Когда важен порядок всех релевантных документов
- В библиотечном поиске, архивах
- TREC evaluations традиционно используют MAP

**Информация для лектора:**
*Ресурсы:*
- Stanford IIR Section 8.4: https://nlp.stanford.edu/IR-book/html/htmledition/evaluation-of-ranked-retrieval-results-1.html
- "Understanding MAP" tutorial: https://web.stanford.edu/class/cs276/handouts/EvaluationNew-handout-1-per.pdf
- pytrec_eval implementation: https://github.com/cvangysel/pytrec_eval
- TREC collections and qrels: https://trec.nist.gov/
- ranx MAP calculation: https://github.com/AmenRa/ranx

*Визуализация:*
- Step-by-step calculation table
- Precision curve график (precision на каждой релевантной позиции)
- Comparison chart: MAP vs NDCG vs MRR на одном примере
- Area under precision curve visualization

*Топики:* 
- MAP более строгая метрика чем NDCG
- Чувствительна к позиции каждого релевантного документа
- Исторически популярна в TREC, но сейчас чаще используют NDCG
- В RAG обычно не используется (смотрим только топ-5/10)
- Вычислительно дороже чем Precision@k или MRR

## Слайд 8
**Название:** Normalized Discounted Cumulative Gain (NDCG)

**Содержание:**
**Зачем нужна NDCG?**
- Precision/Recall/MAP: релевантность = 0 или 1 (бинарная)
- В реальности: документы могут быть "очень релевантны", "частично релевантны", "слабо релевантны"
- **NDCG учитывает градации релевантности**

**Градации релевантности (типичная шкала):**
- 0 = совсем не релевантен
- 1 = слабо релевантен (упоминается тема)
- 2 = релевантен (отвечает на вопрос частично)
- 3 = очень релевантен (полный ответ)

**Формула DCG (Discounted Cumulative Gain):**
\[ DCG@k = \sum_{i=1}^{k} \frac{2^{rel_i} - 1}{\log_2(i+1)} \]

**Компоненты:**
- **Gain:** 2^{rel_i} - 1 (экспоненциально растет с релевантностью)
- **Discount:** 1/log_2(i+1) (убывает с позицией)

**Формула NDCG (Normalized DCG):**
\[ NDCG@k = \frac{DCG@k}{IDCG@k} \]

где IDCG@k - Ideal DCG (DCG для идеального ранжирования)

**Почему нормализация?**
- DCG зависит от количества релевантных документов
- NDCG всегда в диапазоне [0, 1]
- NDCG = 1.0 только при идеальном ранжировании

**Информация для лектора:**
*Ресурсы:*
- "From RankNet to LambdaMART" (Section 3): https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/MSR-TR-2010-82.pdf
- Stanford CS276 NDCG materials: https://web.stanford.edu/class/cs276/
- ir-measures NDCG docs: https://ir-measur.es/en/latest/measures.html#ndcg
- BEIR benchmark paper: https://arxiv.org/abs/2104.08663
- Liu "Learning to Rank" book Chapter 3: https://link.springer.com/book/10.1007/978-3-642-14267-3

*Визуализация:*
- График: Gain function (2^rel - 1) для разных rel
- График: Discount function (1/log(i+1)) для разных позиций
- Heatmap: contribution каждого документа в DCG
- Comparison: DCG vs IDCG side-by-side

*Топики:* 
- Логарифмическая дисконтация отражает реальное поведение пользователей
- Экспоненциальный gain: документ с rel=3 намного ценнее чем rel=1
- NDCG@5 и NDCG@10 - стандарт в современном IR
- NDCG более информативна чем MAP для поисковых систем
- Почти все современные бенчмарки используют NDCG

## Слайд 9
**Название:** NDCG: детальный пример расчета

**Содержание:**
**Запрос:** "deep learning frameworks comparison"

**Система вернула топ-5:**
1. "PyTorch vs TensorFlow detailed comparison" → rel = 3 (идеально!)
2. "NumPy tutorial for beginners" → rel = 0 (не релевантно)
3. "TensorFlow 2.0 guide" → rel = 2 (частично релевантно)
4. "Introduction to neural networks" → rel = 1 (слабо релевантно)
5. "Keras vs PyTorch benchmarks" → rel = 3 (идеально!)

**Расчет DCG@5:**
\[ DCG@5 = \frac{2^3 - 1}{\log_2(2)} + \frac{2^0 - 1}{\log_2(3)} + \frac{2^2 - 1}{\log_2(4)} + \frac{2^1 - 1}{\log_2(5)} + \frac{2^3 - 1}{\log_2(6)} \]

\[ = \frac{7}{1} + \frac{0}{1.585} + \frac{3}{2} + \frac{1}{2.322} + \frac{7}{2.585} \]

\[ = 7.0 + 0 + 1.5 + 0.43 + 2.71 = 11.64 \]

**Идеальное ранжирование (для IDCG):**
- Должны быть отсортированы: [3, 3, 2, 1, 0]

\[ IDCG@5 = \frac{7}{1} + \frac{7}{1.585} + \frac{3}{2} + \frac{1}{2.322} + \frac{0}{2.585} \]

\[ = 7.0 + 4.42 + 1.5 + 0.43 + 0 = 13.35 \]

**Финальный NDCG@5:**
\[ NDCG@5 = \frac{11.64}{13.35} = 0.872 \]

**Интерпретация:**
- NDCG = 0.872 → система на 87.2% от идеала
- Потери из-за того, что нерелевантный документ (NumPy) на позиции 2
- И один очень релевантный (Keras vs PyTorch) только на позиции 5

**Информация для лектора:**
*Ресурсы:* 
- NDCG online calculator: https://ranx.readthedocs.io/
- pytrec_eval usage: https://github.com/cvangysel/pytrec_eval
- "NDCG Step-by-Step" tutorial: https://towardsdatascience.com/demystifying-ndcg-bee3be58cfe0
- ir-measures examples: https://ir-measur.es/en/latest/

*Визуализация:*
- Detailed calculation table с промежуточными значениями
- Bar chart: contribution каждого документа
- Side-by-side comparison: actual ranking vs ideal ranking
- Heatmap visualization: position × relevance

*Топики:* 
- NDCG = 1.0 достигается только при идеальном ранжировании
- Даже если все релевантные в топе, порядок важен!
- Позиция 1 и 2 критически важны (высокий gain, низкий discount)
- NDCG@5 vs NDCG@10: зависит от задачи (RAG обычно @5)

## Слайд 10
**Название:** Дополнительные метрики: Hit Rate и MR

**Содержание:**
**Hit Rate (Success Rate):**
\[ HitRate@k = \frac{\text{# queries with ≥1 relevant in top-k}}{|Q|} \]

**Пример:**
- 100 запросов
- 85 запросов имеют хотя бы 1 релевантный в топ-10
- Hit Rate@10 = 85/100 = 0.85

**Когда использовать:**
- A/B testing (быстрая метрика)
- Базовый sanity check
- Мониторинг production систем

**Mean Rank (MR) и Mean Reciprocal Rank (MR):**
\[ MR = \frac{1}{|Q|} \sum_{i=1}^{|Q|} rank_i \]

**Пример:**
- Query 1: первый релевантный на позиции 2
- Query 2: первый релевантный на позиции 5
- Query 3: первый релевантный на позиции 1
- MR = (2 + 5 + 1) / 3 = 2.67

**Expected Reciprocal Rank (ERR):**
- Моделирует cascade behavior пользователя
- Учитывает вероятность остановки на каждой позиции
- Сложнее в расчете, но более реалистична

\[ ERR = \sum_{i=1}^{k} \frac{1}{i} \prod_{j=1}^{i-1} (1 - R_j) \cdot R_i \]

**Информация для лектора:**
*Ресурсы:*
- TREC 2020 Deep Learning Track: https://arxiv.org/abs/2102.07662
- MTEB benchmark paper: https://arxiv.org/abs/2210.07316
- ERR paper (Craswell et al.): https://dl.acm.org/doi/10.1145/1571941.1572114
- "Click Models" survey: https://dl.acm.org/doi/10.1561/1500000039

*Визуализация:*
- Hit Rate bar chart для разных k

## Слайд 13
**Название:** TF-IDF: Term Frequency - Inverse Document Frequency

**Содержание:**
**Основная идея:**
- Частые термины в документе = важны для этого документа (TF)
- Редкие термины в коллекции = более информативны (IDF)
- Баланс между локальной и глобальной важностью

**Формула TF (Term Frequency):**
\[ TF(t, d) = \frac{f_{t,d}}{\max_{t' \in d} f_{t',d}} \]

или просто: $f_{t,d}$ - сырая частота термина t в документе d

**Формула IDF (Inverse Document Frequency):**
\[ IDF(t) = \log \frac{N}{df_t} \]

где:
- N - общее количество документов в коллекции
- df_t - количество документов, содержащих термин t

**Итоговая формула TF-IDF:**
\[ TFIDF(t, d) = TF(t, d) \times IDF(t) \]

**Score для документа:**
\[ Score(q, d) = \sum_{t \in q} TFIDF(t, d) \]

**Пример расчета:**
**Коллекция:** 1000 документов
**Запрос:** "machine learning"
**Документ:** "machine learning algorithms for data science"

- Термин "machine": встречается в 200 документах
  - IDF("machine") = log(1000/200) = 0.70
  - TF("machine", d) = 1
  - TFIDF = 1 × 0.70 = 0.70

- Термин "learning": встречается в 150 документах  
  - IDF("learning") = log(1000/150) = 0.82
  - TF("learning", d) = 1
  - TFIDF = 1 × 0.82 = 0.82

**Score(q, d) = 0.70 + 0.82 = 1.52**

**Информация для лектора:**
*Ресурсы:*
- Manning IIR Section 6.2: https://nlp.stanford.edu/IR-book/html/htmledition/term-frequency-and-weighting-1.html
- "Understanding TF-IDF" tutorial: https://www.onely.com/blog/what-is-tf-idf/
- scikit-learn TfidfVectorizer: https://scikit-learn.org/stable/modules/generated/sklearn.feature_extraction.text.TfidfVectorizer.html
- Gensim TF-IDF: https://radimrehurek.com/gensim/models/tfidfmodel.html

*Визуализация:*
- График IDF для разных частот документов
- Heatmap: TF-IDF scores для разных терминов
- Comparison: common terms vs rare terms
- Vector space model visualization

*Топики:*
- Стоп-слова (the, is, a) имеют высокий df → низкий IDF
- Редкие технические термины имеют низкий df → высокий IDF
- TF-IDF создает vector representation документа
- Cosine similarity часто используется для сравнения векторов
- Варианты: log TF, sublinear TF, разные формулы IDF

## Слайд 14
**Название:** BM25 (Best Match 25)

**Содержание:**
**Зачем нужен BM25?**
- TF-IDF имеет проблемы:
  - Линейный рост с частотой (10 упоминаний не в 10 раз важнее 1)
  - Не учитывает длину документа (длинные выигрывают)
- BM25 решает эти проблемы

**Формула BM25:**
\[ BM25(q, d) = \sum_{t \in q} IDF(t) \cdot \frac{f_{t,d} \cdot (k_1 + 1)}{f_{t,d} + k_1 \cdot (1 - b + b \cdot \frac{|d|}{avgdl})} \]

**Компоненты:**
- **IDF(t):** как в TF-IDF
- **f_{t,d}:** частота термина t в документе d
- **|d|:** длина документа d
- **avgdl:** средняя длина документа в коллекции
- **k₁:** параметр насыщения TF (обычно 1.2-2.0)
- **b:** параметр нормализации длины (обычно 0.75)

**Ключевые особенности:**

1. **Saturation функция для TF:**
   - При k₁=1.2: freq=1 → weight≈0.55, freq=10 → weight≈0.92
   - Рост замедляется (saturation effect)
   
2. **Длина документа:**
   - b=0: длина не учитывается
   - b=1: полная нормализация
   - b=0.75: стандартное значение (баланс)

**Пример:**
**Запрос:** "neural networks"
**Документ:** 200 слов (avgdl = 150)
**Параметры:** k₁=1.2, b=0.75

Термин "neural" встречается 3 раза:
\[ score = IDF \cdot \frac{3 \cdot 2.2}{3 + 1.2 \cdot (1 - 0.75 + 0.75 \cdot \frac{200}{150})} \]
\[ = IDF \cdot \frac{6.6}{3 + 1.2 \cdot 1.083} = IDF \cdot \frac{6.6}{4.3} = IDF \cdot 1.53 \]

**Информация для лектора:**
*Ресурсы:*
- BM25 original paper: https://www.staff.city.ac.uk/~sbrp622/papers/foundations_bm25_review.pdf
- "Improvements to BM25": https://dl.acm.org/doi/10.1145/1031171.1031181
- Elasticsearch BM25: https://www.elastic.co/guide/en/elasticsearch/reference/current/index-modules-similarity.html
- Pyserini BM25: https://github.com/castorini/pyserini
- Rank-BM25 library: https://github.com/dorianbrown/rank_bm25

*Визуализация:*

- Length normalization effect visualization
- Parameter sensitivity: k₁ и b влияние
- Comparison: TF-IDF vs BM25 scores

*Топики:*

- Параметры k₁ и b обычно не тюнят (defaults хорошие)
- Существуют варианты: BM25+, BM25L
- BM25 часто competitive с BERT на out-of-domain данных
- В гибридных системах BM25 + векторный поиск дают лучший результат

## Слайд 17
**Название:** Learning to Rank: переход от heuristics к ML

**Содержание:**
**Почему нужен Learning to Rank?**

**Проблемы традиционных методов:**
- BM25/TF-IDF: фиксированная формула
- Не учитывают дополнительные features (PageRank, freshness, user signals)
- Нет адаптации к конкретному домену
- Один размер не подходит всем

**Что такое Learning to Rank (LTR)?**
- Применение ML для обучения функции ранжирования
- **Вход:** Query-document пары + features
- **Выход:** Relevance score или ranking
- **Обучение:** На labeled data (qrels - relevance judgments)

**Три парадигмы LTR:**

1. **Pointwise** (Regression/Classification)
   - Предсказываем абсолютный score для каждого документа
   - Loss: MSE, Cross-Entropy
   - Пример: Linear Regression, Neural Network
   
2. **Pairwise** (Preference Learning)
   - Учимся предпочитать один документ другому
   - Loss: Pairwise hinge loss, RankNet loss
   - Пример: RankNet, RankSVM, LambdaRank
   
3. **Listwise** (Direct Optimization)
   - Оптимизируем ranking метрику напрямую
   - Loss: Approximation of NDCG/MAP
   - Пример: ListNet, LambdaMART, AdaRank

**Features для LTR:**
- **Query-document matching:** BM25, TF-IDF scores
- **Document quality:** PageRank, trust score
- **Query features:** Length, type, clarity
- **Document features:** Length, readability
- **User signals:** CTR, dwell time, bounce rate

**Информация для лектора:**
*Ресурсы:*
- "Learning to Rank" comprehensive survey: https://arxiv.org/abs/2101.05699
- Liu "Learning to Rank for IR" book: https://link.springer.com/book/10.1007/978-3-642-14267-3

- LETOR datasets: https://www.microsoft.com/en-us/research/project/letor-learning-rank-information-retrieval/

- В production часто используют gradient boosting (LightGBM, XGBoost)
- Features очень важны - domain knowledge критична
- Современные подходы комбинируют LTR + neural models

## Слайд 18
**Название:** Pointwise Learning to Rank

**Содержание:**
**Основная идея:**
- Рассматриваем каждый query-document pair независимо
- Предсказываем relevance score или класс
- **Regression:** score ∈ ℝ
- **Classification:** rel ∈ {0, 1, 2, 3}

**Формализация:**
- **Training data:** {(q, d, r)} где r - relevance label
- **Model:** f(q, d) → score
- **Loss:** L = Σ (f(q, d) - r)²  (MSE для regression)

**Модели:**
- **Linear Regression:** простейший вариант
- **Logistic Regression:** для классификации
- **Random Forest:** ensemble деревьев
- **MART** (Multiple Additive Regression Trees)
- **Neural Networks:** fully-connected для feature vector

**Пример pipeline:**
1. Feature extraction: [BM25=0.8, PageRank=0.3, Length=500, ...]
2. Model prediction: score = 2.3
3. Ranking: sort by score

**Преимущества:**
✅ Простота реализации
✅ Много готовых ML алгоритмов
✅ Можно использовать любую regression/classification модель

**Недостатки:**
❌ Не учитывает относительный порядок
❌ Одинаковый score для query1 и query2 означает разное
❌ Не оптимизирует ranking metrics напрямую
❌ Менее эффективен чем pairwise/listwise

**Пример кода (sklearn):**
```python
from sklearn.ensemble import RandomForestRegressor

# Features: [BM25, PageRank, TF-IDF, ...]
X_train = [[0.8, 0.3, 0.5, ...], ...]
y_train = [3, 1, 2, ...]  # relevance labels

model = RandomForestRegressor()
model.fit(X_train, y_train)

# Prediction
score = model.predict([[0.7, 0.4, 0.6, ...]])
```

**Информация для лектора:**
*Ресурсы:*
- Liu "LTR" Chapter 2: https://link.springer.com/book/10.1007/978-3-642-14267-3
- "Pointwise approach limitations": https://dl.acm.org/doi/10.1145/1390334.1390355
- sklearn regression models: https://scikit-learn.org/stable/supervised_learning.html#supervised-learning
- LETOR datasets with pointwise: https://www.microsoft.com/en-us/research/project/letor-learning-rank-information-retrieval/

*Визуализация:*
- Independent scoring diagram (каждый пример отдельно)
- Feature importance bar chart
- Prediction vs actual scatter plot
- Limitation example: same score, different queries

*Топики:*
- Pointwise - самый простой подход, но least effective
- Хорош как baseline
- Проблема: loss не связан с ranking quality
- Может предсказать хорошие scores, но плохой ranking
- В modern systems почти не используется в чистом виде

## Слайд 19
**Название:** Pairwise Learning to Rank

**Содержание:**
**Основная идея:**
- Вместо абсолютного score учимся сравнивать пары
- "Документ A релевантнее документа B"
- Минимизируем число неправильных пар

**Формализация:**
- **Preference pairs:** (q, d_i, d_j) где d_i > d_j (более релевантен)
- **Model:** f(q, d) → score
- **Constraint:** f(q, d_i) > f(q, d_j)
- **Loss:** Σ loss(f(q, d_i), f(q, d_j))

**RankNet Loss (самая популярная):**
\[ L = \sum_{(i,j) \in P} \log(1 + e^{-(s_i - s_j)}) \]

где P - множество пар (i лучше j), s_i = f(q, d_i)

**Модели:**

**RankSVM:**
- SVM для pairwise предпочтений
- Constraint: w·φ(q,d_i) > w·φ(q,d_j)
- Hinge loss

**RankNet:**
- Neural network с pairwise loss
- Gradient descent оптимизация
- Можно использовать deep architectures

**LambdaRank:**
- Модификация RankNet
- Взвешивает пары по ΔN DCG
- Больший штраф за ошибки в топе

**Пример:**
**Query:** "machine learning"
**Documents:** A (rel=3), B (rel=1), C (rel=2)

**Правильные пары:**
- (A, B): A > B ✓
- (A, C): A > C ✓
- (C, B): C > B ✓

**Scores:** s_A=2.1, s_B=1.5, s_C=1.8

**Loss calculation:**
- (A, B): log(1 + e^-(2.1-1.5)) = log(1.54) = 0.43
- (A, C): log(1 + e^-(2.1-1.8)) = log(1.35) = 0.30
- (C, B): log(1 + e^-(1.8-1.5)) = log(1.35) = 0.30
**Total loss = 1.03**

**Преимущества:**
✅ Фокус на относительном порядке
✅ Более естественно для ранжирования
✅ Лучше чем pointwise на практике
✅ Много успешных реализаций

**Недостатки:**
❌ O(n²) пар для обработки
❌ Все пары одинаково важны (но см. LambdaRank)
❌ Не оптимизирует NDCG напрямую

**Информация для лектора:**
*Ресурсы:*
- RankNet original paper: https://icml.cc/2015/wp-content/uploads/2015/06/icml_ranking.pdf
- LambdaRank paper: https://www.microsoft.com/en-us/research/publication/from-ranknet-to-lambdarank-to-lambdamart-an-overview/
- RankLib implementation: https://sourceforge.net/p/lemur/wiki/RankLib/

## Слайд 20
**Название:** Listwise Learning to Rank

**Содержание:**
**Основная идея:**
- Оптимизируем ranking метрику напрямую
- Рассматриваем весь список документов целиком
- Наиболее близко к реальной задаче ранжирования

**Зачем нужен listwise?**
- Pointwise/Pairwise не оптимизируют NDCG/MAP напрямую
- Ranking метрики определены на уровне списка
- Можем учитывать position bias

**Основные подходы:**

**1. ListNet (Probability-based):**
- Определяем probability distribution над permutations
- KL divergence между predicted и ground truth

**Top-k probability:**
\[ P(d_i \text{ on position } k) = \frac{e^{s_i}}{\sum_j e^{s_j}} \]

**ListNet Loss:**
\[ L = KL(P_{true} || P_{pred}) \]

**2. ListMLE (Maximum Likelihood):**
- Вероятность правильной permutation
- Negative log-likelihood loss

**3. LambdaMART (Gradient Boosting):**
- Комбинирует LambdaRank + MART (gradient boosting trees)
- Production standard
- Используется в Bing, Yahoo

**LambdaMART характеристики:**
- Ensemble деревьев решений
- Каждое дерево улучшает предыдущие
- Lambda gradients взвешены по ΔNDCG
- Очень эффективен на практике

**Пример ListNet:**
**Ground truth order:** [A, C, B] (scores: [3, 2, 1])
**Predicted scores:** s_A=2.0, s_B=1.0, s_C=1.5

**True distribution (softmax):**
P_true = softmax([3, 2, 1]) = [0.67, 0.24, 0.09]

**Predicted distribution:**
P_pred = softmax([2.0, 1.5, 1.0]) = [0.54, 0.33, 0.13]

**Loss = KL(P_true || P_pred) = 0.67·log(0.67/0.54) + ...**

**Преимущества:**
✅ Оптимизирует ranking метрику напрямую
✅ Учитывает весь список целиком
✅ State-of-the-art performance
✅ LambdaMART - production ready

**Недостатки:**
❌ Сложнее в реализации
❌ Computationally expensive
❌ Требует больше данных

**Информация для лектора:**
*Ресурсы:*
- "Learning to Rank: From Pairwise to Listwise": https://dl.acm.org/doi/10.1145/1273496.1273513
- ListNet paper: https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/tr-2007-40.pdf
- LambdaMART overview: https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/MSR-TR-2010-82.pdf
- XGBoost LambdaMART: https://xgboost.readthedocs.io/en/stable/tutorials/learning_to_rank.html
- LightGBM LambdaRank examples: https://github.com/microsoft/LightGBM/tree/master/examples/lambdarank
- TF-Ranking library: https://github.com/tensorflow/ranking

*Визуализация:*
- Listwise optimization diagram (full list)
- Softmax distribution visualization
- LambdaMART tree ensemble illustration
- Performance comparison: pointwise vs pairwise vs listwise

*Топики:*
- Listwise подходы дают лучшие результаты на бенчмарках
- LambdaMART - золотой стандарт в production (Bing, Yahoo использовали)
- Gradient boosting + ranking objective очень мощная комбинация
- В современных системах часто LightGBM/XGBoost с LambdaRank

## Слайд 23
**Название:** Bi-encoders (Two-tower архитектура)

**Содержание:**
**Архитектура:**
```
Query: "machine learning tutorial"
   ↓
Encoder_q (BERT)
   ↓
embed_q: [0.2, -0.5, 0.8, ...] (768 dims)

Document: "PyTorch ML guide for beginners"
   ↓
Encoder_d (BERT, shared weights)
   ↓
embed_d: [0.3, -0.4, 0.7, ...] (768 dims)

Similarity: cosine(embed_q, embed_d) = 0.87
```

**Ключевые особенности:**
- **Independent encoding:** query и doc кодируются отдельно
- **Pre-computation:** можно заранее закодировать все документы
- **ANN search:** используем FAISS, Annoy для быстрого поиска
- **Scalability:** работает на миллионах документов

**Training:**

**Contrastive learning:**
- Positive pair: (query, relevant_doc)
- Negative pairs: (query, irrelevant_docs)
- **Loss:** InfoNCE, Triplet loss, Multiple Negatives Ranking

**Multiple Negatives Ranking Loss:**
\[ L = -\log \frac{e^{sim(q, d^+)}}{e^{sim(q, d^+)} + \sum_{i} e^{sim(q, d_i^-)}} \]

**In-batch negatives:**
- Используем другие примеры в batch как negatives
- Очень эффективно: batch=64 → 63 negatives бесплатно

**Hard negatives mining:**
- BM25 top-100, но не в ground truth
- Critical для качества модели

**Популярные модели:**
- **all-MiniLM-L6-v2** (22M params, 384 dims)
  - Быстрая, компактная
  - SBERT baseline
  
- **all-mpnet-base-v2** (110M params, 768 dims)
  - Лучшее качество
  - Slower но accurate
  
- **E5-base-v2** (110M params, 768 dims)
  - Text Embeddings by Text
  - State-of-the-art на MTEB

- **BGE-M3** (567M params, multi-lingual)
  - Hybrid: dense + sparse + colbert
  - Многоязычная поддержка

**Преимущества:**
✅ Можно pre-compute document embeddings
✅ Fast ANN search (~10-50ms на 1M docs)
✅ Масштабируется на большие коллекции
✅ Модели доступны на HuggingFace

**Недостатки:**
❌ Нет interaction между query и document
❌ Менее точный чем cross-encoder
❌ Fixed dimensionality
❌ Vocabulary/semantic mismatch

**Информация для лектора:**
*Ресурсы:*
- Sentence-BERT paper: https://arxiv.org/abs/1908.10084
- sentence-transformers documentation: https://www.sbert.net/

**Название:** Cross-encoders для reranking

- Лучше учит различия

- Обрабатываем весь список
- Softmax over candidates
- Most sophisticated

- Baseline для cross-encoding

**ms-marco-MiniLM-L-6-v2** (22M params)

- Slight quality drop

- MiniLM-L6: ~20ms per query-doc pair
- MiniLM-L12: ~30ms per query-doc pair
- BERT-base: ~50ms per query-doc pair

- L6: 20ms × 100 = 2 seconds (too slow!)

**Batching:**
- Batch=32: ~100ms для 32 пар

**Преимущества:**
✅ Наивысшая точность
✅ Full interaction между query и doc
✅ State-of-the-art на бенчмарках

❌ Медленные (нельзя pre-compute)
❌ O(n) по количеству документов
❌ Нужна GPU для reasonable latency
❌ Не масштабируются на миллионы документов

## Слайд 26
**Название:** Продвинутые техники: ColBERT - Late Interaction

**Содержание:**
**Проблема:**
- Bi-encoder: теряет детали (single vector per document)
- Cross-encoder: слишком медленный (full encoding)
- **Вопрос:** Можно ли получить лучшее из обоих миров?

**ColBERT решение:**
- **Col**BERTv = **Col**umn-wise **BERT**
- Сохраняем token-level embeddings
- Late interaction через MaxSim

**Архитектура:**

**Query encoding:**
```
"machine learning" 
  ↓ BERT
["machine": [0.2, 0.5, ...], 
 "learning": [0.3, -0.2, ...]]
→ 2 vectors × 128 dims (compressed)
```

**Document encoding:**
```
"neural networks for ML"
  ↓ BERT
["neural": [...], "networks": [...], "for": [...], "ML": [...]]
→ 4 vectors × 128 dims
```

**Scoring (MaxSim):**
\[ score(q, d) = \sum_{i \in q} \max_{j \in d} sim(q_i, d_j) \]

Для каждого query токена находим максимально похожий document токен

**Пример расчета:**

**Query:** ["machine", "learning"]

## Слайд 27
**Название:** SPLADE: Sparse Lexical AnD Expansion

**Содержание:**
**Зачем нужен SPLADE?**

**Проблема dense vectors:**
- Черный ящик (не интерпретируемо)
- Нет exact match benefits
- Требует специализированных индексов (FAISS)

**Проблема BM25:**
- Только lexical matching
- Vocabulary mismatch

**SPLADE идея:**
- Neural model, но sparse vectors
- Можно использовать inverted index (Elasticsearch)
- Term expansion автоматически

**Архитектура:**

```
Input: "machine learning tutorial"
  ↓
BERT
  ↓
MLM head (vocabulary size)
  ↓
Sparse vector:
{
  "machine": 0.8,
  "learning": 0.9,
  "tutorial": 0.7,
  "ML": 0.6,        # expansion!
  "algorithm": 0.4,  # expansion!
  "training": 0.5    # expansion!
}
```

**Формула:**
\[ w_t = \sum_{i} \log(1 + ReLU(W · h_i)) \]

где h_i - BERT hidden states

**Пример expansion:**

**Query:** "ML tutorial"
**SPLADE weights:**
```
{
  "ml": 0.9,
  "tutorial": 0.8,
  "machine": 0.6,    # added
  "learning": 0.6,   # added
  "guide": 0.5,      # added
  "course": 0.4      # added
}
```

**Document:** "machine learning course"
**Match:** "machine" (0.6), "learning" (0.6), "course" (0.4) → high score!

**Training:**

**Loss = Ranking Loss + Sparsity Loss**
- Ranking: контрастное обучение (как bi-encoder)
- Sparsity: L1 regularization (поощряет zeros)

**FLOPS regularization:**
\[ L_{FLOPS} = \sum_{q,d} (||\mathbf{q}||_0 \cdot ||\mathbf{d}||_0) \]

Минимизируем количество non-zero элементов

**Варианты:**
- **SPLADE**: базовая версия
- **SPLADEv2**: улучшенная спарсификация
- **SPLADE++**: distillation от cross-encoder

**Performance (BEIR zero-shot):**
- BM25: NDCG@10 = 0.404
- Dense (Contriever): NDCG@10 = 0.446
- **SPLADE++: NDCG@10 = 0.488**
- ColBERTv2: NDCG@10 = 0.497

**Преимущества:**
✅ Интерпретируемо (видим термины и веса)
✅ Inverted index (Elasticsearch compatible)
✅ Автоматический term expansion
✅ Zero-shot transfer хорош

**Недостатки:**
❌ Vectors менее sparse чем хотелось бы (~100-200 non-zeros)
❌ Vocabulary ограничен (32k tokens)
❌ Slower inference чем простые embeddings

**Практическое применение:**
- Хорош для domain-specific терминологии
- Работает с существующей инфраструктурой (Elasticsearch)
- Hybrid: SPLADE + dense retrieval

**Информация для лектора:**
*Ресурсы:*
- SPLADE paper: https://arxiv.org/abs/2107.05720
- SPLADE v2: https://arxiv.org/abs/2109.10086
- SPLADE++: https://arxiv.org/abs/2205.04733
- HuggingFace model: https://huggingface.co/naver/splade-cocondenser-ensembledistil
- BEIR evaluation: https://github.com/beir-cellar/beir

*Визуализация:*
- SPLADE architecture diagram
- Term expansion example (query → expanded terms)
- Sparse vector visualization (bar chart)
- Inverted index structure with SPLADE

*Топики:*
- SPLADE bridges gap между neural и lexical
- Term expansion like PRF, но автоматически
- Интерпретируемость важна в некоторых доменах
- В Elasticsearch можно использовать для semantic search
- Комбинация SPLADE + dense хорошо работает

## Слайд 28
**Название:** Hybrid Search: комбинирование подходов

**Содержание:**
**Почему гибридный подход?**

**Сильные стороны разных методов:**
- **BM25:** Exact match, named entities, acronyms
- **Dense:** Synonyms, paraphrases, semantic similarity
- **Sparse (SPLADE):** Term expansion, interpretability

**Пример где BM25 лучше:**
- Query: "COVID-19"
- Dense может найти "coronavirus", "pandemic"
- Но BM25 найдет exact "COVID-19" упоминания

**Пример где Dense лучше:**
- Query: "как обучить нейросеть"
- Dense найдет "neural network training", "ML model fitting"
- BM25 промахнется из-за разных слов

**Методы комбинирования:**

**1. Weighted Sum (Convex Combination):**
\[ score = \alpha \cdot score_{BM25} + (1-\alpha) \cdot score_{dense} \]

**Проблема:** Разные шкалы! BM25 ∈ [0, 20], dense ∈ [0, 1]

**Решение:** Нормализация
\[ score_{norm} = \frac{score - min}{max - min} \]

**Типичные значения α:**
- α = 0.5: balanced (по умолчанию)
- α = 0.7: больше вес lexical (технические домены)
- α = 0.3: больше вес semantic (общие запросы)

**2. Reciprocal Rank Fusion (RRF):**
\[ RRF(d) = \sum_{r \in rankings} \frac{1}{k + rank_r(d)} \]

где k = 60 (стандартное значение)

**Пример RRF:**
```
BM25 ranking: [A, B, C, D, E]
Dense ranking: [C, A, E, F, B]

RRF scores:
A: 1/(60+1) + 1/(60+2) = 0.0164 + 0.0161 = 0.0325
B: 1/(60+2) + 1/(60+5) = 0.0161 + 0.0154 = 0.0315
C: 1/(60+3) + 1/(60+1) = 0.0159 + 0.0164 = 0.0323
...

Final ranking: [A, C, B, E, D, F]
```

**Преимущества RRF:**
✅ Scale-invariant (не нужна нормализация)
✅ Простая реализация
✅ Robust к outliers
✅ Хорошо работает на практике

**3. Distribution-Based Score Fusion:**
- Нормализация по z-score
- Min-max normalization
- Rank normalization

**4. Learning to Combine:**
- Features: [BM25_score, dense_score, position, ...]
- Model: Linear regression, LightGBM
- Обучаем оптимальные веса

**Эмпирические результаты (BEIR):**
- BM25 только: NDCG@10 = 0.404
- Dense только: NDCG@10 = 0.446
- **RRF (BM25 + Dense): NDCG@10 = 0.491** (+10%)

**Практические рекомендации:**

**Для начала:**
- RRF с k=60
- BM25 + один dense model

**Для production:**
- RRF или weighted (α learned on validation)
- Мониторинг: отслеживаем performance каждого компонента

**Для максимального качества:**
- Три этапа: BM25 + Dense → RRF → Cross-encoder
- Ensemble несколько dense models

**Информация для лектора:**
*Ресурсы:*
- RRF original paper: https://plg.uwaterloo.ca/~gvcormac/cormacksigir09-rrf.pdf
- Weaviate hybrid search: https://weaviate.io/developers/weaviate/search/hybrid
- Pinecone sparse-dense: https://www.pinecone.io/learn/hybrid-search-intro/
- Elasticsearch RRF (8.9+): https://www.elastic.co/guide/en/elasticsearch/reference/current/rrf.html
- "Hybrid Search Explained": https://www.algolia.com/blog/ai/what-is-hybrid-search/

*Визуализация:*
- Venn diagram: lexical vs semantic coverage
- RRF formula visualization (step-by-step)
- Hybrid architecture flowchart
- Performance comparison: single vs hybrid

*Топики:*
- Hybrid search почти всегда лучше чем single method
- RRF проще чем weighted sum (не нужно тюнить параметры)
- Разные запросы требуют разного баланса
- В production часто используем RRF для простоты
- Мониторинг критичен: если один компонент сломался, hybrid все равно работает

## Слайд 32
**Название:** Diversity в результатах поиска

**Содержание:**
**Проблема:**
```
Query: "python"
Top-5 results:
1. Python programming tutorial
2. Python programming guide
3. Python programming book
4. Python programming course
5. Python programming examples
```

Все про одно! А пользователь может искать:
- Python язык программирования
- Python змея
- Monty Python
- Python фреймворк

**Maximal Marginal Relevance (MMR):**

**Идея:**
- Балансируем relevance и diversity
- Итеративно выбираем документы
- Каждый новый должен быть релевантен И не похож на уже выбранные

**Формула:**
\[ MMR = \arg\max_{d \in R \setminus S} [\lambda \cdot Sim(d, Q) - (1-\lambda) \cdot \max_{s \in S} Sim(d, s)] \]

где:
- R - retrieved documents
- S - already selected documents
- λ - баланс relevance/diversity (обычно 0.5)

**Алгоритм:**
```python
def MMR(query, documents, k, lambda_param=0.5):
    selected = []
    remaining = documents.copy()
    
    # First: самый релевантный
    first = max(remaining, key=lambda d: similarity(query, d))
    selected.append(first)
    remaining.remove(first)
    
    # Iterative selection
    while len(selected) < k:
        mmr_scores = []
        for doc in remaining:
            relevance = similarity(query, doc)
            diversity = max([similarity(doc, s) for s in selected])
            mmr = lambda_param * relevance - (1 - lambda_param) * diversity
            mmr_scores.append((doc, mmr))
        
        best = max(mmr_scores, key=lambda x: x[1])
        selected.append(best[0])
        remaining.remove(best[0])
    
    return selected
```

**Пример работы:**

**Query:** "python"
**Candidates scores:**
```
Doc A (Python lang):     rel=0.9, sim_to_selected=0
Doc B (Python tutorial): rel=0.85, sim_to_A=0.95
Doc C (Python snake):    rel=0.7, sim_to_A=0.1
Doc D (Monty Python):    rel=0.6, sim_to_A=0.15
```

**Iteration 1:**
- Select A (highest relevance)

**Iteration 2:**
- B: MMR = 0.5×0.85 - 0.5×0.95 = -0.05
- C: MMR = 0.5×0.7 - 0.5×0.1 = 0.30 ✓
- D: MMR = 0.5×0.6 - 0.5×0.15 = 0.225

Select C!

**Final top-3:** [A (lang), C (snake), D (Monty)]
→ Diverse results! ✓

**Параметр λ:**
- **λ = 1.0:** только relevance (no diversity)
- **λ = 0.5:** баланс (стандарт)
- **λ = 0.0:** только diversity (игнорирует relevance)

**Когда использовать:**
- Ambiguous queries
- Exploratory search
- Recommendation systems
- News aggregation

**Недостатки:**
❌ Greedy algorithm (не оптимален)
❌ O(k × n) complexity
❌ Может пропустить релевантные из-за diversity

- On-device embeddings

Retrieval (fast, recall) → Reranking (slow, precision)

- **Speed vs Accuracy:** Bi-encoder vs Cross-encoder
