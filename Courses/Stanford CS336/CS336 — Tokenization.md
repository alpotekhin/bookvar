# CS336 — Tokenization

> Лекция 1 курса Stanford CS336. Как превратить текст в числа — и почему это критически важно для LLM.

**Курс:** [[Stanford CS336/_index|Stanford CS336]]
**Лектор:** Percy Liang
**Связанные концепты:** [[Tokenization]], [[Attention Mechanism]]

## Зачем нужна токенизация

Языковая модель работает с числами, а не с текстом. Токенизация — это мост между человеческим языком и математикой модели. От выбора токенизатора зависит:

- **Размер словаря** — сколько уникальных "слов" знает модель
- **Длина последовательности** — сколько токенов нужно для представления текста
- **Способность к генерализации** — как модель обработает новые/редкие слова
- **Мультиязычность** — насколько эффективно кодируются разные языки

Неудачный токенизатор может увеличить длину последовательности в 2-3 раза, что квадратично влияет на стоимость внимания ([[Attention Mechanism]]).

## Эволюция подходов

### 1. Word-level токенизация

Самый простой подход: каждое слово = один токен.

```
"The cat sat on the mat" → ["The", "cat", "sat", "on", "the", "mat"]
```

**Проблемы:**
- Огромный словарь (сотни тысяч слов)
- OOV (out-of-vocabulary) — неизвестные слова невозможно обработать
- Морфология теряется: "run", "running", "runner" — три разных токена без связи

### 2. Character-level токенизация

Каждый символ = токен. Словарь маленький (~256 для UTF-8 байтов).

**Проблемы:**
- Последовательности становятся очень длинными
- Модели тяжело выучить семантику на уровне символов
- Вычислительно дорого из-за длины

### 3. Subword-level токенизация (современный стандарт)

Компромисс: частые слова остаются целыми, редкие разбиваются на части.

```
"tokenization" → ["token", "ization"]
"unhappiness"  → ["un", "happi", "ness"]
```

## Byte Pair Encoding (BPE)

BPE — доминирующий алгоритм токенизации в современных LLM (GPT-4, Claude, LLaMA).

### Алгоритм обучения

1. **Инициализация:** словарь = все уникальные байты/символы в корпусе
2. **Подсчёт пар:** находим самую частую пару соседних токенов
3. **Слияние:** заменяем все вхождения этой пары новым токеном
4. **Повторяем** шаги 2-3 до достижения нужного размера словаря

**Пример:**

```
Корпус: "low low low low low lowest lowest newer newer newer"

Начальный словарь: {l, o, w, e, s, t, n, r}

Итерация 1: самая частая пара (l, o) → "lo"
Итерация 2: самая частая пара (lo, w) → "low"
Итерация 3: самая частая пара (e, r) → "er"
Итерация 4: самая частая пара (n, er) → "ner"
...
```

### Алгоритм применения (inference)

При кодировании нового текста:
1. Разбиваем на символы/байты
2. Применяем выученные правила слияния **в порядке приоритета**
3. Результат — последовательность токенов из словаря

### Размер словаря

Типичные размеры для современных LLM:

| Модель | Размер словаря |
|--------|---------------|
| GPT-2 | 50,257 |
| GPT-4 | ~100,000 |
| LLaMA | 32,000 |
| LLaMA 3 | 128,256 |

Больший словарь = короче последовательности, но больше embedding-матрица.

## SentencePiece и Unigram

### SentencePiece

Библиотека Google, которая работает **напрямую с raw текстом** (без пре-токенизации по пробелам). Поддерживает два алгоритма:

- **BPE** — описан выше
- **Unigram** — альтернативный подход

### Unigram Language Model

В отличие от BPE (который начинает с маленького словаря и растит его), Unigram:

1. Начинает с **большого** словаря (все подстроки до длины N)
2. Обучает unigram LM: P(token) пропорциональна частоте
3. Итеративно **удаляет** токены, которые меньше всего ухудшают likelihood
4. Повторяет до нужного размера словаря

**Преимущество:** при inference возможны *несколько* разбиений одного слова, что даёт регуляризацию (subword regularization / BPE-dropout).

---

## Byte-level BPE

Современный подход (GPT-2+): работаем не с Unicode-символами, а с **байтами**.

**Преимущества:**
- Базовый словарь всего 256 токенов
- Любой текст на любом языке можно закодировать
- Нет проблемы OOV — в принципе невозможна
- Одинаковый подход для текста, кода, математики

**Нюанс:** некоторые модели (GPT-4) добавляют pre-tokenization regex для разделения по пробелам, числам, пунктуации — чтобы BPE не создавал нежелательные слияния через границы слов.

## Практические соображения

### Влияние на мультиязычность

Токенизатор, обученный преимущественно на английском тексте, будет неэффективен для других языков:

```
English: "Hello world"    → 2 токена
Russian: "Привет мир"     → 4-6 токенов
Japanese: "こんにちは世界"  → 5-8 токенов
```

Это значит, что для русского/японского текста модель тратит больше compute на то же количество *смысла*. LLaMA 3 решает проблему увеличением словаря до 128K.

### Числа и код

Токенизация чисел — известная проблема. "123456" может стать ["123", "456"] или ["1", "234", "56"] в зависимости от контекста. Это затрудняет арифметику. Современные модели используют специальную пре-обработку чисел.

### Специальные токены

Помимо текстовых токенов, в словарь добавляются:

- `<|endoftext|>` — конец документа
- `<|pad|>` — padding
- `<|im_start|>`, `<|im_end|>` — границы сообщений (chat формат)
- `<|tool_call|>` — вызов инструментов

## Ключевые выводы

1. **BPE — стандарт индустрии**, но не единственный вариант
2. **Byte-level BPE** решает проблему OOV и мультиязычности
3. **Размер словаря** — trade-off между длиной последовательности и размером модели
4. **Токенизатор определяет** качество модели на non-English языках
5. В CS336 студенты **реализуют BPE с нуля** в Assignment 1
