# Toolformer: Language Models Can Teach Themselves to Use Tools

## Зачем это нужно: парадокс больших моделей

LLM демонстрируют впечатляющие способности в zero-shot и few-shot задачах, но при этом парадоксально плохо справляются с вещами, которые тривиальны для простейших программ:

- **Арифметика**: GPT-3 175B решает 14% задач ASDiv, обычный калькулятор -- 100%
- **Актуальные факты**: модель не знает, что произошло после даты cutoff
- **Точный поиск**: галлюцинирует факты вместо того, чтобы проверить
- **Время**: не знает текущую дату
- **Перевод редких языков**: ограничена данными pretraining

До Toolformer существовали два подхода к решению проблемы:
1. **Ручная аннотация** (Komeili et al., 2022; Thoppilan et al., 2022) -- дорого и субъективно (то, что полезно человеку, может быть бесполезно модели)
2. **Task-specific tool use** (Gao et al., 2022; Parisi et al., 2022) -- привязано к конкретным задачам, не обобщается

## Ключевая идея: пусть модель сама решит, когда инструмент полезен

**Toolformer** (Schick et al., 2023, Meta AI) -- метод, в котором LLM **самостоятельно обучается** решать, когда и какой инструмент вызвать, какие аргументы передать и как использовать результат. Всё это -- **полностью self-supervised**, без задачеспецифичных аннотаций.

Ключевой критерий: API-вызов считается полезным, если его результат **снижает loss на предсказание следующих токенов**. Если модели легче предсказать продолжение текста, имея результат API -- значит, вызов был нужен.

### Формат API-вызова

API-вызовы вставляются прямо в текст с помощью специальных токенов:

```
<API> ac(ic) -> r </API>
```

Примеры из статьи (Figure 1):
- *"400 (or [Calculator(400/1400) -> 0.29] 29%) passed the test."*
- *"The name derives from "la tortuga", the Spanish word for [MT("tortuga") -> turtle] turtle."*
- *"The Brown Act is California's law [WikiSearch("Brown Act") -> The Ralph M. Brown Act is an act of...] that requires..."*

## Три шага pipeline

### Шаг 1: Sample API Calls

Для каждой позиции $i$ в тексте $x = x_1, \ldots, x_n$ модель с in-context промптом (несколько примеров использования API) генерирует кандидатные API-вызовы. Сначала вычисляется вероятность начала API-вызова на каждой позиции:

$$p_i = p_M(\text{<API>} \mid P(x), x_{1:i-1})$$

Позиции с $p_i > \tau_s$ (sampling threshold) отбираются, и для каждой генерируется до $m$ кандидатных вызовов.

### Шаг 2: Execute API Calls

Все сгенерированные вызовы **выполняются** соответствующими инструментами. Для каждого вызова $c_i$ получаем текстовый результат $r_i$. Как именно получается результат -- зависит от API: это может быть вызов нейросети, Python-скрипта, поисковой системы.

### Шаг 3: Filter API Calls (критический шаг)

Сравниваются два loss:

$$L_i^+ = L_i(e(c_i, r_i)) \quad \text{-- loss с API-вызовом и результатом}$$

$$L_i^- = \min(L_i(\varepsilon), L_i(e(c_i, \varepsilon))) \quad \text{-- loss без вызова или с вызовом без результата}$$

API-вызов сохраняется **только если**:

$$L_i^- - L_i^+ \geq \tau_f$$

Интуиция: вызов полезен, если предоставление модели и запроса, и ответа API **снижает loss** на предсказание следующих токенов по сравнению с (а) отсутствием вызова или (б) вызовом без результата.

Весовая функция $w_t = \max(0, 1 - 0.2 \cdot t)$ убывает с расстоянием от вызова -- API-вызов должен помогать предсказывать **ближайшие** токены.

### Fine-tuning

Модель (GPT-J 6.7B) дообучается на $C^*$ -- корпус с вставленными API-вызовами -- стандартным language modeling objective. Ключевой момент: **помимо вставленных API-вызовов, $C^*$ содержит тот же текст, что и исходный корпус $C$**. Это гарантирует, что модель не теряет general language modeling abilities.

## Пять инструментов

| API | Вход | Выход | Модель/Метод |
|-----|------|-------|--------------|
| **Question Answering** | Вопрос на естественном языке | Ответ | Atlas (retrieval-augmented LM) |
| **Calculator** | Математическое выражение | Число (2 знака) | Python |
| **Wikipedia Search** | Поисковый запрос | Текстовые сниппеты | BM25 retriever |
| **Machine Translation** | Фраза на любом языке | Перевод на английский | NLLB 600M (200 языков) |
| **Calendar** | (пусто) | Текущая дата | Системный вызов |

Единственные требования к инструменту: (i) вход и выход представляются как текст, (ii) есть несколько примеров использования для промпта.

## Результаты: маленькая модель с инструментами побеждает гиганта

### Факты (LAMA)

| Модель | SQuAD | Google-RE | T-REx |
|--------|-------|-----------|-------|
| GPT-J 6.7B | 17.8 | 4.9 | 31.9 |
| OPT 66B | 21.6 | 2.9 | 30.1 |
| GPT-3 175B | 26.8 | 7.0 | 39.8 |
| **Toolformer 6.7B** | **33.8** | **11.5** | **53.5** |

Toolformer 6.7B **превосходит GPT-3 175B** (в 25 раз больше параметров), используя QA-инструмент в 98.1% случаев.

### Математика

| Модель | ASDiv | SVAMP | MAWPS |
|--------|-------|-------|-------|
| GPT-J 6.7B | 7.5 | 5.2 | 9.9 |
| GPT-3 175B | 14.0 | 10.0 | 19.8 |
| **Toolformer 6.7B** | **40.4** | **29.4** | **44.0** |

**Toolformer в 3 раза превосходит GPT-3 175B** на ASDiv! Модель вызывает калькулятор в 97.9% случаев. Даже Toolformer с выключенными API (14.8 на ASDiv) лучше GPT-J (7.5) -- fine-tuning на примерах вычислений улучшает собственные математические способности.

### QA и другие задачи

На Web Questions и Natural Questions Toolformer превосходит все GPT-J-based модели, но уступает GPT-3 175B. Причина: простой BM25 retriever и невозможность переформулировать запрос или просмотреть несколько результатов.

### Perplexity не ухудшается

На WikiText и C4 perplexity Toolformer практически идентична GPT-J + CC (fine-tuned на том же корпусе без API). Модель **не теряет** language modeling abilities.

## Scaling: эмерджентное появление tool use

Авторы исследовали, как способность использовать инструменты зависит от размера модели, используя GPT-2 моделей от 124M до 1.5B.

Ключевой результат: **способность к tool use эмерджентно появляется при ~775M параметров**. Модели меньшего размера не могут научиться осмысленно вставлять API-вызовы. Это перекликается с findings из других работ об эмерджентных способностях LLM.

## Инференс: модифицированный decoding

При генерации текста после fine-tuning:
1. Обычный greedy decoding, пока модель не сгенерирует `->` (ожидает ответ API)
2. Прерываем decoding, вызываем API, вставляем результат и `</API>`
3. Продолжаем decoding

Модификация: `<API>` принимается не только когда это top-1 токен, но когда входит в **top-k (k=10)** -- увеличивает склонность модели использовать инструменты. При этом **максимум один API-вызов на один вход** -- иначе модель может зацикливаться.

## Сравнение с ReAct

| Свойство | Toolformer | [[02 Areas/ML & DL/Concepts/Reasoning/ReAct\|ReAct]] |
|----------|-----------|-------|
| Метод | Fine-tuning | Prompting |
| Когда вызывать | Модель решает сама (self-supervised) | Задано в промпте (dense/sparse thoughts) |
| Reasoning | Нет явных мыслей | Explicit Thought перед каждым Action |
| Цепочки вызовов | Нет (max 1 вызов) | Да (многошаговые траектории) |
| Переформулировка | Нет | Да (через мысли) |
| Generality | Любые API с текстовым I/O | Любые среды |

## Ограничения

- **Максимум 1 API-вызов**: нет цепочек вызовов, нет композиции инструментов
- **Нет интерактивности**: модель не может переформулировать запрос по результатам
- **Зависимость от CCNet**: distribution shift при fine-tuning на подмножестве CCNet может ухудшить multilingual performance
- **Фильтрация**: при высоком $\tau_f$ остаётся мало примеров (напр., 138 для Calculator при $\tau_f = 2.0$)
