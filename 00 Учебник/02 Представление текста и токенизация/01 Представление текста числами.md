# Представление текста числами

Строку `кот спит` нельзя передать полносвязному слою как два числовых
признака. Сначала нужно выбрать единицы текста, затем присвоить им
номера. Например, разбиение по пробелам даст `["кот", "спит"]`,
а заранее построенный словарь может сопоставить им `[2, 3]`.
Входной слой нейросети выберет по этим номерам два вектора
из обучаемой таблицы.

Разбиение строки и поиск номеров выполняет токенизатор.
Выбор векторов — отдельная операция модели, embedding lookup.
Таблица может иметь 50 тысяч строк, но длина конкретного предложения
от этого не становится равной 50 тысячам: в последовательности
остаётся столько позиций, сколько токенов вернул токенизатор.

Есть и другой способ представить тот же текст: посчитать,
сколько раз встретился каждый элемент словаря, и получить один
вектор документа. Последовательность сохраняет позиции токенов.
Вектор частот удобен для линейного классификатора,
но отбрасывает порядок слов.

## Символ, байт, слово и токен

Unicode задаёт кодовые точки, а UTF-8 определяет, какими байтами
их записывать в файле. Одна кодовая точка может занимать от одного
до четырёх байтов UTF-8. Например, буква `к` имеет код U+043A
и кодируется двумя байтами `D0 BA`. Пробел U+0020 занимает один байт.

Для строки `кот спит` получаются три разных счётчика:

| Что считаем | Число |
|---|---:|
| Кодовые точки Unicode | 8 |
| Байты UTF-8 | 15 |
| Токены при разбиении по пробелам | 2 |

Восемь кодовых точек — это семь букв и пробел.
Кириллические буквы в этой строке занимают по два байта,
поэтому длина UTF-8 равна $7\cdot2+1=15$.
Число токенов $2$ относится именно к выбранному разбиению;
другой токенизатор может вернуть другую последовательность.

Видимый знак тоже не обязательно совпадает с одной кодовой точкой.
Букву `é` можно записать как U+00E9 или как `e` U+0065
с последующим знаком ударения U+0301. В Python первая запись
имеет длину $1$, вторая — $2$. Без нормализации это разные строки,
хотя они могут выглядеть одинаково. Нормализация NFC приводит
этот конкретный пример к одной составной кодовой точке.

Последовательность `👩‍💻` содержит три кодовые точки:
U+1F469, соединитель U+200D и U+1F4BB.
Её UTF-8-запись занимает $4+3+4=11$ байтов,
хотя приложение может показывать один составной эмодзи.
Поэтому `len(text)`, длина байтовой записи и число видимых знаков
не являются взаимозаменяемыми величинами.

```python
import unicodedata

text = "кот спит"
assert len(text) == 8
assert len(text.encode("utf-8")) == 15
assert len(text.split()) == 2

composed, decomposed = "é", "e\u0301"
assert composed != decomposed
assert (len(composed), len(decomposed)) == (1, 2)
assert unicodedata.normalize("NFC", decomposed) == composed

emoji = "\U0001F469\u200d\U0001F4BB"
assert len(emoji) == 3
assert len(emoji.encode("utf-8")) == 11
```

Устройство кодовых точек и UTF-8 подробно разобрано у
[Jurafsky и Martin, Words and Tokens, §2.3](https://web.stanford.edu/~jurafsky/slp3/2.pdf#page=7);
операции NFC/NFD — в
[документации unicodedata.normalize](https://docs.python.org/3/library/unicodedata.html#unicodedata.normalize).
Нормализацию текста выбирают для конкретной системы.
Она не восстанавливает исходное написание: после объединения
эквивалентных записей узнать, какая из них была в файле, уже нельзя.

Слово не задаёт универсального разбиения текста.
В китайском пробелы обычно не разделяют слова;
английское `don't`, адрес сайта и программный код допускают
несколько вариантов сегментации.
Токеном называют единицу, которую выделяет конкретный токенизатор.
Это может быть слово, часть слова, знак пунктуации или фрагмент
байтовой последовательности.

При пословном разбиении словарь растёт вместе с корпусом:
появляются имена, новые словоформы и опечатки.
Посимвольное или байтовое представление уменьшает набор единиц,
но удлиняет последовательности.
Алгоритмы BPE, WordPiece и Unigram выбирают промежуточные единицы.
Их обучение и обратимость отдельно разобраны в
[[02 Areas/ML & DL/00 Учебник/02 Представление текста и токенизация/02 BPE, WordPiece и Unigram|главе о токенизации]].
Ниже используем разбиение по пробелам, чтобы все номера
и векторы можно было проверить вручную.

## Словарь и идентификаторы

Возьмём три обучающих документа:

```text
D1: кот кот спит
D2: пёс спит
D3: кот спит бежит
```

Всего здесь восемь употреблений слов, но только четыре разных
словоформы. `кот` и `спит` встречаются по три раза,
`пёс` и `бежит` — по одному.
Различие между числом употреблений и числом разных элементов
введено у [Jurafsky и Martin, §2.1](https://web.stanford.edu/~jurafsky/slp3/2.pdf#page=2).
Для модели одно употребление занимает позицию в последовательности,
а повторяющаяся словоформа использует одну запись словаря.

Добавим два служебных элемента: `<pad>` для дополнения пакета
до общей длины и `<unk>` для неизвестных слов.
Остальные элементы упорядочим по убыванию частоты.
При равных частотах в этом примере сохраним порядок первого появления:

| ID | Элемент |
|---:|---|
| 0 | `<pad>` |
| 1 | `<unk>` |
| 2 | кот |
| 3 | спит |
| 4 | пёс |
| 5 | бежит |

Получился словарь размера $|V|=6$.
Первый документ превращается в `[2, 2, 3]`,
второй — в `[4, 3]`.
Словарь и правила предварительной обработки сохраняют вместе
с моделью. Если при применении построить новый словарь
с другими номерами, модель выберет не те строки таблицы.

Для общей записи

$$
\begin{gathered}
\operatorname{encode}(s)=(i_1,\ldots,i_T),\\
0\le i_t<|V|.
\end{gathered}
$$

Число $i_t$ — адрес, а не измерение смысла.
Разность между ID $2$ и $4$ не измеряет сходство кота и пса.
Если одновременно поменять их номера в словаре и соответствующие
строки embedding-таблицы, входные векторы останутся прежними.
Для полной модели, предсказывающей ID токенов, пришлось бы
также переставить связанные с ID выходные параметры и расшифровку
её ответов.

Построение словаря через подсчёт частот, отсечение редких элементов
и обработку неизвестных подробно показано в
[D2L, Vocabulary](https://d2l.ai/chapter_recurrent-neural-networks/text-sequence.html#vocabulary).
Следующий код использует тот же порядок этапов.
Конкретное соглашение о нумерации здесь задано явно:

```python
from collections import Counter

corpus = ["кот кот спит", "пёс спит", "кот спит бежит"]
reserved = ["<pad>", "<unk>"]

def build_vocab(documents, min_freq=1):
    counts = Counter(word for doc in documents for word in doc.split())
    words = [word for word, count in counts.most_common()
             if count >= min_freq and word not in reserved]
    vocabulary = reserved + words
    return {word: i for i, word in enumerate(vocabulary)}, vocabulary

vocab, inverse = build_vocab(corpus)
def encode(text):
    return [vocab.get(word, vocab["<unk>"]) for word in text.split()]

def decode(ids):
    return [inverse[i] for i in ids]

assert inverse == ["<pad>", "<unk>", "кот", "спит", "пёс", "бежит"]
assert encode(corpus[0]) == [2, 2, 3]
assert decode([2, 2, 3]) == ["кот", "кот", "спит"]
assert encode("лиса тигр") == [1, 1]
assert build_vocab(corpus, min_freq=2)[1] == ["<pad>", "<unk>", "кот", "спит"]
```

Два неизвестных слова получили одинаковый ID.
Обратное преобразование вернёт два `<unk>`, а не `лиса тигр`.
Кроме того, `split()` не сохраняет число пробелов:
`кот  спит` и `кот спит` дают одинаковые токены.
Восстановить последовательность известных токенов и восстановить
исходные байты строки — разные требования.

Набор служебных токенов зависит от модели.
Кроме padding и неизвестного элемента, могут быть маркеры начала
и конца последовательности, границ ролей или инструментальных вызовов.
Их ID не обязаны совпадать с нашими $0$ и $1$.
Байтовые токенизаторы могут обходиться без неизвестного элемента
для корректного текста, если набор базовых байтов и правила декодирования
обеспечивают нужное покрытие.

Если словарь обучается для собственной задачи, его строят
по обучающей части данных и затем фиксируют.
У готовой предобученной модели используют её готовый токенизатор:
наличие в его словаре слова из нашего теста само по себе
не означает утечку. Утечка возникла бы, например, при подборе
предобработки или статистик по тестовым данным собственной задачи.

## One-hot как точная, но неудобная запись адреса

ID $2$ можно представить вектором

$$
o_2=(0,0,1,0,0,0).
$$

В общем случае one-hot-вектор $o_i\in\mathbb R^{|V|}$
содержит единицу в координате $i$ и нули во всех остальных.
Он точно различает элементы словаря.
Для двух разных ID $i\ne j$ получаются

$$
o_i^\top o_j=0,
\qquad \|o_i-o_j\|^2=2.
$$

Поэтому косинусное сходство любых двух разных one-hot-векторов
равно нулю, а евклидово расстояние — $\sqrt2$.
В такой геометрии `кот` столь же далёк от `пёс`, как от `спит`.
Геометрия ещё не содержит сведений об употреблении слов.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/voita-word-embeddings/one-hot.png]]

*В каждом векторе одна ненулевая координата; её положение задаётся
словарём. На рисунке dog, cat и table имеют разные координаты,
но одинаковую длину вектора. Lena Voita,
[Represent as Discrete Symbols: One-hot Vectors](https://lena-voita.github.io/nlp_course/word_embeddings.html#one_hot_vectors).
Оригинальное изображение без изменений.*

Из этого не следует, что one-hot непригоден для обучения.
Линейная модель может обучить отдельный вес для каждой категории,
а следующий обучаемый слой может преобразовать one-hot
в плотный вектор. Именно такое преобразование лежит
в основе embedding lookup.

При большом $|V|$ хранить все нули необязательно.
ID полностью определяет one-hot, поэтому достаточно хранить номер.
One-hot удобен для вывода формул; реальную операцию можно выполнить
без построения этого большого вектора.

## Выбор вектора из таблицы (embedding lookup)

Зададим таблицу $E\in\mathbb R^{6\times2}$.
Числа ниже выбраны вручную для проверки вычислений;
это не результат обучения и не пример найденных смысловых связей:

| Элемент | Строка $E[i]$ |
|---|---|
| `<pad>` | $(0,0)$ |
| `<unk>` | $(-1,-1)$ |
| кот | $(1,0)$ |
| спит | $(0,1)$ |
| пёс | $(1,1)$ |
| бежит | $(-1,1)$ |

Умножение one-hot на таблицу выбирает одну строку:

$$
x_i=o_i^\top E=E[i].
$$

Например, у $o_2$ единственная единица стоит на месте строки `кот`,
поэтому сумма строк таблицы с коэффициентами из $o_2$
равна $1\cdot(1,0)=(1,0)$.
Для ID $3$ получится строка $(0,1)$.
Последовательность `[2, 3, 2]` превращается в матрицу

$$
X=\begin{pmatrix}
1&0\\
0&1\\
1&0
\end{pmatrix}.
$$

В ней три позиции и два признака в каждой позиции.
Два вхождения токена `кот` выбрали одну и ту же строку $E[2]$.
Число позиций осталось равным трём.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/voita-word-embeddings/lookup-table.gif]]

*Анимация Lena Voita:
[How it works: Look-up Table](https://lena-voita.github.io/nlp_course/word_embeddings.html#intro).
Для I, saw, a, cat и точки по очереди выбираются строки
с индексами 39, 1592, 10, 2548 и 5.
Горизонталь таблицы — размерность одного вектора,
вертикаль — размер словаря.
Оригинальная GIF-анимация без изменений.*

Библиотечный слой не обязан умножать one-hot на всю таблицу:
он может сразу прочитать нужную строку по индексу.
Равенство с матричным произведением описывает результат,
а не требует конкретного алгоритма исполнения.
Форма входных ID $(B,T)$ превращается в форму $(B,T,d)$,
где $d$ — ширина таблицы.

Например, при $B=4$, $T=1024$ и $|V|=50\,000$
плотный one-hot в FP32 занял бы $781{,}25$ MiB.
Те же ID в int64 занимают $32$ KiB.
При ширине $d=768$ выбранные векторы в FP32 занимают $12$ MiB,
а вся таблица $E$ — ещё около $146{,}48$ MiB.
Это четыре разных объекта.
Отказ от явного one-hot не устраняет память таблицы
и промежуточных векторов.

### Как обучается выбранная строка

Пусть следующий слой передал градиенты по трём строкам
приведённого $X$:

$$
G=\frac{\partial L}{\partial X}
=\begin{pmatrix}1&2\\3&4\\5&6\end{pmatrix}.
$$

Первая и третья строки $X$ используют один параметр $E[2]$.
По правилу сложения вкладов в backpropagation его градиент равен
$(1,2)+(5,6)=(6,8)$.
Вторая строка даёт градиент $(3,4)$ для $E[3]$.
Остальные строки таблицы в этой операции не использовались.

В общем виде, если $g_t$ — входящий градиент для позиции $t$,

$$
\frac{\partial L}{\partial E[j]}
=\sum_{t:\,i_t=j}g_t.
$$

После SGD с шагом $0{,}1$ строка $E[2]$ изменится
с $(1,0)$ до $(0{,}4,-0{,}8)$,
а $E[3]$ — с $(0,1)$ до $(-0{,}3,0{,}6)$.
Все вхождения токена в следующем проходе увидят обновлённую
общую строку.

```python
import torch
import torch.nn.functional as F

weights = torch.tensor([
    [0., 0.], [-1., -1.], [1., 0.],
    [0., 1.], [1., 1.], [-1., 1.]
], dtype=torch.float64)
layer = torch.nn.Embedding.from_pretrained(weights.clone(), freeze=False)
ids = torch.tensor([2, 3, 2], dtype=torch.long)
x = layer(ids)
one_hot = F.one_hot(ids, num_classes=6).to(weights.dtype)
torch.testing.assert_close(x, one_hot @ weights)

incoming = torch.tensor([[1., 2.], [3., 4.], [5., 6.]], dtype=weights.dtype)
loss = (x * incoming).sum()
loss.backward()
expected_grad = torch.zeros_like(weights)
expected_grad[2] = torch.tensor([6., 8.])
expected_grad[3] = torch.tensor([3., 4.])
torch.testing.assert_close(layer.weight.grad, expected_grad)

optimizer = torch.optim.SGD(layer.parameters(), lr=0.1)
optimizer.step()
torch.testing.assert_close(layer.weight[2],
                           torch.tensor([0.4, -0.8], dtype=weights.dtype))
torch.testing.assert_close(layer.weight[3],
                           torch.tensor([-0.3, 0.6], dtype=weights.dtype))
```

Здесь используется обычное суммирование градиентов повторных ID:
`scale_grad_by_freq=False`, как по умолчанию в PyTorch.
При включённом `scale_grad_by_freq` библиотека делит эти
градиенты на частоту соответствующего ID в мини-батче.

Утверждение о нулевых градиентах остальных строк относится
к операции lookup. Если эту же матрицу используют ещё где-то
в модели или оптимизатор применяет к ней weight decay,
невыбранные строки тоже могут изменяться.
Параметр `sparse=True` у `Embedding` меняет представление градиента,
а не превращает саму таблицу параметров в словарь без остальных строк.
Эти режимы и ограничения оптимизаторов описаны в
[PyTorch 2.14, Embedding](https://docs.pytorch.org/docs/2.14/generated/torch.nn.Embedding.html).

На старте обучения с нуля таблица обычно инициализирована случайно.
Дальнейшая геометрия определяется функцией потерь и данными.
Сам lookup не заставляет похожие слова сближаться.
Обучение по соседним словам в Word2Vec или по следующему токену
создаёт разные обучающие сигналы.
Их устройство разбирается дальше по маршруту.

## Проверка на одном пакете

Второй документ нашего корпуса короче первого.
Для прямоугольного пакета длины $T=3$ дополним его справа:

$$
I=\begin{pmatrix}2&2&3\\4&3&0\end{pmatrix}.
$$

Форма ID равна $(B,T)=(2,3)$.
После выбора из таблицы форма станет $(2,3,2)$.
Первый пример содержит векторы $(1,0),(1,0),(0,1)$,
второй — $(1,1),(0,1),(0,0)$.
Последняя строка второго примера соответствует padding,
а не слову документа.

Если для каждого текста нужен один вектор,
можно рассчитать среднее его токенных векторов.
В этом учебном примере получим

$$
\bar x_1=\frac{(1,0)+(1,0)+(0,1)}3
=\left(\frac23,\frac13\right),
$$

$$
\bar x_2=\frac{(1,1)+(0,1)}2
=\left(\frac12,1\right).
$$

Если усреднить второй пример по всем трём позициям пакета,
включая нулевой padding, получится $(1/3,2/3)$.
Числитель не изменился, но знаменатель стал неверным.
Для получения среднего нужна маска реальных позиций.

```python
import torch
import torch.nn.functional as F

weights = torch.tensor([
    [0., 0.], [-1., -1.], [1., 0.],
    [0., 1.], [1., 1.], [-1., 1.]
], dtype=torch.float64)
ids = torch.tensor([[2, 2, 3], [4, 3, 0]], dtype=torch.long)
valid = ids != 0
x = F.embedding(ids, weights, padding_idx=0)
assert ids.shape == (2, 3) and x.shape == (2, 3, 2)
assert valid.any(dim=1).all()  # В этом примере нет пустых строк.

mask = valid.unsqueeze(-1)
pooled = (x * mask).sum(dim=1) / valid.sum(dim=1, keepdim=True)
expected = torch.tensor([[2/3, 1/3], [1/2, 1.]], dtype=weights.dtype)
torch.testing.assert_close(pooled, expected)
torch.testing.assert_close(x.mean(dim=1)[1],
                           torch.tensor([1/3, 2/3], dtype=weights.dtype))
```

Для пустых текстов нужно отдельное правило: отфильтровать их,
добавить допустимый служебный токен или определить специальный
вектор. Деление на нулевую длину не решает эту задачу.

Само значение `padding_idx=0` не создаёт маску для последующих
слоёв. В `Embedding` оно исключает вклад padding в градиент
соответствующей строки.
Для нового `nn.Embedding` эта строка по умолчанию нулевая,
но при загрузке готовой таблицы следует проверить её значение.
Усреднение, attention и вычисление функции потерь требуют
своих правил обработки padding.

Среднее в этом примере нужно для проверки арифметики.
Из него не следует, что усреднение произвольной входной таблицы
даст хороший embedding предложения.
Для этого оценивают готовую модель и её обучающую задачу.

## Bag of words: порядок отброшен намеренно

Для классификации документов можно построить вектор другого типа.
Его координата соответствует слову словаря,
а значение — числу вхождений этого слова в документ.
Для нашего корпуса, в порядке `кот, спит, пёс, бежит`:

| Текст | кот | спит | пёс | бежит |
|---|---:|---:|---:|---:|
| D1 | 2 | 1 | 0 | 0 |
| D2 | 0 | 1 | 1 | 0 |
| D3 | 1 | 1 | 0 | 1 |

Это матрица $C\in\mathbb R^{N\times M}$,
где $N=3$ — число документов, $M=4$ — число учитываемых слов.
Здесь служебные `<pad>` и `<unk>` не включены в признаки.
Значение одной ячейки

$$
C_{nj}=\operatorname{count}(v_j,D_n).
$$

Такая модель представления называется bag-of-words,
или «мешок слов». Один документ получает один вектор
фиксированной ширины, независимо от своей длины.
В нашем примере повтор `кот` увеличил счётчик до $2$,
но не создал новую координату.

В последовательном представлении D1 имел три вектора ширины $d$.
В bag-of-words у него один вектор `[2, 1, 0, 0]`.
Элементы последнего — частоты слов, а не координаты
выбранных из $E$ плотных векторов.

Цена отбрасывания порядка видна на предложениях
`John loves Mary` и `Mary loves John`:
сами токены и частоты одинаковы, а направление отношения разное.
Ни лемматизация, ни перевод для этого примера не нужны.

Часть порядка можно сохранить, добавив признаки соседних пар —
словесных биграмм. Тогда у первой строки появится `John loves`,
у второй — `Mary loves`.
Однако вектор частот биграмм тоже не хранит всю последовательность.
У `a b a c a` и `a c a b a` совпадают и частоты отдельных токенов,
и наборы пар `a b`, `b a`, `a c`, `c a`.
По этим признакам восстановить порядок двух фрагментов нельзя.
Это отличается от языковой n-граммной модели:
там по контексту вычисляют вероятность продолжения,
а здесь n-граммы служат признаками документа.

### Разреженное хранение и правила токенизации

В большом словаре один короткий документ использует
лишь небольшую долю координат. Остальные значения нулевые.
Поэтому матрицу частот обычно хранят в разреженном виде.
Например, формат CSR сохраняет ненулевые значения,
их номера столбцов и указатели границ строк.

У нашей матрицы $3\times4$ семь ненулевых ячеек.
На столь маленьком примере служебные массивы CSR могут занимать
даже больше памяти, чем сама плотная матрица.
Экономия возникает при большом числе нулей;
из слова «разреженный» не следует экономия для любых размеров.

В scikit-learn `CountVectorizer` объединяет разбиение строк
и подсчёт частот. Его стандартная обработка приводит текст
к нижнему регистру и при стандартном `token_pattern`
исключает односимвольные единицы.
Поэтому `Я люблю NLP` по умолчанию превращается
в `["люблю", "nlp"]`.
В нашем коде ниже разбиение по пробелам задано явно,
чтобы результат совпадал с ручной таблицей.

У `CountVectorizer` неизвестные слова при `transform`
по фиксированному словарю игнорируются.
Наш токенизатор сохранял для неизвестного слова позицию с ID `<unk>`;
`CountVectorizer` не добавляет такую координату.
Документ только из неизвестных слов может стать нулевым вектором.
Обработка stop words также зависит от задачи:
удаление `не` может лишить классификатор различия между
`хорошо` и `не хорошо`.

Определения признаков, разреженность, биграммы и параметры
обработки показаны в
[scikit-learn, Text feature extraction, §§8.2.3.1–8.2.3.4](https://scikit-learn.org/stable/modules/feature_extraction.html#text-feature-extraction).

### TF–IDF: частота в документе и распространённость в корпусе

Слово `спит` встречается во всех трёх документах.
Его наличие не различает эти документы.
`пёс` встречается только в D2.
Вес TF–IDF сочетает частоту в конкретном документе
(term frequency, TF) и обратную документную частоту
(inverse document frequency, IDF).

Для начала выберем несглаженный вариант
с натуральным логарифмом и без нормализации:

$$
\operatorname{tf}(w,D)=\operatorname{count}(w,D),
$$

$$
\operatorname{idf}(w)=\log\frac{N}{\operatorname{df}(w)},
$$

$$
\operatorname{tfidf}(w,D)
=\operatorname{tf}(w,D)\operatorname{idf}(w).
$$

$\operatorname{df}(w)$ — число документов, в которых слово
встречается хотя бы один раз.
У `кот` оно равно $2$, хотя суммарная частота кота
во всём корпусе равна $3$.
Для `спит` документная частота равна $3$:

| Слово | df | IDF |
|---|---:|---:|
| кот | 2 | $\log(3/2)\approx0{,}4055$ |
| спит | 3 | $\log1=0$ |
| пёс | 1 | $\log3\approx1{,}0986$ |
| бежит | 1 | $\log3\approx1{,}0986$ |

Поэтому D1 получает ненормированный вектор

$$
\begin{gathered}
(2\log(3/2),\,0,\,0,\,0)
\\
\approx(0{,}81093,\,0,\,0,\,0).
\end{gathered}
$$

Нулевой IDF у слова во всех документах — свойство
выбранной формулы. Оно не означает, что часто встречающиеся
слова всегда бесполезны для любой задачи.

### Почему библиотека выдаёт другие числа

По умолчанию `TfidfTransformer` в scikit-learn использует
сглаженную формулу с дополнительной единицей:

$$
\operatorname{idf}_{\rm sk}(w)
=1+\log\frac{N+1}{\operatorname{df}(w)+1}.
$$

В нашем порядке слов получается вектор IDF

$$
(1{,}287682,\;1,\;1{,}693147,\;1{,}693147).
$$

У слова во всех документах IDF теперь равен $1$, а не $0$.
До нормализации D1 превращается в
$(2{,}575364,\;1,\;0,\;0)$.

Затем библиотека по умолчанию делит каждую ненулевую строку
на её L2-норму. Для D1:

$$
r=\sqrt{2{,}575364^2+1^2}\approx2{,}7627,
$$

$$
\begin{gathered}
\frac{(2{,}575364,1,0,0)}{r}\\
\approx(0{,}932192,\;0{,}361965,\;0,\;0).
\end{gathered}
$$

Сглаживание, прибавление единицы и L2-нормализация —
три отдельных соглашения.
Даже `smooth_idf=False` в scikit-learn оставляет единицу
снаружи логарифма: получится $1+\log(N/\operatorname{df})$,
а не наш первый ручной вариант.
Другой параметр, `sublinear_tf=True`, заменяет положительный
счётчик $c$ на $1+\log c$.

Здесь все настройки надо читать вместе с формулой.
Определения и пошаговые числовые примеры приведены в
[scikit-learn, Tf–idf term weighting](https://scikit-learn.org/stable/modules/feature_extraction.html#tfidf-term-weighting).

```python
import numpy as np
from sklearn.feature_extraction.text import CountVectorizer, TfidfTransformer

corpus = ["кот кот спит", "пёс спит", "кот спит бежит"]
features = {"кот": 0, "спит": 1, "пёс": 2, "бежит": 3}
vectorizer = CountVectorizer(
    vocabulary=features, tokenizer=str.split,
    token_pattern=None, lowercase=False
)
counts = vectorizer.fit_transform(corpus)
np.testing.assert_array_equal(
    counts.toarray(), [[2, 1, 0, 0], [0, 1, 1, 0], [1, 1, 0, 1]]
)
assert counts.nnz == 7

transformer = TfidfTransformer()
weighted = transformer.fit_transform(counts)
expected_idf = [1 + np.log(4/3), 1., 1 + np.log(2), 1 + np.log(2)]
np.testing.assert_allclose(transformer.idf_, expected_idf)
raw_first = np.array([2 * expected_idf[0], 1., 0., 0.])
np.testing.assert_allclose(weighted.toarray()[0],
                           raw_first / np.linalg.norm(raw_first))
assert vectorizer.transform(["тигр"]).nnz == 0
```

Статистики IDF оценивают по обучающим документам.
Для validation и test вызывают `transform` с уже обученным
преобразованием. Если при кросс-валидации включить vectorizer
и классификатор в `Pipeline`, каждая обучающая часть
может получить свой словарь и IDF без подглядывания в проверочную.
Процедура разделения данных разобрана в
[[02 Areas/ML & DL/00 Учебник/00 Математические и ML-основания/05 Train, validation и test|главе о train, validation и test]].

Для сравнения ненулевых векторов часто используют косинус:

$$
\cos(u,v)=\frac{u^\top v}{\|u\|_2\|v\|_2}.
$$

Если вектор умножить на положительное число,
косинус с ним останется равным $1$.
Например, документ с вектором частот $c$
и документ с частотами $2c$ не различаются по направлению.
У L2-нормированных ненулевых векторов косинус равен
обычному скалярному произведению.
Для нулевого вектора математическая формула не определена;
возвращаемое библиотекой значение — отдельное соглашение.
Геометрия и расчёт косинуса разобраны у
[Jurafsky и Martin, Embeddings, §5.4](https://web.stanford.edu/~jurafsky/slp3/5.pdf#page=8).

## Матрица «токены × признаки» не является контекстом

После lookup два одинаковых ID получили одинаковые строки $E[i]$.
Пусть для следующего примера словарь содержит все слова фраз
`есть лук` и `натягивать лук`, а слово `лук` кодируется одним ID.
В этих фразах оно обозначает разные предметы, но в обоих
случаях выбирает одну строку $E$. Сама таблица не выбирает
значение по соседним словам.

Контекстное представление позиции может учитывать остальные
токены предложения. Его вычисляет, например, RNN или attention.
Преобразование, которое применяется к каждому исходному
вектору независимо, не получит информацию о соседних словах.
Если два входа такого преобразования одинаковы,
его результаты тоже одинаковы.

Позиционная информация решает другую задачу:
помогает различить места токенов в последовательности.
Она сама по себе не сообщает, какие слова стоят рядом.
Сходство размеров этих тензоров не делает их одной сущностью:

| Объект | Одна строка | Форма |
|---|---|---|
| Таблица $E$ | Тип токена | $\mathord{\lvert V\rvert\times d}$ |
| Выход lookup для одного текста | Позиция | $\mathord{T\times d}$ |
| Контекстные состояния одного текста | Позиция с учётом контекста | $\mathord{T\times d}$ |
| Bag-of-words корпуса | Документ | $\mathord{N\times M}$ |

Вектор целого предложения получают ещё одной операцией:
усреднением, выбором специальной позиции или обучаемым объединением.
В примере с padding мы уже получили такой вектор среднего.
Это не строка словаря и не автоматически контекстное
представление каждого слова.

Распределительная гипотеза связывает смысл со сходством
употреблений в корпусе.
Она лежит в основе многих способов обучения представлений,
но не является определением lookup.
Во введении к [Embeddings, §§5.2–5.3](https://web.stanford.edu/~jurafsky/slp3/5.pdf#page=5)
Jurafsky и Martin показывают, как контексты слов превращаются
в признаки. Обучение Word2Vec и GloVe подробно разобрано в
[[02 Areas/ML & DL/00 Учебник/02 Представление текста и токенизация/01 От слов к embeddings|главе о Word2Vec и GloVe]].

## Что мы получили — и чего пока нет

На выходе последовательной обработки есть ID формы $(B,T)$,
маска реальных позиций и векторы формы $(B,T,d)$.
На выходе bag-of-words или TF–IDF — матрица документов,
у которой другие строки и другой смысл координат.
Ни один из этих шагов сам по себе не задаёт вероятность
следующего слова.

Дальше по маршруту мы будем сохранять последовательность
токенов и вычислять вероятность продолжения по контексту.
Для n-граммной модели эти контексты — короткие цепочки ID.
Для нейросетевой модели входами станут выбранные из таблицы
векторы; как обновляется таблица по градиенту,
мы уже разобрали на одном шаге SGD.
