# Вероятность текста и предсказание следующего токена

Языковая модель не выбирает готовое предложение из хранилища и не вычисляет его
целиком за один шаг. Она получает уже известный префикс и строит распределение
вероятностей для следующего токена. Выбранный токен добавляется к префиксу, и
тот же процесс повторяется. Поэтому генерация длинного ответа сводится к одной
обучаемой операции, применённой много раз.

Этот принцип удобно увидеть на маленьком наборе имён, как в курсе Андрея
Карпати [makemore](https://www.youtube.com/watch?v=PaCmpygFfXo). Из строк
`emma`, `olivia`, `ava` можно получить множество пар «известное начало →
следующий символ». Биграммная таблица, многослойная сеть и Transformer решают
одну вероятностную задачу; различаются лишь объём контекста и способ, которым он
преобразуется в прогноз.

<a id="autoregressive-objective"></a>

## Вероятность последовательности

Правило цепочки теории вероятностей раскладывает вероятность последовательности:

$$
P(x_{1:T})=
\prod_{t=1}^{T}P(x_t\mid x_{<t}).
$$

Это тождество не требует нейросети. Модель нужна, чтобы оценивать каждое условное
распределение.

Для текста:

```text
Кот спит на
```

модель выдаёт ненормированные оценки по всему словарю. Softmax превращает их в
вероятности:

```text
диване  0.31
окне    0.18
полу    0.11
...
```

## От биграммы к длинному контексту

Биграммная модель учитывает только предыдущий токен:

$$
P(x_t\mid x_{t-1}).
$$

N-граммная модель использует фиксированное окно. Нейронная языковая модель
превращает контекст в векторы и переносит статистику между похожими контекстами.
Transformer позволяет каждой позиции учитывать весь доступный префикс.

## Один текст даёт много обучающих примеров

Из sequence:

```text
<BOS> кот спит <EOS>
```

получаются задачи:

```text
<BOS>          → кот
<BOS> кот      → спит
<BOS> кот спит → <EOS>
```

При Transformer training они вычисляются одним forward pass. Input и labels
сдвинуты на одну позицию:

```text
input:  <BOS> кот  спит
label:  кот   спит <EOS>
```

Причинная маска запрещает ранним позициям видеть правильные ответы справа.

<a id="stable-cross-entropy"></a>

## Cross-entropy считается из logits

Пусть модель вернула logits $z_{t,j}$ для всех $j\in\{1,\dots,V\}$, а правильный
следующий токен имеет индекс $y_t$. Тогда

$$
L_t=-\log P(y_t\mid x_{<t})
=\log\sum_{j=1}^{V} e^{z_{t,j}}-z_{t,y_t}.
$$

Численно устойчивое вычисление вычитает $m_t=\max_j z_{t,j}$:

$$
\log\sum_j e^{z_{t,j}}
=m_t+\log\sum_j e^{z_{t,j}-m_t}.
$$

Так ни один показатель экспоненты не положителен. Сначала вычислять обычный
softmax, а затем брать логарифм хуже: большие logits могут переполнить `exp`, а
малые вероятности — округлиться к нулю. Поэтому официальные тесты A1 сравнивают
cross-entropy непосредственно по логитам.

Средняя функция потерь берётся только по учитываемым целевым позициям:

$$
L=\frac{1}{\sum_t w_t}\sum_t w_t L_t,
$$

где $w_t=0$ для padding/ignored token и $1$ для обучающей цели. Уверенный
правильный прогноз даёт малую потерю, уверенный неправильный — большую. Это
обучает всё распределение, а не только позицию argmax.

## Perplexity

$$
\operatorname{PPL}=\exp(L).
$$

Её можно приблизительно читать как эффективное число равновероятных вариантов,
между которыми модель колеблется. Но perplexity нельзя честно сравнивать между
разными tokenizers: разбиение текста меняет число шагов предсказания и сложность
каждого шага.

<a id="objective-evidence"></a>

## Что показывает функция потерь — и чего не показывает

Cross-entropy на проверочной выборке измеряет среднее качество условных
распределений при данном токенизаторе. Она не доказывает фактическую точность,
устойчивое планирование или полезность диалога. Даже две проверочные потери
сравнимы лишь при одинаковых данных, разбиении, токенизаторе и правиле
усреднения. Perplexity наследует те же ограничения, потому что является
монотонным преобразованием функции потерь.

Практическая проверка идёт слоями: ручной сдвиг на короткой строке; сравнение
устойчиво вычисленной cross-entropy с библиотечным эталоном; переобучение одного
пакета; затем проверочная кривая без утечки. Эта цепочка переходит в
[[02 Areas/ML & DL/06 Практика/20 Собрать языковую модель с нуля#Этап 3. Функция потерь, оптимизатор, данные и контрольная точка|Capstone 1]],
где функция потерь связана с точным тестом и схемой отчёта.

## Что модель приобретает через простую задачу

Чтобы хорошо предсказывать следующий токен на большом корпусе, модели приходится
выучить:

- орфографию и синтаксис;
- устойчивые факты и имена;
- жанры и стили;
- структуру кода;
- некоторые шаблоны рассуждения.

Это не означает, что обучение следующему токену гарантирует истинность или
планирование. Он награждает правдоподобное продолжение обучающего распределения.

## Базовая модель и assistant

Базовая модель продолжает текст. Формат:

```text
User: вопрос
Assistant:
```

может вызвать диалоговое продолжение и у base LM: такой формат встречается
в текстах, а поведение может задаваться примерами в контексте. Это не равно
надёжному выполнению роли помощника. GPT-3 исследует перенос задач через
контекст без обновления весов ([Brown et al.](https://arxiv.org/abs/2005.14165));
последующее обучение на инструкциях и предпочтениях целенаправленно формирует
следование инструкциям и поведение assistant
([Ouyang et al.](https://arxiv.org/abs/2203.02155)). Архитектура при этом может
остаться той же; меняются веса и распределение поведения, а не сам факт
возможности продолжить диалоговый префикс.

## Минимальная реализация функции потерь

```python
import torch.nn.functional as F

# token_ids: [B, T+1]; token_valid marks real positions, including true EOS.
input_ids = token_ids[:, :-1]
labels = token_ids[:, 1:].clone()
target_valid = token_valid[:, 1:].bool()
labels[~target_valid] = -100
if not target_valid.any():
    raise ValueError("batch has no target tokens")
logits = model(input_ids)              # tensor [B, T, V]; model handles attention masks
loss = F.cross_entropy(
    logits.reshape(-1, logits.size(-1)),
    labels.reshape(-1),
    ignore_index=-100,
)
```

Здесь маска строится по **позициям**, а не сравнением ID с `pad_id`.
Например, при общем ID 2 для EOS и padding строка `[BOS, кот, 2, 2]`
с `token_valid=[1,1,1,0]` даёт labels `[кот,2,-100]`: настоящий EOS
остаётся целью. Если заменить все ID 2 на `-100`, модель перестанет
учиться завершению. Маска loss не заменяет маску attention: реальный
батч с padding должен также передать модели сведения о допустимых
входных позициях. Контракт вызова модели здесь намеренно абстрактный.

Самая опасная ошибка здесь — неверный shift: модель может получить текущий
токен вместо следующего и показать искусственно малую потерю.
