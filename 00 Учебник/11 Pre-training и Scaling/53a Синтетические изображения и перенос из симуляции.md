# Синтетические изображения и перенос из симуляции

A renderer can produce a photograph of a scene together with the identity,
distance and category of the surface visible at each pixel. A camera photograph
contains no such annotation. Training on rendered images therefore replaces
part of the collection and labelling work with scene construction, rendering
and a test of whether the resulting model works on real inputs.

Changing the colour of a stored photograph is an augmentation. Moving a camera
in a three-dimensional scene can reveal a previously hidden surface and change
which object covers each pixel. That requires a new render and new geometric
annotations. A text-to-image model provides another kind of synthetic input:
its prompt describes the desired scene but does not supply verified masks,
boxes or object counts.

<a id="renderer-annotations"></a>
## Scene state becomes an image and an annotation

In BlenderProc's semantic-segmentation example, objects have a `category_id`.
The renderer can return per-pixel category and instance maps along with RGB
and depth. An instance identifies one object; a category can be shared by
several objects. Their numerical IDs need not have the same meaning across
independently constructed scenes.

The original configuration requests three kinds of object information:

```python title="Original BlenderProc semantic-segmentation excerpt"
# enable segmentation masks (per class and per instance)
bproc.renderer.enable_segmentation_output(map_by=["category_id", "instance", "name"])
```

The surrounding script and its scene are required. `name` is not a numerical
pixel value, so BlenderProc also writes a dictionary relating instance IDs
to object attributes. Keeping only a colour preview would discard that mapping.
The code and explanation are from the pinned GPL-3.0 example linked above.

Consider a small instance map containing background 0, cylinder instances
1 and 3, and monkey instance 2. If both cylinders belong to category 1,
their category pixels match even though their instance pixels differ:

```python
import torch

instance = torch.tensor([[0, 1, 1, 0, 3, 3],
                         [0, 1, 1, 2, 3, 3],
                         [0, 0, 2, 2, 2, 0]])
category_by_instance = torch.tensor([0, 1, 2, 1])
semantic = category_by_instance[instance]
assert (instance == 1).sum().item() == 4
assert (instance == 3).sum().item() == 4
assert (semantic == 1).sum().item() == 8
assert torch.equal(semantic[instance == 2], torch.full((4,), 2))
assert not torch.equal(instance, semantic)
print("instance map", instance.tolist())
print("category map", semantic.tolist())
```

This indexing example is not a renderer. It checks the annotation relationship.
An object absent from the visible map may still exist behind another object.
A visible bounding box encloses visible pixels; an amodal box describes the
whole object, including its hidden part. A training pipeline must say which
target it exports. A perfectly rendered mask can still use the wrong category
mapping for the task.

### Camera coordinates must match the target

For a pinhole camera in a computer-vision convention, let
$(X_c,Y_c,Z_c)$ be a point in the camera frame with positive depth $Z_c$.
With focal lengths $f_x,f_y$ and principal point $(c_x,c_y)$,

$$
u=f_x\frac{X_c}{Z_c}+c_x,
\qquad
v=f_y\frac{Y_c}{Z_c}+c_y.
$$

Take world point $(1,2,5)$, camera centre $(1,0,0)$ and identity rotation.
The camera point is $(0,2,5)$. For $f_x=f_y=100$ and principal point
$(320,240)$, its pixel is $(320,280)$. Moving the camera changes this target
even when the object's world coordinates stay fixed.

```python
import torch

point_world = torch.tensor([1., 2., 5.], dtype=torch.float64)
camera_center = torch.tensor([1., 0., 0.], dtype=torch.float64)
rotation_world_to_camera = torch.eye(3, dtype=torch.float64)
point_camera = rotation_world_to_camera @ (point_world-camera_center)
assert point_camera[2] > 0
pixel = 100*point_camera[:2]/point_camera[2] + torch.tensor([320., 240.])
torch.testing.assert_close(pixel, torch.tensor([320., 280.], dtype=pixel.dtype))
assert 0 <= pixel[0] < 640 and 0 <= pixel[1] < 480
print("camera point", point_camera, "pixel", pixel)
```

Positive depth and an in-frame projection do not establish visibility:
another surface may be nearer along the ray. Depth testing resolves that.
Camera-to-world and world-to-camera transforms are inverses, not interchangeable
arrays. Blender's viewing-axis convention also differs from the positive-depth
convention above; a production exporter must perform the corresponding basis
conversion rather than copying this formula onto an arbitrary Blender matrix.

## Randomize the scene variables that could become shortcuts

Suppose every rendered cylinder is purple and every rendered sphere is green.
A classifier can learn colour instead of shape. Randomizing object materials
can remove that particular association. It will not help a task whose answer
depends on colour, such as distinguishing signal states.

The example collects the loaded materials, then makes a separate replacement
decision for every material slot:

```python title="Original BlenderProc material-randomization excerpt"
# Collect all materials
materials = bproc.material.collect_all()

# Go through all objects
for obj in objs:
    # For each material of the object
    for i in range(len(obj.get_materials())):
        # In 50% of all cases
        if np.random.uniform(0, 1) <= 0.5:
            # Replace the material with a random one
            obj.set_material(i, random.choice(materials))
```

A replacement can draw the same material again. If there are $K$ equally
likely material objects and the current one is in the pool, the probability
of a different material identity is $0.5(K-1)/K$, not 0.5. With four materials
it is 0.375. Distinct material objects can also render similarly; identity
change and perceptual change are separate measurements.

```python
from fractions import Fraction

materials = ["red", "green", "blue", "grey"]
current = "red"
replacement_probability = Fraction(1, 2)
changed = sum(replacement_probability/Fraction(len(materials))
              for material in materials if material != current)
assert changed == Fraction(3, 8)
assert changed < replacement_probability
print("probability of a different identity", float(changed))
```

Camera sampling adds another distribution over the data. The released example
samples a location in a box, aims the camera at a point of interest, and adds
an in-plane rotation. These choices are coupled: aiming at the scene is not
the same as independently sampling every Euler angle.

poi = bproc.object.compute_poi(objs)
# Sample five camera poses
for i in range(5):

    location = np.random.uniform([-10, -10, 8], [10, 10, 12])

The values in this original excerpt use the scene's coordinate units and
radians. They are not calibrated camera offsets for a new robot. Scene scale,
intrinsics, camera height, distortion, motion blur and sensor noise must be
chosen for the intended acquisition process.

### Domain randomization is a training distribution

Let $z$ contain scene geometry and identities, and $\xi$ contain sampled
camera, lighting, texture and sensor parameters. A renderer supplies
$x=R(z,\xi)$ and an annotation procedure supplies $y=a(z,\xi)$.
The randomized training objective averages loss over both:

$$
L(\theta)=\mathbb E_{z,\xi}
\big[\ell(f_\theta(R(z,\xi)),a(z,\xi))\big].
$$

For world-position regression, a colour change may leave $y$ unchanged.
For pixel masks, a camera change generally changes $y$. A fully occluded
object may require a visibility flag or exclusion rather than its old box.

Tobin et al., [§III](https://arxiv.org/html/1703.06907v1#S3), randomize
textures, distractors, lighting, camera parameters and noise for tabletop
localization. Their camera range is centred on an approximate real viewpoint;
the table height remains fixed. The task therefore has constraints that a
generic claim of arbitrary real-world transfer would omit. The real-image
evaluation and ablations in §IV distinguish textures, distractors, camera
variation and added noise rather than treating all randomness as one variable.

More simulated samples improve coverage only relative to the chosen generator.
If a rare but relevant event has probability $p$, then $n$ independent draws
miss it with probability $(1-p)^n$. With $p=0.001$ and $n=1000$, that
probability is about 0.368. If the simulator assigns it probability zero,
sampling more cannot produce it.

```python
from math import ceil, log, log1p

p, n = .001, 1000
miss = (1-p)**n
required = ceil(log(.05)/log1p(-p))
assert .367 < miss < .369
assert required == 2995
assert (1-p)**required <= .05 < (1-p)**(required-1)
assert (1-0.)**1_000_000 == 1.
print("miss probability", miss, "draws for at least 95% coverage", required)
```

This calculation assumes independent draws. Thousands of views of one mesh
do not create new object shapes. A shared texture library, asset family or
camera trajectory can also make views dependent. Dataset splits should retain
those parent identities, including asset and generator versions.

<a id="domain-shift-risk"></a>
## The source and target risks can disagree

Let $P_S(x,y)$ describe rendered source data and $P_T(x,y)$ describe real
target data. The target risk is $R_T(f)=\mathbb E_{P_T}\ell(f(x),y)$.
A held-out simulator split estimates a source risk, even if its renders were
not used for training. It does not become a real-world test by being held out.

For a two-condition example, suppose dark and bright scenes have source
probabilities $(0.2,0.8)$ and target probabilities $(0.8,0.2)$.
A fixed classifier's conditional losses are $(0.1,0.6)$. Then source risk
is $0.2(0.1)+0.8(0.6)=0.5$, whereas target risk is 0.2.
The difference comes from weighting the same conditional losses differently.

Under covariate shift, the conditional target law remains the same:
$P_T(y\mid x)=P_S(y\mid x)$, while the input distribution changes.
If every relevant target input has source support, importance weighting gives

$$
R_T(f)=\mathbb E_{P_S}
\left[\frac{p_T(x)}{p_S(x)}\ell(f(x),y)\right].
$$

The two weights here are 4 and 0.25. The identity does not apply unchanged
when the labelling rule changes or target mass lies outside source support.
Estimating large weights from limited data can also produce high variance.
[Sugiyama, Krauledat and Müller](https://jmlr.org/papers/v8/sugiyama07a.html)
develop importance-weighted model selection under the covariate-shift assumption.

```python
from math import isclose

source_mass = [.2, .8]
target_mass = [.8, .2]
conditional_loss = [.1, .6]
source_risk = sum(p*l for p, l in zip(source_mass, conditional_loss))
target_risk = sum(p*l for p, l in zip(target_mass, conditional_loss))
weights = [t/s for s, t in zip(source_mass, target_mass)]
weighted_risk = sum(s*w*l for s, w, l in zip(source_mass, weights, conditional_loss))
assert weights == [4., .25]
assert isclose(source_risk, .5) and isclose(target_risk, .2)
assert isclose(weighted_risk, target_risk)
print("source", source_risk, "target", target_risk, "weights", weights)
```

A different camera can change image statistics while preserving the task.
A changed class definition, annotation convention or class-dependent shortcut
can change $P(y\mid x)$ as well. Comparing unlabelled image histograms alone
does not determine which of these happened.

<a id="domain-adversarial-learning"></a>
## DANN trains a label predictor and an opposing domain predictor

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/sim-to-real-2026-10-28/dann-architecture.png|Original Ganin et al. DANN architecture and gradient directions]]

*Yaroslav Ganin et al.,
[Domain-Adversarial Training of Neural Networks, Figure 1, p.12](https://jmlr.org/papers/volume17/15-239/15-239.pdf#page=12).
CC-by under the [JMLR publication policy](https://jmlr.org/author-info.html#publication).
Full original diagram and derivative legend, extracted at 400 dpi without
redrawing or translated labels.*

The feature extractor $F$ ($G_f$ in the figure) feeds two heads. The label
head $C$ ($G_y$) predicts an object class from labelled source examples.
The domain head $D$ ($G_d$) predicts
whether a feature came from source or target. It needs domain membership,
not target class labels. In unsupervised adaptation, target images participate
in the domain loss while their class labels remain unavailable to training.

The domain head learns to separate the domains. The feature extractor receives
the opposite domain gradient, encouraging representations that this head
cannot separate, while still learning the labelled source task.
For source class loss $L_y$ and domain loss $L_d$, the gradient used to update
the extractor parameters $\theta_F$ is

$$
g_F=\nabla_{\theta_F}L_y-\lambda\nabla_{\theta_F}L_d.
$$

Ganin et al., §4.2, equations 13–15, specify the opposed gradient directions.
Their deep experiments in §5.2.2 use a scheduled $\lambda$ for the extractor
and a fixed multiplier 1 for the domain head. The implementation below follows
that convention: the domain head minimizes $L_d$, without multiplying its
gradient by the scheduled $\lambda$.

### Gradient reversal changes the backward rule

A gradient-reversal layer is the identity in the forward pass, but sends
$-\lambda g$ upstream in the backward pass. It is a custom optimization
rule, not the ordinary derivative of the identity function. It has no learned
parameters. With $\lambda=0$, the domain head can still train while its
gradient no longer reaches the extractor.

```python
import torch
import torch.nn.functional as F

class Reverse(torch.autograd.Function):
    @staticmethod
    def forward(ctx, features, strength):
        ctx.strength = strength
        return features.view_as(features)

    @staticmethod
    def backward(ctx, gradient):
        return -ctx.strength*gradient, None

features = torch.tensor([[1., 0.], [0., 1.]], dtype=torch.float64, requires_grad=True)
domain_weight = torch.tensor([[.4, -.2]], dtype=torch.float64, requires_grad=True)
domain_labels = torch.tensor([0., 1.], dtype=torch.float64)
plain_logits = (features @ domain_weight.T).flatten()
plain_loss = F.binary_cross_entropy_with_logits(plain_logits, domain_labels)
plain_f, plain_d = torch.autograd.grad(plain_loss, (features, domain_weight))
reversed_logits = (Reverse.apply(features, .7) @ domain_weight.T).flatten()
loss = F.binary_cross_entropy_with_logits(reversed_logits, domain_labels)
actual_f, actual_d = torch.autograd.grad(loss, (features, domain_weight))
torch.testing.assert_close(reversed_logits, plain_logits)
torch.testing.assert_close(actual_f, -.7*plain_f)
torch.testing.assert_close(actual_d, plain_d)
print("feature gradient", actual_f, "domain-head gradient", actual_d)
```

Use a positive domain cross-entropy with this layer. Negating that loss again
would cancel the reversal for the extractor and make the domain head maximize
its own error. Checking both gradient signs detects that mistake; observing
the same scalar forward loss would not.

### One update without target class labels

The next program uses `Reverse` from the preceding block. Four fixed source
points have class labels; four target points have only domain labels.
The source mean class loss and the combined domain mean loss are normalized
separately. Other source/target sampling ratios require explicit weighting.

```python
import torch
import torch.nn.functional as F
from torch import nn

torch.manual_seed(71)
source = torch.tensor([[-2., 0.], [-1., 0.], [1., 0.], [2., 0.]], dtype=torch.float64)
target = source + torch.tensor([0., 1.])
source_labels = torch.tensor([0, 0, 1, 1])
domains = torch.tensor([0., 0., 0., 0., 1., 1., 1., 1.], dtype=torch.float64)
encoder = nn.Linear(2, 3).double()
class_head = nn.Linear(3, 2).double()
domain_head = nn.Linear(3, 1).double()
parameters = list(encoder.parameters())+list(class_head.parameters())+list(domain_head.parameters())
optimizer = torch.optim.SGD(parameters, lr=.01)
features = encoder(torch.cat([source, target]))
class_loss = F.cross_entropy(class_head(features[:len(source)]), source_labels)
domain_logits = domain_head(Reverse.apply(features, .5)).flatten()
domain_loss = F.binary_cross_entropy_with_logits(domain_logits, domains)
before = [parameter.detach().clone() for parameter in parameters]
optimizer.zero_grad()
(class_loss+domain_loss).backward()
assert all(p.grad is not None and torch.isfinite(p.grad).all() for p in parameters)
assert encoder.weight.grad.norm() > 0 and domain_head.weight.grad.norm() > 0
optimizer.step()
assert any(not torch.equal(old, new) for old, new in zip(before, parameters))
print("source class loss", class_loss.item(), "domain loss", domain_loss.item())
```

This executes the data path and update, not the paper's image-classification
benchmark. The domain head is not needed to classify an image after training.
Fine-tuning on labelled real examples instead supplies direct target-task
supervision. Self-training uses predicted target labels and can propagate
confident mistakes. These methods differ in which target information they use;
they can also be combined with randomized synthetic pretraining.

<a id="alignment-limits"></a>
## Matching marginals does not identify the target labels

Suppose a scalar feature is 0 or 1, equally often in both domains. In the source,
the class equals the feature. In the target, the class is reversed. A domain
classifier sees identical feature distributions and cannot separate them,
yet the source rule is wrong on every target example.

```python
from fractions import Fraction

source = [(0, 0), (1, 1)]
target = [(0, 1), (1, 0)]
assert sorted(x for x, y in source) == sorted(x for x, y in target)
source_error = sum(x != y for x, y in source)/len(source)
target_error = sum(x != y for x, y in target)/len(target)
best_domain_accuracy = sum(max(Fraction(1, 4), Fraction(1, 4)) for x in [0, 1])
assert source_error == 0 and target_error == 1
assert best_domain_accuracy == Fraction(1, 2)
print("domain accuracy", float(best_domain_accuracy), "target error", target_error)
```

Ganin et al.'s theoretical discussion includes the error of a hypothesis that
must work on both domains; a small discrepancy term alone is insufficient.
In practice, chance domain accuracy can also mean an undertrained domain head
or collapsed features. Target-task evaluation and preservation of class
information therefore remain necessary.

### A small distance can omit the distinction the task needs

The FID proposed by [Heusel et al., p.6, equation 6](https://arxiv.org/abs/1706.08500v6)
compares fitted Gaussian moments in a chosen feature representation.
In one dimension its population Gaussian expression is
$(\mu_S-\mu_T)^2+(\sigma_S-\sigma_T)^2$, where $\mu$ is the mean and
$\sigma$ the standard deviation.
It is not a comparison of every property of two image distributions.

For a numerical counterexample, put source probability 1/2 at −1 and 1.
Put target probability 1/4 at each of $-\sqrt2,\sqrt2$, and 1/2 at 0.
Both distributions have mean 0 and variance 1, hence Gaussian-moment distance 0,
despite having different supports. An RBF-kernel MMD can distinguish this pair.
The population kernel expression is from
[Gretton et al., §2.2, Lemma 6](https://jmlr.org/papers/v13/gretton12a.html).
For independent $x,x'\sim P_S$ and $y,y'\sim P_T$, it is

$$
\begin{aligned}
\operatorname{MMD}^2
&=\mathbb E[k(x,x')]+\mathbb E[k(y,y')]\\
&\quad-2\mathbb E[k(x,y)].
\end{aligned}
$$

The Gaussian radial-basis kernel $k(a,b)=\exp(-(a-b)^2/2)$ gives a larger
similarity to nearby feature values. The program expands these expectations
as finite weighted sums; it obtains approximately 0.03635. This use of
population probabilities includes repeated values, unlike the off-diagonal
formula for an unbiased statistic estimated from a finite sample.

```python
from math import exp, isclose, sqrt

source = [(-1., .5), (1., .5)]
target = [(-sqrt(2), .25), (0., .5), (sqrt(2), .25)]
def moments(distribution):
    mean = sum(x*p for x, p in distribution)
    variance = sum(p*(x-mean)**2 for x, p in distribution)
    return mean, variance
def kernel_mean(left, right):
    return sum(p*q*exp(-(x-y)**2/2) for x, p in left for y, q in right)
ms, vs = moments(source)
mt, vt = moments(target)
gaussian_distance = (ms-mt)**2+(sqrt(vs)-sqrt(vt))**2
mmd_squared = kernel_mean(source, source)+kernel_mean(target, target)-2*kernel_mean(source, target)
assert isclose(gaussian_distance, 0., abs_tol=1e-14)
assert mmd_squared > 0
print("Gaussian moment distance", gaussian_distance, "RBF MMD squared", mmd_squared)
```

This example computes population sums on finite distributions, not an image
FID benchmark. Sample estimates, kernel choice, feature extractor and sample
count add further choices. Neither a low FID nor aligned feature marginals
alone verifies label correctness or safety of a deployed classifier.

<a id="synthetic-real-validation"></a>
## Choose mixtures using real validation data

A synthetic fraction specifies neither the diversity of scenes nor how often
their parents repeat. One million images from ten meshes can be less varied
along the required shape dimension than a smaller collection of independent
objects. Split by the intended generalization unit: object instance or mesh
family, environment, acquisition session, person or time period.

For each candidate mixture, hold the training budget and evaluation protocol
fixed, then evaluate on a real validation set. Keep the final real test set
separate from choices of mixture, augmentation strength and checkpoint.
Synthetic-only, real-only and combined training are controls, not an assumed
ranking in which 50/50 must win. Real-only can be preferable; synthetic-only
can transfer in a restricted task; the required evidence is the target result.

Report per-condition errors as well as aggregate quality. A rendering method
can cover textures well while missing motion blur, transparent surfaces,
sensor saturation or a class-dependent annotation convention. For safety-related
uses, a finite set of successful synthetic tests does not establish coverage
of all relevant real failures.

<a id="synthetic-privacy"></a>
## Synthetic does not mean private

A hand-built procedural scene need not contain a private person's records.
A generator trained on private photographs has a different dependency chain:
private records affect model weights, which affect generated images.
Carlini et al., [Extracting Training Data from Diffusion Models](https://arxiv.org/abs/2301.13188),
demonstrate extraction of training examples with a generate-and-filter attack.
This establishes that synthetic outputs can disclose training examples;
it does not assign the same extraction rate to every model or prompt.

Nearest-neighbour checks and extraction attempts can find disclosure, but a
failed attempt does not prove that no record can be disclosed. Differential
privacy is a guarantee of a mechanism under a stated neighbouring-dataset
definition and budget. If a generator was trained with an appropriate DP
guarantee, generating samples from its released state without renewed access
to private records is post-processing. Training another generator, querying
private records to choose prompts, or filtering against a private database
can introduce additional access that needs its own analysis.

The definition, protected unit, clipping/noise mechanism and composition are
developed in [[02 Areas/ML & DL/00 Учебник/18 Evaluation и методология/59a Responsible systems#Приватность и дифференциальная приватность|Responsible systems: privacy]].
Do not attach a privacy claim to a corpus only because its files were rendered
or generated. Record which assets, training records and downstream operations
