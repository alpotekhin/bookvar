# 41. Сбор, очистка и смеси данных

На странице с ответом о Python рядом с полезным объяснением находятся меню,
предложение войти в аккаунт, объявления и ссылки на другие вопросы. Если просто
удалить HTML-теги, всё это станет одним обучающим документом. Если извлекать
только длинные абзацы, можно потерять сам пример кода. Оба результата получены
из одного URL, но учат языковую модель разному.

При подготовке корпуса приходится последовательно решать три задачи: получить
сохраняемую копию источника, извлечь из неё нужное содержание и определить,
сколько раз оно встретится при обучении. Качество каждой операции проверяют
отдельно. Правильный язык ещё не означает полезный текст; хороший документ
не обязательно следует повторять сто раз; большой архив не обязательно
содержит много разных примеров.

**До этой главы:** [[02 Areas/ML & DL/00 Учебник/11 Pre-training и Scaling/01 Данные и pre-training|Данные и предобучение]].

## От сырого источника к обучающему потоку

### От живого сервиса к неизменяемой записи

<!-- source_unit_id: lecture-13-common-crawl-data-pipeline -->

URL обозначает адрес, но не фиксирует содержимое. Завтра автор исправит статью,
сайт изменит шаблон, а страница форума покажет другие сообщения. Для повторяемого
эксперимента сохраняют полученный ответ и дату загрузки. Краулер обходит ссылки
и создаёт такой снимок; он не видит весь интернет, а получает доступную ему часть
страниц. Авторизация, ограничения сервера и содержимое, появляющееся только после
действий в приложении, делают эту часть неполной. В CS336 этот переход разобран
отдельно: [живой сервис, обход и архив](https://github.com/stanford-cs336/lectures/blob/8b59b50730766695c2ffedd1a79c50cd09b9eb91/lecture_13.py#L90-L156).

[Common Crawl](https://commoncrawl.org/blog/web-archiving-file-formats-explained)
предоставляет несколько представлений результатов обхода:

| Формат | Что находится в записи | Для чего использовать |
| --- | --- | --- |
| WARC | Исходный ответ, например HTML, HTTP-заголовки и архивные метаданные | Повторить извлечение текста другим способом |
| WAT | Производные метаданные, в том числе ссылки и сведения о странице | Анализировать сайты и связи, не разбирая HTML заново |
| WET | Текст, уже извлечённый из страницы | Быстро получить текстовый корпус, приняв решения исходного экстрактора |

WET экономит этап извлечения, но не сохраняет исходную структуру HTML. По строке
«Название Цена Размер» нельзя надёжно восстановить ячейки таблицы. Поэтому для
документа полезно хранить ссылку на соответствующую WARC-запись. Сам архив тоже
может содержать неполный ответ: например, при прерванной загрузке или ограничении
размера. Признак `WARC-Truncated` следует учитывать до извлечения текста, а не
объяснять позднее обрыв статьи ошибкой языковой модели.

У других источников удобнее использовать собственные форматы. Wikipedia
публикует дампы; код можно получить из Git-репозитория вместе с идентификатором
коммита; задачи и обсуждения — через отдельный API или архив событий. Для статьи
PDF, исходный LaTeX и метаданные представляют разные объекты. Их версии и условия
использования фиксируют по отдельности. Наличие файла в публичном архиве само
по себе не определяет условия его дальнейшего распространения.

### Как выглядит запись корпуса

Текст не должен терять связь с источником после первой очистки. Ниже — учебный
пример записи, а не схема Common Crawl. Числа и идентификаторы условные.

```json
{
  "document_id": "crawl17:record0042",
  "source": "web",
  "url": "https://example.org/python-arrays",
  "crawl_id": "crawl17",
  "retrieved_at": "2026-10-01T12:00:00Z",
  "raw_locator": "shard003.warc.gz#record0042",
  "extractor_version": "extractor-v2",
  "text": "An array stores...",
  "language": "en",
  "language_score": 0.97,
  "quality_score": 0.81,
  "decision": "keep",
  "tokenizer_revision": "tokenizer-v3",
  "token_count": 420
}
```

В рабочем корпусе к этой записи добавляют контрольные суммы исходных байтов и
извлечённого текста, версию фильтров и основания использования. Оценка
`quality_score` без версии классификатора бесполезна: после переобучения значение
0,81 может означать другое решение. По той же причине число токенов имеет смысл
только вместе с версией токенизатора.

Решение об удалении и признаки лучше записывать отдельно от текста. Тогда
изменение порога с 0,8 до 0,7 не требует повторно скачивать страницы и вычислять
оценки. Для удалённого документа остаётся объяснение: неподходящий тип содержимого,
пустой результат извлечения, другой язык или конкретное правило фильтра. Это
позволяет отличить ожидаемый отбор от ошибки обработки целого файла.

## Извлечение определяет, какой документ увидит модель

<!-- source_unit_id: lecture-14-section-2-lecture-14-data-ii -->
<!-- source_unit_id: lecture-14-figure-step-19-rendering-1 -->
<!-- source_unit_id: lecture-14-figure-step-21-rendering-1 -->
<!-- source_unit_id: assignment-04-task-extract-text -->
<!-- source_unit_id: assignment-04-deliverable-extract-text-005 -->
<!-- source_unit_id: assignment-04-deliverable-extract-text-006 -->

Из HTML нужно извлечь содержание страницы, а не просто удалить угловые скобки.
Браузер показывает текст меню, баннера и статьи одновременно; только часть этого
текста относится к документу. Экстрактор использует структуру дерева HTML,
плотность текста, долю ссылок и другие признаки, чтобы отделить основное содержание
от повторяющегося оформления (*boilerplate*). Но правило «оставлять длинные
абзацы» может убрать короткий ответ, заголовок или программу.

Рассмотрим маленький фрагмент документации:

```html
<nav>Home | Login | Products</nav>
<main>
  <h1>Filtering positive values</h1>
  <p>Keep elements greater than zero:</p>
  <pre>positive = [x for x in values if x > 0]</pre>
</main>
<footer>Subscribe | Privacy policy</footer>
```

Полезный результат сохраняет заголовок, объяснение и строку кода в таком порядке.
При сохранении всех видимых строк модель дополнительно учится продолжениям
«Login | Products» и «Subscribe | Privacy policy». При удалении `<pre>` объяснение
остаётся без ответа. Для таблицы нужно сохранить соответствие заголовков и ячеек,
а не просто выписать все слова; для Python — значимые отступы. Поэтому один
экстрактор проверяют на нескольких типах страниц: статьях, форумах, документации,
каталогах и страницах с таблицами.

Есть и более ранний источник ошибок: HTML приходит как байты. Если не-UTF-8
страницу декодировать с безусловным `errors="ignore"`, часть букв исчезнет ещё
до определения языка. В
[Assignment 4, §2.2](https://github.com/stanford-cs336/assignment4-data/blob/0555bea66369872d912652debf10b115ca0688c8/cs336_assignment4_data.pdf)
предлагается сначала корректно декодировать ответ, при необходимости определить
кодировку и затем вызвать `resiliparse.extract.html2text.extract_plain_text`.
Проверка на одном корректном UTF-8 документе не покрывает этот случай: отдельно
нужны входы с другой кодировкой, HTML-сущностями, незакрытыми тегами и пустым телом.

### Проверка извлечения: текст и обученная модель

Для нескольких десятков страниц можно вручную сопоставить исходник и результат:
что осталось от основного текста, сколько навигации сохранилось, не переставились
ли строки и не исчезли ли формулы. Долю сохранённых символов считать полезно,
но сама по себе она ничего не говорит о правильности: экстрактор, оставляющий
вообще всё, выигрывает по этому показателю.

В DCLM провели следующую проверку: извлекли текст тремя способами, применили
одинаковые эвристики RefinedWeb и обучили модели по фиксированному рецепту
**1B–1×** — примерно 1,4 млрд параметров и 28,8 млрд обучающих токенов.
Результаты из таблицы 3 статьи:

| Извлечение текста | Core ↑ | Extended ↑ |
| --- | ---: | ---: |
| Resiliparse | 24,1 | 13,4 |
| Trafilatura | 24,5 | 12,5 |
| Готовые WET-файлы | 20,7 | 12,2 |

Это сводные оценки языковой модели на группах задач DCLM, **не точность
HTML-парсера**. В данном опыте оба повторных извлечения из HTML лучше готового
WET по Core; лучший результат по Core и по Extended при этом у разных
экстракторов. Из таблицы нельзя вывести единственного победителя для любых
документов. Источник: Jeffrey Li и соавторы,
[DataComp-LM, §4.2 и таблица 3](https://arxiv.org/html/2406.11794v4#S4.SS2).

### Почему PDF требует отдельного разбора

В PDF порядок объектов не обязан совпадать с порядком чтения. Две колонки
могут храниться как набор текстовых фрагментов с координатами; таблица — как
отдельные строки и линии; скан страницы вообще не содержит распознанных букв.
Поэтому наличие извлекаемого текста ещё не означает, что он правильно собран.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/corpus-collection-review-2026-10/docling-pdf-pipeline.png]]

*Nikolaos Livathinos и соавторы, [Docling, рисунок 1](https://arxiv.org/html/2501.17887v1#S1.F1),
CC BY 4.0. Оригинал без изменений. Верхняя ветвь разделяет распознавание текста,
анализ расположения блоков и восстановление таблиц; только затем части собираются
в документ. Это схема устройства инструмента, а не результат сравнения качества.*

Для цифрового PDF можно читать текстовые объекты и восстанавливать порядок по
координатам. Для скана требуется OCR. Модель анализа разметки помогает выделить
заголовки, абзацы и таблицы; модель распознавания таблиц восстанавливает ячейки.
Вариант с VLM получает изображение страницы и генерирует текст, поэтому к ошибкам
распознавания добавляется риск выдуманного содержимого. Проверять такой результат
нужно по исходной странице, а не только другой языковой моделью.

В [FinePDFs](https://huggingfacefw-finepdfsblog.hf.space/)
использовали разные пути для документов с извлекаемым текстом и документов,
требующих OCR. Это позволяет не запускать дорогой распознаватель на каждой
странице, но добавляет ещё одну проверяемую ошибку: скан может быть неверно
направлен в обычный парсер и дать пустой результат.

После извлечения сохраняют хэш результата, версию программы, выбранную кодировку
и предупреждения. Если после обновления программы средняя длина документов
уменьшилась вдвое, это повод просмотреть исходники: возможно, удалено меню,
а возможно — вторая колонка каждой статьи.

<a id="language-id"></a>
## Определение языка — задача с отказом, а не один ярлык

<!-- source_unit_id: assignment-04-task-language-identification -->
<!-- source_unit_id: assignment-04-deliverable-language-identification-007 -->
<!-- source_unit_id: assignment-04-deliverable-language-identification-008 -->
<!-- source_unit_id: assignment-04-deliverable-language-identification-009 -->

Классификатор языка получает извлечённый текст и возвращает метку с численной
оценкой. Например, [готовая модель fastText `lid.176`](https://fasttext.cc/docs/en/language-identification.html)
различает 176 языков и обучена на Wikipedia, Tatoeba и SETimes. В её ответе
`en, 0.97` число 0,97 — оценка модели. Это не обещание, что ровно 97% подобных
страниц действительно английские: соответствие оценки частоте правильных
ответов нужно проверять на своём корпусе.

Короткая строка «Java, Python, Go» почти не даёт языковых признаков. Статья
на русском с английским меню может изменить метку после качественного удаления
навигации. Документация нередко содержит английский текст, код и цитату на другом
языке. Если задача требует учитывать такие случаи, поверх классификатора
добавляют решение `unknown` или `mixed`, либо отдельно анализируют абзацы.
Стандартная метка языка всего документа этого различия не гарантирует.

Пусть из 100 вручную проверенных страниц 80 подходят для английского корпуса.
При низком пороге фильтр сохраняет 78 подходящих и 12 неподходящих страниц.
Его точность равна $78/(78+12)\approx86{,}7\%$, а полнота — $78/80=97{,}5\%$.
После повышения порога он оставляет 70 подходящих и 2 неподходящих:
точность становится $70/72\approx97{,}2\%$, полнота падает до $70/80=87{,}5\%$.
Это **условный пример**, показывающий цену порога. На реальном корпусе даже
рост точности при повышении порога следует подтвердить измерением.

Ошибки распределены неравномерно. Полезно отдельно разметить короткие и длинные
документы, разговорные тексты, код и смешанные языки. Иначе хорошая средняя
точность на длинных новостных статьях скроет удаление коротких ответов. В
[Assignment 4, §2.3](https://github.com/stanford-cs336/assignment4-data/blob/0555bea66369872d912652debf10b115ca0688c8/cs336_assignment4_data.pdf)
ручная проверка случайных записей отделена от двух программных тестов интерфейса:
успех тестов на английском и китайском не доказывает качество фильтра на вебе.

Кроме доли документов считают долю токенов. Девять подходящих страниц по
100 токенов и одна неподходящая на 9 100 токенов дают 90% подходящих документов,
но только 9% подходящих токенов. Именно второй состав будет преобладать
в обучающем потоке, если документы используются целиком.

В [CCNet](https://arxiv.org/abs/1911.00359) после определения языка документы
дополнительно ранжируются по перплексии языковой модели, обученной на Wikipedia.
Это уже другой вопрос: не «на каком языке написан текст», а «насколько он
похож на тексты, знакомые этой модели». Смешивать два решения в один
необъясняемый порог не стоит: хороший специализированный текст может быть
очевидно английским и при этом иметь высокую перплексию.

## Фильтрация: какие документы оставлять

<!-- source_unit_id: lecture-13-section-420-model-based-filtering -->
<!-- source_unit_id: lecture-14-quality-filter-experiment -->
<!-- source_unit_id: lecture-14-figure-step-32-rendering-1 -->
<!-- source_unit_id: lecture-14-figure-step-93-rendering-1 -->
<!-- source_unit_id: assignment-04-task-gopher-quality-filters -->
<!-- source_unit_id: assignment-04-deliverable-gopher-quality-filters-019 -->
<!-- source_unit_id: assignment-04-deliverable-gopher-quality-filters-020 -->
<!-- source_unit_id: assignment-04-task-quality-classifier -->
<!-- source_unit_id: assignment-04-deliverable-quality-classifier-021 -->
<!-- source_unit_id: assignment-04-deliverable-quality-classifier-022 -->

Страница входа, пустая карточка товара и законченная статья могут быть написаны
на одном языке. Для языковой модели их ценность различна: повторение формы
«логин — пароль» почти не добавляет новых связей между словами, тогда как статья
содержит объяснения и примеры. Быстрые правила удаляют очевидно неподходящие
страницы. Более сложный отбор использует коллекцию желательных текстов $T$,
чтобы найти похожие документы $T'$ среди большого исходного корпуса $R$.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/stanford-cs336-2026/data-corpus/raw-target-schema.png]]

*Percy Liang и команда [Stanford CS336, Lecture 14](https://github.com/stanford-cs336/lectures/blob/8b59b50730766695c2ffedd1a79c50cd09b9eb91/lecture_14.py#L59-L85).
Жёлтая коллекция $T$ служит примером нужных текстов, а $T'$ выбирается из
исходного корпуса $R$. Например, по размеченным математическим страницам можно
научиться находить новые математические страницы в веб-архиве.*

### Прозрачные правила

В Assignment 4 используется часть правил из рецепта Gopher:

| Проверка документа | Когда документ отбрасывается | Что правило пытается обнаружить |
| --- | --- | --- |
| Число слов | Меньше 50 или больше 100 000 | Слишком короткие заготовки и аномально длинные страницы |
| Средняя длина слова | Меньше 3 или больше 10 символов | Обрывки, идентификаторы, испорченный текст |
| Строки с `...` в конце | Больше 30% строк | Страницы со списками обрезанных анонсов |
| Слова хотя бы с одной буквой | Меньше 80% слов | Преобладание чисел и символов вместо связного текста |

Границы относятся именно к
[учебному подмножеству правил, Assignment 4, §2.6](https://github.com/stanford-cs336/assignment4-data/blob/0555bea66369872d912652debf10b115ca0688c8/cs336_assignment4_data.pdf);
полный рецепт MassiveText шире и приведён в
[Rae и соавторы, приложение A](https://arxiv.org/abs/2112.11446).
Для применения нужно ещё определить, что считать словом и строкой. Разбиение
по пробелам, NLTK и модельный токенизатор дают разные единицы; число слов в этом
правиле нельзя незаметно заменить числом BPE-токенов.

Например, у страницы 100 слов, из которых 79 содержат буквы: она не проходит
последнее правило, даже если остальные признаки допустимы. Если 4 из 10 строк
заканчиваются многоточием, не проходит и предпоследнее. Сохранение обеих причин
позволяет увидеть их пересечение. Сумма числа срабатываний тогда может быть
больше числа удалённых документов — ошибки в счётчиках здесь нет.

Но таблица измерений закономерно содержит много чисел, а короткий правильный
ответ может занимать двадцать слов. В корпусе программ правило длины слова
может отбрасывать тексты с длинными именами переменных. Эти ограничения не делают
правила бесполезными: они объясняют, почему пороги проверяют для нужного типа
данных и не переносят механически с английских веб-статей на все источники.

### Обучаемый фильтр

Положительные примеры можно получить без ручной разметки каждой веб-страницы.
В WebText для GPT-2 использовали ссылки из сообщений Reddit с достаточным числом
положительных голосов. Assignment 4 предлагает страницы, на которые ссылается
Wikipedia. Это **косвенные признаки полезности**, а не проверка истинности
написанного. Статья может ссылаться на спорное утверждение, архивную страницу
или текст, который она критикует.

Для обучения бинарного классификатора таким страницам присваивают $y=1$,
а случайной выборке веба — $y=0$. Модель, например fastText, учится различать
две коллекции. Она получает признаки слов и их сочетаний, а на выходе даёт
оценку $s(x)=\hat p(y=1\mid x)$. После обучения можно вычислить её для всего
корпуса и оставить документы с $s(x)\ge\tau$.

Из этого определения следуют два ограничения. Во-первых, случайный веб не
является набором заведомо плохих текстов: в отрицательном классе есть полезные
страницы. Во-вторых, классификатор может выучить стиль и тематику положительного
источника вместо свойства, которое нас интересует. Если положительный класс
состоит только из энциклопедических статей, бытовое объяснение с тем же содержанием
может получить меньшую оценку.

Перед обучением обе коллекции обрабатывают одним экстрактором. Иначе модель
может отличать формат источников: скажем, находить характерное меню Wikipedia
вместо качественного текста. Разделение на обучение и проверку по сайтам или
группам похожих документов помогает обнаружить такую зависимость. Затем вручную
просматривают и сохранённые, и отброшенные страницы, особенно около порога.
Просмотр только принятых записей не показывает, сколько полезного потеряно.

Другой способ отбора — языковая модель, обученная на желательной коллекции $T$.
Она оценивает предсказуемость текста:

$$
\begin{gathered}
s_{gen}(x)=\frac{1}{L}\sum_{t=1}^{L}\log p_T(x_t\mid x_{<t}),\\
PPL(x)=\exp(-s_{gen}(x)).
\end{gathered}
$$

Деление на $L$ позволяет сравнивать тексты разной длины: сумма логарифмов сама
по себе уменьшается при добавлении токенов. При среднем отрицательном
логарифме вероятности 3 перплексия равна $e^3\approx20{,}1$, при значении 4 —
$e^4\approx54{,}6$. Для отбора по $s_{gen}$ оставляют большие значения, для
отбора по PPL — меньшие. Низкая перплексия показывает знакомый модели текст,
но не гарантирует достоверность или разнообразие; повторяющийся шаблон тоже
бывает легко предсказуем. В CCNet такую оценку строили с помощью
$n$-граммной модели KenLM, обученной на Wikipedia.

### Отбор по вероятности вместо жёсткого порога: GPT-3

Оценка классификатора может задавать частоту сохранения, а не единственный
порог. В [GPT-3, приложение A](https://arxiv.org/html/2005.14165v4#A1)
логистический классификатор различал отобранные тексты и исходный Common
Crawl. Документ с оценкой $s$ сохраняли при условии
`np.random.pareto(9) > 1 - s`.
Это правило также разобрано в
[CS336 Lecture 14, функция filtering](https://github.com/stanford-cs336/lectures/blob/8b59b50730766695c2ffedd1a79c50cd09b9eb91/lecture_14.py#L109-L116).

Здесь нельзя читать $s=0{,}8$ как «оставить 80% таких страниц».
Для сдвинутого распределения Парето, которое использует
[NumPy](https://numpy.org/doc/stable/reference/random/generated/numpy.random.pareto.html),
вероятность $P(X>x)=(1+x)^{-\alpha}$ при $x\ge0$.
Подстановка $x=1-s$ даёт вероятность сохранения

$$
r(s)=(2-s)^{-9},\qquad 0\le s\le1.
$$

| Оценка $s$ | Вероятность сохранить документ |
|---:|---:|
| 0 | около 0,1953% |
| 0,5 | около 2,6012% |
| 0,8 | около 19,3807% |
| 1 | 100% |

При оценке 0,8 большая часть документов всё ещё отбрасывается.
При оценке 0,5 небольшая часть проходит. Если есть по тысяче страниц
с оценками 0,5 и 0,8, ожидаются примерно 26 и 194 сохранённых страницы,
а не 500 и 800. Реальное число случайно; длинные и короткие страницы
с одинаковой вероятностью сохранения также дадут разные доли токенов.

Следующий CPU-пример вычисляет это правило без NumPy и без запуска
классификатора. Сравнение равномерного $U$ с $r(s)$ имеет ту же вероятность
успеха, что исходное условие с Pareto, но не обязано выдавать те же решения
при одном и том же seed другой библиотеки.

```python
from math import isfinite

def gpt3_keep_probability(score, alpha=9):
    if not isfinite(score) or not 0 <= score <= 1:
        raise ValueError("score must be finite and in [0, 1]")
    if not isfinite(alpha) or alpha <= 0:
        raise ValueError("alpha must be finite and positive")
    return (2 - score) ** (-alpha)

uniform_draws = (0.01, 0.10, 0.90)
for score in (0.5, 0.8, 1.0):
    decisions = [u < gpt3_keep_probability(score)
                 for u in uniform_draws]
    print(score, decisions)
```

Результат: для 0,5 проходит только первое число, для 0,8 — первые
два, для 1 — все три. Это учебные входы, не измерение отбраковки веба.
Авторы GPT-3 выбрали $\alpha=9$, сопоставляя распределение оценок
с WebText. Переносить эту константу на другой классификатор без проверки
нельзя. Если исходная плотность документов по оценке равна $f(s)$,
после отбора она пропорциональна $f(s)r(s)$: результат зависит и от
правила сохранения, и от того, каких страниц изначально было больше.

Вероятностное правило не устраняет смещение положительной коллекции:
классификатор по-прежнему может предпочитать знакомые ему стиль и темы.
Оно меняет способ использовать его оценку и оставляет ненулевую
вероятность пройти для низко оценённых страниц.

### Сквозной пример: OpenWebMath

В математическом корпусе нужно сохранить не только слова, но и формулы.
Наличие MathJax в HTML ещё не означает, что в архиве уже есть готовые
отрендеренные формулы: Common Crawl сохраняет ответ сервера без последующего
выполнения JavaScript браузером. Если обычный экстрактор удалит исходные
LaTeX-фрагменты, фильтр ниже по цепочке увидит другой документ.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/corpus-collection-2026-10-23/openwebmath-pipeline.png]]

*Keiran Paster, Marco Dos Santos, Zhangir Azerbayev, Jimmy Ba,
[OpenWebMath: исходная схема из репозитория](https://github.com/keirp/OpenWebMath/blob/98f81d0ae14ff8dd877b84226b69c825b64da498/imgs/pipeline.png),
[Apache-2.0](https://github.com/keirp/OpenWebMath/blob/98f81d0ae14ff8dd877b84226b69c825b64da498/LICENSE).
PNG 4968 × 908 перенесён без изменений. Числа между фильтрами обозначают
документы; конечные 14.7B — токены, а не ещё одна стадия подсчёта страниц.
Лицензия рисунка из репозитория не заменяет условия использования
самих веб-документов.*

В [README закреплённой версии](https://github.com/keirp/OpenWebMath/blob/98f81d0ae14ff8dd877b84226b69c825b64da498/README.md#openwebmath-pipeline)
авторы описывают последовательность так; язык оригинала сохранён:

> 1. **Prefiltering HTML Documents**:
>    - We apply a simple prefilter to all HTML documents in Common Crawl in order to skip documents without mathematical content to unnecessary processing time.
> 2. **Text Extraction**:
>    - Extract text, including LaTeX content, from the HTML documents while removing boilerplate.
> 3. **Content Classification and Filtering**:
>    - Apply a FastText language identification model to keep only English documents.
>    - Filter high perplexity documents using a KenLM model trained on Proof-Pile.
>    - Filter non-mathematical documents using our own MathScore model.
> 4. **Deduplication**:
>    - Deduplicate the dataset using SimHash in text-dedup.
> 5. **Manual Inspection**:
>    - Inspect the documents gathered from previous steps and remove low quality pages.

На схеме стадии разделены ещё подробнее. Из 237 млрд HTML-страниц после
предварительного отбора остаётся около 1 млрд; после определения языка —
336 млн, MathScore — 66 млн, перплексии — 59 млн, дедупликации —
7,8 млн, ручного отбора — 6,3 млн. Например, этап дедупликации сохраняет
примерно $7{,}8/59\approx13{,}2\%$ своего входа. Конечные
$6{,}3\text{ млн}/237\text{ млрд}\approx0{,}00266\%$ относятся ко всему
исходному архиву. Подсчёты приблизительны, поскольку числа на схеме округлены.

Эта последовательность требует нескольких разных решений. Дешёвый
предварительный отбор ищет признаки математической разметки, прежде чем
тратить время на полное извлечение. При извлечении учитываются разделители
MathJax, специальные теги, текст формулы в атрибутах изображения и MathML.
Один поиск тега `<math>` не покрывает эти способы хранения.
Далее проверяются язык, тематическая близость и предсказуемость текста;
после них всё ещё остаются повторяющиеся страницы.

MathScore получает косвенную разметку: признак наличия распространённых
LaTeX-команд. Из признаков для обучения сами формулы удаляют.
Иначе классификатор мог бы находить те же команды, которыми создана
метка, вместо словесного окружения математического объяснения.
Такой фильтр может отбирать технический текст без извлечённых формул,
но его оценка не проверяет правильность доказательства.

Для страницы с извлечённой формулой статья задаёт более мягкий порог,
чем для страницы без формулы. Например, при MathScore 0,5 и PPL 10 000
первая проходит эти два условия, а вторая — нет. Если экстрактор потерял
формулу, результат отбора изменится, хотя слова и оценка классификатора
остались прежними. Поэтому качество извлечения и итог фильтрации
нельзя проверять независимо только по среднему числу сохранённых символов.

У статьи и опубликованного кода есть расхождение параметров:

| Источник рецепта | Условия MathScore и перплексии |
|---|---|
| [Статья v1, §3.5](https://arxiv.org/html/2310.06786v1#S3.SS5) | При извлечённом LaTeX: $s>0{,}17$; без него: $s>0{,}8$; PPL не выше 15 000 |
| [extract_from_warc.py, commit 98f81d0](https://github.com/keirp/OpenWebMath/blob/98f81d0ae14ff8dd877b84226b69c825b64da498/extract_from_cc/extract_from_warc.py#L215-L234) | При извлечённом LaTeX: $s\ge0{,}15$; без него: $s\ge0{,}8$; PPL не выше 30 000 |

Например, документ с формулой, оценкой 0,16 и PPL 20 000 не проходит
рецепт статьи, но проходит эти условия кода. Различается и предварительный
отбор: в данной версии `contains_math` доходит до резервного MathScore
только внутри ветви с найденной командой через обратную косую черту.
Это не точное воспроизведение описанного в §3.3 общего резервного пути.
Для воспроизводимого запуска нужно явно выбрать версию кода и параметры;
одной ссылки на название корпуса недостаточно.

В конце авторы просматривали наиболее частые домены, отдельно по числу
страниц и символов, и самые длинные документы. Это позволяет обнаружить
проблему, занимающую большую долю корпуса, даже если она редко попадается
в равномерной выборке страниц. Такой просмотр дополняет случайную
проверку, но не доказывает отсутствие ошибок на всех остальных сайтах.

### Почему нельзя выбирать порог без бюджета обучения

Пусть после мягкого отбора доступно 100 млрд токенов, после строгого — 10 млрд.
Для обучения на 5 млрд токенов оба варианта дают достаточно материала без
полного повторения корпуса. Для обучения на 100 млрд строгий вариант означает
уже десять проходов. Исходное преимущество более чистого текста приходится
сопоставлять с потерей разнообразия. Порог, подходящий короткому эксперименту,
может оказаться неудачным для большого запуска.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/stanford-cs336-2026/data-corpus/data-filtering-scale.png]]

*Percy Liang и команда [Stanford CS336, Lecture 14](https://github.com/stanford-cs336/lectures/blob/8b59b50730766695c2ffedd1a79c50cd09b9eb91/lecture_14.py#L134-L138).
Модель на 157 млн параметров обучается на вариантах корпуса из 100 WARC-файлов.
Горизонтальная ось — число обучающих токенов в логарифмическом масштабе,
вертикальная — `eval/lima/loss` (меньше лучше). Штрихи отмечают проходы по данным.
[Открыть исходный рисунок в полном размере](https://raw.githubusercontent.com/stanford-cs336/lectures/8b59b50730766695c2ffedd1a79c50cd09b9eb91/images/data-filtering-scale.png).*

У синей линии `dclm` один проход содержит только 97,6 млн токенов. К 4,42 млрд
обучающих токенов это около 45 проходов; у фиолетовой `resiliparse` тот же объём
соответствует одному проходу. Синяя линия сначала снижается, а затем растёт,
хотя обучение продолжается. На графике видно, почему сравнение по одной ранней
точке недостаточно. При этом названия линий относятся к конкретным вариантам
эксперимента курса: это не утверждение, что любой корпус DCLM неизбежно ведёт
себя так же.

## Дедупликация

Фильтрация оценивает документ отдельно, а дедупликация сравнивает записи между
собой. Точное совпадение можно искать по хэшу нормализованного текста. Один из
способов найти почти совпадающие документы использует шинглы, MinHash и
отдельную проверку кандидатов по сходству Жаккара. Вывод алгоритма, выбор представителя кластера,
обработка PII и проверка контаминации вынесены в следующую главу:
[[02 Areas/ML & DL/00 Учебник/11 Pre-training и Scaling/41a Дедупликация, PII и контроль качества корпуса|Дедупликация, PII и контроль качества корпуса]].

### RedPajama: a reproduction recipe and an annotated web pool

RedPajama V1 follows the seven-source recipe described for the first

V2 changes the collection: it processes 84 Common Crawl snapshots in
English, French, German, Italian and Spanish. The
[release announcement](https://www.together.ai/blog/redpajama-data-v2)
describes over 100 trillion raw tokens and more than 40 precomputed
quality signals for a smaller annotated subset. These signals let a
downstream user select or weight documents; they are not human
certificates of correctness.

The
[dataset card at revision aa033f6](https://huggingface.co/datasets/togethercomputer/RedPajama-Data-V2/blob/aa033f6b6480c445557e9118283993403f069f6a/README.md)
separates four components:

| Component | What it supplies |
| --- | --- |
| Documents | Text and source metadata, including snapshot, language and CCNet bucket |
| Quality signals | Document- or span-level measurements |
| Duplicate IDs | Records to exclude for the released exact-deduplication selection |
| MinHash signatures | Features for finding near-duplicate candidates |

The published deduplicated `head_middle` subset contains about
20.8 billion documents and an estimated 30.4 trillion tokens. Those
counts do not describe every raw document or a fixed model-training
budget. The raw files retain duplicates; downloading them and applying
a quality threshold does not also apply the separate duplicate-ID list.

A constructed example shows the two decisions. Suppose a document
passes a length rule but its ID is in the duplicate list: it still has
to be excluded from the deduplicated selection. Another document may
be unique but fail the length rule. Recomputing one score cannot resolve
both cases. Keep the document key consistent across components, apply
the selected rules, then count the resulting tokens before choosing a
mixture. The MinHash candidate step is developed in
[[02 Areas/ML & DL/00 Учебник/11 Pre-training и Scaling/41a Дедупликация, PII и контроль качества корпуса|the deduplication chapter]].

## Смеси данных

### От физического корпуса к фактической смеси

<!-- source_unit_id: lecture-14-figure-step-320-rendering-1 -->
<!-- source_unit_id: lecture-14-figure-step-325-rendering-1 -->

После очистки у нас есть несколько конечных наборов документов, но ещё нет
правила, по которому модель будет их видеть. Самый большой источник может
занимать почти весь диск и при этом давать только половину обучающих токенов.
Так бывает, когда небольшие источники намеренно используются чаще.

Обозначим через $n_i$ число доступных токенов источника $i$ после окончательной
обработки, а через $p_i$ — его желательную долю в обучающем потоке. Если $D_i$
описывает распределение обучающих контекстов этого источника, смесь записывается
как

$$
D_{mix}=\sum_i p_iD_i,\qquad \sum_i p_i=1.
$$

Здесь веса должны относиться к одной и той же единице. Например, можно выбирать
источник с вероятностью $p_i$, а затем брать из его потока очередной блок
ровно из 2 048 токенов. Каждый выбор даёт одинаковое число токенов, поэтому
доля блоков совпадает с долей токенов. Если выбираются целые документы разной
длины, это уже не так.

При бюджете $T_{train}$ ожидаемое число выбранных токенов источника равно
$p_iT_{train}$, а отношение этого числа к его физическому объёму —

$$
e_i=\frac{p_iT_{train}}{n_i}.
$$

Если каждый источник перемешивают и проходят без возвращения до исчерпания,
$e_i$ удобно понимать как число проходов, включая неполный последний. При
независимой выборке с возвращением это средний объём использования: отдельные
документы могут встретиться разное число раз. В обоих случаях $e_i$ не является
числом новых уникальных токенов.

Для примера возьмём три подготовленных источника и бюджет 300 млрд токенов.
Числа условные; названия обозначают тип текста, а не конкретный релиз корпуса.

| Источник | Доступно $n_i$, млрд токенов | Доля $p_i$ | Будет выбрано $p_iT_{train}$, млрд | Проходы $e_i$ |
| --- | ---: | ---: | ---: | ---: |
| Веб | 800 | 50% | 150 | 0,1875 |
| Код | 80 | 30% | 90 | 1,125 |
| Научные тексты | 20 | 20% | 60 | 3 |

Суммарный архив содержит 900 млрд токенов — втрое больше бюджета обучения.
Тем не менее маленький источник повторяется три раза. Проверка только общего
объёма не обнаружила бы этого. Повторение не всегда вредно, но его эффект
нужно оценивать вместе с размером модели, длительностью обучения и задачами.

### Почему одинаковое число документов не даёт равных долей

Пусть сначала выбирается источник с вероятностью $q_i$, затем один его документ
со средней эффективной длиной $\ell_i$. В достаточно длинном потоке ожидаемая
доля токенов равна

$$
p_i=\frac{q_i\ell_i}{\sum_jq_j\ell_j}.
$$

При $q_1=q_2=0{,}5$ и длинах 100 и 900 токенов получаются доли 10% и 90%.
Из десяти документов каждого источника первый даёт 1 000 токенов, второй —
9 000. Чтобы в среднем уравнять токены, нужно выбирать короткие документы
в девять раз чаще: $q_1=0{,}9$, $q_2=0{,}1$.

Для заранее заданных токенных долей можно обратить формулу:

$$
q_i=\frac{p_i/\ell_i}{\sum_j p_j/\ell_j}.
$$

Вместо такой поправки часто удобнее смешивать уже подготовленные блоки
одинаковой длины. Однако добавление разделителей, усечение, отбрасывание
неполного блока и маскирование части целевых токенов всё равно требуют учёта.
Обычная упаковка, которая не теряет токены, сама по себе состав не меняет.
Фактические доли проверяют по прочитанным токенам, а при маскировании — ещё и
по токенам, участвующим в функции потерь.

### Равномерная смесь, сглаживание и предел повторений

При пропорциональной выборке $p_i=n_i/\sum_jn_j$ все источники имеют одинаковое
$e_i=T_{train}/\sum_jn_j$: большой набор используется чаще именно потому,
что он больше. При равных токенных долях $p_i=1/k$ каждый из $k$ источников
получает одинаковый объём обучения; маленькие наборы повторяются чаще.
Между этими вариантами находится сглаживание

$$
p_i=\frac{n_i^\alpha}{\sum_j n_j^\alpha},\qquad 0\le\alpha\le1.
$$

При $\alpha=0$ доли равны, при $\alpha=1$ пропорциональны объёму. Промежуточное
значение повышает относительный вес малых источников, но не ограничивает число
повторов напрямую.

Такое ограничение вводит [UniMax](https://arxiv.org/abs/2304.09151). В исходной
многоязычной постановке объёмы измеряются символами; тот же принцип можно
применить к токенам, если все величины согласованы. Для максимума $E_{max}$
проходов необходимо

$$
\begin{gathered}
p_iT_{train}\le E_{max}n_i,\\
p_i\le\frac{E_{max}n_i}{T_{train}}.
\end{gathered}
$$

Алгоритм старается распределить бюджет равномерно, но сначала ограничивает
маленькие источники. Для наших объёмов $800,80,20$ и бюджета 300 млрд токенов
равномерный вариант дал бы по 100 млрд каждому. При $E_{max}=2$ научным текстам
можно выделить только $2\cdot20=40$ млрд. Остаток 260 млрд поровну распределяется
между вебом и кодом — по 130 млрд. Получается $0{,}1625$, $1{,}625$ и 2 прохода.
Если суммарно $E_{max}\sum_i n_i<T_{train}$, выполнить бюджет без нарушения
ограничения невозможно: нужны новые данные, меньший бюджет или больший предел.

### Как искать смесь по небольшим экспериментам

Вес источника можно подбирать по влиянию на проверочные задачи, а не только
по размеру. **RegMix** обучает много небольших языковых моделей на разных
смесях. Для каждого опыта сохраняется пара: вектор долей $p$ и полученная
ошибка. Затем отдельная регрессионная модель учится предсказывать ошибку по
вектору долей. Её вычисление значительно дешевле нового обучения LLM, поэтому
с её помощью можно перебрать много смесей и выбрать кандидатов для большого
запуска.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/stanford-cs336-2026/data-corpus/regmix.png]]

*Qian Liu и соавторы, [RegMix, рисунок 1](https://arxiv.org/abs/2407.01492), CC BY 4.0,
копия из [CS336](https://github.com/stanford-cs336/lectures/blob/8b59b50730766695c2ffedd1a79c50cd09b9eb91/images/regmix.png).
Слева сверху — реально обученные малые модели; справа — обучение регрессии
и её предсказания для новых долей. Значение 5,34 внизу — **предсказанная**
ошибка выбранной смеси, а не заранее известный результат большой модели.*

У поиска две независимые проверки. Регрессия может ошибаться на смесях,
которых не было в её обучении, особенно около найденного минимума. Кроме того,
удачный состав для маленькой модели не обязан оставаться удачным при большем
числе параметров и токенов. Поэтому часть небольших опытов откладывают для
проверки регрессии, а перед основным запуском проверяют несколько кандидатов
на промежуточном масштабе. Если оптимизатор нашёл слишком большое преимущество
в узкой области, это может быть ошибкой предсказателя, а не свойством данных.

В [Olmix](https://arxiv.org/abs/2602.12237) сопоставлены несколько вариантов
такого поиска. Таблица ниже сохраняет параметры сравнения из Lecture 14,
но вместо широкого изображения методы расположены по строкам.

| Метод | Размер малой модели | Число моделей при $m$ источниках | Как выбираются пробные смеси | Предсказатель; целевая оценка | Ограничение повторений; поиск |
| --- | --- | --- | --- | --- | --- |
| RegMix | 1M | 512 ($m=17$) | Dirichlet с prior по объёмам | LightGBM; сводная | Нет; перебор кандидатов |
| DML | 70, 160, 305, 410M | 20 ($m=7$) | Экспоненциальная сетка | Log-linear; сводная | Нет; перебор кандидатов |
| AutoScale | Как у целевой модели | $2m+1$ | Экспоненциальная сетка | Power law; по задачам | Нет; градиентный спуск |
| BiMix | 280M | 4 | Взвешивание энтропией | Power law; по задачам | Нет; точный решатель |
| ADMIRE-BayesOpt | 1M, 60M | 101 ($m=17$) | Адаптивно | Gaussian process; сводная | Нет; поиск |
| CLIMB | 350M | 112 ($m=21$) | Dirichlet с prior по объёмам | LightGBM; сводная | Нет; поиск |
| OlmixBase | 30M | $3(m+1)$ | Dirichlet с prior по объёмам; разреженные смеси тем, плотные смеси источников | Log-linear; по задачам | Да; точный решатель с KL-регуляризацией |

сравнение опубликованных постановок, не рейтинг качества. `M` означает миллионы
параметров. «По задачам» означает отдельное предсказание для каждой проверочной
задачи вместо одного среднего балла. Точный решатель минимизирует функцию
предсказателя; это не делает его ответ точным предсказанием качества LLM.

### Как учесть повторения уже в маленьком опыте

Пусть большой запуск должен прочитать $T_{large}=1$ трлн токенов из двух
источников: в вебе доступно 10 трлн, в специализированном — 10 млрд. Если
второму выделить половину обучения, он повторится 50 раз. Маленький опыт на
$T_{small}=10$ млрд токенов из тех же исходных наборов прочитает лишь половину
специализированного источника и вообще не покажет проблему повторения.

Приём **simulated epoching** уменьшает доступные наборы в той же пропорции,
что и обучающий бюджет:

$$
\begin{gathered}
r=\frac{T_{small}}{T_{large}},\\
n_i^{small}=r n_i^{large},\\
\frac{p_iT_{small}}{n_i^{small}}
=\frac{p_iT_{large}}{n_i^{large}}.
\end{gathered}
$$

Здесь $r=0{,}01$. В малом опыте оставляют 100 млрд веб-токенов и 100 млн
специализированных; при доле 50% второй источник снова повторяется 50 раз.
Сохраняется именно число проходов. Размер модели, разнообразие подвыборки
и обучение на редких примерах всё ещё отличаются, поэтому равенство не
гарантирует переноса итогового качества. Приём и его ограничения обсуждаются
в [William Held и соавторы, Optimizing Pretraining Data Mixtures with LLM-Estimated Utility, §3.2](https://arxiv.org/html/2501.11747v1#S3.SS2)
и [Lecture 14](https://github.com/stanford-cs336/lectures/blob/8b59b50730766695c2ffedd1a79c50cd09b9eb91/lecture_14.py#L381-L408).

## Токенизация, упаковка и версия корпуса

Число токенов окончательно становится известно после выбора токенизатора.
Поэтому смесь, рассчитанную по исходным байтам, пересчитывают на его выходе.
Короткие документы объединяют в блоки нужной длины, но при этом нужно определить,
могут ли они видеть друг друга через внимание. EOS обозначает границу, однако
сам по себе не запрещает внимание к предыдущему документу. Блочно-диагональная
маска и правило расчёта потерь задают другую задачу, чем обычная непрерывная
последовательность. Подробный разбор с проверкой независимости документов
дан в [[02 Areas/ML & DL/00 Учебник/10 ML Systems/06 Data pipeline, padding и packing|главе о padding и packing]].

Перед запуском полезно выполнить расчёт, не требующий GPU:

```python
from math import isclose

def mixture_report(available, shares, training_tokens):
    if set(available) != set(shares) or not available:
        raise ValueError("Sources must match and must not be empty")
    if training_tokens <= 0 or any(n <= 0 for n in available.values()):
        raise ValueError("Token counts must be positive")
    if any(p < 0 for p in shares.values()):
        raise ValueError("Shares must be non-negative")
    if not isclose(sum(shares.values()), 1.0, abs_tol=1e-12):
        raise ValueError("Shares must sum to one")
    return {
        name: {
            "sampled_tokens": shares[name] * training_tokens,
            "epochs": shares[name] * training_tokens / n,
        }
        for name, n in available.items()
    }

available = {"web": 800e9, "code": 80e9, "science": 20e9}
shares = {"web": 0.5, "code": 0.3, "science": 0.2}
report = mixture_report(available, shares, 300e9)
for name, row in report.items():
    print(name, row["sampled_tokens"] / 1e9, row["epochs"])
```

Вывод для условного примера: `web 150.0 0.1875`, `code 90.0 1.125`,
`science 60.0 3.0`. Это проверка бюджета смеси, а не обучение и не оценка её
качества. После запуска эти ожидаемые значения сравнивают с фактическими
счётчиками чтения: ошибки перемешивания, перезапуск обработчика или пропущенный
файл могут изменить состав даже при правильном конфигурационном файле.

Чтобы результат можно было повторить, вместе с корпусом сохраняют манифест:

- **Вход:** список снимков и файлов, контрольные суммы, указатели исходных
  записей, условия использования.
- **Преобразования:** версии экстрактора и токенизатора, модели фильтров,
  пороги, порядок операций, правила нормализации и дедупликации.
- **Выход:** число документов, байтов и токенов по источникам, языкам и стадиям;
  причины удаления и выборки записей для ручной проверки.
- **Обучающий поток:** веса смеси, бюджет, ожидаемые повторения, начальное
  состояние генератора случайных чисел, перемешивание, упаковка и правила границ.
- **Проверочная выборка:** отдельная версия, способ её отделения и результат
  поиска пересечений. Такой отчёт описывает выполненные проверки, а не обещает
  отсутствие любых возможных совпадений.

Порядок операций здесь существенен. Если один фильтр удаляет страницу целиком,
а другой только вырезает строки, применение второго меняет признаки для первого.
Одинаковый перечень правил в другом порядке может дать другой корпус.
Для пересмотра одного порога полезно хранить оценки до принятия решения;
для исправления экстрактора понадобится вернуться к исходным байтам.

Наконец, аккуратный манифест ещё не доказывает, что модель станет лучше. Новый
рецепт сравнивают с прежним при одинаковой архитектуре, токенизаторе, бюджете,
настройках оптимизатора и проверочных задачах. Если меняется только экстрактор,
не стоит одновременно менять веса смеси: иначе причина различия останется
неясной. До длинного запуска проверяют несколько вариантов на небольшом
масштабе, учитывая описанную выше проблему повторения данных.
