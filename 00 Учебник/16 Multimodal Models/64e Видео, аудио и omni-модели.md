# Видео, аудио и omni-модели

Человек открывает дверь и произносит «Я вернулся». Через несколько секунд в ролике звучит другая фраза. На вопрос «что он сказал, когда открыл дверь?» недостаточно отдельно распознать дверь и получить транскрипцию всей записи. Нужно найти действие на временной шкале и сопоставить его с речью в том же интервале.

В дальнейшем этот минутный ролик служит учебным примером. Открытие двери происходит около 18.4 секунды. Система получает видео и звук, отвечает текстом, а при необходимости произносит ответ. В записи, доступной целиком, она может искать нужный момент повторно. В живом разговоре будущие кадры и звук ещё не получены: доступный контекст и время начала ответа становятся частью постановки задачи.

<span id="1-от-видеофайла-до-visual-tokens"></span>
## 1. От видеофайла до визуальных токенов

Видео содержит кадры с временными метками. После декодирования контейнера система выбирает часть кадров, подготавливает их разрешение и получает признаки через vision encoder. Проектор переводит признаки в размерность языковой модели. Обычная линейная проекция или MLP меняет размерность каждого вектора, но сохраняет число позиций. Чтобы сократить последовательность, нужен дополнительный механизм объединения или отбора.

Пусть из минуты выбраны два кадра в секунду. Получаются 120 кадров. Если после пространственного сжатия каждый даёт 256 визуальных токенов, LLM получит $120\cdot256=30\,720$ токенов изображения. При 8 кадрах/с и том же представлении кадра потребуется уже 122 880 токенов. Расходы на аудио, вопрос и служебные разделители добавляются отдельно.

Частота выборки определяет, какие наблюдения вообще доступны модели. Если дверь начинает открываться в 18.3 и заканчивает в 18.5 секунды, равномерные кадры 18.0 и 18.5 не показывают самого движения. По разнице состояний модель ещё может заключить, что дверь открылась, но точный момент и сопутствующее краткое действие уже не наблюдаются.

~~~python
from fractions import Fraction

def sample_times(duration, fps):
    return [Fraction(i, fps) for i in range(duration * fps)]

low, high = sample_times(60, 2), sample_times(60, 8)
event = (Fraction("18.3"), Fraction("18.5"))
inside = lambda times: [t for t in times if event[0] <= t < event[1]]
assert len(low) == 120 and len(high) == 480
assert len(low) * 256 == 30_720
assert len(high) * 256 == 122_880
assert inside(low) == []
assert inside(high) == [Fraction("18.375")]
~~~

Равномерная выборка обеспечивает известный шаг по времени. Выбор по границам сцен лучше сохраняет переходы между планами, но граница сцены не обязана совпадать с нужным действием. Отбор по вопросу может сосредоточиться на нужном эпизоде, если он есть среди исходных кандидатов. Ни последующий resampler, ни LLM не восстановят изображение события, не попавшее в переданный набор.

### Один интерфейс для изображения, набора изображений и видео

[LLaVA-OneVision, §3](https://arxiv.org/abs/2408.03326v1) использует общий визуальный энкодер и проектор, но по-разному распределяет токены между режимами. Одиночное изображение можно разбить на подробные фрагменты. При нескольких изображениях и особенно видео такой расход на каждый кадр быстро переполняет контекст. Поэтому для видео применяется более сильное пространственное объединение признаков.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/stanford-cs336-2026/multimodal/llava-onevision-modalities.png]]

*LLaVA-OneVision, сопоставление режимов из [Stanford CS336, Lecture 17](https://github.com/stanford-cs336/lectures/blob/8b59b50730766695c2ffedd1a79c50cd09b9eb91/lecture_17.py), по [Li et al., LLaVA-OneVision](https://arxiv.org/abs/2408.03326v1). Общие компоненты не означают одинаковое число токенов на изображение.*

Более грубый кадр может сохранять положение человека, но терять мелкую надпись. Для нашего вопроса о двери это допустимо, если действие и человек различимы. Для чтения номера автомобиля может потребоваться повторно получить выбранные кадры в большем разрешении. Условия эксперимента поэтому включают и число кадров, и размер их изображения, и итоговый бюджет токенов.

<span id="xgen-video-temporal-compression"></span>
### xGen-MM-Vid: сжать представление после выбора кадров

<!-- source_unit_id: meeting-07-slides-xgen-video -->

[Ryoo et al., xGen-MM-Vid, §2.1–2.3](https://arxiv.org/abs/2410.16267v2) добавляют временной энкодер после покадрового представления. В описанной конфигурации SigLIP обрабатывает восемь равномерно выбранных кадров, Perceiver Resampler выдаёт по 128 токенов на кадр, а временной энкодер переводит все 1024 токена в $M$ выходов для Phi-3.

Для варианта $M=32$ путь имеет вид:

$$
\begin{aligned}
8\cdot729=5832&\longrightarrow8\cdot128=1024\\
&\longrightarrow M=32.
\end{aligned}
$$

Это числа промежуточных признаков, а не число операций и не измерение ускорения. Покадровый SigLIP всё равно обрабатывает выбранные изображения.

Простое усреднение по времени уничтожает порядок. Последовательности признака «дверь открыта» $[0,0,1,1]$ и $[1,1,0,0]$ имеют одно среднее 0.5, хотя первая соответствует открытию, а вторая — закрытию. Обучаемое пространственно-временное объединение назначает входным токенам разные веса; для различения порядка сами признаки должны также содержать сведения о времени.

~~~python
import numpy as np

opening = np.array([0., 0., 1., 1.])
closing = opening[::-1]
assert opening.mean() == closing.mean() == 0.5
# Учебные веса для последней части последовательности, не веса модели.
weights = np.array([0.05, 0.05, 0.45, 0.45])
assert np.isclose(weights @ opening, 0.9)
assert np.isclose(weights @ closing, 0.1)
assert 8 * 729 == 5832 and 8 * 128 == 1024
assert 1024 // 32 == 32
assert 128 * 4 == 512
~~~

Статья сравнивает эти варианты на [оригинальной Figure 3](https://arxiv.org/html/2410.16267v2#S2.F3). В последовательном варианте состояние памяти обновляется после каждого кадра. У каждого из 128 покадровых токенов есть своя группа из четырёх ячеек. Получаются 512 ячеек памяти; затем обучаемое объединение преобразует их в $M$ выходных токенов. Вход LLM из 32 токенов не означает, что вся система хранит только 32 вектора.

Временные метки в памяти помогают отличать ранние наблюдения от поздних. Ограничение остаётся содержательным: одинаковый выходной бюджет не гарантирует сохранение всех мелких деталей и событий произвольно длинной записи. Для опубликованного [варианта 32 tokens / 8 frames](https://huggingface.co/Salesforce/xgen-mm-vid-phi3-mini-r-v1.5-32tokens-8frames) именно эти условия составляют часть описания модели.

<span id="gens-question-aware-frame-selection"></span>
### GenS: сначала найти кадры, нужные для вопроса

<!-- source_unit_id: meeting-07-slides-gens -->

[Yao et al., GenS, §2.2–2.3](https://aclanthology.org/2025.findings-acl.921/) решают другую задачу: выбирают кадры под вопрос, после чего передают их отвечающей модели. Generative Frame Sampler на основе Aria получает несколько кадров с текстовыми индексами и генерирует JSON с индексами или интервалами и оценками релевантности. Оценка относится к полезности кадра для вопроса, а не к вероятности правильности будущего ответа.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/omni-review-2026-10/gens-frame-selection.png]]

*Linli Yao et al., [GenS, Figure 1](https://aclanthology.org/2025.findings-acl.921.pdf#page=2). Вопрос содержит отношение «сразу после». Слева сравниваются выбранные наблюдения; справа приведены результаты авторов на указанном в статье подмножестве LongVideoBench. [CC BY 4.0](https://aclanthology.org/faq/copyright/).*

На рисунке отдельный кадр с человеком на совещании ещё не отвечает на вопрос о следующем действии. Покадровая похожесть на слова вопроса может выбрать совещание, но пропустить приготовление еды после него. GenS совместно обрабатывает наблюдения и вопрос, чтобы выбирать последовательность, относящуюся к заданному временному отношению.

Контекст GenS в исходной конфигурации ограничен 256 кадрами. Видеозапись разбивается на временные окна; локальные индексы связываются с исходными метками времени. Из найденных кандидатов берутся $K=\min(N_{\mathrm{ret}},N_{\mathrm{budget}})$ кадров. Если найдено 45, а отвечающей модели разрешены 32, остальные не поступят в её вход.

~~~python
windows = [(start, min(start + 256, 600)) for start in range(0, 600, 256)]
assert [end - start for start, end in windows] == [256, 256, 88]
# Локальная нумерация начинается с 1; глобальные индексы — с 0.
global_index = windows[1][0] + (1 - 1)
assert global_index == 256
timestamp_at_1fps = global_index
assert timestamp_at_1fps == 256  # Не первая секунда всей записи.

candidates = [(i, 45 - i) for i in range(45)]  # Учебные оценки.
budget = 32
selected = sorted(candidates, key=lambda item: (-item[1], item[0]))[:budget]
assert len(selected) == min(len(candidates), budget) == 32
~~~

Пример окон неперекрывающийся. При перекрытии одно наблюдение может прийти из нескольких окон: перед окончательным отбором кандидатов связывают с глобальными индексами и устраняют дубликаты. Индекс не является физическим временем без таблицы соответствия кадров.

GenS-Video-150K содержит синтетическую разметку релевантности. В §2.1 описаны получение подробных покадровых описаний, генерация вопросов с привязкой к кадрам, расширение набора кандидатов и назначение оценок. Такой учитель задаёт, что считать полезным наблюдением. Ошибка разметки может научить отборщик пропускать нужный момент, даже если отвечающая модель способна понять его по изображению.

Стоимость системы включает просмотр кандидатов самим GenS и работу отвечающей VLM. Сравнивать только число кадров последней недостаточно. Для вопроса о произнесённой фразе выбранный визуальный интервал нужно дополнительно сопоставить со звуком: GenS не заменяет аудиоэнкодер.

## 2. Номер кадра и физическое время

Номер кадра задаёт порядок в выбранном наборе. При двух кадрах/с соседние наблюдения разделены примерно половиной секунды; при переменной частоте кадров интервал меняется. Для измерения времени используют временную метку показа, presentation timestamp, и её time base.

~~~python
from fractions import Fraction

pts = [0, 15_000, 66_000]
time_base = Fraction(1, 30_000)
times = [p * time_base for p in pts]
assert times == [Fraction(0), Fraction("0.5"), Fraction("2.2")]
assumed_constant_rate = Fraction(2, 2)  # Индекс 2 при предположении 2 fps.
assert times[2] != assumed_constant_rate
~~~

В этом примере третье выбранное наблюдение относится к 2.2 секунды, а не к 1 секунде. Подстановка номера выбранного кадра вместо его исходного timestamp сместит и ответ о времени, и поиск соответствующей речи.

### Timestamp token и temporal position — разные сигналы

[Qwen2.5-VL, §2.1.2](https://arxiv.org/abs/2502.13923v1) связывает временные position IDs с физическим временем. [Qwen3-VL, §2.3](https://arxiv.org/abs/2511.21631v1) использует явные текстовые timestamps кадров вместо прежней абсолютной временной привязки, сохраняя interleaved MRoPE. Текстовая метка позволяет языковой части читать значение времени. Позиционный механизм задаёт взаимное расположение представлений внутри attention.

Изменение FPS не должно произвольно переименовывать оставшиеся кадры. Если кадр снят на 18.4 секунде, его физическая метка сохраняется и после прореживания записи. Меняются число наблюдений, расстояния между выбранными кадрами и построенная по ним последовательность позиций.

Qwen3-VL и Qwen3-Omni используют разные интерфейсы времени. Во второй модели сохраняется привязка TM-RoPE к абсолютной сетке 80 мс. Нельзя перенести схему timestamps из одной модели в другую только по общему названию семейства.

Практическая задача о выборе кадров, чтении номера и накоплении наблюдений разобрана в [[02 Areas/ML & DL/06 Практика/19 Найти автомобильный номер в видеопотоке|поиске автомобильного номера в видеопотоке]].

## 3. От звуковой волны к признакам и аудиотокенам

Цифровая запись хранит амплитуду звука через равные интервалы. При частоте 16 кГц секунда монофонического сигнала содержит 16 000 отсчётов. Частота дискретизации не равна частоте речи и не определяет число токенов LLM. Она определяет временную сетку исходного сигнала, из которого далее извлекаются признаки.

### Спектрограмма и аудиоэнкодер

Речь меняется во времени: один спектр всей минуты смешал бы фонемы, паузы и шум. Коротковременное преобразование Фурье вычисляет спектры перекрывающихся окон. Mel-спектрограмма дополнительно объединяет частотные отсчёты по mel-фильтрам; логарифм сжимает диапазон энергий. Аудиоэнкодер получает последовательность этих признаков, обрабатывает временной контекст и может уменьшать её длину свёртками.

[Whisper, §2.2](https://arxiv.org/abs/2212.04356v1) использует 16 кГц, окна 25 мс и шаг 10 мс. В исходной конфигурации из статьи mel-каналов 80, а вторая начальная свёртка уменьшает временную частоту вдвое. Это параметры конкретной версии, не универсальный стандарт. У Qwen2.5-Omni вход содержит 128 mel-каналов, а выход аудиоэнкодера соответствует примерно 40 мс на позицию.

Для 16 кГц окно 25 мс содержит 400 отсчётов, шаг 10 мс — 160. В следующем расчёте чистый тон 440 Гц попадает в частотный отсчёт 11. Это демонстрация FFT до применения mel-фильтров, а не реализация всего препроцессора Whisper.

~~~python
import numpy as np

sample_rate = 16_000
window, hop = 400, 160
t = np.arange(window) / sample_rate
signal = np.sin(2 * np.pi * 440 * t)
spectrum = np.abs(np.fft.rfft(signal * np.hanning(window)))
frequencies = np.fft.rfftfreq(window, 1 / sample_rate)
assert np.isclose(frequencies[spectrum.argmax()], 440)
assert window / sample_rate == 0.025
assert hop / sample_rate == 0.01
assert 1 + (16_000 - window) // hop == 98
~~~

В секунде получается 98 полных окон без дополнения по краям. Число 100 окон/с описывает частоту шага в длинной записи; точное число зависит от padding и правил обрезки. Передача в модель также может дополняться до фиксированного размера. Для синхронизации сохраняют соответствие выходных признаков физическому времени, включая эти краевые условия.

Непрерывные признаки аудиоэнкодера подходят для понимания звука и распознавания речи. Они не являются автоматически дискретными кодами, по которым можно восстановить исходную волну. У ASR-декодера выход — текст; у генератора речи нужен выходной интерфейс для самого звука.

### Векторное и остаточное квантование

Нейронный аудиокодек учится восстанавливать волну через сжатое представление. Энкодер выдаёт вектор на каждый временной шаг. Векторный квантователь выбирает ближайший элемент обучаемого словаря, codebook, и передаёт его целочисленный индекс. Декодер получает выбранный вектор по индексу и восстанавливает звук.

В остаточном квантовании, RVQ, второй словарь кодирует ошибку первого, третий — оставшуюся ошибку второго. Если исходный вектор $(0.9,0.2)$ заменён на $(1,0)$, остаток равен $(-0.1,0.2)$. Второй словарь может выбрать $(-0.1,0.25)$. Сумма выбранных векторов станет $(0.9,0.25)$; ошибка уменьшится до 0.05.

~~~python
import numpy as np

z = np.array([0.9, 0.2])
codebooks = [
    np.array([[0., 0.], [1., 0.]]),
    np.array([[0., 0.], [-0.1, 0.25]]),
]
residual = z.copy()
reconstructed = np.zeros_like(z)
indices, errors = [], []
for book in codebooks:
    index = int(np.argmin(((book - residual) ** 2).sum(axis=1)))
    indices.append(index)
    reconstructed += book[index]
    residual = z - reconstructed
    errors.append(float(np.linalg.norm(residual)))
assert indices == [1, 1]
assert np.allclose(reconstructed, [0.9, 0.25])
assert errors[1] < errors[0] and np.isclose(errors[1], 0.05)
~~~

Это двумерный учебный пример. В кодеке векторы и словари обучаются совместно с остальными компонентами. [EnCodec, §3.1–3.2](https://arxiv.org/abs/2210.13438v1) использует набор RVQ-словарей; количество активных словарей задаёт компромисс между объёмом кодов и качеством восстановления. Обычная цель реконструкции не гарантирует, что первый словарь будет представлять именно слова или фонемы.

### Mimi: семантическая и акустическая ветви

[Moshi, §3.3](https://arxiv.org/abs/2410.00037v2) вводит Mimi, причинный кодек с частотой 12.5 шагов/с. Один шаг соответствует 80 мс звука. Для модели речи желательно одновременно сохранять произнесённое содержание и подробности звучания, но эти цели не совпадают.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/omni-review-2026-10/mimi-split-rvq.png]]

*Alexandre Défossez et al., [Moshi, Figure 2](https://arxiv.org/pdf/2410.00037v2#page=10). Семантический VQ и акустический RVQ работают параллельно; их выходы объединяются перед декодером. Синие ветви относятся к обучению. [CC BY-NC-SA 4.0](https://creativecommons.org/licenses/by-nc-sa/4.0/).*

Семантическая ветвь обучается воспроизводить признаки WavLM через задачу дистилляции. WavLM во время подготовки целей может видеть будущий контекст; на инференсе его нет в составе причинного кодека. Такое использование учителя при обучении само по себе не даёт модели доступ к будущему звуку в работающем приложении.

В Mimi один VQ получает семантическую цель, а отдельный RVQ из семи уровней кодирует акустические сведения. Обе ветви получают представление энкодера через отдельные линейные проекции. Акустический RVQ поэтому не продолжает остаток семантического VQ. Авторы называют это split RVQ, сравнивают с последовательным вариантом и указывают на конфликт между сохранением акустики и семантической целью.

Кодек и модель, генерирующая его индексы, обучаются по разным целям. Генератору нужны вероятности дискретных кодов и cross-entropy. Кодек обучается качеству восстановленного звука. В EnCodec используются реконструкционные и состязательные потери; в описанном варианте Mimi авторы отказываются от явной реконструкционной потери в пользу состязательных и feature losses, сохраняя семантическую дистилляцию. Считать это одним обычным next-token loss было бы неверно.

В конфигурации Mimi восемь словарей по 2048 элементов. Индекс требует 11 бит. При 12.5 шагах/с получаются 100 индексов/с и 1100 бит/с без учёта служебной информации. За 10 секунд — 125 временных шагов и 1000 индексов.

~~~python
from math import prod

sample_rate, frame_rate = 24_000, 12.5
assert prod([4, 5, 6, 8, 2]) == 1920
assert sample_rate / 1920 == frame_rate
assert sample_rate / frame_rate == 1920  # 80 мс исходного звука.
codebooks, bits_per_index = 8, 11
assert 2 ** bits_per_index == 2048
assert frame_rate * codebooks * bits_per_index == 1100
assert 10 * frame_rate * codebooks == 1000
assert 24_000 / prod([2, 4, 5, 8]) == 75  # EnCodec 24 kHz из §3.1.
~~~

У EnCodec 24 кГц частота составляет 75 шагов/с, а не 12.5. Поэтому «восемь аудиотокенов» или «минута звука» без указания кодека, временной частоты и числа словарей не определяют размер последовательности.

## 4. Каскадная и сквозная обработка речи

Каскад ASR → LLM → TTS сначала получает транскрипцию, затем формирует текстовый ответ и синтезирует его. Эти результаты можно проверять отдельно. Если в транскрипции «Я вернулся» ошибочно стало «Я не вернулся», языковая модель уже получает другое высказывание. Просмотр только итогового ответа не показывает, где возникла ошибка.

Каскад можно выполнять потоково: ASR выдаёт частичные гипотезы, LLM начинает ответ до полной транскрипции, TTS озвучивает готовые фрагменты. Задержка поэтому не обязана равняться времени обработки всей реплики последовательно тремя моделями. Однако частичная гипотеза может быть пересмотрена, когда слово завершится; уже произнесённый ответ нельзя отозвать так же легко, как заменить текст в интерфейсе.

| Свойство | ASR → LLM → TTS | Модель с прямым аудиовходом |
|---|---|---|
| Вход языковой части | Транскрипция и сохранённые метаданные | Непрерывные признаки или аудиокоды |
| Контроль ошибки | Доступны промежуточные текстовые результаты | Нужны проверки аудиовхода и отдельных выходов |
| Интонация и фон | Теряются, если не передать отдельно | Могут сохраняться в аудиопредставлении |
| Потоковый режим | Возможен у каждого компонента | Зависит от масок, кодека и генерации |
| Замена компонента | Можно обновлять ASR, LLM и TTS раздельно | Совместно обученные интерфейсы ограничивают замену |

Для пересказа лекции транскрипция может содержать почти все необходимые сведения. Для различения вопроса, иронии или звука сирены одного текста недостаточно. Это ограничение выбранного промежуточного представления, а не доказательство, что всякий каскад хуже сквозной модели.

### Общее пространство ImageBind

[Girdhar et al., ImageBind, §3.1–3.3](https://arxiv.org/abs/2305.05665v1) связывают шесть модальностей через пары с изображениями. Отдельные энкодеры преобразуют текст, звук, изображение, глубину, тепловые данные и IMU в нормированные векторы общей размерности. Контрастивная цель сближает представления парных наблюдений относительно других примеров батча.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/vlm-2026/imagebind-figure1-capabilities.png]]

*Rohit Girdhar et al., [ImageBind, Figure 1](https://arxiv.org/pdf/2305.05665v1#page=1). Показаны межмодальный поиск, операции над embeddings и использование представления звука с уже обученным генератором изображений. Последняя панель не означает, что сам ImageBind обучен декодировать изображения.*

После обучения звук потрескивающего огня можно использовать как запрос к изображениям. Энкодер звука выдаёт вектор, который сравнивают с векторами изображений; выбирается наибольшее сходство. Ни ASR-транскрипция, ни генерация ответа для этой операции не требуются.

~~~python
import numpy as np

audio = np.array([0.8, 0.6])  # Учебный нормированный вектор.
images = np.array([[1., 0.], [0., 1.], [-1., 0.]])
scores = images @ audio
assert np.allclose(scores, [0.8, 0.6, -0.8])
assert scores.argmax() == 0
~~~

Числа здесь показывают косинусный поиск, а не выходы настоящего ImageBind. Общее пространство позволяет сравнивать входы, но не задаёт последовательность фонем или звуковых кодов для ответа. Для речевого диалога нужны дополнительные генеративные компоненты.

## 5. Общая временная ось аудио и видео

В учебной записи дверь открывается в 18.4 секунды. Аудиоэнкодер и визуальный энкодер выдают разное число признаков за секунду. Совместимость размерностей после проекции не определяет, какие из них относятся к одному моменту.

[Qwen2.5-Omni, §2.2](https://arxiv.org/abs/2503.20215v1) использует TMRoPE с тремя компонентами позиции: время, высота, ширина. Для аудио три компонента имеют одинаковые IDs. Для кадра время постоянно внутри кадра, а пространственные координаты меняются по сетке. Шаг временной шкалы соответствует 40 мс.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/vlm-2026/qwen25omni-figure3-tmrope.png]]

*Jin Xu et al., [Qwen2.5-Omni, Figure 3](https://arxiv.org/pdf/2503.20215v1#page=4). Верхние тройки задают время и пространственное положение, нижние — позиции аудио. Скобки объединяют признаки двухсекундных интервалов. [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/).*

Сначала удобно считать позиции относительно начала ролика, до добавления общего offset последовательности. Секунда соответствует ID 25, две секунды — ID 50. Кадр на 18.4 секунды получает временную компоненту 460. Аудиопризнаки около того же момента располагаются рядом на этой шкале. Для Qwen3-Omni шаг составляет уже 80 мс и тому же времени соответствует 230.

~~~python
from fractions import Fraction

time = Fraction("18.4")
assert time / Fraction("0.04") == 460
assert time / Fraction("0.08") == 230
assert Fraction(2) / Fraction("0.04") == 50

sample_rate = 16_000
start, end = Fraction("18.0"), Fraction("18.8")
audio_slice = (int(start * sample_rate), int(end * sample_rate))
assert audio_slice == (288_000, 300_800)
~~~

В Qwen2.5-Omni представления группируются по двухсекундным интервалам: сначала визуальные признаки данного интервала, затем аудио. Это ограничивает расстояние между относящимися к одному отрезку модальностями в сериализованном входе. Наличие временных IDs всё равно необходимо: само соседство токенов не определяет, какая фраза относится к какому кадру.

В Qwen3-Omni абсолютная временная сетка имеет шаг 80 мс, а жёсткая группировка аудио и видео по две секунды заменена выравниванием через временные IDs. Порядок потоковых данных, способ их кодирования и сетка позиций составляют единый интерфейс; менять только одну часть без пересчёта метаданных нельзя.

### Проверка связи действия и фразы

Пусть «Я вернулся» звучит с 18.24 до 18.72 секунды, а «Подожди» — с 20.24 до 20.72. Момент открытия двери 18.4 попадает в первую фразу. Если сдвинуть звук вперёд на две секунды, в момент двери этой речи уже нет; при сдвиге назад на две секунды туда попадёт вторая фраза.

~~~python
from fractions import Fraction as F

segments = [
    (F("18.24"), F("18.72"), "Я вернулся"),
    (F("20.24"), F("20.72"), "Подожди"),
]
def words_at(segments, time, shift=F(0)):
    return [text for start, end, text in segments if start + shift <= time < end + shift]

assert words_at(segments, F("18.4")) == ["Я вернулся"]
assert words_at(segments, F("18.4"), F(2)) == []
assert words_at(segments, F("18.4"), F(-2)) == ["Подожди"]
~~~

Здесь проверена арифметика интервалов, не работа VLM. В эксперименте нужно изменить настоящую аудиодорожку и убедиться, что препроцессор не вернул старый кэш или старую транскрипцию. Требование «после любого сдвига ответ обязан измениться» некорректно: при небольшой задержке та же фраза может по-прежнему перекрывать событие.

## 6. Thinker–Talker: понимание и речь

### Qwen2.5-Omni

[Qwen2.5-Omni, §2.1–2.3](https://arxiv.org/abs/2503.20215v1) разделяет мультимодальный текстовый ответ и генерацию речи. Thinker получает текст и представления аудио, изображений и видео. Talker получает представления Thinker и embeddings реально выбранных текстовых токенов, после чего предсказывает речевые коды.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/vlm-2026/qwen25omni-figure2-thinker-talker.png]]

*Jin Xu et al., [Qwen2.5-Omni, Figure 2](https://arxiv.org/pdf/2503.20215v1#page=3). Нижняя часть показывает входы Thinker; верхняя — условную генерацию Talker и декодирование звука. [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/).*

Скрытое представление может передавать контекст ответа, но оно не заменяет выбранное слово. Если два фонетически разных слова близки по смыслу, одного семантического сходства недостаточно, чтобы решить, какое произнести. Поэтому Talker получает и более богатые состояния, и дискретный текстовый выбор.

На примере фразы «Я вернулся» Thinker последовательно выбирает текстовые токены. Talker начинает формировать соответствующий звуковой поток, используя уже доступный текст и состояние. Ему не требуется ждать завершения всего ответа. Это не означает жёсткого соответствия «один текстовый токен — один аудиотокен»: длительность звучания слова зависит от речи, а не от BPE-разбиения.

В Qwen2.5-Omni речевые коды преобразуются в mel-спектрограмму через Flow-Matching DiT, затем модифицированный BigVGAN восстанавливает волну. Ограничения контекста этого декодера влияют на момент, когда можно выдать первые отсчёты; они разобраны в разделе 7.

### Qwen3-Omni: другие входы Talker и другой декодер

[Qwen3-Omni, §2.1–2.5](https://arxiv.org/abs/2509.17765v1) сохраняет Thinker–Talker, но меняет связи между компонентами. Talker получает дискретный текст и мультимодальные признаки; скрытые представления именно текстовых позиций Thinker больше не являются его условием. Это позволяет вмешаться в текстовый результат перед озвучиванием, например применить внешний фильтр или передать подготовленный текст.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/omni-review-2026-10/qwen3omni-architecture.png]]

*Qwen Team, [Qwen3-Omni, Figure 2](https://arxiv.org/pdf/2509.17765v1#page=3). Talker предсказывает нулевой код, небольшой MTP — оставшиеся коды кадра; causal Code2Wav выдаёт звук. [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/).*

AuT, входной аудиоэнкодер Qwen3-Omni, уменьшает частоту mel-признаков в восемь раз до 12.5 позиций/с. Он обучен на распознавании речи и других аудиозадачах, а не только на восстановлении волны. Выходной многословарный кодек решает отдельную задачу синтеза. Совпадение частоты входных и выходных позиций не означает, что их векторы или индексы взаимозаменяемы.

За один временной шаг Talker выбирает первый код кадра. Небольшой MTP Transformer авторегрессионно предсказывает оставшиеся словари этого же кадра; это последовательные шаги маленькой модели, а не одновременный независимый выбор всех кодов. Затем лёгкий причинный ConvNet Code2Wav восстанавливает волну из кодов. Вместо ожидания будущего блока DiT можно обрабатывать уже полученный кадр кодека с левым контекстом.

| Компонент | Qwen2.5-Omni | Qwen3-Omni |
|---|---|---|
| Аудиовход | Энкодер Qwen2-Audio, около 25 позиций/с | AuT, около 12.5 позиций/с |
| Временная сетка | 40 мс и чередование двухсекундных интервалов | 80 мс и выравнивание по IDs |
| Текстовое условие Talker | Скрытые состояния и выбранные текстовые токены | Дискретный текст без прежних скрытых текстовых состояний |
| Генерация кодов | Dual-track авторегрессия | Первый код Talker, остальные — MTP |
| Восстановление волны | Flow-Matching DiT и BigVGAN | Причинный ConvNet |

Thinker и Talker Qwen3-Omni имеют MoE-архитектуру. Размер KV-cache всё равно определяется параметрами attention и длиной контекста; само наличие экспертов не задаёт его объём. Аналогично сокращение частоты аудиопозиций уменьшает число временных шагов, но не делает бесплатными энкодер, MTP и Code2Wav.

### Почему «аудиоголова» — неоднозначное название

Входной проектор переводит аудиопризнаки в размерность LLM. Классифицирующая голова выдаёт, например, класс звукового события. Генератор речи предсказывает последовательность кодов, а кодек превращает их в волну. В Qwen-Omni Talker сам является Transformer; обозначать весь этот путь одной линейной «головой» недостаточно для описания вычислений и обучения.

### Moshi: временная и глубинная авторегрессия

[Moshi, §3.4.1](https://arxiv.org/abs/2410.00037v2) разделяет предсказания по времени и по номеру потока внутри временного шага. Большой Temporal Transformer получает контекст предыдущих шагов и формирует состояние $z_s$. Небольшой Depth Transformer последовательно предсказывает компоненты текущего шага, опираясь на $z_s$ и уже выбранные компоненты.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/omni-review-2026-10/moshi-rq-transformer.png]]

*Alexandre Défossez et al., [Moshi, Figure 3](https://arxiv.org/pdf/2410.00037v2#page=13). Сумма embeddings предыдущего шага поступает в Temporal Transformer; Depth Transformer обрабатывает компоненты нового шага. На рисунке для наглядности четыре компонента, а не фактическое число потоков Moshi. [CC BY-NC-SA 4.0](https://creativecommons.org/licenses/by-nc-sa/4.0/).*

Для одного потока Mimi за секунду нужно предсказать $12.5\cdot8=100$ кодов. Если развернуть их в одну последовательность, большая модель делает 100 шагов/с. При разделении по двум осям она делает 12.5 временных шагов, а маленькая модель выполняет внутрикодовые предсказания. Коды никуда не исчезают; уменьшается число шагов именно большого Transformer.

Для двух звуковых потоков и одного текстового потока Moshi имеет $K=2\cdot8+1=17$ компонентов на шаг. Сначала предсказывается текстовый компонент; затем компоненты аудио. В приложении пользовательский поток берётся из настоящего звука, а не заменяется предсказаниями модели.

~~~python
from math import log, isclose

seconds, rate, codebooks = 300, 12.5, 8
time_steps = int(seconds * rate)
assert time_steps == 3750
assert time_steps * codebooks == 30_000
streams = 2 * codebooks + 1
assert streams == 17 and time_steps * streams == 63_750

# Два условных выбора внутри шага: p(a)=0.6, p(b|a)=0.5.
joint = 0.6 * 0.5
assert isclose(joint, 0.3)
assert isclose(-log(joint), -log(0.6) - log(0.5))
~~~

Произведение условных вероятностей сохраняет зависимости внутри шага. Заменить его произведением безусловных вероятностей компонентов можно только с дополнительным предположением об их независимости. Приведённые вероятности учебные, не выходы Moshi; расчёт числа шагов тоже не измеряет ускорение.

### Inner Monologue, задержка акустики и два потока

Inner Monologue в Moshi — текстовое представление собственной произносимой речи, выровненное с аудио. Это название потока транскрипции, а не требование генерировать скрытое рассуждение. Позиции между словами заполняются PAD; EPAD отмечает завершение заполнения перед следующим словом.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/omni-review-2026-10/moshi-duplex-streams.png]]

*Alexandre Défossez et al., [Moshi, Figure 4](https://arxiv.org/pdf/2410.00037v2#page=15). Ниже пунктирной линии находятся собственные текст и звук модели, выше — пользовательский звук. В акустических рядах есть задержка на один шаг относительно семантических. [CC BY-NC-SA 4.0](https://creativecommons.org/licenses/by-nc-sa/4.0/).*

При акустической задержке $\tau=1$ на шаге $s$ передаётся семантический код кадра $s$, но акустические коды кадра $s-1$. Для трёх кадров условное расписание выглядит так:

| Шаг | Семантика | Акустика |
|---|---|---|
| 0 | Кадр 0 | Ещё нет |
| 1 | Кадр 1 | Кадр 0 |
| 2 | Кадр 2 | Кадр 1 |
| 3 | Завершение | Кадр 2 |

Последний акустический кадр требует дополнительного шага выдачи. Восьмидесятимиллисекундный шаг с такой задержкой добавляет один интервал к доступности полного набора кодов кадра.

~~~python
semantic = ["s0", "s1", "s2"]
acoustic = ["a0", "a1", "a2"]
delayed = [None] + acoustic
semantic_with_flush = semantic + [None]
schedule = list(zip(semantic_with_flush, delayed))
assert schedule == [("s0", None), ("s1", "a0"), ("s2", "a1"), (None, "a2")]
assert delayed[1:] == acoustic
assert 1 / 12.5 == 0.08
~~~

Таблица использует условную нумерацию с нуля и упрощённое завершение; в работающей модели есть собственные специальные значения и состояние потоков. Задержка кодов означает будущий контекст для акустического кадра относительно его семантического кода, но не доступ к ещё не полученному звуку пользователя.

В [§3.4.4](https://arxiv.org/abs/2410.00037v2) относительная задержка текста и аудио позволяет получать режимы ASR и TTS. Если подаются реальные аудиокоды и выбирается текст, модель работает как потоковый распознаватель. Если задан текстовый поток, который опережает аудиокоды, он управляет синтезом. Выравнивание слов, заполнители и задержка определяют смысл этого условия.

Два аудиопотока позволяют представлять одновременную речь и молчание, не вводя обязательные непересекающиеся ходы. Full duplex означает, что во время собственной речи система продолжает принимать пользовательскую. Это отличается от простой выдачи TTS по кускам при выключенном микрофоне.

<span id="7-streaming-меняет-причинный-контракт"></span>
## 7. Потоковая обработка и прерывание ответа

### Причинность и размер блока

Потоковый интерфейс не гарантирует, что модель не использует будущее. Если энкодер обрабатывает двухсекундный блок двунаправленно, признак в начале блока может зависеть от его конца. Такую обработку можно выполнять по мере поступления блоков, но первый результат требует дождаться соответствующего контекста.

В Qwen2.5-Omni аудиоэнкодер использует блоки по две секунды. У выходного DiT другой блоковый механизм: доступ ограничен текущим блоком, двумя предыдущими и одним следующим. Две секунды входного аудиоблока нельзя автоматически приписывать размеру выходного блока кодов.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/omni-review-2026-10/qwen25omni-block-attention.png]]

*Jin Xu et al., [Qwen2.5-Omni, Figure 4](https://arxiv.org/pdf/2503.20215v1#page=5). Маска sliding-window DiT включает левый контекст и один будущий блок. Показан выходной codec-to-waveform тракт, а не маска входного аудиоэнкодера. [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/).*

Для блока с индексом 3 необходимы блоки 1, 2, 3 и 4. Декодирование требует дождаться блока 4; для выдачи без этого ожидания понадобится другая маска, на которую модель должна быть обучена. В условном случае выходной блок длительностью 160 мс и lookahead в один блок добавляют ожидание 160 мс. Это учебная длительность, не восстановленный параметр Qwen2.5-Omni.

~~~python
import numpy as np

query = np.arange(6)[:, None]
key = np.arange(6)[None, :]
allowed = (key >= query - 2) & (key <= query + 1)
assert np.flatnonzero(allowed[3]).tolist() == [1, 2, 3, 4]
assert allowed[3, 4] and not allowed[3, 5]
assert 1 * 0.160 == 0.160
~~~

У причинного оператора изменение будущего не должно менять уже доступный префикс. Это можно проверить на свёртке: сохраняя нужную историю на границе блоков, потоковый расчёт воспроизводит обычную причинную свёртку всей последовательности.

~~~python
import numpy as np

x = np.array([1., 2., 3., 4., 5., 6.])
kernel = np.array([0.5, 0.3, 0.2])
full = np.convolve(x, kernel)[:len(x)]
history = np.zeros(len(kernel) - 1)
pieces = []
for chunk in [x[:2], x[2:5], x[5:]]:
    joined = np.r_[history, chunk]
    output = np.convolve(joined, kernel)
    start = len(history)
    pieces.append(output[start:start + len(chunk)])
    history = joined[-(len(kernel) - 1):]
assert np.allclose(np.concatenate(pieces), full)

changed = x.copy()
changed[3:] += 100
assert np.allclose(np.convolve(changed, kernel)[:3], full[:3])
centered = np.convolve(x, np.ones(3) / 3, mode="same")
centered_changed = np.convolve(changed, np.ones(3) / 3, mode="same")
assert centered_changed[2] != centered[2]
~~~

Последняя свёртка использует будущий соседний отсчёт. На настоящем кодеке проверяют всю цепочку: padding свёрток, временную нормализацию, attention, кэш и склейку волн. Совпадение при одной длине блока не доказывает корректность на других границах.

### Первый звук, непрерывное воспроизведение и RTF

Задержка до первого слышимого звука включает поступление нужного контекста, подготовку признаков, вычисления Thinker и Talker, декодирование кодов, передачу и воспроизведение. Лог «первый токен сгенерирован» фиксирует только один этап.

Real-time factor, RTF, сравнивает длительность вычисления с длительностью полученного звука. RTF ниже единицы означает, что в среднем звук создаётся быстрее, чем воспроизводится. Это не гарантирует отсутствие пауз: один задержавшийся блок может исчерпать накопленный буфер.

~~~python
import numpy as np

audio_durations = np.array([0.08, 0.08, 0.08, 0.08])
compute_times = np.array([0.02, 0.02, 0.25, 0.02])
arrivals = compute_times.cumsum()
rtf = compute_times.sum() / audio_durations.sum()
playback_start = arrivals[0]
deadlines = playback_start + np.r_[0., audio_durations.cumsum()[:-1]]
late = arrivals > deadlines + 1e-12
assert np.isclose(rtf, 0.96875) and rtf < 1
assert np.flatnonzero(late).tolist() == [2, 3]
~~~

Третий и четвёртый блоки опаздывают относительно исходного расписания, хотя средний RTF меньше единицы. После остановки проигрывания расписание сдвинется; этот расчёт не подсчитывает число реальных заиканий. Предварительное накопление буфера может устранить паузу ценой более позднего начала ответа.

### Прерывание

Для прерывания нужно продолжать слушать микрофон, обнаружить новую реплику, остановить генерацию и очистить ещё не проигранный звук. Уже отправленные в устройство отсчёты могут воспроизводиться и после отмены серверного запроса.

Пусть пользователь начал говорить в 1000 мс, система обнаружила речь в 1040, отменила запрос в 1055, а последний звук модели был слышен до 1180. Задержка прерывания равна 180 мс, а не 55. Оставшиеся 125 мс относятся к уже подготовленному выходу и тракту воспроизведения. Эти числа задают учебный журнал событий, не характеристику конкретного продукта.

Содержимое диалога тоже требует согласования. Модель могла успеть сгенерировать предложение целиком, а пользователь услышал только первую половину. Следующее состояние не должно безусловно считать всё предложение произнесённым. Приложение сохраняет границу реально воспроизведённого ответа и использует её при продолжении.

## 8. Что именно означает «omni»

Общее пространство представлений, понимание нескольких входных модальностей и генерация нескольких выходных модальностей задают разные операции. ImageBind выполняет межмодальное сравнение. VLM с ответом текстом может понимать изображение и звук, не имея декодера для их генерации. Talker добавляет речевой выход, но не превращает модель в генератор видео.

| Система | Вход | Выход в рассматриваемой постановке |
|---|---|---|
| ImageBind | Текст, изображение, звук и другие поддерживаемые модальности | Векторы для сравнения и переноса |
| Whisper | Аудио | Текст, язык, временные токены заданного режима |
| xGen-MM-Vid | Выбранные кадры и текст | Текстовый ответ |
| Qwen2.5/3-Omni | Текст, изображения, видео, аудио | Текст и речь |
| Moshi | Пользовательский звуковой поток и история | Собственный текстовый и звуковой потоки |

Эта таблица описывает зафиксированные в источниках интерфейсы. Для сравнения развёрнутых систем дополнительно проверяют, доступны ли все входы одновременно, продолжается ли приём звука во время ответа и какие выходные режимы реально поддерживает используемый API.

Архитектура, обучение и интерфейс сервиса могут расходиться. Причинный кодек не гарантирует, что приложение перестанет буферизовать всю реплику. Наличие отдельного Talker не гарантирует прерывание через клиентский проигрыватель. Обучение мультимодального понимания подробно связано с [[02 Areas/ML & DL/00 Учебник/16 Multimodal Models/64c Обучение VLM — alignment, instruction tuning и данные|данными и стадиями обучения VLM]].

<span id="9-матрица-оценивания"></span>
## 9. Оценивание видео и речи

Для исходного вопроса о двери нужны как минимум три проверки: найден ли момент действия, верно ли прочитана речь и сопоставлены ли они на одной временной оси. Удачная транскрипция всей минуты не подтверждает правильный выбор нужного предложения.

| Задача | Что фиксируется | Проверка |
|---|---|---|
| Распознавание действия | Выбранные кадры и их timestamps | Замена или удаление целевого события |
| Порядок событий | Пары событий и их порядок | Перестановка при сохранении самих объектов |
| Поиск момента | Начало и конец интервала | Temporal IoU с эталоном |
| ASR | Транскрипция | WER/CER с указанной нормализацией |
| Неречевой звук | Класс и интервал | Точность по событиям и условиям шума |
| Аудиовизуальная связь | Действие и соответствующий звук | Контролируемый сдвиг дорожки |
| Содержание ответа | Ответ до синтеза и произнесённое | Проверка смысла и ошибок синтеза раздельно |
| Звучание | Восстановленная волна | Разборчивость и слепое слушательское оценивание |
| Потоковый режим | Моменты поступления и воспроизведения | Первый звук, паузы, RTF, задержка прерывания |

Для интервалов temporal IoU равен длительности пересечения, делённой на длительность объединения. Если правильный эпизод занимает $[18.3,18.7]$, а модель вернула $[18,19]$, точка 18.4 лежит в обоих, но IoU равен всего 0.4. Попадание одной точки не означает точной локализации всего события.

~~~python
from math import isclose

gold, predicted = (18.3, 18.7), (18.0, 19.0)
intersection = max(0, min(gold[1], predicted[1]) - max(gold[0], predicted[0]))
union = (gold[1] - gold[0]) + (predicted[1] - predicted[0]) - intersection
assert isclose(intersection / union, 0.4)
assert gold[0] <= 18.4 < gold[1] and predicted[0] <= 18.4 < predicted[1]
~~~

Аудиокачество проверяют при известных уровнях шума. Отношение сигнал/шум в децибелах вычисляется как $10\log_{10}(P_{\mathrm{signal}}/P_{\mathrm{noise}})$. При SNR 10 дБ мощность сигнала в десять раз выше мощности шума. Это не означает, что шум безвреден для любого слова: важны спектр шума, совпадение по времени и тип события.

~~~python
import numpy as np

rng = np.random.default_rng(20261020)
signal = np.sin(2 * np.pi * 440 * np.arange(1600) / 16_000)
noise = rng.normal(size=len(signal))
signal_power = np.mean(signal ** 2)
noise *= np.sqrt(signal_power / (10 * np.mean(noise ** 2)))
snr_db = 10 * np.log10(signal_power / np.mean(noise ** 2))
assert np.isclose(snr_db, 10)
~~~

Эти примеры проверяют формулы, а не качество обученных моделей. Для сравнения архитектур нужен один и тот же набор роликов и вопросов, одинаковый доступ к звуку и сопоставимые бюджеты кадров. Для сравнения сервиса дополнительно измеряются вся задержка и потребление ресурсов, включая отбор кадров, энкодеры, речевой декодер и клиентское воспроизведение.
