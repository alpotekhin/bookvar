# Документы, OCR и visual grounding

В счёте рядом могут стоять стоимость товаров, налог, уже внесённый аванс и сумма к оплате. Прочитать все четыре числа ещё не значит ответить на вопрос «сколько осталось заплатить?». Нужно определить назначение каждой строки и выбрать значение, которое относится к вопросу. Если в документе нет готового ответа, придётся выполнить вычисление.

Предположим, пользователь спрашивает: «Какова итоговая сумма и где она указана?» На странице написано:

| Поле | Значение |
|---|---:|
| Промежуточный итог | 11 000 ₽ |
| Налог | 1 480 ₽ |
| Итого | 12 480 ₽ |

Здесь ожидается сумма 12 480 ₽ с указанием страницы и области, в которой она напечатана. Система может отдельно проверить равенство $11\,000+1\,480=12\,480$. Такое совпадение помогает обнаружить ошибку чтения, но само по себе не устанавливает, что выбрана нужная строка: в другом счёте под итогом может быть указан аванс.

## 1. Из каких подзадач складывается ответ

Оптическое распознавание текста, OCR, восстанавливает символы по изображению. В распространённом каскаде детектор сначала находит текстовые строки или слова, а распознаватель преобразует каждый найденный фрагмент в последовательность символов. Детектор может пропустить строку; распознаватель может спутать цифру ноль и букву «О». Повторное распознавание найденного фрагмента не вернёт строку, которую детектор вообще не передал дальше.

После распознавания требуется восстановить порядок чтения. На простой странице строки идут сверху вниз. На двухколоночной странице сначала обычно читается одна колонка, затем другая. Таблица, подпись к рисунку и сноска имеют собственные правила. Сортировка всех слов по вертикальной координате смешает строки двух колонок, хотя каждое слово может быть распознано верно.

Следующий шаг связывает текст с его ролью. Для счёта это отношения между названием поля и значением, для таблицы — между ячейкой и заголовками, для графика — между отметкой и шкалой. Связь с местом на изображении называют visual grounding. Ответ может сопровождаться рамкой вокруг суммы, точкой внутри объекта или маской его пикселей; эти представления дают разную информацию.

| Подзадача | Результат для счёта | Возможная ошибка |
|---|---|---|
| Обнаружение | Область «Итого 12 480 ₽» | Строка не найдена |
| Распознавание | Символы «12 480» | Получено «12 48О» |
| Порядок чтения | Заголовок и сумма в своей строке | Сумма присоединена к соседней колонке |
| Извлечение | Значение связано с «Итого» | Выбран промежуточный итог |
| Локализация | Страница и рамка суммы | Рамка указывает на налог |
| Вычисление | Проверка суммы слагаемых | Ошибка арифметики при верном чтении |

Каскадная система хранит эти результаты раздельно. Модель, которая сразу генерирует ответ по изображению, может выполнять несколько подзадач внутри одного прохода. Однако её результат оценивают по тем же различиям: правильное число не подтверждает правильность рамки, а безошибочная транскрипция не подтверждает правильность выбора поля.

## 2. Четыре архитектурных подхода

### Каскад с внешним OCR

Внешний OCR возвращает текст и координаты. Следующий компонент находит поле «Итого» и связанную сумму. Этот компонент может быть набором правил, моделью классификации или LLM. Если LLM получает только текст, она уже не видит исходное начертание спорной цифры. Для повторной проверки ей нужно передать изображение соответствующей области либо снова вызвать распознаватель.

Координаты сохраняют и после текстовой токенизации. Если слово разбилось на три subword-токена, все три можно связать с исходной областью. По найденному диапазону токенов тогда удастся восстановить фрагмент страницы. Если оставить только строку «Итого 12480», эта связь исчезнет.

Геометрия помогает сузить выбор, но не определяет семантику поля сама по себе. Число справа от «Итого» является хорошим кандидатом в счёте с обычной вёрсткой. При переносе значения на следующую строку или расположении полей справа налево такое правило потребует изменений.

### LayoutLMv3: текст, расположение и изображение

[Huang et al., LayoutLMv3, §2.1–2.2](https://arxiv.org/abs/2204.08387v3) объединяют OCR-текст и изображение в двунаправленном Transformer. Текстовая ветвь содержит embedding токена, его позицию в последовательности и двумерное расположение текстового сегмента. В LayoutLMv3 слова одного сегмента разделяют его координаты. Визуальная ветвь получает линейные проекции патчей страницы. Обе последовательности поступают в общий Transformer, поэтому представление слова может учитывать соседние слова и визуальное содержимое страницы.

В базовой конфигурации из статьи изображение $224\times224$ разбивается на патчи $16\times16$. Получаются $14\times14=196$ патчей. Это сравнительно грубое изображение для мелкого текста, зато OCR уже передал распознанные символы через текстовую ветвь. LayoutLMv3 не является OCR-free моделью.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/documents-review-2026-10/layoutlmv3-objectives.png]]

*Yupan Huang et al., [LayoutLMv3, Figure 3](https://arxiv.org/pdf/2204.08387v3#page=3). Текстовые и визуальные токены поступают в общий Transformer; сверху показаны три предобучающие цели. Оригинальные подписи сохранены, удалены поля и подпись страницы. [CC BY-NC-SA 4.0](https://creativecommons.org/licenses/by-nc-sa/4.0/).*

Три цели обучения используют разные наблюдаемые величины.

1. Masked language modeling, MLM, восстанавливает закрытые текстовые токены. Их координаты остаются известны, поэтому модель может использовать и текстовый контекст, и соответствующий участок изображения.
2. Masked image modeling, MIM, восстанавливает дискретные коды закрытых патчей. Целью служат коды отдельного image tokenizer, а не RGB-значения пикселей. Такой tokenizer нужен для подготовки обучающих целей; его нельзя смешивать с линейной проекцией входных патчей.
3. Word-patch alignment, WPA, предсказывает, закрыты ли соответствующие видимому слову патчи. Когда слово и его визуальная область доступны, метка — aligned. Если соответствующее изображение закрыто, метка — unaligned. Закрытые текстовые токены исключаются из WPA.

На рисунке $T_1$ и $T_2$ закрыты, поэтому модель восстанавливает их через MLM. Патчи $V_2$ и $V_3$ восстанавливаются через MIM. Видимое слово $T_3$ связано с закрытым патчем и получает unaligned, а $T_4$ связано с видимым $V_4$ и получает aligned. WPA здесь не является задачей «найти правильную рамку среди нескольких кандидатов».

Пусть в учебном примере правильным целям назначены вероятности 0.8 для одного текстового токена, 0.5 для одного кода патча и 0.9 для одной WPA-метки. При одной позиции в каждой задаче сумма трёх cross-entropy равна

$$
\begin{aligned}
L&=-\log 0.8-\log 0.5-\log 0.9\\
 &\approx1.02165.
\end{aligned}
$$

Вероятности выбраны для расчёта; это не измерение обученной LayoutLMv3. На реальном батче учитываются все выбранные позиции и конкретная нормировка потерь.

~~~python
from math import log, isclose

probabilities = {"MLM": 0.8, "MIM": 0.5, "WPA": 0.9}
losses = {name: -log(p) for name, p in probabilities.items()}
assert isclose(sum(losses.values()), 1.0216512475319812)
assert 224 // 16 * (224 // 16) == 196
~~~

Для прикладной задачи поверх выходных представлений обучают соответствующую голову. Извлечение сущностей может размечать текстовые токены, ответ на вопрос — выбирать начало и конец текстового диапазона. Это отличается от свободной генерации JSON: извлекающая голова выбирает из OCR-текста. Если OCR вообще не распознал сумму, правильного диапазона в её входе нет.

### Donut: от изображения к последовательности полей

[Kim et al., Donut, §2.2–2.4](https://arxiv.org/abs/2111.15664v5) исключают внешний OCR из пути инференса. Swin Transformer преобразует изображение в визуальные представления. Авторегрессионный декодер на основе BART, инициализированный многоязычными весами, генерирует текст, обращаясь через cross-attention к выходу энкодера. Задание определяется префиксом: классификация документа, ответ на вопрос или разбор полей.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/documents-review-2026-10/donut-overview.png]]

*Geewook Kim et al., [Donut — official implementation, overview](https://github.com/clovaai/donut/blob/4cfcf972560e1a0f26eb3e294c8fc88a0d336626/misc/overview.png). Одно изображение используется для классификации, VQA и извлечения структуры. Исходный PNG без изменений. © 2022–present NAVER Corp.; [MIT license](/licenses/donut-4cfcf972-MIT.txt).*

Для поля суммы обучающая цель может иметь вид:

~~~text
<s_total>12480</s_total><s_currency>RUB</s_currency>
~~~

Специальные токены обозначают границы полей. Декодер последовательно предсказывает открывающий токен, содержимое и закрывающий токен; детерминированный преобразователь восстанавливает объект:

~~~json
{"total": "12480", "currency": "RUB"}
~~~

В опубликованном коде Donut это функции [json2token и token2json](https://github.com/clovaai/donut/blob/4cfcf972560e1a0f26eb3e294c8fc88a0d336626/donut/model.py#L499). Для списка используется разделитель `<sep/>`. Последовательность с двумя товарными позициями должна сохранять границы как полей, так и элементов списка. Преобразователь не проверяет смысл значений и не исправляет неверно прочитанную цифру.

На обучении используется teacher forcing. При предсказании содержимого поля декодер видит правильный предыдущий префикс; при инференсе — собственный. Если модель не сгенерировала закрывающий токен, поле может не восстановиться. Если она сгенерировала корректные теги с неверной суммой, JSON успешно разберётся, но ответ останется неверным. Проверки формата и значения нужны раздельно.

OCR-free относится к входам модели при инференсе. Предобучение Donut всё равно использует текстовую разметку: для реальных сканов IIT-CDIP авторы получили псевдометки внешним OCR, а SynthDoG создаёт синтетические документы с известным текстом. Сначала модель обучают читать текст страницы по порядку, затем дообучают на последовательности, соответствующие прикладной структуре. Отсутствие внешнего OCR на инференсе не означает отсутствия OCR-меток в подготовке данных.

Координаты не появляются из такой сериализации автоматически. Если цель содержит только `total`, модель обучается возвращать сумму, но не её рамку. Для локализации нужна отдельная разметка и поддерживаемый формат либо дополнительный этап поиска значения на странице.

### Pix2Struct: восстановление структуры по скриншоту

[Lee et al., Pix2Struct, §2.2–2.5](https://proceedings.mlr.press/v202/lee23g.html) тоже используют image-encoder/text-decoder, но выбирают другую задачу предобучения. Для веб-страницы доступны скриншот и HTML-дерево. Из дерева удаляют невидимые элементы и лишние уровни вложенности, оставляя текст, а также имена файлов и alt-text изображений. Цель — упрощённая сериализация структуры, а не исходный HTML со всеми стилями и скриптами.

Если сериализация всей страницы не помещается в выходную последовательность, выбирают поддерево. Его область отмечают на скриншоте. Часть текста внутри области закрывают масками, а декодер восстанавливает всё выбранное поддерево, включая видимые и закрытые фрагменты. В статье маскируют 50% текста выбранного поддерева.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/documents-review-2026-10/pix2struct-screenshot-parsing.png]]

*Kenton Lee et al., [Pix2Struct, Figure 3](https://proceedings.mlr.press/v202/lee23g/lee23g.pdf#page=4). Слева исходная форма, посередине выделенная область с масками, справа целевая сериализация. Сохранён полный рисунок без окружающего текста. [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/).*

В исходном примере формы слово Python закрыто, C++ остаётся видимым, а у Java закрыта часть надписи. Модель должна восстановить все три пункта и их вложенность, а не только дописать закрытые буквы. Восстановление видимого C++ обучает чтению; восстановление Python требует использовать контекст формы и оставшееся изображение; поля `img_alt` добавляют описание изображения. Обучающая цель объединяет эти сигналы в одной последовательности.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/vlm-2026/pix2struct-figure1-tasks.png]]

*Kenton Lee et al., [Pix2Struct, Figure 1](https://proceedings.mlr.press/v202/lee23g/lee23g.pdf#page=2). Слева screenshot parsing, справа diagram QA, описание интерфейса и DocVQA. Вопросы на примерах VQA напечатаны над изображением. Та же иллюстрация восстановлена из PDF в большем разрешении, без заголовка страницы статьи. [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/).*

При дообучении на VQA Pix2Struct получает вопрос как надпись над изображением. Он читает вопрос и документ через визуальный вход; это решение Pix2Struct, а не обязательное свойство OCR-free моделей. В задачах выбора элемента интерфейса рамку кандидата рисуют на изображении, модель оценивает кандидатов, а не обязана сразу генерировать координаты.

Перед screenshot parsing авторы обучают модель читать синтетические изображения текстовых фрагментов. В §2.4 это reading curriculum: первоначальная задача даёт декодеру навык чтения до перехода к более сложной структурной цели. Предобучение на структуру не устраняет потребность в распознавании символов.

### Универсальная VLM и документные данные

Универсальная VLM получает визуальные токены и текстовую инструкцию. Её документные возможности зависят от разрешения, способа сжатия визуальных токенов, разметки и заданий обучения. Наличие vision encoder и LLM ещё не определяет, какие поля модель способна надёжно читать или локализовать.

[Qwen2.5-VL, §2.2](https://arxiv.org/abs/2502.13923v1) использует документные цели, в которых HTML содержит текст, таблицы, формулы, порядок элементов и координаты областей. В [Qwen3-VL, §3.2.3](https://arxiv.org/abs/2511.21631v1) разметку реальных документов готовят каскадом: layout-модель определяет области и порядок чтения, Qwen2.5-VL-72B распознаёт отдельные области, затем результаты собираются с сохранением расположения.

У Qwen3-VL указаны два представления: QwenVL-HTML с рамками отдельных элементов и QwenVL-Markdown, в котором локализуются изображения и таблицы, а таблицы записываются в LaTeX. Наличие рамки для каждой строки текста во втором формате нельзя предполагать без дополнительной разметки.

| Подход | Вход после подготовки страницы | Возможный выход |
|---|---|---|
| OCR + правила или LLM | Распознанный текст и сохранённые метаданные | Выбранные поля или ответ |
| Layout-aware encoder | OCR-токены, расположение и патчи | Метки или диапазон ответа |
| OCR-free encoder–decoder | Изображение и поддерживаемое задание | Последовательность текста или структуры |
| Универсальная VLM | Визуальные токены и инструкция | Ответ в поддерживаемом обучением формате |

Эти варианты допускают сочетание. Внешний OCR может подготовить индекс документов, VLM — проверить найденную страницу, а правила — сверить сумму позиций. Каскад оценивают целиком и по этапам: удачный отдельный OCR не гарантирует правильного ответа по документу.

## 3. Как проходит один запрос

Для счёта из начала главы сначала сохраняется исходная страница. Если PDF содержит текстовый слой, его можно использовать как отдельный источник кандидатов; для скана требуется распознавание изображения. Текстовый слой тоже может быть ошибочным или относиться к прежней версии изображения, поэтому его наличие не заменяет проверку видимого документа.

После растеризации каждый обнаруженный фрагмент получает текст, рамку, страницу и идентификатор. В учебном примере страница имеет размер $1000\times1400$ пикселей. OCR вернул четыре фрагмента в произвольном порядке:

~~~text
v_total     "12 480"                 [700, 1140, 910, 1180]
l_subtotal  "Промежуточный итог"      [100, 1060, 500, 1100]
l_total     "Итого"                  [100, 1140, 250, 1180]
v_subtotal  "11 000"                 [700, 1060, 910, 1100]
~~~

Порядок списка не является порядком чтения. Области лежат в двух непересекающихся горизонтальных строках. Их можно сгруппировать по центру вертикальной координаты, затем упорядочить слева направо. Получатся строки «Промежуточный итог 11 000» и «Итого 12 480».

~~~python
items = [
    ("v_total", "12 480", (700, 1140, 910, 1180)),
    ("l_subtotal", "Промежуточный итог", (100, 1060, 500, 1100)),
    ("l_total", "Итого", (100, 1140, 250, 1180)),
    ("v_subtotal", "11 000", (700, 1060, 910, 1100)),
]
# Границы строк известны из учебной постановки.
groups = {}
for ident, text, box in items:
    cy = (box[1] + box[3]) / 2
    row = 0 if cy < 1120 else 1
    groups.setdefault(row, []).append((box[0], ident, text))
rows = [
    [entry[1] for entry in sorted(groups[row])]
    for row in sorted(groups)
]
assert rows == [["l_subtotal", "v_subtotal"], ["l_total", "v_total"]]
answer_id = rows[1][1]
answer_box = next(box for ident, _, box in items if ident == answer_id)
assert answer_box == (700, 1140, 910, 1180)
~~~

Правило границы `1120` применимо только к заданным строкам. В реальной странице строки могут наклоняться, пересекаться с таблицей или принадлежать разным колонкам. Тогда сначала определяют блоки и их порядок, а уже внутри блока — строки. Этот код показывает, какую связь нужно сохранить, а не реализует общий анализ вёрстки.

После выбора поля ответ ссылается на `v_total`. Для показа пользователю система берёт рамку этой области, а не просит языковую модель заново придумать координаты по текстовому ответу. Если VLM непосредственно генерирует рамку по изображению, её рассматривают как отдельное предсказание и проверяют относительно страницы.

Для многостраничного документа добавляется выбор страницы. Пусть нужная таблица есть на страницах 7 и 12, но на 7-й находится прошлый год, а на 12-й — текущий. Поиск слова «Итого» найдёт обе. Вопрос сопоставляется с заголовком, датой и содержимым страницы; после выбора сохраняются номер страницы и конкретная таблица. Если поиск не вернул страницу 12, модель ответа не сможет извлечь её значение из переданного контекста. Этот случай связывает документный QA с [[02 Areas/ML & DL/00 Учебник/15 Embeddings, Retrieval и RAG/63 RAG — полный конвейер|поиском и RAG]].

## 4. Почему разрешение и структура неразделимы

Пусть исходная страница имеет высоту 2800 пикселей, а строчная буква занимает 20 пикселей. Уменьшение высоты до 448 сокращает букву до $20\cdot448/2800=3.2$ пикселя. После интерполяции тонкий штрих может исчезнуть. По такому входу нельзя гарантированно отличить два символа, если различие больше не представлено пикселями.

Разбиение страницы на фрагменты сохраняет более крупные буквы, но требует собрать результат обратно. Строка на границе двух фрагментов может распознаться дважды или оказаться обрезанной в обоих. Перекрытие уменьшает вероятность обрезки, одновременно создавая дубликаты. Их объединяют после перевода координат в общую систему страницы, учитывая текст и геометрическое совпадение. Совпадающий текст сам по себе недостаточен: сумма 12 480 может законно встречаться в двух разных местах.

Pix2Struct меняет размер изображения с сохранением пропорций и выбирает разрешение под бюджет патчей. Двумерные позиционные embeddings сохраняют расположение патчей в сетке. Это позволяет использовать вытянутые страницы без обязательного растяжения в квадрат.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/documents-review-2026-10/pix2struct-variable-resolution.png]]

*Kenton Lee et al., [Pix2Struct, Figure 2](https://proceedings.mlr.press/v202/lee23g/lee23g.pdf#page=3). Слева пропорции сохранены, справа изображение растянуто; оба примера используют бюджет 36 патчей. Сохранены обе панели и подписи, удалён окружающий текст. [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/).*

В условной сетке из 36 патчей вытянутая страница может занять $3\times12$ патчей вместо квадратных $6\times6$. Первая сетка сохраняет отношение сторон $1:4$, вторая — $1:1$. Обе имеют одинаковое число элементов, но геометрия текста различается. Конкретный preprocessing учитывает также округление размеров и ограничения модели; схема не задаёт универсальный алгоритм подбора сетки.

~~~python
from math import isclose

original_height, letter_height = 2800, 20
reduced_letter = letter_height * 448 / original_height
assert isclose(reduced_letter, 3.2)
assert 3 * 12 == 6 * 6 == 36
assert isclose(3 / 12, 0.25)
~~~

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/vlm-2026/qwen2vl-figure11-dense-ocr.png]]

*Peng Wang et al., [Qwen2-VL, Figure 11](https://arxiv.org/pdf/2409.12191v1#page=29). В исходной демонстрации запрошен перевод плотного китайского текста на английский. Это качественный пример чтения с последующей генерацией перевода, а не посимвольная транскрипция и не измерение CER. Существующий рисунок сохранён без изменений.*

Перевод может выглядеть связно даже при пропуске слова или числа в исходнике. Демонстрация перевода не устанавливает точность извлечения банковских реквизитов или суммы. Для таких полей нужен эталон исходных символов и отдельная проверка значения.

## 5. Таблица и график не являются линейным текстом

В таблице число определяется заголовками строки и столбца. Рассмотрим две товарные позиции:

| Товар | Количество | Цена за единицу, ₽ | Сумма строки, ₽ |
|---|---:|---:|---:|
| Кофе | 2 | 900 | 1800 |
| Чай | 1 | 300 | 300 |

Для кофе число 900 является ценой единицы, 2 — количеством, 1800 — стоимостью позиции. Последнее проверяется как $2\cdot900$. Итог равен $1800+300=2100$. Если OCR сохранил числа, но поменял местами заголовки «Цена» и «Сумма», транскрипция отдельных ячеек может остаться правильной, а извлечение данных — стать неверным.

Структурное представление хранит строку, столбец и при необходимости объединение ячеек. Заголовок «2025» может занимать два столбца: «Выручка» и «Расходы». Чтобы ответить о расходах за 2025 год, нужны оба уровня заголовка. Плоская строка «2025 Выручка Расходы» без связей не задаёт, к какому числу относится каждый заголовок.

В JSON позиции можно сохранить так:

~~~json
[
  {"name": "Кофе", "quantity": 2, "unit_price": "900.00", "line_total": "1800.00"},
  {"name": "Чай", "quantity": 1, "unit_price": "300.00", "line_total": "300.00"}
]
~~~

Денежные значения записаны десятичными строками. При проверке используется десятичная арифметика, чтобы ошибки двоичного округления не выдавались за расхождение с документом. Налог, скидку, доставку и правила округления добавляют отдельными полями, когда они действительно присутствуют в документе.

~~~python
from decimal import Decimal

positions = [
    {"quantity": 2, "unit_price": "900.00", "line_total": "1800.00"},
    {"quantity": 1, "unit_price": "300.00", "line_total": "300.00"},
]
for position in positions:
    expected = position["quantity"] * Decimal(position["unit_price"])
    assert expected == Decimal(position["line_total"])
total = sum((Decimal(p["line_total"]) for p in positions), Decimal("0"))
assert total == Decimal("2100.00")
~~~

Проверка равенства не восстанавливает потерянный заголовок: если ошибочно прочитаны и количество, и сумма, случайное согласование возможно. Сохраняются и исходные значения, и области, из которых они прочитаны. Вычисленное значение отдельно отмечается как вычисленное, а не напечатанное.

Для графика нужно определить оси, единицы, легенду и тип шкалы. Пусть отметке 10 соответствует вертикальная координата $y=300$, отметке 100 — $y=100$, а точка лежит при $y=200$. На линейной шкале это середина между 10 и 100, то есть 55. На логарифмической шкале это середина между их логарифмами: $\sqrt{10\cdot100}\approx31.62$.

Обозначим долю расстояния от нижней отметки к верхней через $t=(y_{\mathrm{low}}-y)/(y_{\mathrm{low}}-y_{\mathrm{high}})$. Тогда линейная интерполяция равна $a+t(b-a)$, а логарифмическая — $\exp((1-t)\log a+t\log b)$ для положительных $a,b$.

~~~python
from math import exp, log, isclose

a, b = 10.0, 100.0
y_low, y_high, y = 300.0, 100.0, 200.0
t = (y_low - y) / (y_low - y_high)
linear = a + t * (b - a)
logarithmic = exp((1 - t) * log(a) + t * log(b))
assert linear == 55.0
assert isclose(logarithmic, 31.622776601683793)
~~~

Здесь пиксельная координата задана точно. При чтении настоящего графика толщина линии, сжатие изображения и выбор центра отметки дают погрешность, которую следует переносить на численное значение. Ответ «31.6227766» не оправдан, если линия занимает несколько пикселей.

## 6. Grounding как язык доказательства

Точка сообщает, какой экземпляр имеется в виду, но не описывает его границы. Рамка приближённо ограничивает объект прямоугольником и может включать фон или соседние объекты. Маска выделяет множество пикселей и подходит для проверки формы или площади. Нельзя восстановить точную маску только по рамке без дополнительного предсказания.

В [Molmo and PixMo, §3–4](https://arxiv.org/abs/2409.17146v2) аннотаторы описывают объект и указывают все его экземпляры. В данных присутствуют запросы об отсутствующих объектах. Для подсчёта модель последовательно выдаёт точки, соответствующие экземплярам, а затем количество. Координаты Molmo записываются в диапазоне 0–100; при нескольких объектах точки упорядочиваются сверху вниз и слева направо.

Для вопроса о трёх чашках ожидаются три точки в трёх разных чашках. Четыре точки не доказывают наличие четырёх чашек: две могут попасть в один экземпляр. В учебной проверке ниже экземпляры заданы непересекающимися прямоугольниками. На реальном изображении нужны эталонные области либо независимая разметка; общая близость точек не заменяет принадлежность экземплярам.

~~~python
regions = [(0, 0, 10, 10), (20, 0, 30, 10), (40, 0, 50, 10)]
points = [(5, 5), (25, 5), (26, 5), (45, 5)]
def instances_hit(regions, points):
    hits = []
    for x, y in points:
        candidates = [
            i for i, (x1, y1, x2, y2) in enumerate(regions)
            if x1 <= x < x2 and y1 <= y < y2
        ]
        assert len(candidates) == 1  # Условие именно этого примера.
        hits.append(candidates[0])
    return hits

hits = instances_hit(regions, points)
assert hits == [0, 1, 1, 2]
assert len(points) == 4 and len(set(hits)) == 3
assert instances_hit(regions, []) == []
~~~

На счёте рамка суммы позволяет увидеть выбранное место. Она не доказывает причинную зависимость ответа от этого места: модель могла отдельно угадать сумму и правдоподобную рамку. Такая зависимость проверяется вмешательствами в изображение, описанными ниже.

Различать следует и единицы координат.

| Модель и зафиксированный источник | Представление координат |
|---|---|
| Molmo, §4, arXiv v2 | Нормированные координаты 0–100 |
| Qwen2.5-VL, §2.1.2 и grounding data, arXiv v1 | Абсолютные координаты изображения |
| Qwen3-VL, §3.2.4, arXiv v1 | Нормированные координаты 0–1000 |

Это соглашения конкретных моделей. Размер изображения, к которому относится абсолютная координата, должен совпадать с соглашением используемого процессора. Интерфейс, который перед вызовом самостоятельно уменьшил изображение, обязан сохранить это преобразование.

## 7. Возврат координат в оригинал

Пусть исходную страницу масштабировали в $s$ раз, затем добавили padding $(p_x,p_y)$ и взяли фрагмент с началом $(o_x,o_y)$ в получившемся изображении. Модель указала точку $(u,v)$ внутри фрагмента. Сначала возвращается смещение фрагмента, затем удаляется padding, затем отменяется масштабирование:

$$
x=\frac{u+o_x-p_x}{s},\qquad
y=\frac{v+o_y-p_y}{s}.
$$

При $s=0.5$, $p_x=20$, $p_y=0$, начале фрагмента $(500,800)$ и локальной точке $(120,60)$ получается $(1200,1720)$. Если модель выдала нормированную координату, её сначала переводят в пиксели фрагмента. Для фрагмента $600\times400$ точка Molmo $(20,15)$ означает $(120,60)$ пикселей. Qwen3-VL записал бы ту же геометрическую точку как $(200,150)$.

~~~python
from math import isclose

tile_width, tile_height = 600, 400
molmo, qwen3 = (20, 15), (200, 150)
molmo_px = (molmo[0] / 100 * tile_width, molmo[1] / 100 * tile_height)
qwen3_px = (qwen3[0] / 1000 * tile_width, qwen3[1] / 1000 * tile_height)
assert molmo_px == qwen3_px == (120, 60)

s, px, py, ox, oy = 0.5, 20, 0, 500, 800
u, v = molmo_px
x, y = (u + ox - px) / s, (v + oy - py) / s
assert isclose(x, 1200) and isclose(y, 1720)
~~~

Деление нормированных координат на 100 вместо 1000 даст десятикратную ошибку, хотя строка с координатами будет синтаксически правильной. Обрезка результата до границы страницы может скрыть ошибку, но не исправит преобразование.

### Поворот и рамки

Для нескольких преобразований удобно использовать однородные координаты. Пусть матрица $A$ переводит исходную точку $(x,y,1)^\top$ в координаты фрагмента $(u,v,1)^\top$. Тогда обратный переход задаётся $A^{-1}$. В случае масштаба, padding и crop:

$$
A=
\begin{pmatrix}
s&0&p_x-o_x\\
0&s&p_y-o_y\\
0&0&1
\end{pmatrix}.
$$

Если перед масштабированием страницу повернули на 90° по часовой стрелке, при координатах границ изображения шириной $W$ и высотой $H$ используется $x'=H-y,\;y'=x$. Это соглашение о непрерывных границах $[0,W]\times[0,H]$; для индексов центров пикселей формулы и крайние значения отличаются.

Рамка $[700,1140,910,1180]$ на странице $1000\times1400$ после такого поворота имеет границы $[220,700,260,910]$. Чтобы вернуть рамку, преобразуют все четыре угла, затем берут минимум и максимум каждой координаты. Для произвольного угла прямоугольная оболочка повернутого объекта включает лишнюю площадь; точнее сохранять четырёхугольник.

~~~python
import numpy as np

W, H = 1000, 1400
rotation = np.array([[0, -1, H], [1, 0, 0], [0, 0, 1]], dtype=float)
corners = np.array([
    [700, 1140, 1], [910, 1140, 1],
    [910, 1180, 1], [700, 1180, 1],
], dtype=float).T
rotated = rotation @ corners
rotated_box = (
    rotated[0].min(), rotated[1].min(),
    rotated[0].max(), rotated[1].max(),
)
assert rotated_box == (220, 700, 260, 910)
assert np.allclose(np.linalg.inv(rotation) @ rotated, corners)

scale_crop = np.array([[0.5, 0, -480], [0, 0.5, -800], [0, 0, 1]])
original = np.array([1200, 1720, 1])
assert np.allclose(scale_crop @ original, [120, 60, 1])
assert np.allclose(np.linalg.inv(scale_crop) @ [120, 60, 1], original)
~~~

PDF и растр тоже могут иметь разные начала координат. Если в выбранной системе PDF начало снизу слева, а у растра сверху слева, прямого умножения на DPI недостаточно. Для неповёрнутой страницы без смещения crop box, высотой 700 points при масштабе 2 pixels/point, точка PDF $(100,100)$ перейдёт в пиксельную точку $(200,1200)$. Параметры страницы, crop box и поворот берут у rasterizer, а не восстанавливают по внешнему виду.

## 8. Метрики на конкретных примерах

### CER и WER

Расстояние Левенштейна — минимальное число вставок, удалений и замен, превращающих одну последовательность в другую. Для CER единицами являются символы, для WER — слова. Обе метрики делят число операций на длину эталона, но в соответствующих единицах:

$$
\begin{aligned}
\mathrm{CER}&=\frac{S+D+I}{N_{\mathrm{chars}}},\\
\mathrm{WER}&=\frac{S+D+I}{N_{\mathrm{words}}}.
\end{aligned}
$$

В эталоне `итого 12480` и результате `итого 1248О` отличается один символ: цифра `0` заменена кириллической буквой `О`. Если пробелы включены, длина эталона равна 11 и CER составляет $1/11\approx9.09\%$. Если удалить пробелы перед оцениванием, длина будет 10 и CER — 10%. На уровне двух слов ошибочно второе слово, поэтому WER равен 50%. Политика нормализации является частью определения эксперимента.

~~~python
from math import isclose

def edit_distance(a, b):
    previous = list(range(len(b) + 1))
    for i, left in enumerate(a, 1):
        current = [i]
        for j, right in enumerate(b, 1):
            current.append(min(
                previous[j] + 1, current[j - 1] + 1,
                previous[j - 1] + (left != right),
            ))
        previous = current
    return previous[-1]

reference, prediction = "итого 12480", "итого 1248О"
cer_spaces = edit_distance(reference, prediction) / len(reference)
cer_no_spaces = (
    edit_distance(reference.replace(" ", ""), prediction.replace(" ", ""))
    / len(reference.replace(" ", ""))
)
wer = edit_distance(reference.split(), prediction.split()) / len(reference.split())
assert isclose(cer_spaces, 1 / 11)
assert isclose(cer_no_spaces, 0.1) and isclose(wer, 0.5)
assert edit_distance("12", "12345") / len("12") == 1.5
~~~

Последний пример показывает, что CER может превышать 100% из-за вставок. Эта метрика не является вероятностью ошибки и не ограничена единицей. Exact match проверяет полное совпадение поля и для неверной последней цифры даёт ноль.

### ANLS для текстового ответа

[DocVQA 2020](https://www.docvqa.org/challenges/2020) использует Average Normalized Levenshtein Similarity. [Biten et al., ST-VQA, §3.4](https://openaccess.thecvf.com/content_ICCV_2019/papers/Biten_Scene_Text_Visual_Question_Answering_ICCV_2019_paper.pdf) задают нормированное расстояние как расстояние редактирования, делённое на большую длину двух строк. Если оно меньше порога 0.5, оценка равна единице минус расстояние; иначе — нулю. При нескольких допустимых эталонах выбирается наибольшая оценка, затем результаты усредняются по вопросам.

Для `12480` и `1248О` расстояние равно $1/5=0.2$, оценка — 0.8. Для банковской суммы ответ всё ещё ошибочен. ANLS допускает частичный балл за близкую строку, но не определяет пригодность поля для автоматического использования.

~~~python
from math import isclose

def levenshtein(a, b):
    row = list(range(len(b) + 1))
    for i, x in enumerate(a, 1):
        new = [i]
        for j, y in enumerate(b, 1):
            new.append(min(row[j] + 1, new[j - 1] + 1, row[j - 1] + (x != y)))
        row = new
    return row[-1]

def anls_one(reference, prediction):
    # Регистр игнорируется; пробелы сохраняются, как в DocVQA 2020.
    a, b = reference.lower(), prediction.lower()
    length = max(len(a), len(b))
    distance = levenshtein(a, b) / length if length else 0.0
    return 1 - distance if distance < 0.5 else 0.0

assert isclose(anls_one("12480", "1248О"), 0.8)
assert anls_one("ab", "ac") == 0.0  # Ровно 0.5: порог не пройден.
assert anls_one("RUB", "rub") == 1.0
assert max(anls_one(a, "12480") for a in ["12 480", "12480"]) == 1.0
~~~

Эта реализация показывает формулу и явно выбранную нормализацию. Для воспроизведения конкретной таблицы результатов используется её официальный evaluator: правила обработки нескольких ответов, пустых строк и пробелов могут отличаться между версиями задач.

### Локализация и извлечение полей

Для рамок $A$ и $B$ пересечение над объединением равно

$$
\mathrm{IoU}(A,B)=\frac{|A\cap B|}{|A|+|B|-|A\cap B|}.
$$

Если эталонная рамка $[0,0,10,10]$, а предсказанная $[2,0,14,10]$, их площади равны 100 и 120, пересечение — 80. IoU равен $80/140\approx0.571$. Учебный порог 0.5 засчитает локализацию. Однако правая часть предсказанной рамки может захватить число из соседнего столбца. Для документа проверяется и содержимое выделенного фрагмента.

~~~python
from math import isclose

def box_iou(a, b):
    intersection = (
        max(0, min(a[2], b[2]) - max(a[0], b[0]))
        * max(0, min(a[3], b[3]) - max(a[1], b[1]))
    )
    area_a = (a[2] - a[0]) * (a[3] - a[1])
    area_b = (b[2] - b[0]) * (b[3] - b[1])
    union = area_a + area_b - intersection
    return intersection / union if union else 0.0

assert isclose(box_iou((0, 0, 10, 10), (2, 0, 14, 10)), 4 / 7)
assert box_iou((0, 0, 10, 10), (20, 0, 30, 10)) == 0.0
assert box_iou((0, 0, 10, 10), (0, 0, 10, 10)) == 1.0
~~~

Для полей задают единицу сравнения, например пару «название поля, точное значение», а для локализованного извлечения добавляют страницу и условие на рамку. Неверная сумма не становится правильным извлечением из-за похожего написания.

Пусть в эталоне пять полей. Система вернула четыре, из которых три совпали. Получаются precision $3/4=0.75$, recall $3/5=0.6$, F1 $2\cdot3/(4+5)=2/3$. Сравнение только имён полей дало бы другую метрику и не обнаружило бы неверных значений.

Для таблиц отдельно оценивают текст ячеек и структуру, включая объединения и соответствие заголовкам. Для многостраничного QA проверяют выбранную страницу, текст ответа и его локализацию. Результаты разбивают по языку, размеру текста, числу колонок, повороту, качеству скана и наличию рукописных фрагментов: среднее по крупным печатным полям может скрыть провал на мелких реквизитах.

## 9. Диагностические вмешательства

Для исходного счёта сохраняются вопрос, версия модели, параметры декодирования и процедура подготовки изображения; меняется только заранее выбранный фрагмент. Каждый тест должен сохранять читаемость и иметь проверенный ожидаемый результат.

| Изменение | Что проверяет тест | Ожидаемое поведение |
|---|---|---|
| Закрыть сумму вместе с её текстовым слоем | Извлечение без видимого поля | Учесть отсутствие поля; сумма может остаться вычислимой |
| Заменить итог и согласованно изменить слагаемые | Зависимость от нового содержимого | Прочитать новое значение |
| Переставить строки вместе с заголовками | Устойчивость к расположению | Значение следует заголовку, а не прежней координате |
| Поменять только значения у двух заголовков | Связь поля и значения | Прочитать новое поле; можно отметить противоречие арифметики |
| Удалить фрагмент с итогом из переданного набора | Учёт неполного входа | Не приписывать точную рамку недоступной области |

Маскирование только напечатанного итога не всегда должно приводить к отказу. Если все слагаемые видны, система может вычислить ответ; тогда она указывает использованные области и называет сумму вычисленной. У теста заранее определяют, проверяется извлечение готового поля или арифметическое восстановление.

Перестановка строк вместе с заголовками тоже не обязана менять ответ. Она меняет расположение, но сохраняет связь «Итого — 12 480». Требование обязательно изменить ответ в этом случае проверяло бы неверное поведение.

Тесты повторяют на наборе документов. Отдельно от обычного качества оценивают долю ожидаемых изменений, устойчивость к несущественным изменениям и случаи ложной уверенности. Один удачный изменённый счёт показывает поведение на этом счёте, а не общую надёжность модели.

## 10. Контракт документной системы

Ответ различает прочитанное значение, нормализованное представление и вычисление. Строка `12 480 ₽` может нормализоваться в десятичное значение `12480.00` с валютой RUB. Нормализация сохраняет смысл исходной записи и её происхождение; она не должна незаметно заменять букву «О» на ноль в спорном поле.

Для нашего примера ответ может содержать:

~~~json
{
  "field": "total",
  "status": "extracted",
  "raw_text": "12 480",
  "value": "12480.00",
  "currency": "RUB",
  "evidence": {
    "page": 1,
    "coordinate_space": "page_pixels",
    "page_size": [1000, 1400],
    "box_xyxy": [700, 1140, 910, 1180],
    "region_id": "v_total"
  },
  "checks": {
    "arithmetic": "passed",
    "requires_review": false
  }
}
~~~

Номер страницы здесь начинается с 1; порядок рамки — `x1,y1,x2,y2`. Это заданный интерфейс учебного примера, а не универсальный формат Qwen или Donut. Для воспроизведения сохраняются также идентификатор исходного файла, версия rasterizer, размеры и преобразования страницы, OCR-результат, версия модели и запрос. При показе подсветки интерфейс использует тот же масштаб и поворот, что учтены в метаданных.

Произвольное число `confidence: 0.95`, сгенерированное в JSON, не является проверенной вероятностью правильности суммы. Вероятность последовательности токенов тоже не равна вероятности правильного извлечения поля. Если confidence используется для автоматического принятия решения, его проверяют на отдельной размеченной выборке: как часто верны ответы с таким диапазоном оценки, сколько документов система принимает и какова ошибка среди принятых.

При четырёх ответах с оценками 0.99, 0.95, 0.80 и 0.60 первые два могут оказаться соответственно верным и неверным. Порог 0.90 примет два из четырёх ответов, но ошибка среди принятых составит 50%. Высокое число не заменяет проверку калибровки.

~~~python
from math import isclose

scores = [0.99, 0.95, 0.80, 0.60]
correct = [True, False, True, False]
accepted = [ok for score, ok in zip(scores, correct) if score >= 0.90]
coverage = len(accepted) / len(scores)
risk = sum(not ok for ok in accepted) / len(accepted)
assert isclose(coverage, 0.5) and isclose(risk, 0.5)

tp, predicted, expected = 3, 4, 5
assert isclose(tp / predicted, 0.75)
assert isclose(tp / expected, 0.6)
assert isclose(2 * tp / (predicted + expected), 2 / 3)
~~~

При расхождении распознавателей, отсутствии нужной страницы или неоднозначном заголовке система возвращает причину неполного ответа и доступные области для проверки. Для спорной цифры пользователю нужен исходный фрагмент достаточного разрешения; повторение уверенной фразы модели не добавляет сведений о документе.
