# 69. Coding, web и computer-use agents

Написать фрагмент кода, назвать кнопку на скриншоте и исправить ошибку в
репозитории — три разные задачи. Первая может завершиться одним ответом модели.
Во второй нужно связать пиксели с допустимым действием. В третьей приходится
несколько раз читать файлы, строить гипотезу, изменять программу, запускать
тесты и учитывать их результат. Поэтому качество computer-use agent нельзя
вывести только из качества базовой модели: его определяют также интерфейс
действий, представление наблюдений, управление состоянием среды, стратегия
поиска и способ проверки результата.

В этой главе мы проследим одну общую конструкцию в трёх средах: репозитории,
web-приложении и полноценной виртуальной машине. Базовая граница между моделью
и исполнителем разобрана в [[02 Areas/ML & DL/00 Учебник/17 Tools и Agents/65 Tool use — от вызова функции к действию|главе о tool use]], устройство контекста — в [[02 Areas/ML & DL/00 Учебник/17 Tools и Agents/66 Agent harness и context engineering|главе о harness]]. Здесь нас интересует следующий уровень: как из этих частей собрать систему, способную пройти длинную, проверяемую траекторию в изменяемой среде.

## Агент как многошаговая программа с инструментами

<!-- source_unit_id: meeting-05-slides-coding-agent-orientation -->

Полезное рабочее определение агента намеренно невелико: это программа, которая
несколько раз вызывает модель и между вызовами исполняет выбранные ею действия.
Планирование, скрытое рассуждение или несколько взаимодействующих моделей могут
улучшать такую программу, но не являются обязательными признаками. Существенен
замкнутый цикл:

$$
o_t = O(s_t), \qquad
a_t \sim \pi_\theta(a\mid g,o_{\le t},a_{<t}), \qquad
s_{t+1}=T(s_t,a_t),
$$

где $g$ — задача, $s_t$ — фактическое состояние среды, $o_t$ — доступное модели
наблюдение, $a_t$ — действие, а $T$ — переход, который выполняет не модель, а
исполнитель. История
$\tau_t=(o_0,a_0,o_1,\ldots,a_{t-1},o_t)$ хранит только наблюдаемую часть
процесса; среда почти всегда содержит больше состояния, чем помещается в
контекст.

Это различие особенно хорошо видно на исправлении программы. Модель может
предположить, что ошибка находится в парсере, но только чтение конкретной версии
файла превращает предположение в проверяемую гипотезу. Она может сгенерировать
патч, но лишь применение патча и запуск тестов изменяют состояние репозитория и
дают обратную связь. Успешный ответ агента поэтому состоит не только из текста,
а из конечного состояния и доказательства того, что оно удовлетворяет задаче.

## SWE-agent: модель управляет циклом через ACI

<!-- source_unit_id: meeting-05-slides-swe-agent-loop -->

[SWE-agent](https://arxiv.org/abs/2405.15793) оставляет модели выбор следующего
шага, но не отдаёт ей необработанный компьютер. Между LLM и репозиторием
находится **agent-computer interface (ACI)** — небольшой набор команд,
спроектированных именно для модели. Он позволяет искать и просматривать код,
редактировать ограниченные диапазоны строк и запускать программы, а результат
каждой команды возвращает в кратком, предсказуемом формате.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/coding-web-computer-use/m05-p17-react-aci.png]]

*ACI SWE-agent дополняет стандартные Linux Bash-команды специальными средствами
просмотра, поиска и редактирования — это явно указано в
[Table 4 оригинальной статьи](https://arxiv.org/html/2405.15793v2#A1).
Удобный интерфейс уменьшает сложность выбора действий, но сам по себе не
служит границей полномочий: ограничения задают sandbox и права исполнителя. Источник слайда:
[Berkeley Advanced LLM Agents, Meeting 5](https://rdi.berkeley.edu/adv-llm-agents/sp25), физическая стр. 17; первичные работы — [ReAct](https://arxiv.org/abs/2210.03629) и [SWE-agent](https://arxiv.org/abs/2405.15793). Полный слайд воспроизведён без обрезки.*

Хороший ACI меняет не косметику, а геометрию поиска. Если действие `open_file`
по умолчанию выдаёт весь файл, один неудачный выбор способен вытеснить из
контекста условие задачи и историю тестов. Если `edit` принимает произвольный
shell-скрипт, модель должна одновременно решить задачу и безошибочно управлять
редактором. Специализированная команда может принимать путь и диапазон строк,
проверять, что ожидаемый старый текст действительно найден, и возвращать только
изменённый фрагмент. Тогда одна модельная ошибка реже превращается в повреждение
состояния.

Цикл SWE-agent удобно читать как систему управления:

1. harness собирает условие, текущую часть траектории и описание доступных
   команд;
2. модель выбирает информационное или изменяющее действие;
3. ACI валидирует аргументы и исполняет действие в sandbox;
4. наблюдение сообщает не только вывод, но и новый статус среды;
5. модель либо уточняет гипотезу, либо завершает работу;
6. независимый grader проверяет конечный репозиторий.

Последний пункт не следует заменять самоотчётом модели. Фраза «tests pass» в
ответе ничего не доказывает, если harness не сохранил команду, exit code, stdout,
stderr и снимок рабочего дерева.

<span id="свободный-loop-aci-и-процедурный-workflow"></span>
## Где находится управление: свободный цикл, ACI и процедурный workflow

<!-- source_unit_id: meeting-05-slides-coding-agent-design-comparisons -->

Главный архитектурный выбор — **где находится control flow**. В динамической
системе модель сама решает, искать ли ещё один символ, перечитать ли тест или
вернуться к прежней гипотезе. В процедурной системе порядок этапов задаёт код, а
модель вызывается внутри каждого этапа. Между этими полюсами лежит множество
гибридов.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/coding-web-computer-use/m05-p22-agentless-control-flow.png]]

*В Agentless последовательность `localize → repair → validate` задаёт обычная
программа: модель участвует во всех трёх стадиях, но не выбирает следующую.
Источник: Berkeley Advanced LLM Agents, Meeting 5, физическая стр. 22;
[Agentless](https://arxiv.org/abs/2407.01489). Полный слайд без обрезки.*

**SWE-agent** расположен ближе к динамическому краю: одна продолжающаяся
траектория выбирает команды по мере появления новых наблюдений. **Agentless**
фиксирует три стадии — локализацию, генерацию исправления и проверку патча.
**AutoCodeRover** занимает промежуточную позицию: поиск контекста и генерация
патча допускают собственные итерации, но остаются двумя отдельными траекториями
с разными инструкциями. **Passerine** снова использует динамический ReAct-loop,
однако действует через реальные внутренние инструменты Google — поиск кода,
Bazel, чтение и редактирование файлов — без прямого доступа к командной строке.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/coding-web-computer-use/m05-p28-autocoderover-two-trajectories.png]]

*AutoCodeRover разделяет поиск места ошибки и построение патча на две траектории
с отдельными контекстами: у фаз могут различаться system instructions и критерии
завершения. Источник: Berkeley Advanced LLM
Agents, Meeting 5, физическая стр. 28; [AutoCodeRover](https://arxiv.org/abs/2404.05427). Полный слайд без обрезки.*

У этих вариантов нет постоянного победителя. Динамический loop полезен, когда
новое наблюдение меняет сам способ решения: неожиданная ошибка компилятора может
потребовать нового поиска. Процедурный workflow предпочтительнее, когда этапы
известны заранее: он не тратит токены на повторное открытие процесса и не даёт
ранней ошибке бесконтрольно разрастись. С ростом возможностей модели лучший
design point может смещаться, но это эмпирический вопрос. Его проверяют на одной
модели, одном бюджете и одинаковом grader, а не по названиям архитектур.

Практический способ выбрать control flow — выписать решения, которые действительно
зависят от наблюдений. Всё, что не зависит, стоит оставить детерминированному
коду: подготовку окружения, лимиты, формат артефактов, обязательный запуск тестов
и восстановление состояния. Модели передают только те развилки, где полезна её
семантическая оценка.

## Почему бенчмарки программирующих агентов быстро устаревают

Coding benchmark — не вечная шкала «интеллекта». Репозитории меняются, тесты
могут быть неполными, часть задач попадает в обучающие данные, а новый harness
меняет доступную агенту информацию. Даже `resolved` обычно означает только, что
патч применился и прошёл набор тестов в зафиксированном контейнере. Он не
гарантирует эквивалентность эталонному исправлению и отсутствие регрессий вне
тестового набора.

При нескольких сэмплах нельзя сравнивать `pass@1` одной системы с `pass@20`
другой. Следует сохранять число попыток, температуру, максимальное число шагов,
цену, версию model endpoint, конкретный commit benchmark и образ среды. Почему
простая доля успехов и оценка `pass@k` отвечают на разные вопросы, подробно
разобрано в [[02 Areas/ML & DL/00 Учебник/17 Tools и Agents/68 Оценивание агентных систем#6. Срок жизни benchmark и несмещённый pass@k|главе об оценивании агентов]].

## CTF: состояние, специализированные инструменты и обратная связь

<!-- source_unit_id: meeting-05-slides-ctf-agents -->
<!-- source_unit_id: meeting-05-reading-01-catalogue-record -->

Capture-the-Flag задачи делают скрытое состояние инструмента особенно заметным.
Отладчик должен помнить запущенный процесс, breakpoints и текущий frame;
соединение — сокет и протокол; decompiler — выбранный бинарный объект. Поэтому
превратить GDB в stateless функцию `run(command)` недостаточно. Следующее
действие зависит от состояния, созданного предыдущим, и это состояние нужно
явно привязать к эпизоду.

[EnIGMA](https://arxiv.org/abs/2409.16165) дополняет общие файловые и shell-команды
интерактивными средствами для debugger и network connection. Длинный вывод
предварительно суммируется отдельным модельным шагом, а подсказки из неудачных
траекторий возвращаются в prompt. Такой дизайн показывает два общих принципа.
Во-первых, специализированный инструмент позволяет сохранить важное состояние,
не заставляя модель каждый раз восстанавливать его из текста. Во-вторых,
суммаризация является частью интерфейса и должна проверяться: пропущенный адрес,
exception или exit status способен сделать всю последующую траекторию
правдоподобной, но бесполезной.

CTF остаётся изолированной учебной средой. Эти методы нельзя переносить на
чужую инфраструктуру без разрешения. Для воспроизводимого учебного эпизода
нужны sandbox без внешней сети, зафиксированный образ, лимит ресурсов и журнал
каждой команды.

<span id="почему-генерация-патча-и-поиск-уязвимости-разные-задачи"></span>
## Почему генерация патча и поиск уязвимости — разные задачи

<!-- source_unit_id: meeting-05-slides-vulnerability-discovery-problem -->

В исправлении известной ошибки issue обычно сообщает симптом, затронутый
компонент или ожидаемое поведение. При поиске неизвестной уязвимости такого
локатора нет. Агенту приходится сначала выбрать поверхность атаки, восстановить
поток данных между функциями, сформулировать условие нарушения и лишь затем
искать вход, который его проявит. Локальный фрагмент часто недостаточен:
проверка границы могла произойти в вызывающей функции или быть гарантирована
типом, который не виден в текущем файле.

Отсюда другой критерий успеха. Красивое словесное объяснение не подтверждает
уязвимость, а sanitizer crash ещё требуется сделать воспроизводимым и отделить
от ошибок самого harness. Полезный evidence bundle включает точный commit,
сборочные флаги, минимальный вход, stderr sanitizer, exit code и повторный запуск
в чистой среде.

<span id="big-sleep-гипотеза-исполнение-sanitizer-воспроизводимый-crash"></span>
## Big Sleep: от гипотезы к воспроизводимому crash через исполнение

<!-- source_unit_id: meeting-05-slides-charles-sutton-vulnerability-discovery-loop -->
<!-- source_unit_id: meeting-05-reading-02-catalogue-record -->

В описанном Google Project Zero цикле [Big Sleep](https://projectzero.google/2024/10/from-naptime-to-big-sleep.html)
модель не просто классифицирует код. Она переходит по definitions и
cross-references, выдвигает гипотезу о достижимом ошибочном состоянии, создаёт
кандидатный вход и запускает программу под динамической проверкой. Debugger и
sanitizer превращают часть рассуждения во внешний эксперимент.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/coding-web-computer-use/m05-p48-big-sleep-design.png]]

*Схема задаёт проверяемый ритм Big Sleep: навигация по коду формирует гипотезу,
интерпретатор строит вход, debugger и sanitizer проверяют последствие. Источник:
Berkeley Advanced LLM Agents, Meeting 5, физическая стр. 48; первичный источник
— [Google Project Zero](https://projectzero.google/2024/10/from-naptime-to-big-sleep.html).
Полный слайд без обрезки.*

Здесь внешний сигнал сильнее самооценки модели, но его границы остаются узкими.
Отсутствие crash не доказывает безопасность: вход мог не достичь нужной ветви,
сборка могла отключить проверку, а ограниченный бюджет — преждевременно завершить
поиск. И наоборот, crash ещё не устанавливает эксплуатируемость. Правильная
формулировка результата: «этот вход воспроизводимо приводит данную сборку к
такому sanitizer report», после чего начинается независимый security review.

## Как выбирать степень свободы агента

<!-- source_unit_id: meeting-05-slides-coding-agent-conclusions -->

Степень свободы следует выбирать по цене ошибки и качеству обратной связи.
Разрешить модели самостоятельно продолжать траекторию разумно, когда действия
обратимы, состояние можно сохранить, а ошибку быстро обнаруживает компилятор,
тест или verifier. Чем необратимее действие и слабее grader, тем больше control
flow должно оставаться в обычном коде и тем чаще требуется одобрение человека.

Для coding agent это приводит к простой лестнице:

| Режим | Что выбирает модель | Что фиксирует программа | Когда уместен |
|---|---|---|---|
| один вызов | текст патча | применение и тесты | маленький известный контекст |
| процедурный workflow | ответ внутри заданной фазы | порядок `localize → repair → validate` | типовая починка |
| ACI-loop | следующий специализированный tool call | права, формат, лимиты, grader | исследование репозитория |
| shell/IDE loop | почти любое локальное действие | главным образом sandbox и бюджет | доверенная одноразовая среда |

Эта таблица описывает не уровни «умности», а распределение ответственности.

## VisualWebArena: страница как частично наблюдаемая среда

<!-- source_unit_id: meeting-06-slides-visualwebarena -->
<!-- source_unit_id: meeting-06-reading-02-catalogue-record -->
<!-- source_unit_id: meeting-06-reading-03-catalogue-record -->

Web agent получает не абстрактный список кнопок, а состояние приложения,
разнесённое между DOM, визуальным layout, cookies, history, server-side данными и
несколькими вкладками. Наблюдение неизбежно частично: screenshot не показывает
элементы ниже fold, accessibility tree может пропустить canvas, а HTML содержит
невидимые узлы и служебный текст. Удобно рассматривать задачу как POMDP, где
агент действует по истории наблюдений, а не по полному состоянию сайта.

[WebArena](https://arxiv.org/abs/2307.13854) создаёт самодостаточные сайты и
проверяемые задачи; [VisualWebArena](https://jykoh.com/vwa) добавляет задания,
для которых визуальная информация действительно необходима. Например,
инструкция может ссылаться на товар, показанный изображением, а нужный вариант
определяется одновременно ценой, типом и адресом доставки.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/coding-web-computer-use/m06-p18-visualwebarena-shopping.png]]

*В этой задаче VisualWebArena изображение задаёт требуемый тип товара, а страница
магазина сообщает варианты, цены и состояние корзины. Агенту нужно совместить
обе части наблюдения, после чего grader проверяет не описание действий, а
изменившуюся корзину. Источник: Berkeley Advanced LLM Agents, Meeting 6, физическая
стр. 18; [VisualWebArena](https://jykoh.com/vwa). Полный слайд без обрезки.*

Формулировка задачи — только начало контракта. Для воспроизводимости нужно
сохранить исходный snapshot сайтов, пользовательские данные, authentication
state, допустимый action space, максимальную длину эпизода и grader конечного
состояния. Если один запуск оставил товар в корзине, следующий уже решает другую
задачу. Поэтому reset — часть benchmark, а не техническая деталь.

## Как представить страницу: HTML, accessibility tree, screenshot и Set-of-Marks

<!-- source_unit_id: meeting-06-slides-vision-language-web-agents -->
<!-- source_unit_id: meeting-06-reading-01-catalogue-record -->

Представление страницы определяет, какую задачу фактически решает модель.
Сырой HTML точен, но велик и засорён скриптами, стилями и невидимыми узлами.
Accessibility tree короче и сохраняет семантические роли, но зависит от качества
разметки. Screenshot передаёт layout, изображения и визуальное состояние, зато
не даёт стабильных символьных идентификаторов. Set-of-Marks (SoM) наносит метки
на интерактивные элементы и связывает visual grounding с дискретным действием
вида `click(mark=17)`.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/coding-web-computer-use/m06-p29-html-vs-som.png]]

*Слева — длинное текстовое представление страницы, справа — screenshot с
пронумерованными интерактивными областями. Рисунок позволяет сравнить две цены:
контекстный шум у HTML/a11y и ошибку visual grounding у SoM. Источник: Berkeley
Advanced LLM Agents, Meeting 6, физическая стр. 29. Полный слайд без обрезки.*

SoM не устраняет проблему восприятия. Метка может закрыть текст, два элемента —
перекрыться, а responsive layout — измениться между наблюдением и кликом. HTML
также не является «истиной»: идентификатор может быть динамическим, а action по
нему — выбрать невидимый или disabled element. Поэтому сильный interface часто
объединяет screenshot, компактное дерево доступности и согласованные IDs.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/coding-web-computer-use/m06-p35-som-trajectory.png]]

*Успешная траектория блокировки пользователя показывает, что grounding нужно
сохранять на каждом шаге: нужный объект сначала находят по изображению, затем
переходят в профиль и только после этого выполняют изменение состояния.
Источник: Berkeley Advanced LLM Agents, Meeting 6, физическая стр. 35;
VisualWebArena. Полный слайд без обрезки.*

При выборе observation format полезно провести ablation: одна и та же policy и
одни и те же задачи получают только a11y, только screenshot+SoM или обе
модальности. Измеряют не только итоговый success, но и grounding error,
invalid-action rate, длину траектории и размер контекста.

## Почему реактивный следующий клик ломается на длинном горизонте

<!-- source_unit_id: meeting-06-slides-search-agent-motivation -->

Локально правдоподобный клик может иметь глобально плохие последствия. Агент
добавляет не тот вариант товара, переходит на страницу без обратимой навигации
или изменяет фильтр так, что нужный объект исчезает. Даже при условной
вероятности правильного шага $p$ вероятность безошибочной траектории длины $H$
в грубом независимом приближении равна $p^H$. При $p=0.9$ десять шагов дают лишь
$0.9^{10}\approx0.35$.

Это не точная модель реального агента: ошибки зависимы, некоторые исправимы, а
некоторые действия несущественны. Но она объясняет, почему рост single-step
accuracy не гарантирует надёжности длинного workflow. Нужен механизм, который
сравнивает промежуточные состояния и умеет отказаться от уже начатой ветви.

## Best-first search в реальной web-среде

<!-- source_unit_id: meeting-06-slides-web-agent-tree-search -->
<!-- source_unit_id: meeting-06-reading-04-catalogue-record -->

[Tree Search for Language Model Agents](https://arxiv.org/abs/2407.01476)
переносит best-first search из текстового дерева в исполняемую web-среду. Для
этого нужны четыре компонента:

1. baseline policy предлагает несколько следующих действий;
2. среда исполняет каждое действие из соответствующего состояния;
3. value evaluator оценивает получившееся промежуточное состояние относительно
   цели;
4. search выбирает самый перспективный узел, а при необходимости возвращается к
   сохранённому состоянию другой ветви.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/coding-web-computer-use/m06-p50-best-first-search.png]]

*Best-first search требует не только proposal policy и value function, но и
реального способа восстановить состояние браузера. Источник: Berkeley Advanced
LLM Agents, Meeting 6, физическая стр. 50; [Koh et al.](https://arxiv.org/abs/2407.01476).
Полный слайд без обрезки.*

Пусть узел $n$ хранит snapshot среды $s(n)$, историю $\tau(n)$ и оценку
$V(n)$. Упрощённый алгоритм имеет вид:

```text
frontier = {root snapshot}
while budget remains:
    n = pop_highest_value(frontier)
    for action in propose_actions(task, τ(n)):
        restore(s(n))
        child_state, observation = execute(action)
        child = Node(parent=n, action=action, observation=observation,
                     snapshot=child_state,
                     history=τ(n) + [(action, observation)])
        if terminal_success(child_state): return trajectory(child)
        frontier.add(child, value(task, trajectory(child), child_state))
```

Каждая альтернатива должна начинаться с одного и того же родительского
состояния. Если в корзине нет товаров, ветви «добавить книгу» и «добавить
тетрадь» должны дать две отдельные корзины, а не корзину с обоими товарами.
Поэтому `restore` находится внутри цикла по действиям.

Проверим это на числовой среде: состояние равно 10, альтернативы — прибавить 1 и умножить на 2. Независимые дети должны хранить 11 и 20; ошибочная последовательная реализация даст 11 и 22.

```python
from copy import deepcopy

root = {"id": "root", "snapshot": {"x": 10}}
actions = [("add_one", lambda x: x + 1), ("double", lambda x: 2 * x)]
children = []
for name, transition in actions:
    env = deepcopy(root["snapshot"])  # restore перед каждой альтернативой
    env["x"] = transition(env["x"])
    children.append({
        "parent": root["id"], "action": name,
        "observation": {"x": env["x"]}, "snapshot": deepcopy(env)
    })
assert [c["snapshot"]["x"] for c in children] == [11, 20]
assert all(c["parent"] == "root" for c in children)
assert root["snapshot"]["x"] == 10
print("branch isolation: PASS (11, 20)")
```

Это тест инварианта алгоритма, не доказательство полноценного snapshot браузера: cookies, server-side записи и внешние эффекты требуют отдельного reset contract.

Вернуть текстовую историю недостаточно: корзина,
авторизация, серверные записи и вкладки уже могли измениться. В локальном
benchmark можно клонировать VM или перезапускать детерминированный сайт. В живом
интернете точного simulator часто нет; тогда часть ветвей становится
необратимой, а поиск необходимо ограничивать read-only действиями или
компенсирующими транзакциями.

Value model тоже не является oracle. В работе evaluator реализован prompting-ом
мультимодальной модели. Он может предпочесть визуально похожее состояние,
пропустить скрытый побочный эффект или быть плохо откалиброванным. Поэтому
следует хранить его оценки, проверять calibration и сравнивать поиск не только с
одной greedy-траекторией, но и с repeated sampling при равном compute budget.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/coding-web-computer-use/m06-p60-search-backtracking.png]]

*Верхняя траектория продолжает раннюю ошибку до failure. Нижняя сохраняет
альтернативные состояния, возвращается после низкой оценки ветви и продолжает
по более перспективному пути. Источник: Berkeley Advanced LLM Agents, Meeting
6, физическая стр. 60. Это один полный кадр последовательности, без монтажа и
обрезки.*

## Когда дополнительный поиск окупается

<!-- source_unit_id: meeting-06-slides-web-agent-tree-search-results -->

В зафиксированной авторами конфигурации поиск повысил success rate GPT-4o на
VisualWebArena до **26.4%**; это **39.7% относительного улучшения** относительно
соответствующего baseline. Эти числа нельзя соединять в одно «+39.7 процентных
пункта»: первая величина абсолютная, вторая вычисляется относительно исходного
уровня. Слайд курса округляет сравнение до 19% и 26%.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/coding-web-computer-use/m06-p70-search-results.png]]

*Округлённые результаты на WebArena и VisualWebArena показывают, что поиск
помогает обеим базовым моделям в данном эксперименте. Для цитирования точного
результата нужно пользоваться [статьёй](https://arxiv.org/abs/2407.01476), а не
считывать столбцы со слайда. Источник изображения: Berkeley Advanced LLM Agents,
Meeting 6, физическая стр. 70. Полный слайд без обрезки.*

Дополнительный поиск оправдан, если прирост успеха превышает цену ветвления,
restore и evaluator calls. Поэтому отчёт должен показывать success как функцию
числа model calls или стоимости, а не только максимальную точку. В среде с
дорогими либо необратимыми действиями лучше тратить compute на внутреннее
моделирование до действия; в дешёвой resettable среде можно исполнять ветви.

## InSTA: синтетические задачи из работающего web

<!-- source_unit_id: meeting-06-slides-insta-setup -->

Ручные демонстрации плохо покрывают длинный хвост сайтов. [InSTA](https://arxiv.org/abs/2502.06776)
строит данные непосредственно из работающего web: LLM получает домен,
предлагает реалистичную задачу, агент пытается её выполнить, затем отдельная
модель проверяет траекторию. Процесс применён к 150 тысячам сайтов, выбранным с
помощью Common Crawl PageRank.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/coding-web-computer-use/m06-p80-insta-pipeline.png]]

*InSTA разделяет generation, evaluation и data collection. Рисунок следует
читать слева направо и на каждом переходе спрашивать, какой фильтр не позволяет
ошибке предыдущей стадии стать «размеченным успехом». Источник: Berkeley
Advanced LLM Agents, Meeting 6, физическая стр. 80; [Trabucco et al.](https://arxiv.org/abs/2502.06776).
Полный слайд без обрезки.*

Это не свободное автономное изменение интернета. В описанном сборе задания
формулируются так, чтобы не менять состояние внешних сайтов: преобладает поиск
информации. Такое ограничение одновременно снижает риск и упрощает повторное
исполнение. Оно также меняет распределение данных: по этим траекториям нельзя
судить, насколько хорошо агент совершает покупки, отправляет формы или управляет
аккаунтом.

Полезная схема data contract здесь содержит домен и timestamp, текст задачи,
observation/action schema, полный trace, версию policy, ответ verifier, его
confidence и причину отбраковки. Без этих полей невозможно отличить обучение на
новой стратегии от запоминания quirks конкретного сайта.

## Верификатор как фильтр синтетической траектории

<!-- source_unit_id: meeting-06-slides-insta-verification-scaling -->

Verifier InSTA видит последовательность действий и последнее наблюдение и
оценивает

$$
V_{\text{LLM}}(s_T,a_{1:T})
=P(\text{success}\mid s_T,a_{1:T}).
$$

На 150 тысячах предложенных задач только **14,6%** получили максимальную
уверенность verifier в успехе — около 22 тысяч траекторий. Это не accuracy
агента, а доля траекторий, прошедших весь конвейер отбора. Она одновременно
зависит от сложности сгенерированных задач, качества policy и строгости
оценщика.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/coding-web-computer-use/m06-p90-automatic-verifier.png]]

*Формула на слайде делает границу явной: verifier оценивает успех по trace и
финальному наблюдению, а не читает скрытое состояние сайта. Источник: Berkeley
Advanced LLM Agents, Meeting 6, физическая стр. 90; InSTA. Полный слайд без
обрезки.*

Авторы отдельно проверяют компоненты pipeline на человеческой разметке и
сообщают 97% accuracy фильтра harmful content, 89% rate feasible task generation
и 82.6% accuracy определения успешной траектории. Эти три числа относятся к
разным классификационным задачам; усреднять их в «качество данных» нельзя.
Даже высокая aggregate accuracy может скрывать опасный тип ошибки — принятие
неуспешной или вредной траектории. Поэтому production pipeline нуждается в
confusion matrix, выборочной ручной проверке наиболее уверенных примеров,
дедупликации и отдельном security filter.

<span id="osworld-resettable-vm-executable-action-and-final-state-grader"></span>
## OSWorld: восстанавливаемая VM, исполняемые действия и проверка результата

<!-- source_unit_id: meeting-07-slides-osworld -->
<!-- source_unit_id: meeting-07-reading-01-catalogue-record -->

[OSWorld](https://arxiv.org/abs/2404.07972) переносит оценивание с одного сайта
на полноценный компьютер: 369 задач охватывают приложения и взаимодействия
между ними. Контракт начинается с task-specific initial-state configuration,
который разворачивает виртуальную машину в известном состоянии. Agent получает
инструкцию и наблюдения — screenshot, accessibility tree, иногда terminal
output — и выдаёт mouse/keyboard либо программные действия. После остановки
execution-based evaluator читает реальное конечное состояние.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/coding-web-computer-use/m07-p11-osworld-contract.png]]

*Схема OSWorld связывает четыре вещи, которые нельзя подменять друг другом:
initial setup, наблюдение агента, исполняемое действие и final-state evaluation.
Источник: Berkeley Advanced LLM Agents, Meeting 7, физическая стр. 11;
[OSWorld](https://arxiv.org/abs/2404.07972). Полный слайд без обрезки.*

Final-state grader предпочтительнее сравнения траектории с одной эталонной
последовательностью. Пользовательскую цель «создать слайд и сохранить его под
таким именем» можно выполнить разными допустимыми путями. Grader должен
проверить файл, содержимое и расположение, а не требовать конкретных кликов.
Trajectory metrics всё же полезны для диагностики: invalid actions,
необязательные рискованные шаги, повторы и нарушения policy показывают, почему
две одинаково успешные попытки имеют разное качество.

Reset VM обязателен и для честного сравнения, и для безопасности. Он исключает
помощь от следов предыдущей попытки, ограничивает persistence и позволяет
повторить failure. Именно этот контракт воспроизводится в [[02 Areas/ML & DL/06 Практика/25 Воспроизводимо оценить и red-team компьютерного агента|практике 25]].

<span id="agenttrek-tutorials-guided-replay-trajectories"></span>
## AgentTrek: от руководств к траекториям через управляемое воспроизведение

<!-- source_unit_id: meeting-07-slides-agenttrek -->

[AgentTrek](https://arxiv.org/abs/2412.09605) использует web tutorials как
источник целей и промежуточного руководства. Pipeline находит tutorial-like
текст, превращает его в task goal и шаги, а затем VLM-agent воспроизводит эти
шаги в настоящем цифровом окружении. VLM-based evaluator фильтрует полученные
траектории.

Смысл guided replay не в буквальном копировании инструкции. Tutorial может быть
устаревшим, описывать другую версию интерфейса или пропускать очевидный для
человека шаг. Агент сопоставляет текстовое руководство с текущим наблюдением и
сохраняет исполненную последовательность действий. Поэтому запись должна
хранить и исходный tutorial, и итоговую trajectory, и вердикт evaluator: иначе
невозможно понять, что было перенесено из текста, а что восстановлено агентом.

Численные заявления о масштабе и качестве AgentTrek следует брать из первичной
публикации или её официального artifact, а не из пересказа слайда. Для учебника
важен механизм: внешний procedural prior уменьшает пространство поиска, но не
заменяет исполнение и проверку в актуальной среде.

<span id="taco-совместно-обучать-reasoning-и-action-tokens"></span>
## TACO: совместное обучение токенов рассуждения и действий

<!-- source_unit_id: meeting-07-slides-taco -->

[TACO](https://arxiv.org/abs/2412.05479v1) рассматривает мультимодальное решение как
чередование текста и исполняемых действий. В Chain-of-Thought-and-Action (CoTA)
модель может вызвать OCR, object localization, depth estimation, crop, search
или calculator, получить observation и продолжить решение. Так supervision
покрывает не только финальный ответ, но и место вызова инструмента, его аргументы
и использование результата.

Синтетический pipeline начинает более чем с миллиона сгенерированных traces и
после filtering/mixing оставляет 293 тысячи качественных CoTA examples. Один из
важных фильтров удаляет **action-useless** примеры: если действие не добавляет
информации и не влияет на ответ, оно учит модель декоративным tool calls. Ablation
в работе поддерживает принцип quality over quantity: меньшая очищенная смесь
может быть полезнее большего массива слабых траекторий.

CoTA не делает сгенерированное объяснение истинным. Исполняемые observations
можно проверить, но reasoning tokens остаются обучающим scaffold и могут
содержать post-hoc объяснение. Поэтому оценивание должно раздельно измерять
final answer, корректность выбора инструмента, валидность arguments, полезность
observation и устойчивость без рассуждений либо без действий.

<span id="aguvis-единое-визуальное-observationaction-space"></span>
## Aguvis: единое визуальное пространство наблюдений и действий

<!-- source_unit_id: meeting-07-slides-aguvis -->
<!-- source_unit_id: meeting-07-reading-02-catalogue-record -->

GUI datasets используют несовместимые текстовые схемы: DOM element IDs,
accessibility nodes, platform-specific widgets или координаты. [Aguvis](https://arxiv.org/abs/2412.04454)
выбирает единый pure-vision interface: модель наблюдает screenshot и выдаёт
визуально привязанное действие. Это позволяет одному action space работать с
web, desktop и mobile интерфейсами, в том числе там, где структурное дерево
недоступно.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/coding-web-computer-use/m07-p69-aguvis-design-goals.png]]

*Три design goals Aguvis: единое визуальное представление, обучение action
grounding и явная многошаговая reasoning trajectory. Источник: Berkeley Advanced
LLM Agents, Meeting 7, физическая стр. 69; [Aguvis](https://arxiv.org/abs/2412.04454).
Полный слайд без обрезки.*

Преимущество единого пространства одновременно создаёт главный риск. Координата
не несёт семантики элемента и чувствительна к масштабу, разрешению, прокрутке и
задержке между screenshot и click. Поэтому визуальный agent должен обучить две
связанные способности: понять высокоуровневую задачу и точно локализовать
низкоуровневое действие.

В Aguvis они разводятся по двум стадиям данных. Первая использует свыше миллиона
GUI-grounding examples; вторая — 35 тысяч многошаговых trajectories с явным
inner monologue. Такая последовательность сначала привязывает команды к
пикселям, затем учит связывать действия в решение.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/coding-web-computer-use/m07-p75-aguvis-data-stages.png]]

*Две стадии данных разделяют grounding и многошаговое управление. Таблицы на
слайде также показывают происхождение и платформу каждой части смеси — это
нужно сохранить при воспроизведении обучения. Источник: Berkeley Advanced LLM
Agents, Meeting 7, физическая стр. 75; Aguvis. Полный слайд без обрезки.*

Ablation позволяет проверить, выполняют ли стадии разные функции. Удаление
stage 1, stage 2 или обеих меняет результаты неодинаково на ScreenSpot,
Multimodal-Mind2Web и AndroidControl; удаление inner monologue отдельно ухудшает
часть показателей. Это свидетельство внутри конкретной модели и смеси, а не
универсальное доказательство, что скрытое рассуждение необходимо любому GUI
agent.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/coding-web-computer-use/m07-p80-aguvis-ablation.png]]

*Ablation нужно читать по строкам: поочерёдно убираются stage 2, stage 1, обе
стадии и inner monologue. Источник: Berkeley Advanced LLM Agents, Meeting 7,
физическая стр. 80; Aguvis. Полный слайд без обрезки.*

<span id="что-ограничивает-web-agents-perception-value-state-restoration-and-safety"></span>
## Семь ограничений web-агента: от восприятия до безопасности

<!-- source_unit_id: meeting-06-slides-web-agent-synthesis -->

Результат web или computer-use agent обычно ограничен не одним bottleneck, а
цепочкой:

1. **Perception:** нужный элемент не попал в observation или неверно
   локализован.
2. **Action grounding:** выбран правильный смысл, но неверный ID или координата.
3. **Planning:** локально допустимые действия не ведут к глобальной цели.
4. **Value estimation:** search предпочитает правдоподобное, но тупиковое
   состояние.
5. **State restoration:** backtracking возвращает текстовую историю, но не
   фактическое состояние приложения.
6. **Verification:** judge принимает красивое финальное сообщение вместо
   проверки результата.
7. **Safety:** инструкция внутри страницы получает влияние, которого у неё не
   должно быть, или инструмент обладает лишними правами.

Поэтому ablation должна выключать компоненты по одному: заменить screenshot на
a11y, убрать search, дать oracle state restoration, заменить LLM judge на
execution grader, ограничить права. Только тогда можно сказать, чему обязан
прирост. Суммарный success rate без failure taxonomy скрывает, нужно ли улучшать
модель, интерфейс или среду.

Security нельзя добавлять после достижения высокого success rate. Web content
является недоверенными данными, а не системной инструкцией; изменения аккаунта,
платежи и отправка сообщений требуют policy enforcement вне LLM. Полная модель
угроз и принцип least privilege разобраны в [[02 Areas/ML & DL/00 Учебник/17 Tools и Agents/72 Безопасность агентных систем|главе 72]].

## Сквозной разбор: задача «найди, измени, проверь»

Рассмотрим задачу: открыть репозиторий, найти причину падения parser test,
исправить код и подготовить отчёт.

**Наблюдение.** Harness передаёт issue, состояние git и небольшой индекс
репозитория. Модель не получает весь проект одним prompt.

**Локализация.** Policy вызывает code search и читает найденные определения.
Процедурный workflow может ограничить эту фазу отдельным контекстом, как
AutoCodeRover; динамический ACI-loop может вернуться к поиску после test failure.

**Изменение.** Исполнитель применяет патч только если совпал expected context,
показывает diff и не разрешает запись за пределами worktree.

**Обратная связь.** Тест запускается в зафиксированном окружении. Ошибка
становится наблюдением следующего шага, а не пересказом модели.

**Поиск.** Если есть несколько правдоподобных патчей, каждый исполняется в
отдельном snapshot. Value может ранжировать промежуточные ветви, но финальный
выбор делает test suite и дополнительные invariants.

**Завершение.** Grader независимо проверяет чистоту diff, релевантные тесты и
отсутствие запрещённых изменений. Итоговый ответ ссылается на сохранённый trace.

### Минимальный parser repair с наблюдаемым результатом

Пусть договор функции — разделить строку по первому `=`, удалить внешние пробелы и сохранить остальные `=` в значении. В fixture исходный код такой:

```python
def parse_assignment(line):
    key, value = line.split("=")
    return key.strip(), value.strip()
```

Тест `assert parse_assignment("token=a=b") == ("token", "a=b")` падает с `ValueError: too many values to unpack (expected 2)`. Есть две гипотезы: H1 — ошибочно разделяем все вхождения; H2 — мешают пробелы. В failing input пробелов нет, поэтому добавление `strip()` не устраняет наблюдаемый отказ. Чтение функции подтверждает H1: `split("=")` возвращает три части.

Исполнитель применяет минимальный патч к совпадающему исходному контексту:

```diff
-    key, value = line.split("=")
+    key, value = line.split("=", 1)
```

Регрессионная проверка проверяет и исходный отказ, и соседние случаи:

```python
assert parse_assignment("token=a=b") == ("token", "a=b")
assert parse_assignment(" timeout = 30 ") == ("timeout", "30")
assert parse_assignment("empty=") == ("empty", "")
try:
    parse_assignment("missing_separator")
except ValueError:
    pass
else:
    raise AssertionError("missing separator must fail")
print("parser contract: PASS (4 cases)")
```

В учебном запуске Python выводит `parser contract: PASS (4 cases)` и завершает процесс с кодом 0; исходная версия воспроизводит указанный ValueError. Terminal evidence связывает этот вывод с версией кода и командой, а проверка diff подтверждает, что менялась только операция разделения, не сами assertions. Эти четыре случая не доказывают общий parser для любого формата: например, кавычки и escape-последовательности не входят в выбранный контракт.

Ту же схему можно перенести в браузер, заменив code search на perception,
worktree snapshot на snapshot сайта, tests на final-state grader. Именно
сохранение ролей — policy предлагает, executor действует, environment хранит
состояние, verifier проверяет — позволяет сравнивать разные типы агентов без
словесной путаницы.

## Минимальный протокол эксперимента

Перед сравнением двух agent architectures зафиксируйте:

- задачи и точную версию среды;
- reset procedure и проверку начального состояния;
- observation/action schemas;
- модель, decoding parameters и максимальный бюджет вызовов;
- права инструментов и human-approval gates;
- правило остановки;
- execution grader и независимые safety invariants;
- полный trace, artifacts и стоимость каждой попытки;
- не менее нескольких trials на задачу и uncertainty для итоговой метрики.

После этого сравнивайте не только success, но и invalid-action rate, число
восстановлений состояния, ошибки perception, verifier false positives, цену и
длину траектории. Практическая реализация такого контракта дана в
[[02 Areas/ML & DL/06 Практика/25 Воспроизводимо оценить и red-team компьютерного агента|лабораторной работе по OSWorld-style evaluation и red teaming]].
