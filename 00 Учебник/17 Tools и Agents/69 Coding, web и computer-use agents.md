# Программирующие агенты и работа с интерфейсами

Парсер должен разобрать `token=a=b` на ключ `token` и значение `a=b`.
Тест вместо результата получает `ValueError`. Агенту нужно найти
причину, изменить функцию и убедиться, что обычные строки по-прежнему
разбираются.

В браузере агент получает другое наблюдение: дерево элементов или снимок.
После клика он узнаёт, что изменилось. Например, переход к оформлению
заказа меняет страницу и таблицу меток кнопок; успешный вызов клика ещё
не говорит, что заказ оформлен на нужный адрес. В обоих случаях модель
выбирает следующий шаг, исполнитель действует, а результат проверяется
по состоянию среды, как в
[[00 Учебник/17 Tools и Agents/68 Оценивание агентных систем|главе об оценивании]].

## Как агент исправляет парсер

<span id="минимальный-parser-repair-с-наблюдаемым-результатом"></span>
<span id="пример-исправление-парсера"></span>

### От падения теста до проверки патча

Требование к функции: разделить строку по первому `=`, убрать внешние
пробелы и сохранить остальные `=` в значении. Агент читает исходную
функцию по пути из отчёта теста:

```python
def parse_assignment(line):
    key, value = line.split("=")
    return key.strip(), value.strip()
```

Тест `assert parse_assignment("token=a=b") == ("token", "a=b")` завершается
ошибкой `ValueError: too many values to unpack (expected 2)`. После
`split("=")` получается список `["token", "a", "b"]`. При распаковке
в две переменные возникает ошибка, поэтому дело не доходит
даже до `strip()`. Ограничение одним разбиением меняет список на
`["token", "a=b"]`.

Исполнитель применяет минимальный патч к совпадающему исходному контексту:

```diff
-    key, value = line.split("=")
+    key, value = line.split("=", 1)
```

Регрессионные тесты охватывают исходный отказ и соседние случаи:

```python
def parse_assignment(line):
    key, value = line.split("=", 1)
    return key.strip(), value.strip()

assert parse_assignment("token=a=b") == ("token", "a=b")
assert parse_assignment(" timeout = 30 ") == ("timeout", "30")
assert parse_assignment("empty=") == ("empty", "")
try:
    parse_assignment("missing_separator")
except ValueError:
    pass
else:
    raise AssertionError("missing separator must fail")
print("parser contract: PASS (4 cases)")
```

До правки падает тест с двумя знаками `=`. После правки он проходит;
остальные три проверяют пробелы, пустое значение и отсутствие разделителя.
Отчёт должен ссылаться на проверенную ревизию и результат запуска, а diff
показывает, что изменилось правило деления, а не тесты. Контракт не включает
кавычки и экранирование, и четыре проверки ничего о них не доказывают.

### Что видит модель между вызовами

<!-- source_unit_id: meeting-05-slides-coding-agent-orientation -->

До правки модель получила строку ошибки и прочитала функцию. После правки
исполнитель запустил тест и вернул новый вывод. Ни на одном шаге модели
не требовалось читать весь репозиторий. Обозначим фактическое состояние
среды через $s_t$, доступное наблюдение через $o_t$, а действие через $a_t$:

$$
\begin{aligned}
o_t &= O(s_t),\\
a_t &\sim \pi_\theta(a\mid g,o_{\le t},a_{<t}),\\
s_{t+1} &= T(s_t,a_t).
\end{aligned}
$$

Здесь $g$ задаёт цель. Модель выбирает $a_t$ по текущему наблюдению и
прошлым действиям; переход $T$ выполняет программа. В истории
$\tau_t=(o_0,a_0,o_1,\ldots,a_{t-1},o_t)$ остаются сообщения о чтении,
патче и тестах, но актуальные файлы хранятся в репозитории. Если после
сбоя запуск восстановлен на другом коммите, прежний вывод теста не
подтверждает исправление на этом коммите.

## Какие команды получает модель в SWE-agent

<!-- source_unit_id: meeting-05-slides-swe-agent-loop -->

[SWE-agent](https://arxiv.org/abs/2405.15793) оставляет модели выбор следующего
шага через подготовленный для неё интерфейс. Между LLM и репозиторием
находится *agent-computer interface* (ACI) — набор команд,
спроектированных именно для модели. Он позволяет искать и просматривать код,
редактировать ограниченные диапазоны строк и запускать программы, а результат
каждой команды возвращает в кратком, предсказуемом формате.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/computer-agents-2026-11-09/swe-agent-overview.png|SWE-agent посылает команды через ACI в терминал и файловую систему; ответ среды возвращается через тот же интерфейс]]

*John Yang et al., [SWE-agent v3, Figure 1](https://arxiv.org/html/2405.15793v3#S1.F1).
[Оригинальный PNG](https://arxiv.org/html/2405.15793v3/swe_agent_overview.png),
без изменений, [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/).
[Berkeley, лекция 5, слайд 17](https://rdi.berkeley.edu/adv-llm-agents/slides/Code%20Agents%20and%20AI%20for%20Vulnerability%20Detection.pdf#page=17).*

Верхняя стрелка показывает команды, нижняя — ответ среды. Например, `open`
выбирает файл в репозитории, а в ответе модель видит путь, номера строк и
часть содержимого. После `edit` интерфейс сам возвращает обновлённый фрагмент;
ещё один вызов для чтения не нужен. Специальные команды дополняют обычный
Linux shell. Права на чтение, запись и запуск программ задаёт исполнитель,
а не схема команд ACI.

От интерфейса зависит, сколько информации приходится обрабатывать модели и
насколько сложно ей сформировать правильную команду. Если действие `open_file`
по умолчанию выдаёт весь файл, один неудачный выбор способен вытеснить из
контекста условие задачи и историю тестов. Если `edit` принимает произвольный
shell-скрипт, модель должна одновременно решить задачу и безошибочно управлять
редактором. Специализированная команда может принимать путь и диапазон строк,
проверять, что ожидаемый старый текст действительно найден, и возвращать только
изменённый фрагмент. Тогда одна модельная ошибка реже превращается в повреждение
состояния.

В [SWE-agent v3, §3](https://arxiv.org/html/2405.15793v3#S3) поиск возвращает
не более 50 результатов; при превышении лимита агент получает просьбу
уточнить запрос. Команда `open` показывает окно до 100 строк с номерами,
путём и числом скрытых строк, а `goto` переносит это окно к нужной позиции.
После `edit 404:407` просмотрщик сразу показывает изменённый участок.
Если проверка выявляет определённые синтаксические ошибки, изменение
отбрасывается, а агент получает сообщение для следующей попытки.
Так сочетаются поиск, чтение, правка и обратная связь; успешная
синтаксическая проверка при этом ещё не подтверждает исправление дефекта.

В агенте такого типа обязанности распределяются следующим образом:

1. управляющая программа собирает условие, историю действий и описание доступных
   команд;
2. модель выбирает информационное или изменяющее действие;
3. исполнитель проверяет аргументы и выполняет команду в изолированной среде;
4. результат команды возвращается модели вместе со сведениями о состоянии среды;
5. модель либо уточняет гипотезу, либо завершает работу;
6. отдельная проверяющая программа оценивает изменения в репозитории.

Для воспроизводимой проверки нужны команда запуска тестов, код завершения,
стандартный вывод, сообщения об ошибках и версия проверенного кода. Фраза
«тесты прошли» в ответе модели не заменяет эти результаты.

## Кто выбирает следующий шаг

<!-- source_unit_id: meeting-05-slides-coding-agent-design-comparisons -->

Если правка парсера не сработала, SWE-agent может сам решить, какой файл
перечитать и какой тест запустить. Agentless передаёт управление следующему
этапу по заранее заданному порядку: модель отвечает за выбор места правки
и предлагаемые патчи, а порядок локализации, генерации и проверки задан кодом.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/coding-web-computer-use/m05-p23-agentless-pipeline.png|Три блока Agentless: поиск места ошибки, генерация нескольких патчей и их отбор по тестам.]]

*Agentless: локализация места ошибки, генерация исправлений и отбор по тестам.
Синий, фиолетовый и зелёный блоки соответствуют трём стадиям; стрелки показывают,
какие данные передаются между ними. Источник: Charles Sutton,
[Coding Agents and AI for Vulnerability Detection, слайд 23](https://rdi.berkeley.edu/adv-llm-agents/slides/Code%20Agents%20and%20AI%20for%20Vulnerability%20Detection.pdf#page=23),
Berkeley Advanced LLM Agents, Spring 2025; схема — Xia et al.,
[Agentless](https://arxiv.org/abs/2407.01489).*

Верхний блок схемы постепенно сужает область поиска. Сначала описание ошибки
сопоставляется со структурой репозитория и извлекаются подходящие файлы. Затем
модель выбирает классы и функции, а внутри них — места, которые требуется
изменить. Это позволяет не помещать весь проект в один запрос. На каждом шаге
модель получает уже отобранный контекст, но переход от файлов к функциям, а
затем к строкам определён программой заранее.

В нижнем правом блоке из выбранных участков кода генерируется несколько
кандидатных исправлений. Параллельно по описанию ошибки строятся тесты,
воспроизводящие исходный отказ. Нижний левый блок использует результаты тестов
для фильтрации и ранжирования кандидатов; на выходе остаётся один патч. Такой
порядок позволяет расходовать дополнительные вызовы модели на новые варианты
исправления, не поручая ей каждый раз заново выбирать весь процесс работы.
При этом сгенерированный тест может неверно описывать требование: прохождение
этого теста — основание для отбора, но не доказательство общей корректности
программы.

В SWE-agent модель выбирает команды по мере появления новых наблюдений. Agentless
фиксирует три стадии — локализацию, генерацию исправления и проверку патча.
В версии [Agentless v2, §3.3](https://arxiv.org/html/2407.01489v2#S3.SS3)
сгенерированный тест сначала запускают на исходном коде: он должен
воспроизвести описанный отказ. Патчи с наименьшим числом регрессий затем
проверяют новым тестом. Для парсера это значит: сначала отсеять варианты,
которые ломают прежнее поведение, затем проверить строку с двумя знаками `=`.
Если ни один патч не проходит сгенерированный тест, Agentless возвращается
к отбору по регрессиям: модель могла написать неверный тест. Оставшиеся патчи
нормализуют через AST и ранжируют по частоте одинаковых исправлений.
Итог зависит и от качества сгенерированных тестов, и от покрытия регрессионного
набора; ни один из этих фильтров не располагает безошибочным ответом.

AutoCodeRover занимает промежуточную позицию: поиск контекста и генерация
патча допускают собственные итерации, но остаются двумя отдельными траекториями
с разными инструкциями. Passerine снова использует динамический ReAct-loop,
однако действует через реальные внутренние инструменты Google — поиск кода,
Bazel, чтение и редактирование файлов — без прямого доступа к командной строке.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/coding-web-computer-use/m05-p28-autocoderover-two-trajectories.png|У AutoCodeRover поиск контекста и генерация патча показаны как две отдельные траектории.]]

*AutoCodeRover разделяет поиск места ошибки и построение патча на две траектории
с отдельными контекстами: у фаз могут различаться system instructions и критерии
завершения. Источник: Berkeley Advanced LLM
Agents, Meeting 5, физическая стр. 28; [AutoCodeRover](https://arxiv.org/abs/2404.05427). Полный слайд без обрезки.*

В [AutoCodeRover v1, §§4.2–4.5](https://arxiv.org/html/2404.05427v1#S4.SS2)
поиск использует структуру программы: `search_class` возвращает сигнатуру
класса, а `search_method` — реализацию метода. Сигнатура помогает выбрать
следующий запрос, не читая сразу всё тело класса. Авторы разбирают issue
`django-13230`: одного определения `add_item` недостаточно, поскольку ошибка
находится в месте его использования. Если агент слишком рано объявит
найденный метод достаточным контекстом, генерация патча начнётся с неверной
локализации.

При наличии тестов AutoCodeRover может дополнить поиск статистикой покрытия:
методы, чаще встречающиеся в неуспешных тестах, становятся дополнительными
кандидатами. Это подсказка для поиска, а не замена анализа причины. Повтор
генерации патча из-за неверного формата или синтаксиса тоже отличается
от подтверждения исправления: в исходной конфигурации для него выделено
до трёх попыток.

У [Passerine v1, §III](https://arxiv.org/html/2501.07531v1#S3) пять основных
команд: `cat`, `code_search`, `edit`, `bazel`, `finish`. Они обращаются
к внутренним API Google и возвращают код завершения и текст. Отсутствие shell
здесь не означает отсутствие изоляции: её обеспечивает инфраструктура
репозитория и запуска тестов. При оценивании исторической ошибки поиск
ограничен состоянием до эталонного исправления, иначе агент мог бы найти
готовое решение в более поздней версии кода.

Свободный выбор следующей команды полезен, когда новое наблюдение меняет ход
решения: например, неожиданная ошибка компилятора требует снова искать
определение функции. Фиксированные этапы упрощают типовую задачу: программа
сама передаёт найденные участки кода на исправление, а кандидаты — на проверку.
Однако ошибка ранней локализации может остаться неисправленной, если возврат к
этому этапу не предусмотрен. Ни один вариант не гарантирует лучшего результата
во всех задачах. Для сравнения нужно использовать одну модель, одинаковый
бюджет и одну процедуру проверки.

При проектировании полезно отделять решения, зависящие от новых наблюдений,
от обязательных операций. Поиск причины неожиданного отказа можно поручить
модели; подготовку окружения, ограничение ресурсов, сохранение файлов и запуск
проверок задаёт обычный код.

### RepairAgent: управление через конечный автомат

[RepairAgent v2, §III](https://arxiv.org/html/2403.17134v2#S3) ограничивает
набор инструментов текущим состоянием работы. В состоянии `Understand the bug`
агент изучает сбой и формулирует гипотезу. Вызов `express_hypothesis` переводит
его в `Collect information to fix the bug`, где собирается контекст для
исправления. Команда `write_fix` применяет патч, запускает тесты и переводит
систему в `Try to fix the bug`. Если тесты не проходят, изменения откатываются.
Агент может запросить дополнительные сведения или отбросить гипотезу;
переход к `Done` завершает работу.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/external-figure-review-2026-11-10/repairagent-figure2.svg|Конечный автомат RepairAgent: состояния исследования ошибки, сбора контекста, проверки исправления и завершения.]]

*Islem Bouzenia, Premkumar Devanbu, Michael Pradel,
[RepairAgent v2, Figure 2](https://arxiv.org/html/2403.17134v2#S3.F2).
[Оригинальный SVG](https://arxiv.org/html/2403.17134v2/states_diagram2.drawio.svg),
[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/).
Стрелки допускают возврат к прежним состояниям.*

Например, после неудачного патча агент может вызвать `collect_more_information`,
прочитать вызывающий метод и предложить другой патч. При опровержении самой
причины ошибки он вызывает `discard_hypothesis` и возвращается к её изучению.
Автомат задаёт допустимые команды, но оставляет модели выбор перехода:
это не однократный проход по фиксированным стадиям Agentless.

Перед очередным вызовом middleware обновляет в prompt состояние, инструменты,
накопленные сведения и результат последней команды. Проверка тестами остаётся
ограниченной их покрытием. Кроме того, исходная работа по умолчанию допускает
идеальную локализацию дефекта; такие результаты нельзя прямо сопоставлять
с поиском ошибки по одному issue в целом репозитории.

## Какие патчи принимает проверка

`resolved` в SWE-bench означает, что патч прошёл закреплённый за задачей
набор тестов. Если в нашем наборе для парсера нет строки `token=a=b`,
исходная версия может пройти все проверки: результат о дефекте в таком
случае ничего не говорит. Качество оценивания зависит и от того, какую
версию репозитория читает агент и не видел ли он готовое исправление.
Правила `FAIL_TO_PASS` и `PASS_TO_PASS` разобраны в
[[00 Учебник/17 Tools и Agents/68 Оценивание агентных систем|главе об оценивании]].

Вызов модели закончился, но отладчик ещё держит остановленную программу.
Если исполнитель откроет новый сеанс, он потеряет кадр стека и точку
останова, даже если в истории сообщений по-прежнему написано «остановились
в парсере».

<span id="один-сеанс-от-запуска-до-остановки"></span>

### Что хранится в сеансе отладчика

[EnIGMA, §2.1](https://proceedings.mlr.press/v267/abramovich25a.html)
расширяет ACI интерактивными инструментами. У них своё, отдельное от
терминала состояние. В конфигурации авторов одновременно работает не
более одного интерактивного сеанса, а обычный терминал остаётся доступен.

Допустим, вместо падения теста мы остановили учебный парсер перед
разбиением строки. Пока процесс остановлен, модель может прочитать
исходник через редактор, а затем запросить значение `line` из того
же кадра стека. Если сеанс закрылся, прежний идентификатор кадра
больше не годится. Если исполнитель не дождался ответа, по журналу
нельзя решить, остановился ли процесс или уже продолжил работу.
Сначала нужно получить состояние сеанса, затем выбирать действие.

<span id="что-модель-получает-вместо-длинного-вывода"></span>

### Сводка команды и исходный журнал

В Figure 3 статьи сравниваются три способа передать один вывод.
Можно положить все 170 строк в контекст, сохранить их в файл и
показать первые 15 с пометкой «ещё 155», или вернуть пересказ и путь
к полному выводу. Во втором случае модель знает, сколько пропущено,
и может открыть нужный участок. В третьем может найти его по сводке,
но причину исключения и номер строки следует брать из журнала теста,
а не из пересказа. Сами команды не меняются, меняется наблюдение.

В Table 3 полный EnIGMA с Claude 3.5 Sonnet решил 29,5% из 390
лабораторных CTF-задач за одну попытку на задачу, а без двух
интерактивных инструментов — 27,4%. Это разность для двух изменений
сразу. В отдельных категориях эффекты расходятся: для `pwn` показатель
изменился с 20,45% до 11,36%, а для `web` — с 13,79% до 17,24%.
Эти числа относятся к задачам с готовым критерием успеха. Они не
измеряют поиск неизвестных дефектов в произвольном ПО.

## Что можно заключить из сбоя программы

<!-- source_unit_id: meeting-05-slides-vulnerability-discovery-problem -->
<!-- source_unit_id: meeting-05-slides-charles-sutton-vulnerability-discovery-loop -->
<!-- source_unit_id: meeting-05-reading-02-catalogue-record -->

Отчёт о дефекте обычно задаёт симптом или нарушенное требование:
парсер не должен отбрасывать часть значения. При проверке сообщения
о неизвестной ошибке команда ещё должна установить, что программа
нарушила свой контракт и что отказ произошёл в ней, а не при
подготовке теста. Для этого фиксируют версию программы, конфигурацию
сборки и наблюдавшийся вид сбоя. Например, отсутствующая зависимость
может прервать тест до запуска нужной функции; такой результат нельзя
считать подтверждением дефекта.

В [отчёте Big Sleep](https://projectzero.google/2024/10/from-naptime-to-big-sleep.html)
исходной подсказкой было изменение в SQLite. Авторы описывают поиск
варианта уже известного дефекта, а не проверку репозитория с нуля.
Первый подтверждённый сигнал в опубликованном опыте — срабатывание
`assert` в инструментированной сборке. Поведение сборки без assertions
исследовали отдельно. В лекции 5 Berkeley обсуждается и другой случай,
обнаруженный AddressSanitizer; это не та же траектория. Разница существенна
для отчёта: авария в одной конфигурации, нарушение безопасности памяти
и доказанная эксплуатируемость — разные утверждения.

## Как выбирать степень свободы агента

<!-- source_unit_id: meeting-05-slides-coding-agent-conclusions -->

Степень свободы следует выбирать по цене ошибки и качеству обратной связи.
Разрешить модели самостоятельно продолжать траекторию разумно, когда действия
обратимы, состояние можно сохранить, а ошибку быстро обнаруживает компилятор,
тест или другая проверяющая программа. Чем труднее отменить действие и
обнаружить его ошибочность, тем важнее ограничения исполнителя и одобрение
человека.

Для программирующего агента можно выделить следующие варианты:

| Режим | Что решает модель и что задаёт программа |
|---|---|
| Один вызов | Когда нужная функция уже найдена, модель пишет патч, а программа применяет его и запускает тесты. |
| Фиксированные этапы | Для повторяемого исправления код задаёт порядок локализации, правки и проверки. Модель решает задачу каждого этапа. |
| Цикл с ACI | При исследовании репозитория модель выбирает следующую команду из ограниченного интерфейса. Исполнитель проверяет её формат, права и лимиты. |
| Цикл с shell или IDE | Модель выбирает команды из более широкого набора. Одноразовая среда ограничивает доступ и ресурсы, а программа следит за бюджетом. |

Набор команд и способ управления — разные решения. Доступ к shell расширяет
возможности агента, но сам по себе не улучшает выбор следующего действия.

## Что видно агенту на сайте

<!-- source_unit_id: meeting-06-slides-visualwebarena -->
<!-- source_unit_id: meeting-06-reading-02-catalogue-record -->
<!-- source_unit_id: meeting-06-reading-03-catalogue-record -->

Состояние веб-приложения включает структуру страницы, расположение элементов,
cookies, историю переходов, серверные данные и открытые вкладки. Агент видит
только часть этих сведений. На снимке экрана нет элементов за пределами видимой
области; в дереве доступности могут отсутствовать объекты, нарисованные на
canvas; HTML, напротив, содержит множество невидимых узлов и служебный текст.
Такую задачу описывают как частично наблюдаемый марковский процесс принятия
решений (POMDP): действие выбирается по истории наблюдений, а не по полному
состоянию сайта.

[WebArena](https://arxiv.org/abs/2307.13854) создаёт самодостаточные сайты и
проверяемые задачи; [VisualWebArena](https://jykoh.com/vwa) добавляет задания,
для которых визуальная информация действительно необходима. Например,
инструкция может требовать распознать товар по фотографии или прочитать адрес,
который не продублирован в тексте задачи.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/coding-web-computer-use/m06-p18-visualwebarena-shopping.png|Задание про цветной фотопринтер использует адрес, указанный на фотографии конвертов.]]

*Нужно купить самый дешёвый цветной фотопринтер и отправить его Emily по адресу
на фотографии конвертов. Тип товара указан в тексте, а адрес нужно прочитать
на изображении. Источник: [Berkeley, лекция 6, слайд 18](https://rdi.berkeley.edu/adv-llm-agents/slides/ruslan-multimodal.pdf#page=18); [VisualWebArena](https://jykoh.com/vwa). Полный слайд без обрезки.*

В показанной далее на слайдах 21–25 траектории агент открывает категорию
принтеров, сравнивает цены подходящих моделей, выбирает товар и добавляет
его в корзину. Затем он переходит к оформлению заказа, заполняет адрес
доставки по фотографии и подтверждает заказ. Нужный товар в корзине
ещё не означает выполнения: покупка должна завершиться с требуемым адресом.
Здесь различаются три возможных отказа: ошибка выбора товара, ошибка чтения
адреса и незавершённое оформление. Одинаковый текст финального ответа
агента может сопровождать каждое из этих состояний.

Для повторяемого эксперимента мало сохранить текст задачи. Нужны также
исходное состояние сайтов, пользовательские данные, состояние авторизации,
список допустимых действий, максимальная длина эпизода и способ проверки
результата. Если одна попытка оставила товар в корзине, следующая уже
начинается с других условий. Перед каждым запуском исходное состояние нужно
восстанавливать.

## Дерево доступности, снимок и метки элементов

<!-- source_unit_id: meeting-06-slides-vision-language-web-agents -->
<!-- source_unit_id: meeting-06-reading-01-catalogue-record -->

Если действие зависит от цвета или положения кнопки, одного её имени
может не хватить. HTML сохраняет атрибуты, но содержит также скрипты,
стили и невидимые узлы.
Дерево доступности (*accessibility tree*) короче и сохраняет роли элементов —
например, «кнопка» или «поле ввода», — но зависит от качества разметки. Снимок
экрана передаёт расположение, изображения и видимое состояние элементов, зато
не содержит их символьных идентификаторов. Метод Set-of-Marks (SoM) добавляет
метки к интерактивным элементам. Модель выбирает номер на изображении, а
исполнитель превращает команду вида `click(mark=17)` в щелчок по соответствующему
элементу.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/coding-web-computer-use/m06-p29-html-vs-som.png|Слева текстовое представление страницы; справа снимок с номерами у интерактивных элементов.]]

*Слева — длинное текстовое представление страницы, справа — снимок экрана с
пронумерованными интерактивными областями. В первом случае модель ищет нужный
элемент в тексте, во втором — выбирает метку на изображении. Источник: [Berkeley, лекция 6, слайд 29](https://rdi.berkeley.edu/adv-llm-agents/slides/ruslan-multimodal.pdf#page=29). Полный слайд без обрезки.*

SoM не устраняет ошибки восприятия. Метка может закрыть текст, два элемента —
перекрыться, а расположение объектов — измениться между наблюдением и кликом.
У обращения к HTML тоже есть ограничения: идентификатор может измениться,
а найденный элемент — оказаться невидимым или недоступным для нажатия. Поэтому
снимок экрана и дерево доступности можно использовать совместно, связывая
их элементы одними идентификаторами.

<a id="web-agent-observation-bound-marks"></a>

### Метка относится к тому снимку, на котором её выбрали

В [VisualWebArena v2, §3.1–3.2](https://arxiv.org/html/2401.13649v2#S3.SS1)
модель получает рамки и номера, а `click [elem]` использует номер из
текущего наблюдения. На одном снимке под номером 17 может быть выбор
способа доставки, а после перерисовки — подтверждение заказа. Подстановка
старого номера в новую таблицу меток нажмёт другую кнопку, хотя текст
команды не изменился.

В учебном примере исполнитель сохраняет с предложенной командой ключ
наблюдения: вкладку, документ и ревизию разметки. Исполнитель берёт ключ
кадра, отправленного модели с этим запросом. Когда приходит ответ,
исполнитель не заменяет старый ключ ключом нового кадра.

~~~python
frame1 = (("shop-tab", "checkout", 1), {17: "shipping"})
frame2 = (("shop-tab", "checkout", 2),
          {17: "confirm_order", 23: "shipping"})
old_click = (frame1[0], 17)
fresh_click = (frame2[0], 23)
click_log = []

def dispatch_click(request, current, click):
    observed_key, mark = request
    current_key, marks = current
    if observed_key != current_key:
        return "stale_observation"
    if mark not in marks:
        return "unknown_mark"
    click(marks[mark])
    return "dispatched"

# A dispatcher that uses only the latest mark table targets another button.
assert frame2[1][old_click[1]] == "confirm_order"
assert dispatch_click(old_click, frame2, click_log.append) == "stale_observation"
assert dispatch_click((frame2[0], 99), frame2, click_log.append) == "unknown_mark"
assert click_log == []
assert dispatch_click(fresh_click, frame2, click_log.append) == "dispatched"
assert click_log == ["shipping"]
~~~

При `stale_observation` модель должна получить новое наблюдение и
заново выбрать элемент. Состояние страницы может измениться и между
проверкой ключа и щелчком. В реальном браузере исполнитель должен
проверить актуальный элемент непосредственно перед действием или
отказаться от координатного клика, если цель нельзя связать с наблюдением.
Проверка свежести не заменяет разрешения на подтверждение заказа.
Статус `dispatched` означает вызов исполнителя, а не подтверждённый
результат действия. Здесь браузер не запускается: проверяется контракт
передачи команды, а не реализация VisualWebArena.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/coding-web-computer-use/m06-p35-som-trajectory.png|На кадрах задачи агент находит пользователя по изображению и переходит в его профиль перед действием.]]

*В примере блокировки пользователя нужный объект сначала находят по изображению, затем
переходят в профиль и только после этого выполняют изменение состояния.
Источник: [Berkeley, лекция 6, слайд 35](https://rdi.berkeley.edu/adv-llm-agents/slides/ruslan-multimodal.pdf#page=35);
VisualWebArena. Полный слайд без обрезки.*

Чтобы сравнить представления страницы, можно запускать одну модель на одних
задачах с разными входами: только деревом доступности, снимком с SoM или обоими
представлениями. Помимо доли решённых задач, измеряют ошибки выбора элемента,
долю недопустимых команд, число действий и размер контекста.

### Mind2Web: от множества элементов к одному действию

[Mind2Web v1, §§2–3](https://arxiv.org/html/2306.06070v1#S2) содержит
записанные людьми задания и действия на реальных сайтах. В каждой позиции
нужно выбрать элемент, операцию и, если требуется, значение для ввода
или выбора. Порядок «найти нужный элемент → решить, что с ним сделать»
выражен в системе MindAct двумя отдельными моделями.

Сначала небольшой cross-encoder сопоставляет задачу и предыдущие действия
с каждым кандидатом из DOM. Представление кандидата включает его текст,
атрибуты и соседние элементы. При обучении размеченный элемент является
положительным примером, случайные другие элементы — отрицательными.
После ранжирования большая модель получает только выбранных кандидатов
с небольшим окружением. Она выбирает элемент и формирует операцию.
В варианте с несколькими вариантами ответа кандидаты группируются
по пять с дополнительным вариантом `None`; выбранные элементы могут
перейти в следующий раунд отбора.

Если задача — выбрать нужный размер товара, ранжировщик должен сохранить
соответствующий список размеров, а большая модель — выбрать значение
из этого списка. Ошибка первого этапа ограничивает второй: нужный элемент,
не попавший в кандидаты, уже нельзя выбрать правильно. Поэтому отдельно
измеряют полноту отбора элементов и точность выбора действия.

Исходная оценка [Mind2Web, §4.2](https://arxiv.org/html/2306.06070v1#S4.SS2)
выполняется по записанным шагам: модели подаётся правильная история
предыдущих действий. Даже успешное предсказание всех таких шагов не является
запуском замкнутого цикла на живом сайте. В нём собственная ранняя ошибка
агента изменила бы последующие наблюдения. Этим записанный набор отличается
от исполнения задач в WebArena и OSWorld.

<span id="почему-реактивный-следующий-клик-ломается-на-длинном-горизонте"></span>
<span id="почему-ошибки-накапливаются-в-длинной-последовательности-действий"></span>

## Ошибки в последовательности кликов

<!-- source_unit_id: meeting-06-slides-search-agent-motivation -->

Отдельное действие может выглядеть разумным, но мешать выполнению всей задачи. Агент
добавляет не тот вариант товара, переходит на страницу без обратимой навигации
или изменяет фильтр так, что нужный объект исчезает. Если все $H$ шагов необходимы и вероятность правильного шага при условии,
что все предыдущие были правильны, всегда равна $p$, то по правилу
произведения получается $p^H$. При $p=0.9$ десять шагов дают
$0.9^{10}\approx0.35$. Здесь нельзя подставить точность на записанных
шагах Mind2Web и получить долю выполненных задач: в браузере ошибки меняют
следующие наблюдения, часть ошибок исправима, а допустимых путей несколько.
Поиск даёт агенту возможность сравнить варианты, прежде чем продолжать один.

<span id="best-first-search-в-реальной-web-среде"></span>

## Поиск с возвратом к другой ветви

<!-- source_unit_id: meeting-06-slides-web-agent-tree-search -->
<!-- source_unit_id: meeting-06-reading-04-catalogue-record -->

[Tree Search for Language Model Agents](https://arxiv.org/abs/2407.01476)
использует поиск по наиболее перспективным состояниям (*best-first search*)
при работе с сайтом. Вместо немедленного выбора единственного действия агент
рассматривает несколько продолжений:

1. алгоритм извлекает кандидата из очереди;
2. среда восстанавливается и исполняет путь к этому кандидату;
3. оценочная модель определяет, насколько полученное состояние приближает к цели;
4. если поиск продолжается, модель предлагает следующие действия,
   а алгоритм добавляет соответствующие пути в очередь.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/coding-web-computer-use/m06-p50-best-first-search.png|Дерево действий браузера: из одного наблюдения можно продолжить несколько ветвей.]]

*Разветвления соответствуют альтернативным действиям. Для сравнения ветвей
нужно уметь восстановить состояние браузера. Источник:
[Berkeley, лекция 6, слайд 50](https://rdi.berkeley.edu/adv-llm-agents/slides/ruslan-multimodal.pdf#page=50);
[Koh et al.](https://arxiv.org/abs/2407.01476).
Полный слайд без обрезки.*

В [§3.3](https://arxiv.org/html/2407.01476v1#S3.SS3) очередь хранит
кандидатов на дальнейшую проверку. После выбора узла среда восстанавливается
в соответствующее состояние, затем модель оценивает его. Если оценка стала
лучшей среди уже проверенных узлов, запоминается путь к нему. При достижении
порога или исчерпании бюджета поиск заканчивается возвратом к лучшему
найденному состоянию. Иначе модель предлагает несколько продолжений.

Авторы откладывают оценку детей до извлечения из очереди. При добавлении
ребёнок получает приоритет родителя: немедленная оценка каждой альтернативы
потребовала бы больше восстановлений браузера. Поэтому приоритет в очереди
и уже вычисленная оценка конкретного состояния — разные величины.
Название best-first не означает гарантии найти оптимальный путь:
модельная эвристика может предпочесть неверную ветвь.

В [§5.4](https://arxiv.org/html/2407.01476v1#S5.SS4) описано фактическое
восстановление: среду сбрасывают и повторяют последовательность действий
от начала. Нажатия браузерной кнопки «назад» недостаточно, поскольку оно
может не восстановить введённый текст или прокрутку. Повторение действий
опирается на детерминированную тестовую среду; живой сайт не обязан вернуть
то же состояние. Сохранённый список действий сам по себе не является
снимком серверной базы.

Каждая альтернатива должна начинаться с одного и того же родительского
состояния. Если в корзине нет товаров, ветви «добавить книгу» и «добавить
тетрадь» должны дать две отдельные корзины, а не корзину с обоими товарами.
Поэтому `restore` находится внутри цикла по действиям.

Проверим это на числовой среде: состояние равно 10, альтернативы — прибавить 1 и умножить на 2. Независимые дети должны хранить 11 и 20; ошибочная последовательная реализация даст 11 и 22.

```python
from copy import deepcopy

root = {"id": "root", "snapshot": {"x": 10}}
actions = [("add_one", lambda x: x + 1), ("double", lambda x: 2 * x)]
children = []
for name, transition in actions:
    env = deepcopy(root["snapshot"])  # restore перед каждой альтернативой
    env["x"] = transition(env["x"])
    children.append({
        "parent": root["id"], "action": name,
        "observation": {"x": env["x"]}, "snapshot": deepcopy(env)
    })
assert [c["snapshot"]["x"] for c in children] == [11, 20]
assert all(c["parent"] == "root" for c in children)
assert root["snapshot"]["x"] == 10
print("branch isolation: PASS (11, 20)")
```

Этот пример проверяет независимость ветвей в простой среде. В браузере
отдельно приходится восстанавливать cookies, серверные записи и другие
изменения, которые не сводятся к копированию локального объекта.

Клонирование VM или восстановление тестового сайта может вернуть состояние,
которого уже нет в истории браузера. На внешнем сайте наличие копии вкладки
не возвращает содержимое серверной корзины. Поиск по альтернативам обычно
ограничивают чтением; запись допустима для пробных ветвей лишь там, где
среда специально предоставляет независимые копии или обратимые операции.

В исходном [§4.1](https://arxiv.org/html/2407.01476v1#S4.SS1) оценочная
модель получает задачу, снимки экрана, прошлые действия и текущий URL.
Её ответы «успех», «продвижение к цели» и «неуспех» преобразуются
в числа 1, 0,5 и 0; неверный формат также получает 0. Для одного состояния
генерируют 20 таких ответов и усредняют. Например, четыре ответа об успехе,
двенадцать о продвижении и четыре о неуспехе дают $(4+12\cdot0{,}5)/20=0{,}5$.
Это эвристическая оценка по наблюдениям, а не независимая проверка базы сайта.

Параметры исходного опыта — глубина 5, до пяти продолжений и бюджет 20
оценённых состояний за один поиск. Для получения пяти продолжений модель
генерирует 20 кандидатов, из которых выбираются наиболее частые действия.
Поэтому «20 оценок» не равно двадцати простым вызовам модели: отдельно
оплачиваются предложения действий, сэмплы оценщика и повторное исполнение.

### Учебный поиск с возвратом к другой ветви

Следующая среда задана таблицей переходов; браузер и модель здесь не
запускаются. На странице `start` есть две ссылки. Первая ведёт к рекламе,
которая выглядит перспективно, но заканчивается тупиком. Вторая ведёт
к товару, а затем к ответу. Числа оценщика заданы заранее, чтобы было видно,
как выбор зависит от эвристики.

~~~python
import heapq
from itertools import count

transitions = {
    "start": {"open_first": "advert", "open_second": "product"},
    "advert": {"follow_banner": "dead_end"},
    "product": {"read_details": "answer"},
    "dead_end": {}, "answer": {},
}
values = {"start": 0.5, "advert": 0.8, "dead_end": 0.0,
          "product": 0.6, "answer": 1.0}

def replay(path):
    state = "start"
    for action in path:
        state = transitions[state][action]
    return state

def best_first_fixture(budget=5, depth=2, threshold=0.95):
    if type(budget) is not int or budget < 0 or type(depth) is not int or depth < 0:
        raise ValueError("budget and depth must be nonnegative integers")
    serial = count()
    frontier = [(0.0, next(serial), ())]
    best_path, best_value, visited = None, float("-inf"), []
    reason = "budget"
    while frontier and len(visited) < budget:
        _, _, path = heapq.heappop(frontier)
        state = replay(path)  # reset to start and replay this branch
        value = values[state]
        visited.append((state, value))
        if value > best_value:
            best_path, best_value = path, value
        if value >= threshold:
            reason = "threshold"
            break
        if len(path) < depth:
            for action in transitions[state]:
                heapq.heappush(frontier, (-value, next(serial), path + (action,)))
    else:
        reason = "frontier_empty" if not frontier else "budget"
    return {"path": best_path,
            "state": replay(best_path) if best_path is not None else None,
            "value": best_value if best_path is not None else None,
            "visited": visited, "reason": reason}

result = best_first_fixture()
assert [state for state, _ in result["visited"]] == [
    "start", "advert", "dead_end", "product", "answer"]
assert result["path"] == ("open_second", "read_details")
assert result["state"] == "answer"
assert best_first_fixture(budget=2)["state"] == "advert"
~~~

Оба ребёнка `start` сначала имеют приоритет 0,5. Первой рассматривается
реклама и получает оценку 0,8. Её продолжение попадает в очередь с этим
приоритетом и проверяется раньше второй ссылки, но получает 0. После этого
поиск возвращается к пути через товар и доходит до ответа. При бюджете
две оценки лучшим остаётся рекламное состояние с 0,8. Даже корректный
алгоритм поиска не превращает ошибочную оценку в правильный результат.

Порог оценщика означает «достаточно перспективный кандидат». Подтверждение
решения выполняется отдельно после поиска. Если снизить порог до 0,7,
этот пример остановится на рекламе. Сравнивать поиск следует также
с независимыми повторными попытками при том же полном бюджете,
как в [[02 Areas/ML & DL/00 Учебник/17 Tools и Agents/68 Оценивание агентных систем|главе об оценивании]].

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/coding-web-computer-use/m06-p60-search-backtracking.png|Верхняя траектория заканчивается неудачей; нижняя возвращается к развилке и выбирает другое действие.]]

*Верхняя траектория продолжает раннюю ошибку до неудачного завершения. Нижняя сохраняет
альтернативные состояния, возвращается после низкой оценки ветви и продолжает
по более перспективному пути. Источник: [Berkeley, лекция 6, слайд 60](https://rdi.berkeley.edu/adv-llm-agents/slides/ruslan-multimodal.pdf#page=60). Это один полный кадр последовательности, без монтажа и
обрезки.*

В опыте [Koh et al. 2024, §4.2](https://arxiv.org/html/2407.01476v1#S4.SS2)
поиск повысил долю решённых GPT-4o задач на
VisualWebArena с 18,9% до 26,4% по Table 2. Разница составляет

В сопровождающем таблицу абзаце v1 указано 18,6%, что не согласуется

*Округлённые результаты на WebArena и VisualWebArena показывают, что поиск
помогает обеим базовым моделям в данном эксперименте. Для цитирования точного

Поиск требует дополнительных вызовов модели, исполнения альтернативных

недостаточно: нужно показать, как доля решённых задач зависит от числа вызовов
или стоимости. Если действия дороги или необратимы, сравнивать варианты
приходится до исполнения, оценивая предполагаемые последствия. Если среда
допускает дешёвое восстановление, альтернативы можно проверить непосредственно.

<span id="insta-синтетические-задачи-из-работающего-web"></span>

## Как InSTA собирает примеры на сайтах

<!-- source_unit_id: meeting-06-slides-insta-setup -->

Ручной сбор демонстраций трудно повторить для множества разных сайтов.
[InSTA v1](https://arxiv.org/abs/2502.06776v1) автоматизирует его: LLM получает домен,
предлагает реалистичную задачу, агент пытается её выполнить, затем отдельная
модель проверяет траекторию. Процесс применён к 150 тысячам сайтов, выбранным с
помощью Common Crawl PageRank. В описанной версии сначала рассматривается
миллион доменов; около 85% исключает модельный фильтр, оставляя примерно
150 тысяч задач. Фильтр использует инструкцию и URL домена; содержимое
каждой будущей страницы сайта он не проверяет.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/coding-web-computer-use/m06-p80-insta-pipeline.png|InSTA предлагает задачу по домену, исполняет её и передаёт записанную траекторию на проверку.]]

*Сбор данных в InSTA: генерация задачи, попытка её выполнения и проверка
результата. Сохранённая траектория становится обучающим примером только после
отбора. Источник: [Berkeley, лекция 6, слайд 80](https://rdi.berkeley.edu/adv-llm-agents/slides/ruslan-multimodal.pdf#page=80); [Trabucco et al.](https://arxiv.org/abs/2502.06776).
Полный слайд без обрезки.*

В описанном сборе генератору запрещено предлагать задачи с покупками,
комментариями и созданием аккаунтов: преобладает поиск информации.
На сайт выделяется одна задача и не более десяти действий
([InSTA v1, Appendix A](https://arxiv.org/html/2502.06776v1#A1)).
Это инструкции генератору и агенту, а не гарантия запрета операций
на уровне исполнителя. Они также меняют распределение данных: по этим траекториям нельзя
судить, насколько хорошо агент совершает покупки, отправляет формы или управляет
аккаунтом.

Чтобы проверить такой набор данных, для каждой попытки нужно знать сайт и
время сбора, условие задачи, наблюдения и действия, версию модели и решение
оценщика. Для отклонённых примеров полезно сохранять причину отказа. Это
позволяет проследить, какие задачи попадали в обучение, и повторно проверить
качество отбора.

<span id="верификатор-как-фильтр-синтетической-траектории"></span>

## Как InSTA отбирает удачные траектории

<!-- source_unit_id: meeting-06-slides-insta-verification-scaling -->

Оценщик InSTA получает задачу, историю действий и последнее текстовое
наблюдение страницы. Он генерирует ответ, из которого извлекается число
от 0 до 1. В [§5.1](https://arxiv.org/html/2502.06776v1#S5.SS1)
это записано как преобразование ответа модели:

$$
\widehat r_T=\operatorname{parse}\!\left(
\operatorname{LLM}(c,a_{1:T},o_T)\right).
$$

Здесь $c$ — задача, $o_T$ — доступное наблюдение, а $\widehat r_T$ —
заявленная моделью оценка успеха. Она не становится калиброванной
вероятностью только от того, что записана числом. Для сопоставления
с человеческой разметкой авторы относят $\widehat r_T>0{,}5$ к успеху.
Уверенность равна $2|\widehat r_T-0{,}5|$. При оценке 0,9 она составляет
0,8, а при 0 и 1 достигает максимума. Отбор демонстраций поэтому требует
отдельно успеха и максимальной уверенности.

На слайде 91 курса приведены 14,6% задач с оценкой уверенного успеха,
или примерно 22 тысячи из 150 тысяч. В закреплённой
[InSTA v1, §5.2](https://arxiv.org/html/2502.06776v1#S5.SS2)
указаны 16,7%. Это разные опубликованные числа; оснований объявлять их
одним и тем же замером нет. Ни одно из них не является независимой
человеческой оценкой всей коллекции: это доля, принятая модельным оценщиком.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/coding-web-computer-use/m06-p90-automatic-verifier.png|Вход оценщика InSTA — задача, действия и итоговое наблюдение; выход — оценка успеха.]]

*Оценщик получает историю действий и финальное наблюдение. Скрытое состояние
сайта ему недоступно. Источник: [Berkeley, лекция 6, слайд 90](https://rdi.berkeley.edu/adv-llm-agents/slides/ruslan-multimodal.pdf#page=90); InSTA. Полный слайд без
обрезки.*

Авторы сопоставляют компоненты с человеческой разметкой, но лучшие
показатели относятся к разным моделям и выборкам. На 100 доменах Gemini
1.5 Pro дал 97% правильных решений о пригодности сайта. Для предложенных
им задач люди сообщили о выполнимости 89%. Лучший результат проверки
траекторий — 82,6% совпадений GPT-4o с человеческими метками. В массовом
сборе используется Llama 3.1 70B: соответствующие показатели в статье
равны 85%, 75% и 81,7%. Смешивать их в одну оценку качества конвейера
нельзя.

Для решений Llama с максимальной уверенностью авторы отдельно приводят
93,1% общей точности, precision 0,87 и recall 0,82 на проверочной выборке.
Даже здесь максимальная уверенность не исключает ложного принятия.
Для обучающей выборки особенно существенны ложноположительные решения:
оценщик принимает неудачную попытку за успешную, и модель затем обучается
воспроизводить её. Общая точность не показывает частоту именно этой ошибки;
для неё нужны отдельный подсчёт и ручная проверка выбранных примеров.

### Что попадает в обучение InSTA

После отбора по успеху InSTA дополнительно требует максимальной уверенности
оценщика и положительной оценки того, что действия действительно вели к
решению. Оставляют траектории не короче трёх действий, без серверных ошибок,
captcha и блокировки доступа. Из 7 463 отобранных демонстраций 500 откладывают
для проверки, а 6 963 смешивают с человеческими данными
([InSTA v1, §6](https://arxiv.org/html/2502.06776v1#S6)).
Условие уверенности само по себе недостаточно: оценка 0 тоже максимально
уверенна, но соответствует неуспеху.

Долю человеческих примеров задают при формировании мини-пакета, независимо
от размеров двух коллекций. В опытах с малым количеством человеческих
действий она равна 0,5, в остальных — 0,8. Добавление синтетических
траекторий расширяет набор сайтов и вариантов действий, на которых
обучается агент; увеличение файла данных без изменения вероятности выбора источника ещё
не определяет, как часто модель увидит каждый источник.

В режиме с 32 человеческими действиями авторы сообщают относительный
прирост Step Accuracy на 89,5% для Mind2Web и 122,1% для WebLINX.
Это проверка выбора правильного элемента и действия на шаге, а не доля
целиком выполненных заданий. При большом объёме человеческих данных
на официальных тестах результаты сопоставимы. Более заметное улучшение
авторы получают на отложенных данных своего конвейера с новыми сайтами.
Такой тест проверяет перенос внутри способа сбора InSTA; его модельный
отбор и метрика шага не заменяют независимую проверку выполнения задач
в живой среде.

## Как OSWorld проверяет изменения в приложении

<!-- source_unit_id: meeting-07-slides-osworld -->
<!-- source_unit_id: meeting-07-reading-01-catalogue-record -->

[OSWorld](https://arxiv.org/abs/2404.07972) переносит оценивание с одного сайта
на полноценный компьютер: 369 задач охватывают приложения и взаимодействия
между ними. Для каждой задачи заданы начальная конфигурация виртуальной
машины и проверка результата. Агент получает инструкцию и наблюдения — снимок
экрана, дерево доступности или вывод терминала, в зависимости от настройки.
Он управляет мышью и клавиатурой либо выполняет программные команды. После
завершения проверяющая программа исследует фактическое состояние среды.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/computer-agents-2026-11-09/osworld-task-environment.png|OSWorld: конфигурация задачи поступает координатору; агент взаимодействует с виртуальной машиной через симулятор, а артефакты получает проверяющая программа]]

*Tianbao Xie et al., [OSWorld v1, Figure 2](https://arxiv.org/html/2404.07972v1#S2.F2).
[Оригинальный PNG](https://arxiv.org/html/2404.07972v1/arch_figure_w_config_new.png),
без изменений, [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/).
[Berkeley, лекция 7, слайд 11](https://rdi.berkeley.edu/adv-llm-agents/slides/Multimodal_Agent_caiming.pdf#page=11).*

Слева в конфигурации показана задача обновить бухгалтерскую таблицу.
`Set-up` готовит таблицу и открывает её до запуска агента. После его
остановки `Postprocess` активирует окно Calc, `Getter` получает файл
из виртуальной машины, а `Metrics` сравнивает заданные диапазоны с
эталонным файлом. Снимок окна помогает агенту редактировать таблицу,
но проверка на рисунке читает файл. Если правки остались в памяти
приложения и не попали в извлечённый файл, они не участвуют в сравнении.

Проверка результата допускает разные способы решения. Например, создать
слайд и сохранить его под нужным именем можно несколькими последовательностями
действий. Проверяются файл, его содержимое и расположение, а не совпадение
кликов с единственной эталонной записью. Саму последовательность всё же
полезно анализировать: недопустимые команды, повторы и рискованные действия
объясняют различия между попытками с одинаковым конечным результатом.

В [Table 1 исходной статьи](https://arxiv.org/html/2404.07972v1#S2.SS2.SSS3)
есть задание удалить cookies Amazon. Проверка извлекает cookies из среды
и применяет правило для домена `.amazon.com`. Закрытое окно настроек
или фраза агента «cookies удалены» не подтверждают результат. Для задачи
с таблицей проверяющая программа получает сам файл и сравнивает имена
листов и данные. Это разные способы наблюдать итоговое состояние,
а не один универсальный тест по скриншоту.

Подготовка тоже задаётся по шагам: базовая VM восстанавливается из снимка,
затем конфигурация задачи подготавливает файлы, открывает приложения
и настраивает окна. После попытки возможны отдельные операции сохранения
и извлечения артефактов. Поэтому в отчёте нужно различать действия агента
и действия проверяющей инфраструктуры. В исходной постановке оценка может
быть частичной; не каждый ненулевой балл означает полное выполнение.

Перед новой попыткой виртуальную машину восстанавливают. Иначе агент
может открыть таблицу, уже исправленную предыдущим запуском, и получить
успех без своих действий. Этот случай соответствует чистому снимку среды
в [[00 Учебник/17 Tools и Agents/68 Оценивание агентных систем#agent-eval-coverage|главе об оценивании]].

### Как наблюдение и история влияют на результат OSWorld

В исходном [OSWorld v1, §4.1](https://arxiv.org/html/2404.07972v1#S4.SS1)
сравниваются четыре входа: отфильтрованное дерево доступности, снимок экрана,
их сочетание и SoM. В текстовом варианте модель получает в том числе
координаты элементов; в SoM выбирает номер, который исполнитель отображает
в координаты. В §4.1 описана история из трёх наблюдений и действий,
а [приложение C.1](https://arxiv.org/html/2404.07972v1#A3.SS1) указывает
лимит 15 шагов и 30 минут для базовых агентов. В §2.1 той же версии
для общего цикла приведён пример с 20 шагами. При воспроизведении
конкретного результата нужно брать лимит из его конфигурации.

В [§5.2](https://arxiv.org/html/2404.07972v1#S5.SS2) авторы отдельно
меняют разрешение снимка и длину истории на подмножестве задач.
Для агента со снимками увеличение разрешения обычно помогает, но для SoM
зависимость немонотонна: уменьшение до 768×432 дало лучший результат,
чем исходный размер, а дальнейшее уменьшение ухудшило его. При этом
координаты ответа в варианте со снимком по-прежнему ожидались относительно
1920×1080. Значит, опыт затрагивает и восприятие, и сопоставление
уменьшенного изображения с координатами исполнения.

Более длинная история улучшала результаты SoM, но аналогичного выигрыша
от добавления прошлых снимков в визуальном варианте не получили. Поэтому
«сохранить больше истории» и «помочь модели использовать историю» — разные
требования. Отдельный опыт менял положение и размер окон и добавлял
посторонние приложения. Даже на отобранных 28 сравнительно успешных задачах
результаты ухудшались: агент мог переключить окно, но не развернуть его
перед продолжением. При переносе на другой рабочий стол приходится
проверять восстановление видимой рабочей области, а не только знание
координат кнопок из прежней записи.

## Как AgentTrek исполняет инструкции из руководств

<!-- source_unit_id: meeting-07-slides-agenttrek -->

[AgentTrek](https://arxiv.org/abs/2412.09605) собирает обучающие примеры по
руководствам из интернета. Сначала система находит текст с пошаговой
инструкцией и выделяет из него цель и действия. Затем агент на основе
мультимодальной модели пытается выполнить эти действия в приложении.
Полученные записи оценивает другая мультимодальная модель.

До исполнения работает отдельный конвейер отбора
([§2.1](https://arxiv.org/html/2412.09605v2#S2.SS1)). Из большого корпуса
сначала выбирают тексты с признаками руководства: глаголами действий,
названиями элементов интерфейса и подходящей длиной. GPT-4o mini размечает
часть кандидатов; по этой разметке обучается более дешёвый FastText-фильтр.
Затем текст приводится к схеме с платформой, предпосылками, задачей,
шагами и ожидаемым исходом. Таким способом отделяют поиск руководства
от получения исполняемой демонстрации: список шагов ещё не содержит
текущих экранов и координат.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/external-figure-review-2026-11-10/agenttrek-figure4.png|Отбор руководств AgentTrek. После предварительных фильтров остаётся 68,8 млн записей, после FastText — 54 млн, после дедупликации — 18,8 млн.]]

*Yiheng Xu et al., [AgentTrek v2, Figure 4](https://arxiv.org/html/2412.09605v2#S2.F4).
[Оригинальный PNG](https://arxiv.org/html/2412.09605v2/images/data_flow_v6.png),
без изменений, [CC BY-NC-ND 4.0](https://creativecommons.org/licenses/by-nc-nd/4.0/).*

Читайте числа вдоль верхней линии: 68,8 млн записей осталось после
предварительного отбора, 54 млн после FastText, 18,8 млн после удаления
дубликатов. Правый край, `Web 2.24M`, ещё относится к отбору исходных
текстов. Ни на одном из этих этапов браузерный агент не выполняет
инструкции, поэтому эти числа нельзя принимать за размер корпуса траекторий.

Руководство уменьшает число решений, которые агенту приходится находить
самостоятельно, но не заменяет взаимодействие с приложением. Оно может
описывать старую версию интерфейса или пропускать очевидный для человека
шаг. Агент сопоставляет инструкцию с текущим экраном и записывает фактически
выполненные действия. Поэтому для проверки данных нужны исходное руководство,
полученная последовательность наблюдений и действий и решение оценщика.
По ним можно установить, где агент следовал тексту, а где адаптировал его к
текущему интерфейсу.

На [Figure 5 исходной статьи](https://arxiv.org/html/2412.09605v2#S2.F5)
стрелка `Action` идёт от агента к сайту, а `Observation` возвращается
обратно. В [примере поиска правил возврата, Figure 6](https://arxiv.org/html/2412.09605v2#S2.F6)
одного открытия страницы недостаточно: нужно найти правило для нужной
категории товаров и дать ответ, опираясь на страницу.
При воспроизведении агент получает снимок экрана и дерево доступности,
выполняет команды Playwright, а сборщик сохраняет также DOM, сетевой журнал
и запись действий. Архивируемые данные поэтому шире входа модели.
После исполнения оценщик рассматривает соответствие задаче, полноту
выполнения и при неудаче ищет первый ошибочный шаг. Его оценка остаётся
модельной: сопоставление с людьми в статье даёт 84% совпадений, а не
безошибочную проверку каждой траектории.

В [§2.3](https://arxiv.org/html/2412.09605v2#S2.SS3) из записей получают
два варианта обучающих данных. Для текстового агента наблюдением служит
дерево доступности, действием — команда Playwright. Для визуального агента
используют экран и команды по пиксельным координатам. Исходные действия
нужно отобразить в эту систему координат, а операции вроде выбора
выпадающего пункта могут требовать специального действия. Это изменение
контракта наблюдений и команд, а не простая замена одного имени API другим.

## Какие токены предсказывает модель в TACO

<!-- source_unit_id: meeting-07-slides-taco -->

[TACO](https://arxiv.org/abs/2412.05479v1) рассматривает мультимодальное решение как
чередование текста и исполняемых действий. В Chain-of-Thought-and-Action (CoTA)
модель может распознать текст на изображении, найти объект, оценить глубину,
вырезать фрагмент изображения, выполнить поиск или расчёт. Результат
инструмента возвращается модели, и она продолжает решение. Обучающий пример
содержит не только итоговый ответ, но и выбор момента вызова, аргументы и
последующее использование результата.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/coding-web-computer-use-2026-10/taco-cota-examples.png|Четыре примера CoTA связывают вопрос с вызовом OCR, поиска объектов, вычисления или внешнего источника.]]

*Zixian Ma et al., [TACO v1, Figure 1, p. 2](https://arxiv.org/pdf/2412.05479v1#page=2).
Четыре исходных примера: OCR, поиск объектов, вычисление и обращение
к внешним знаниям. Полный оригинал с английской подписью, CC BY 4.0.*

В верхнем левом примере вопрос относится к цене помидоров на фотографии.
Модель выбирает `OCR(image-0)`. Инструмент возвращает текст с ценниками,
после чего модель связывает название товара с `8,00` и завершает ответом
`8.00`. Она генерирует выбор инструмента и итог, а результат OCR получает
от исполнителя. Если OCR неверно распознал ценник, последующий связный
текст не исправляет это автоматически.

В [§2](https://arxiv.org/html/2412.05479v1#S2) шаг CoTA состоит из текста
рассуждения $t_i$, действия $a_i$ и наблюдения $o_i$. Обучающая функция
потерь применяется к генерируемым $t_i$ и $a_i$; вывод инструмента $o_i$
вставляется в контекст, но не является целевым текстом модели на этом шаге.
В примере с ценником при выборе OCR модель ещё не видит будущий результат
OCR. Он появляется перед формированием ответа. Модель учится выбирать
вызов и использовать полученный результат, а не предсказывать текст
самого результата инструмента. Проверка происхождения наблюдений при
исполнении остаётся обязанностью оболочки: одна маска потерь не запрещает
модели сочинить лишний текст.

Получение данных имеет две ветви
([§§2.1–2.2](https://arxiv.org/html/2412.05479v1#S2.SS1)). В первой GPT-4o
решает существующие вопросы по изображениям, вызывая доступные инструменты.
Проверяются итоговый ответ и возможность разобрать действия как JSON.
При ошибке пример переводится в формат прямого правильного ответа,
а неверная цепочка не сохраняется как успешная CoTA. Во второй ветви
Python-программы заполняют шаблоны по размеченным объектам, отношениям
и оценкам глубины. Это позволяет увеличить долю редко вызываемых
инструментов, но шаблонные рассуждения могут ухудшать другие задачи.

Обозначение *action-useless* в статье относится к источникам данных,
а не к доказанной бесполезности каждого отдельного вызова. Источник получает
эту метку, если доля правильных CoT без действий превышает долю правильных
CoTA более чем на 10 процентных пунктов, либо неправильные CoTA настолько
же чаще правильных. Это эмпирическое правило отбора по результатам
генератора. Например, 50% правильных CoT и 35% правильных CoTA дают разность
15 пунктов и удовлетворяют первому условию; это не устанавливает причину
ошибки в каждом из примеров.

В разных опытах авторы меняют форматы, источники и долю программных данных.
Их основной вариант — 293 тысячи правильных CoTA от GPT-4o из всех
31 источника. Поэтому итог нельзя описывать как универсальный выигрыш
от удаления всех *action-useless* источников или добавления большего числа
программных примеров. Состав данных сравнивается на нескольких наборах:
польза OCR и вычислений не гарантирует улучшения задач, для которых
в доступном наборе нет подходящего инструмента.

Записанное объяснение не обязательно отражает действительную причину выбора
инструмента: оно может быть составлено уже после получения ответа. Поэтому
правильность ответа, выбор инструмента, его аргументы и полезность результата
нужно проверять отдельно. Сравнение вариантов без текста рассуждения или без
действий помогает установить, какие части примера повлияли на качество.

## Как Aguvis учится нажимать на нужное место

<!-- source_unit_id: meeting-07-slides-aguvis -->
<!-- source_unit_id: meeting-07-reading-02-catalogue-record -->

Одна и та же кнопка представлена по-разному в разных средах: идентификатором
DOM на сайте, узлом дерева доступности в настольном приложении или координатами
на снимке экрана. Модель, обученную только на одной из этих форм, нельзя просто
перенести в другую среду. [Aguvis](https://arxiv.org/abs/2412.04454) использует
единое визуальное представление: на вход подаётся снимок экрана, а на выходе
формируется действие, связанное с определённой областью изображения. Общими
для сайтов, настольных и мобильных приложений становятся операции щелчка,
ввода текста и нажатия клавиш; при необходимости к ним добавляются специальные
действия конкретной платформы.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/coding-web-computer-use/m07-p70-aguvis-observation-action.png|По снимку формы маршрута Aguvis выбирает поле To, щелчок по нему и ввод North Station.]]

*Один шаг Aguvis при поиске маршрута из аэропорта Boston Logan до North Station.
Снимок формы связывает общую инструкцию с выбором поля «To» и командами щелчка
и ввода текста. Источник: Caiming Xiong,
[Multimodal Agents — From Perception to Action, слайд 70](https://rdi.berkeley.edu/adv-llm-agents/slides/Multimodal_Agent_caiming.pdf#page=70),
Berkeley Advanced LLM Agents, Spring 2025; схема — Xu et al.,
[Aguvis](https://arxiv.org/abs/2412.04454).*

В примере на рисунке поле отправления уже заполнено. По текущему экрану модель
определяет, что следующим нужно указать пункт назначения. Её ответ содержит
три связанные части: объяснение выбора, инструкцию «нажать поле To и ввести
North Station» и команды для выполнения. Таким образом, выбор следующей
подзадачи и выбор точки на экране принадлежат одному шагу, но проверять их
нужно отдельно. Правильное решение заполнить пункт назначения бесполезно,
если щелчок попал в поле отправления.

Координаты не описывают назначение элемента и меняются при масштабировании,
прокрутке или перестроении страницы. После выполнения команды требуется новый
снимок: иначе следующее действие может опираться на уже устаревшее расположение
элементов. Поэтому агенту необходимы две способности — выбирать действие по
задаче и точно находить место его выполнения на текущем экране.

Предположим, исходный снимок имеет размер 1440×900, а модель получает
его уменьшенную копию 960×600 без обрезки. Центр кнопки `(1170, 210)`
на исходном изображении находится в `(780, 140)` на уменьшенном.
Если исполнитель ожидает координаты исходного снимка, передача `(780, 140)`
попадёт в другую точку. Масштаб нужно обратить; при обрезке или смещении
окна дополнительно учитывается смещение. Это учебный геометрический
пример, а не утверждение о внутренней нормировке Aguvis. Конкретный
исполнитель должен явно задавать, в каких координатах принимает действие.

В Aguvis эти способности обучаются последовательно. Сначала модель учится
находить на снимке экрана элемент, названный в короткой инструкции. Затем она
учится сама выбирать очередное действие по общей задаче, текущему экрану и
истории предыдущих действий.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/coding-web-computer-use/m07-p72-aguvis-two-stage-training.png|Первая стадия учит находить заданный элемент; вторая — выбирать следующее действие по задаче и истории.]]

*Две стадии обучения Aguvis. Слева инструкция «дважды нажать Best Software»
сопоставляется с координатами элемента. Справа модель получает задачу целиком
и предыдущие действия, после чего формирует следующий шаг. Источник: Caiming
Xiong, [Multimodal Agents — From Perception to Action, слайд 72](https://rdi.berkeley.edu/adv-llm-agents/slides/Multimodal_Agent_caiming.pdf#page=72),
Berkeley Advanced LLM Agents, Spring 2025; Xu et al., Aguvis.*

На первой стадии целевой ответ — конкретная команда, например двойной щелчок
по указанному элементу. Ошибка здесь состоит в неверном сопоставлении текста
и изображения: модель может понимать, что нужно нажать ссылку, но выбрать
соседний объект. На второй стадии этого умения уже недостаточно. Модель должна
учесть, что сделано ранее, определить следующий шаг и связать его с командой
для интерфейса. В обучающих примерах между наблюдением и действием записано
словесное обоснование, названное авторами *inner monologue*.

В [§2.5](https://arxiv.org/html/2412.04454v1#S2.SS5) первая стадия
упаковывает несколько пар «инструкция — действие» для одного экрана
в многотуровый пример. Один и тот же снимок не приходится повторно
обрабатывать для каждой кнопки. На второй стадии смешиваются разные
форматы: от короткой инструкции действия до полного описания наблюдения,
рассуждения и команды. Это обучение по демонстрациям, а не оптимизация
награды за каждую живую попытку в приложении.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/coding-web-computer-use/m07-p73-aguvis-data-collection.png|Разметка элементов даёт инструкции и координаты; размеченные траектории дополняются объяснениями.]]

*Подготовка данных для двух стадий. Слева подписи элементов и координаты
превращаются в пары «инструкция — действие». Справа уже размеченные действия
в траекториях дополняются структурированными объяснениями GPT-4o. Источник:
Caiming Xiong, [слайд 73](https://rdi.berkeley.edu/adv-llm-agents/slides/Multimodal_Agent_caiming.pdf#page=73);
Xu et al., [Aguvis](https://arxiv.org/abs/2412.04454).*

Эти данные собираются по-разному. Для первой стадии достаточно снимка экрана,
названия элемента и его координат: из них можно составить инструкции для
щелчка, двойного щелчка или перетаскивания. Для второй нужны последовательности
наблюдений и действий. GPT-4o получает размеченное действие и дописывает
обоснование и более короткую инструкцию к нему. Поэтому такое обоснование —
синтетическая обучающая разметка, а не запись того, как исходный исполнитель
действительно рассуждал.

В опубликованной смеси первая стадия использует свыше миллиона примеров
сопоставления инструкций с элементами интерфейса, вторая — 35 тысяч
многошаговых траекторий со словесными обоснованиями. Их состав приведён ниже.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/coding-web-computer-use/m07-p75-aguvis-data-stages.png|Наборы данных Aguvis сгруппированы по двум стадиям обучения и по платформам.]]

*Состав обучающих данных Aguvis: наборы для нахождения элементов интерфейса
и многошаговые траектории, сгруппированные по платформам. Источник: Caiming
Xiong, [слайд 75](https://rdi.berkeley.edu/adv-llm-agents/slides/Multimodal_Agent_caiming.pdf#page=75);
Aguvis.*

Абляционный эксперимент проверяет вклад каждой стадии: авторы повторяют
оценивание, убирая первую стадию, вторую или обе сразу. Результаты меняются
неодинаково на ScreenSpot, Multimodal-Mind2Web и AndroidControl. Отдельный
вариант без словесных обоснований также ухудшает часть показателей. Это
свидетельство пользы выбранного обучения для конкретной модели и набора
данных, а не доказательство того, что любому агенту необходим текст
«внутреннего рассуждения».

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/coding-web-computer-use/m07-p80-aguvis-ablation.png|Абляция Aguvis показывает результаты без первой стадии, без второй и без словесных обоснований.]]

*Результаты Aguvis при исключении отдельных стадий обучения и словесных
обоснований. Источник: Caiming Xiong,
[слайд 80](https://rdi.berkeley.edu/adv-llm-agents/slides/Multimodal_Agent_caiming.pdf#page=80);
Aguvis.*

## Где искать причину неудачи веб-агента

<!-- source_unit_id: meeting-06-slides-web-agent-synthesis -->

Неудачное завершение задачи может иметь разные причины:

1. **Восприятие:** нужный элемент не попал в наблюдение или был неверно распознан.
2. **Выбор объекта действия:** модель правильно определила, что нужно сделать,
   но указала не тот элемент или координаты.
3. **Планирование:** допустимые по отдельности действия не приводят к цели.
4. **Оценка продолжений:** поиск предпочёл ветвь, которая оказалась тупиковой.
5. **Восстановление состояния:** при возврате к предыдущему шагу восстановилась
   история сообщений, но не фактическое состояние приложения.
6. **Проверка:** оценщик принял сообщение об успехе без подтверждения результата.
7. **Безопасность:** агент выполнил постороннюю инструкцию из содержимого
   страницы или использовал избыточные права инструмента.

Эти ошибки требуют разных исправлений. Увеличение числа вариантов поиска не
поможет, если агент систематически нажимает соседнюю кнопку. Замена оценщика
не восстановит потерянное состояние сайта. Чтобы установить причину
улучшения, компоненты сравнивают по отдельности: меняют представление страницы,
отключают поиск или заменяют модельную оценку программной проверкой результата.
Помимо общей доли успехов, полезно считать ошибки каждого типа.

Содержимое сайта может включать посторонние инструкции. Ограничения на
изменение аккаунта, платежи и отправку сообщений должны проверяться
исполнителем, а не только инструкцией модели. Модель угроз и предоставление
инструментам минимально необходимых прав разобраны в
[[02 Areas/ML & DL/00 Учебник/17 Tools и Agents/72 Безопасность агентных систем|главе 72]].

## Что сохранять для сравнения агентов

Чтобы сравнить две агентные системы, зафиксируйте:

- задачи и точную версию среды;
- процедуру восстановления и проверку начального состояния;
- формат наблюдений и допустимые действия;
- модель, параметры генерации и максимальный бюджет вызовов;
- права инструментов и действия, требующие одобрения человека;
- правило остановки;
- программную проверку результата и ограничения безопасности;
- журнал действий, полученные файлы и стоимость каждой попытки;
- число повторных запусков и способ расчёта неопределённости.

Сравнивайте системы при одной процедуре измерения. Помимо доли решённых
задач, сохраняйте число недопустимых действий и восстановлений, ошибки
выбора элемента, ложные вердикты проверки, стоимость и число шагов.

## Источники

- [Berkeley Advanced LLM Agents, Spring 2025](https://rdi.berkeley.edu/adv-llm-agents/sp25): лекции 5–7 посвящены программирующим агентам, работе в браузере и обучению управлению графическим интерфейсом. Номера использованных слайдов и ссылки на оригинальные рисунки из статей указаны в подписях.
- [SWE-agent](https://arxiv.org/abs/2405.15793), [Agentless](https://arxiv.org/abs/2407.01489), [AutoCodeRover](https://arxiv.org/abs/2404.05427), [Passerine](https://arxiv.org/abs/2501.07531) и [RepairAgent](https://arxiv.org/abs/2403.17134v2): разные способы выбора действий и организации инструментов программирующего агента.
- [EnIGMA, ICML 2025](https://proceedings.mlr.press/v267/abramovich25a.html) и [Big Sleep](https://projectzero.google/2024/10/from-naptime-to-big-sleep.html): инструменты с сохраняемым состоянием, отладка и проверка гипотез при исследовании безопасности.
- [Mind2Web](https://arxiv.org/abs/2306.06070), [WebArena](https://arxiv.org/abs/2307.13854), [VisualWebArena](https://jykoh.com/vwa) и [Tree Search for Language Model Agents](https://arxiv.org/abs/2407.01476): данные для браузерных задач, воспроизводимые сайты, визуальные наблюдения и поиск с возвратом к предыдущим состояниям.
- [InSTA](https://arxiv.org/abs/2502.06776): генерация, исполнение и проверка синтетических браузерных задач.
- [OSWorld](https://arxiv.org/abs/2404.07972), [AgentTrek](https://arxiv.org/abs/2412.09605), [TACO v1](https://arxiv.org/abs/2412.05479v1) и [Aguvis](https://arxiv.org/abs/2412.04454): оценивание в виртуальной машине, сбор траекторий по руководствам, обучение на рассуждениях и действиях, управление интерфейсом по снимкам экрана. Здесь используется первая версия TACO; поздняя v4 того же arXiv ID переименована в LATTE и рассматривает изменённую постановку.
