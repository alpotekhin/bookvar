# Оценивание агентных систем

Агент сообщил, что перенёс семинар на пятницу. В календаре действительно
появилась запись на пятницу, но старая бронь осталась, а приглашение отправлено
дважды. Проверка по финальному сообщению поставит успех. Проверка «есть ли
запись на пятницу» тоже пропустит ошибку. Чтобы оценить выполнение задачи,
нужно заранее определить, какие записи должны появиться, какие исчезнуть
и какие действия недопустимы.

Одна попытка агента включает вызовы модели, действия инструментов, ответы среды
и завершение. Каждый шаг может изменить условия следующего. Результат зависит
от модели, инструкций, доступных инструментов, организации контекста, разрешений,
лимита шагов и исходного состояния. Поэтому оценка относится к этой системе
целиком. Если нужно установить влияние одного компонента, его меняют при
сохранении остальных условий. Пример семинара ниже учебный; устройство
бенчмарков и их проверок разбирается по первичным работам.

## 1. Сначала определяется успешное состояние

Сообщение агента «выполнено» не подтверждает результат действия. Успех
задаётся наблюдаемым состоянием среды:

- нужный тест проходит, а существующие не сломаны;
- бронирование создано с правильными датами и ровно один раз;
- документ содержит необходимые поля и ссылки на источники;
- запрещённые файлы, права и внешние системы не изменены;
- если действие невозможно, агент корректно запросил решение человека.

Проверка конечного состояния (*outcome grader*) читает фактический результат:
записи базы, файлы или ответы проверочного сервиса. Её нельзя заменять просьбой
к той же модели подтвердить, что она всё сделала. Успешный вызов создания брони
тоже недостаточен: после него агент мог удалить бронь или изменить её дату.
Проверяется состояние после завершения попытки, а для необратимых действий —
также достоверный журнал выполнения.

[![Одиночная проверка ответа и многошаговая проверка программирующего агента с инструментами и средой](https://www-cdn.anthropic.com/images/4zrzovbb/website/bd42e7b2f3e9bb5218142796d3ede4816588dec0-4584x2834.png)](https://www-cdn.anthropic.com/images/4zrzovbb/website/bd42e7b2f3e9bb5218142796d3ede4816588dec0-4584x2834.png)

*Слева grader сопоставляет один ответ с ожиданием; справа coding agent получает
инструменты и среду, выполняет многошаговую траекторию, а unit tests проверяют
получившийся MCP-сервер. Источник: Anthropic,
[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents),
схема simple eval и multi-turn eval. Оригинал подключён с сайта автора.*

Условие «забронировать аудиторию» приходится уточнить до проверяемого задания:
для семинара 42 должна существовать ровно одна подтверждённая бронь аудитории
204 на 9 октября 2026 года, 19:00, UTC+3. Если предварительного разрешения
на запись нет, допустимым результатом будет запрос разрешения, а не бронь.
Такой сценарий нужно оформить отдельной задачей: иначе проверяющая программа
будет наказывать агента за соблюдение ограничений.

Следующая функция показывает два независимых критерия для сценария, где
бронирование уже разрешено. Она работает с заранее заданными данными, а не
с настоящим календарём. Поле `authorized` в журнале записывает доверенная
оболочка исполнения; текстовое заявление агента таким свидетельством не служит.

~~~python
def grade_booking(state, trace):
    bookings = [row for row in state["bookings"]
                if row["seminar_id"] == "seminar-42"]
    expected = {"seminar_id": "seminar-42", "room": "204",
                "start": "2026-10-09T19:00:00+03:00", "status": "confirmed"}
    outcome = len(bookings) == 1 and bookings[0] == expected
    policy = all(event["authorized"] for event in trace if event["kind"] == "write")
    return {"outcome": outcome, "policy": policy, "success": outcome and policy}

booking = {"seminar_id": "seminar-42", "room": "204",
           "start": "2026-10-09T19:00:00+03:00", "status": "confirmed"}
allowed = [{"kind": "write", "authorized": True}]
assert grade_booking({"bookings": [booking]}, allowed)["success"]
duplicate = grade_booking({"bookings": [booking, dict(booking)]}, allowed)
assert not duplicate["outcome"]
without_approval = grade_booking({"bookings": [booking]},
                                [{"kind": "write", "authorized": False}])
assert without_approval["outcome"] and not without_approval["success"]
~~~

Проверка существования одной подходящей строки приняла бы обе брони;
проверка только конечного состояния приняла бы запись без разрешения.
Но и приведённая функция покрывает лишь перечисленные условия: она не
проверяет рассылку, сохранность чужих событий, полноту журнала или подлинность
согласия. Для каждого из этих требований нужен свой наблюдаемый признак.
Сам проверяющий код и его исходные данные должны быть недоступны агенту для
изменения. Иначе он сможет получить высокий балл, изменив проверку.

## 2. Исход, траектория и процесс

Конечное состояние не показывает, были ли в процессе запрещённые действия
или лишние расходы. Вместе с результатом сохраняют последовательность
действий и сведения о работе проверяющей системы.

| Уровень | Что проверяется | Пример |
|---|---|---|
| outcome | конечное состояние | скрытые тесты прошли |
| trajectory | последовательность решений | не было запрещённого shell-вызова |
| process | работа инфраструктуры | среда сброшена, лог полон, timeout соблюдён |

Проверка траектории (*trajectory grader*) выявляет повторы, ошибки аргументов,
нарушения прав и лишние действия. При этом допустимых последовательностей
может быть несколько: правильный способ решения не обязан совпадать
с заранее записанным образцом.
Критерии результата и безопасности сохраняют раздельно. Их объединение в
итоговый успех не должно позволять хорошему результату компенсировать
запрещённое действие.

[![Компоненты оценивания: задача, попытка, агент, среда, журнал, исход и проверяющие программы](https://www-cdn.anthropic.com/images/4zrzovbb/website/0205b36f9639fc27f2f6566f73cb56b06f59d555-4584x2580.png)](https://www-cdn.anthropic.com/images/4zrzovbb/website/0205b36f9639fc27f2f6566f73cb56b06f59d555-4584x2580.png)

*Задача, harness, среда, попытка и graders являются отдельными компонентами
оценивания. Источник: Anthropic,
[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents),
схема «Components of evaluations for agents». Оригинал подключён с сайта автора.*

Задача (*task*) задаёт вход и критерии, попытка (*trial*) — одно выполнение
этой задачи. Журнал (*transcript*) хранит полученные сообщения и выполненные
вызовы, а исход (*outcome*) описывает результат в среде. Один журнал можно
проверить несколькими способами: тестом состояния, анализом разрешений,
подсчётом задержки и экспертной рубрикой.

При этом agent harness и evaluation harness выполняют разную работу. Первый
организует действия модели. Второй подготавливает среду, запускает первый,
сохраняет журнал, получает независимые данные для проверки и сводит оценки.
Если подготовка среды не завершилась, агент ещё не получил корректную попытку.
Если же агент сам исчерпал лимит, это уже наблюдаемый результат выполнения,
а не основание убрать неудобный пример из статистики.

## 3. Benchmark состоит из задач и исполняемых сред

[AgentBench](https://arxiv.org/abs/2308.03688) стал одним из первых широких
наборов для LLM-as-Agent: восемь сред включают операционную систему, базу данных,
граф знаний, карточную игру, латеральные задачи, ALFWorld, WebShop и web browsing.
Сравнение показывает, почему одна средняя оценка скрывает профиль способности:
модель может уверенно работать с БД и проваливаться в домашней среде или длинной
покупательской траектории.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/agent-evaluation-2026-10/agentbench-environments-results.png]]

*Профили по восьми средам и агрегированная оценка AgentBench. Источник: Xiao
Liu et al., [AgentBench v2, Figure 1, p. 1](https://arxiv.org/pdf/2308.03688v2#page=1),
технический отчёт октября 2023 года. Оригинал с английской подписью,
crop без постороннего абзаца, CC BY 4.0.*

Среды проверяют разные операции и используют разные оценки. В операционной
системе можно проверять выполнение задания по состоянию файлов, в карточной
игре — долю побед, а в поиске по графу знаний — F1 по найденным сущностям.
Число 0,7 в этих случаях имеет разный смысл. Их нельзя складывать без
явного правила нормировки и взвешивания. У агрегированного результата
нужно сохранять исходные оценки по средам и способ их объединения
([AgentBench, §3](https://arxiv.org/html/2308.03688v2#S3)).

Например, агент нашёл нужные записи базы, но не выполнил требуемую запись.
Частичная метрика прогресса может отметить верный поиск, а двоичная проверка
полного выполнения останется нулевой. Такая дополнительная оценка помогает
разобрать неудачу, но не заменяет критерий завершения. Старые абсолютные
значения на рисунке относятся к версиям моделей, оболочек и данных статьи;
они не являются измерением современных систем.

## 4. SWE-bench: состояние репозитория как grader

[SWE-bench](https://arxiv.org/abs/2310.06770) строит задачу из реального GitHub
issue и версии репозитория. Агент получает описание проблемы, изменяет код, а
оценка запускает закреплённые за задачей тесты. Они проверяют исправление
исходной ошибки и сохранение выбранной существующей функциональности.
Разные патчи могут пройти эти тесты, поэтому совпадения с эталонным diff
не требуется. Однако прохождение выбранных тестов не доказывает отсутствие
любых регрессий во всём репозитории.

### От исправленного issue к задаче

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/agent-evaluation-2026-10/swe-bench-construction.png]]

*Carlos E. Jimenez et al., [SWE-bench v3, Figure 2, p. 2](https://arxiv.org/pdf/2310.06770v3#page=2).
Отбор PR по связи с issue, наличию тестов и исполнимости. Полный оригинал
с английской подписью, crop без перерисовки, CC BY 4.0.*

В исходном наборе берут принятый PR, исправляющий issue и содержащий изменения
тестов. Код разделяют на исправление и тестовую часть. Новые тесты применяют
к версии до исправления, затем проверяют их на исправленной версии. Хотя бы
один тест должен перейти из неуспеха в успех. Если среда не устанавливается
или такого перехода нет, кандидат исключается. Иначе неизвестно, измеряет ли
он способность исправить описанную ошибку. Этот отбор в статье дал 2294 задачи
из 12 Python-репозиториев; это характеристики того набора, не нынешнего
лидерборда.

### Как оценивается новый патч

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/agent-evaluation-2026-10/swe-bench-evaluation.png]]

*Carlos E. Jimenez et al., [SWE-bench v3, Figure 8, p. 20](https://arxiv.org/pdf/2310.06770v3#page=20).
Модель получает репозиторий и условие, а проверяющая система применяет патч
и тесты и сохраняет результаты. Оригинальный рисунок с подписью, CC BY 4.0.*

Для проверки предсказанного патча восстанавливают исходную версию репозитория,
готовят окружение и применяют тестовую часть эталонного PR. Затем применяют
предсказанное исправление и запускают тестовый сценарий. Результаты разбираются
по идентификаторам тестов. В Appendix A.4 требуются две группы:

- `FAIL_TO_PASS` — тесты, которые падали до эталонного исправления;
- `PASS_TO_PASS` — тесты, которые проходили и до, и после него.

Все обязательные тесты обеих групп должны присутствовать в журнале и пройти.
Отсутствующий тест не считается успешным. Например, патч может исправить
обработку пустого пароля, но сломать обычный вход: первая группа пройдёт,
вторая — нет. Если же тесты вообще не затрагивают другой сломанный режим,
бенчмарк его не обнаружит. Поэтому статус `resolved` означает принятие
данной проверкой, а не доказанную корректность программы на всех входах.

Результат зависит и от оболочки вокруг модели. Доступные команды, способ
просмотра файлов, лимит шагов, сохранение истории, возможность запускать тесты
и формат ошибок меняют информацию, на основании которой агент действует.
[SWE-agent](https://arxiv.org/abs/2405.15793) исследует этот слой как
Agent–Computer Interface. Устройство интерфейса и его проверки разобраны
в [[02 Areas/ML & DL/00 Учебник/17 Tools и Agents/66 Agent harness и context engineering|главе об исполняющей оболочке]].

Для воспроизводимого отчёта сохраняют точный снимок модели и параметры
декодирования; ревизию harness, инструкций, схем инструментов и политики
контекста; хэш образа среды, сетевой режим и правило сброса; ревизию набора
задач и проверяющей программы; предел шагов и времени. Маркетингового имени
модели и названия benchmark недостаточно для повторения.

## 5. Интерактивный пользователь меняет задачу

В задачах поддержки клиентов среда включает человека, который отвечает на
уточнения и может менять запрос. [τ-bench](https://arxiv.org/abs/2406.12045)
использует симулятор пользователя и доменные инструменты для авиакомпании
и розничной торговли. Агенту доступна политика предметной области, а скрытая
инструкция симулятора задаёт личность, намерение и предпочтения пользователя.
В исходном опыте текст пользователя генерирует gpt-4-0613. Симулятор видит
разговор с агентом, но не историю обращений агента к инструментам. Поэтому
агент должен сам задать уточняющие вопросы и получить недостающие сведения.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/agent-evaluation-2026-10/tau-bench-task-components.png]]

*Shunyu Yao et al., [τ-bench v1, Figure 2, p. 4](https://arxiv.org/pdf/2406.12045v1#page=4).
Четыре компонента одной задачи: база, API, политика и скрытая аннотация.
Оригинальный рисунок с английскими подписями, CC BY 4.0. Скрытая часть
используется симулятором и оцениванием, а не передаётся решающему агенту.*

В примере нужно выбрать между возвратом бутылки и обменом других товаров,
если политика не позволяет выполнить оба действия с заказом. Инструкция
уточняет предпочтение пользователя: выбрать вариант с большей экономией,
но сообщить обе суммы. В аннотации указан ожидаемый возврат и строки
`54.04`, `41.64`, которые должны присутствовать в ответе. Во время выполнения
агент не получает эти ответы заранее: их нужно получить из данных и правил.

Награда исходного τ-bench имеет вид $r=r_{\text{action}}r_{\text{output}}$.
Первая часть сравнивает конечную базу с ожидаемой, вторая проверяет наличие
нужной информации в ответах. В §3 авторы прямо отмечают, что $r=1$ может
быть недостаточно для соблюдения всей политики: возврат без явного согласия
пользователя способен дать правильное состояние базы, но нарушает правило.
Поэтому этот бенчмарк нельзя описывать как исчерпывающую автоматическую
проверку всех ограничений. Отдельная проверка согласия в начале главы как раз
добавляет условие, которого одного сравнения конечных баз не обеспечивает.

Для симулятора пользователя фиксируют модель, инструкцию и параметры
генерации, а также проверяют, не подсказывает ли он решение. Полезны сценарии
с недостающей информацией,
противоречивой просьбой, попыткой обойти политику и изменением решения после
частично выполненного действия.

## 6. Срок жизни benchmark и несмещённый pass@k

<!-- source_unit_id: meeting-05-slides-coding-agent-evaluation -->

Набор задач не остаётся одинаково полезным навсегда. HumanEval и MBPP в 2021
году находились в удачной точке: задачи были достаточно трудными, решения ещё
не успели широко попасть в обучающие корпуса, а автоматические тесты позволяли
быстро сравнивать модели. В лекции Charles Sutton 2025 года обсуждаются причины,
по которым эти наборы перестают различать сильные системы: высокие баллы,
распространение задач и решений по сети, недостаточное покрытие тестами.
Потолочный эффект возникает, когда несколько систем получают почти одинаковый
высокий результат и новые улучшения уже трудно увидеть. Это критика
пригодности набора для конкретного этапа исследований, а не утверждение,
что любая модель решает все его задачи.

SWE-bench повысил реалистичность: вместо короткой функции агент исправляет
настоящий issue в существующем репозитории. SWE-bench Verified дополнительно
отфильтровал 500 задач вручную, удаляя недоопределённые постановки и случаи с
неподходящими тестами. Проверки всё ещё могут пропустить ошибку или отвергнуть
правильный вариант. Набор языков и проектов ограничен, а многократный подбор
конфигурации по публичной таблице результатов и утечки меняют смысл оценки.
Вместе с результатом фиксируют версию и дату оценки, проверяют насыщение
и попадание задач в обучение. Для новых решений сохраняют обновляемый или
закрытый временной срез. См.
[Charles Sutton, Berkeley Advanced LLM Agents, лекция 5, pp. 5–14](https://rdi.berkeley.edu/adv-llm-agents/sp25)
и [описание SWE-bench Verified](https://openai.com/index/introducing-swe-bench-verified/).

Стохастическая генерация требует аккуратной метрики. Пусть из $n$ независимо
сгенерированных программ тесты прошли $c$. Вероятность того, что среди $k$
выбранных без возвращения кандидатов окажется хотя бы один правильный,
оценивается формулой из работы о Codex:

$$
\widehat{\operatorname{pass@k}}
= 1-\frac{\binom{n-c}{k}}{\binom{n}{k}}, \qquad n\ge k.
$$

Доля $c/n$ является естественной оценкой pass@1, но подстановка её в
$1-(1-c/n)^k$ даёт смещённую оценку pass@k, особенно при небольшом $n$.
Комбинаторная формула считает долю наборов размера $k$, состоящих только из
неуспешных программ, и вычитает её из единицы. Она не превращает pass@k в
продуктовую метрику автоматически: если система не умеет распознать правильный
кандидат среди $k$, возможность однажды сгенерировать его ещё не означает, что
пользователь его получит.

В учебной выборке $n=10$, $c=2$, $k=3$ имеется $\binom83=56$ полностью
неуспешных троек из $\binom{10}3=120$. Оценка равна
$1-56/120\approx0{,}5333$. Подстановка $\hat p=0{,}2$ даёт
$1-0{,}8^3=0{,}488$. Разница относится к оцениванию по конечной выборке:
она не означает, что истинная вероятность успеха изменилась. Вывод
несмещённой оценки дан в
[Chen et al., Appendix A](https://arxiv.org/html/2107.03374v2#A1).

Несмещённость следует из способа получения исходных кандидатов.
Если $n$ ответов получены независимо одним и тем же способом,
любой заранее выбранный набор из $k$ их индексов имеет ту же вероятность
успеха, что и новые $k$ попыток. Усреднение по всем наборам индексов сохраняет
это математическое ожидание. После наблюдения конкретных $c$ успешных ответов
оно записывается комбинаторной формулой выше. Если же следующие попытки
обучаются на ошибках предыдущих или получают обратную связь, распределение
меняется. Для такого адаптивного процесса нельзя без обоснования использовать
эту оценку по независимым кандидатам.

Ниже исходная функция из
[openai/human-eval](https://github.com/openai/human-eval/blob/b9453e8f1865df0a0057a1383767caa400acfbcf/human_eval/evaluation.py#L13),
ревизия `b9453e8f1865df0a0057a1383767caa400acfbcf`, без изменений.
OpenAI, [MIT license](/licenses/human-eval-b9453e8f-MIT.txt).
Импорты добавлены, чтобы пример запускался отдельно. Функция предполагает
корректные входы: целые $0\le c\le n$ и $1\le k\le n$.

~~~python
import itertools
from typing import List, Union
import numpy as np

def estimate_pass_at_k(
    num_samples: Union[int, List[int], np.ndarray],
    num_correct: Union[List[int], np.ndarray],
    k: int
) -> np.ndarray:
    """
    Estimates pass@k of each problem and returns them in an array.
    """

    def estimator(n: int, c: int, k: int) -> float:
        """
        Calculates 1 - comb(n - c, k) / comb(n, k).
        """
        if n - c < k:
            return 1.0
        return 1.0 - np.prod(1.0 - k / np.arange(n - c + 1, n + 1))

    if isinstance(num_samples, int):
        num_samples_it = itertools.repeat(num_samples, len(num_correct))
    else:
        assert len(num_samples) == len(num_correct)
        num_samples_it = iter(num_samples)

    return np.array([estimator(int(n), int(c), k) for n, c in zip(num_samples_it, num_correct)])

assert np.isclose(estimate_pass_at_k(10, [2], 3)[0], 8/15)
~~~

Вычисление через произведение избегает прямого построения огромных
биномиальных коэффициентов. Функция возвращает отдельное число для каждой
задачи; среднее по набору считают после этого, а не по общему числу правильных
кандидатов из разных задач.

## 7. Несколько запусков вместо одной траектории

Даже при одинаковом входе случайная генерация, сеть и состояние инструментов
дают разные траектории. По каждой задаче сохраняют результат каждого повтора,
чтобы разделить различия трудности задач и случайность их выполнения.

Следует публиковать:

- число уникальных задач и число повторов;
- pass@1 и вероятность хотя бы одного успеха из $k$ попыток;
- доверительный интервал, построенный на уровне независимой задачи;
- медиану и хвост распределения стоимости, шагов и задержки;
- долю задач, где исход нестабилен между повторами.

`pass@k` измеряет возможность получить хотя бы один принимаемый проверкой
кандидат за $k$ попыток. Это полезная исследовательская метрика и для системы,
которая пока не умеет выбирать лучший ответ. Для оценки доставленного
пользователю результата отдельно измеряют *selected-answer success* — долю
правильных ответов после выбора. При одной и той же проверке идеальный выбор
ограничен сверху долей запросов с хотя бы одним принятым кандидатом.
Ошибки самой проверки при этом сохраняются: принятый ею ответ может быть
содержательно неверным.

[![Вероятность хотя бы одного успеха растёт с числом попыток, вероятность успеха всех попыток падает](https://www-cdn.anthropic.com/images/4zrzovbb/website/3ddac5be07a0773922ec9df06afec55922f8194a-4584x2580.png)](https://www-cdn.anthropic.com/images/4zrzovbb/website/3ddac5be07a0773922ec9df06afec55922f8194a-4584x2580.png)

*При росте числа попыток вероятность хотя бы одного успеха `pass@k` растёт, а
вероятность успеха всех попыток `pass^k` падает. Источник: Anthropic,
[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents),
схема «pass@k and pass^k diverge». Оригинал подключён с сайта автора.*

Для одной задачи с постоянной вероятностью успеха $p$ и независимыми попытками
вероятности равны $1-(1-p)^k$ и $p^k$. Например, при $p=0{,}75$ три попытки
дают хотя бы один успех с вероятностью 0,984375, а три успеха подряд — лишь
с вероятностью 0,421875. Первая величина описывает возможность найти решение
за несколько попыток; вторая — повторяемость выполнения той же задачи.

Для конечной выборки независимых попыток оценка из τ-bench равна

$$
\widehat{\operatorname{pass}^{k}}
=\frac{\binom{c}{k}}{\binom{n}{k}},\qquad n\ge k.
$$

В выборке $n=10$, $c=2$, $k=3$ эта оценка равна нулю: из двух успешных
попыток невозможно выбрать три. Это не доказывает, что истинная вероятность
трёх будущих успехов равна нулю. Новых наблюдений пока недостаточно, чтобы
увидеть такую тройку. Правила $\binom{c}{k}=0$ при $c<k$ и
$\binom{n-c}{k}=0$ при $n-c<k$ задают граничные случаи обеих оценок.

Показатели вычисляют по каждой задаче, затем усредняют с заранее выбранными
весами. Пусть половина задач всегда решается, а другая половина никогда.
Тогда средние pass@1, pass@3 и $\operatorname{pass}^{3}$ равны 0,5:
повторения не помогают второй половине и не мешают первой. Если вместо этого
подставить общее $p=0{,}5$ в формулы одной задачи, получатся 0,875 и 0,125.
Такое вычисление ошибочно смешивает трудность разных задач со случайностью
повторного выполнения одной и той же задачи.

### Что действительно получает пользователь

Наличие правильного кандидата и его выбор проверяются отдельно. Допустим,
для десяти запросов система сгенерировала по три ответа. Для восьми запросов
хотя бы один ответ принят проверкой, но выбирающая модель нашла его только
в пяти случаях. Наблюдаемая доля запросов с правильным кандидатом — 8/10,
а доля выбранных правильных ответов — 5/10. Именно второе число характеризует
доставленный результат при этом способе выбора. Это учебный подсчёт, не
эксперимент с конкретной моделью.

Учитывается и цена поиска. Попытка, которая завершилась неудачно, всё равно
израсходовала токены и время. При расчёте стоимости одного успеха общие
расходы всех попыток делят на число успешных результатов. В качестве
сопоставимого бюджета можно фиксировать число токенов, стоимость, время
или число действий; одинаковые три попытки не обязательно стоят одинаково.
Для последовательного исправления после обратной связи следует оценивать
весь процесс, а не объявлять его тремя независимыми кандидатами.

## 8. Парное сравнение модели и исполняющей оболочки

Чтобы сравнить две системы, их запускают на одинаковых задачах и по возможности
одинаковых снимках среды. Анализируют пары: обе успешны, обе неуспешны, только A
успешна, только B успешна. Именно две последние группы показывают регрессии и
исправления; их следует просматривать вручную и разбивать по причинам.

Предположим, на четырёх задачах A получила результаты `[1, 1, 0, 0]`,
а B — `[1, 0, 1, 1]`. Средние равны 0,5 и 0,75, разность — 0,25.
Но за этой разностью стоят два исправления и одна регрессия. Если показать
лишь два средних, регрессия исчезнет из отчёта. Парные разности по задачам
равны `[0, −1, 1, 1]`; они сохраняют информацию о том, где системы сравнивались.

Чтобы оценить неопределённость на новых задачах из того же распределения,
при bootstrap переотбирают задачи вместе со всеми относящимися к ним
повторами и результатами A/B. Нельзя независимо перемешать попытки из одной
задачи и объявить их новыми задачами. Сто повторов на четырёх задачах
помогают оценить нестабильность этих четырёх задач, но не дают ста разных
примеров для вывода о новых задачах.

Для маленького примера можно перебрать все $4^4=256$ bootstrap-выборок
по четыре задачи с возвращением, не используя генератор случайных чисел:

~~~python
from itertools import product
import numpy as np

a = np.array([1, 1, 0, 0])
b = np.array([1, 0, 1, 1])
difference = b - a
resampled_means = np.array([np.mean(sample)
                           for sample in product(difference.tolist(), repeat=4)])
interval = np.quantile(resampled_means, [0.025, 0.975])
assert np.isclose(difference.mean(), 0.25)
assert len(resampled_means) == 256
assert np.allclose(interval, [-0.5, 1.0])
~~~

Получился широкий percentile-bootstrap интервал от −0,5 до 1. Четырёх задач
недостаточно для уверенного вывода о преимуществе B, несмотря на разность
в 25 процентных пунктов в этой выборке. На столь малом наборе сам bootstrap
тоже не обеспечивает точного заявленного покрытия; пример показывает способ
переотбора, а не заменяет полноценный статистический анализ. Если задачи
сгруппированы по репозиторию, пользователю или сценарию, единицей переотбора
может потребоваться сделать эту группу.

Чтобы установить влияние компонента оболочки, меняют только его: например,
схему инструмента, сжатие контекста, память или правило повторных попыток.
Если одновременно заменить модель, инструкцию и лимит шагов, результат
нельзя приписать ни одному изменению. Для дорогостоящих агентных запусков
допустимы последовательные эксперименты с накоплением данных. Правило
остановки задают заранее и учитывают при статистическом анализе: обычный
интервал для фиксированного размера выборки нельзя автоматически применять
после остановки при первом удобном результате.

## 9. Модель-судья

Модель-судья (*LLM-as-a-judge*) получает ответ или артефакт и рубрику, затем
выдаёт оценку. Она позволяет проверять свойства, для которых трудно написать
полный тест: например, полноту объяснения или соответствие отчёта требованиям.
Однако её решение также требует проверки. В
[Zheng et al., §§3.3–3.4](https://arxiv.org/html/2306.05685v4#S3.SS3)
показаны зависимость оценки от порядка ответов и предпочтение более длинной
версии без новой информации. Предпочтение собственных ответов авторы
рассматривают, но не устанавливают однозначно. Эти наблюдения относятся
к исследованным моделям и протоколу статьи, а не задают одинаковую величину
смещения для любого будущего судьи.

Для парного сравнения можно предъявить ответы дважды, поменяв порядок.
Если судья каждый раз выбирает первый ответ, победитель не определён.
В статье такой случай консервативно считается ничьей. Случайное
распределение позиций уменьшает систематическое преимущество на большом
наборе, но не исправляет конкретное ошибочное решение. Совпадение оценок
при перестановке тоже не доказывает их правильность.

Для агентных траекторий добавляется ограничение контекста: полный журнал
может не помещаться во вход судьи. Выбор выдержек становится частью
проверяющей системы, которую тоже нужно оценивать.

Протокол проверки включает следующие условия:

1. исполнимые проверки и состояние среды используются везде, где возможно;
2. рубрика разбивается на наблюдаемые критерии;
3. имена систем скрываются, порядок пары случайно меняется;
4. оценки судьи сопоставляются с человеческой разметкой;
5. расхождения и пограничные случаи передаются человеку;
6. версия судьи, инструкция и входные выдержки сохраняются вместе с оценкой.

### PaperBench: рубрика с проверяемыми частями

[PaperBench](https://arxiv.org/html/2504.01848v3#S2) предлагает реплицировать
результаты научной статьи. Код, его выполнение и совпадение результатов
оцениваются раздельно. В полном протоколе репозиторий агента переносят
в новую среду и запускают `reproduce.sh`. Записанный агентом график или
сообщение «эксперимент выполнен» не заменяют этот шаг. Критерий типа
*Code Development* может дать частичный балл за реализацию; *Execution*
требует свидетельства выполнения; *Result Match* — полученного результата.
Оценку облегчённого Code-Dev нельзя называть результатом полной репликации.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/agent-evaluation-2026-10/paperbench-rubric-tree.png]]

*Giulio Starace et al., [PaperBench v3, Figure 2, p. 3](https://arxiv.org/pdf/2504.01848v3#page=3).
В листьях двоичные проверки, в промежуточных узлах взвешенные средние.
Полный оригинальный рисунок с английской подписью, crop, CC BY 4.0.*

Веса задаются относительно соседних требований, а итог вычисляется снизу
вверх. В нижнем фрагменте рисунка листья 0, 1, 1 имеют веса 1, 2, 1:
их родитель получает $(0+2+1)/4=0{,}75$. Выше узел с этим результатом
и лист 0 имеют веса 1 и 2, что даёт $0{,}75/3=0{,}25$. После такого же
вычисления остальных ветвей дети корня получают 1, 0,5 и 0,4 с весами
1, 3 и 2. Корневая оценка равна $(1+3\cdot0{,}5+2\cdot0{,}4)/6=0{,}55$.
Это точный разбор чисел исходного рисунка, а не результат запуска агента.

~~~python
from fractions import Fraction

def weighted_score(children):
    return sum(weight * Fraction(score) for weight, score in children) / sum(
        weight for weight, _ in children)

score_075 = weighted_score([(1, 0), (2, 1), (1, 1)])
score_025 = weighted_score([(2, 0), (1, score_075)])
score_050_leaf = weighted_score([(1, 1), (1, 0)])
score_050 = weighted_score([(1, 1), (2, score_025), (1, score_050_leaf)])
score_040 = weighted_score([(2, 1), (3, 0)])
replication_score = weighted_score([(1, 1), (3, score_050), (2, score_040)])
assert replication_score == Fraction(11, 20)
~~~

Среднее по всем листьям без учёта дерева дало бы другую оценку. Веса отражают
важность частей работы, а не число пунктов, на которое редактор раздробил
каждую часть. Для применения рубрики нужно сохранять и критерии, и веса,
и правила свёртки.

### Как проверять самого судью

В PaperBench SimpleJudge оценивает каждый лист отдельно. Поскольку весь
репозиторий не помещается во вход, судья предварительно ранжирует файлы и
читает десять наиболее подходящих. Если нужный файл не попал в этот контекст,
ошибочная оценка может возникнуть до собственно рассуждения о критерии.
В протоколе [JudgeEval, §4.2](https://arxiv.org/html/2504.01848v3#S4.SS2)
решения автоматического судьи сопоставляются с человеческими оценками
отдельных листьев; показатели агрегируются по статьям. Это отдельное испытание
судьи, а не оценка агента, написавшего репозиторий.

Рассмотрим учебную калибровочную выборку из 50 результатов:

| Решение человека | Судья принял | Судья отклонил |
|---|---:|---:|
| Корректно | 18 | 2 |
| Некорректно | 6 | 24 |

Общая точность судьи равна $(18+24)/50=0{,}84$, но среди 24 принятых
результатов верны лишь 18: precision равен 0,75. Из 20 правильных результатов
судья нашёл 18: recall равен 0,9. Одного числа accuracy недостаточно, если
ложное принятие и ложное отклонение имеют разную цену. Матрицу ошибок
проверяют также по типам критериев: судья может хорошо находить наличие кода,
но плохо отличать воспроизведённый эксперимент от правдоподобного отчёта.

Калибровочная выборка должна включать полные и частичные решения, верные
варианты, отличающиеся от эталона, и правдоподобные ошибки. Имена систем
и порядок предъявления меняют так, чтобы судья не мог использовать их как
подсказку. Если вход обрезан или доказательств не хватает, нужен отдельный
исход «не удалось оценить», а не вынужденное уверенное решение.


## 10. Безопасность оценивается как инвариант

Средняя доля успешных задач не компенсирует редкое критическое нарушение.
Отдельно проверяются:

- выполнение недоверенной инструкции из результата инструмента;
- чтение или вывод секрета;
- выход за разрешённый путь и обход через symlink;
- необратимое действие без подтверждения;
- повтор побочного эффекта после тайм-аута;
- отравление долговременной памяти;
- использование обратной связи проверяющей программы, недоступной в рабочей системе.

Нулевой допуск к действию задаётся контролем разрешений, изоляцией и проверкой
подтверждения перед выполнением. Нулевое число нарушений в выборке не
доказывает нулевую вероятность нарушения. Пусть в $N$ независимых испытаниях
из одного фиксированного распределения не наблюдалось ни одного нарушения.
При постоянной вероятности нарушения $p$ вероятность такого результата равна
$(1-p)^N$. Односторонняя точная 95%-ная верхняя граница для $p$ находится из
уравнения $(1-p)^N=0{,}05$:

$$
p_{\mathrm{upper}}=1-0{,}05^{1/N}.
$$

Для 100 испытаний граница составляет примерно 2,95%. Чтобы при тех же
предпосылках получить границу не выше 1%, нужны как минимум 299 испытаний
без нарушения. Это расчёт для двоичного события в заданном распределении,
не гарантия безопасности при любой атаке. Повторы одного сценария могут
оказаться зависимыми, а отсутствующий в наборе тип атаки вообще не
проверяется. Поэтому испытания дополняют защитой в самой среде исполнения;
статистическая оценка не заменяет запрет опасного действия.

## 11. Contamination и benchmark overfitting

Популярные задачи, issues и решения могут попасть в предобучение, SFT,
синтетические траектории или системные инструкции. Тогда исправление знакомой
задачи может опираться на запомненный патч. Точное совпадение строк обнаруживает
лишь часть утечки: названия функций можно заменить, сохранив структуру решения.
Перефразировка условия тоже не делает известную задачу новой. Более сильная
проверка использует закрытые репозитории или задачи, созданные после даты
обучения; дату и доступность данных при этом нужно знать, а не предполагать.

Оболочка также может переобучиться на бенчмарк, даже если веса модели
не менялись. Например, разработчик многократно просматривает неудачи на одном
наборе и подбирает команды поиска, инструкции и лимиты под эти случаи.
Набор становится данными разработки. Для оценки новой версии нужен отложенный
набор, который не использовался при таком подборе. Публичную таблицу
результатов дополняют обновляемой выборкой и реальными задачами будущего
применения: балл на открытых Python-проектах сам по себе не оценивает работу
с закрытым монорепозиторием на другом языке.

## 12. Сопоставимость тестовой и рабочей среды

Для переноса результата в рабочую систему сопоставляют версии зависимостей,
права, сеть, скорость инструментов, данные, схемы API, правила подтверждений
и доступный контекст. Если испытание даёт агенту `search_code`, которого нет
в продукте, измеренная способность искать код не характеризует продуктовый
вариант. Задержка инструмента тоже меняет условия: агент может исчерпать
временной лимит при том же числе действий.

Каждый запуск начинается с чистого снимка состояния. Иначе второй запуск может найти
файл или запись, созданные первым. Инфраструктурные сбои отмечаются отдельно
от ошибок агента, а правило включения в метрику задаётся до запуска.

Например, запланировано 100 испытаний; в двух среда не подготовилась,
а среди остальных 98 получено 70 успехов. Условная доля успеха при корректно
подготовленной среде равна $70/98\approx71{,}43\%$. Доля успеха среди всех
запланированных попыток равна $70/100=70\%$. Оба числа имеют смысл, но
измеряют разное. В отчёте сохраняют и знаменатель, и причины двух сбоев.
Нельзя после просмотра результатов исключать неудачи агента под названием
«ошибка среды».

Неверный аргумент инструмента относится к действиям агента. Недоступность
сервиса до начала задачи относится к подготовке среды. Если запрос записи
завершился тайм-аутом, исход может быть неизвестен: сервис успел записать
данные, но ответ потерялся. Повтор без проверки способен создать дубликат.
Такой случай требует чтения состояния или идемпотентного ключа, как в
[[02 Areas/ML & DL/00 Учебник/17 Tools и Agents/65 Tool use — от вызова функции к действию|главе об инструментах]].

## 13. Срезы и классификация ошибок

Агрегированную метрику разбивают по числу требуемых шагов, типу инструмента,
необходимости восстановления, языку, длине контекста, правам и виду конечной
проверки. Затем выборку неуспехов кодируют по месту возникновения:

| Этап | Типичный провал |
|---|---|
| понимание | неверно определено требуемое состояние |
| планирование | пропущена зависимость или проверка |
| вызов инструмента | выбран не тот инструмент или аргумент |
| наблюдение | проигнорирована ошибка или усечение |
| контекст | важный факт потерян после сжатия истории |
| память | извлечена устаревшая или чужая запись |
| исполнение | отказ в доступе, тайм-аут, частичное изменение состояния |
| остановка | преждевременное «готово» или бесконечный цикл |
| оценивание | ложное принятие или отклонение проверяющей программой |

У одной попытки может быть несколько связанных ошибок. Агент потерял
подтверждение после сжатия истории, повторил запись и создал дубликат.
В разметке сохраняют первую причину и последующие последствия, а также
ссылку на шаг журнала, подтверждающий диагноз. Проверка новой версии схемы
инструмента на задачах с неверными аргументами и на отложенных задачах
покажет, исправляет ли она выбранный класс ошибок без новых регрессий.

## 14. Минимальный отчёт

Для повторения измерения сохраняют:

1. Версию задач и их исходных состояний, критерии успеха, ограничения
   безопасности и обработку частичного выполнения.
2. Снимок модели, параметры генерации, ревизию оболочки, инструкции,
   схемы инструментов, правила памяти и лимиты. Для среды — образ,
   зависимости, сетевые разрешения и процедуру сброса.
3. Число уникальных задач, повторов и запланированных запусков; успехи,
   неуспехи, инфраструктурные сбои и неоценённые случаи. Для `pass@k` —
   число кандидатов, проверку и способ выбора ответа.
4. Журналы действий и проверок, итоговые артефакты, стоимость всех попыток
   и правила удаления секретов из сохраняемых данных. Для LLM-судьи —
   входные выдержки, ответы и результат калибровки.
5. Парные изменения относительно исходной системы, неопределённость оценки,
   результаты по типам задач и разбор нарушений. При повторном выборе
   конфигурации — отдельную отложенную проверку.

Порог приёмки задаётся отдельно от описания измерения. Например, можно
потребовать сохранения результатов на регрессионном наборе, ограничения
стоимости и отсутствия известных нарушений разрешений. Даже успешная
приёмка относится к проверенным задачам, бюджету и версии среды; изменение
инструментов или прав требует новой проверки.
