# 70. Формальные доказательства и математические агенты

Пусть известно, что выполнены два утверждения: `P` и `Q`. Чтобы доказать
`Q ∧ P`, достаточно взять доказательство `Q`, затем доказательство `P`
и объединить их. В Lean эта перестановка записывается так:

```lean
theorem swap_and (P Q : Prop) (h : P ∧ Q) : Q ∧ P := by
  constructor
  · exact h.right
  · exact h.left
```

Тактика `constructor` создаёт две подцели. Первая требует доказать `Q`;
`h.right` извлекает его из гипотезы `h`. Вторая требует `P` и закрывается
через `h.left`. Ошибка, например `exact h.left` в первой ветви, обнаружится
сразу: предъявлено доказательство не того утверждения.

Математический агент строит такие последовательности действий для задач,
в которых подходящая лемма или промежуточное утверждение заранее неизвестны.
Модель предлагает шаги, система доказательств исполняет их и возвращает
состояния или ошибки. Поиск перебирает альтернативы. Законченное
доказательство проверяется относительно точно заданных определений и аксиом.
Это позволяет обнаружить неверный формальный шаг, но само по себе
не устанавливает, правильно ли записана исходная человеческая задача.

<span id="часть-i-формальная-среда-и-базовый-контракт"></span>
## Часть I. Формальная среда: состояния, действия и доказательства

### Неформальное решение, формальная теорема и проверяемое доказательство

В математической статье автор может сослаться на рисунок, опустить
алгебраическое преобразование или воспользоваться соглашением о обозначениях.
В формальной записи должны быть определены:

1. типы объектов и все предпосылки;
2. точное утверждение;
3. определения, леммы и область их видимости;
4. доказательство, которое после разрешения обозначений и исполнения тактик
   превращается в терм для проверки ядром.

Автоформализация (*autoformalization*) переводит неформальное утверждение
или доказательство на формальный язык. Автоматическое доказательство
(*theorem proving*) начинает с уже записанного формального утверждения.
У этих задач разные ошибки: в первом случае можно потерять условие,
во втором — не найти доказательство верной теоремы. Даже у системы,
выполняющей оба этапа, нужно сохранять их результаты раздельно.

Lean — язык программирования и интерактивная система доказательств.
Библиотека Mathlib содержит определения и теоремы, которыми можно пользоваться
при доказательстве. Например, для простого числа нужны определение простоты
и леммы о делимости. Знакомый человеку результат может отсутствовать
в импортированном модуле или иметь другую формулировку. Тогда агенту нужно
найти эквивалентную лемму либо доказать вспомогательный факт.

<span id="один-шаг-lean-proof-state-tactic-kernel-check"></span>
### Один шаг Lean: состояние доказательства, тактика и проверка ядром

Рассмотрим состояние доказательства:

```text
n : ℕ
⊢ ∃ p, n ≤ p ∧ Nat.Prime p
```

Перед `⊢` записан локальный контекст, здесь натуральное число `n`.
После знака стоит цель: найти простое `p`, не меньшее `n`. Это снимок
состояния, а не самостоятельный Lean-файл. Для его воспроизведения нужны
импорты Mathlib и соответствующее определение `Nat.Prime`.

Тактика (*tactic*) — программа, строящая часть доказательства.
Она может закрыть цель, создать несколько подцелей или завершиться ошибкой.
Для приведённой задачи математический план состоит в выборе простого
делителя числа `n! + 1`: ни одно простое число, не превосходящее `n`,
не может делить одновременно `n!` и `n! + 1`. Формальный поиск должен
выразить этот план через доступные определения и леммы о факториале,
наименьшем простом делителе и делимости разности.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/formal-math/m08-p79.png]]

*Thomas Hubert, [Berkeley Meeting 8, физическая стр. 79](https://rdi.berkeley.edu/adv-llm-agents/slides/alphaproof.pdf#page=79). Предложение модели вводит делитель `n! + 1`; Lean вычисляет, какие обязательства остаются после этого шага.*

Полный цикл одного шага таков:

1. агент записывает локальный контекст, цель и нужную часть истории в запрос;
2. поисковый модуль добавляет доступные определения и леммы;
3. модель предлагает тактику или готовый терм;
4. парсер проверяет формат ответа;
5. Lean выполняет действие и возвращает новые цели либо диагностическое сообщение;
6. ядро проверяет законченный терм относительно окружения.

<span id="интуиция-предлагает-структуру-kernel-принимает-только-формальный-терм"></span>

Ядру не требуется повторять поиск модели или доверять её рассуждению.
В обычной тактике результатом поиска служит проверяемый терм. Однако
разработчик тактики может также объявить аксиому или оставить пропуск
`sorry`. Ядро проверит применение такой аксиомы, не установив её истинность.
Поэтому приёмка включает проверку зависимостей доказательства;
ниже это существенно для LeanEuclid.

<span id="lean-термы-tactics-proof-state-and-environment"></span>
### Lean: термы, тактики, состояние доказательства и окружение

В Lean утверждения имеют тип `Prop`, а доказательство утверждения `P`
является термом типа `P`. Так, доказательство конъюнкции состоит из двух
доказательств её частей. Пример в начале главы можно записать без тактик:

```lean
theorem swap_and_term (P Q : Prop) (h : P ∧ Q) : Q ∧ P :=
  And.intro h.right h.left
```

`And.intro` принимает доказательства `Q` и `P` и возвращает доказательство
`Q ∧ P`. Тактическая запись строит терм по частям, показывая незавершённые
обязательства. Окружение определяет значение всех имён: импортированные
модули, определения, обозначения, экземпляры классов типов и теоремы.
Одинаково напечатанная цель в двух проектах может ссылаться на разные
определения; одного текста цели для воспроизводимости недостаточно.

Например, индукция по натуральному числу превращает одну цель в базовый и индукционный случаи:

```lean
theorem zero_add_example (n : Nat) : 0 + n = n := by
  induction n with
  | zero => rfl
  | succ n ih => simp [Nat.add, ih]
```

В базовом случае получается `0 + 0 = 0`, которое следует из определения
сложения. В шаге индукции доступна гипотеза `ih : 0 + n = n`.
Определение сложения преобразует новую цель в
`Nat.succ (0 + n) = Nat.succ n`; подстановка `ih` делает обе стороны
одинаковыми. `simp` выполняет эти переписывания, а `rfl` закрывает равенство
выражений, совпадающих после вычисления.

Эти три небольших примера используют стандартную библиотеку Lean 4.19.0,
без Mathlib. Различие между термами, целями и тактиками подробнее разобрано
в [Theorem Proving in Lean 4, главы 3 и 5](https://lean-lang.org/theorem_proving_in_lean4/Propositions-and-Proofs/).

<span id="neural-prover-premise-retrieval-tactic-proposal-search-kernel"></span>
### Нейросетевой prover: от поиска посылок до проверки ядром

В крупной библиотеке слишком много лемм для одного запроса к модели.
[LeanDojo, §§3–4](https://arxiv.org/html/2306.15626v1#S3) извлекает из проектов
состояния доказательств, тактики и использованные определения или теоремы
(*premises*). Для каждой точки доказательства определяется, какие посылки
действительно доступны: модуль должен быть импортирован, а объявление
не должно находиться ниже ещё не доказанной теоремы. Семантически подходящая
лемма из будущей части файла не является допустимой подсказкой.

ReProver кодирует цель и доступные посылки трансформером. Близость векторов
задаёт порядок поиска; обучение использует посылки из человеческих
доказательств как положительные примеры и, в частности, другие посылки
того же файла как трудные отрицательные. В версии v1 применяется
контрастивная функция потерь на основе среднеквадратической ошибки.
Из выбранных результатов составляется контекст генератора тактик;
поиск выбирает 100 посылок, после чего ограничение длины входа может
оставить лишь часть их текстов.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/formal-math/m09-p55.png]]

*Kaiyu Yang, [Berkeley Meeting 9, физическая стр. 55](https://rdi.berkeley.edu/adv-llm-agents/slides/mathverification.pdf#page=55). Общее дерево нейросетевого поиска: модель предлагает тактики, а система доказательств вычисляет переходы между состояниями. Этот слайд не изображает обучение retriever ReProver.*

У одной цели может быть несколько корректных продолжений, но только часть
из них приведёт к доказательству в доступное время. ReProver поддерживает
очередь состояний и выполняет поиск с приоритетами, основанными
на вероятностях тактик. Последовательность операций имеет вид:

```text
formal theorem
  → initial proof state
  → retrieve accessible premises
  → sample/rank tactics
  → execute in Lean
  → enqueue valid successor states; reject errors and loops
  → repeat until no goals remain
  → kernel checks the reconstructed term
```

Например, `apply` может успешно заменить цель тремя предпосылками леммы,
две из которых в текущем контексте легко доказать, а третья недостижима.
Такой переход допустим, но не завершает доказательство. Высокая полнота
поиска посылок также не гарантирует успеха: модель может не использовать
найденную лемму или исчерпать бюджет на другой ветви.

### SFT и RLVR для формальных действий

При обучении с учителем модель получает пары «состояние — следующая тактика»
из человеческих или синтетических доказательств. Для начального примера
это состояния перед `constructor`, `exact h.right` и `exact h.left`.
Модель учится воспроизводить действия в таких состояниях; данных о том,
как выйти из произвольной собственной ошибки, в этих трёх парах нет.

В обучении с проверяемой наградой, RLVR, модель предлагает собственные
последовательности, а система доказательств устанавливает результат.
Можно дать награду за законченное доказательство и ноль за остальные
попытки. Ошибки синтаксиса, новые подцели и время выполнения дополнительно
доступны алгоритму, но их использование как промежуточной награды является
отдельным решением. Уменьшение числа целей, например, не всегда означает
упрощение задачи: одна оставшаяся цель может оказаться недоказуемой.
Формальный проверяющий устраняет необходимость поручать другой LLM оценку
логической правильности шага, но не исправляет неверную постановку задачи.

<a id="finite-products-and-missing-assumptions"></a>
### Worked example: finite products and missing assumptions

<!-- source_unit_id: meeting-08-slides-riemann-zeta-demo -->

При переносе математического решения в Lean приходится уточнять не только
имена лемм, но и смысл каждого преобразования: сохраняет ли оно множество
решений, по каким объектам берётся сумма, при каких условиях существует
предел. В демонстрации Thomas Hubert
([Meeting 8, страницы 94–107](https://rdi.berkeley.edu/adv-llm-agents/slides/alphaproof.pdf#page=94))
эти вопросы возникают в задаче AIME и при переходе от разложения чисел
на простые множители к произведению Эйлера.

#### AIME warm-up: a necessary condition can admit an extra candidate

The warm-up on slide 95 asks for positive integers $n$ such that
the remainder of $1^3+2^3+\cdots+n^3$ modulo $n+5$ is 17.
The remainder must be smaller than the divisor, so $m=n+5>17$.
Using the sum-of-cubes identity gives

$$
\begin{aligned}
S_n&=\left(\frac{n(n+1)}{2}\right)^2,\\
4S_n&=((m-5)(m-4))^2.
\end{aligned}
$$

Modulo $m$, the product $(m-5)(m-4)$ is 20. Thus the original condition
implies $400\equiv68\pmod m$, or $m\mid332$.
The divisors of $332=4\cdot83$ exceeding 17 are 83, 166 and 332.
They give $n=78,161,327$ respectively. Substitution into the original
remainder condition retains the first two and rejects the third:

| $n$ | $m=n+5$ | $S_n\bmod m$ |
|---:|---:|---:|
| 78 | 83 | 17 |
| 161 | 166 | 17 |
| 327 | 332 | 100 |

Multiplication by 4 preserved a necessary condition, not an equivalence
for every modulus. For $m=332$, the difference $100-17=83$ is not
divisible by 332, but four times that difference is. Cancelling 4 modulo
$m$ would require an additional invertibility argument. Testing the
original condition avoids making that invalid reverse step.
The requested sum is therefore $78+161=239$.

```python
def cube_sum(n):
    return (n * (n + 1) // 2) ** 2

moduli = [m for m in range(18, 333) if 332 % m == 0]
assert moduli == [83, 166, 332]
candidates = [m - 5 for m in moduli]
remainders = [cube_sum(n) % (n + 5) for n in candidates]
assert remainders == [17, 17, 100]
answers = [n for n in candidates if cube_sum(n) % (n + 5) == 17]
assert answers == [78, 161]
assert sum(answers) == 239
```

This code checks the finite candidate list after the divisibility argument.
It is not a search over an arbitrarily chosen upper bound for $n$:
the necessary condition $m\mid332$ supplies the complete list.

#### Expanding a product means choosing one exponent for each prime

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/formal-zeta-2026-10-26/prime-factorization.jpg|Произведение Эйлера: знаменатели разложены на простые множители]]

*Thomas Hubert, [Berkeley Meeting 8, слайд 99](https://rdi.berkeley.edu/adv-llm-agents/slides/alphaproof.pdf#page=99). Каждый знаменатель разложен на простые множители: например, $12=2^2\cdot3$. При раскрытии произведения показатель каждого простого выбирается независимо. Здесь изображён гармонический ряд, который расходится. На странице 97 лекции указан канал [zetamath](https://www.youtube.com/@zetamath); точный ролик не установлен.*

To remove the convergence question temporarily, take just the primes 2 and
3 and allow the exponents 0, 1 and 2. Distributing the two finite sums gives

$$
\begin{gathered}
\left(1+\frac12+\frac14\right)
\left(1+\frac13+\frac19\right)\\
=\sum_{a=0}^{2}\sum_{b=0}^{2}\frac{1}{2^a3^b}
=\frac{91}{36}.
\end{gathered}
$$

Each pair of exponents selects one term from each factor. The denominators
form the following finite set:

| | $b=0$ | $b=1$ | $b=2$ |
|---|---:|---:|---:|
| $a=0$ | 1 | 3 | 9 |
| $a=1$ | 2 | 6 | 18 |
| $a=2$ | 4 | 12 | 36 |

Unique prime factorization makes the map $(a,b)\mapsto2^a3^b$ injective.
Thus collecting terms by their integer denominator does not lose a
multiplicity. Replacing the primes by 2 and 4 would break that argument:
the denominator 4 can arise from choosing $2^2$ or from choosing $4^1$.
Distributivity still holds, but a sum over distinct denominators would
no longer equal the product.

The right-hand side is also not the ordinary partial sum
$1+1/2+1/3$. It includes numbers larger than 3, such as 18 and 36,
and excludes 5, 7 and every other integer with a prime factor outside
$\{2,3\}$. A correct formal statement must describe this indexing set.

```python
from fractions import Fraction as F

denominators = [2**a * 3**b for a in range(3) for b in range(3)]
assert len(denominators) == len(set(denominators)) == 9
left = (1 + F(1, 2) + F(1, 4)) * (1 + F(1, 3) + F(1, 9))
right = sum((F(1, d) for d in denominators), F(0))
assert left == right == F(91, 36)
assert right != 1 + F(1, 2) + F(1, 3)
nonprime_denominators = [2**a * 4**b for a in range(3) for b in range(3)]
assert len(set(nonprime_denominators)) < len(nonprime_denominators)
```

#### A finite set of primes can still index an infinite sum

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/formal-zeta-2026-10-26/prime-geometric-factors.jpg|Произведение Эйлера: отдельный геометрический ряд для каждого простого числа]]

*Thomas Hubert, [слайд 100](https://rdi.berkeley.edu/adv-llm-agents/slides/alphaproof.pdf#page=100), повторённый на слайде 104. В каждой скобке собраны степени одного простого числа. При раскрытии произведения выбор слагаемого из каждой скобки задаёт знаменатель $2^a3^b5^c\cdots$. Полное исходное изображение; затенение нижней части присутствует в оригинале.*

Keeping the primes 2 and 3 while allowing every nonnegative exponent gives
all positive integers of the form $2^a3^b$, an infinite set. For the exponent
$s=2$, the two geometric series converge and their product is

$$
\frac{1}{1-2^{-2}}\frac{1}{1-3^{-2}}
=\frac43\frac98=\frac32.
$$

This is a sum over integers whose prime factors belong to $\{2,3\}$,
not over all positive integers. For example, its terms include $1/36^2$
but not $1/5^2$. Adding more primes changes the indexing set; increasing
the exponent cutoff changes it in a different way.

Mathlib separates these steps explicitly. The following is the complete
introductory explanation from Michael Stoll's
[`EulerProduct/Basic.lean`, Mathlib v4.19.0](https://github.com/leanprover-community/mathlib4/blob/c44e0c8ee63ca166450922a373c7409c5d26b00b/Mathlib/NumberTheory/EulerProduct/Basic.lean),
retained in its original English under Apache 2.0:

Here `HasSum` and `HasProd` state convergence to a particular value;
`Summable` requires the existence of a sum. The condition on the norm
requires absolute convergence. The finite-prime lemma uses `factoredNumbers`
for the positive integers supported on the selected primes. A second lemma
controls the omitted tail as the finite set eventually contains every
prime below a sufficiently large bound. The final theorem combines those
two statements.

The module also assumes $f(1)=1$; this hypothesis and coprime
multiplicativity are declared before the final theorem. Copying only its
last two lines would hide those inherited assumptions.

For the zeta series, take $f(0)=0$ and $f(n)=n^{-s}$ for positive $n$.
The extra zero value is explicit because the Mathlib sum ranges over
natural numbers including 0. The series and Euler product converge
absolutely when $\operatorname{Re}s>1$
([DLMF 25.2.1 and 25.2.11](https://dlmf.nist.gov/25.2#E11)).

$$
\begin{aligned}
\zeta(s)&=\sum_{n=1}^{\infty}n^{-s}\\
&=\prod_{p\ \mathrm{prime}}(1-p^{-s})^{-1},\\
&\hspace{1em}\operatorname{Re}s>1.
\end{aligned}
$$

The raw $s=1$ expressions on slides 98–102 illustrate the combinatorics;
they are not equalities between finite complex values. The harmonic
series diverges, and the analytically continued zeta function has a pole
at 1. Its divergence also gives a proof that there are infinitely many
primes, the topic named on slide 94. Suppose instead that all primes
belonged to a finite set $P$. Each geometric series with ratio $1/p$
would have the finite sum $(1-1/p)^{-1}$, so their finite product would
be some constant $M$. Every integer from 1 to $N$ factors over $P$;
choosing a sufficiently large exponent cutoff includes each of their
reciprocals in the expanded product. All terms are positive, hence
$H_N=\sum_{n=1}^{N}1/n\leq M$ for every $N$.

But the harmonic series has no such bound. The block of terms with
$2^{j-1}<n\leq2^j$ contains $2^{j-1}$ terms, each at least $2^{-j}$.
Each block therefore contributes at least $1/2$, giving
$H_{2^r}\geq1+r/2$. For large enough $r$ this exceeds $M$,
contradicting the assumption of finitely many primes. This argument uses
finite partial sums and bounds; it does not assign a finite value to
$\zeta(1)$.

Substituting a point in the critical strip into the convergent
Euler-product argument would also violate its assumptions.

#### What the final slide leaves implicit

The last three frames relate products over primes to products or sums over
zeros of the analytically continued zeta function. These are different
indexing sets. Trivial zeros, nontrivial zeros and the pole at 1 must be
accounted for consistently; a product only over nontrivial zeros requires
additional factors, as in [DLMF 25.2.12](https://dlmf.nist.gov/25.2#E12).

For the final prime-counting relation, Terence Tao's
[246B Notes 4, Theorem 8](https://terrytao.wordpress.com/2021/02/12/246b-notes-4-the-riemann-zeta-function-and-the-prime-number-theorem/)
gives a precise version for non-integer $x>1$:

$$
\begin{aligned}
\psi(x)&=\sum_{p^k\leq x}\log p,\\
Z(x)&=\lim_{T\to\infty}
\sum_{\substack{\rho:\,|\operatorname{Im}\rho|\leq T}}
\frac{x^\rho}{\rho},\\
\psi(x)&=x-Z(x)-\log(2\pi)\\
&\quad-\frac12\log(1-x^{-2}).
\end{aligned}
$$

The sum defining $\psi$ uses primes $p$ and positive integers $k$;
the sum defining $Z$ uses nontrivial zeros, counted with multiplicity.
The symmetric limit specifies how that sum is taken. At $x=2.5$ the
prime-power sum is $\log2$; at $x=3.9$ it is $\log2+\log3$; at $x=4.1$
it additionally includes $\log2$ from $2^2$. This jump explains why a
statement at a prime power needs an endpoint convention. The logarithmic
correction in the displayed version accounts for trivial zeros that are
not included in $Z$.

These analytic statements are not consequences of the nine-term finite
calculation alone. A formal prover would also need the relevant definitions,
convergence results and analytic-continuation theorems in its environment.
The finite Python checks above do not establish those theorems or reproduce
the live AlphaProof demonstration. The full Mathlib proof is available in
the pinned module; the original source and reuse conditions are recorded in
[[05 Источники/Papers/Mathlib Euler products|the Mathlib source note]].

## Часть II. Автоформализация и смысл постановки

<span id="три-разрыва-theorem-statement-proof-steps-and-semantic-equivalence"></span>
### Три разрыва: постановка, шаги доказательства и смысловая эквивалентность

Рассмотрим фразу «для каждого натурального числа найдётся большее».
В ней порядок кванторов определяет, можно ли выбирать новое число
для каждого входа. Правильная запись допускает выбор `m = n + 1`:

```lean
theorem larger_exists : ∀ n : Nat, ∃ m : Nat, m > n := by
  intro n
  exact ⟨n + 1, Nat.lt_succ_self n⟩
```

При перестановке кванторов получается утверждение о едином числе,
которое больше всех натуральных. Оно ложно: достаточно подставить это же
число вместо `n`.

```lean
theorem no_largest : ¬ (∃ m : Nat, ∀ n : Nat, m > n) := by
  intro h
  obtain ⟨m, hm⟩ := h
  exact (Nat.lt_irrefl m) (hm m)
```

Обе формулы имеют корректный синтаксис и почти одинаковые слова.
Ошибка возникла при записи постановки, до поиска доказательства.
Другой тип ошибки появляется при переводе готового решения: автор
пропустил промежуточный факт, который агент теперь должен восстановить.
Наконец, даже две доказанные формальные теоремы могут выражать разные
вещи. Для проверки их равносильности требуется ещё одно доказательство,
связывающее формулировки и определения.

### Почему BLEU и компиляция не доказывают эквивалентность теорем

BLEU измеряет совпадение фрагментов текста с эталоном. Перестановка
`∀` и `∃` мало меняет строку, хотя полностью меняет смысл. Переименование
переменных, напротив, может ухудшить текстовую метрику без изменения теоремы.
Поэтому ни высокое значение BLEU, ни компиляция записи утверждения
не заменяют проверку смысла.

В [Autoformalization with Large Language Models, §4](https://arxiv.org/html/2205.12615v1#S4)
авторы отдельно приводят BLEU и ручную оценку. При разборе 150 задач
38 переводов оказались правильными; среди ошибок были несовпадающие
определения, пропущенные предпосылки, типы и применение функций.
Это результат моделей и протокола 2022 года, не текущая оценка всех LLM.
Полезно само разделение измерений: корректно ли разобрана запись,
что именно она означает и удалось ли построить доказательство
при разрешённых аксиомах.

### LIPS: сузить бесконечное пространство действий символическим инструментом

Для доказательства неравенства можно раскрывать скобки, заменять выражение
оценкой, вводить переменные или применять известное неравенство.
Число вариантов быстро растёт. [LIPS, §§2–4](https://arxiv.org/html/2502.13834v3#S2)
разделяет преобразования на получение оценок (*scaling*) и переписывание
выражения (*rewriting*). Здесь scaling не означает умножение на масштабный
коэффициент: например, это может быть применение неравенства
между средним арифметическим и геометрическим.

Пусть требуется доказать `F ≤ G`. Если известна верхняя оценка `F ≤ U`,
достаточно доказать `U ≤ G`. Однако новое утверждение сильнее исходного
и может быть ложным. При `F = x²`, `G = x² + 1`, `U = x² + 2`
исходное неравенство верно для всех действительных `x`, а новая цель
неверна уже при `x = 0`. Корректная оценка выражения ещё не означает
полезного шага доказательства.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/formal-math/m09-p58.png]]

*Kaiyu Yang, [Berkeley Meeting 9, физическая стр. 58](https://rdi.berkeley.edu/adv-llm-agents/slides/mathverification.pdf#page=58). Символический модуль задаёт допустимые преобразования неравенства. Следующие слайды 61–64 и [статья LIPS](https://arxiv.org/html/2502.13834v3#S3) раскрывают отбор порождённых целей и участие LLM.*

Символический модуль LIPS сопоставляет выражения с шаблонами оценок
и порождает новые цели. Проверки с помощью цилиндрической алгебраической
декомпозиции, накопленных контрпримеров и численной оптимизации отбрасывают
часть ложных целей. Численный поиск может обнаружить контрпример,
но отсутствие найденного контрпримера не доказывает неравенство.
Эвристики на основе разложений Тейлора и разделения переменных помогают
ранжировать оставшиеся варианты; десять лучших передаются LLM
для дополнительного выбора. Эти оценки управляют поиском,
а не заменяют заключительное доказательство.

Переписывание может сделать подходящую оценку видимой. Например, при
`a² + b² + c² = 1` выражение преобразуется так:

$$
\frac{1}{3a^2+3b^2+c^2}
= \frac{1}{3-2c^2}.
$$

В знаменателе использована подстановка
`3a² + 3b² = 3(1 − c²)`. При `a = 1/3`, `b = c = 2/3`
оба знаменателя равны `19/9`, а обе дроби — `9/19`.
Для доказательства через дроби нужны также условия ненулевого знаменателя;
их нельзя опустить при формальном переписывании.
Здесь из суммы квадратов следует `c² ≤ 1`, поэтому `3 − 2c² ≥ 1`.
Оба равных знаменателя положительны, и преобразование допустимо.

В §5.1 версии v3 авторы описывают формализацию в Lean 4
96 тактик оценивания и 16 тактик переписывания. Это связывает предметные
операции с проверяемыми шагами. При переносе подхода на другой раздел
математики набор операций и условия их применения придётся строить заново.

### LeanEuclid: как связать текст, диаграмму, формальную систему и SMT

В евклидовой геометрии часть условий обычно передаёт рисунок.
Текст может перечислить равные стороны и параллельные прямые,
не сообщив, по какую сторону от прямой лежат точки.
[LeanEuclid, §§3–4](https://arxiv.org/html/2405.17216v1#S3) использует
формальную систему `E`, где заданы точки, прямые, окружности,
отношения порядка и правила геометрических построений.
Набор статьи содержит 173 задачи: 48 из первой книги *Начал*
и 125 из UniGeo. В репозитории отдельно выделены 100 отложенных задач
UniGeo; это не другой общий размер исходного набора.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/formal-math-2026-10-21/leaneuclid-autoformalization.png]]

*Logan Murphy et al., [Autoformalizing Euclidean Geometry, Figure 1, ICML 2024, PMLR 235](https://proceedings.mlr.press/v235/murphy24a.html), CC BY 4.0. Слева исходная задача и рисунок, в центре формальное утверждение и доказательство, справа две роли SMT: сравнение формулировок и восстановление геометрических предпосылок. Оригинальные английские подписи сохранены.*

В системе `E` разделены правила построения объектов и выводы об уже
построенной конфигурации. Например, для построения равностороннего
треугольника на отрезке `AB` вводятся окружность с центром `A`, проходящая
через `B`, и окружность с центром `B`, проходящая через `A`.
Прежде чем ввести точку их пересечения `C`, нужно установить,
что окружности пересекаются. После построения принадлежность `C`
обеим окружностям даёт `AC = AB` и `BC = BA`, то есть нужные равенства
сторон. SMT-решатель автоматизирует вывод части таких условий из контекста;
модель выбирает последовательность построений и применения теорем.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/formal-math-2026-10-21/leaneuclid-construction-rules.png]]

*Logan Murphy et al., [Autoformalizing Euclidean Geometry, Figure 2, ICML 2024, PMLR 235](https://proceedings.mlr.press/v235/murphy24a.html), CC BY 4.0. Оригинальный рисунок и английская подпись сохранены целиком. Сплошные стрелки обозначают явно применённые правила, пунктирные — восстановление недостающих предпосылок через SMT. Рисунок показывает порядок вывода; ограничения доверия к реализации разобраны ниже.*

#### Что именно проверено в реализации LeanEuclid

В зафиксированной версии репозитория
[`33a72c0`](https://github.com/loganrjmurphy/LeanEuclid/tree/33a72c0fa83914202532998a2e7b8771295c3cc7)
SMT-ответ не реконструируется в обычное доказательство Lean.
Файл [`SystemE/Meta/Smt/Solver.lean`](https://github.com/loganrjmurphy/LeanEuclid/blob/33a72c0fa83914202532998a2e7b8771295c3cc7/SystemE/Meta/Smt/Solver.lean#L44-L47)
объявляет аксиому `SMT_VERIF (P : Prop) : P`.
Когда решатель возвращает `unsat`, тактика закрывает цель применением
этой аксиомы. Сама аксиома позволяет вывести любое `P`, включая `False`.

Авторы прямо предупреждают об этой потере логической надёжности
в [README](https://github.com/loganrjmurphy/LeanEuclid/blob/33a72c0fa83914202532998a2e7b8771295c3cc7/README.md#acknowledgements).
Здесь приходится доверять переводу в SMT, решателю и обвязке его вызова.
Успешная сборка такого доказательства не равна независимой проверке
геометрического вывода ядром без дополнительных аксиом.
Эта оговорка относится к указанному коду, а не к невозможности
надёжно формализовать евклидову геометрию вообще.

### Разобранный пример: скрытая посылка на диаграмме

В предложении I.24 Евклид сравнивает третьи стороны двух треугольников,
у которых две пары сторон равны, а заключённые между ними углы различны.
Доказательство вводит вспомогательную точку `G` и использует
равнобедренный треугольник `DGF`. Однако положение `D` и `G`
относительно прямой `EF` требует разбора случаев. Одна удобная картинка
не покрывает их все.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/formal-math/m09-p89.png]]

*Kaiyu Yang, [Berkeley Meeting 9, физическая стр. 89](https://rdi.berkeley.edu/adv-llm-agents/slides/mathverification.pdf#page=89). Вспомогательная конструкция и равные углы равнобедренного треугольника.*

В [Appendix B статьи](https://arxiv.org/html/2405.17216v1#A2)
разобран пропущенный в исходном доказательстве случай: точки `D` и `G`
лежат по разные стороны `EF`. На следующем рисунке обозначено:

$$
\begin{aligned}
\alpha &= \angle DGF = \angle DFG,\\
x &= \angle EFG,\qquad y = \angle EGF.
\end{aligned}
$$

Из расположения лучей получаются два выражения для углов:

$$
\begin{aligned}
\angle DGE &= \alpha+y < \pi,\\
\angle DFE &= 2\pi-\alpha-x < \pi.
\end{aligned}
$$

Первое неравенство даёт `y < π − α`, второе — `x > π − α`.
Следовательно, `x > y`. В треугольнике `EFG` напротив большего угла
лежит большая сторона: `EG > EF`. Построение даёт `EG = BC`, откуда
`BC > EF`. Для этого вывода потребовались и равнобедренность `DGF`,
и конкретный порядок лучей в пропущенной конфигурации.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/formal-math/m09-p97.png]]

*Kaiyu Yang, [Berkeley Meeting 9, физическая стр. 97](https://rdi.berkeley.edu/adv-llm-agents/slides/mathverification.pdf#page=97). Случай с `D` и `G` по разные стороны `EF`; обозначения `α`, `x`, `y` соответствуют вычислениям выше.*

### Семантическая эквивалентность и диаграммные следствия

Проверяющий E3 из LeanEuclid сравнивает предсказанную формулировку
с эталонной в общем языке системы `E`. Он пытается установить оба
направления следования: эталон влечёт предсказание и предсказание
влечёт эталон. Одного направления недостаточно: если модель выбросила
условие, она могла получить более сильную теорему; если добавила условие,
то более слабую. Отдельная проверка непротиворечивости нужна,
чтобы противоречивые предпосылки не дали формального успеха за счёт
того, что из них следует что угодно.

Когда полную эквивалентность установить не удаётся, E3 может сравнивать
отдельные части формулировок. Эта приближённая оценка сопоставляет
переменные эвристически и проверяет совпадающие по смыслу условия;
она не является доказательством равносильности всей теоремы.
Описанные выше ограничения SMT-проверки относятся и к этой процедуре.

### Сквозная автоформализация без смешения перевода и доказательства

Для воспроизведения сквозного решения нужно сохранить:

```text
informal statement
  → candidate formal statement
  → semantic/domain checks
  → candidate proof
  → proof-assistant execution trace
  → checked term + axiom dependencies
```

Например, запись неверного порядка кванторов можно отклонить до запуска
дорогого поиска. Если же постановка верна, а поиск исчерпал время,
сохраняются конкретные состояния и неудачные действия.
По одному итоговому флагу `solved` эти случаи не различить.

### Граница автоматической проверки

<span id="что-даёт-формальная-среда-и-что-остаётся-человеческой-работой"></span>

Человек или отдельная процедура проверяют соответствие исходной задаче.
Система доказательств проверяет терм и его зависимости в формальном
окружении. Если исходное условие было неправильно переведено,
безупречное доказательство перевода не исправляет эту ошибку.

<span id="часть-iii-обучение-поиск-и-модульные-prover"></span>
## Часть III. Обучение и организация поиска

### Почему формальная математика допускает AlphaZero-подобный цикл

При поиске доказательства доступна исполнимая среда: действие изменяет
состояние, а проверяющий определяет, закончена ли работа. Поэтому можно
обучать модель на результатах собственных попыток. В лекции Thomas Hubert
сопоставляет этот цикл с AlphaZero: поиск находит успешные продолжения,
а обучение повышает вероятность действий, которые к ним привели.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/formal-math/m08-p30.png]]

*Thomas Hubert, [Berkeley Meeting 8, физическая стр. 30](https://rdi.berkeley.edu/adv-llm-agents/slides/alphaproof.pdf#page=30). Сопоставление масштабируемого опыта, проверяемой обратной связи, поиска и подбора задач. Оно не означает полного совпадения алгоритмов AlphaZero и AlphaProof.*

В игре начальная позиция и правила уже определены. Для математической
задачи сначала нужны формальная постановка, библиотека и набор упражнений
подходящей сложности. Неудача поиска не доказывает ложность утверждения:
причиной может быть недостаточный бюджет. Доказательство отрицания
требует отдельной успешной формальной траектории.

<span id="alphaproof-как-формализатор-prover-и-поиск"></span>
### AlphaProof: формализатор, модель доказательства и поиск

В AlphaProof одна модель переводит неформальные задачи в утверждения Lean,
другая предлагает шаги доказательства. Поиск хранит дерево состояний
и выбирает, какие продолжения исследовать. Формализатор позволяет получить
больше упражнений, чем содержится в библиотеке человеческих доказательств;
Lean даёт обратную связь для обучения решателя.

<span id="от-mathlib-sft-к-rl-с-lean-verifier"></span>
### Обучение на доказательствах Mathlib и на результатах поиска

Начальная модель учится на человеческих доказательствах Mathlib.
Затем формализатор создаёт дополнительные задачи из неформального корпуса.
Решатель пытается их доказать или опровергнуть. Найденные и проверенные
траектории становятся новыми обучающими примерами, после чего обновлённая
модель снова участвует в поиске. Лёгкие задачи позволяют получать
успешный опыт, когда самые трудные ещё не решаются.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/formal-math/m08-p84.png]]

*Thomas Hubert, [Berkeley Meeting 8, физическая стр. 84](https://rdi.berkeley.edu/adv-llm-agents/slides/alphaproof.pdf#page=84). Связь формализатора, решателя и обучения на проверенных результатах. `O(1M)` и `O(100M)` — оценки масштаба на слайде, не независимый подсчёт данных.*

Возврат успешных траекторий в обучение называют итеративным обучением
по найденным решениям, или *expert iteration*. Название не означает,
что каждую новую траекторию размечает человек: роль эксперта здесь
выполняет поиск вместе с формальной проверкой.

### Test-time RL как локальная специализация вокруг трудной задачи

Для особенно трудной задачи можно создать семейство связанных вариантов
и продолжить обучение на них во время решения. Если часть вариантов
уже решается, их доказательства дают обучающие данные для специализации
модели. Именно такой процесс в лекции называется *test-time RL*.
Исходная трудная задача при этом может ещё оставаться нерешённой.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/formal-math/m08-p91.png]]

*Thomas Hubert, [Berkeley Meeting 8, физическая стр. 91](https://rdi.berkeley.edu/adv-llm-agents/slides/alphaproof.pdf#page=91). Учебная схема специализации на вариантах задачи. Расширение области решаемых задач изображено концептуально, без гарантии решения каждой новой цели.*

При обычном поиске можно увеличить число попыток, не меняя веса модели.
При test-time RL меняется сама модель. Для воспроизведения второго
эксперимента недостаточно сохранить запрос и число попыток: нужны
созданные варианты, найденные траектории, настройки обучения и контрольные
точки до и после специализации.

<span id="что-именно-проверял-imo-protocol"></span>
### Что именно проверял протокол IMO

В эксперименте IMO 2024 эксперты вручную переводили постановки
на формальный язык. По лекции Meeting 8, для задач с требованием найти
ответ Gemini предлагал около ста кандидатов. Их можно было проверять
и отсеивать, затем продолжать обучение вокруг оставшейся трудной задачи.
Геометрию решала отдельная AlphaGeometry 2, а AlphaProof использовался
для других разделов.

Таким образом, опубликованный результат включает работу людей
над формальной постановкой. Он не измеряет автономное решение всех этапов
от исходного текста олимпиады до доказательства.

### Результат и границы утверждения

По [официальному сообщению Google DeepMind](https://deepmind.google/discover/blog/ai-solves-imo-problems-at-silver-medal-level/)
и слайдам Meeting 8, AlphaProof решил задачи 1, 2 и 6,
AlphaGeometry 2 — задачу 4. Четыре полных решения дали 28 из 42 баллов,
при золотом пороге 29. Одна задача решилась за минуты,
другие потребовали до трёх дней, тогда как участникам отводились
две сессии по 4,5 часа.

Слайды дополнительно отмечают, что задача 5 не была формализована
в день соревнования; задачи 3 и 5 не дали зачётных баллов.
Это исторический протокол 2024 года. Для сравнения с другим решателем
нужно сохранить ручной перевод постановок, разделение двух систем,
генерацию кандидатов ответа и фактическое время решения.

Следующие методы используют неформальные рассуждения в более ограниченных
ролях: для выбора одной тактики, составления плана или подбора лемм.
Эти роли требуют разных данных и разных алгоритмов поиска.

<span id="lean-star-thought-before-tactic-and-expert-iteration"></span>
### Lean-STaR: рассуждение перед тактикой и expert iteration

Обычная модель тактик предсказывает действие по состоянию доказательства.
[Lean-STaR, §3](https://arxiv.org/html/2407.10040v1#S3) сначала генерирует
краткое неформальное рассуждение, затем тактику. При цели `Q ∧ P`
таким рассуждением могло бы быть предложение сначала построить конъюнкцию,
а обе части взять из гипотезы `h : P ∧ Q`. Lean исполняет `constructor`
и последующие тактики; поясняющий текст он не проверяет.

Данных с человеческими мыслями перед каждой тактикой обычно нет.
Поэтому авторы получают начальную разметку ретроспективно: GPT-4 видит
состояние и уже известную правильную тактику, после чего пишет
объяснение её выбора. Модель Lean-CoT учится на тройках
«состояние — объяснение — тактика». Эти объяснения являются синтетической
разметкой, а не записью мыслей автора доказательства и не подтверждением
того, как модель действительно принимает решение.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/formal-math-2026-10-21/leanstar-pipeline.png]]

*[Lean-STaR, Figure 4](https://arxiv.org/html/2407.10040v1#S3.F4), Lin et al., CC BY 4.0. Оригинальная схема: разметка рассуждений, обучение Lean-CoT, сбор успешных траекторий и следующая итерация обучения. Английские подписи сохранены.*

Затем модель сама пытается доказать обучающие теоремы. Полностью успешные
траектории отбираются по результату Lean, дубликаты удаляются,
а сохранённые тройки используются для следующего дообучения.
Отбирается результат формальных действий; правдоподобие сопровождающего
рассуждения отдельно не гарантируется.

#### Почему изменён алгоритм поиска

В обычном поиске с приоритетами состояние можно оценивать по вероятностям
тактик, приведших к нему. Авторы обнаружили, что средняя логарифмическая
вероятность токенов плохо ранжирует продолжения, содержащие ещё и
неформальный текст. Часто встречающееся объяснение может иметь высокую
вероятность, не приближая доказательство к завершению.

Вместо такого ранжирования Lean-STaR использует параллельные траектории.
Из начального состояния запускаются `K` попыток. В каждой попытке
модель предлагает рассуждение и тактику; корректная тактика переводит
поиск в новое состояние. Некорректная отбрасывается, и следующее
предложение делается из того же состояния. Неудачные предложения
тоже расходуют предел `N` генераций на попытку.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/formal-math-2026-10-21/leanstar-search-sampling.png]]

*[Lean-STaR, Figure 5](https://arxiv.org/html/2407.10040v1#S3.F5), Lin et al., CC BY 4.0. Слева поиск с ветвлением по нескольким тактикам, справа независимые траектории с повторной генерацией после недопустимого шага.*

В оригинальном рисунке положительные числа подписаны `log p`, хотя
логарифм вероятности не может быть положительным. Числа на этой схеме
не следует использовать для расчёта приоритетов; правило ранжирования
описано отдельно в §3.3 статьи. Различие между деревом и траекториями
от этой неточности обозначений не зависит.

В Table 3 статьи для InternLM2-Math-plus-7B и `K = 64`, `N = 50`,
температуры 0,7 получены 43,4% у SFT, 45,5% у Lean-CoT
и 46,3% после одной итерации Lean-STaR. Это сопоставимые строки
одного протокола, в котором `K = 64` получено двумя наборами по 32 попытки.
Результаты другой базовой модели и поиска с другим бюджетом
не следует подставлять в это сравнение.

<span id="почему-prover-стоит-разложить-на-retrieval-atp-and-search"></span>
<span id="почему-prover-стоит-разделить-на-retrieval-atp-и-поиск"></span>
### Зачем разделять поиск посылок и автоматическое доказательство

Модель может выбрать полезный математический план и всё же ошибиться
в имени библиотечной леммы. Автоматический решатель, напротив,
может быстро закрыть локальную алгебраическую цель, не найдя
вспомогательную конструкцию для всей теоремы. Разделение этих задач
позволяет использовать модель для плана, поиск по библиотеке для посылок,
а специализированную автоматизацию — для отдельных обязательств.

<span id="draftsketchprove-отделить-математический-план-от-заполнения-holes"></span>
### Draft–Sketch–Prove: отделить математический план от заполнения пропусков

[Draft–Sketch–Prove, §3](https://arxiv.org/html/2210.12283v1#S3)
разделяет решение на три стадии. Сначала человек или LLM составляет
неформальное доказательство. Затем модель переводит его в формальный
план (*sketch*) с промежуточными утверждениями и пропусками.
В экспериментах статьи эти пропуски заполняет автоматизация Isabelle,
в том числе Sledgehammer. Пропуски допустимы в плане поиска,
но не в принятом окончательном доказательстве.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/formal-math/m10-p64.png]]

*Sean Welleck, [Berkeley Meeting 10, физическая стр. 64](https://rdi.berkeley.edu/adv-llm-agents/slides/welleck2025_berkeley_bridging.pdf#page=64). Модель переводит неформальное решение в план с явно обозначенными пропусками `<proof>`.*

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/formal-math/m10-p66.png]]

*Sean Welleck, [Berkeley Meeting 10, физическая стр. 66](https://rdi.berkeley.edu/adv-llm-agents/slides/welleck2025_berkeley_bridging.pdf#page=66). Несколько неформальных решений порождают разные формальные планы; автоматизация пытается заполнить пропуски в каждом.*

Например, в Figure 2 статьи требуется доказать для действительного `a`:

$$
10a \leq 28a^2+1.
$$

Неформальный план предлагает выделить полный квадрат. Сначала
`(a − 5/28)² ≥ 0`, затем после раскрытия скобок и умножения на 28:

$$
28a^2-10a+\frac{25}{28}\geq 0.
$$

Поскольку `25/28 < 1`, прибавление `3/28` к левой части сохраняет
неотрицательность. Получается `28a² − 10a + 1 ≥ 0`, то есть исходная цель.
План содержит выбор сдвига `5/28`; отдельная автоматизация может проверить
неотрицательность квадрата, раскрытие скобок и арифметику дробей.

В формальном плане каждый такой переход становится самостоятельным
обязательством. Если модель выбрала неверный коэффициент или потеряла
предпосылку, заполнение пропусков может остановиться. Тогда нужно менять
план, а не считать оставшиеся пропуски доказанными.

<span id="leanhammer-premise-selector-atp-aesop-and-reconstruction"></span>
### LeanHammer: выбор посылок, ATP, Aesop и реконструкция доказательства

*Hammer* соединяет интерактивную систему доказательств с внешним
автоматическим решателем, ATP. Сначала выбираются посылки,
затем цель и посылки переводятся на язык решателя.
После успешного внешнего поиска нужно восстановить доказательство
в исходной системе. Без этой последней стадии доверие к ядру
заменилось бы доверием ко всему внешнему решателю и переводу.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/formal-math/m10-p78.png]]

*Thomas Zhu, [Berkeley Meeting 10, физическая стр. 78](https://rdi.berkeley.edu/adv-llm-agents/slides/welleck2025_berkeley_bridging.pdf#page=78). Выбор посылок, перевод через Lean-auto, поиск в Zipperposition и реконструкция с Duper. Выбран кадр, в котором все четыре стадии показаны без затенения.*

В [LeanHammer, §3](https://arxiv.org/html/2506.07477v1#S3)
поисковый модуль кодирует цель и посылки и ранжирует их по близости.
Представление включает полные имена констант вместо неоднозначных
сокращений и перегруженных обозначений. Иначе одинаково напечатанное
`gcd` могло бы обозначать разные операции. Локальные гипотезы
добавляются во время работы; векторы библиотечных посылок можно
вычислить заранее. Контрастивное обучение сближает цель с использованными
посылками; маскирование не позволяет считать другую известную
положительную посылку отрицательным примером того же запроса.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/formal-math/m10-p82.png]]

*Thomas Zhu, [Berkeley Meeting 10, физическая стр. 82](https://rdi.berkeley.edu/adv-llm-agents/slides/welleck2025_berkeley_bridging.pdf#page=82). Обучение кодировщика для поиска посылок. Сближение векторов помогает ранжировать леммы, но ещё не даёт доказательства цели.*

Деревом поиска управляет Aesop. Внешний путь состоит из перевода
через Lean-auto, поиска в Zipperposition и реконструкции с помощью Duper.
Duper строит доказательство Lean по посылкам, которые понадобились
внешнему решателю. Кроме того, Aesop может непосредственно применить
лемму и получить новые подцели. В конфигурации статьи внешнему решателю
передаются 16 посылок, а для непосредственного применения доступны 32.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/formal-math/m10-p85.png]]

*Thomas Zhu, [Berkeley Meeting 10, физическая стр. 85](https://rdi.berkeley.edu/adv-llm-agents/slides/welleck2025_berkeley_bridging.pdf#page=85). Aesop сочетает прямое применение тактик Lean с внешним поиском на выбранных посылках.*

В [Appendix B](https://arxiv.org/html/2506.07477v1#A2) разобрана теорема
`Associated y (gcd x y) ↔ y ∣ x`. Ассоциированность означает равенство
с точностью до умножения на обратимый элемент. В частном случае
натуральных чисел это знакомый факт: `gcd(x, y) = y` тогда и только тогда,
когда `y` делит `x`; например, при `x = 6`, `y = 3` обе части верны.

Aesop разделяет эквивалентность на два направления. Первое внешний
решатель доказывает с леммами на позициях 1 и 6 в выдаче поиска,
после чего Duper реконструирует доказательство. Для второго направления
первых 16 посылок недостаточно. Но лемма `associated_of_dvd_dvd`
на позиции 18 входит в набор из 32: Aesop применяет её напрямую
и получает два обязательства делимости. Одно закрывается новым вызовом
внешнего решателя и реконструкцией, другое — прямым применением
`gcd_dvd_right` на позиции 4. Дополнительное ветвление позволило
использовать лемму, не попавшую во вход ATP.

<span id="minictx-контекст-реального-проекта-и-time-split"></span>
<span id="где-ломается-переход-от-олимпиадной-задачи-к-проекту-mathlib"></span>
### miniCTX: контекст реального проекта и временное разделение данных

В олимпиадном наборе формулировка часто самодостаточна, а нужные понятия
уже есть в стандартной библиотеке. В исследовательском проекте
определение могло появиться несколькими строками выше, а подходящая
лемма — в соседнем файле. [miniCTX, §§2–4](https://arxiv.org/html/2408.03350v1#S2)
проверяет работу с таким контекстом. Версия v1 включает 376 теорем:
87 из PrimeNumberTheoremAnd, 54 из PFR, 50 из более поздних пополнений
Mathlib и 185 из проекта учебника HTPI.

*Sean Welleck, [Berkeley Meeting 10, физическая стр. 109](https://rdi.berkeley.edu/adv-llm-agents/slides/welleck2025_berkeley_bridging.pdf#page=109). Проекты и временная отсечка miniCTX. Защита от утечки действует лишь относительно известной отсечки обучения конкретной модели; набор 2024 года нельзя автоматически считать невиданным для модели 2026 года.*

Контекст внутри файла (*in-file*) содержит предшествующие определения,
обозначения и леммы. Межфайловые зависимости (*cross-file*) требуют
учёта импортов и поиска в других модулях. Эталонное доказательство
самой целевой теоремы не должно попадать во вход. Разделение по теоремам,
новым определениям и целым проектам проверяет разные уровни обобщения:
новая теорема в знакомом проекте не равна новому проекту с незнакомыми
определениями.

*Sean Welleck, [Berkeley Meeting 10, физическая стр. 110](https://rdi.berkeley.edu/adv-llm-agents/slides/welleck2025_berkeley_bridging.pdf#page=110). Зависимости внутри одного файла и между импортированными модулями.*

При *file tuning* модель обучается на тройках
«предшествующий код — состояние — следующая тактика».
Например, если цель использует только что определённый предикат,
его тело объясняет модели, какие условия потребуется раскрыть.
Модель, получившая одно имя предиката в состоянии, этого тела не видит.
В простом варианте статьи контекст обрезается до бюджета 1024 токена;
более далёкое определение может оказаться потерянным.

нельзя: бюджет и способ решения различаются.

### COPRA: поиск с состоянием, возвратом и формальной обратной связью

[COPRA, §§2–3](https://arxiv.org/html/2310.04353v1#S2)
использует готовую LLM, не обновляя её веса после каждого шага.
В запрос входят текущее состояние доказательства, часть истории,
неудачные действия и при необходимости найденные леммы.
Предложенная тактика исполняется в системе доказательств;
ответ среды определяет следующее действие поиска.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/formal-math/m11-p16.png]]

*Swarat Chaudhuri, [Berkeley Meeting 11, физическая стр. 16](https://rdi.berkeley.edu/adv-llm-agents/slides/swarat.pdf#page=16). Цикл COPRA: предложение тактики, разбор ответа, исполнение, обратная связь, поиск лемм и возврат к прежнему состоянию.*

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/formal-math/m11-p17.png]]

*Swarat Chaudhuri, [Berkeley Meeting 11, физическая стр. 17](https://rdi.berkeley.edu/adv-llm-agents/slides/swarat.pdf#page=17). Формат запроса и ответа COPRA с текущими целями и сведениями о неудачных действиях.*

Поиск устроен как обход в глубину с возвратом. COPRA хранит стек состояний
и словарь неудач `Bad(O)` для каждого состояния `O`.
Если действие оказалось некорректным или ветвь была исчерпана,
поиск возвращается к предшествующему состоянию и исключает уже
неудавшееся продолжение именно в нём. Глобально запрещать такую тактику
нельзя: в другом контексте она может быть правильной.

Возврат требует восстановления состояния системы доказательств,
а не только удаления последней строки из запроса. После ошибки формата
COPRA может запросить исправленный ответ; после ошибки самой тактики —
другое действие. Дополнительный фильтр по частичному порядку состояний
отсекает повторения и часть переходов к заведомо более трудным
обязательствам. Фильтр неполон: он не обязан обнаружить каждый тупик
или каждый полезный путь. Число запросов и глубина поиска ограничиваются.

В лекционном примере сначала предлагается неформальное решение задачи
о взаимной простоте `21n + 4` и `14n + 3`.
Их целочисленная комбинация `3(14n + 3) − 2(21n + 4) = 1`
показывает, что общий положительный делитель должен равняться 1.
Затем задача разбивается на вспомогательные утверждения.
При записи полного доказательства o3-mini предлагает имя
`Nat.gcd_sub_right`, недоступное в данном окружении.
Обратная связь Lean позволяет заменить этот шаг использованием уже
доказанных подлемм. Это исправление в ходе поиска с фиксированными весами,
а не шаг RL-обучения модели.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/formal-math/m11-p24.png]]

*Swarat Chaudhuri, [Berkeley Meeting 11, физическая стр. 24](https://rdi.berkeley.edu/adv-llm-agents/slides/swarat.pdf#page=24). Вход COPRA содержит уже доказанные подлеммы; результат использует их для завершения теоремы. Внизу лектор отмечает ошибочную ссылку `Nat.gcd_sub_right`; сам журнал ошибки Lean на слайде не показан.*

### ImProver: улучшение уже найденного доказательства

Если доказательство существует, можно искать более короткую или более
понятную запись, не меняя утверждения. [ImProver, §3](https://arxiv.org/html/2410.04753v1#S3)
получает теорему, контекст, исходное доказательство и выбранную метрику.
Новый кандидат сначала должен пройти Lean; только затем сравнивается
его значение метрики. Текст, не доказывающий теорему, не становится
предпочтительным за счёт краткости.

Авторы рассматривают число вызовов тактик как меру длины. В начальном
примере главы это три вызова: `constructor` и два `exact`.
Запись `exact And.intro h.right h.left` использует один вызов
и доказывает то же утверждение. Это учебное сравнение двух записей,
а не результат запуска ImProver. Уменьшение числа тактик также
не означает уменьшения времени проверки.

Вторая метрика статьи оценивает долю тактик `have` с явно записанным
типом промежуточного утверждения. Такие шаги могут пояснять структуру
решения, но метрика остаётся приближением читаемости: больше `have`
не всегда означает более понятное доказательство.

Для подсказки модели ImProver извлекает состояния из `InfoTree` Lean
и вставляет их в комментарии к доказательству. Эта *Chain-of-States*
показывает реально вычисленные обязательства до и после тактик,
в отличие от сгенерированных объяснений Lean-STaR.
В режиме выбора из нескольких кандидатов проверяются все предложенные
записи. В режиме итеративной правки модель получает предыдущий результат,
ошибки и оценку, затем предлагает следующую версию. Сочетание
`m` повторов с `n` кандидатами расходует до `m × n` генераций;
его нельзя сравнивать с одной попыткой, учитывая только `n`.

Поиск похожих примеров улучшений и справка по тактикам дают модели
дополнительный контекст. При оценивании фиксируют не только итоговую
длину, но и долю сохранившихся корректных доказательств, стоимость
проверки и выбранное определение читаемости.

## Часть IV. Проектный пример и приёмка результата

### Сквозной пример: корректность компилятора

В примере из [Meeting 11, страницы 25–39](https://rdi.berkeley.edu/adv-llm-agents/slides/swarat.pdf#page=25)
используется Coq. Требуется доказать, что компилятор арифметического языка
сохраняет результат вычисления. Попытка индукции подсказывает,
что формулировку нужно усилить: разрешить произвольные исходный стек
и продолжение программы. После этого обе индукционные гипотезы
применяются к тем состояниям, которые действительно возникают
при исполнении.

Определения ниже следуют слайдам; доказательство леммы приведено
в самостоятельной записи со стандартной `List.app_assoc`.
Coq-блоки, расположенные по порядку, составляют один файл
для Coq 8.20.1 без сторонних тактических библиотек.

#### 1. Исходный язык и его семантика

Выражения состоят из констант, сложения и умножения. `expDenote` вычисляет значение выражения.

```coq
Require Import Coq.Lists.List.

Inductive binop : Set := Plus | Times.

Inductive exp : Set :=
| Const : nat -> exp
| Binop : binop -> exp -> exp -> exp.

Definition binopDenote (b : binop) : nat -> nat -> nat :=
  match b with Plus => plus | Times => mult end.

Fixpoint expDenote (e : exp) : nat :=
  match e with
  | Const n => n
  | Binop b e1 e2 => binopDenote b (expDenote e1) (expDenote e2)
  end.
```

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/formal-math/m11-p27.png]]

*Исходная семантика задана рекурсивно: константа обозначает натуральное число, а бинарный узел сначала вычисляет оба подвыражения и затем применяет `Plus` или `Times`. Именно это значение обязан сохранить компилятор. Источник: Berkeley Meeting 11, физическая стр. 27.*

#### 2. Целевой стековый язык

Инструкция либо кладёт константу на стек, либо снимает два аргумента
и применяет бинарную операцию. Голова списка — вершина стека.
Если аргументов недостаточно, результатом становится `None`;
при успехе возвращается `Some` с новым стеком.

```coq
Inductive instr : Set :=
| iConst : nat -> instr
| iBinop : binop -> instr.

Definition prog := list instr.
Definition stack := list nat.

Definition instrDenote (i : instr) (s : stack) : option stack :=
  match i with
  | iConst n => Some (n :: s)
  | iBinop b =>
      match s with
      | arg1 :: arg2 :: s' => Some (binopDenote b arg1 arg2 :: s')
      | _ => None
      end
  end.

Fixpoint progDenote (p : prog) (s : stack) : option stack :=
  match p with
  | nil => Some s
  | i :: p' =>
      match instrDenote i s with
      | None => None
      | Some s' => progDenote p' s'
      end
  end.
```

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/formal-math/m11-p30.png]]

*Swarat Chaudhuri, [Berkeley Meeting 11, физическая стр. 30](https://rdi.berkeley.edu/adv-llm-agents/slides/swarat.pdf#page=30). `instrDenote` исполняет одну инструкцию и возвращает `None` при нехватке аргументов. Исполнение всей программы через `progDenote` приведено на следующей странице лекции и в тексте выше.*

#### 3. Компилятор

Для `Binop b e1 e2` сначала компилируется `e2`, затем `e1`, затем операция: такой порядок согласован с тем, как `instrDenote` снимает `arg1` и `arg2`.

```coq
Fixpoint compile (e : exp) : prog :=
  match e with
  | Const n => iConst n :: nil
  | Binop b e1 e2 => compile e2 ++ compile e1 ++ iBinop b :: nil
  end.
```

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/formal-math/m11-p32.png]]

*Компилятор разворачивает дерево выражения в стековую программу: сначала код правого аргумента, затем левого, затем бинарная инструкция. Обратный на вид порядок нужен из-за порядка снятия операндов со стека. Источник: Berkeley Meeting 11, физическая стр. 32.*

Например, выражение `(2 + 3) × 4` превращается в последовательность
`push 4; push 3; push 2; add; multiply`. При пустом исходном стеке
исполнение проходит так:

| Выполненная инструкция | Стек, вершина слева |
|---|---|
| исходное состояние | `[]` |
| `iConst 4` | `[4]` |
| `iConst 3` | `[3, 4]` |
| `iConst 2` | `[2, 3, 4]` |
| `iBinop Plus` | `[5, 4]` |
| `iBinop Times` | `[20]` |

Для сложения и умножения перестановка аргументов случайно сохранила бы
число из-за коммутативности. Но определение компилятора согласует
именно первый и второй аргументы, поэтому доказательство не должно
опираться на это случайное свойство двух выбранных операций.

#### 4. Естественная теорема оказывается слишком слабой для индукции

Хотим доказать корректность запуска с пустой программой продолжения и пустым стеком:

```text
Theorem compile_correct :
  forall e,
    progDenote (compile e) nil = Some (expDenote e :: nil).
```

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/formal-math/m11-p33.png]]

*Первая формулировка корректности сравнивает вычисление выражения с исполнением скомпилированной программы на пустом стеке. Утверждение верно, но фиксированные `nil` скрывают контекст, необходимый индукционной гипотезе. Источник: Berkeley Meeting 11, физическая стр. 33.*

На странице 34 лекции отмечена неудача автоматической попытки, но её
трасса не приведена. Препятствие для прямой индукции видно из определений:
в ветви `Binop` после исполнения `compile e2` остаётся непустой стек
и невыполненное продолжение. Гипотеза, сформулированная только
для пустого стека и без продолжения, к этому случаю неприменима.

#### 5. Усиливаем индукционное утверждение

Нужна лемма, параметризованная произвольными продолжением `p` и стеком `s`:

```coq
Lemma compile_one_instr :
  forall e p s,
    progDenote (compile e ++ p) s =
    progDenote p (expDenote e :: s).
```

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/formal-math/m11-p37.png]]

*Усиленная лемма квантифицирует произвольные стек `s` и продолжение `p`: скомпилированное выражение должно положить своё значение поверх любого стека, не меняя смысла последующей программы. Это и есть недостающий инвариант. Источник: Berkeley Meeting 11, физическая стр. 37.*

Теперь индукционная гипотеза достаточно общая: она описывает компиляцию подвыражения внутри любой окружающей программы. После ассоциативности `++` можно последовательно применить гипотезы для `e2` и `e1`.

```coq
Proof.
  induction e as [n | b e1 IH1 e2 IH2].
  - intros p s. simpl. reflexivity.
  - intros p s. simpl.
    repeat rewrite <- app_assoc.
    rewrite IH2.
    rewrite IH1.
    reflexivity.
Qed.
```

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/formal-math/m11-p38.png]]

*Swarat Chaudhuri, [Berkeley Meeting 11, физическая стр. 38](https://rdi.berkeley.edu/adv-llm-agents/slides/swarat.pdf#page=38). Слайд использует `app_assoc_reverse`, определение которой здесь не показано. Исполняемый текст выше заменяет её переписыванием стандартной `app_assoc`; исходный слайд сохранён без правок.*

Здесь `compile_one_instr` — историческое имя со слайда; лемма описывает
компиляцию целого выражения, а не одной машинной инструкции.
В константной ветви компилятор добавляет ровно одно число,
после чего исполняется `p`. В бинарной ветви сначала применяется
гипотеза для `e2` к стеку `s` и продолжению
`compile e1 ++ iBinop b :: p`. Затем гипотеза для `e1` применяется
уже к стеку `expDenote e2 :: s`. Операция снимает оба результата
и кладёт на стек значение всего выражения.

#### 6. Исходная теорема становится следствием

У общей леммы выбираются `p = nil` и `s = nil`.
Правая часть становится `Some (expDenote e :: nil)`,
а конкатенация с пустым продолжением в левой части удаляется
по `app_nil_r`.

```coq
Theorem compile_correct :
  forall e,
    progDenote (compile e) nil = Some (expDenote e :: nil).
Proof.
  intro e.
  pose proof (compile_one_instr e nil nil) as H.
  rewrite app_nil_r in H.
  exact H.
Qed.
```

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/formal-math/m11-p39.png]]

*Swarat Chaudhuri, [Berkeley Meeting 11, физическая стр. 39](https://rdi.berkeley.edu/adv-llm-agents/slides/swarat.pdf#page=39). Другой способ получить исходную теорему: разобрать конструкторы выражения и применить общую лемму к подвыражениям. В исполняемом коде выше используется прямой выбор пустых продолжения и стека.*

Продолжение действительно может использовать прежний стек.
Если до вычисления выражения на стеке лежало `7`, то компиляция
добавит `20` и оставит `[20, 7]`. Следующая инструкция сложения
даст `[27]`. Такой случай исходная теорема с пустым стеком
не описывала, а усиленная лемма описывает.

```coq
Definition sample_expr : exp :=
  Binop Times (Binop Plus (Const 2) (Const 3)) (Const 4).

Example sample_value : expDenote sample_expr = 20.
Proof. reflexivity. Qed.

Example sample_run :
  progDenote (compile sample_expr) nil = Some (20 :: nil).
Proof. reflexivity. Qed.

Example sample_with_continuation :
  progDenote (compile sample_expr ++ iBinop Plus :: nil) (7 :: nil)
    = Some (27 :: nil).
Proof. reflexivity. Qed.

Example insufficient_stack :
  progDenote (iBinop Times :: nil) nil = None.
Proof. reflexivity. Qed.

Print Assumptions compile_one_instr.
Print Assumptions compile_correct.
```

Эти вычисления проверяют конкретные случаи; лемма доказывает свойство
для всех конечных выражений, стеков и продолжений.
`Print Assumptions` дополнительно показывает, не использованы ли
недоказанные предположения.

### Сравнение способов построения доказательства

| Система | Роль модели | Организация поиска | Проверка результата |
|---|---|---|---|
| ReProver | поиск посылок и генерация тактик | очередь состояний, доступность посылок | исполнение тактик и итоговый терм Lean |
| LIPS | выбор преобразований неравенства | символические правила, фильтрация и ранжирование целей | формализованные преобразования Lean 4 |
| LeanEuclid | формализация геометрической задачи | правила `E` и SMT | в указанном коде SMT-результат принимается через `SMT_VERIF` |
| Lean-STaR | неформальное рассуждение и тактика | независимые траектории; обучение на успешных | исполнение и доказательство в Lean; текст рассуждения не проверяется |
| Draft–Sketch–Prove | неформальное решение и формальный план | автоматизация заполняет пропуски | законченный результат в Isabelle |
| LeanHammer | ранжирование посылок | Aesop, прямое применение лемм и внешний ATP | реконструкция с Duper в Lean |
| COPRA | тактика с учётом состояния и ошибок | обход в глубину, словарь неудач и возврат | система доказательств исполняет действия |
| AlphaProof | формализация задач и шаги доказательства | поиск и обучение, включая специализацию во время решения | Lean и протокол проверки формальных задач |
| ImProver | новая версия существующего доказательства | несколько кандидатов или итеративная правка | сначала Lean, затем выбранная метрика улучшения |

Строки таблицы нельзя ранжировать по одному опубликованному проценту:
они относятся к разным задачам, библиотекам, базовым моделям и бюджетам.

<span id="воспроизводимый-research-workflow"></span>
### Воспроизводимый исследовательский процесс

Для повторения эксперимента сохраняют коммит проекта, версию Lean или Coq,
импорты и контрольные точки моделей. Разбиение данных определяет,
что разрешено видеть при обучении: саму теорему, предшествующий контекст,
посылки из того же файла или другие файлы проекта.
Версия библиотеки может изменить и доступность леммы, и поведение тактики.

Бюджет описывается через реально выполненные операции: запросы к LLM,
предложения тактик, раскрытые состояния, время и стоимость проверки.
В Lean-STaR некорректная тактика расходует генерацию, хотя не создаёт
новое состояние. В LeanHammer один узел может потребовать нескольких
внешних вызовов и реконструкцию. Одно число «шагов» без определения
не позволяет сравнить эти системы.

Журнал содержит предложенное действие, входное состояние, результат
исполнения, ошибку и возврат к прежнему состоянию. Причины остановки
разделяют: доказано, исчерпан бюджет, ошибка окружения, недопустимые
зависимости. Ни тайм-аут, ни отсутствие найденного доказательства
не являются свидетельством ложности теоремы.

<span id="acceptance-contract-без-пропусков-и-подмены-постановки"></span>
### Приёмка: зависимости доказательства и неизменность постановки

Успешно обработанный Lean терм может опираться на недопустимую аксиому.
Следующие примеры компилируются, но не принимаются как доказательства `False`:

```lean
theorem unfinished : False := by sorry
axiom invented : False
theorem forged : False := invented
#print axioms unfinished
#print axioms forged
```

Первый зависит от `sorryAx`, второй — от `invented`.
`#print axioms` показывает транзитивные зависимости: пропуск может находиться
в другом модуле, на который ссылается окончательная теорема.
Поиск слова `sorry` только в её тексте такой случай пропустит.
Так же выявляется зависимость от `SMT_VERIF`, даже если сам текст
геометрического доказательства не содержит ни `sorry`, ни `axiom`.

По официальному руководству [Validating a Lean Proof](https://lean-lang.org/doc/reference/latest/ValidatingProofs/)
обычный допустимый набор включает `propext`, `Classical.choice`
и `Quot.sound`. Доменные аксиомы согласуют отдельно до проверки;
`sorryAx` и произвольная аксиома, позволяющая доказать любое утверждение,
в этот набор не входят. Аксиомы нативного вычисления зависят от версии
Lean и также требуют отдельного решения о доверии.

Кроме зависимостей сравнивают итоговое утверждение с неизменяемым
доверенным условием задачи, включая определения. Если агент заменил
теорему на `True` или переопределил смысл используемого предиката,
успешная проверка нового терма не решает исходную задачу.

Для случайных ошибок сборка и просмотр зависимостей дают полезную
защиту. Для намеренно вредоносного проекта этого недостаточно:
тактики и метапрограммы выполняют код. Их запускают в изоляции
без секретов, а принятие результата отделяют от доверия к этому процессу.
Описанный в актуальном руководстве усиленный путь с `comparator`
сопоставляет задачу, экспортирует терм и проверяет его вне изолированного
процесса. Это отдельный протокол, зависящий от версии инструментов.
Для примеров этой главы запускались Lean 4.19.0 и Coq 8.20.1;
`comparator`, полный LeanEuclid и обучение моделей здесь не запускались.
