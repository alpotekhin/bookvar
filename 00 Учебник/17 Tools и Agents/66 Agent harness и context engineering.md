# Управляющая программа агента и контекст

Пользователь просит изменить `timeout` в конфигурации с 30 на 45 и проверить
результат тестом. Модель читает файл, предлагает правку и получает подтверждение
записи. Теперь она отвечает «готово», хотя тест ещё не запускался. Программа
может вернуть этот ответ пользователю или продолжить работу, указав, какая
проверка осталась. Выбор правила завершения меняет результат даже при одинаковых
предложениях модели.

Управляющая программа агента, или agent harness, собирает вход модели,
исполняет разрешённые действия и сохраняет состояние между вызовами.
Для приведённой задачи ей нужно знать текущую версию конфигурации,
результат теста именно для этой версии, оставшиеся ограничения и историю
уже выполненных действий. Часть этих сведений передаётся модели, а часть
используется программой для проверки её предложений.

## 1. Из чего состоит один шаг

Одна итерация включает подготовку запроса, вывод модели и обработку результата.
До запроса программа читает состояние задачи и собирает контекст. После
вывода она разбирает предложенное действие, проверяет права, вызывает
инструмент и записывает наблюдение. Если модель предлагает финальный ответ,
программа применяет правило завершения вместо вызова инструмента.

Для изменения `timeout` последовательность может выглядеть так:

| Шаг | Предложение модели | Подтверждённое состояние после обработки |
|---|---|---|
| 1 | Прочитать конфигурацию | timeout=30, версия 0 |
| 2 | Записать timeout=45 при ожидаемой версии 0 | timeout=45, версия 1; проверки версии 1 ещё нет |
| 3 | Сообщить «готово» | Завершение отклонено: нужен тест текущей версии |
| 4 | Запустить проверку | Тест прошёл для версии 1 |
| 5 | Сообщить результат | Можно завершить, если версия конфигурации всё ещё 1 |

Последняя оговорка исключает принятие устаревшего теста: если после проверки
файл снова изменён, её результат уже не подтверждает новое содержимое.
Полный исполняемый вариант этого учебного эпизода приведён в конце главы.

[Unrolling the Codex agent loop](https://openai.com/index/unrolling-the-codex-agent-loop/)
описывает реализацию Codex CLI на 23 января 2026 года: в начальный input входят инструкции
модели, описание sandbox и разрешений, проектные `AGENTS.md`, сведения о среде,
схемы инструментов и сообщение пользователя. После вызова инструмента его
результат добавляется к истории, и новая последовательность снова отправляется
модели. Это пример конкретного формата и порядка сообщений, а не обязательный
контракт для любой агентной системы.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/agent-harness-2026-10/swe-agent-prompt-workflow.png]]

*John Yang et al., [SWE-agent v3, Appendix C, Figure 26, PDF p. 39](https://arxiv.org/pdf/2405.15793v3#page=39), CC BY 4.0. Исходная схема и английская подпись сохранены.*

В SWE-agent начальные system, demonstration и instance messages добавляются
до первой итерации. Дальше выбор сообщения зависит от результата: обычный
вывод, успешное действие без вывода или ошибка разбора ответа модели.
Пустой stdout сам по себе неоднозначен, поэтому в показанной реализации
его сопровождает явное сообщение об успешном исполнении. Ошибка формата
возвращается для исправления; такое действие не должно незаметно исполняться
как shell-команда.

На схеме есть и другие причины остановки: команда `submit`, превышение
стоимости и повторные ошибки формата. Они заканчивают эпизод по разным причинам.
Ни превышение лимита, ни хорошо сформатированный `submit` не доказывают,
что ошибка в программе действительно исправлена.

## 2. Сборщик контекста

Контекст — это не вся информация, которой располагает система. Это выбранная
проекция состояния, помещённая в один вызов модели. Сборщик контекста решает,
что включить и в каком порядке:

| Слой | Примеры | Обычное время жизни |
|---|---|---|
| стабильные инструкции | роль, правила безопасности, формат работы | несколько сессий или версия модели |
| схемы возможностей | инструменты, MCP-ресурсы, допустимые параметры | до изменения конфигурации |
| задача | запрос, критерии готовности, ограничения | один эпизод |
| состояние среды | cwd, права, ветка, запущенные процессы | до следующего события |
| рабочая траектория | сообщения, действия, наблюдения | растёт каждый шаг |
| найденные сведения | фрагменты файлов, документы, память | пока полезны текущему решению |
| событийные вставки | ошибка, смена прав, reminder | до обработки или истечения |

[![Prompt engineering и повторная сборка контекста в агентном цикле](https://www-cdn.anthropic.com/images/4zrzovbb/website/faa261102e46c7f090a2402a49000ffae18c5dd6-2292x1290.png)](https://www-cdn.anthropic.com/images/4zrzovbb/website/faa261102e46c7f090a2402a49000ffae18c5dd6-2292x1290.png)

*Prompt engineering меняет отдельный prompt, а context engineering заново
отбирает вход перед каждым вызовом модели. Источник: Anthropic Applied AI team,
[Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents),
схема «Prompt engineering vs. context engineering».*

После записи `timeout=45` модели нужны исходное требование, подтверждение
правки и сведения о незапущенном тесте. Полный журнал установки зависимостей
обычно не помогает выбрать следующий шаг. Он может остаться во внешнем
хранилище с адресом, по которому его можно открыть при необходимости.
Так отбор контекста сохраняет доступ к данным, не требуя каждый раз включать
все их токены во вход.

[![Выбор подробности системных инструкций](https://www-cdn.anthropic.com/images/4zrzovbb/website/0442fe138158e84ffce92bed1624dd09f37ac46f-2292x1288.png)](https://www-cdn.anthropic.com/images/4zrzovbb/website/0442fe138158e84ffce92bed1624dd09f37ac46f-2292x1288.png)

*Две крайности системной инструкции: каталог частных случаев и слишком общее
пожелание. Между ними — компактная роль, способ работы и правила эскалации.
Источник: Anthropic Applied AI team,
[Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents),
схема «Calibrating the system prompt».*

Левая часть рисунка пытается заранее записать в prompt все ветви процесса. Такое
описание быстро устаревает и конкурирует с текущими данными. Правая оставляет
слишком много неоднозначности. Средний вариант фиксирует устойчивые принципы, а
меняющиеся сведения и узкие процедуры подгружаются как инструменты, документы
или skills только тогда, когда они нужны.

### Загрузка сведений по мере необходимости

При предварительной загрузке найденные документы помещаются во вход до начала
работы модели. При загрузке по запросу в контексте сначала остаются адреса
и краткие описания: путь к файлу, имя функции, идентификатор отчёта.
Модель выбирает, какой объект прочитать следующим. Эти способы можно сочетать.

Для исправления конфигурации программе достаточно заранее сообщить рабочий
каталог, ограничения записи и команду нужного теста. После поиска по ключу
`timeout` модель получает несколько совпадений, читает соответствующий файл
целиком или нужный диапазон, затем проверяет места использования настройки.
Если сразу загрузить весь репозиторий, значительная часть входа окажется
не связана с этой правкой. Если передать только имя файла без возможности
чтения, модель будет вынуждена угадывать его содержимое.

В [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
такое поэтапное раскрытие информации описано как just-in-time retrieval
и progressive disclosure. Цена подхода — дополнительные вызовы и зависимость
от качества навигации. Найденная ссылка не равна прочитанному документу,
а старый индекс может ссылаться на уже изменившуюся версию.

### Бюджет одного входа

Окно ограничивает суммарный объём входа и генерации. Число символов в
исходном файле для этого недостаточно: учитываются токены после сериализации
сообщений и инструментов, а для мультимодального входа — правила конкретной
модели. В учебном расчёте обозначим окно через $W$, весь вход через $I$,
место под выход через $O$, технический запас через $R$:

$$
\begin{aligned}
I &= T_{\mathrm{instructions}}+T_{\mathrm{tools}}\\
  &\quad+T_{\mathrm{task}}+T_{\mathrm{state}}+T_{\mathrm{history}},\\
I+O+R &\le W.
\end{aligned}
$$

Пусть $W=8192$, под ответ оставлены 1024 токена, запас равен 256.
Инструкции занимают 1200, инструменты 500, задача 280, сведения о среде 200.
Для истории остаётся 4732 токена. Текущие 4500 помещаются, но следующий
результат инструмента ожидается объёмом 1700. Добавлять его без изменения
истории уже нельзя: общий объём с резервами составит 9660.

~~~python
window = 8192
output_reserve, safety = 1024, 256
fixed = 1200 + 500 + 280 + 200
history, incoming = 4500, 1700
history_capacity = window - output_reserve - safety - fixed
assert history_capacity == 4732
assert fixed + history + output_reserve + safety == 7960
assert fixed + history + incoming + output_reserve + safety == 9660

summary, recent_tail = 600, 1200
compaction_instruction = 100
summary_request = fixed + history + compaction_instruction + summary + safety
after_compaction = fixed + summary + recent_tail + incoming + output_reserve + safety
assert summary_request == 7636 and summary_request <= window
assert after_compaction == 6960 and after_compaction <= window
~~~

В этом расчёте старую часть истории заменяют 600 токенами резюме, а последние
1200 сохраняют без изменений. Сжатие запускается до добавления большого
наблюдения; отдельный запрос на резюме тоже помещается в окно. Числа заданы
для примера и не означают, что любой текст удастся без потерь сжать до 600
токенов. Если сам запрос на сжатие уже не помещается, требуется иной
протокол сокращения входа, а не повтор того же переполненного запроса.

## 3. Стабильный префикс и динамический суффикс

Порядок влияет не только на внимание модели, но и на стоимость. Prompt cache
обычно переиспользует точный общий префикс. Поэтому стабильные инструкции,
примеры и схемы инструментов размещают раньше, а изменяющиеся наблюдения —
позже. Если на каждом шаге переставлять инструменты или переписывать системный
prompt, кеш перестаёт совпадать.

Кеш хранит вычисленные KV-состояния префикса, а не готовый ответ на вопрос.
Новая часть входа всё равно обрабатывается, а новый ответ генерируется
заново. В [официальной документации OpenAI о prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)
совпадение относится к полному сериализованному префиксу, включая инструкции
и схемы инструментов. Наличие подходящего совпадения не гарантирует cache hit:
действуют правила размещения, порогов, контрольных точек и времени хранения.

Пусть условные token IDs стабильной части равны `[10,11,12,13]`,
а результат последнего действия добавляет `[20,21]`. При следующем
действии общий префикс можно сохранить. Если же меняющуюся метку времени
ставить в самое начало, совпадение оборвётся на ней.

~~~python
def common_prefix_length(left, right):
    for index, (a, b) in enumerate(zip(left, right)):
        if a != b:
            return index
    return min(len(left), len(right))

stable = [10, 11, 12, 13]
first = stable + [20, 21]
next_request = first + [30, 31]
assert common_prefix_length(first, next_request) == 6
assert common_prefix_length([900] + first, [901] + next_request) == 0
assert common_prefix_length(stable, [10, 11, 99, 13]) == 2
~~~

Этот код проверяет только совпадение последовательностей. Он не моделирует
серверные контрольные точки кеша, тарификацию или задержку.

Но оптимизация кеша не должна скрывать изменение реальности. При смене рабочей
директории или прав harness сообщает новое состояние. В описании Codex CLI
от января 2026 года смена разрешений добавляется новым developer-сообщением,
а смена cwd — новым user-сообщением. Это сохраняет прежние элементы префикса.
Проверка фактических прав при исполнении всё равно использует текущую
политику; старое разрешение в истории не должно её отменять.

## 4. Состояние не равно стенограмме

В длинной работе полезно хранить минимум три объекта отдельно:

- **полный журнал событий** — неизменяемая трасса для отладки и аудита;
- **активный контекст** — ограниченный набор токенов для следующего вызова модели;
- **авторитетное состояние задачи** — цели, завершённые и незавершённые шаги,
  версии артефактов, бюджеты и блокировки.

Если единственным состоянием служит чат, после сжатия может исчезнуть имя файла
или обязательная проверка. Если единственным источником истины становится
резюме модели, вымышленное «тесты прошли» будет выглядеть так же убедительно,
как фактический результат. Поэтому состояние задачи обновляется событиями и
сверяется с внешней средой; резюме лишь помогает модели его прочитать.

В примере с конфигурацией журнал может содержать событие записи версии 1
и отдельное событие теста этой версии. Активному контексту достаточно
небольшого сообщения «версия 1 записана; тест ещё не выполнен» до проверки
и «тест версии 1 прошёл» после неё. Состояние завершения меняется по
результату исполнителя и verifier, а не по фразе `tests passed`, которую
модель могла написать в резюме.

При сжатии удаляются или заменяются элементы активного представления.
Это не должно удалять соответствующие события из хранилища доказательств.
И наоборот, сохранённый большой журнал не помогает модели, если необходимые
сведения не выбраны для следующего входа.

## 5. Использование длинной истории

В [Lost in the Middle](https://aclanthology.org/2024.tacl-1.9/) авторы
разделили два изменения входа: перестановку документа с ответом и увеличение
числа документов без ответа. В одном контролируемом примере вопрос о первом
лауреате Нобелевской премии по физике остаётся тем же. Меняются место нужного
отрывка и число отвлекающих отрывков, но желаемый ответ не меняется.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/agent-harness-2026-10/lost-middle-task-controls.png]]

*Nelson F. Liu et al., [Lost in the Middle, Figures 2–4, PDF p. 4 / печатная p. 160](https://aclanthology.org/2024.tacl-1.9.pdf#page=4), CC BY 4.0. Исходные примеры входа, ответа и двух способов изменения контекста.*

Так можно отличить нехватку факта во входе от неудачного использования
присутствующего факта. В опытах с 10, 20 и 30 документами качество ряда
исследованных моделей зависело от позиции: начало и конец часто давали
более высокий результат, чем середина. На следующем рисунке показан один
из этих опытов, с GPT-3.5-Turbo-0613 и 20 документами. Пунктир соответствует
ответам вообще без документов; в части позиций добавление источников
не улучшило этот baseline.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/agent-harness-2026-10/lost-middle-position-effect.png]]

*Nelson F. Liu et al., [Lost in the Middle, Figure 1, PDF p. 2 / печатная p. 158](https://aclanthology.org/2024.tacl-1.9.pdf#page=2), CC BY 4.0. Результаты исходного исследования, не замер современных моделей.*

Из этого опыта не следует единая кривая для любой модели и любой задачи.
В самой работе Claude-1.3 почти безошибочно решал другую, синтетическую
задачу поиска значения по ключу, хотя испытывал трудности в вопросах
по нескольким документам. Проверять нужно и извлечение точной строки,
и использование найденного факта в требуемом ответе.

У агентной истории есть дополнительные источники ошибок. Сообщение
`timeout=30` могло быть верным до правки, а теперь устарело. Старое
«следующий шаг — изменить файл» уже не нужно после успешной записи.
Несколько одинаковых выводов теста занимают место без новых сведений.
Эти случаи требуют обновления или отбора контекста, даже когда всё
содержимое формально помещается в окно.

Основные способы управления историей различаются по тому, что они могут
потерять:

| Метод | Операция | Риск |
|---|---|---|
| усечение | удалить самые старые сообщения | исчезает причинная цепочка |
| очистка наблюдений | заменить старый большой вывод ссылкой или выдержкой | источник может стать недоступен |
| выборка | вернуть найденные фрагменты по запросу | поиск пропускает критический факт |
| структурированные заметки | вынести факты и прогресс в файл/БД | заметка устаревает без протокола обновления |
| compaction | заменить траекторию компактным представлением | резюме искажает детали и незавершённость |
| новая сессия | передать состояние в чистый контекст | плохой handoff маскирует потерю |

В описанной в статье SWE-agent политике сохранялись полные тексты последних
пяти наблюдений, а более старые заменялись однострочным указанием объёма,
например `Old output omitted (101 lines)`. При семи наблюдениях это
означает сокращение первых двух с сохранением пяти последних.
Последовательность действий при этом остаётся в истории.
Это очистка вывода, а не LLM-резюме содержания: из строки о 101 пропущенной
строке нельзя восстановить их текст. Если прежний вывод снова нужен,
его получают из сохранённого журнала или выполняют допустимое новое чтение.

<span id="6-compaction-как-преобразование-состояния"></span>
## 6. Compaction и сохранение состояния задачи

Сжатие следует запускать до переполнения окна, оставляя место для самого
запроса на compaction и ответа. Оно должно сохранять не «общую тему разговора»,
а информацию, необходимую для продолжения:

1. исходную цель и критерии завершения;
2. принятые решения и их основания;
3. фактическое состояние артефактов;
4. неудачные попытки, если их нельзя безопасно повторять;
5. незавершённые шаги и текущую блокировку;
6. точные идентификаторы, пути, версии и ссылки на первичные данные.

Compaction преобразует активное представление истории. Она не выполняет
незавершённые действия и не подтверждает успех задачи. После сжатия программа
проверяет, сохранились ли цель и ограничения, не потеряны ли неизвестные исходы
операций и ссылки на результаты.

Существуют разные форматы такого преобразования. LLM может написать обычное
текстовое резюме. В [Responses API](https://developers.openai.com/api/docs/guides/compaction)
результат включает непрозрачный compaction item. Его нельзя отредактировать
как свободный текст. По документации на 20 октября 2026 года отдельно вызванный
`/responses/compact` возвращает целое следующее окно; его нужно передать
дальше полностью, а не извлекать только `encrypted_content`. Это отличается
от управления массивом при серверной автоматической compaction.
Внешние подтверждения действий и прикладное состояние задачи хранятся
по правилам приложения, независимо от формата сжатого контекста.

### Что именно сжимает OpenHands

В [OpenHands Context Condenser](https://docs.openhands.dev/sdk/guides/context-condenser)
активная история представлена объектом `View`, построенным из событий.
Condenser возвращает другое представление или событие `Condensation`
с идентификаторами заменяемых событий, резюме и местом его вставки.
Так исходный журнал и представление для модели остаются разными объектами.

[![Замена старых событий резюме в OpenHands](https://mintcdn.com/allhandsai/hwL6uO0ZqM-lmlYG/sdk/guides/assets/condenser_overview_light_mode.png?fit=max&auto=format&n=hwL6uO0ZqM-lmlYG&q=85&s=dc85afa9f2821b1f7a305ad1406ab3d9)](https://mintcdn.com/allhandsai/hwL6uO0ZqM-lmlYG/sdk/guides/assets/condenser_overview_light_mode.png?fit=max&auto=format&n=hwL6uO0ZqM-lmlYG&q=85&s=dc85afa9f2821b1f7a305ad1406ab3d9)

*OpenHands contributors, [Context Condenser](https://docs.openhands.dev/sdk/guides/context-condenser), исходная обзорная схема. Защищённое начало истории и границы связанных групп событий на ней не показаны; они рассматриваются ниже по коду.*

В [закреплённом коде LLMSummarizingCondenser](https://github.com/OpenHands/software-agent-sdk/blob/0996c33916c2a977ea9fe38deee660ff0e1389f2/openhands-sdk/openhands/sdk/context/condenser/llm_summarizing_condenser.py)
`max_size` ограничивает число событий, а не число токенов.
Один результат инструмента может быть длиннее сотни коротких событий,
поэтому у реализации есть и отдельная проверка токенов. `keep_first`
сохраняет начало; свежий хвост оставляется без суммаризации. Диапазоны
подбираются по границам атомарных групп, чтобы не разорвать связанное
взаимодействие инструмента.

Для показанной в документации конфигурации `max_size=10, keep_first=2`
11 независимых событий превышают порог. Плановый размер нового представления
равен `10//2=5`: два начальных события, одно резюме и два последних.
При индексах от 0 до 10 сжимаются события 2–8. Реальные границы могут
сдвинуться из-за группировки связанных событий; пять — не обещание
точного результата в любой траектории.

В той же ревизии событие превышения `max_size` считается мягкой причиной
сжатия, а нехватка токенов — жёсткой. Если мягкое сжатие недоступно,
`RollingCondenser` может вернуть прежнее представление. Так нельзя
поступать с уже переполненным входом: для жёсткого случая предусмотрено
восстановление или ошибка. Эти детали зависят от версии библиотеки;
само имя «condenser» не задаёт единой политики.

### Handoff после записи с неизвестным исходом

Пусть агент должен создать одну заметку Runbook в проекте `P7`.
Перед запросом приложение сохраняет в журнале имя `create_note`, проект,
название и ключ `task-42-note-1`. После разрешения на эти аргументы запрос
отправлен, но соединение обрывается до ответа. Среда могла уже создать объект;
запись `timeout` не означает ни успех, ни отсутствие эффекта.

Резюме «Создание заметки почти закончено; повторить запрос и сообщить
об успехе» теряет ключ, неопределённость и необходимость проверки.
Для продолжения нужно сохранить эти сведения явно:

```json
{
  "task_id": "task-42",
  "goal": "Exactly one Runbook note in project P7",
  "status": "in_progress",
  "pending_operation": {
    "name": "create_note",
    "arguments": {"project": "P7", "title": "Runbook"},
    "idempotency_key": "task-42-note-1",
    "outcome": "unknown",
    "event_ref": "events/42#17"
  },
  "next_action": "read_by_idempotency_key",
  "terminal_verified": false,
  "forbidden": ["create_with_new_key", "claim_success_without_readback"]
}
```

Исправленное резюме говорит: «Ответ на запись потерян; сначала прочитать
состояние по `task-42-note-1`, не создавать новый ключ. Завершение не
проверено». После возобновления harness перечитывает текущую политику и
состояние проекта. Если чтение возвращает `note_id=N9`, проект `P7`,
название `Runbook` и тот же ключ, сверяются эти поля. Отсутствие дубликатов
нуждается в контракте дедупликации сервера или отдельной проверке;
единственный найденный объект ещё не доказывает, что других нет.
При eventual consistency ответ `not_found` одного чтения также не доказывает
отсутствие эффекта. Тогда используют контракт идемпотентного API или
сохраняют неопределённый исход. Механизм повторов подробно разобран
в [[00 Учебник/17 Tools и Agents/65 Tool use — от вызова функции к действию#Потерянный ответ после записи|главе 65]].

При передаче состояния операция с `outcome=unknown` должна остаться
неразрешённой, с прежним ключом. `terminal_verified` остаётся false до чтения
и сверки результата. Указатель `events/42#17` связывает компактное описание
с полным исходным запросом. Это учебный пример отказа; внешняя заметка
здесь не создавалась.

Ниже показана проверка защищённых полей перед продолжением именно этого
эпизода с неизвестным исходом. `trusted` представляет сохранённую запись приложения,
а `candidate` — предложенное компактное представление. Свободный текст
резюме может меняться, но эти поля до новой сверки со средой изменяться
не должны.

~~~python
from copy import deepcopy

trusted = {
    "task_id": "task-42",
    "goal": "Exactly one Runbook note in project P7",
    "status": "in_progress",
    "pending_operation": {
        "name": "create_note",
        "arguments": {"project": "P7", "title": "Runbook"},
        "idempotency_key": "task-42-note-1",
        "outcome": "unknown",
        "event_ref": "events/42#17",
    },
    "terminal_verified": False,
    "forbidden": ["create_with_new_key", "claim_success_without_readback"],
}

def valid_checkpoint(candidate):
    return all(candidate.get(key) == value for key, value in trusted.items())

candidate = deepcopy(trusted)
candidate["summary"] = "Read back task-42-note-1 before deciding what to do."
assert valid_checkpoint(candidate)
bad = deepcopy(candidate)
bad["pending_operation"]["idempotency_key"] = "new-key"
assert not valid_checkpoint(bad)
bad = deepcopy(candidate)
bad.update(status="done", terminal_verified=True)
assert not valid_checkpoint(bad)
~~~

Этот тест обнаруживает потерю зафиксированных ограничений. Он не проверяет
истинность произвольного текста резюме и не заменяет чтение результата.
После подтверждённого исхода приложение обновит авторитетное состояние,
и проверка следующего checkpoint будет опираться уже на него.

<span id="7-reminder-tokens--не-особый-вид-токена"></span>
## 7. Текстовые напоминания: reminder tokens

В этой главе reminder tokens означают текст, который управляющая программа
добавляет к входу модели: напоминание о цели, ограничении или незавершённой
проверке. Это не название дополнительного блока памяти в архитектуре LLM.
Строка `<system-reminder>` сама по себе также не задаёт полномочия сообщения:
роль и происхождение определяются приложением и протоколом.

В SWE-agent перед началом задачи повторяются ограничения интерфейса
и советы, полученные после анализа неудачных траекторий.
В [instance template, Appendix C, Figure 29](https://arxiv.org/pdf/2405.15793v3#page=42)
есть, например, следующий пункт. Сохранён английский текст источника:

> If you run a command and it doesn't work, try running a different command. A command that did not work once will not work the second time unless you modify it!

*John Yang et al., SWE-agent v3, Figure 29, CC BY 4.0. Фигура начинается
на PDF p. 41, продолжается на p. 42, общая подпись находится на p. 43.*

Совет относится к повтору неудачного способа работы с интерфейсом.
Временная недоступность сервиса может исчезнуть без изменения аргументов;
безопасность такого повтора определяют по контракту операции. Присутствие
совета в стартовом шаблоне не доказывает пользу повторения той же фразы
после каждого действия. В описании системы
начальные шаблоны используются однократно, а `next step` — после результатов.
Для динамического напоминания нужно отдельно определить событие, содержание
и условие удаления.

### Напоминание о непроверенной правке

После записи версии 1 можно перед попыткой завершения добавить сообщение:
«Проверка версии 1 ещё не выполнена; запусти тест текущей версии».
После успешного теста версии 1 напоминание устаревает. Если затем появилась
версия 2, прежний результат снова не подтверждает текущий артефакт.

~~~python
def update_reminders(slots, state):
    updated = dict(slots)
    current_checked = (
        state["tested_revision"] == state["revision"]
        and state["test_passed"] is True
    )
    if current_checked:
        updated.pop("verification", None)
    else:
        updated["verification"] = {
            "id": f"verify-revision-{state['revision']}",
            "source": "harness",
            "text": f"Run the test for current revision {state['revision']}.",
        }
    return updated

state = {"revision": 1, "tested_revision": None, "test_passed": False}
slots = update_reminders({}, state)
assert len(update_reminders(slots, state)) == 1
state.update(tested_revision=1, test_passed=True)
assert update_reminders(slots, state) == {}
state["revision"] = 2
assert update_reminders({}, state)["verification"]["id"] == "verify-revision-2"
~~~

Повторная подготовка входа не накапливает одинаковые сообщения: напоминание
хранится в одном слоте. Смена ревизии меняет его идентификатор, а подтверждённая
проверка удаляет его. Пример использует доверенное состояние исполнителя;
найденный на странице текст с таким же тегом не может обновить `slots`
или выдать себе роль управляющей инструкции.

Сам текст не запрещает раннее завершение. Отказ выдаёт verifier, проверяющий
текущий артефакт. Напоминание сообщает модели причину отказа и способ
продолжить работу. Аналогично, фраза «не записывай в этот каталог» не заменяет
ограничения доступа к файловой системе.

Полезность формулировки проверяют сравнением на одних и тех же задачах,
с фиксированными моделью, инструментами и бюджетами. Сравнивают число
преждевременных завершений и успех всей задачи, а также лишние вызовы и токены.
Если одновременно изменить модель и добавить напоминание, результат
не позволит установить вклад самого напоминания.

### Событийные обработчики, или hooks

Вместо одной большой функции harness может вызывать обработчики в
определённых точках: перед инструментом, после его результата или при
попытке завершения. Один обработчик проверяет возможность действия,
другой подготавливает контекст следующего запроса. Событие после записи
уже не может отменить побочный эффект простым отказом; запрет исполнения
нужен до неё.

В [Claude Code hooks](https://code.claude.com/docs/en/hooks#add-context-for-claude)
это разные каналы. `additionalContext` добавляет сведения к следующему
входу модели, а решение о блокировке использует поля соответствующего
события. Например, `PostToolUse` может сообщить, какой тест нужен после
редактирования. Приложение оборачивает текст в system reminder.
Вставка буквального тега в результат поиска не создаёт такого события.

При восстановлении сессии сохранённая вставка может быть воспроизведена
из журнала, а не вычислена заново. Поэтому помещённая туда ветка Git,
версия файла или время проверки могут устареть. Обработчик и сборщик
контекста должны различать историческое наблюдение и текущее состояние.
Имена событий и поля различаются между фреймворками; функция
`update_reminders` выше показывает собственную политику отбора,
а не универсальный API hooks.


## 8. Выполнение, права и изоляция

Перед реальным действием запрос проходит цепочку проверок:

1. синтаксический разбор и JSON-schema;
2. семантическая проверка значений, путей и ресурсов;
3. решение политики: разрешить, запретить или запросить подтверждение;
4. выполнение в sandbox с ограничениями сети, файлов, процессов и секретов;
5. нормализация результата и обновление авторитетного состояния.

Разрешения должны учитывать не только имя инструмента. Команда чтения способна
раскрыть секрет; символическая ссылка может вывести путь за пределы рабочей
области; разрешённый MCP-сервер не становится автоматически доверенным.
В январском описании Codex CLI sandbox встроенного shell отделён от внешних
инструментов: исполнение на MCP-сервере не становится изолированным только
потому, что локальный shell ограничен. Это свойство рассматриваемой реализации.

## 9. Повторы и частичные побочные эффекты

Harness классифицирует ошибку прежде, чем повторять действие. Для временного
503 проверяют, допускает ли операция безопасный повтор; затем применяют
задержку и предел попыток. Неверный аргумент возвращают модели с пояснением.
Отказ в доступе нельзя исправлять поиском обходного пути. Если соединение
оборвалось после записи, исход устанавливают по контракту операции, как
в примере handoff выше.

Пределы задаются отдельно для числа вызовов модели, вызовов инструментов,
прошедшего времени, токенов и стоимости. Исчерпание бюджета означает
`incomplete`, а не успех.
Прогресс сохраняется так, чтобы новый запуск продолжил работу без повторения
необратимых действий.

Checkpoint должен содержать и счётчики расхода. Иначе повторный запуск
сможет обходить лимит, каждый раз начиная подсчёт заново. Остановка по
времени может также произойти посреди работающего процесса. Его идентификатор
и состояние нужно сохранить: отсутствие ответа не означает, что процесс
завершился и его можно безопасно запустить ещё раз.

## 10. Наблюдаемость и доказательство завершения

Для разбора ошибки трасса связывает запрос модели, предложенное действие,
решение политики и наблюдение. В ней сохраняют:

- хэш/версию собранного контекста и политики compaction;
- идентификатор версии модели и параметры генерации;
- запрошенное действие, решение policy engine и подтверждение пользователя;
- фактически исполненные аргументы, ссылки на stdout/stderr, задержку и стоимость;
- изменение состояния и результат независимой проверки.

Хеш контекста позволяет сравнить два входа, но восстановить вход по одному
хешу нельзя. Для воспроизведения нужны сами разрешённые к хранению сообщения,
версии инструментов и снимок исходной среды. Секреты не должны попадать
в открытый журнал; доступ к исходным выводам и очищенным трассам задают отдельно.
Даже полная трасса не гарантирует побитового повторения внешнего сервиса
или генерации модели.

Фраза модели «готово» является предложением остановиться. Для изменения
конфигурации терминальное условие включает значение настройки и тест
текущей ревизии. Правило должно существовать до попытки завершения:
иначе модель может выбрать удобный тест уже после получения результата.

### Работа в нескольких сессиях

В [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
длительная разработка разделена на начальную и последующие рабочие сессии.
Первая подготавливает список проверяемых требований, запуск окружения
и сведения для продолжения. Дальше агент выбирает незавершённую функцию,
вносит изменение, проверяет её и сохраняет результат.
В статье начальный и рабочий агенты отличаются пользовательскими
инструкциями; это не обязательно разные модели или разные harness.

Вместо записи «чат работает» проверяемое требование может звучать так:
нажатие New Chat создаёт беседу, отправленный текст появляется в ней,
ответ отображается, а беседа доступна после повторного открытия страницы.
Unit-тест обработчика кнопки не доказывает всю эту последовательность.
В следующей сессии сначала устанавливают текущее состояние приложения,
а не принимают прежнюю отметку `passes=true` за свежий результат.

Артефакт прогресса помогает найти выполненную работу и оставшиеся шаги.
История версий помогает установить, к какой редакции относится тест.
Оба источника требуют сверки после изменения кода или окружения.
Коммиты и другие изменения состояния делают в пределах разрешённого
пользователем процесса; рекомендация из учебного примера не даёт
приложению дополнительных полномочий.

## Практика и первоисточники

### Исполняемый цикл и продолжение из checkpoint

Следующий пример воспроизводит таблицу из начала главы. Конфигурация,
тест и журнал находятся в памяти; предложения модели заданы списком.
Это позволяет отдельно проверить правила управляющей программы без вызова
LLM и без изменения настоящих файлов.

Контекст состоит из инструкций, истории и свежих сведений об окружении.
Журнал сохраняется отдельно. Проверка завершения читает фактическое состояние
учебной среды и результат теста, а не текст `answer`. При возврате checkpoint
сохраняются история, использованные идентификаторы и счётчики.

~~~python
from copy import deepcopy
import hashlib
import json

def initial_state():
    return {
        "status": "in_progress", "reason": None,
        "model_steps": 0, "tool_calls": 0,
        "tested_revision": None, "test_passed": False,
        "history": [], "events": [], "used_call_ids": [],
    }

def build_context(state, env, can_write):
    return [
        {"role": "system", "content": "Use allowed tools and report verified facts."},
        {"role": "user", "content": "Set timeout to 45 and test the current revision."},
        *deepcopy(state["history"]),
        {"role": "developer", "content": {
            "current_revision": env["revision"], "can_write": can_write,
            "tested_revision": state["tested_revision"],
        }},
    ]

def run_episode(proposals, env, checkpoint=None, *,
                model_limit=8, tool_limit=4, can_write=True):
    state = deepcopy(checkpoint) if checkpoint is not None else initial_state()
    state.update(status="in_progress", reason=None)

    def event(kind, **payload):
        state["events"].append({
            "number": len(state["events"]) + 1, "kind": kind,
            **deepcopy(payload),
        })

    def stop(reason):
        state.update(status="incomplete", reason=reason)
        return state

    for proposal in proposals:
        if state["model_steps"] >= model_limit:
            return stop("model_budget")
        context = build_context(state, env, can_write)
        digest = hashlib.sha256(
            json.dumps(context, sort_keys=True).encode()
        ).hexdigest()
        event("model_input", sha256=digest)
        state["model_steps"] += 1
        state["history"].append({"role": "assistant", "content": deepcopy(proposal)})

        if proposal.get("kind") == "final":
            verified = (
                env["timeout"] == 45
                and state["tested_revision"] == env["revision"]
                and state["test_passed"] is True
                and proposal.get("timeout") == env["timeout"]
            )
            event("finish_check", revision=env["revision"], passed=verified)
            if verified:
                state.update(status="done", reason="verified")
                return state
            state["history"].append({
                "role": "developer",
                "content": "Goal or test of the current revision is not verified.",
            })
            continue

        if proposal.get("kind") != "tool":
            return stop("invalid_proposal")
        call_id = proposal.get("call_id")
        if not isinstance(call_id, str) or not call_id or call_id in state["used_call_ids"]:
            return stop("invalid_call_id")
        state["used_call_ids"].append(call_id)
        name = proposal.get("name")
        args = proposal.get("arguments", {})
        if state["tool_calls"] >= tool_limit:
            observation = {"ok": False, "error": "tool_budget", "executed": False}
        elif name == "set_timeout" and not can_write:
            observation = {"ok": False, "error": "permission_denied", "executed": False}
        else:
            state["tool_calls"] += 1
            if name == "read_config":
                observation = {"ok": True, **deepcopy(env)}
            elif name == "set_timeout":
                if (not isinstance(args, dict)
                        or type(args.get("value")) is not int or args.get("value") != 45
                        or type(args.get("expected_revision")) is not int
                        or args.get("expected_revision") != env["revision"]):
                    observation = {"ok": False, "error": "precondition_failed"}
                else:
                    env.update(timeout=45, revision=env["revision"] + 1)
                    state.update(tested_revision=None, test_passed=False)
                    observation = {"ok": True, **deepcopy(env)}
            elif name == "run_test":
                state.update(tested_revision=env["revision"],
                             test_passed=env["timeout"] == 45)
                observation = {"ok": True, "revision": env["revision"],
                               "passed": state["test_passed"]}
            else:
                observation = {"ok": False, "error": "unknown_tool"}
        event("tool_result", call_id=call_id, name=name, result=observation)
        state["history"].append({
            "role": "tool", "call_id": call_id, "content": observation,
        })
        if observation.get("error") in {"tool_budget", "permission_denied"}:
            return stop(observation["error"])
    return stop("no_more_proposals")

proposals = [
    {"kind": "tool", "call_id": "c1", "name": "read_config"},
    {"kind": "tool", "call_id": "c2", "name": "set_timeout",
     "arguments": {"value": 45, "expected_revision": 0}},
    {"kind": "final", "timeout": 45},
    {"kind": "tool", "call_id": "c3", "name": "run_test"},
    {"kind": "final", "timeout": 45},
]
env = {"timeout": 30, "revision": 0}
complete = run_episode(proposals, env)
assert complete["status"] == "done"
assert complete["model_steps"] == 5 and complete["tool_calls"] == 3
checks = [e["passed"] for e in complete["events"] if e["kind"] == "finish_check"]
assert checks == [False, True]

env = {"timeout": 30, "revision": 0}
partial = run_episode(proposals[:2], env)
assert partial["status"] == "incomplete" and env["revision"] == 1
saved = json.loads(json.dumps(partial))
resumed = run_episode(proposals[2:], env, checkpoint=saved)
assert resumed["status"] == "done" and env["revision"] == 1
assert resumed["model_steps"] == 5 and resumed["tool_calls"] == 3
~~~

Первое предложение завершить работу записано в журнал, но отвергнуто:
изменение есть, проверки нет. После `run_test` тот же verifier принимает
результат. Во втором запуске эпизод прерывается после записи конфигурации.
При продолжении используется сохранённый checkpoint, а проверка читает
текущий словарь `env`: его содержимое не восстанавливается из резюме.
Повторной записи не происходит, поэтому ревизия остаётся 1.

Здесь реализованы два счётчика, проверка разрешения на запись, ревизия
артефакта и правило завершения. Полная проверка JSON Schema, настоящее
хранилище событий, изоляция процесса, таймауты работающих инструментов,
токенизация и автоматическая суммаризация в этот учебный исполнитель
не входят. Его формат сообщений также не является готовым запросом к SDK.
Точность выбора действий LLM этим тестом не измеряется.
