# Train, validation и test

Низкий loss на данных, по которым обновлялись параметры, доказывает только, что
оптимизация смогла подогнать модель под эти данные. Нас интересует другое:
сохранится ли качество на новых примерах из той среды, где модель будет
работать? Для ответа данные делят на части с разными полномочиями.

[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/). Проценты являются
примером, а не универсальным правилом.*

## Три части — три разных вопроса

**Training set** используется для вычисления градиентов и изменения параметров.
Модель видит эти примеры многократно.

**Validation set** используется в процессе разработки: выбрать learning rate,
архитектуру, checkpoint, число эпох, tokenizer, состав данных или prompting
strategy. Его примеры не участвуют в backpropagation, но результаты влияют на
решения разработчика.

**Test set** предназначен для финальной оценки уже выбранной процедуры. Если
после каждого test result менять модель, test фактически превращается в ещё один
validation set.

Разница определяется не файлом и не названием колонки, а информационным потоком:
какие данные способны повлиять на параметры, гиперпараметры и выбор версии.

## Цикл разработки

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/google-mlcc/model-selection-loop.svg]]

*Параметры обучаются на train; решения о модели принимаются по validation; test
используется после выбора. Источник: Google Machine Learning Crash Course,
[Dividing the original dataset](https://developers.google.com/machine-learning/crash-course/overfitting/dividing-datasets),
[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/).*

Один training run — только часть более крупного цикла. Мы обучаем несколько
вариантов, сравниваем их на validation и выбираем один. Поэтому validation score
тоже оптимизируется, хотя и через решения человека или tuning system, а не
напрямую через градиент. После сотен экспериментов можно переобучиться и на
validation set.

## Почему случайный split подходит не всегда

Случайное перемешивание разумно, когда будущие примеры действительно похожи на
случайную выборку из того же распределения. Но структура данных может требовать
другого разбиения.

| Ситуация | Правильная единица split | Что сломает случайный split |
|---|---|---|
| сообщения пользователей | пользователь | стиль одного человека окажется в train и test |
| временной прогноз | время | модель увидит признаки будущего |
| медицинские снимки | пациент | почти одинаковые снимки одного пациента попадут в разные части |
| документы LLM | документ или источник | соседние chunks и дубликаты протекут в test |
| code generation | репозиторий | шаблоны и решения из одного проекта окажутся по обе стороны |

Split должен имитировать способ появления новых данных. Для deployment в будущем
часто нужен temporal split: обучение на прошлом, проверка на более позднем
периоде.

Для непрерывно поступающих данных границу приходится определять алгоритмически.
Стабильное хеширование по правильной единице группировки не даёт одному объекту
случайно мигрировать между train и evaluation. Если же дата является частью
целевого сценария, её включают в ключ намеренно, чтобы разбиение отражало
появление новых дней.

## Data leakage

Leakage возникает, когда в обучение или выбор модели попадает информация,
которой не будет в момент реального предсказания либо которая принадлежит
evaluation set.

Типичные случаи:

- нормализация рассчитана по всему датасету до split;
- один документ нарезан на chunks, после чего chunks случайно разнесены по
  train и test;
- target прямо или косвенно присутствует среди признаков;
- benchmark contamination: задачи или их решения были в pre-training corpus;
- synthetic data сгенерированы моделью, уже видевшей test answers;
- ручной подбор prompt многократно выполнялся на том же test set.

Все обучаемые преобразования — vocabulary, scaler, imputer, feature selection —
нужно fit только на train, а затем неизменно применять к validation и test.
Именно поэтому безопасный порядок начинается со split, а не с предварительной
обработки всего массива. Pipeline должен учить статистики преобразований внутри
каждого training fold; иначе кросс-валидация также получает подсказку из своей
проверочной части.

## Каким должен быть test set

Размер в процентах не является главным критерием. Test set должен:

- содержать достаточно примеров для нужной статистической точности;
- представлять реальные сценарии и важные срезы;
- не содержать дубликатов и производных объектов из train;
- оставаться закрытым от итеративного выбора модели;
- иметь стабильную процедуру разметки и расчёта метрик.

Для редких классов полезно стратифицированное разбиение. Для временных и
групповых данных важнее сохранить границы групп, чем одинаковые пропорции.

## LLM: одного held-out loss недостаточно

В pre-training held-out token loss проверяет способность моделировать похожий
текст. Но он не измеряет instruction following, factuality, безопасность,
качество tool use или поведение на свежих знаниях. Поэтому у LLM появляется
несколько уровней evaluation:

1. validation loss для контроля обучения и выбора checkpoint;
2. task suites и benchmarks для способностей;
3. human или model-based preference evaluation для качества ответов;
4. safety и robustness evaluations;
5. online metrics и мониторинг после deployment.

Каждый уровень нуждается в защите от contamination и в собственном описании
целевой популяции.

## Краткие итоги

- Train обновляет параметры, validation направляет разработку, test подтверждает
  результат после выбора.
- Повторное принятие решений по test превращает его в validation.
- Split должен сохранять реальные границы времени, пользователей, пациентов,
  документов или репозиториев.
- Leakage определяется информационным потоком, а не только совпадением строк.
- Evaluation LLM требует нескольких наборов и метрик, потому что token loss не
  описывает всё поведение системы.
