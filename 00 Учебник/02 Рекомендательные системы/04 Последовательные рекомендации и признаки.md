# Последовательные рекомендации и признаки

Две истории A → B → C и C → B → A содержат одни и те же объекты.
Матрица количества взаимодействий будет одинаковой, но последний объект
и переходы между объектами различаются. Для прогноза следующего действия
порядок может быть частью входных данных.

В последовательной рекомендации модель получает историю до момента
решения и оценивает возможные следующие объекты. Сессия может принадлежать
анонимному посетителю; постоянный user ID для этой постановки не обязателен.
Промежутки времени, типы действий и границы сессии добавляются отдельно:
по одним порядковым номерам нельзя отличить минутную паузу от месячной.

Для построения примеров достаточно первых глав модуля.
Caser требует [[00 Учебник/01 Основы нейронных сетей/07 CNN — от свёртки до ResNet|свёрток и pooling]],
SASRec — [[00 Учебник/05 Attention и Transformer/02 Self-Attention — Q, K, V|self-attention]]
и [[00 Учебник/05 Attention и Transformer/Masking, multi-head и формы тензоров|масок]].
Эти архитектурные разделы можно прочитать после соответствующих глав
о нейронных сетях.

## Как матрица теряет задачу

Пусть в обучении встречались четыре сессии:

```text
A → B → C
A → B → C
D → B → E
D → B → E
```

Модель переходов первого порядка использует только последний объект.
После B она оценивает C и E одинаково: каждый переход встретился дважды.
Если учитывать два последних действия, после A → B известны только
продолжения C, а после D → B — только E. Это наблюдение о заданном журнале,
а не утверждение, что следующий реальный выбор детерминирован.

```python
from collections import Counter, defaultdict
import numpy as np

sessions = [list("ABC"), list("ABC"), list("DBE"), list("DBE")]
first_order = defaultdict(Counter)
second_order = defaultdict(Counter)
for session in sessions:
    for t in range(1, len(session)):
        first_order[session[t-1]][session[t]] += 1
    for t in range(2, len(session)):
        second_order[tuple(session[t-2:t])][session[t]] += 1
assert first_order["B"] == {"C": 2, "E": 2}
assert second_order[("A", "B")] == {"C": 2}
assert second_order[("D", "B")] == {"E": 2}
print(first_order["B"], second_order[("A", "B")])
```

Увеличение длины явного контекста создаёт много редких сочетаний.
Caser и SASRec вместо отдельного счётчика для каждого сочетания обучают
общие embeddings и преобразования истории. Сначала необходимо определить,
какие части истории разрешены для каждого прогноза.

## Сначала split, потом окна

Возьмём события одного пользователя A, B, C, D, E, F в указанном порядке.
В per-user leave-two-out протоколе первые четыре события образуют train,
E служит validation target, F — test target.

Для максимальной длины контекста $L=3$ можно создать обучающие пары
$[A]\to B$, $[A,B]\to C$ и $[A,B,C]\to D$.
Validation получает $[B,C,D]\to E$.
Если к тестовому запросу событие E уже наблюдалось, его разрешено использовать
в истории: $[C,D,E]\to F$. Использование E как наблюдаемого входа
не означает дополнительного обучения на validation target.

```python
def last_two_split(history):
    if len(history) < 3:
        raise ValueError("Нужны train history и два отложенных события")
    return list(history[:-2]), history[-2], history[-1]

def prefix_examples(history, max_len):
    if max_len < 1:
        raise ValueError("max_len должен быть положительным")
    return [
        (list(history[max(0, t-max_len):t]), history[t])
        for t in range(1, len(history))
    ]

full_history = list("ABCDEF")
train_history, valid_target, test_target = last_two_split(full_history)
train_pairs = prefix_examples(train_history, 3)
valid_pair = (train_history[-3:], valid_target)
test_pair = ((train_history + [valid_target])[-3:], test_target)
assert train_pairs == [(["A"], "B"), (["A", "B"], "C"), (["A", "B", "C"], "D")]
assert valid_pair == (["B", "C", "D"], "E")
assert test_pair == (["C", "D", "E"], "F")
print(train_pairs, valid_pair, test_pair)
```

Per-user границы не являются общей датой. В объединённой таблице часть
train-событий одного пользователя может быть позже test-запроса другого.
Если эксперимент имитирует развёртывание модели на конкретную дату,
сначала разделяют весь журнал по этой дате, как в
[[00 Учебник/02 Рекомендательные системы/01 Задача рекомендации, данные и pipeline|главе о данных]].
Leave-two-out отвечает на другую, явно сформулированную офлайн-задачу.

Окна пересекаются внутри train, и это допустимо. Утечка возникает,
когда отложенный target попадает в обучающий пример или его признаки.
Случайное разделение уже построенных окон может поместить
$[A,B]\to C$ в test, а $[A,B,C]\to D$ в train: объект C уже
участвовал в обучении, хотя объявлен будущим проверочным откликом.

### Каталог и отрицательные примеры

Для исторического запроса объект должен уже существовать и быть доступен.
Пусть A доступен с момента 1, B — с 2, C — с 3, D — с 6.
Для запроса в момент 4 с историей A и положительным target B
отрицательным кандидатом может быть C, но не ещё не появившийся D.
Положительный target исключают
из отрицательной выборки, даже если его ещё нет в префиксе.

```python
def negative_pool_at(catalog_available_at, request_time, prefix, positive):
    visible = {
        item for item, available_at in catalog_available_at.items()
        if available_at <= request_time
    }
    if positive not in visible:
        raise ValueError("Положительный объект отсутствует в доступном каталоге")
    return visible - set(prefix) - {positive}

catalog_times = {"A": 1, "B": 2, "C": 3, "D": 6}
assert negative_pool_at(catalog_times, 4, ["A"], "B") == {"C"}
assert negative_pool_at(catalog_times, 6, ["A"], "B") == {"C", "D"}
```

В закреплённом
[WarpSampler Recommenders](https://github.com/recommenders-team/recommenders/blob/6232b154548c955315650d58dca6bf1411c56020/recommenders/models/sasrec/sampler.py)
используется другая офлайн-конвенция: общий train-каталог,
исключение всей обучающей истории пользователя и равномерный выбор
оставшегося ID. Это не реконструкция каталога в момент каждого события.
Такую выборку можно использовать для snapshot-обучения, но нельзя
без изменений назвать проверкой исторической доступности.

Неизвестный объект по-прежнему не становится наблюдаемым отказом.
Если допустимый пул пуст, пример надо пропустить или изменить контракт
выборки; бесконечный поиск случайного ID не является решением.
Для музыки и повторных покупок уже виденный объект может быть допустимым
положительным продолжением. Правило исключения просмотренного в выдаче
задают отдельно от правила получения negatives.

## Caser: свёртки по истории

В [D2L](https://d2l.ai/chapter_recommender-systems/seqrec.html)
Caser объединяет короткую историю с постоянным вектором пользователя.
Последние $L$ объектов превращаются в матрицу
$E\in\mathbb R^{L\times d}$: строки идут от старого действия к новому,
столбцы соответствуют координатам embeddings.

Горизонтальное ядро $F\in\mathbb R^{h\times d}$ охватывает $h$ соседних
действий и все координаты. При сдвиге на одну позицию без padding
получается $L-h+1$ чисел:

$$
c_t=\phi\left(
\sum_{a=1}^h\sum_{b=1}^d
E_{t+a-1,b}F_{ab}+\beta
\right).
$$

После активации максимум по $t$ оставляет один скаляр от каждого фильтра.
Ядра нескольких высот позволяют находить сочетания разной длины.
Порядок внутри окна участвует в вычислении: перестановка строк меняет,
какие значения умножаются на веса ядра.

Вертикальное ядро $g\in\mathbb R^{L\times1}$ охватывает всю историю,
но одну координату за раз:

$$
o'_b=\sum_{a=1}^L g_a E_{ab}+\gamma.
$$

Один такой фильтр возвращает $d$ чисел. Горизонтальный max pooling
к вертикальной ветви в реализации D2L не применяется.
Пусть $n_h$ — число горизонтальных фильтров высоты $h$, $n_v$ — число
вертикальных. Длина объединённого результата равна
$\sum_h n_h+dn_v$.

Для $L=3$, $d=2$ рассмотрим

$$
\begin{aligned}
E&=\begin{bmatrix}1&0\\0&1\\1&1\end{bmatrix},
\quad F=\begin{bmatrix}1&0\\0&1\end{bmatrix},\\
g&=\begin{bmatrix}1\\0\\-1\end{bmatrix}.
\end{aligned}
$$

Горизонтальная ветвь даёт $(2,1)$ до pooling и 2 после него.
Вертикальная даёт $(0,-1)$: первая и последняя позиции вычитаются
по каждой координате отдельно. В этом примере все biases равны нулю.

```python
E = np.array([[1., 0.], [0., 1.], [1., 1.]])
F = np.eye(2)
g_vertical = np.array([1., 0., -1.])
horizontal_raw = np.array([
    np.sum(E[t:t+len(F)] * F) for t in range(len(E)-len(F)+1)
])
horizontal = np.maximum(0., horizontal_raw).max()
vertical = g_vertical @ E
combined = np.r_[horizontal, vertical]
W_history = np.array([[0.5, 0., 1.], [0., 1., -1.]])
z = np.maximum(0., W_history @ combined)
user_vector = np.array([0.2, 0.3])
candidate_vector = np.array([1., 0.5, 1., 0.])
caser_score = candidate_vector @ np.r_[z, user_vector]
np.testing.assert_allclose(horizontal_raw, [2., 1.])
np.testing.assert_allclose(vertical, [0., -1.])
np.testing.assert_allclose(z, [0., 1.])
np.testing.assert_allclose(caser_score, 0.7)
print(horizontal_raw, vertical, z, caser_score)
```

Вектор свёрточных признаков проходит через полносвязный слой:

$$
\begin{aligned}
z&=\operatorname{ReLU}(W[o;o']+b),\\
s(u,i,t)&=v_i^\top[z;p_u]+b_i.
\end{aligned}
$$

Входная таблица объектов истории $Q$ и выходная таблица кандидатов $V$
различаются: здесь $v_i\in\mathbb R^{2d}$, а $q_i\in\mathbb R^d$.
Функцию оценки можно обучать BPR или hinge из
[[00 Учебник/02 Рекомендательные системы/03 Ranking и нейронные рекомендательные модели|предыдущей главы]].

Левая ветвь рисунка содержит max pooling, правая — только свёртку.
Обозначение $k$ источника соответствует нашему $d$.
Верхний $z$ на упрощённой схеме объединяет и пользовательскую ветвь;
в формулах и коде D2L полносвязный слой сначала обрабатывает $[o;o']$,
а $p_u$ присоединяется после него. Этот порядок использован в расчёте выше.

Если несколько дней без событий отделяют два действия, обычный Caser
видит лишь соседство строк. Признак паузы или разрыв сессии требуется
добавить явно. Последовательное окно также ограничено $L$;
max pooling не восстанавливает события, которые в него не попали.

## SASRec: causal self-attention

SASRec строит вектор текущего состояния из истории с помощью causal
self-attention. Отдельной таблицы пользовательских ID в базовом варианте
нет: при отключённом dropout два пользователя с одинаковыми входами
получат одинаковые scores. Их различия представлены в самой истории.

### Сдвиг входа и цели

Для обучающей истории A, B, C, D входом может быть A, B, C,
целями — B, C, D. Выход первой позиции должен предсказывать B
только по A, выход второй — C по A, B, и так далее.
Сдвиг targets не разрешает смотреть на последующие входные позиции.

ID 0 зарезервируем для PAD, настоящие объекты получат ID от 1.
Короткий вход дополняется слева; длинный обрезается слева,
оставляя последние $L$ действий.

```python
def pad_left(values, max_len):
    if max_len < 1:
        raise ValueError("max_len должен быть положительным")
    tail = list(values[-max_len:])
    return np.array([0] * (max_len-len(tail)) + tail, dtype=np.int64)

def shifted_train(history, max_len):
    if any(item <= 0 for item in history):
        raise ValueError("История должна содержать реальные положительные ID")
    return pad_left(history[:-1], max_len), pad_left(history[1:], max_len)

seq, positive = shifted_train([1, 2, 3, 4], 4)
np.testing.assert_array_equal(seq, [0, 1, 2, 3])
np.testing.assert_array_equal(positive, [0, 2, 3, 4])
short_seq, short_positive = shifted_train([1], 4)
assert not np.any(short_seq) and not np.any(short_positive)
print(seq, positive)
```

Это один вариант batch-подготовки, а не тождество всем наборам отдельных
окон. В частности, абсолютные позиции A в длинном входе и в отдельно
дополненном префиксе A могут различаться. Правило назначения позиций
сохраняют между подготовкой данных и обслуживанием.

Нижний ряд содержит действия $s_1,s_2,s_3,s_4$, но encoder получает

над $s_3$ — $s_4$. Стрелки разрешают второй позиции учитывать первую,
третьей — первую и вторую. Будущие targets не должны проникать
в соответствующие состояния.

### Embeddings, attention и FFN

Для слота $t$ складываются embedding объекта и обучаемый embedding позиции:

$$
h_t^{(0)}=e_{i_t}+p_t.
$$

Позиция здесь означает место в обрезанном входе, а не время в секундах.
PAD-позиции исключаются из вычисления состояния. Даже при нулевом
$e_{\mathrm{PAD}}$ добавление $p_t$, biases или нормализация могут
создать ненулевые значения; одной нулевой строки таблицы недостаточно.

Один attention head использует $Q=HW_Q$, $K=HW_K$, $V=HW_V$.
Для настоящей query-позиции $t$ разрешены только настоящие ключи $j\le t$.
Из разрешённых logits получается softmax, затем взвешенная сумма values.
FFN после attention действует независимо по позициям и не смешивает
состояние $t$ с состояниями будущих позиций.

Обычный блок также содержит нормализацию, residual connections и dropout.
Их порядок надо сверять с конкретной реализацией; название TransformerBlock
не определяет pre-norm, расположение residual и маскирование автоматически.
Упрощённый расчёт ниже проверяет только attention, без FFN и residual.

### Causal mask, PAD keys и PAD targets

У масок разные задачи. Causal mask запрещает ключи справа от текущей
позиции. Маска PAD keys запрещает искусственные элементы независимо
от их позиции. Маска targets исключает заполнение из функции потерь.
Выходы PAD queries можно занулить отдельно, чтобы не переносить
бессодержательное состояние в следующие операции.

Рассмотрим ID $[0,A,B,C]$. Для query A разрешён только ключ A,
для B — A и B, для C — A, B и C. Ключ PAD запрещён везде.
Диагональ настоящих элементов разрешена: прогноз после B должен
использовать уже наблюдаемый B.

В реализации не стоит определять PAD через сумму координат вектора.
Настоящий embedding $(1,-1)$ тоже имеет сумму 0.
Надёжный источник маски — ID или отдельная маска длины.

```python
def causal_attention(vectors, ids):
    vectors = np.asarray(vectors, dtype=float)
    ids = np.asarray(ids)
    if (vectors.ndim != 2 or ids.ndim != 1
            or len(ids) != len(vectors) or min(vectors.shape) < 1):
        raise ValueError("Ожидаются L векторов и L идентификаторов")
    valid = ids != 0
    L, d = vectors.shape
    allowed = (
        np.tril(np.ones((L, L), dtype=bool))
        & valid[:, None] & valid[None, :]
    )
    logits = vectors @ vectors.T / np.sqrt(d)  # Q=K=V только в этом примере.
    masked = np.where(allowed, logits, -np.inf)
    row_max = masked.max(axis=1, keepdims=True)
    row_max = np.where(np.isfinite(row_max), row_max, 0.)
    exp_logits = np.exp(masked-row_max)
    denominator = exp_logits.sum(axis=1, keepdims=True)
    weights = np.divide(
        exp_logits, denominator, out=np.zeros_like(exp_logits),
        where=denominator > 0,
    )
    return weights @ vectors, weights

ids = np.array([0, 1, 2, 3])
vectors = np.array([[100., 100.], [1., 0.], [0., 1.], [1., 1.]])
attended, weights = causal_attention(vectors, ids)
np.testing.assert_allclose(weights[0], 0.)
np.testing.assert_allclose(weights[1], [0., 1., 0., 0.])
assert np.all(weights[:, 0] == 0)
np.testing.assert_allclose(weights[2, 1:3], [0.33023845, 0.66976155])
changed_future = vectors.copy()
changed_future[3] = [-50., 80.]
np.testing.assert_allclose(causal_attention(changed_future, ids)[0][:3], attended[:3])
changed_pad = vectors.copy()
changed_pad[0] = [-99., 700.]
np.testing.assert_allclose(causal_attention(changed_pad, ids)[0], attended)
print(weights, attended)
```

Полностью маскированная строка имеет нулевые веса и нулевой выход.
Это выбранный контракт учебной функции; обычный softmax от одних
$-\infty$ дал бы NaN. Пустую историю при выдаче обрабатывают отдельным
fallback, а не трактуют нулевой вектор как изученное предпочтение.

### Обучение следующего объекта

Последнее настоящее состояние $h_t$ оценивает кандидата как
$s(i\mid i_{\le t})=h_t^\top e_i$. В SASRec входная и выходная таблицы
объектов могут быть общими. Асимметрия перехода сохраняется благодаря
преобразованию истории: из общего embedding не следует
$s(B\mid A)=s(A\mid B)$.

Для каждого обучающего состояния выбирают positive $i^+$ и negative $i^-$.
В закреплённом SASRec Recommenders используется сумма двух бинарных потерь,
а не BPR от разности scores:

$$
\begin{aligned}
\ell_t
&=\operatorname{softplus}(-s_t^+)\\
&\quad+\operatorname{softplus}(s_t^-),\\
\mathcal L
&=\frac{\sum_t M_t\ell_t}{\sum_t M_t},
\qquad M_t=\mathbf1[i_t^+\ne0].
\end{aligned}
$$

Знаменатель считает настоящие targets, не длину дополненного массива.
Если в batch нет ни одного настоящего target, это среднее не определено:
batch пропускают или сообщают об ошибке подготовки данных.
Если заменить его на $BL$, короткие истории получат меньший вес
из-за технического PAD. Даже при правильном знаменателе среднее по всем
позициям и среднее пользовательских средних являются разными objectives.

```python
def masked_sequence_bce(positive, negative, mask):
    positive, negative = np.asarray(positive), np.asarray(negative)
    mask = np.asarray(mask, dtype=bool)
    if positive.shape != negative.shape or mask.shape != positive.shape:
        raise ValueError("Logits и mask должны иметь одинаковую форму")
    if not mask.any():
        raise ValueError("Нет настоящих targets")
    losses = np.logaddexp(0., -positive) + np.logaddexp(0., negative)
    return losses[mask].mean()

pos_logits = np.array([[0., 2., -1.], [0., 0., 1.]])
neg_logits = np.array([[0., -1., 1.], [0., 0., -2.]])
target_mask = np.array([[False, True, True], [False, False, True]])
per_position_loss = (
    np.logaddexp(0., -pos_logits) + np.logaddexp(0., neg_logits)
)
masked_loss = masked_sequence_bce(pos_logits, neg_logits, target_mask)
user_means = [
    per_position_loss[row][target_mask[row]].mean()
    for row in range(len(target_mask))
]
user_average_loss = np.mean(user_means)
assert abs(masked_loss-user_average_loss) > 0.1
assert target_mask.sum() == 3
print("By target / by user:", masked_loss, user_average_loss)
```

Производные по logits равны $\sigma(s_t^+)-1$ и $\sigma(s_t^-)$,
с учётом выбранного усреднения. Технические PAD targets не дают
градиента. Число negatives, распределение их выбора и нормировка
определяют обучение; эти scores не являются автоматически
калиброванной вероятностью реального клика.

В
[[05 Источники/Courses/Linux Foundation Recommenders/examples/00_quick_start/sasrec_amazon.ipynb|notebook Recommenders]]
пример использует Amazon Electronics, `maxlen=50`, два блока,
размер hidden state 100, одну голову и 100 тестовых negatives.
Это параметры конкретного опыта, не универсальные настройки.
Его сохранённые метрики и время обучения не являются нашими замерами.

### Длина истории и стоимость

При длине $L$, ширине $d$ и $b$ блоках encoder требует порядка
$O(b(L^2d+Ld^2))$ операций при стандартном полном attention.
Удвоение длины умножает attention-часть примерно на четыре,
но FFN-часть — примерно на два. Нельзя без измерений обещать
четырёхкратное изменение времени всего запроса.

После вычисления одного состояния оценка $C$ кандидатов через dot product
требует $O(Cd)$. Для чистого скалярного произведения применим поиск MIPS;
фильтрация, обновление истории и построение состояния остаются
отдельными частями обслуживания.

## SSE-PT: явный вектор пользователя

В классе
[SSEPT Recommenders](https://github.com/recommenders-team/recommenders/blob/6232b154548c955315650d58dca6bf1411c56020/recommenders/models/sasrec/ssept.py)
к embedding каждого объекта присоединяется один и тот же пользовательский
вектор. При размерах $d_i$ и $d_u$ ширина становится $d_i+d_u$:

$$
\begin{aligned}
x_t&=[e_{i_t};p_u]+p_t^{\mathrm{pos}},\\
s(u,i,t)&=h_t^\top[e_i;p_u].
\end{aligned}
$$

В этой реализации объектные и пользовательские embeddings перед
конкатенацией также масштабируются на корень из своего размера.
Пользовательский вектор влияет на построение $h_t$ внутри attention.
Поэтому это не просто добавление постоянного смещения к готовой выдаче.

В [статье SSE-PT, §3.3.5](https://arxiv.org/html/1908.05435v1#S3.SS3.SSS5)
дополнительно используется Stochastic Shared Embeddings.
Во время обучения часть обращений к таблице случайно перенаправляется
на другую строку. У пользовательской подмены согласуются входной
и выходной lookup; вероятности для пользователя, входных объектов
и выходных объектов могут различаться. PAD не должен становиться
случайным настоящим объектом.

```python
def replace_ids(ids, probability, real_ids, rng):
    ids = np.asarray(ids, dtype=np.int64)
    choices = np.asarray(real_ids, dtype=np.int64)
    if not 0 <= probability <= 1 or len(choices) == 0 or np.any(choices <= 0):
        raise ValueError("Нужны вероятность [0,1] и непустые реальные ID")
    result = ids.copy()
    replace = (ids != 0) & (rng.random(ids.shape) < probability)
    result[replace] = rng.choice(choices, size=replace.sum())
    return result

random_state = np.random.default_rng(25)
original_ids = np.array([0, 1, 2, 3])
np.testing.assert_array_equal(
    replace_ids(original_ids, 0., [1, 2, 3], random_state), original_ids
)
replaced = replace_ids(original_ids, 1., [9], random_state)
np.testing.assert_array_equal(replaced, [0, 9, 9, 9])
# Один заменённый user ID затем используется и во входе, и в выходе.
input_user_id = output_user_id = replace_ids(
    np.array([7]), 1., [12], random_state
)[0]
assert input_user_id == output_user_id == 12
print(replaced, input_user_id)
```

Это иллюстрация lookup-подмены, не полная реализация SSE-PT.
В прочитанных `ssept.py` и `sampler.py` закреплённой версии Recommenders
такой случайной замены embeddings нет. Наличие класса с названием SSEPT
само по себе не воспроизводит регуляризацию и эксперимент статьи.

В [SSE-PT++, §3.4](https://arxiv.org/html/1908.05435v1#S3.SS4)
длинную обучающую историю используют через смесь окон:
часть обновлений получает последнее окно, часть — более раннее случайное.
Это меняет выбор обучающих данных, но не позволяет attention одного
forward-pass видеть всю историю длиннее $L$ одновременно.

```python
def choose_training_window(history, length, earlier_probability, rng):
    if length < 1 or not 0 <= earlier_probability <= 1:
        raise ValueError("Неверная длина или вероятность")
    if len(history) <= length:
        return list(history)
    latest_start = len(history)-length
    if rng.random() < earlier_probability:
        start = int(rng.integers(0, latest_start))  # Последнее окно исключено.
    else:
        start = latest_start
    return list(history[start:start+length])

assert choose_training_window(list("ABCDEFG"), 3, 0., random_state) == list("EFG")
older = choose_training_window(list("ABCDEFG"), 3, 1., random_state)
assert older in [list("ABC"), list("BCD"), list("CDE"), list("DEF")]
print("Earlier training window:", older)
```

Результат выборки остаётся обучающим окном: из него отдельно строятся
входы и targets. В тесте нельзя случайно выбирать прошлое окно вместо
истории, доступной перед текущим решением, и называть это тем же запросом.

## Long-term, short-term и context

Caser хранит $p_u$ отдельно от короткого окна. SASRec без user ID
получает всё представление из последовательности. SSE-PT подаёт
$p_u$ внутрь каждого входного слота. Это разные способы объединения
источников сигнала; польза каждого проверяется на одинаковых данных.

| Вариант | Что остаётся доступно |
| --- | --- |
| Только популярность | Частоты обучающего каталога |
| Только user ID | Устойчивый вектор известного пользователя |
| Только последние действия | История, в том числе у нового ID |
| История и user ID | Последовательность и обученная таблица пользователей |
| История и контекст | Дополнительно известные признаки запроса |

Время суток или устройство не заменяют историю, а добавляют условия
запроса. Можно объединить их с представлением истории в ранжирующей сети.
Чтобы определить вклад, сравнивают варианты с удалёнными группами
признаков при одном split, каталоге, sampling и бюджете подбора.

<a id="feature-rich-ctr-prediction"></a>
## Признаки запроса и прогноз клика

В журнале показов каждая строка связывает объект, запрос и последующий
отклик. CTR на наборе показов равен числу кликов, делённому на число
показов по принятому определению метки. Модель бинарного отклика
оценивает условную вероятность

$$
P(y=1\mid u,i,c,\mathrm{shown}).
$$

В [D2L, Feature-Rich Recommender Systems](https://d2l.ai/chapter_recommender-systems/ctr.html)
приведён анонимизированный advertising dataset.
Названия его полей не раскрывают реальную семантику: нельзя утверждать,
что конкретный столбец — устройство или категория. Пример полей ниже
задан отдельно для объяснения.

Категориальные признаки, например `device=mobile` и `category=camera`,
получают строки в отдельных словарях. Численные признаки обрабатывают
преобразованиями, обученными на train. Для validation, test и обслуживания
используют те же словари и параметры, а неизвестные категории получают
заранее выбранный OOV ID.

<a id="worked-example-field-interactions"></a>
### Словарь категорий и OOV

Пусть устройство встречалось в train как mobile, desktop, mobile.
При пороге 2 отдельную строку получит mobile, а редкий desktop
и новое tablet попадут в OOV. Значения test не увеличивают словарь.

```python
def fit_categories(train_values, minimum_count=2):
    if minimum_count < 1:
        raise ValueError("minimum_count должен быть положительным")
    counts = Counter(train_values)
    return {
        value: index+1
        for index, value in enumerate(sorted(
            value for value, count in counts.items() if count >= minimum_count
        ))
    }

device_vocabulary = fit_categories(["mobile", "desktop", "mobile"])
oov_id = 0
encoded_test = [
    device_vocabulary.get(value, oov_id)
    for value in ["tablet", "desktop", "mobile"]
]
assert device_vocabulary == {"mobile": 1}
assert encoded_test == [0, 0, 1]
assert device_vocabulary == {"mobile": 1}
print(encoded_test)
```

Здесь OOV=0 относится к отдельному словарю устройства, а PAD=0 —
к словарю последовательности объектов. Их смысл различается;
одинаковое число не разрешает смешать две таблицы.

FM и DeepFM из предыдущей главы обучают взаимодействия полей.
Последовательная сеть может дать ещё один признак — состояние истории.
Чем именно считать клик, какое окно отклика использовать и как связать
его с показом, решается до выбора архитектуры.

## Признаки без утечки

Для запроса в момент $t$ версия признака должна быть уже доступна системе.
Событие с event time раньше $t$, но доставленное позже, в этот вход
не включается. Признаки `item_ctr_7d` и пользовательская история
также не могут включать отклик, который предстоит предсказать.

Point-in-time join и два времени подробно разобраны в
[[00 Учебник/02 Рекомендательные системы/01 Задача рекомендации, данные и pipeline#data-contract|главе о данных]].
Та же проверка относится к последовательности: сортировка всех
когда-либо полученных событий по event time не воспроизводит
прошлое состояние online-системы.

```python
events = [
    {"item": "A", "event_at": 10, "available_at": 10},
    {"item": "B", "event_at": 20, "available_at": 35},
    {"item": "C", "event_at": 25, "available_at": 26},
]
request_at = 30
actual_history = [
    e["item"] for e in sorted(events, key=lambda e: (e["event_at"], e["item"]))
    if e["event_at"] < request_at and e["available_at"] <= request_at
]
event_time_only = [e["item"] for e in events if e["event_at"] < request_at]
assert actual_history == ["A", "C"]
assert event_time_only == ["A", "B", "C"]
print("Available history:", actual_history)
```

На момент 30 система знает A и C, но ещё не получила B.
Если позднее восстановить A, B, C и использовать эту историю как вход
запроса в момент 30, получится утечка. В реальном журнале дополнительно
понадобятся правила исправлений, дедупликации и разрешения одинаковых timestamps.

Позиция в старой выдаче влияет на вероятность отклика и сама выбрана
старым алгоритмом. Добавление позиции в признаки может улучшить прогноз
его логов, но не устанавливает эффект новой перестановки объектов.
Для причинной оценки нужны отдельные предположения и подходящие данные;
нейронная архитектура не заменяет их.

## Cold start

У нового пользователя нет обученного свободного user embedding.
Модель истории без user ID может обработать его первые действия,
если соответствующие объекты уже представлены в каталоге.
При пустой истории нужен другой сигнал: популярность, контекст
или явно полученные предпочтения.

У нового объекта нет обученной ID-строки. Текстовый, визуальный
или категориальный encoder может дать представление, но его нужно
обучить в той же задаче и согласовать с пользовательским пространством.
Произвольный вектор другого encoder не становится заменой $e_i$
в уже обученном dot product.

| Случай | Что требуется |
| --- | --- |
| Новый пользователь без событий | Исходная выдача по контексту или предпочтениям |
| Новый пользователь с историей | Модель истории и известные embeddings объектов |
| Новый объект с описанием | Обученное отображение признаков в пространство модели |
| Новый объект без признаков | Отдельная стратегия исследования и начальных показов |

Проверка новых пользователей требует user-holdout, новых объектов —
item-holdout с временной доступностью признаков и каталога.
Удаление ID только из части взаимодействий не проверяет cold start,
если его обученный вектор или будущая популярность всё равно переданы модели.

<a id="failure-modes-sequence-models"></a>
## История при обучении и обслуживании

Повторные прослушивания и покупки расходников делают правило
«никогда не рекомендовать просмотренное» неверным для некоторых задач.
Границы сессии тоже зависят от продукта: новый поисковый запрос может
сменить намерение раньше фиксированного тайм-аута.

Для модели, обученной на последних 50 действиях с левым PAD,
правое дополнение или иной порядок positional IDs при обслуживании
создают другой вход. Отдельно проверяют одинаковый суффикс истории,
версию словаря и точное положение последнего настоящего элемента.
Нельзя всегда брать последний слот, если используется правый PAD.

После обновления модели прошлый кешированный hidden state может
не соответствовать новым весам или словарю. Удобство кеширования
не доказывает совместимость: версионируют модель, историю и способ
получения состояния. Пересчёт усечённого окна с переназначенными
позициями тоже не обязан совпадать с простым добавлением элемента
к старому KV cache.

<a id="production-contract"></a>
## Что зафиксировать перед запуском

Для воспроизведения входа нужны определение сессии, сортировка одинаковых
timestamps, фильтрация дубликатов и ботов, типы действий и правила их веса.
Ко входному контракту относятся максимальная длина, сторона truncation
и PAD, reserved IDs, positional convention, словарь и поведение OOV.

Для выдачи задают допустимый каталог, правило повторных рекомендаций,
способ поиска кандидатов и fallback при пустой или устаревшей истории.
Свежесть признаков измеряют отдельно от времени forward-pass:
быстрая модель с запаздывающим состоянием получает другую историю.

Offline-отчёт сохраняет полный или sampled каталог, источник negatives,
размер $K$, правила ties и срезы по длине истории, новым ID и давности
последнего события. Сравнение со счётчиком переходов, популярностью
и моделью без порядка показывает, какой вклад даёт сама последовательность.
