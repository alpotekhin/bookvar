# Рекомендательные системы

Рекомендательная система отвечает не на вопрос «к какому классу относится
объект», а на вопрос «какие объекты следует показать этому пользователю сейчас
и в каком порядке». Входом служат история взаимодействий, признаки пользователя
и объектов, контекст запроса и множество доступных кандидатов. Выходом обычно
является ранжированный список. Поэтому качество системы определяется не одной
моделью: на него одновременно влияют сбор событий, способ разбиения данных,
генерация кандидатов, функция обучения, ранжирование, правила фильтрации и
онлайн-эксперимент.

Полный исходный учебный слой сохранён на английском:

- [[05 Источники/Courses/Dive into Deep Learning — Recommender Systems|Dive into Deep Learning — complete recommender-systems chapter]] — одиннадцать полных глав с формулами, исходными рисунками, MXNet-кодом и упражнениями;
- [[05 Источники/Courses/Linux Foundation Recommenders|Linux Foundation Recommenders — practical labs]] — девять полных notebooks от подготовки данных до operationalization.

## Почему это отдельная дисциплина

В обычной классификации множество классов сравнительно мало, target наблюдается
для каждого объекта, а ошибка модели не меняет будущую обучающую выборку. В
рекомендациях каталог может содержать миллионы items, положительных событий у
каждого пользователя мало, а система наблюдает response только для показанных
объектов. Выдача сегодня определяет логи, на которых будет обучена следующая
версия модели.

Поэтому полезно держать в голове замкнутый цикл:

$$
\text{policy}_t
\longrightarrow \text{exposure}_t
\longrightarrow \text{response}_t
\longrightarrow \text{dataset}_{t+1}
\longrightarrow \text{policy}_{t+1}.
$$

Этот цикл объясняет сразу несколько практических трудностей. Ненаблюдаемый
объект нельзя автоматически считать неинтересным. Offline test отражает
поведение прежней policy. Модель, которая чаще показывает популярные items,
получает ещё больше подтверждающих их кликов. Даже корректный supervised loss
не устраняет feedback loop.

## Три слоя системы

Удобно разделять рекомендательную систему на три уровня.

**Модель предпочтения** вычисляет score $s(u,i,c)$. Это может быть popularity
baseline, matrix factorization, factorization machine, two-tower retriever,
sequential Transformer или feature-rich ranker.

**Алгоритм выбора** превращает scores в slate: получает candidates, сортирует,
фильтрует недоступные items, ограничивает повторы, применяет diversity и
policy constraints.

**Экспериментальная policy** решает, что действительно увидит пользователь:
production model, control, exploration bucket или fallback. Именно этот слой
создаёт exposure data.

Если смешать уровни, легко приписать модели улучшение, полученное новым
candidate generator, или обвинить loss в ошибке, вызванной business filter.

## Минимальный сквозной dataset

Для учебных примеров достаточно четырёх таблиц:

| Таблица | Необходимые поля | Зачем |
|---|---|---|
| `users` | `user_id`, стабильные признаки, время создания | cold start и slices |
| `items` | `item_id`, content/category, availability interval | candidates и фильтрация |
| `impressions` | request, candidates, positions, scores, policy version | exposure и честная evaluation |
| `events` | request, user, item, action, timestamp, value | target и последовательности |

exposure. Поэтому он удобен для математики, а не для доказательства готовности
промышленной системы. Исходная глава D2L показывает загрузку и структуру
MovieLens:

## Сквозной пример

Пусть сервис хранит события

$$
(u, i, a, t, c),
$$

где $u$ — пользователь, $i$ — объект, $a$ — действие, $t$ — время, $c$ —
контекст. Из этих событий можно построить разные задачи:

- спрогнозировать rating $r_{ui}$;
- оценить вероятность клика $P(a=\mathrm{click}\mid u,i,c)$;
- выбрать $K$ объектов из каталога;
- предсказать следующий объект по последовательности $i_1,\ldots,i_t$.

Эти постановки нельзя оценивать одной метрикой. RMSE подходит для rating
prediction, но почти ничего не говорит о порядке первых десяти рекомендаций.
Recall@$K$ измеряет, попал ли релевантный объект в выдачу, но не различает
первую и десятую позицию. NDCG@$K$ учитывает позицию, однако не гарантирует
разнообразия, свежести или отсутствия популярностного перекоса.

### Один лог — разные targets

Предположим, пользователь последовательно открыл items `A`, `B`, `C`, купил
`C`, затем увидел `D` и ничего не сделал.

- Для rating regression этот лог непригоден без явных ratings.
- Для implicit pointwise learning `C` — сильный positive, открытия `A` и `B`
  могут быть более слабыми positives, `D` — exposed negative.
- Для pairwise ranking можно построить $(u,C,D)$.
- Для next-item prediction появляются пары
  $[A]\to B$, $[A,B]\to C$.
- Для candidate retrieval значение имеет полный каталог, доступный в каждый
  момент, а не только четыре записанных items.

Тем самым target — редакционное и продуктовое решение, а не готовый столбец в
логах.

## Два маршрута чтения

**Модельный маршрут:** задача → MF → BPR/NCF/FM → sequential models →
offline metrics. Он нужен, чтобы понимать objectives и архитектуры.

**Системный маршрут:** события и exposure → temporal split → candidates →
ranking → post-ranking → logging → A/B test → monitoring. Он нужен, чтобы
модельное улучшение не исчезло при развёртывании.

Оба маршрута сходятся в последней главе. Рекомендатель нельзя считать
проверенным, если известен только loss, но неизвестны candidate set, data split
и способ показа.

## Что должно остаться после модуля

Читатель должен уметь:

- сформулировать recommendation task через доступное feedback и продуктовый
  контракт;
- построить честный temporal или leave-one-out split;
- реализовать popularity и bias baselines до сложной модели;
- вывести matrix factorization и BPR;
- объяснить, когда нейронная модель добавляет полезную нелинейность, а когда
  лишь увеличивает стоимость;
- разделить retrieval и ranking;
- выбрать accuracy и beyond-accuracy metrics;
- связать offline evaluation с online experiment и эксплуатационными
  ограничениями.
