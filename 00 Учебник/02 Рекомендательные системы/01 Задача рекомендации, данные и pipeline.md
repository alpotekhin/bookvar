# Задача рекомендации, данные и конвейер

В магазине два свободных места для рекомендаций и каталог из ста тысяч товаров.
Нужно выбрать два товара для конкретного посетителя. Для обучения есть покупки
и клики, но неизвестно, что посетитель подумал о каждом из остальных товаров.
Часть из них он не видел, часть уже недоступна, а часть появилась после
последнего обучения модели.

Единица предсказания здесь — пара «пользователь, объект» в определённом
контексте, а единица решения — весь показанный список. Поиск похожих объектов,
прогноз клика и выбор списка решают разные части этой задачи.

## Сначала определить событие и решение

Пользователь поставил фильму две звезды: это явная оценка, или *explicit
feedback*. Пользователь посмотрел фильм: это наблюдаемое поведение, или
*implicit feedback*. Просмотр мог означать интерес, разочарование или желание
досмотреть до конца уже начатый фильм. Он не задаёт численную оценку
удовлетворённости.

В [D2L, Explicit Feedback and Implicit Feedback](https://d2l.ai/chapter_recommender-systems/recsys-intro.html#explicit-feedback-and-implicit-feedback)
это различие вводится до моделей. Для обучения оно определяет смысл строки
данных: оценка 2 является наблюдаемым значением, а пропуск в матрице оценок
не является оценкой 0.

Пусть в каталоге есть товары `A`–`F`. У Ани записана покупка `A`, у Бориса —
покупка `B`. Из этих двух событий нельзя заключить, что Ане не нравится `B`,
а обоим не нравятся `C`–`F`. Для такой интерпретации не хватает данных о
показах и доступности. Даже зарегистрированный показ ещё не гарантирует,
что пользователь заметил объект.

Для одного решения полезно различать четыре записи:

| Запись | Пример | Смысл |
| --- | --- | --- |
| Запрос | Аня открыла главную в 10:00 | момент выбора и известный контекст |
| Кандидат | `C` найден поиском похожих товаров | объект отобран внутри системы |
| Показ | `C` оказался на позиции 2 | выдача с объектом доставлена |
| Отклик | в 10:03 произошёл клик по `C` | действие после показа |

Кандидат, который был отфильтрован, не становится показом. Серверный ответ,
который приложение не отобразило, тоже нельзя безоговорочно считать просмотром.
Поэтому в контракте логирования указывают, что означает impression:
включение в ответ, отрисовку карточки или попадание карточки в видимую область.
Сравниваемые версии системы должны использовать одно определение.

## Четыре разные задачи

### Rating prediction

Для наблюдаемых оценок $(u,i)\in\mathcal K$ модель предсказывает
$\hat r_{ui}$. Средняя квадратичная ошибка считается только по размеченным
парам:

$$
\mathcal L_{\mathrm{MSE}}
=\frac{1}{|\mathcal K|}
\sum_{(u,i)\in\mathcal K}(r_{ui}-\hat r_{ui})^2.
$$

Например, истинные оценки трёх фильмов равны $(5;4;1)$. Модель A предсказывает
$(4;4{,}1;1)$, модель B — $(5;3;2)$. У A меньше MSE: примерно $0{,}337$
против $0{,}667$. Но если показать только один фильм, A выберет второй,
а B — первый, у которого оценка выше.

```python
truth = [5.0, 4.0, 1.0]
prediction_a = [4.0, 4.1, 1.0]
prediction_b = [5.0, 3.0, 2.0]

def mse(actual, predicted):
    return sum((a - p) ** 2 for a, p in zip(actual, predicted)) / len(actual)

best_a = max(range(3), key=lambda i: prediction_a[i])
best_b = max(range(3), key=lambda i: prediction_b[i])
assert mse(truth, prediction_a) < mse(truth, prediction_b)
assert (best_a, best_b) == (1, 0)
print(round(mse(truth, prediction_a), 6),
      round(mse(truth, prediction_b), 6))
```

Оптимизация ошибки численных оценок может менять и порядок рекомендаций,
но сама метрика не выделяет первые позиции. Выбор функции обучения и выбор
метрики должны соответствовать тому, что система действительно показывает.

<a id="top-kkk-recommendation"></a>
### Top-K recommendation

Для пользователя $u$ в момент $t$ задают доступное множество $\mathcal A(u,t)$.
Из него выбирают упорядоченный список из $K$ объектов. При независимой
оценке объектов это первые $K$ значений $s(u,i,c)$, где $c$ — контекст запроса.
Если учитываются разнообразие или ограничения на весь список, одних
независимых scores недостаточно: выбор следующего объекта может зависеть
от уже выбранных.

Объекты из прошлой истории иногда исключают, как уже купленную книгу.
В других задачах повтор нужен: музыкальный сервис может рекомендовать
знакомую композицию. Исключение просмотренного — правило конкретной задачи,
а не свойство всех рекомендательных систем.

### CTR или response prediction

Для показанного объекта можно предсказывать вероятность клика:

$$
\hat p=P(y=1\mid u,i,c,\text{показ}).
$$

Здесь $y$ означает клик в заранее заданном окне. Позиция, устройство и вид
карточки могут входить в $c$. Вероятность клика по товару на позиции 1
не обязана совпадать с вероятностью клика по тому же товару на позиции 10.

Логи прежнего алгоритма содержат выбранные им показы. Модель оценивает
отклик на этом распределении данных; из этого ещё не следует, что она умеет
предсказывать эффект произвольного нового способа показа. Поправки на
экспозицию и причинное оценивание разбираются в
[[00 Учебник/02 Рекомендательные системы/05 Оценивание и эксплуатация|главе об оценивании]].

### Next-item prediction

Для истории $i_1,\ldots,i_t$ цель — следующий объект $i_{t+1}$.
Из последовательности `A,B,C` получаются примеры `[A] → B` и `[A,B] → C`.
При построении второго входа `C` ещё неизвестен и не должен попасть
в признаки или агрегаты.

Следующий клик, следующая покупка и покупка в течение суток задают разные
цели. Если каждое открытие товара превращается в отдельный target,
длинные сессии получают больший вес. Если цель задаётся на сессию,
нужно определить её границы и правило выбора целевого события.
Модели последовательностей рассматриваются в
[[00 Учебник/02 Рекомендательные системы/04 Последовательные рекомендации и признаки|отдельной главе]].

## От показа к обучающей метке

Для прогноза клика недостаточно объединить таблицу пользователей с таблицей
кликов. Нужны показы, по которым отклик мог не наступить. Одна строка обучения
может соответствовать одному объекту в одном запросе:

`request_id, user_id, item_id, position, shown_at, label`.

Положим, что клик относится к показу, если совпадают `request_id` и `item_id`
и он произошёл в интервале $(t,t+10\text{ мин}]$. Нулевую метку можно поставить
лишь после окончания этого интервала и получения всех относящихся к нему
событий.

Пусть данные полны до 10:26:

| Запрос и объект | Показ | Клик | Метка |
| --- | --- | --- | --- |
| `r1, A` | 10:00 | 10:01 | 1 |
| `r1, B` | 10:00 | нет | 0 |
| `r2, C` | 10:00 | 10:12 | 0 для окна 10 минут |
| `r3, D` | 10:20 | пока нет | ещё неизвестна |

Последнюю строку нельзя включать в обучение как отрицательную. До 10:30
пользователь ещё может кликнуть в пределах окна. Если события поступают
с задержкой, границу полноты данных, или *watermark*, сдвигают дополнительно.
В примере ниже доставка мгновенная; watermark обозначает именно полноту
событий, а не текущее время на часах.

```python
from datetime import datetime, timedelta

def clock(hm):
    return datetime.fromisoformat("2026-09-01T" + hm)

impressions = [
    ("r1", "Anya", "A", 1, clock("10:00")),
    ("r1", "Anya", "B", 2, clock("10:00")),
    ("r2", "Boris", "C", 1, clock("10:00")),
    ("r3", "Anya", "D", 1, clock("10:20")),
]
clicks = [
    ("r1", "A", clock("10:01")),
    ("r2", "C", clock("10:12")),
]

def click_labels(impressions, clicks, watermark, window):
    if window <= timedelta(0):
        raise ValueError("The label window must be positive.")
    result = []
    for request, user, item, position, shown_at in impressions:
        end = shown_at + window
        if end > watermark:
            label = None
        else:
            label = int(any(
                req == request and clicked_item == item
                and shown_at < at <= end
                for req, clicked_item, at in clicks
            ))
        result.append((request, item, label))
    return result

labels = click_labels(impressions, clicks, clock("10:26"),
                      timedelta(minutes=10))
assert [row[2] for row in labels] == [1, 0, 0, None]
print(labels)
```

Клик по `C` не исчезает из журнала. Он просто не является положительной
меткой для выбранного десятиминутного target. При окне 15 минут метка
этого показа станет 1. При переходе к покупкам понадобится другой тип
события и, возможно, другое окно атрибуции.

Нулевая метка в этой таблице означает «не зарегистрирован целевой отклик
в окне после данного показа». Она не доказывает неприязни к объекту:
пользователь мог не заметить карточку или отвлечься.

## От каталога к выдаче

Для каталога из $10^6$ объектов вычисление за 1 мкс на объект уже заняло бы
1 с последовательной работы. Векторизация и параллелизм меняют расчёт,
но дорогую модель с большим числом признаков обычно применяют к сокращённому
набору кандидатов.

![[00 Учебник/Assets/Figures/curated/recommender-data-2026-10-25/google-process.svg]]

*Google, [Recommendation systems overview](https://developers.google.com/machine-learning/recommendation/overview/types):
исходная схема candidate generation → scoring → re-ranking, без изменения
надписей или геометрии. [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/).
Части страницы воспроизведены из материалов, созданных и
[предоставленных Google](https://developers.google.com/terms/site-policies).*

На первом этапе несколько способов поиска предлагают кандидатов:
близкие к истории объекты, популярные в сегменте, похожие по содержимому.
На втором модель оценивает объединённое множество. На третьем из
ранжированного списка составляют выдачу с учётом ограничений, например
удаляют недоступные товары или ограничивают повторы одной категории.
На схеме Google это три этапа; название «двухступенчатая модель» обычно
относится к паре retrieval и ranking, без выделения последующей обработки
в отдельную модель.

Числа кандидатов зависят от каталога и бюджета времени. Их не следует
переносить из одной системы в другую как обязательную конфигурацию.
В учебном примере каталог может состоять из шести объектов, поиск вернёт
четыре, а итоговая выдача — два. Ошибку потери объекта на первом этапе
можно показать уже в таком масштабе.

## Split должен имитировать будущее

В [D2L, Splitting the dataset](https://d2l.ai/chapter_recommender-systems/movielens.html#splitting-the-dataset)
показаны два режима: случайное разбиение взаимодействий и исключение
последнего события каждого пользователя. В
[Recommenders, Data splitting techniques](https://github.com/recommenders-team/recommenders/blob/6232b154548c955315650d58dca6bf1411c56020/examples/01_prepare_data/data_split.ipynb)
к ним добавлены разбиение по времени внутри групп пользователей или объектов
и случайное разбиение внутри этих групп. Эти протоколы отвечают на разные
вопросы.

Случайное разбиение может быть уместно для восстановления скрытых оценок
из фиксированной таблицы. Оно не воспроизводит обучение в прошлом
с последующим предсказанием будущего: в обучении окажутся более поздние
взаимодействия того же пользователя и других пользователей.

### Две временные границы

Для модели, которую обучают 3 сентября и проверяют на последующих событиях,
обозначим границы через $t_1=3$ сентября и $t_2=5$ сентября.
Глобальные интервалы имеют вид:

$$
\begin{aligned}
\text{train}:&\quad t<t_1,\\
\text{validation}:&\quad t_1\le t<t_2,\\
\text{test}:&\quad t\ge t_2.
\end{aligned}
$$

На validation выбирают настройки; test используют после этого выбора.
В реальном эксперименте нужно также задать конец тестового интервала.
Если после выбора настроек модель переобучают на train и validation,
это уже новая обученная версия с более поздней границей. Её статистики
не следует приписывать исходной модели от 3 сентября.

<a id="worked-example-временного-split"></a>
### Почему последнее событие пользователя не задаёт общую дату

Пусть события имеют следующий вид:

| ID | Имя | Дата | Объект |
| --- | --- | --- | --- |
| 1 | Аня | 1 сентября | `A` |
| 2 | Борис | 1 сентября | `B` |
| 3 | Аня | 2 сентября | `B` |
| 4 | Аня | 3 сентября | `C` |
| 5 | Борис | 4 сентября | `D` |
| 6 | Борис | 5 сентября | `E` |
| 7 | Вера | 6 сентября | `F` |

При leave-last-one-out в test попадут 4, 6, 7, а в train — 1, 2, 3, 5.
Но для предсказания события Ани 3 сентября общие параметры модели уже
могут учитывать событие Бориса 4 сентября. Сохранение порядка внутри
каждой пользовательской истории не сохраняет порядок между историями.

```python
def date(day):
    return datetime(2026, 9, day)

events = [
    dict(id=1, user="Anya", item="A", at=date(1)),
    dict(id=2, user="Boris", item="B", at=date(1)),
    dict(id=3, user="Anya", item="B", at=date(2)),
    dict(id=4, user="Anya", item="C", at=date(3)),
    dict(id=5, user="Boris", item="D", at=date(4)),
    dict(id=6, user="Boris", item="E", at=date(5)),
    dict(id=7, user="Vera", item="F", at=date(6)),
]
cutoff, test_start = date(3), date(5)
train = [e for e in events if e["at"] < cutoff]
validation = [e for e in events if cutoff <= e["at"] < test_start]
test = [e for e in events if e["at"] >= test_start]
assert [[e["id"] for e in part] for part in (train, validation, test)] == [
    [1, 2, 3], [4, 5], [6, 7]
]

last = {}
for e in sorted(events, key=lambda e: (e["at"], e["id"])):
    last[e["user"]] = e["id"]
user_test = [e for e in events if e["id"] == last[e["user"]]]
user_train = [e for e in events if e["id"] != last[e["user"]]]
assert [e["id"] for e in user_train] == [1, 2, 3, 5]
assert max(e["at"] for e in user_train) > min(e["at"] for e in user_test)
print("Global split:", len(train), len(validation), len(test))
print("Per-user last events:", [e["id"] for e in user_test])
```

У Веры одна запись; при таком leave-last-one-out у неё нет обучающей истории.
Её нельзя объявить warm-start пользователем. Если исключить Веру,
оценка будет условной на выбранное подмножество пользователей.
В отчёте нужны правило исключения и размер этого подмножества.

У событий с одинаковым timestamp может не быть достоверного внутреннего
порядка. Сортировка по `id` делает код воспроизводимым, но не превращает
этот порядок в известную хронологию. Если цель — предсказание по прошлому,
одновременные события следует группировать либо использовать дополнительное
поле порядка, которое действительно было известно системе.

Метод `python_chrono_split(filter_by="user")` из Recommenders проводит
временную границу отдельно внутри каждой группы. Его название не означает,
что все обучающие события глобально предшествуют всем тестовым. Сами функции
разбиения также не восстанавливают признаки, доступность каталога и задержку
меток: эти проверки остаются частью подготовки данных.

<a id="data-contract"></a>
## Признаки на момент решения

Глобальное разбиение строк не спасает от признака, вычисленного с учётом
будущего. Допустим, запрос пришёл в 10:05. Покупка совершена в 10:00,
но поступила в систему в 10:07, а агрегат числа покупок обновился в 10:08.
Хотя время покупки меньше 10:05, новое значение агрегата было недоступно
в момент запроса.

У версии признака нужны как минимум два времени:
`event_time` — момент описываемого состояния и `available_at` — момент,
когда эта версия могла использоваться при обслуживании.
Для запроса $t$ оба должны быть не больше $t$. У признаков со сроком
актуальности дополнительно ограничивают возраст состояния.

В документации [Feast, Point-in-time joins](https://docs.feast.dev/getting-started/concepts/point-in-time-joins)
признаки относятся к водителю `101`. Это не пример рекомендаций, но операция
соединения та же, что для истории покупок или числа просмотров товара.

Для каждой строки запросов ищут последнее состояние того же водителя,
которое не позже времени запроса и не старше двух часов. В 01:15:30
подходит строка 01:00, но не 02:00. В 04:32:45 подходит 04:00.
Для запроса предыдущего дня нет прошлого значения вообще; для 16:26:17
последнее состояние 05:00 уже слишком старое.

[Apache 2.0](/licenses/feast-1e5e90ca-Apache-2.0.txt).*

TTL отсчитывают от времени каждой строки запроса. Если собрать этот же
учебный набор через неделю, подходящие исторические строки не должны
исчезнуть только из-за даты запуска подготовки.

```python
base = datetime(2021, 9, 17)
feature_rows = [
    dict(driver=101, event_time=base + timedelta(hours=h),
         available_at=base + timedelta(hours=h), trips=trips, earnings=money)
    for h, trips, money in [
        (0, 0, 0.0), (1, 1, 50.0), (2, 3, 142.0),
        (3, 4, 184.0), (4, 6, 238.0), (5, 8, 301.0)
    ]
]
query_times = [
    "2021-09-16T23:00:00", "2021-09-17T01:15:30",
    "2021-09-17T04:32:45", "2021-09-17T05:43:10",
    "2021-09-17T16:26:17",
]

def point_in_time(rows, driver, at, ttl, require_available=True):
    if ttl < timedelta(0):
        raise ValueError("TTL cannot be negative.")
    eligible = [
        row for row in rows
        if row["driver"] == driver
        and at - ttl <= row["event_time"] <= at
        and (not require_available or row["available_at"] <= at)
    ]
    return max(eligible,
               key=lambda row: (row["event_time"], row["available_at"]),
               default=None)

joined = [
    point_in_time(feature_rows, 101, datetime.fromisoformat(at),
                  timedelta(hours=2))
    for at in query_times
]
assert [None if row is None else row["trips"] for row in joined] == [
    None, 1, 6, 8, None
]
assert [None if row is None else row["earnings"] for row in joined] == [
    None, 50.0, 238.0, 301.0, None
]

# A correction of the 01:00 value arrived only at 03:00.
corrected = feature_rows + [
    dict(driver=101, event_time=base + timedelta(hours=1),
         available_at=base + timedelta(hours=3), trips=99, earnings=999.0)
]
query = datetime.fromisoformat(query_times[1])
safe = point_in_time(corrected, 101, query, timedelta(hours=2))
leaky = point_in_time(corrected, 101, query, timedelta(hours=2),
                      require_available=False)
assert (safe["earnings"], leaky["earnings"]) == (50.0, 999.0)
print([None if row is None else row["trips"] for row in joined])
print("Available then / later correction:",
      safe["earnings"], leaky["earnings"])
```

Первая часть кода воспроизводит пять строк исходного рисунка. Исправление
в 03:00 добавлено отдельно, чтобы показать второе время: для запроса
в 01:15:30 ответ 999 является утечкой, хотя `event_time` версии равен 01:00.

Согласно [документации Feast на ревизии 1e5e90ca](https://github.com/feast-dev/feast/blob/1e5e90ca01b0a6b1877a6c809436f0d8d574aad6/docs/getting-started/concepts/point-in-time-joins.md), обычный point-in-time join
ограничивает время события, а `created_timestamp_column` без дополнительного
режима служит для дедупликации. Режим `filter_by_created_timestamp=True`
добавляет проверку времени создания версии. При этом строки без timestamp
создания исключаются. Неподдерживающее этот режим хранилище выдаёт ошибку.
Это поведение описано для указанной ревизии; установленная версия Feast
и выбранное хранилище требуют отдельной проверки.

Даже этот режим восстанавливает доступность при обслуживании только тогда,
когда соответствующий timestamp отражает реальную доступность значения
онлайн. Время записи в хранилище и время публикации в онлайн-сервис
могут различаться.

## Как строятся negatives

Для уже зарегистрированного показа отрицательная метка означает отсутствие
целевого отклика в завершённом окне. Для обучения поиска кандидатов часто
нужно сравнить положительный объект с объектами, по которым показа не было.
Такие объекты называют *sampled negatives*: это обучающее допущение,
а не наблюдаемая отрицательная оценка.

Пусть Аня купила `A` 1 сентября и `B` 2 сентября. Для примера с положительным
`B` разрешённый каталог на 2 сентября состоит из `A,B,C`. Если исключить
прошлую покупку `A` и текущий положительный `B`, остаётся `C`.
3 сентября Аня действительно купит `C`. Во время обучения по состоянию
на 2 сентября это ещё неизвестно: выбранный negative может оказаться
будущим положительным объектом.

```python
import random

catalog = {
    "A": date(1), "B": date(1), "C": date(2),
    "D": date(4), "E": date(5), "F": date(6),
}

def available_unseen(user, at):
    available = {item for item, published_at in catalog.items()
                 if published_at <= at}
    # This toy log has no ingestion delays.
    seen = {e["item"] for e in events
            if e["user"] == user and e["at"] < at}
    return sorted(available - seen)

def sample_unobserved(user, positive, at, k, seed=7):
    if positive not in catalog or catalog[positive] > at:
        raise ValueError("The positive must be available at the decision time.")
    pool = [i for i in available_unseen(user, at) if i != positive]
    if not 0 <= k <= len(pool):
        raise ValueError("Not enough distinct candidates for this sample.")
    return random.Random(seed).sample(pool, k)

negatives = sample_unobserved("Anya", "B", date(2), k=1)
batch = [("Anya", "B", 1)] + [("Anya", item, 0) for item in negatives]
assert negatives == ["C"]
assert "C" in {e["item"] for e in events
               if e["user"] == "Anya" and e["at"] > date(2)}
assert all(catalog[item] <= date(2) for _, item, _ in batch)
print(batch)
```

Здесь выборка равномерная без повторов. При требовании четырёх negatives
код сообщит об ошибке, а не войдёт в бесконечный цикл и не добавит
будущие товары `D,E,F`. В большой системе пул обычно не перечисляют
целиком; это не меняет ограничения доступности и смысл меток.

Другой вариант — использовать положительные объекты других пользователей
в том же mini-batch. При *in-batch negatives* распределение сравниваемых
объектов определяется составом batch; популярный объект может встречаться
чаще и одновременно быть подходящим для нескольких пользователей.
Такой способ не устраняет ложные отрицательные примеры.

Распределение семплирования $q(i\mid u,t)$ входит в определение эксперимента.
Равномерная выборка объектов и выборка пропорционально популярности дают
разные частоты ошибок. В задаче обучения порядку это могут быть разные
функции риска; при обучении вероятностей дополнительные отрицательные
примеры также меняют долю классов. Выход такой модели нельзя автоматически
считать калиброванной вероятностью клика в исходном потоке.

![[Assets/Sources/Dive into Deep Learning — Recommender Systems/rec-ranking.svg]]

*Zhang et al., [D2L, Personalized Ranking](https://d2l.ai/chapter_recommender-systems/ranking.html):
исходная схема перехода от взаимодействий пользователя к парным сравнениям.
[CC BY-SA 4.0](https://github.com/d2l-ai/d2l-en/blob/23d7a5aecceee57d1292c56e90cce307f183bb0a/LICENSE-SUMMARY).
Вывод BPR по этой схеме продолжается в
[[00 Учебник/02 Рекомендательные системы/03 Ranking и нейронные рекомендательные модели|главе о ранжировании]].*

В левой матрице строки соответствуют пользователям, столбцы — объектам.
У пользователя $u_1$ есть положительные взаимодействия с $i_2$ и $i_3$;
для $i_1$ и $i_4$ стоят знаки вопроса. Справа для этого же пользователя
построена матрица сравнений: столбец задаёт объект $i$, строка — объект $j$.
Плюс в строке $j_1$ и столбце $i_2$ означает допущение $i_2>_{u_1}i_1$.
В симметричной ячейке стоит минус: там сравнивают обратную пару.

Из строки $u_1$ получаются четыре положительных сравнения:
$i_2>_{u_1}i_1$, $i_2>_{u_1}i_4$, $i_3>_{u_1}i_1$ и $i_3>_{u_1}i_4$.
Порядок между двумя положительными объектами $i_2,i_3$ не задан,
как и порядок между двумя ненаблюдаемыми $i_1,i_4$: в этих ячейках остаётся
вопрос. Диагональ не используется. Парные метки получены из предположения,
что объект с положительным взаимодействием предпочтительнее объекта
без такого взаимодействия. Пользователь не сообщал все четыре сравнения
непосредственно.

## Какие ошибки остаются после поиска кандидатов

Пусть для запроса в каталоге есть два релевантных объекта `C` и `E`.
Один поиск вернул `A,B,C`, другой — `B,D`. После объединения и удаления
повторов ranker получает `A,B,C,D`. Объект `E` потерян до ранжирования.

При $K=2$ ранжирование может показать `C` и ещё один объект.
Тогда в выдачу попал один из двух релевантных объектов: recall равен $1/2$.
Более точная модель ранжирования не сможет вернуть `E` из отсутствующих
кандидатов.

```python
channels = {
    "history": ["A", "B", "C"],
    "popular": ["B", "D"],
}
candidate_sources = {}
for name, items in channels.items():
    for item in items:
        candidate_sources.setdefault(item, []).append(name)

relevant = {"C", "E"}
candidate_set = set(candidate_sources)
scores = {"A": 0.6, "B": 0.8, "C": 0.9, "D": 0.7}
slate = sorted(candidate_set, key=lambda i: (-scores[i], i))[:2]

candidate_recall = len(relevant & candidate_set) / len(relevant)
conditional_recall = len(relevant & set(slate)) / len(relevant & candidate_set)
final_recall = len(relevant & set(slate)) / len(relevant)
assert slate == ["C", "B"]
assert (candidate_recall, conditional_recall, final_recall) == (0.5, 1.0, 0.5)
assert final_recall == candidate_recall * conditional_recall
assert candidate_sources["B"] == ["history", "popular"]
print(slate, candidate_recall, final_recall)
```

Для одного запроса обозначим множество релевантных объектов через $G$,
кандидатов — через $C$, итоговую выдачу — через $F\subseteq C$. Если
$|G|>0$ и $|G\cap C|>0$, то

$$
\begin{aligned}
R_{\mathrm{cand}}&=\frac{|G\cap C|}{|G|},\\
R_{\mathrm{rank}\mid C}&=\frac{|G\cap F|}{|G\cap C|},\\
R_{\mathrm{final}}&=R_{\mathrm{cand}}R_{\mathrm{rank}\mid C}.
\end{aligned}
$$

Когда $G\cap C$ пусто, итоговый recall равен нулю, а условная доля
имеет нулевой знаменатель и не определена. Её нужно отдельно оговорить
в реализации метрики.

Средние по пользователям нельзя перемножать таким же образом.
Например, у первого пользователя один релевантный объект, он найден,
но не показан. У второго четыре релевантных объекта, один найден и показан.
Средний итоговый recall равен $(0+1/4)/2=1/8$, тогда как произведение
средних двух множителей равно $((1+1/4)/2)\cdot((0+1)/2)=5/16$.
Разложение точно для одного запроса и для согласованного подсчёта
общих числителей и знаменателей, но не для произвольных средних метрик.

## Популярность как воспроизводимая исходная модель

В глобальном train из примера осталось три события: покупка `A` Аней
и две покупки `B` разными пользователями. Число взаимодействий с `A`
равно 1, с `B` — 2. Для `C` обучающих событий нет, хотя на момент
запроса этот товар уже доступен.

```python
from collections import Counter

popularity = Counter(e["item"] for e in train)

def recommend_popular(user, at, k):
    if k < 0:
        raise ValueError("k cannot be negative.")
    if at < cutoff:
        raise ValueError("This model was trained after the request time.")
    eligible = available_unseen(user, at)
    return sorted(eligible, key=lambda item: (-popularity[item], item))[:k]

assert dict(popularity) == {"A": 1, "B": 2}
assert recommend_popular("Anya", date(3), 3) == ["C"]
assert recommend_popular("Boris", date(3), 3) == ["A", "C"]
assert recommend_popular("Vera", date(3), 3) == ["B", "A", "C"]
print(dict(popularity), recommend_popular("Vera", date(3), 3))
```

Счётчики обучены только на train. История конкретного пользователя содержит
только события до момента запроса. Модель со счётчиками на 3 сентября
не применяется для исторического запроса 1 сентября. Из кандидатов
исключены уже купленные объекты, а при равенстве популярности порядок
определяется идентификатором. Поэтому для Ани остаётся `C`, для Бориса —
`A,C`, а для новой Веры — `B,A,C`. Выдача может содержать меньше $K$
объектов, если допустимый пул меньше $K$.

Монотонное преобразование $\log(1+\mathrm{count}(i))$ сохранило бы этот порядок.
Оно не добавило бы персонализации и не сделало бы нулевой счётчик нового
товара оценкой его качества.

<a id="bias-baseline-как-проверка-dataset"></a>
Для явных оценок другая исходная модель имеет вид

$$
\hat r_{ui}=\mu+b_u+b_i,
$$

где $\mu$ — общий уровень оценок, $b_u$ — склонность пользователя ставить
более высокие или низкие оценки, $b_i$ — отклонение для фильма.
Её обучение и численный пример начинаются в
[[00 Учебник/02 Рекомендательные системы/02 Collaborative filtering и matrix factorization|следующей главе]].
Хороший результат простой модели сам по себе не доказывает утечку;
проверять нужно происхождение признаков, разбиение и целевые события.

## Типичные ошибки постановки

До сравнения моделей у эксперимента должны быть зафиксированы момент
обучения, интервалы признаков и меток, доступный каталог, правило повторных
рекомендаций и способ получения отрицательных примеров. Иначе меняется
сама задача, а разницу метрик легко приписать архитектуре.

В частности, нельзя сравнивать две модели на разных наборах кандидатов
и объявлять разницу качеством ранжирования. При исключении новых пользователей
нужно отдельно показать их число и результат для этого среза.
Клики без логов показов не позволяют построить ту же задачу response
prediction, что полные логи показов.
