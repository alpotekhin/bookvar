# GPU, CUDA и иерархия памяти

Чтобы сложить два вектора, достаточно прочитать пару чисел, сложить их
и записать результат. Разные пары не зависят друг от друга, поэтому
их можно обрабатывать параллельно. У матричного умножения параллельной
работы ещё больше, но появляется другая возможность: одно загруженное
число участвует во многих произведениях. Для GPU важны обе особенности —
много независимой работы и повторное использование данных.

При этом короткое сложение на GPU может оказаться медленнее, чем на CPU.
Подготовка запуска и передача массивов иногда стоят дороже самой операции.
А большая матрица может обрабатываться медленно даже при свободных
арифметических блоках, если те ждут операнды из памяти. Чтобы понимать
такие результаты, разберём путь от программы на CUDA до её выполнения
на устройстве.

## Один запуск, тысяча элементов

Функцию, запускаемую на GPU, называют **ядром**, или *kernel*.
Обычно один и тот же код ядра выполняется многими потоками, но каждый
поток получает свой номер и обрабатывает свою часть данных.

Пусть два входных массива и выходной массив уже находятся в памяти GPU.
Для 1000 чисел FP32 достаточно такого фрагмента CUDA C++:

```cpp
__global__ void add(const float* a, const float* b, float* c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) {
        c[i] = a[i] + b[i];
    }
}

// Фрагмент запуска: выделение памяти, копирование и проверки ошибок опущены.
add<<<4, 256>>>(a, b, c, 1000);
```

CPU, запускающий работу, называется **host**, GPU — **device**.
Числа 4 и 256 задают четыре блока по 256 потоков. Все блоки одного запуска
образуют сетку — *grid*. Всего запущено 1024 потока, но полезных элементов
1000. Проверка границы не даёт последним 24 потокам обратиться за пределы
массива.

| Блок | Номера потоков внутри блока | Индексы элементов |
|---|---|---|
| 0 | 0…255 | 0…255 |
| 1 | 0…255 | 256…511 |
| 2 | 0…255 | 512…767 |
| 3 | 0…255 | 768…1023; запись только до 999 |

Например, поток 7 блока 2 вычисляет $i=2\cdot256+7=519$.
Соседний поток получает 520. У FP32 размер элемента равен четырём байтам,
поэтому адреса отличаются на четыре байта.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/stanford-cs336-2026/systems/cuda-grid-cta.png]]

*Программная иерархия CUDA: grid содержит блоки, каждый блок — потоки.
CTA означает Cooperative Thread Array; в обычном CUDA C++ это thread block.
Оригинальная схема NVIDIA из [PTX ISA](https://docs.nvidia.com/cuda/parallel-thread-execution/#thread-hierarchy),
использованная в [Stanford CS336, Lecture 6](https://github.com/stanford-cs336/lectures/blob/8b59b50730766695c2ffedd1a79c50cd09b9eb91/lecture_06.py).
Зелёная рамка обозначает один запуск программы, а не отдельное устройство.*

Номера потоков задают работу, но не время её выполнения. Четыре блока
не обязаны стартовать одновременно или в порядке номеров. Кроме того,
возврат из строки запуска означает, что работа поставлена в очередь,
а не что массив уже заполнен. Зависимости с CPU и другими запусками
нужно задавать явно. Подробная семантика и пример проверки границ —
в [CUDA Programming Guide: Intro to CUDA C++](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/intro-to-cuda-cpp.html).

## Как блоки попадают на вычислители

GPU содержит несколько **потоковых мультипроцессоров** — Streaming
Multiprocessors, или SM. В рамках обычного выполнения блок размещается
на одном SM: его потоки используют регистры этого SM и общую память блока.
Один SM может одновременно держать несколько блоков, если хватает ресурсов.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/stanford-cs336-2026/systems/gpu-hardware.png]]

*Схема из [Stanford CS336, Lecture 6](https://github.com/stanford-cs336/lectures/blob/8b59b50730766695c2ffedd1a79c50cd09b9eb91/lecture_06.py).
Внутри каждого SM выделены регистры и область L1/shared memory; L2 обслуживает
много SM, а HBM хранит основные массивы за пределами вычислительного кристалла.
Число нарисованных SM условно. Планировщики и арифметические блоки на этой
схеме не показаны.*

Потоки блока объединяются в группы по 32 — **warps**. Позиция потока
в группе называется *lane*. В нашем блоке из 256 потоков восемь warps.
Когда одна группа не может продолжить вычисление, например ожидает
результат чтения памяти, планировщик может выбрать другую готовую группу.
Для этого её состояние уже должно находиться на SM.

Так GPU скрывает часть задержек: пока одни операнды доставляются,
другие инструкции выполняются. Задержка чтения сама по себе не исчезает.
Если готовых групп нет или все они ждут один и тот же ограниченный ресурс,
переключаться не на что.

При сложении всего 1000 элементов мы запускаем только четыре блока.
На устройстве с десятками SM многие мультипроцессоры вообще не получат
работы. Этот пример объясняет индексацию, но не демонстрирует эффективную
загрузку большого GPU.

### Почему ветвление внутри warp бывает дорогим

Модель выполнения называется **SIMT** — Single Instruction, Multiple Threads.
При выдаче инструкции она применяется к активным потокам группы.
Если часть потоков должна выполнить одну ветку, а часть другую,
для этих путей используются разные маски активности. В простом случае
оба пути приходится выполнить, причём в каждом работает только часть lanes.

Например, если первые 16 потоков выполняют длинный расчёт A, а остальные —
длинный расчёт B, это не эквивалентно двум независимым процессорам,
исполняющим A и B одновременно. Если же условие одинаково для всей группы,
такого расхождения внутри неё нет. Короткий условный код компилятор также
может заменить предикатными инструкциями; стоимость определяется получившимся
кодом, а не одним наличием `if`.

Начиная с Volta, NVIDIA поддерживает независимое планирование потоков
(*Independent Thread Scheduling*). Поэтому объяснение SIMT нельзя превращать
в обещание, что все 32 потока всегда находятся на одной строке программы.
В частности, обмен через память нельзя считать синхронизированным только
потому, что участники находятся в одном warp. Для обмена внутри группы
и внутри блока существуют соответствующие операции синхронизации.
[CUDA Programming Guide: SIMT kernels](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html).

### Occupancy: сколько групп помещается, а не сколько пользы они приносят

**Occupancy** — отношение числа размещённых на SM warps к аппаратному
максимуму. Размещённая группа не обязательно готова выполнять инструкцию:
она может ждать память или зависимый результат. Поэтому occupancy
и доля полезной работы — разные величины.

Рассмотрим условный SM с 65 536 регистрами по 32 бита и максимумом
64 warps. Блок содержит 128 потоков, каждый использует 160 регистров.
Только по регистрам получаем:

$$
\begin{aligned}
R_{\mathrm{block}}&=128\cdot160=20480,\\
B_{\mathrm{resident}}&=\lfloor65536/20480\rfloor=3,\\
W_{\mathrm{resident}}&=3\cdot(128/32)=12.
\end{aligned}
$$

Occupancy в этом упрощённом расчёте равна $12/64=18.75\%$.
Реальное размещение дополнительно ограничивают общая память,
число блоков и потоков, а также гранулярность выделения регистров.
В [CS336 Lecture 6](https://github.com/stanford-cs336/lectures/blob/8b59b50730766695c2ffedd1a79c50cd09b9eb91/lecture_06.py)
можно выполнить этот расчёт и посмотреть, как меняется результат
при другом размере блока и расходе регистров.

Снизив число регистров до 64 на поток, по тем же ограничениям можно
разместить восемь блоков, то есть 32 warps и получить 50%.
Но это ещё не доказывает ускорения. Возможно, первый вариант дольше
хранил полезные промежуточные значения в регистрах, а второй вынужден
пересчитывать их или обращаться к памяти. Максимизировать occupancy
как самостоятельную цель не нужно.

Похожий эффект возникает в конце сетки. Если 16 SM могут держать только
по одному нашему блоку, а мы запускаем 17 одинаковых блоков, условно
получаются две волны: 16 блоков и один. Большая часть устройства простаивает
в конце. Это *wave quantization*. Если на SM помещается несколько блоков,
ёмкость волны другая; правило «сделать число блоков кратным числу SM»
без этой оговорки неверно.

## Где хранится один элемент

Предположим, поток выполняет `c[i] = a[i] + b[i]`.
Массивы находятся в глобальном адресном пространстве устройства.
Нужные значения проходят через систему памяти, попадают в регистры,
и инструкция сложения работает с этими операндами. Результат затем
записывается обратно. Попадание в кэш может избавить от чтения
более далёкого уровня.

| Уровень | Кто использует | Как появляется повторное использование |
|---|---|---|
| Регистры | Отдельный поток; физически регистровый файл SM | Компилятор сохраняет промежуточные значения |
| Shared memory | Обычно потоки одного блока | Программа явно загружает общий фрагмент и синхронизирует участников |
| L1 | Обращения, обслуживаемые данным SM | Аппаратное кэширование; политика зависит от инструкции и архитектуры |
| L2 | Многие SM устройства | Повторные обращения к уже загруженным данным |
| Память устройства, например HBM | Глобальные массивы и другие данные | Основное хранилище весов, активаций и буферов |

L1 и shared memory могут использовать общий физический ресурс SRAM,
но семантика у них разная: кэшем управляет аппаратура, а shared memory
явно использует программа. Обычные блоки не могут обращаться к shared memory
друг друга. В новых архитектурах есть отдельные механизмы кластеров блоков
и distributed shared memory; они требуют соответствующего способа запуска
и не подразумеваются в нашем примере.

**Local memory** — особенно неудачное для интуиции название. Это память,
логически принадлежащая одному потоку, а не обязательно быстрая память
рядом с вычислителем. Если регистров не хватает, часть значений может
попасть в local memory; такой перенос называется *register spill*.
Он создаёт дополнительные чтения и записи через систему памяти.
Local memory используется и по другим причинам, например для некоторых
локальных массивов. Появление такого массива в исходнике ещё не говорит,
как именно компилятор его разместит.

Размеры кэшей и задержки нельзя переносить с одной модели GPU на другую
без проверки. И даже для одного устройства нужно различать ресурс
одного SM и суммарный ресурс всех SM. Для объяснения механизма важнее
сначала понять владельца и способ доступа, а затем подставлять
параметры конкретного ускорителя.

## Coalescing: сколько секторов затронул warp

Память обслуживает обращения не по одному байту. Рассмотрим глобальные
чтения FP32 на NVIDIA с compute capability не ниже 6.0: полезная
модель объединения обращений использует выровненные **32-байтовые секторы**.
Одна инструкция чтения 32 потоков может затронуть несколько таких секторов.
Это называется *memory coalescing*.

Если все потоки читают соседние числа, а начало массива выровнено
по 32 байтам, первые восемь чисел попадают в сектор 0, следующие восемь —
в сектор 1 и так далее. Для 32 чисел нужны четыре сектора, то есть 128 байт.
Все запрошенные данные используются.

Увидеть роль границ проще на уменьшенной схеме. В примере ниже всего
четыре потока, а каждый сегмент содержит четыре адреса. Слева потоки
запрашивают адреса 0–3, справа — 8–11. В обоих случаях вся группа
обращается внутрь одного сегмента.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/systems-visuals-2026-09/nvidia-coalescing-4.png]]

*Обращения внутри одного сегмента. NVIDIA и University of Illinois,
[GPU Teaching Kit, Memory Coalescing, слайд 4](https://engineering.purdue.edu/~smidkiff/ece563/NVidiaGPUTeachingToolkit/Mod6/Lecture-6-2-memory-coalescing.pdf#page=4),
[CC BY-NC 4.0](https://creativecommons.org/licenses/by-nc/4.0/).
Из слайда выделена исходная схема; подписи и стрелки не изменены.
Четыре потока и четыре адреса на сегмент — учебное упрощение,
не размеры warp и сектора современного GPU.*

На следующем рисунке слева шаг между адресами увеличился до двух:
0, 2, 4, 6. Справа адреса 10–13 идут подряд, но пересекают границу
сегментов 8–11 и 12–15. Теперь в каждом из двух примеров затронуты
два сегмента, хотя потокам по-прежнему нужны только четыре значения.
Первый случай показывает влияние шага, второй — выравнивания.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/systems-visuals-2026-09/nvidia-coalescing-5.png]]

*Шаг и смещение увеличивают число затронутых сегментов.
NVIDIA и University of Illinois,
[Memory Coalescing, слайд 5](https://engineering.purdue.edu/~smidkiff/ece563/NVidiaGPUTeachingToolkit/Mod6/Lecture-6-2-memory-coalescing.pdf#page=5),
[CC BY-NC 4.0](https://creativecommons.org/licenses/by-nc/4.0/).
Выделена оригинальная схема. Её надпись «Un-coalesced» означает,
что обращения не помещаются в один сегмент; это не отменяет
объединения обращений внутри каждого из затронутых сегментов.*

Вернёмся к 32 потокам и 32-байтовым секторам.
Теперь поток с номером $\ell$ читает элемент $s\ell$, где $s$ — шаг
в элементах. Адрес относительно начала массива равен $4s\ell$ байтам.
Получаем:

| Шаг $s$ | Индексы первых четырёх потоков | Секторов на warp | Байтов в затронутых секторах | Полезная доля |
|---:|---|---:|---:|---:|
| 1 | 0, 1, 2, 3 | 4 | 128 | 100% |
| 2 | 0, 2, 4, 6 | 8 | 256 | 50% |
| 4 | 0, 4, 8, 12 | 16 | 512 | 25% |
| 8 | 0, 8, 16, 24 | 32 | 1024 | 12.5% |
| 32 | 0, 32, 64, 96 | 32 | 1024 | 12.5% |

Во всех строках потокам нужны те же 128 полезных байт. Меняется число
секторов, которые приходится затронуть. Это не обещание такого же
отношения времени: повторные обращения могут попасть в кэш, а другие
операции — ограничить скорость. Число секторов инструкции также не равно
безусловно объёму обмена с HBM.

Выравнивание тоже важно. Если последовательный доступ начать со второго
числа, то есть со смещения 4 байта, 128 полезных байт пересекут уже
пять секторов. И наоборот: перестановка номеров потоков, читающих
**тот же набор адресов**, не увеличит число секторов. «Соседние потоки
читают соседние числа» — удобный достаточный шаблон, не обязательное
соответствие один к одному.

Иллюстрации этих случаев и измерения на V100 есть в
[NVIDIA CUDA Best Practices, Coalesced Access to Global Memory](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/#coalesced-access-to-global-memory).
В лекционных объяснениях иногда используют модель 128-байтовых cache lines;
её нельзя выдавать за универсальное число фактических транзакций современных GPU.

## Shared memory: почему соседние банки лучше одного

Блоку часто нужно не просто читать свои элементы, а обмениваться ими.
Для этого потоки могут загрузить общий фрагмент в shared memory.
Близость этой памяти помогает, но не делает все способы доступа равноценными.

Для обычных 32-битных обращений shared memory разделена на 32 банка.
Последовательные слова попадают в последовательные банки. Если один warp
обращается к разным словам одного банка, запрос приходится разбить на
несколько конфликтно-свободных обращений — возникает **bank conflict**.
Чтение одного и того же слова несколькими потоками допускает рассылку
значения, поэтому его нельзя приравнивать к чтению разных слов одного банка.

Начнём с меньшего примера: четыре потока и четыре банка.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/systems-foundations-review-2026-09/banks-stride-1.svg]]

*Шаг 1: четыре потока T0–T3 обращаются к четырём разным банкам.
Конфликта нет.*

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/systems-foundations-review-2026-09/banks-stride-2.svg]]

*Шаг 2: адреса распределились между двумя банками; каждому приходится
обслужить два разных слова последовательно.*

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/systems-foundations-review-2026-09/banks-stride-4.svg]]

*Шаг 4: все четыре разных слова находятся в одном банке.
Все три оригинальные схемы — Jakub Beránek,
[Hardware Effects on GPU: Bank Conflicts](https://github.com/Kobzol/hardware-effects-gpu/blob/1b03fa9816002ba835132a2a34581a7481964e61/bank-conflicts/README.md),
[MIT](https://github.com/Kobzol/hardware-effects-gpu/blob/1b03fa9816002ba835132a2a34581a7481964e61/LICENSE.md).
Это уменьшенная учебная модель, не утверждение, что в NVIDIA GPU четыре банка.*

Теперь вернёмся к 32 банкам. Двумерный FP32-массив `tile[32][32]`
хранится по строкам. С точностью до постоянного смещения банка:

$$
\operatorname{bank}(r,c)=(32r+c)\bmod32=c.
$$

При чтении строки разные потоки обращаются к разным банкам. При чтении
столбца `tile[lane][c]` все 32 разных слова оказываются
в банке $c$: конфликт требует обслужить 32 разных обращения последовательно.

Добавим одну служебную колонку и выделим `tile[32][33]`.
Теперь

$$
\begin{aligned}
\operatorname{bank}(r,c)&=(33r+c)\bmod32\\
&=(r+c)\bmod32.
\end{aligned}
$$

Для фиксированного столбца $c$ разные номера строки дают все 32 банка.
Дополнительные 32 числа занимают 128 байт, или 3.125% от прежних 4096 байт.
Изменилось размещение, а не математическая операция. Этот padding устраняет
именно описанный конфликт FP32-доступов; для другой ширины данных
и векторных инструкций схему нужно проверить заново.

Объединение глобальных обращений и конфликты банков относятся к разным
уровням. Можно хорошо прочитать строки из глобальной памяти, а затем
неудачно записать столбцы в shared memory. В задаче транспонирования
поэтому приходится согласовывать оба этапа.
[NVIDIA: Shared Memory and Memory Banks](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/#shared-memory-and-memory-banks).

## Блочное матричное умножение

Пусть $C=AB$, где $A$ имеет форму $M\times K$, а $B$ — $K\times N$.
Каждый элемент результата равен

$$
C_{ij}=\sum_{k=0}^{K-1}A_{ik}B_{kj}.
$$

Если поток независимо вычисляет один $C_{ij}$, он запрашивает строку A
и столбец B. Соседний результат снова использует многие из тех же чисел.
Кэши могут помочь, но программа пока не задаёт совместное использование
внутри блока.

В **блочном алгоритме**, или *tiling*, блок отвечает за прямоугольный
фрагмент C. На очередном шаге по оси K потоки совместно загружают
соответствующие фрагменты A и B, используют их для многих произведений,
а частичные суммы сохраняют до следующего шага.

Проследим это на матрицах $4\times4$ и фрагментах $2\times2$.
В оригинальных схемах ниже матрицы названы M, N и P: это наши A, B
и C соответственно, а не размеры матриц из формулы выше. Блок (0, 0)
вычисляет четыре элемента в левом верхнем углу результата.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/systems-visuals-2026-09/nvidia-gemm-step-6.png]]

*Шаг 1 — загрузка. NVIDIA и University of Illinois,
[GPU Teaching Kit, Tiled Matrix Multiplication, слайд 6](https://engineering.purdue.edu/~smidkiff/ece563/NVidiaGPUTeachingToolkit/Mod4/Lecture-4-3-tiled-matrix-multiplication.pdf#page=6),
[CC BY-NC 4.0](https://creativecommons.org/licenses/by-nc/4.0/).
Здесь и на трёх следующих рисунках выделены исходные схемы без перерисовки.*

Четыре потока совместно переносят два фрагмента в shared memory:
первые два столбца нужных строк M и первые две строки нужных столбцов N.
Всего загружено восемь чисел. После завершения загрузки каждый поток
может читать не только собственный элемент, но и элементы, принесённые
соседями по блоку.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/systems-visuals-2026-09/nvidia-gemm-step-7.png]]

*Шаг 2 — произведения для $k=0$.
NVIDIA и University of Illinois,
[Tiled Matrix Multiplication, слайд 7](https://engineering.purdue.edu/~smidkiff/ece563/NVidiaGPUTeachingToolkit/Mod4/Lecture-4-3-tiled-matrix-multiplication.pdf#page=7),
[CC BY-NC 4.0](https://creativecommons.org/licenses/by-nc/4.0/).*

Для $P_{0,0}$ нужны $M_{0,0}$ и $N_{0,0}$, для $P_{0,1}$ —
тот же $M_{0,0}$ и $N_{0,1}$. Две стрелки от $M_{0,0}$ показывают
повторное использование: одно загруженное число участвует в двух
результатах. Аналогично $N_{0,0}$ используется для $P_{0,0}$ и $P_{1,0}$.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/systems-visuals-2026-09/nvidia-gemm-step-8.png]]

*Шаг 3 — произведения для $k=1$ из тех же загруженных фрагментов.
NVIDIA и University of Illinois,
[Tiled Matrix Multiplication, слайд 8](https://engineering.purdue.edu/~smidkiff/ece563/NVidiaGPUTeachingToolkit/Mod4/Lecture-4-3-tiled-matrix-multiplication.pdf#page=8),
[CC BY-NC 4.0](https://creativecommons.org/licenses/by-nc/4.0/).*

Нового чтения входов из глобальной памяти на этом шаге не требуется.
Например, накопленная сумма для $P_{0,0}$ теперь равна
$M_{0,0}N_{0,0}+M_{0,1}N_{1,0}$. Это ещё не весь результат:
во внутреннем измерении четыре элемента, а мы обработали только два.
Стрелки к P показывают, в какую сумму входит произведение; они
не требуют записывать эту сумму в глобальную память после каждого шага.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/systems-visuals-2026-09/nvidia-gemm-step-9.png]]

*Шаг 4 — загрузка следующей пары фрагментов.
NVIDIA и University of Illinois,
[Tiled Matrix Multiplication, слайд 9](https://engineering.purdue.edu/~smidkiff/ece563/NVidiaGPUTeachingToolkit/Mod4/Lecture-4-3-tiled-matrix-multiplication.pdf#page=9),
[CC BY-NC 4.0](https://creativecommons.org/licenses/by-nc/4.0/).*

По M сдвигаемся вправо, по N — вниз: нужны значения для $k=2,3$.
Фрагмент P остаётся тем же. После двух следующих умножений с накоплением
каждый из четырёх результатов будет готов. Данные в shared memory
меняются, а накопленные суммы сохраняются в регистрах потоков.

Для квадратных фрагментов $b\times b$ одна полная фаза — загрузка пары
фрагментов и обработка всех b значений k — даёт:

$$
\begin{aligned}
\text{загружено чисел}&=2b^2,\\
\text{выполнено FMA}&=b^3,\\
\text{FLOP}&=2b^3.
\end{aligned}
$$

FMA — умножение с накоплением; при таком подсчёте оно считается двумя
арифметическими операциями. При $b=16$ загружаются 512 чисел FP32,
то есть 2048 байт, и выполняются 8192 FLOP. Получается 4 FLOP на байт
входных фрагментов. Здесь пока не учтены итоговая запись C,
неполные края и обращения других блоков.

При независимом чтении двух операндов для каждого произведения было бы
$2b^3=8192$ запросов чисел вместо 512: повторное использование уменьшает
их число в 16 раз. Это сравнение алгоритмических загрузок, не гарантия
16-кратного сокращения реального HBM-трафика: исходный вариант тоже мог
пользоваться кэшами.

В реализации через shared memory возникает важная зависимость.
Нельзя начинать использовать фрагмент до завершения его загрузки всеми
участниками. И нельзя перезаписывать общий буфер следующей порцией,
пока другие потоки читают предыдущую. Для простого CUDA-ядра это две
точки синхронизации блока; `__syncthreads()` должны достигать
все участвующие потоки, а не только потоки с допустимым индексом на краю.
Недостающие элементы обычно заполняют нулями, сохраняя согласованный барьер.

Увеличение фрагмента повышает повторное использование, но требует больше
регистров для сумм и больше shared memory для входов. Блоков на SM
может стать меньше; неполные края будут тратить больше работы впустую.
Поэтому размер фрагмента подбирают под форму задачи и устройство,
а не увеличивают без ограничений.

### Повторное использование между блоками: роль L2

Shared memory обслуживает взаимодействие внутри блока. Кэш L2 может
помочь разным блокам, которым нужны одинаковые части A или B.
На это влияет порядок соответствия программ выходным фрагментам.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/inference-serving/triton-grouped-vs-row-major.png]]

*Оригинальная иллюстрация из [Triton, Matrix Multiplication](https://triton-lang.org/main/getting-started/tutorials/03-matrix-multiplication.html),
[исходный файл](https://github.com/triton-lang/triton/blob/1b24a39939875de5333e3990bec3ddcbfc64eb80/docs/getting-started/tutorials/grouped_vs_row_major_ordering.png),
MIT. Сравнивается порядок обхода выходных блоков, а не устройство одного
Tensor Core. Числа 90 и 54 относятся к примеру авторов на рисунке.*

На рисунке каждая матрица разбита на сетку из девяти строк и девяти
столбцов блоков. Для первых девяти результатов в верхнем варианте нужна
одна строка A и вся B: $9+81=90$ разных входных блоков. В нижнем варианте
первые девять результатов занимают квадрат $3\times3$ в C. Для них нужны
три строки A и три столбца B: $27+27=54$ входных блока. Это число разных
фрагментов для выбранной группы результатов, не общее число загрузок
за всё умножение.

При построчном порядке вычисляются подряд блоки одной строки C.
Потребность в одном фрагменте A повторяется, но используемые фрагменты B
могут успеть вытесниться до перехода к следующей строке. Группировка
нескольких строк повышает шанс повторно использовать и A, и B.
Это не отменяет независимости блоков и не гарантирует порядок их
завершения. Алгоритм остаётся корректным при любом разрешённом расписании;
порядок назначения блоков здесь влияет на локальность, а не на результат.

### Tensor Cores — другая инструкция для той же алгебры

Tensor Cores выполняют специализированное матричное умножение с накоплением.
Вместо длинной последовательности скалярных инструкций группа потоков
совместно подготавливает фрагменты и вызывает матричные инструкции.
Точные формы фрагментов, поддерживаемые типы и способы передачи операндов
зависят от поколения GPU.

Из этого не следует, что произвольная запись `A @ B`
автоматически достигает паспортного пика. Нужны подходящие форматы,
размещение данных и достаточно работы. Точность входов и точность
накопления также различаются: например, произведения низкой точности
могут накапливаться в FP32. Подробности численных ошибок относятся к
[[05 Численные форматы и mixed precision|главе о форматах чисел]].

Повторное использование повышает арифметическую интенсивность
$I=F/Q$: на каждый переданный байт приходится больше работы.
В модели roofline производительность ограничена
$\min(P_{\mathrm{peak}},BW\cdot I)$.
Но без указания уровня памяти $Q$ неоднозначно: трафик shared memory,
L2 и HBM — разные величины. Именно это различие понадобится
в [[03 Измерение производительности и roofline|следующей главе]].

## Объединение ядер: не записывать промежуточный массив

Рассмотрим поэлементный расчёт $y=\max(0,ax+b)$, где $a$ и $b$ —
скаляры. В прямой реализации три ядра создают промежуточные массивы:
сначала умножение, затем сложение, затем ReLU. Каждое читает N элементов
и записывает N элементов.

Объединённое ядро читает один элемент x, выполняет все три операции
в регистрах и записывает только y. Это **operator fusion**.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/systems-visuals-2026-09/nvidia-fusion.svg]]

*Отдельные ядра и объединённое ядро. NVIDIA,
[Introduction to Warp](https://github.com/NVIDIA/accelerated-computing-hub/blob/c16da250e9aa79936b28a1976738877fc772f8a2/tutorials/warp/notebooks/images/intro-to-warp/warp-kernel-fusion.svg),
[CC BY-NC-SA 4.0](https://github.com/NVIDIA/accelerated-computing-hub/blob/c16da250e9aa79936b28a1976738877fc772f8a2/README.md#license).
Оригинальная векторная схема, без изменений.*

На рисунке другой поэлементный пример: вычислить ускорение a,
обновить скорость v, затем координату x. Слева промежуточные значения
передаются между ядрами через глобальную память, справа остаются
в регистрах одного ядра. Чтение начального состояния и запись итогового
результата на схеме опущены: объединение не устраняет эти обращения.
Для нашей цепочки умножения, сложения и ReLU экономию можно посчитать явно.

| Реализация | Чтений элементов | Записей элементов | Всего байт FP32 |
|---|---:|---:|---:|
| Три отдельных ядра | $3N$ | $3N$ | $24N$ |
| Одно объединённое ядро | $N$ | $N$ | $8N$ |

При $N=2^{20}$ получается 24 MiB против 8 MiB логических обращений
к массивам. Дополнительно вместо трёх запусков нужен один.
Это не обязательно трёхкратное ускорение: часть прежних обращений могла
обслуживаться кэшем, а большой объединённый код — потребовать больше
регистров. Численная эквивалентность также требует проверки:
компилятор может объединить умножение и сложение в FMA и изменить округление.

Не любую цепочку выгодно объединять. У матричного слоя есть собственные
веса и сложный способ повторного использования, у нормировки —
редукция по нескольким элементам. Формулу «один вход и один выход»
из поэлементного примера нельзя переносить на произвольную цепь слоёв.
В [CS336 Lecture 6](https://github.com/stanford-cs336/lectures/blob/8b59b50730766695c2ffedd1a79c50cd09b9eb91/lecture_06.py)
идея объединения исследуется на GeLU; дальнейшие примеры есть в
[[08 GPU kernels и Triton — от программы к измерению|главе о Triton]].

## Передача данных и асинхронное выполнение

У дискретного GPU память обычно отделена от оперативной памяти CPU.
Входы нужно передать на устройство, а необходимые CPU результаты —
вернуть. Для этого могут использоваться PCIe и другие межсоединения.
NVLink поддерживает быстрый обмен в соответствующих конфигурациях,
но наличие имени интерфейса не задаёт скорость любого пути между
двумя устройствами: важны поколение, топология и поддержка обмена.

Стандартный способ организовать работу CUDA — **stream**, упорядоченная
очередь операций. Копирование входа и ядро в одном stream выполнятся
в нужном порядке. Другой stream может содержать независимую работу.
Отсутствие зависимости разрешает перекрытие, но не создаёт дополнительных
вычислителей и полосы памяти.

**Event** отмечает точку выполнения в stream. Другой stream может ждать
этого события, не останавливая весь GPU. Это позволяет выразить две
важные зависимости: ядро ждёт готовности входа, а следующая запись
в повторно используемый буфер ждёт завершения его прежнего читателя.

Сравним два расписания из CUDA-курса NVIDIA. Программа периодически
сохраняет состояние симуляции: копирует его в отдельный буфер на GPU,
передаёт этот буфер на CPU и записывает на диск. Расчёт следующих шагов
симуляции может продолжаться, пока CPU получает предыдущее состояние.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/systems-visuals-2026-09/nvidia-same-stream.png]]

*Передача результата и расчёт в одном stream. NVIDIA,
[CUDA C++: Streams](https://github.com/NVIDIA/accelerated-computing-hub/blob/c16da250e9aa79936b28a1976738877fc772f8a2/tutorials/cuda-cpp/notebooks/02.03-Streams/02.03.01-Streams.ipynb),
[CC BY-NC-SA 4.0](https://github.com/NVIDIA/accelerated-computing-hub/blob/c16da250e9aa79936b28a1976738877fc772f8a2/README.md#license).
Оригинальная схема, без изменений.*

На схеме CPU асинхронно ставит команды в очередь, но GPU выполняет передачу и расчёт
последовательно: они принадлежат одному stream. Асинхронность относительно
CPU сама по себе не даёт перекрытия на устройстве.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/systems-visuals-2026-09/nvidia-two-streams.png]]

*Передача и расчёт в разных streams. NVIDIA,
[Exercise: Async Copy and Streams](https://github.com/NVIDIA/accelerated-computing-hub/blob/c16da250e9aa79936b28a1976738877fc772f8a2/tutorials/cuda-cpp/notebooks/02.03-Streams/02.03.02-Exercise-Async-Copy.ipynb),
[CC BY-NC-SA 4.0](https://github.com/NVIDIA/accelerated-computing-hub/blob/c16da250e9aa79936b28a1976738877fc772f8a2/README.md#license).
Оригинальная схема возможного перекрытия; это не измеренная трасса.*

Второе расписание разрешает выполнять передачу параллельно с расчётом.
Отдельный буфер сохраняет данные предыдущего состояния, пока вычисления
меняют рабочие массивы. CPU ждёт завершения копирования перед чтением
своего буфера, а перед следующим циклом нужно дождаться готовности
нового состояния. На рисунках передача направлена **с GPU на CPU (D2H)**;
ниже рассмотрим обратное направление, H2D. Возможность реального
перекрытия в обоих случаях зависит ещё и от памяти и оборудования.

В [следующем уроке курса — Pinned Memory](https://github.com/NVIDIA/accelerated-computing-hub/blob/c16da250e9aa79936b28a1976738877fc772f8a2/tutorials/cuda-cpp/notebooks/02.04-Pinned-Memory/02.04.01-Pinned.ipynb)
авторы проверяют этот код профилировщиком: после добавления второго stream
передача и вычисления всё ещё идут последовательно. Буфер CPU выделен
в обычной, незакреплённой памяти. Показанное на рисунке перекрытие — цель,
для достижения которой курс затем меняет и способ выделения этого буфера.

Для обычного перекрытия H2D- или D2H-копирования с вычислением используют закреплённую
в оперативной памяти область — *pinned*, или *page-locked memory*,
асинхронное копирование, подходящие streams и устройство с нужными
copy engines. Закреплённую память нельзя выделять без ограничений:
она уменьшает ресурсы, которыми может свободно распоряжаться ОС.
Поведение default stream также зависит от выбранного режима;
старый legacy default stream может создавать неочевидные зависимости.
[CUDA: Asynchronous Execution](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/asynchronous-execution.html).

### Три пакета и два буфера

Пусть копирование одного пакета занимает 3 мс, вычисление — 7 мс.
CPU не задерживает подготовку; один copy engine может работать одновременно
с вычислением. Входной буфер нельзя перезаписывать до завершения его ядра.
Обратная передача результатов и остальные расходы в примере не учитываются.

Без перекрытия три пакета заняли бы $3(3+7)=30$ мс.
Выделим два входных буфера A и B и будем чередовать их:

| Пакет | Буфер | Копирование | Вычисление |
|---|---|---|---|
| 1 | A | 0–3 мс | 3–10 мс |
| 2 | B | 3–6 мс | 10–17 мс |
| 3 | A | 10–13 мс | 17–24 мс |

Третий пакет нельзя копировать в A в интервале 6–9 мс: первое ядро
ещё читает этот буфер до 10 мс. После его завершения запись разрешена
и перекрывается с вычислением второго пакета. Всё заканчивается
через 24 мс. Первый результат появляется через 10 мс, а последующие —
с интервалом 7 мс. Сократилось время всей последовательности,
а не длительность каждого ядра.

Для воспроизведения нужны зависимости готовности данных и освобождения
буфера. Два stream без таких зависимостей могут дать гонку, а один stream
со всеми операциями — правильное, но последовательное выполнение.
Наличие слова `Async` в названии функции не доказывает,
что нужные участки реально перекрылись: это проверяют по временной
диаграмме профилировщика.

Получение результата на CPU также может потребовать ожидания.
Например, чтение GPU-скаляра через `.item()` в PyTorch
должно дождаться его значения. Если делать это на каждом шаге ради печати
отладочной метрики, можно непреднамеренно убрать перекрытие.
Этот случай разобран в [рекомендациях PyTorch по производительности](https://docs.pytorch.org/tutorials/recipes/recipes/amp_recipe.html#troubleshooting).

## Почему модель GPU нельзя буквально переносить на TPU

GPU и TPU решают похожие задачи линейной алгебры, но описанные warps,
CUDA blocks и shared-memory banks относятся к NVIDIA CUDA.
TPU использует другой набор вычислителей и способов организации памяти.
Для него нужно отдельно разбирать матричные и векторные операции,
локальные буферы, компилятор и межчиповую сеть.

Общие вопросы сохраняются: где лежат операнды, сколько раз они используются,
какие участки выполняются параллельно и сколько данных передаётся.
Но число CUDA-потоков не является переносимой характеристикой программы.
Сравнение ускорителей на этих основаниях дано в
[Stanford CS336, Lecture 5](https://github.com/stanford-cs336/lectures/blob/8b59b50730766695c2ffedd1a79c50cd09b9eb91/lecture_05.pdf).

## Что проверять в работающем ядре

Сначала проверяют результат относительно эталона: значения, границы,
формы тензоров и выбранную численную точность. После этого разбирают,
почему правильный код работает с измеренной скоростью.

Если устройство загружено не полностью, нужно различить слишком маленькую
сетку, ограничения размещения блоков и ожидание данных. Если трафик велик,
нужно посмотреть, какие адреса читает warp, сколько данных используется
повторно и где появляются промежуточные записи. Если планировалось
перекрытие, нужны реальные интервалы копирования и вычисления.

Далее [[03 Измерение производительности и roofline|глава об измерениях]]
свяжет эти причины с метриками и аппаратными пределами.
[[08 GPU kernels и Triton — от программы к измерению|Глава о Triton]]
покажет полный путь от эталонной операции до собственного ядра.
Пример CUDA в начале этой страницы объясняет модель выполнения;
он не является полным исполняемым приложением или результатом GPU-бенчмарка.
