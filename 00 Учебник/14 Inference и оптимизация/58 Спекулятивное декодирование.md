# Спекулятивное декодирование

Пусть при жадном выборе языковая модель после данного префикса выдаёт A, B, D.
Обычное декодирование последовательно запускает её для A, затем для B,
затем для D. Если небольшая модель заранее предложит A, B, C, основная
сможет проверить всё предложение за один проход: принять A и B,
отклонить C и выдать D. Дорогой проход даст сразу три новых токена.

В этой процедуре небольшая модель строит черновик (*draft*), а основная,
или *target*, определяет окончательное продолжение. Для жадного выбора
достаточно сравнивать токены с максимумом вероятности основной модели.
Для случайной выборки потребуется другое правило: оно должно сохранять
всё распределение, включая маловероятные ответы.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/speculative-review-2026-10/leviathan-generation.png]]

*Yaniv Leviathan, Matan Kalman, Yossi Matias,
[Fast Inference from Transformers via Speculative Decoding, Figure 1](https://arxiv.org/abs/2211.17192v2),
[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/).
Каждая строка — один цикл. Зелёным показаны принятые предложения,
красным с зачёркиванием — отклонённые, синим — замены.
В первой строке четыре предложения приняты, затем вместо «bond» выбран
токен «n»: за один проход основной модели выдано пять токенов.
Это исходный рисунок из авторского архива, без изменения.*

## Откуда берётся возможность ускорения

При декодировании одного запроса большая плотная модель часто тратит
больше времени на чтение весов, чем на умножения. Для одного нового токена
через слои проходит одна строка активаций. Если обрабатывать несколько
известных токенов сразу, строки можно объединить в матричную операцию
и использовать прочитанные веса для нескольких позиций.

Неизвестное продолжение нельзя просто подать на вход. Его сначала
предлагает черновая модель. После этого задача основной модели становится
похожей на обработку известного текста: для префикса s и кандидатов
$d_1,d_2,d_3$ нужны распределения

$$
\begin{aligned}
q_1&=q(\cdot\mid s),\\
q_2&=q(\cdot\mid s,d_1),\\
q_3&=q(\cdot\mid s,d_1,d_2),\\
q_4&=q(\cdot\mid s,d_1,d_2,d_3).
\end{aligned}
$$

Причинная маска внимания не разрешает более ранней позиции видеть
более поздние. Поэтому один проход по известному продолжению даёт
те же условные распределения, которые потребовались бы при
последовательной проверке. Это обычная обработка известных входов,
а не одновременное угадывание независимых будущих токенов.

Черновик при этом строится последовательно. Если его длина K,
обычная схема требует K дешёвых шагов и одного дорогого прохода проверки.
За цикл выдаются принятый префикс и ещё один токен: замена при отказе
или дополнительный токен после полностью принятого черновика.
До остановки по EOS или лимиту длины это от одного до K+1 токенов.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/speculative-review-2026-10/leviathan-timeline.png]]

*Leviathan et al.,
[Figure 5: simplified trace diagram](https://arxiv.org/abs/2211.17192v2),
[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/).
Нижняя строка показывает обычное декодирование; в двух верхних перед
крупными фиолетовыми блоками проверки стоят короткие синие шаги черновика.
На рисунке $M_p$ — основная модель, $M_q$ — черновая; ниже в тексте,
как у Chen et al., используются обратные обозначения: draft p, target q.
Жёлтый и оранжевый блоки относятся к encoder-decoder модели из эксперимента.
У decoder-only LLM отдельных энкодеров нет.
Полный рендер авторского векторного PDF, без обрезки.*

В [Chen et al., Conditional Scoring](https://arxiv.org/abs/2302.01318v1)
отдельно разобраны линейные слои, чтение KV и обмен между устройствами.
При малом K линейные слои могут использовать прочитанные веса
для нескольких позиций, а небольшие коллективные операции — оставаться
ограниченными задержкой, а не объёмом пересылки.
По мере роста K увеличиваются вычисления,
активации и трафик. Стоимость проверки не обязана оставаться равной
одному обычному шагу. Подробности ограничений памяти и вычислений
введены в [[55a Физика LLM inference — prefill, decode и roofline|главе о prefill и decode]].

## Почему нельзя просто принять совпавший argmax

### Жадное декодирование

Для greedy decoding продолжают принимать кандидатов, пока каждый
совпадает с argmax основной модели при уже принятом префиксе.
При первом несовпадении выдают argmax основной модели и заканчивают цикл.
Распределения для оставшихся позиций были вычислены при неверном
префиксе и больше не используются.

| Позиция | Префикс проверки | Кандидат | Argmax основной модели | Действие |
|---|---|---|---|---|
| 1 | s | A | A | Принять A |
| 2 | s, A | B | B | Принять B |
| 3 | s, A, B | C | D | Выдать D и закончить цикл |

Результат A, B, D совпадает с тремя обычными жадными шагами.
Следовать за C дальше нельзя, даже если следующий кандидат
совпадёт с argmax, вычисленным для s, A, B, C.

<!-- checked-example: speculative-greedy -->
```python
import numpy as np

def greedy_verify(candidates, target_rows):
    output = []
    for i, candidate in enumerate(candidates):
        chosen = int(np.argmax(target_rows[i]))
        output.append(chosen)
        if chosen != candidate:
            return output
    output.append(int(np.argmax(target_rows[-1])))
    return output

# A=0, B=1, C=2, D=3. Последняя строка нужна только при полном принятии.
rows = np.array([[.7, .1, .1, .1],
                 [.1, .7, .1, .1],
                 [.1, .1, .1, .7],
                 [.1, .1, .7, .1]])
assert greedy_verify([0, 1, 2], rows) == [0, 1, 3]
```

При фиксированных логитах и одинаковом разрешении равных максимумов
это рассуждение даёт точное совпадение greedy-последовательностей.
На реальном ускорителе проверка нескольких позиций может использовать
другие ядра и порядок округления, чем одиночный шаг. Равенство
математического алгоритма не гарантирует побитового совпадения логитов.

### Случайная выборка

При sampling модель должна иногда выдавать не самый вероятный токен.
Если принимать лишь совпавший argmax, такие исходы потеряются.
Рассмотрим распределения на словаре A, B, C:

| Токен | Черновая модель p | Основная модель q |
|---|---:|---:|
| A | 0.6 | 0.2 |
| B | 0.3 | 0.5 |
| C | 0.1 | 0.3 |

Черновая модель предлагает A втрое чаще, чем нужно основной.
Поэтому из предложений A принимают только треть. Предложения B и C
можно принимать всегда: их черновая модель предлагает реже нужного.

Для кандидата $x\sim p$ это записывается так:

$$
a(x)=\min\left(1,\frac{q(x)}{p(x)}\right).
$$

В примере вероятности принятия A, B, C равны $1/3,1,1$.
Безусловные вероятности «кандидат предложен и принят» составляют

$$
\min(p,q)=(0.2,0.3,0.1).
$$

Сумма равна 0.6. С вероятностью 0.4 предложение отклоняется;
для таких случаев недостающие вероятности основной модели равны $(0,0.2,0.2)$.
После нормировки получится $(0,0.5,0.5)$.
Именно из него выбирают замену после отказа.

В общем случае остаточное, или корректирующее, распределение равно

$$
r(x)=
\frac{\max(0,q(x)-p(x))}
{\sum_y\max(0,q(y)-p(y))}.
$$

Подставим числа:

<!-- checked-example: speculative-mass -->
```python
proposal = np.array([.6, .3, .1])
target = np.array([.2, .5, .3])
acceptance = np.minimum(1, target / proposal)
accepted_mass = proposal * acceptance
reject_probability = 1 - accepted_mass.sum()
residual = np.maximum(target - proposal, 0)
residual /= residual.sum()

np.testing.assert_allclose(acceptance, [1/3, 1, 1])
np.testing.assert_allclose(accepted_mass, [.2, .3, .1])
np.testing.assert_allclose(residual, [0, .5, .5])
np.testing.assert_allclose(accepted_mass + reject_probability * residual, target)

# Если после отказа заново выбирать из target, получится другое распределение.
wrong = accepted_mass + reject_probability * target
np.testing.assert_allclose(wrong, [.28, .5, .22])
```

Повторная выборка непосредственно из q после отказа даст A вероятность
0.28 вместо 0.2. Принятая часть уже использовала часть вероятностей q;
коррекция должна восполнять лишь недостающую часть.

Доказательство для произвольного словаря повторяет этот расчёт.
Принятая масса токена x равна $\min(p(x),q(x))$.
Вероятность отказа равна сумме положительных разностей q−p.
Поэтому после отказа безусловная масса токена равна
$\max(0,q(x)-p(x))$, и в сумме

$$
\begin{aligned}
&\min(p(x),q(x))\\
&\quad+\max(0,q(x)-p(x))=q(x).
\end{aligned}
$$

Этот вывод приведён в
[Leviathan et al., Appendix A.1](https://arxiv.org/abs/2211.17192v2)
и [Chen et al., Theorem 1](https://arxiv.org/abs/2302.01318v1).
Если p=q, отказы невозможны и нормировать нулевой остаток не требуется.
Если $p(x)=0$, черновая модель не предложит x, но основная всё равно
может выдать его через корректирующее распределение.

### Какие вероятности подставлять

В p нужно подставлять фактическое распределение, из которого строился
черновик, а в q — распределение требуемого декодирования основной модели.
Температуру, top-k, top-p, ограничения на токены и другие преобразования
учитывают до расчёта отношения и остатка. Сырые вероятности softmax
не подходят, если выборка шла из обрезанного и заново нормированного словаря.
Настройки черновой модели могут отличаться от настроек основной.

У Leviathan et al. эта договорённость выделена в §2.2. Оригинальный абзац
сохранён на английском, [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/).
В нём p и q обозначают соответственно target и draft, наоборот относительно
нашей записи.

«Сохранить распределение» означает получить тот же закон распределения
последовательностей при той же политике основной модели и остановки.
Одинаковый seed не обязан давать одинаковую строку: обычный и спекулятивный
алгоритмы расходуют случайные числа по-разному.

## Один цикл: принять B, отклонить A, выдать замену

Пусть черновик состоит из трёх токенов B, A, C.
Для каждой позиции сохраняют распределение черновой модели и выбранный
из него токен. Основная модель получила четыре распределения для тех же
префиксов:

| Префикс | p для A, B, C | q для A, B, C | Кандидат |
|---|---|---|---|
| s | 0.6, 0.3, 0.1 | 0.2, 0.5, 0.3 | B |
| s, B | 0.5, 0.2, 0.3 | 0.1, 0.6, 0.3 | A |
| s, B, A | 0.2, 0.3, 0.5 | 0.2, 0.3, 0.5 | C |
| s, B, A, C | — | 0.1, 0.2, 0.7 | — |

B принимается всегда: отношение 0.5/0.3 больше единицы.
Для A отношение равно 0.1/0.5=0.2.
Если проверочное случайное число равно 0.7, A отклоняется.
Остаток при префиксе s, B равен $(0,0.4,0)$, после нормировки $(0,1,0)$.
Значит, заменой станет B. Цикл выдаст B, B.

Распределения для s, B, A и s, B, A, C не используются:
действительное продолжение теперь начинается с s, B, B.
Чтобы продолжить после него, нужна новая проверка.

Ниже функция проверяет уже подготовленные распределения. Она не запускает
нейросети и не является GPU-реализацией.

<!-- checked-example: speculative-cycle -->
```python
def categorical_from_uniform(probability, u):
    assert 0 <= u < 1
    return int(np.searchsorted(np.cumsum(probability), u, side="right"))

def verify_chain(candidates, proposals, targets, uniforms, replacement_uniform):
    accepted = []
    for i, token in enumerate(candidates):
        p, q = proposals[i], targets[i]
        assert p[token] > 0
        if uniforms[i] < min(1.0, q[token] / p[token]):
            accepted.append(token)
            continue
        residual = np.maximum(q - p, 0)
        residual /= residual.sum()  # Эта ветвь достижима только при ненулевом остатке.
        correction = categorical_from_uniform(residual, replacement_uniform)
        return accepted + [correction], len(accepted), "reject"
    bonus = categorical_from_uniform(targets[-1], replacement_uniform)
    return accepted + [bonus], len(accepted), "all-accepted"

p_rows = np.array([[.6, .3, .1], [.5, .2, .3], [.2, .3, .5]])
q_rows = np.array([[.2, .5, .3], [.1, .6, .3],
                   [.2, .3, .5], [.1, .2, .7]])
# A=0, B=1, C=2
assert verify_chain([1, 0, 2], p_rows, q_rows, [.8, .7, .4], .4) == (
    [1, 1], 1, "reject"
)
assert verify_chain([1, 0, 2], p_rows, q_rows, [.8, .1, .4], .4) == (
    [1, 0, 2, 2], 3, "all-accepted"
)
```

Во втором запуске проверочное число для A равно 0.1, и A принимается.
Затем принимается C; последняя строка q даёт дополнительный токен C.
Результат B, A, C, C содержит K+1=4 токена.

При встрече принятого EOS или достижения предельной длины выдачу
останавливают. Поздние токены этого цикла не добавляют в ответ.
Поэтому утверждение о K+1 описывает цикл без такого досрочного завершения.

## Полный алгоритм на исходном слайде

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/topics-53-59-source-first/speculative-sampling-algorithm.png]]

*Charlie Chen et al.,
[Algorithm 2, Speculative Sampling](https://arxiv.org/abs/2302.01318v1),
[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/),
также в [Stanford CS336 Lecture 10](https://github.com/stanford-cs336/lectures/blob/8b59b50730766695c2ffedd1a79c50cd09b9eb91/lecture_10.py#L507-L535).
Верхний цикл строит черновик; далее основная модель получает K+1
распределений; нижний цикл принимает префикс до первого отказа.
Код выше отдельно показывает ветвь коррекции и ветвь дополнительного токена.*

Параллельно вычисляются логиты основной модели, но проверка префикса
имеет последовательную логику. Результат следующей позиции разрешено
использовать лишь после принятия всех предыдущих кандидатов.
Иначе изменится условие, при котором распределение было вычислено.

Классический алгоритм использует полные распределения p и q.
У специальных алгоритмов и ядер возможны иные способы организовать
вычисления и хранение, но для остаточной коррекции недостаточно знать
только вероятность выбранного токена.

## KV-cache двух моделей

Проверка оставляет в KV-cache состояния ещё не подтверждённых токенов.
При отказе эти состояния нужно исключить из дальнейшего внимания.
Физическое освобождение страниц может происходить позже;
для корректности существенны видимая длина и соответствие содержимого
подтверждённому префиксу.

Выбранный токен не обязательно уже обработан
моделью. Его логиты были получены на предыдущем входе, а собственный KV
появится только после следующего прямого прохода.
[[55 KV-cache, пакетирование и PagedAttention|Различие между выбором токена и записью KV]]
нужно учитывать и при обычном, и при спекулятивном декодировании.

Рассмотрим конкретную организацию основной модели. Подтверждены пять
токенов u, v, x, y, z. Кеш содержит первые четыре, а z ожидает обработки.
Для черновика B, A, C в один проход подаётся z, B, A, C.
Его четыре выходные строки дают распределения из предыдущего примера.

| Момент | Подтверждённый текст | KV основной модели |
|---|---|---|
| До проверки | u v x y z | u v x y |
| После прохода, до решения | u v x y z | u v x y z B A C — хвост временный |
| B принят, A отклонён, замена B | u v x y z B B | u v x y z B |
| Перед следующей проверкой | Последний B ожидает обработки | Нельзя видеть отвергнутые A, C |

Последний B в тексте и последний B в кеше — разные позиции:
в кеше находится первый принятый B; корректирующий B ещё не обработан.

<!-- checked-example: speculative-kv -->
```python
confirmed = list("uvxyz")
cached_before = confirmed[:-1]
pending = confirmed[-1]
draft = list("BAC")
temporary_cache = cached_before + [pending] + draft
accepted_count = 1
committed_cache = temporary_cache[:len(confirmed) + accepted_count]
new_confirmed = confirmed + draft[:accepted_count] + ["B"]

assert temporary_cache == list("uvxyzBAC")
assert committed_cache == list("uvxyzB")
assert new_confirmed == list("uvxyzBB")
assert committed_cache == new_confirmed[:-1]
```

Черновая модель поддерживает своё состояние. Его тоже согласуют с принятым
путём; оно не обязано в каждый момент иметь ту же длину, что и кеш основной
модели. Например, при последовательном построении черновика KV последнего
предложенного токена может ещё отсутствовать. При полном принятии нужно
учесть и этот токен, и дополнительный токен основной модели.
Реализация может дообработать их вместе, хранить ожидающий хвост или
организовать синхронизацию иначе.

Для деревьев вместо простого обрезания непрерывного хвоста может понадобиться
сборка KV единственного принятого пути из разрозненных позиций.
Узлы других ветвей не должны остаться видимыми.

## Вероятность принятия и число токенов за цикл

Для одного префикса вероятность принять предложение равна

$$
\begin{aligned}
\beta&=\sum_x\min(p(x),q(x))\\
&=1-\frac12\sum_x|p(x)-q(x)|.
\end{aligned}
$$

Вторая часть выражает её через расстояние полной вариации между
распределениями. В трёхтокенном примере $\beta=0.6$.
Одинаковый argmax не определяет эту величину: распределения могут
совпадать на самом вероятном токене и существенно расходиться на остальных.

Пусть A — число подряд принятых кандидатов из K.
Чтобы принять не менее i, нужно пройти все первые i проверок.
Для любого такого A верно

$$
\mathbb E[A]=\sum_{i=1}^{K}\Pr(A\ge i).
$$

При упрощении, в котором условная вероятность принятия на каждом шаге
равна одной и той же $\alpha$, получаем

$$
\begin{aligned}
\mathbb E[N]
&=1+\mathbb E[A]\\
&=\sum_{i=0}^{K}\alpha^i\\
&=\frac{1-\alpha^{K+1}}{1-\alpha}.
\end{aligned}
$$

Здесь N включает корректирующий или дополнительный токен.
При $\alpha=1$ предельное значение равно K+1.
В реальной последовательности условные вероятности зависят от префикса;
произведение наблюдённых средних по позициям не обязано давать
точную вероятность пройти весь путь.

Разделы §3.1–3.3
[Leviathan et al.](https://arxiv.org/abs/2211.17192v2) связывают
это число со временем. Если обычный шаг занимает $T_0$,
каждый шаг черновика — $T_d$, а проверка K кандидатов — $T_v(K)$, то

$$
S(K)\approx
\frac{T_0\,\mathbb E[N]}
{K T_d+T_v(K)}.
$$

Это оценка длительного стационарного режима без дополнительных накладных
расходов, а не формула для TTFT или гарантированное ускорение.

## Почему больше draft-токенов не всегда лучше

Возьмём учебные, не измеренные на LLM значения:
$T_0=10$ ms, $T_d=1$ ms, $T_v(K)=10+0.5K$ ms и $\alpha=0.8$.

| K | Ожидается токенов за цикл | Время цикла, ms | Ускорение |
|---|---:|---:|---:|
| 1 | 1.8000 | 11.5 | 1.57× |
| 2 | 2.4400 | 13.0 | 1.88× |
| 4 | 3.3616 | 16.0 | 2.10× |

## Чем может быть draft

Отдельная небольшая языковая модель удобна тем, что уже выдаёт
распределение по словарю. Можно использовать существующий checkpoint
или обучить черновую модель имитировать основную.
Чем ближе распределения на нужных запросах, тем меньше отказов;
но увеличение черновой модели повышает стоимость каждого предложения.

Другие подходы используют промежуточные слои основной модели
(*self-speculation*, ранний выход), дополнительные предсказывающие головы
или повторяющиеся фрагменты текста. Для prompt lookup находят
совпадение текущего суффикса с более ранним фрагментом входа
и предлагают его продолжение.

Например, если в документе уже встречалось «срок оплаты составляет
30 дней», после повторного «срок оплаты составляет» можно предложить
«30 дней», не вызывая отдельную черновую нейросеть.
Основная модель всё равно должна проверить это продолжение.
Детерминированное предложение можно формально представить точечной
вероятностью; случайную выборку тогда согласуют с этим фактическим
механизмом предложения, а не с вымышленными логитами.

Medusa и EAGLE могут предлагать дерево вместо одной цепочки.
У дерева появляются альтернативные продолжения одного префикса,
но также растут число проверяемых позиций, объём временного KV
и затраты на организацию маски. Сохранение распределения зависит
от проверяющего алгоритма; само наличие дерева его не обеспечивает.

Для разных токенизаторов появляется ещё одна задача:
граница одного draft-токена может проходить внутри target-токена.
Текст нужно перекодировать и согласовать префиксы.
[Universal Assisted Generation](https://huggingface.co/blog/universal_assisted_generation)
описывает такую синхронизацию; это отдельное расширение,
а не непосредственная подстановка двух разных словарей в формулу q/p.

## EAGLE: draft на уровне признаков

### EAGLE-1: почему нужен уже выбранный следующий токен

Пусть основная модель обработала «How can» и выбрала «I».
Её состояние после «can» задаёт распределение следующего токена,
но ещё не является состоянием после «I».
Чтобы предсказать это следующее состояние, нужно знать, какой токен
был выбран: «I» или другое допустимое продолжение.

[EAGLE, §3.1](https://arxiv.org/html/2401.15077v3#S3.SS1)
подаёт небольшой черновой модели последовательность признаков
$f_1,\ldots,f_t$ из основного трансформера и сдвинутую последовательность
эмбеддингов токенов $e_2,\ldots,e_{t+1}$.
При ширине d их объединение имеет форму $[B,L,2d]$.
Линейная проекция уменьшает ширину до d, один decoder-блок
предсказывает следующее представление $\hat f_{t+1}$.
Замороженная LM head основной модели превращает его в распределение
токена $t+2$.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/speculative-review-2026-10/eagle-shifted-input.png]]

*Li et al.,
[EAGLE, Figure 6, ICML 2024, PMLR 235](https://proceedings.mlr.press/v235/li24bt.html),
[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/).
Внизу первый токен $t_1$ отбрасывается. Эмбеддинги $e_2,e_3$
объединяются с признаками $f_1,f_2$, а не с $f_2,f_3$:
это сдвиг на одну позицию. После проекции и decoder-блока
предсказанный $f_3$ проходит через LM head и задаёт следующий токен $t_4$.
Из опубликованного PDF извлечён целый рисунок, без перерисовки.*

После выборки этого токена его эмбеддинг и предсказанный признак
становятся входом следующего дешёвого шага.
Основная модель пока не вызывается; неточные признаки могут
накапливаться в черновой цепочке.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/speculative-review-2026-10/eagle-feature-tree.png]]

*Yuhui Li, Fangyun Wei, Chao Zhang, Hongyang Zhang,
[EAGLE: исходная схема из официального репозитория](https://github.com/SafeAILab/EAGLE/blob/cb7e0841fe0c206c6ed74a197ad5e2a1f13f5a2b/figs/fig1.png),
[Apache-2.0](https://github.com/SafeAILab/EAGLE/blob/cb7e0841fe0c206c6ed74a197ad5e2a1f13f5a2b/LICENSE).
Слева основная модель обрабатывает «How can»; посередине
авторегрессионная голова использует признаки и сдвинутые эмбеддинги;
справа показаны альтернативные ветви после трёх дешёвых проходов.
Рисунок скопирован без изменения. Это схема EAGLE-1, не EAGLE-3.*

Обучение в [§3.2](https://arxiv.org/html/2401.15077v3#S3.SS2)
содержит две составляющие. Smooth L1 сближает предсказанный признак
с признаком основной модели. Cross-entropy сближает распределения,
полученные через одну и ту же замороженную LM head из настоящего
и предсказанного признаков. Это мягкая цель учителя,
а не просто правильный ID токена из текста.

В исходном эксперименте коэффициент классификационной части равен 0.1.
Обучаются линейная проекция и авторегрессионный блок, а эмбеддинги
и LM head берутся из основной модели. К входным признакам добавляют
небольшой шум, чтобы черновая модель сталкивалась с неточностью
не только во время генерации.

### EAGLE-2: расширение и повторный отбор дерева

[EAGLE-2, §4](https://aclanthology.org/2024.emnlp-main.422/)
оставляет черновую модель и её обучение, но меняет организацию дерева.
На каждом уровне расширяют только выбранные узлы,
затем перед проверкой заново отбирают лучшие узлы из всего дерева.

Вероятность черновой модели служит приближённой оценкой вероятности
принятия. Это эмпирическое наблюдение статьи, не тождество.
Оценка узла учитывает весь путь:

$$
V(v)\approx\prod_{u\in\operatorname{path}(v)}c(u),
$$

где c — условная вероятность предложенного токена у черновой модели.
Даже уверенное продолжение маловероятного родителя может иметь низкую
оценку всего пути.

Пусть от корня идут A с вероятностью 0.6 и B с вероятностью 0.4.
У A есть дети C, D, E с вероятностями 0.5, 0.3, 0.2;
у B — F и G с вероятностями 0.9 и 0.1.
Оценки путей равны:

| Узел | Оценка V |
|---|---:|
| A | 0.60 |
| B | 0.40 |
| C | 0.60 × 0.50 = 0.30 |
| D | 0.60 × 0.30 = 0.18 |
| E | 0.60 × 0.20 = 0.12 |
| F | 0.40 × 0.90 = 0.36 |
| G | 0.40 × 0.10 = 0.04 |

На втором уровне при бюджете двух расширений выбираются F и C.
Для финальной проверки при бюджете четырёх предложенных узлов
выбираются A, B, F, C. Корень учитывается отдельно.
Все выбранные узлы сохраняют родителей.

<!-- checked-example: speculative-rerank -->
```python
value = {"A": .6, "B": .4, "C": .6*.5, "D": .6*.3,
```

Оценка ребёнка не больше оценки родителя, поскольку каждый множитель
лежит в [0,1]. При равенстве сначала берут менее глубокий узел.
Это позволяет сохранить связность при отборе наибольших V.

В опубликованной статье этот аргумент сформулирован так;
[EMNLP 2024, §4.2](https://aclanthology.org/2024.emnlp-main.422/),
[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/):

### Proposal, verification и rollback дерева

Упаковка дерева в один массив не превращает его в обычную
последовательность. В примере с корнем R, его детьми A, B,
детьми A — C, D и ребёнком B — E узел D может видеть R и A,
но не B, C или E.

Квадратная маска показывает видимость самих узлов.
Уже обработанный подтверждённый префикс доступен им отдельно.

| Запрос \ ключ | R | A | B | C | D | E |
|---|---:|---:|---:|---:|---:|---:|
| R | 1 | 0 | 0 | 0 | 0 | 0 |
| A | 1 | 1 | 0 | 0 | 0 | 0 |
| B | 1 | 0 | 1 | 0 | 0 | 0 |
| C | 1 | 1 | 0 | 1 | 0 | 0 |
| D | 1 | 1 | 0 | 0 | 1 | 0 |
| E | 1 | 0 | 1 | 0 | 0 | 1 |

Если R занимает позицию n, позиционные индексы равны
$n,n+1,n+1,n+2,n+2,n+2$.
Место в упакованном массиве не заменяет глубину.
Обычная нижнетреугольная маска позволила бы B прочитать A
и изменила бы проверяемый префикс.

<!-- checked-example: speculative-tree -->
```python
parents = [-1, 0, 0, 1, 1, 2]
depth = np.zeros(len(parents), dtype=int)
tree_mask = np.zeros((len(parents), len(parents)), dtype=bool)
for node, par in enumerate(parents):
    if par >= 0:
        depth[node] = depth[par] + 1
    ancestor = node
    while ancestor >= 0:
        tree_mask[node, ancestor] = True
        ancestor = parents[ancestor]

np.testing.assert_array_equal(depth, [0, 1, 1, 2, 2, 2])
np.testing.assert_array_equal(tree_mask[4], [1, 1, 0, 0, 1, 0])
np.testing.assert_array_equal(tree_mask[5], [1, 0, 1, 0, 0, 1])
assert np.tril(np.ones((6, 6), dtype=bool))[2, 1] and not tree_mask[2, 1]

# Greedy-проверка: из корня выбран B, затем E, затем отсутствующий ребёнок F.
children = {"R": {"A", "B"}, "A": {"C", "D"}, "B": {"E"}, "E": set()}
target_next = {"R": "B", "B": "E", "E": "F"}
node, emitted = "R", []
while True:
    chosen = target_next[node]
    emitted.append(chosen)
    if chosen not in children[node]:
        break
    node = chosen
assert emitted == ["B", "E", "F"]
```

Для greedy-проверки выбирают следующий argmax основной модели.
Если такой ребёнок есть, принимают его и продолжают из него.
Если нет, выдают этот токен и заканчивают цикл.
Сохраняют KV только пройденного пути; последний выданный токен
может ещё ожидать обработки. Ветви A, C, D в примере не используются.

Для sampling нужно проверять вероятности предложений, а не искать
самый длинный путь совпадений.
[EAGLE, Appendix A.2](https://arxiv.org/html/2401.15077v3#A1.SS2)
описывает несколько раундов проверки детей одного узла.
После отказа от первого кандидата вместо немедленной выборки замены
можно проверить второго, но уже относительно обновлённого остатка.

Например, при $q=(0.2,0.5,0.3)$, $p_1=(0.6,0.3,0.1)$
отказ от первого предложения оставляет $r_1=(0,0.5,0.5)$.
Если следующее предложение действительно выбрано из
$p_2=(0,0.75,0.25)$ и оказалось B, его принимают с вероятностью
$0.5/0.75=2/3$. После второго отказа остаток целиком приходится на C.

Второе отношение использует $r_1/p_2$, а не исходное $q/p_1$.
Распределение $p_2$ должно описывать реальный способ получить второго
кандидата, включая выбор без повторения, если он используется.
Детерминированный top-k нельзя объявить случайной выборкой из исходного p.
Без этих условий формула одной цепочки не даёт доказательства
корректности для произвольно построенного дерева.

### EAGLE-3: объединение слоёв и обучение на собственных состояниях

В [EAGLE-3, §3](https://arxiv.org/html/2503.01840v3#S3)
черновая модель больше не обязана восстанавливать конкретный признак
верхнего слоя. Её обучают предсказанию токенов, убрав отдельную
ошибку регрессии признаков.

Вместо одного слоя используются представления из нижней, средней
и верхней частей основной модели. При ширине d три вектора
объединяют в 3d, затем линейно приводят к d.
Полученный вектор g объединяют с эмбеддингом выбранного следующего
токена. Проекция и небольшой decoder-блок дают внутреннее
представление a, из которого LM head получает распределение.

В примере статьи основная модель обработала «How can» и выбрала «I».
Первый дешёвый шаг использует $g_{\mathrm{how}},g_{\mathrm{can}}$
и сдвинутые эмбеддинги, выдавая представление $a_{\mathrm I}$
и следующий токен «do».
Для второго шага настоящего $g_{\mathrm I}$ ещё нет:
основная модель не обрабатывала «I».
На его место черновая подаёт собственное $a_{\mathrm I}$.
Далее собственный $a_{\mathrm{do}}$ заменяет недоступное
$g_{\mathrm{do}}$. Так продолжается черновой проход.

| Версия | Входные признаки | Обучающая цель | Дерево |
|---|---|---|---|
| EAGLE-1 | Признаки одного верхнего уровня и сдвинутые эмбеддинги | Регрессия признаков + мягкая cross-entropy | Фиксированная структура |
| EAGLE-2 | То же | То же | Расширение и повторный отбор по текущему контексту |
| EAGLE-3 | Объединённые признаки нескольких уровней, затем собственные состояния | Предсказание токенов без отдельной регрессии признаков | Используется динамическое дерево EAGLE-2 |

*Training-time test* означает, что собственные a возвращают на вход
ещё при обучении. Если обучать только на настоящих g основной модели,
следующие шаги генерации получат другой тип входных состояний.
Развёрнутые обучающие шаги знакомят модель с этим режимом заранее.

У таких шагов своя маска внимания. Для обучающего текста «How can I»
предсказания «are», «we», «do» продолжают три разных префикса:
«How», «How can», «How can I».
Они не образуют общую последовательность «are we do».
На следующем шаге «are» видит ветвь «How → are»,
«we» — «How can → we», «do» — «How can I → do».
Поэтому блок внимания между новыми ветвями диагональный,
а видимость исходного текста определяется соответствующим префиксом.
Метки для позиций берут из обучающих данных.

Оригинальные
[Figure 5, схема инференса, и Figure 6, обучающие маски](https://proceedings.neurips.cc/paper_files/paper/2025/file/c7b5a35ea98b62512a869c19ea7b03cb-Paper-Conference.pdf#page=5)

Обозначения f, g и a в этих версиях не взаимозаменяемы:
у EAGLE-1 предсказанный вектор привязан к признаку учителя,
у EAGLE-3 такой регрессионной обязанности нет.

### Пример расчёта выигрыша дерева

Пусть обычный шаг основной модели занимает 10 ms,
построение дерева из 12 узлов — 2.5 ms,
а проверка — 13 ms. Если цикл в среднем выдаёт 4.2 токена,
включая дополнительный, то

$$
\mathrm{TPOT}\approx\frac{2.5+13}{4.2}
=3.69\text{ ms/token}.
$$

Получается примерно 2.71× относительно 10 ms/token.
Если на другом домене продвижение упало до 1.4 токена,
при тех же затратах будет 11.07 ms/token: медленнее исходного.
Числа учебные, а не результаты запуска EAGLE.

С ростом пакета обычная модель может лучше использовать прочитанные
веса и без черновика. Поэтому опубликованные коэффициенты ускорения
для одного запроса и throughput при большом пакете описывают разные
условия. Например, EAGLE-3 отдельно сообщает 1.38× по throughput
при batch=64 в SGLang v0.4.4, на одном H100, LLaMA 3.1 8B и MT-bench.
В этой части эксперимента использовалась цепочка длины 3, без дерева.
Это измерение авторов, не универсальный коэффициент метода.

## Когда ускорения не будет

Если обычное декодирование уже хорошо использует вычислительные блоки,
дополнительные позиции проверки занимают ресурсы, которых раньше
не хватало. Большой continuous batch способен уменьшить преимущество
спекуляции, хотя конкретный результат зависит от ядер и планировщика.

Дорогой черновик, низкое принятие на нужном домене и длинное дерево
увеличивают время до следующей выдачи токенов.
Длинный контекст добавляет чтения KV и работу внимания.
При распределённой проверке меняются размеры коллективных операций;
ускорение одиночного линейного слоя не определяет весь цикл.

Дополнительные веса и временные KV уменьшают память для других запросов.
Даже ускорив один запрос, система может обслуживать меньше запросов
в пределах заданного SLO.
Короткие ответы, EOS и лимит длины дополнительно сокращают число
использованных предложений.

## Как измерять

Сначала фиксируют целевое декодирование: модель и точность вычислений,
температуру, top-p/top-k, ограничения на токены и правила остановки.
Версия черновика, длина цепочки или бюджет дерева, режимы ядер
и параметры планировщика также входят в описание эксперимента.

Время разделяют на построение черновика, проверку, выбор токенов,
согласование KV и прочие расходы.
Для продвижения нужно явно указать, включён ли дополнительный токен:
число принятых предложений A и число выданных токенов N=A+1
различаются. Среднее по всем предложенным узлам и вероятность пройти
следующую проверку — тоже разные метрики.

Затем измеряют TTFT, TPOT и межтокенные задержки, память,
пропускную способность и goodput на одинаковых запросах и нагрузке.
Выдача нескольких токенов одним циклом может быть неравномерной;
средний TPOT не описывает все паузы, видимые пользователю.

Маленькие дискретные примеры позволяют точно перебрать вероятности
и проверить остаточную коррекцию. Статистическая проверка на реальных
генерациях полезна для поиска ошибки реализации, но близкие метрики
на XSum или HumanEval сами по себе не доказывают равенство распределений.
Для greedy сначала проверяют совпадение выбранных токенов при
фиксированных логитах, затем отдельно исследуют численные различия
реального исполнения.
