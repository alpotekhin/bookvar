> В понедельник мастерская получила 12 заявок на ремонт. К среде
> специалисты закрыли 8 из них. В четверг две из четырёх оставшихся
> заявок передали подрядчику. График работы мастерской не изменился.

В еженедельной сводке эти четыре предложения можно заменить одним:
«К среде закрыли 8 из 12 заявок, полученных в понедельник; в четверг
подрядчику передали две из четырёх оставшихся». Число 12 относится
к поступившим заявкам, число 8 — к закрытым. Если сохранить оба числа,
но перепутать, к каким действиям они относятся, резюме будет неверным.

<a id="sum-task"></a>

## Что должно остаться в резюме

Для сводки по заявкам достаточно трёх фактов: сколько поступило,
сколько закрыли и сколько передали подрядчику. Для объявления
посетителям полезнее знать, что график работы не изменился.
Требования к выходу определяют и состав обучающих данных. В
[XSum](https://aclanthology.org/D18-1206/) целевой текст — одно
предложение, передающее тему новости. В CNN/DailyMail цель состоит
из редакционных выжимок из нескольких пунктов. Модель, выучившая
один из этих форматов, не получает автоматически представления
о том, что нужно указывать в отчёте ремонтной мастерской.

При извлекающей суммаризации ответ ограничен фрагментами документа:
например, двумя из его предложений. Генеративная модель может
соединить сведения из разных частей текста в одном предложении.
В задаче перевода, разобранной в
[[02 Areas/ML & DL/00 Учебник/06 Encoder, Decoder и Encoder-Decoder/08 Машинный перевод|предыдущей главе]], содержание по возможности
сохраняется целиком. Здесь часть сведений нужно опустить, и эталонное
резюме показывает, какие именно сведения отобрал автор.

<a id="sum-extractive"></a>

## Как BERTSum отбирает предложения

Простой ориентир для нашего отчёта — взять два первых предложения.
В них есть поступление и закрытие заявок, но нет передачи подрядчику.
Чтобы выбирать по содержанию, можно закодировать весь отчёт и получить
по одному вектору на предложение.

В правой части рисунка перед каждым предложением стоит собственный
[CLS]. На выходе Transformer соответствующие векторы показаны
синим в нижней строке. Цвета $E_A$ и $E_B$ обозначают чередующиеся
эмбеддинги сегментов: первое и третье предложения используют $E_A$,
второе — $E_B$. Контекст у [CLS] не ограничен своим предложением:
двунаправленный энкодер обрабатывает документ целиком.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/summarization-2026-11-22/liu-bertsum-fig1.png|Слева в оригинальном BERT один CLS. Справа в BERTSum по CLS перед каждым предложением, сегменты A, B, A и три контекстных CLS на выходе.]]

*Yang Liu и Mirella Lapata, [Text Summarization with Pretrained Encoders, рис. 1](https://aclanthology.org/D19-1387.pdf#page=3), [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/). Схема из PDF; подпись статьи заменена пояснением выше.*

В BERTSumExt над этими векторами работают дополнительные слои
Transformer. Они уточняют представление предложения с учётом других
предложений. Из каждого уточнённого вектора линейный слой с
сигмоидой получает оценку включения. Оценки не обязаны суммироваться
до единицы: в резюме могут попасть несколько предложений.

Для обучения требуются метки «включить» и «не включать». Поскольку
редакторское резюме может быть написано другими словами, Liu и
Lapata строят приближённую разметку жадным отбором исходных предложений
по приросту ROUGE с эталоном. Затем обучают модель бинарной
кросс-энтропией. При построении резюме авторы ранжируют предложения
по оценкам и пропускают кандидата, если хотя бы одна его триграмма
уже встречается в отобранном тексте. Это правило уменьшает буквальные повторы, но
не распознаёт два пересказа одного факта.

Для бюджета в два предложения предположим оценки 0,85; 0,93; 0,89;
0,20. Выбираем второе и третье и возвращаем их в порядке документа.
Появилась передача подрядчику, но пропало сообщение о том, когда
поступили заявки, а «из них» потеряло явную отсылку. Даже подходящие
по отдельности предложения могут дать неудобное резюме. Переставить
слова или восстановить отсылку этот отбор не может.

<a id="sum-generation"></a>

## От копирования слов до генерации

В модели See, Liu и Manning на каждом шаге декодер распределяет
вероятность двумя способами. Первый — softmax по фиксированному
словарю. Второй — внимание по словам исходного текста. Если
слово встречается несколько раз, его вероятности копирования
с разных позиций складываются. При весе генерации $g$ итог равен

$$
\begin{aligned}
p(w) &= g\,p_{\mathrm{vocab}}(w) + (1-g)c(w),\\
c(w) &= \sum_{i:x_i=w} a_i.
\end{aligned}
$$

Слева на рисунке синие столбцы — внимание к позициям источника.
Справа зелёные столбцы — распределение по словарю. Сверху два
распределения складываются уже по словам, а не по позициям.
Например, у *Argentina* есть вклад с обеих сторон; *2‑0* в примере
авторов отсутствует в фиксированном словаре, но может быть скопировано.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/summarization-2026-11-22/see-pointer-generator-fig3.png|В pointer-generator веса внимания источника умножаются на 1 минус p_gen, распределение словаря на p_gen. Вверху они дают общую вероятность для слова Argentina.]]

*Abigail See, Peter J. Liu и Christopher D. Manning, [Get To The Point, рис. 3](https://aclanthology.org/P17-1099.pdf#page=3), [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/). Исходная диаграмма с английскими подписями.*

В английской версии отчёта слово *requests* встречается дважды. Пусть
на этих позициях веса внимания 0,20 и 0,15, а в словарном
распределении у слова вероятность 0,05. При $g=0{,}60$ получаем
$0{,}60\cdot0{,}05+0{,}40\cdot(0{,}20+0{,}15)=0{,}17$.
Вес $g$ модель вычисляет заново на каждом шаге по вектору контекста,
состоянию декодера и его входу. При обучении loss берут по итоговой
вероятности целевого слова: отдельной метки «скопировать» нет.

В той же работе coverage хранит сумму предыдущих весов внимания
по каждой позиции. Если на одну позицию раньше пришлось 0,20 и
0,30, то накоплено 0,50. На шаге с новым весом 0,25 штраф за эту
позицию равен $\min(0{,}25;0{,}50)=0{,}25$. Авторы подают
накопленные веса на вход механизма внимания и добавляют штраф к loss.
Повторное внимание становится дороже, но модель всё равно может
перепутать, к чему относятся числа 8 и 12, или повторить факт,
прочитав его в другой части текста.

Модель [BART](https://aclanthology.org/2020.acl-main.703/) показывает
другой путь. При предобучении её энкодер получает испорченный текст, а
декодер учится восстанавливать исходную последовательность. Например,
при *text infilling* целый фрагмент может быть заменён одним токеном
маски. На нижней панели рисунка вход энкодера и целевая
последовательность декодера различаются; при предобучении целью
служит полный текст.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/summarization-2026-11-22/lewis-bart-fig1c.png|Слева двунаправленный энкодер получает изменённую последовательность с пропусками, справа авторегрессионный декодер восстанавливает A, B, C, D, E.]]

*Mike Lewis и соавторы, [BART, рис. 1(c)](https://aclanthology.org/2020.acl-main.703.pdf#page=2), [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/). Показана только панель BART.*

При дообучении для суммаризации энкодер видит исходный документ
без искусственной порчи, а целевые токены берутся из короткого
редакторского резюме. На тренировочном шаге декодер получает
его эталонный префикс; при генерации приходится продолжать
уже собственный вывод, как при
[[02 Areas/ML & DL/00 Учебник/06 Encoder, Decoder и Encoder-Decoder/08 Машинный перевод#mt-objective|обучении перевода]].
Отдельного выхода «скопировать слово с позиции $i$» у BART нет.
Если в данных обычно достаточно сообщить, что «поступило 12 заявок»,
предобучение на восстановление текста само по себе не сделает
число закрытых заявок обязательным для вывода.

<a id="sum-rouge"></a>

## Почему ROUGE может предпочесть ошибку

ROUGE-N считает совпадения $n$-грамм с эталоном. В статье
[Chin-Yew Lin](https://aclanthology.org/W04-1013/) ROUGE-N
определён через полноту: число совпадений делят на число
эталонных $n$-грамм. Можно также посчитать точность относительно
длины ответа и F1. При сравнении результатов указывают вариант
метрики и настройки токенизации. ROUGE-2 работает с соседними
парами слов, а ROUGE-L вычисляют через наибольшую общую
подпоследовательность: она сохраняет порядок, но допускает пропуски.

Возьмём короткий английский эталон только для первых двух фактов,
без передачи подрядчику: *The desk received 12 requests and closed
8 by Wednesday*. После приведения к нижнему регистру и удаления
пунктуации в нём 10 слов.

| Вариант | Совпало слов | Полнота | Точность | F1 |
| --- | ---: | ---: | ---: | ---: |
| The desk received 12 requests and closed 12 by Wednesday | 9 | 9/10 | 9/10 | 0,900 |
| Of the 12 requests, 8 were resolved by Wednesday | 6 | 6/10 | 6/9 | 0,632 |

Повторы учитываются с ограничением по эталону. В первой строке
число 12 стоит дважды, но в совпадения входит один раз. Во второй
совпали *the*, *12*, *requests*, *8*, *by*, *Wednesday*. Верный
пересказ получил меньшую оценку, потому что иначе составил
предложение. Из роста ROUGE на реальном наборе нельзя отдельно
вывести, стали ли лучше передаваться числа, даты и причинные связи.

<a id="sum-faithfulness"></a>

## Проверка утверждений по документу

Для оценки сводки о заявках можно выписать отдельно ожидаемые
факты и утверждения, которые есть в резюме. В сводке из первого
раздела три утверждения, и все три подтверждаются отчётом.
В варианте про 12 закрытых заявок из двух утверждений подтверждается
одно. Полноту такой проверки считают по ожидаемым фактам, а долю
подтверждённых утверждений — по написанным в резюме. Одно правильное
утверждение может дать точность 1 и при этом не покрыть большую
часть отчёта.

В разметке [Maynez и соавторов](https://aclanthology.org/2020.acl-main.173/)
ошибка вроде «закрыли 12» относится к *intrinsic hallucination*:
резюме искажает содержание источника. Фраза «подрядчик работал
бесплатно» — пример *extrinsic hallucination*: по отчёту это
проверить нельзя. Вторая ситуация не означает, что подрядчику
в действительности заплатили. Проверка верности источнику
не устанавливает, что произошло за пределами документа.

Авторы [QAGS](https://aclanthology.org/2020.acl-main.450/) генерируют
вопросы по резюме. Затем одна и та же модель извлечения отвечает
на них отдельно по документу и по резюме. Ответы сравнивают
по F1 на токенах и усредняют. Для варианта с ошибкой подставим
два ручных вопроса:

| Вопрос | Ответ по документу | Ответ по резюме | F1 |
| --- | --- | --- | ---: |
| Сколько заявок поступило? | 12 | 12 | 1 |
| Сколько заявок закрыли к среде? | 8 | 12 | 0 |

Среднее равно 0,5. Это результат для двух заданных вопросов,
а не оценка, которую выдала модель QAGS. Такая проверка найдёт
подмену числа, только если появится соответствующий вопрос и модель
правильно извлечёт оба ответа. Пропущенную передачу подрядчику
эта схема в общем случае не заметит: в резюме нет утверждения,
по которому можно было бы спросить о передаче.

<a id="sum-long-documents"></a>

## Когда документ не помещается в контекст

Представим, что понедельничная запись и четверговая запись стоят
на разных страницах. Разрезав отчёт между ними, можно оставить
фразу «две из четырёх оставшихся» без описания того, какие заявки
остались. Сжатие каждой страницы в отдельности уменьшит объём,
но при повторной суммаризации восстановить отброшенную связь
можно лишь по исходным фрагментам.

В сводке, которую будут перепроверять, имеет смысл хранить рядом
с каждым утверждением ссылки на места в исходном отчёте. Например,
для «передали две из четырёх» нужна запись о передаче, а для связи
с понедельничной партией может понадобиться соседняя запись.
Если от задачи требуется состояние заявок на определённую дату,
при отборе фрагментов важны переходы между состояниями и даты,
а не только близость абзаца к слову «заявка».

<details>
<summary>Проверить расчёты из главы в Python</summary>

```python
from collections import Counter
from math import isclose


def overlap(a, b):
    return sum((Counter(a) & Counter(b)).values())


def rouge1(candidate, reference):
    candidate, reference = candidate.split(), reference.split()
    hits = overlap(candidate, reference)
    precision = hits / len(candidate)
    recall = hits / len(reference)
    f1 = 2 * hits / (len(candidate) + len(reference))
    return precision, recall, f1


scores = [0.85, 0.93, 0.89, 0.20]
selected = sorted(
    sorted(range(1, 5), key=lambda i: scores[i - 1], reverse=True)[:2]
)
assert selected == [2, 3]

g = 0.60
requests_probability = g * 0.05 + (1 - g) * (0.20 + 0.15)
assert isclose(requests_probability, 0.17)
assert min(0.25, 0.20 + 0.30) == 0.25

reference = "the desk received 12 requests and closed 8 by wednesday"
wrong = "the desk received 12 requests and closed 12 by wednesday"
faithful = "of the 12 requests 8 were resolved by wednesday"
assert rouge1(wrong, reference) == (0.90, 0.90, 0.90)
assert isclose(rouge1(faithful, reference)[2], 12 / 19)

pairs = [("12", "12"), ("8", "12")]
answer_f1 = sum(
    2 * overlap(a.split(), b.split()) / (len(a.split()) + len(b.split()))
    for a, b in pairs
) / len(pairs)
assert answer_f1 == 0.50
print(selected, round(requests_probability, 2), round(12 / 19, 3), answer_f1)
```

</details>
