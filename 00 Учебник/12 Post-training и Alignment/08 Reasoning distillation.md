# Дистилляция моделей рассуждения

> [!abstract] После главы
> Вы научитесь различать три метода, которые часто объединяют словом
> «дистилляция»: SFT на решениях более сильной модели, согласование распределений
> вероятностей и обучение на собственных генерациях ученика. Мы построим процесс
> создания проверенного набора данных, вручную рассчитаем KL-дивергенцию и
> выберем подход в зависимости от доступных выходов учителя и вычислительных
> ресурсов.

## Три разных объекта под одним названием

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/post-training-courses/distillation-two-meanings.png]]

*Два значения слова «дистилляция», которые особенно важно не смешивать:
классическое согласование мягких распределений и современное SFT на текстах
сильной модели. Третий вариант — обучение на состояниях ученика — будет введён
после этих двух. Источник: Nathan Lambert,
[RLHF & Post-Training, лекция 7, слайд 12](https://rlhfbook.com/teach/course/lec7-chap12-synthetic-data/#/11).*

1. **Дистилляция последовательностей:** учитель порождает решение, а ученик
   увеличивает его правдоподобие с помощью SFT. Так обучались
   DeepSeek-R1-Distill и воспроизведение Open-R1.
2. **Дистилляция логитов:** ученик приближает полное распределение вероятностей
   учителя по словарю.
3. **Дистилляция на данных ученика:** ученик порождает собственные ответы, а
   учитель сообщает распределения вероятностей именно для состояний, в которых
   оказался ученик.

Эти методы используют разные данные и функции потерь и по-разному ошибаются.
Успех одного метода не доказывает применимости остальных.

## Сквозной пример

Запрос: `Реши 3x+6=18; закончи FINAL: число`.

Учитель породил три решения:

```text
t1: Вычтем 6: 3x=12. Разделим на 3. FINAL: 4       pass
t2: Перенесём 6: 3x=24. FINAL: 8                   fail
t3: Проверка: 3·4+6=18. Следовательно FINAL: 4     pass
```

Проверяющая программа оставляет `t1` и `t3`. Однако правильный финальный ответ
ещё не определяет лучший учебный пример: `t3` показывает проверку, а `t1` —
прямое решение. Вместо автоматического выбора самого длинного ответа нужны
явные правила, учитывающие правильность, однозначность разбора, отсутствие
дубликатов, язык, длину и разнообразие способов решения.

## Дистилляция последовательностей: ответы учителя как данные SFT

<a id="sequence-distillation"></a>

### Запись исходной генерации

```json
{
  "prompt_id": "linear-0042",
  "teacher": "DeepSeek-R1",
  "teacher_revision": "2025-01",
  "sampling": {"temperature": 0.6, "top_p": 0.95, "max_tokens": 16384},
  "seed": 31,
  "completion_raw": "Вычтем 6... FINAL: 4",
  "parsed_answer": "4",
  "verifier_revision": "numeric-v3",
  "verdict": "pass",
  "token_count": 19
}
```

Следует сохранять и неудачные исходные ответы: без них нельзя измерить смещение,
внесённое фильтром. Итоговая запись для SFT может быть проще:

```json
{
  "messages": [
    {"role": "user", "content": "Реши 3x+6=18..."},
    {"role": "assistant", "content": "Вычтем 6... FINAL: 4"}
  ],
  "provenance": {"prompt_id": "linear-0042", "teacher_sample": 0}
}
```

### Целевая функция и ручной расчёт

Для target tokens $y^T$:

$$
\mathcal L_{seq}=-\sum_t m_t\log\pi_S(y_t^T|x,y^T_{<t}).
$$

Пусть вероятности трёх токенов ответа равны $(0.50,0.25,0.80)$.

$$
L=-[\ln0.50+\ln0.25+\ln0.80]
=-\ln0.1\approx2.303.
$$

Средняя отрицательная логарифмическая вероятность токена равна $0.768$, а
перплексия — $e^{0.768}\approx2.16$. Все альтернативы исчезли: ученик видит
одну выбранную последовательность, но не видит неопределённость учителя.

### Минимальный код

```python
from importlib.metadata import version
from datasets import load_dataset
from transformers import AutoTokenizer
from trl import SFTConfig, SFTTrainer

assert version("trl") == "0.23.1"
model_id = "Qwen/Qwen2.5-Math-1.5B"
tokenizer = AutoTokenizer.from_pretrained(model_id)
tokenizer.eos_token = "<|im_end|>"
# Учебный ChatML для текстовых сообщений; EOS входит в assistant mask.
tokenizer.chat_template = (
    "{% for m in messages %}"
    "{{ '<|im_start|>' + m['role'] + '\\n' }}"
    "{% if m['role'] == 'assistant' %}{% generation %}"
    "{{ m['content'] + '<|im_end|>' }}{% endgeneration %}"
    "{% else %}{{ m['content'] + '<|im_end|>' }}{% endif %}"
    "{{ '\\n' }}{% endfor %}"
    "{% if add_generation_prompt %}{{ '<|im_start|>assistant\\n' }}{% endif %}"
)
probe = tokenizer.apply_chat_template(
    [{"role": "user", "content": "2 + 2?"},
     {"role": "assistant", "content": "4"}],
    tokenize=True, return_dict=True, return_assistant_tokens_mask=True,
)
targets = [t for t, m in zip(probe["input_ids"], probe["assistant_masks"]) if m]
assert targets and targets[-1] == tokenizer.eos_token_id
assert tokenizer.decode(targets) == "4<|im_end|>"
assert 0 in probe["assistant_masks"]  # запрос не является target

data = load_dataset("open-r1/Mixture-of-Thoughts", "all", split="train")
args = SFTConfig(
    output_dir="reasoning-student",
    max_length=32768,
    assistant_only_loss=True,
    eos_token="<|im_end|>",
    packing=False,
    learning_rate=4e-5,
    num_train_epochs=1,
    bf16=True,
    gradient_checkpointing=True,
)
trainer = SFTTrainer(
    model=model_id,
    processing_class=tokenizer,
    args=args,
    train_dataset=data,
)
trainer.train()
```

Пример использует [API TRL 0.23.1](https://huggingface.co/docs/trl/v0.23.1/sft_trainer)
(`pip install trl==0.23.1` в отдельном окружении). Это конфигурация учебного
запуска, не выполненное обучение. До загрузки весов probe проверяет фактическую
маску и EOS токенизатора; при несовместимой версии Transformers он должен
остановить запуск. Для воспроизводимого эксперимента дополнительно закрепляют
ревизии модели и датасета и весь lockfile окружения.

Шаблон диалога должен позволять отделить маской токены ассистента. Для базовых
моделей Qwen токен конца должен совпадать с используемым в ChatML
`<|im_end|>`; в Open-R1 эта распространённая ошибка разобрана отдельно.

## Как Open-R1 создавал данные рассуждений

[Open-R1 Update #2](https://huggingface.co/blog/open-r1/update-2) — редкий
публичный разбор крупного процесса подготовки данных:

- 400 тысяч математических задач из NuminaMath 1.5;
- два решения учителя, иногда четыре: всего около 800 тысяч генераций;
- до 16 тысяч токенов на ответ; ограничения в 8 тысяч хватало лишь примерно для 75% задач;
- Math-Verify для автоматической проверки;
- Llama-3.3-70B как дополнительный оценщик для части неразобранных ответов;
- 220 тысяч задач после фильтрации.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/post-training-courses/distillation-data-pipeline.png]]

*Базовая схема дистилляции последовательностей: запросы поступают сильной
модели, её ответы превращаются в синтетический набор, а затем служат целями
обычного SFT. Для reasoning-моделей между ответами и набором появляются
проверка, фильтрация и сохранение длинных трасс; именно эти стадии подробно
разобраны в списке Open-R1 выше. Источник: Nathan Lambert,
[RLHF & Post-Training, лекция 7, слайд 15](https://rlhfbook.com/teach/course/lec7-chap12-synthetic-data/#/14).*

Это существенно сложнее, чем «скачать ответы R1 и обучить модель». Ограничение
длины, число попыток, полнота проверяющей программы и правила отбора определяют,
какую учебную программу в итоге увидит ученик.

## s1: 59 тысяч → 1 тысяча

<!-- source_unit_id: meeting-04-slides-s1k-data -->

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/berkeley-agents-2025/reasoning-posttraining-memory/m04-p128-s1-data-funnel.png]]

*Прочитайте воронку как четыре разных решения о данных, а не как один фильтр:
техническая пригодность, корректность формата, трудность для выбранных student
models и разнообразие предметных областей. Число 1 000 имеет смысл только вместе
с этими критериями. Источник: Hanna Hajishirzi, Berkeley Advanced LLM Agents,
meeting 4,
[слайд 128](https://rdi.berkeley.edu/adv-llm-agents/slides/OLMo-Tulu-Reasoning-Hanna.pdf#page=128).*

В работе s1 подробно документирован процесс отбора синтетических решений.
Авторы собрали 59 029 задач из открытых
математических, научных и логических наборов и добавили собственные трудные
задачи. Для каждой задачи Gemini Flash Thinking породила рассуждение и финальный
ответ. Эта исходная коллекция ещё не была готовым учебным набором: в ней
оставались ошибки API, испорченная разметка, простые примеры и сильный перекос в
сторону самых многочисленных источников.

Сокращение происходило в три содержательно разных этапа:

| этап | осталось | что удаляли | зачем |
|---|---:|---|---|
| исходная генерация | 59 029 | — | сохранить широкий пул задач и решений учителя |
| проверка качества | 54 116, затем 51 581 | ошибки API, пустые или неправильно оформленные ответы | не обучать модель на технически испорченных последовательностях |
| проверка трудности | 24 496 | задачи, которые уже решали Qwen2.5-7B-Instruct или Qwen2.5-32B-Instruct | направить ограниченный бюджет на примеры, где ученику ещё есть чему учиться |
| отбор разнообразия | 1 000 | избыток близких задач внутри доменов | покрыть 50 предметных областей, сохранив трудные длинные решения |

На последнем этапе задачи распределили по предметным областям и выбирали их так,
чтобы области были представлены равномернее. Внутри области предпочтение
отдавали более длинным рассуждениям: длина служила приближённым признаком
трудности. Получившийся s1K использовали для обычного SFT Qwen2.5-32B-Instruct.
Следовательно, переход от 59 тысяч к тысяче — это не утверждение «меньше данных
всегда лучше», а попытка убрать лёгкие и повторяющиеся примеры при фиксированном
бюджете обучения.

У такого отбора есть цена. Трудность определяется успехом двух конкретных
моделей, поэтому задача, лёгкая для них, могла бы быть полезна другому ученику.
Длинное решение не обязательно труднее или лучше короткого. Наконец,
автоматические фильтры не гарантировали истинность каждой трассы. По вердиктам
grader авторов правильными признаны 53,6% ответов s1K и 63,0% ответов
s1K-1.1. Второе число относится не к ручной правке прежних ответов: для тех же
1 000 задач заново сгенерировали трассы с DeepSeek-R1. Протокол проверки
сопоставляет ответ с эталоном с помощью Claude 3.5 Sonnet; эти доли не означают
доказанную правильность каждого промежуточного шага. См.
[s1, §2.2, Appendix A и C.3](https://arxiv.org/html/2501.19393#A1).
Поэтому названия стадий `quality`, `difficulty` и `diversity` описывают правила
отбора, но не доказывают качество, трудность и разнообразие каждого примера.

Воронка отбора показана в
[Berkeley Advanced LLM Agents, meeting 4, слайды 126–132](https://rdi.berkeley.edu/adv-llm-agents/slides/OLMo-Tulu-Reasoning-Hanna.pdf#page=126),
а точные правила, источники задач и проверка качества описаны в
[s1: Simple test-time scaling](https://arxiv.org/abs/2501.19393). Продолжение
работы — принудительное управление вычислительным бюджетом во время генерации —
относится уже к test-time compute, а не к созданию s1K.

## Смещение, внесённое отбором

<a id="selection-bias"></a>

Фильтр «оставить только прошедшие проверку» меняет распределение данных:

- трудные задачи, которые учитель редко решает, исчезают чаще;
- переоценивается стиль, который легко разбирается программой;
- короткие задачи дешевле и могут доминировать;
- популярная стратегия учителя вытесняет редкие, но корректные стратегии;
- дополнительный модельный оценщик создаёт отдельный класс меток с иной надёжностью.

В наборе данных следует хранить число попыток и долю успешных решений учителя.
Один прошедший ответ из 64 попыток представляет иную сложность, чем четыре
успешных ответа из четырёх.

## Дистилляция логитов

Учитель и ученик получают один и тот же префикс. При температуре $T$

$$
p_T(v)=\operatorname{softmax}(z_T(v)/T),\qquad
p_S(v)=\operatorname{softmax}(z_S(v)/T),
$$

$$
L_{KD}=T^2\sum_v p_T(v)\log\frac{p_T(v)}{p_S(v)}.
$$

$T>1$ делает видимой дополнительную информацию распределения: учитель может
считать несколько токенов правдоподобными, хотя в готовом ответе выбран лишь один.

### Ручной KL

Для трёх токенов учитель даёт $p_T=(0.7,0.2,0.1)$, а ученик —
$p_S=(0.5,0.4,0.1)$ при уже выбранном $T=1$:

$$
D_{KL}=0.7\ln(1.4)+0.2\ln(0.5)+0.1\ln(1)
\approx0.2355-0.1386=0.0969.
$$

Перекрёстная энтропия с жёсткой меткой увидела бы только правильный токен.
KL-дивергенция дополнительно сообщает, что второй токен учитель считает вдвое
вероятнее третьего.

```python
import torch.nn.functional as F

def kd_loss(student_logits, teacher_logits, temperature=2.0):
    s = F.log_softmax(student_logits / temperature, dim=-1)
    t = F.softmax(teacher_logits / temperature, dim=-1)
    return F.kl_div(s, t, reduction="batchmean") * temperature**2
```

### Ограничения

- Нужен доступ к логитам учителя, которых обычный API не предоставляет.
- Полный тензор `пакет × последовательность × словарь` дорог в хранении и передаче.
- Прямое вычисление KL требует общего пространства токенов. Для разных
  токенизаторов нет естественного соответствия индексов словаря.
- Заранее сохранённые логиты на последовательностях учителя не устраняют
  расхождение с состояниями, в которые ученик попадает при собственной генерации.

## Дистилляция на собственных генерациях ученика

<a id="distillation-vs-rft"></a>

### Где заканчивается online RL и начинается новый датасет

В reasoning-пайплайнах одни и те же траектории могут пройти через разные
алгоритмы, поэтому различать их следует по распределению выборки и gradient
signal.

| этап | кто генерирует | какие ответы входят в обучение | сигнал |
|---|---|---|---|
| on-policy RLVR | текущий student | вся rollout-группа | положительные и отрицательные advantages |
| RFT / expert iteration | обычно текущий student | прошедшие verifier | SFT log-likelihood |
| teacher distillation | более сильная модель | отобранные teacher traces | SFT или token-level KL |

RFT можно рассматривать как самодистилляцию лишь в широком бытовом смысле. В
эксперименте это важное различие: после сохранения успешных rollouts и нескольких
SFT epochs данные уже stale, модель не исследует новые ответы и не оптимизирует
ожидаемый verifier reward напрямую. Чтобы снова получить expert iteration,
цикл `generate → verify → train` повторяют и версионируют каждый снимок данных.

DeepSeek-R1 использует около 600 тысяч reasoning-примеров и около 200 тысяч
неризонинговых примеров — 804 745 записей в смешанном SFT-наборе — для обучения
меньших Qwen- и Llama-моделей. Это доказательство переноса поведения в
рамках указанного набора моделей и benchmarks, а не доказательство копирования
внутреннего алгоритма учителя. Kimi и Qwen также чередуют online-стадии с
отбором и SFT; в описании результата всегда следует указывать, какая модель
породила traces и каким verifier они прошли.

При дистилляции последовательностей или логитов ученик обучается на траекториях
учителя. Во время самостоятельной генерации он попадает в собственные префиксы,
для которых ответы учителя не собирались. Дистилляция на данных ученика меняет
порядок действий:

1. ученик порождает $y^S\sim\pi_S$;
2. учитель оценивает распределение следующего токена для префиксов $y^S_{<t}$;
3. ученик приближается к учителю именно на распределении собственных состояний.

$$
L_{on-policy}=\mathbb E_{x,\,y^S\sim\pi_S}
\sum_t D(\pi_T(\cdot|x,y^S_{<t})||\pi_S(\cdot|x,y^S_{<t})).
$$

Как и в интерактивном обучении с подкреплением, данные здесь меняются вместе с
учеником. Однако сигналом служит распределение учителя, а не скалярная награда
проверяющей программы.

### Практическая реализация

Экспериментальный [TRL DistillationTrainer](https://github.com/huggingface/trl/blob/main/docs/source/distillation_trainer.md)
использует следующие компоненты:

- набор данных, содержащий только запросы;
- буфер генераций, отделяющий большой пакет vLLM от обучающего микропакета;
- внешний сервер vLLM с моделью-учителем;
- бинарную передачу логарифмов вероятностей вместо огромных сообщений JSON.

API находится в `trl.experimental`, поэтому версию зависимости или конкретный
коммит необходимо фиксировать.

## Как выбрать способ дистилляции

<a id="reasoning-recipes"></a>

| условие | естественный выбор |
|---|---|
| учитель доступен только через текстовый API | дистилляция последовательностей |
| доступны параметры или логиты и общий токенизатор | дистилляция логитов |
| важны собственные ошибки ученика и учитель доступен во время обучения | дистилляция на генерациях ученика |
| ответы можно надёжно проверить, но логиты недоступны | SFT на проверенных решениях |
| ученик почти никогда не решает задачу | сначала SFT и постепенное усложнение |
| учитель дорог и данные нужно использовать многократно | заранее сохранённые ответы или логиты |

Методы можно сочетать: сначала дать ученику проверенные решения для начального
SFT, затем перейти к дистилляции на его собственных генерациях или к RLVR на
задачах, где он уже получает ненулевую награду.

## Дистилляция не копирует внутренний алгоритм

Функция потерь ограничивает только наблюдаемое поведение на встретившихся
префиксах. Ученик может найти другой внутренний способ решения, не вместить
стратегию учителя или просто запомнить поверхностные шаблоны. Записанная цепочка
рассуждений также не обязана точно описывать внутренние вычисления. Поэтому
корректно говорить о переносе распределения наблюдаемых ответов на выбранных
данных, а не о копировании алгоритма мышления.

## Характерные ошибки и оценивание

<a id="distillation-evaluation"></a>

### Данные

- пересечение исходных задач с проверочными наборами;
- повторяющиеся шаблоны после поверхностного удаления дубликатов;
- правильный итоговый ответ при ошибочном рассуждении;
- преобладание одного языка, формата или стиля учителя;
- оценки без сведений об их происхождении;
- обрезка, удаляющая итоговый ответ или важный шаг проверки.

### Обучение

- маска ассистента ошибочно включает токены запроса;
- шаблон диалога или токен конца отличается между обучением и применением;
- плотная укладка последовательностей смешивает независимые диалоги;
- длинные решения доминируют из-за большего числа токенов;
- при дистилляции логитов перепутано направление KL-дивергенции;
- логиты учителя и ученика относятся к разным позициям токенов.

### Evaluation

Следует измерять pass@1 и pass@$k$, правильность по уровням сложности, квантили
длины ответа, долю успешно разобранных ответов, ошибки рассуждений на ручной
выборке, общие контрольные задачи, смешение стилей и языков, калибровку и
стоимость одного решённого примера. Сравнивать с обычным SFT нужно при равном
числе **обучающих токенов**, а не записей.

## Воспроизводимая схема Open-R1

```bash
ACCELERATE_LOG_LEVEL=info accelerate launch \
  --config_file recipes/accelerate_configs/zero3.yaml \
  src/open_r1/sft.py \
  --config recipes/OpenR1-Distill-7B/sft/config_distill.yaml
```

[Open-R1](https://github.com/huggingface/open-r1) публикует конфигурацию, набор
данных, команды оценки и промежуточную модель. Это удобная исходная точка для
воспроизводимого опыта. [Distilabel](https://github.com/argilla-io/distilabel)
помогает организовать массовое создание синтетических данных, но сам по себе не
определяет функцию потерь дистилляции.

## Практика и первоисточники

### Задания

1. Для 1000 задач сгенерируйте по четыре решения учителя и сохраните неудачные попытки.
2. Реализуйте проверку и укажите происхождение каждого решения.
3. Сравните три правила отбора: первый успешный ответ, кратчайший успешный ответ
   и набор разнообразных успешных ответов.
4. Обучите одну и ту же модель-ученика на каждой выборке при равном числе токенов.
5. Вручную проверьте 100 решений и оцените долю ложных принятий проверяющей программы.
6. На игрушечном словаре воспроизведите KL $0.0969$ и проверьте направление градиента.
7. Добавьте ошибочный префикс ученика и сравните ответ учителя на нём с целью,
   заранее сохранённой на последовательности учителя.
8. Проведите оценивание с теми же параметрами генерации и отдельным генератором новых задач.
9. В отчёте разделите улучшения от объёма данных, фильтрации и самой функции потерь.
