# SFT и instruction data

> [!abstract] Результат урока
> После этой главы вы сможете превратить диалоговую строку датасета в токены и
> labels, вручную посчитать masked cross-entropy, написать минимальный SFT step
> и объяснить, почему хороший instruction dataset — не «коллекция ответов», а
> спецификация поведения будущего ассистента.

## Зачем обучать модель ещё раз

Pretraining учит продолжать текст. Если строка заканчивается словами «Как
удалить файл в Linux?», правдоподобным продолжением может быть команда, спор на
форуме или второй вопрос из FAQ. Ни одно из них не нарушает next-token objective.
Но пользователю нужен не произвольный фрагмент интернета, а ответ определённого
типа.

Andrej Karpathy в *State of GPT* предлагает полезное различие: base model
имитирует документы, assistant model — ответы полезного собеседника. SFT — первый
этап этого перехода. Мы показываем модели диалоги, которые хотели бы получать на
inference, и продолжаем обычное обучение следующему токену, но уже на тщательно
отобранном распределении.

![[02 Areas/ML & DL/00 Учебник/Assets/Figures/curated/instructgpt/chatgpt-training-pipeline.png]]

*SFT — левая часть pipeline InstructGPT: люди пишут demonstrations, а модель
учится их воспроизводить. Источник схемы: Ouyang et al., 2022, Figure 2.*

## Сквозной пример

Будем обучать технического ассистента на запросе:

> Объясни разницу между TCP и UDP начинающему. Приведи по одному примеру и
> уложись в 90 слов.

Эксперт написал ответ:

> TCP устанавливает соединение и контролирует доставку и порядок данных.
> Поэтому он подходит для загрузки веб-страницы: пропущенный фрагмент будет
> отправлен снова. UDP посылает датаграммы без гарантии доставки и порядка,
> зато не ждёт подтверждений. Его часто используют в голосовых звонках, где
> свежий звук полезнее запоздавшей повторной передачи. UDP не «всегда быстрее»:
> это другой набор компромиссов.

Один такой пример сообщает сразу несколько вещей: отвечай на вопрос, соблюдай
ограничение длины, объясняй без лишнего жаргона, не превращай компромисс в
ложное абсолютное правило. Поэтому качество demonstrations важнее механического
числа строк.

## 1. От сырой строки до обучающей последовательности

### Строка датасета

Удобный переносимый формат — список сообщений:

```json
{
  "messages": [
    {"role": "system", "content": "Ты точный технический ассистент."},
    {"role": "user", "content": "Объясни разницу между TCP и UDP..."},
    {"role": "assistant", "content": "TCP устанавливает соединение..."}
  ],
  "source": "expert_networking_v2",
  "quality": 0.94
}
```

`source` и `quality` не подаются модели автоматически. Они нужны, чтобы
фильтровать, взвешивать и расследовать ошибки. Без provenance невозможно понять,
какой источник научил модель неверному поведению.

### Chat template — часть модели

JSON не попадает в Transformer. Tokenizer превращает роли и сообщения в одну
строку, например:

```text
<|system|>Ты точный технический ассистент.<|end|>
<|user|>Объясни разницу между TCP и UDP...<|end|>
<|assistant|>TCP устанавливает соединение...<|end|>
```

Названия маркеров условны: у Llama, Qwen и других семейств свои шаблоны. Нельзя
обучить модель с одним template, а обслуживать с другим и считать это безобидным
форматированием. Служебные токены участвуют в условном распределении модели.

Пусть игрушечный tokenizer дал такую последовательность:

| позиция | token | id | label | loss? |
|---:|---|---:|---:|:---:|
| 0 | `<system>` | 101 | −100 | нет |
| 1 | `точный` | 25 | −100 | нет |
| 2 | `<user>` | 102 | −100 | нет |
| 3 | `TCP` | 41 | −100 | нет |
| 4 | `<assistant>` | 103 | −100 | нет |
| 5 | `TCP` | 41 | 41 | да |
| 6 | `надёжен` | 72 | 72 | да |
| 7 | `UDP` | 51 | 51 | да |
| 8 | `быстрее` | 88 | 88 | да |
| 9 | `<end>` | 104 | 104 | да |

`−100` — соглашение PyTorch: позиция контекстная, но в cross-entropy не входит.
Модель видит system и user tokens через attention, однако мы не учим её
воспроизводить слова пользователя.

> [!warning] Сдвиг labels
> Logits в позиции $i$ предсказывают token $i+1$. Большинство model classes
> выполняют сдвиг внутри `forward(labels=...)`; в собственном коде его нужно
> сделать явно. Ошибка на одну позицию может давать «работающий» loss и полностью
> бессмысленное обучение.

### Multi-turn: что считать target

В диалоге с несколькими ходами есть три распространённых режима:

1. loss по каждому сообщению assistant — эффективно использует данные;
2. loss только по последнему ответу — предыдущие ответы считаются контекстом;
3. отдельный пример на каждый assistant turn — прозрачно, но дороже хранить.

Выбор зависит от происхождения истории. Если ранний ответ сгенерировала старая
модель и человек исправил только последний, учить ранний ответ как эталон опасно.

## 2. Что минимизирует SFT

Пусть $x$ — system, prompt и история, $y=(y_1,\ldots,y_T)$ — экспертный ответ,
$m_t$ — маска обучаемых позиций. Тогда

$$
\mathcal L_{\mathrm{SFT}}(\theta)
=-\frac{1}{\sum_t m_t}\sum_{t=1}^{T}m_t
\log \pi_\theta(y_t\mid x,y_{<t}).
$$

Модель получает правильный префикс $y_{<t}$ — это **teacher forcing**. Она не
должна сначала сама сгенерировать начало ответа. Градиент повышает вероятность
каждого target token в контексте правильного предыдущего текста.

### Ручной расчёт

Сократим ответ до трёх targets. Модель присвоила правильным токенам вероятности:

| target | $p(y_t\mid x,y_{<t})$ | $-\ln p$ |
|---|---:|---:|
| `TCP` | 0.50 | 0.693 |
| `надёжен` | 0.20 | 1.609 |
| `<end>` | 0.80 | 0.223 |

Средний loss:

$$
\mathcal L=(0.693+1.609+0.223)/3=0.842.
$$

Perplexity на этих трёх позициях равна $e^{0.842}\approx2.32$. Самый сильный
градиент придёт от слова `надёжен`: эталонный токен имел лишь 20% вероятности.
Но loss не знает, что «надёжность» концептуально важнее пунктуации: все
учитываемые токены являются targets. Это одна из причин тщательно готовить текст.

## 3. Минимальный code companion

```python
import torch
from torch.nn import functional as F

def assistant_only_loss(model, input_ids, assistant_mask):
    # input_ids: [batch, seq]; mask=1 только на assistant targets
    logits = model(input_ids).logits                # [B, S, V]
    pred = logits[:, :-1].contiguous()              # предсказывает следующий
    target = input_ids[:, 1:].clone()
    target[assistant_mask[:, 1:] == 0] = -100
    return F.cross_entropy(
        pred.view(-1, pred.size(-1)),
        target.reshape(-1), ignore_index=-100
    )

loss = assistant_only_loss(model, input_ids, assistant_mask)
loss.backward()
optimizer.step()
```

Перед полноценным запуском полезен unit test: распечатать decoded tokens,
labels и маску одного batch. Если `<assistant>` или конец ответа замаскированы
не так, loss curve этого не объяснит.

### Packing

Короткие диалоги обычно объединяют до длины контекста, иначе GPU считает
padding. При packing нужно определить границы документов, корректно поставить
EOS и убедиться, что loss не перескочил из конца одного диалога в начало другого.
Вариант с полной causal attention между упакованными примерами встречается, но
это осознанный компромисс, а не бесплатная оптимизация.

## 4. Как строят instruction data

### Human demonstrations

Эксперту дают prompt, подробную rubric и примеры. Это дорого, зато позволяет
создать якорный набор поведения. InstructGPT отдельно отбирал и обучал labelers:
«человек написал ответ» ещё не означает «получился эталон».

### Existing tasks и преобразование форматов

Классификацию можно превратить в инструкцию, но простой ответ `B` часто учит
формату benchmark, а не объяснению. Следует решить, нужен ли только label,
обоснование или структурированный output.

### Synthetic instruction data

Teacher model генерирует prompts и ответы, после чего данные фильтруют по
верификаторам, judge-моделям и дедупликации. Это масштабируется, но наследует
стиль, ошибки и «любимые» задачи teacher. Synthetic data должна расширять
покрытие, а не клонировать один голос миллионы раз.

### Data mixture

Пусть 90% строк — простые ответы общего назначения и 10% — качественный tool
use. Равномерное перемешивание почти гарантирует, что редкое поведение будет
недообучено. Mixture задаёт, какие навыки модель встречает на каждом шаге;
обычно управляют sampling weights, cap на источник и curriculum.

## 5. Что SFT умеет и чего не обещает

SFT хорошо задаёт chat template, стиль, tool syntax, структуру решения и
типовые отказы. Оно может сообщить факты, но не является надёжной заменой
поиска или регулярного pretraining: небольшой набор demonstrations легко
переобучается, а факт оказывается связан с конкретной формулировкой.

Главное ограничение: один target не показывает, *почему* он лучше альтернатив.
Если ответ одновременно точный, короткий и вежливый, loss не разделяет эти
причины. Для этого собирают preference data — тема следующей главы.

## 6. Failure cases и диагностика

| Симптом | Возможная причина | Проверка |
|---|---|---|
| модель повторяет user prompt | loss считался по user tokens | визуализировать labels |
| не заканчивает ответ | EOS отсутствует или masked | доля EOS targets |
| ломает роли | train/inference templates различаются | сравнить exact token ids |
| говорит одним шаблонным стилем | synthetic monoculture | кластеризация n-grams/styles |
| забывает базовые навыки | LR/epochs велики, смесь узкая | base vs SFT eval suite |
| train loss падает, ответы хуже | leakage/duplicates/плохая rubric | ручной blind audit |

Не оценивайте SFT только loss. Нужны held-out prompts, проверка формата,
фактической точности, длины, safety и сохранения прежних возможностей.

## Практикум

1. Возьмите два multi-turn диалога. Постройте labels для режимов «все assistant
   turns» и «только последний». Объясните, где расходятся градиенты.
2. Для вероятностей $0.7,0.1,0.4,0.8$ вручную вычислите средний NLL и perplexity.
3. Реализуйте проверку, что в каждом примере есть хотя бы один unmasked target
   и последним target является EOS.
4. Сравните пять generations base и SFT model одним sampling config. Разметьте
   отдельно correctness, instruction following, style и format.
5. Найдите в датасете 20 почти одинаковых synthetic answers. Предложите правило
   дедупликации, которое не удалит содержательно разные решения.
