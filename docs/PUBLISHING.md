# Сборка и публикация Bookvar

Все команды ниже выполняются из корня репозитория. Редактируемые исходники
хранятся в Markdown; адаптер в `publishing/` готовит страницы для Astro
Starlight в `site/`.

## Исходники и оглавления

`publishing/navigation.yml` задаёт опубликованные исходники, стабильные
адреса, боковое меню и порядок чтения. Полное объяснение механизма находится
в одной главе учебника. Предметный справочник открывает те же главы;
семейства моделей, сравнения и хронология входят в него как отдельные
подразделы. Оглавления оригинальных курсов находятся в библиотеке источников.

При добавлении главы проверьте её место в последовательности чтения,
ссылки из соседних глав и оглавление `00 Учебник/_index.md`.
Для существующей английской версии указывается `source_en` в той же
записи manifest. Новый перевод не требуется для публикации русской главы.

Если весь канонический текст уже написан на английском, укажите в его
frontmatter `source_language: en`. Адаптер использует один исходник для
обоих адресов, сохраняя язык текста и ссылки соответствующей локали.
Такой материал не требует копии в `en/` и не считается новым переводом.
Для русского или смешанного текста допустимы `source_language: ru` и
`source_language: mixed`: без отдельной английской страницы сайт сохраняет
явное уведомление о показе канонического текста. Не ставьте `en` только
потому, что в русской главе есть английские цитаты или код.

Предметные указатели `01 Справочник/_index.md` и
`en/01 Reference/_index.md` генерируются из manifest. После изменения
состава тем или названий обновите их командой:

```bash
pnpm --dir publishing exec tsx tools/sync-topic-index.ts
pnpm --dir publishing check:topics
```

Первая команда записывает два указателя. Вторая только проверяет,
что их содержимое соответствует исходникам. Не исправляйте сгенерированный
список вручную. Если инструмент сообщает о неклассифицированной теме,
проверьте её маршрут и соответствующую группу в
`publishing/tools/sync-topic-index.ts`.

Для отдельного метода внутри большой главы можно добавить в её frontmatter
`reference_terms`. Каждая запись содержит `label`, `label_en` и `anchor`.
Значение `anchor` должно совпадать с уникальным явным HTML-якорем в этой же
главе. Указатель создаст вложенную ссылку на раздел; дополнительная справочная
статья не нужна. Несуществующий или неоднозначный якорь остановит генерацию.

Старые справочные адреса сохраняются как прямые перенаправления после
содержательной сверки и снимка исходной статьи; порядок описан в
[CONTRIBUTING.md](../CONTRIBUTING.md#объединение-старой-статьи-с-главой).
Не убирайте старый URL из manifest только потому, что его больше нет
в боковом меню.

## Локальный просмотр

Используйте Node.js из `.nvmrc` и pnpm 10.32.1, как в workflow.

```bash
pnpm install --frozen-lockfile
pnpm --dir site dev
```

Команда `site dev` сначала запускает адаптер через `predev`. Для
отдельного повторного запуска адаптера есть команда:

```bash
pnpm --dir publishing build
```

Она обновляет публикационные Markdown и отчёт адаптера, но не создаёт
готовый HTML-сайт. После правок исходного Markdown или manifest повторите
эту команду: запущенный Astro dev увидит обновлённые сгенерированные файлы.
Проверьте изменение в открытой странице. После изменения конфигурации
сайта перезапустите dev-сервер.

Не редактируйте `site/src/content/docs/generated/` и
`site/generated-sidebar.mjs`: это результаты сборки. Исходные главы,
рисунки и сведения об их происхождении должны оставаться в отслеживаемых
файлах репозитория, а не только в локальном `raw/`.

## Проверки перед pull request

```bash
pnpm --dir publishing check:topics
pnpm --dir publishing test:publication
pnpm --dir site check
pnpm --dir site build
pnpm --dir publishing test:output
pnpm --dir site test
pnpm --dir publishing check:links
pnpm --dir publishing check:size
```

`site check` и `site build` вызывают адаптер через `precheck` и
`prebuild`. Тесты `test:output` требуют готовые `site/dist/`
и индекс Pagefind, поэтому запускаются после сборки. `check:links`
проверяет внутренние адреса, якоря и файлы в готовом HTML; доступность
внешних сайтов эта команда не устанавливает.

Этот набор работает после клонирования публичного репозитория. В него входят
проверки адаптера, маршрутов, оглавлений, публичных файлов изображений,
лицензионных файлов и собранных страниц. Старые изображения, для которых
контрольная сумма ещё не была записана, перечислены в историческом списке
`publishing/tests/fixtures/legacy-unhashed-assets.json`; для новых изображений
SHA-256 обязателен. Этот список не подтверждает качество рисунков или права
на их использование.

Для полной локальной сверки с сохранёнными оригиналами выполните:

```bash
pnpm --dir publishing test:unit
```

Команда сохраняет весь набор тестов, включая сравнение с исходными PDF,
HTML, кодом авторов и лицензионными снимками. Эти материалы хранятся локально
в `05 Источники/Originals/` и не добавляются в Git автоматически. Без архива
полный набор завершится ошибкой, а не пропустит проверки. Только сверку
источников можно запустить через `test:evidence`; её состав указан в
`publishing/tests/source-evidence-suites.json`.

CI запускает `test:publication` и проверки готового сайта. При изменении
объяснения или рисунка отдельно укажите в pull request, какие исходные
материалы сопоставлены и какие проверки источников выполнены. Прохождение
публичного CI не заменяет эту сверку.

При переносе материала курса также проверьте соответствующий реестр
покрытия:

```bash
pnpm --dir publishing check:source-coverage
pnpm --dir publishing check:course-ingestion
```

Эти проверки сверяют записи и связи. Они не доказывают, что объяснение
полно или что весь курс уже встроен в учебник. Содержательная приёмка,
примеры, происхождение объектов и визуальная проверка описаны в
[редакционных правилах](../.agents/references/editorial.md).

Для просмотра готовой сборки:

```bash
pnpm --dir site preview
```

На затронутых страницах проверьте формулы, изображения с подписями, ссылки
на разделы и соседние главы при обычной и узкой ширине. Для alias откройте
старый адрес и проверьте конечную главу и раздел. Успешные тесты не
заменяют осмотр страницы.

## GitHub Pages

Текущая публикация выполняется workflow
[`pages.yml`](../.github/workflows/pages.yml) при push в `dev`
или ручном запуске workflow. `verify.yml` проверяет pull request,
но само по себе прохождение PR-проверок сайт не публикует.

Workflow сначала выполняет перечисленные выше проверки сборки от корня.
`test:output` проверяет именно эту сборку: его утверждения содержат адреса
вида `/textbook/…`. Затем workflow заново собирает `site/dist/` с
`PUBLICATION_BASE_PATH=/bookvar` и проверяет ссылки уже в этом артефакте.
В Pages загружается вторая сборка.

Для локальной проверки Pages после корневых проверок выполните:

```bash
PUBLICATION_BASE_PATH=/bookvar pnpm --dir site build
PUBLICATION_BASE_PATH=/bookvar pnpm --dir publishing check:links
pnpm --dir publishing check:size
PUBLICATION_BASE_PATH=/bookvar pnpm --dir site preview
```

При таком запуске `check:links` также отклоняет внутренние ссылки,
которые выходят из `/bookvar`, даже если файл существует в `site/dist/`.
В preview откройте `/bookvar/`, проверьте переходы между главами,
переключение языка, изображения и поиск.

`check:size` считает полный размер файлов, а не размер сжатого архива,
и останавливает публикацию при превышении 1 000 000 000 байт. Полные PDF
лекций с проверенными официальными адресами открываются у авторов;
локальные оригиналы остаются для сверки. Иллюстрации и текст учебника
эта настройка не исключает. Длинные исходные программы в библиотеке
показываются без пословной подсветки; их текст и возможность копирования
сохраняются. Примеры в главах учебника сохраняют подсветку.

Оригиналы курсов без отдельной английской редакции публикуются один раз,
в исходном языке, по адресу `/sources/courses/…`. Их прежние адреса
`/en/sources/courses/…` перенаправляют прямо к оригиналу, сохраняя раздел
и параметры запроса. Оглавления курсов и настоящие английские редакции
сохраняют отдельные страницы. Это правило библиотеки не меняет русские
и английские главы нашего учебника.

После изменения текста успешная локальная сборка подтверждает только
локальный результат. Публикацию подтверждают завершившийся deploy workflow
и открытая страница с нужным изменением. В отчёте о правке разделяйте
изменённые исходники, выполненные локальные проверки и опубликованную версию.
