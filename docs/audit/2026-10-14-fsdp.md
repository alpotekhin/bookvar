## Содержательные исправления

1. Введены отдельные обозначения: количество скаляров Psi и байтовые P/G/O.
   Старая атрибуция «12 байт в CS336» была неверна: p.17 явно включает
   FP32 master weight, то есть 16 байт. Сохранена условная 12-байтовая схема
   с явными допущениями, не как дефолт Adam/FSDP2. Добавлен численный расчёт
   7B/64 процесса: 112, 29.3125, 15.53125 и 1.75 GB.
2. Объяснено, почему состояния Adam можно распределять по владельцам
   параметров; простой SGD-пример показывает локальные обновления.
   Разделено упрощённое задание CS336 с broadcast и оптимизированное
   расписание ZeRO-1.
3. Убрана безусловная фраза «полные параметры живут ровно до конца forward».
   Показаны стадии обычного full-shard, активации и асинхронное освобождение.
4. Объём all-gather весов и reduce-scatter градиентов разделён на Mw/Mg.
   Для 1B параметров / 8 процессов: BF16-веса + FP32-градиенты дают
   7 GB отправленных данных; оба BF16 — 5.25 GB. Это расчёт, не измерение.
5. Разобран пик буферов 6/8 GiB: последовательное хранение 8, перекрытие 14.
   Локальные FP32-части не приравнены к BF16-размеру / N.
   Отличаются resident state, временные веса/градиенты, workspace,
   алиасы и память аллокатора.
6. Для FSDP2 объяснены bottom-up вызовы, принадлежность параметров группе,
   создание оптимизатора после fully_shard, согласованная инициализация
   и вызов model(inputs) с необходимыми hooks.
7. Зафиксирован PyTorch 2.14 default reshard_after_forward=None:
   вложенные группы освобождают полные веса, корень сохраняет только
   собственные. Не перенесён старый limit_all_gathers в новый API.
8. Различаются original dtype, param_dtype и reduce_dtype, исходные
   FP32-шарды/градиенты/моменты и временные BF16-буферы.
   MixedPrecisionPolicy не обещает создать FP32 master weights
   для заранее преобразованной BF16-модели.
9. DeviceMesh объяснён через реальные rank-группы 2×2; имена осей не
   объявлены физической топологией или размещением DTensor.
   Shard/Replicate/Partial объяснены через данные и коллективные операции.
10. Для hybrid память делится на S, а нормировка градиентов охватывает RS.
    Добавлены полный вывод токен-взвешенной потери и исполняемая функция,
    нулевой локальный вклад, глобально пустой batch, накопление градиентов.
11. DCP сокращён до границ ответственности со ссылкой на 44g.
    Убрана гарантия переноса любого состояния на любой mesh;
    условные 1.12 TB / 200 GB/s = 5.6 s не приписываются автоматически
    checkpoint модели 70B.

## Воспроизводимые проверки

Команда из корня worktree:

~~~sh
/opt/homebrew/bin/uv run --with torch --python /Users/aleksan.potekhin/.cache/codex-runtimes/codex-primary-runtime/dependencies/python/bin/python3 python publishing/tools/check_fsdp_examples.py
~~~

Наблюдаемый результат: PASS, PyTorch 2.14.1, четыре настоящих процесса
CPU/Gloo с FileStore и ограничением времени. Все пять Python-блоков
извлекаются из текущей главы, синтаксически проверяются и исполняются.
Нет подмены fully_shard, DTensor или коллективов.

Проверены:

- Численные примеры 12/16 B, 7B/64, коммуникации, GiB-буферы,
  размещения матриц и нижняя оценка сохранения.
- Реальные rank-группы mesh2×2; локальные и восстановленные значения
  из иллюстрации EDLS; Partial→Replicate и Partial→Shard.
- Обычный 1D FSDP2 и HSDP2×2: по три шага AdamW. После каждого шага
  полные параметры, градиенты и оба момента сравнены с FP64-моделью
  на объединённом батче: atol=2e-10, rtol=2e-8.
- На процессах 0/1/2/3 учитываются соответственно 0/1/2/3 токена.
  Также проверено согласованное отклонение глобально пустого batch
  без изменения параметров.
- Два микробатча с отключённой/включённой синхронизацией:
  результат совпадает с глобальным эталоном по всему окну.
- Реальное публичное представление параметров после forward:
  вложенный блок уже DTensor, корневая проекция ещё полный Tensor.
  После синхронизированного backward параметры снова разделены.
- Реальные CPU BF16 forward-веса и входы; FP32 исходные параметры,
  конечные градиенты и моменты AdamW. Это проверка типов/исполнения,
  не проверка численного совпадения BF16 с FP32 или объёма трафика.

Первый вариант дополнительной проверки накопления неверно предполагал,
что несинхронизированный полный градиент доступен через публичный
`model.parameters().grad` после повторного шардирования. В FSDP2 он
сохраняется отдельно. Ошибочное утверждение самого теста удалено;
теперь используется публичная проверка размещения и численный результат
последующей синхронизации. Код библиотеки не менялся и не имитировался.
Окончательный полный прогон прошёл, редактор независимо повторил его.

Дополнительно проверены SHA256 исходных PDF/изображений/лицензий,
размеры PNG, сохранность восьми source_unit_id и старых якорей,
существование локальных ссылок, git diff --check для принадлежащих файлов.

## Границы доказательства

- Не выполнялись CUDA/NCCL, межузловые обмены, overlap-профилирование,
  GPU peak-memory и throughput benchmarks.
- Временное хранение несинхронизированных градиентов проверено по исходному
  коду и численному результату накопления; объём private-буфера не измерен.
- BF16-проверка подтверждает исполнение и форматы на CPU, не качество
  обучения и не характеристики конкретных GPU-ядер.
- Не запускались официальные student adapters CS336 и их test suite;
  официальные тесты прочитаны, а наш checker проверяет фактический
  публичный FSDP2 API.
- DCP save/restore, смена mesh и точное восстановление RNG/data position
  здесь не исполнялись; это область главы 44g и отдельной практики.
- UI после интеграции, общий реестр, глобальные тесты и сборка проверяются
  основным редактором. Просмотр PNG не объявляется проверкой веб-вёрстки.

Маршрут/имя главы сохранены. Сохранены явный cs336-distributed-fsdp,
все восемь source_unit_id, старые якоря peak-memory-synchronization
и контракт-корректности-custom-fsdp. Prev/next остаются 44d/44f.
